## この段階の目的

**会議に持ち込んで、キーボードだけで正常系のシナリオを打ち切れ、全ステップに「失敗したら？」の問いが立つ状態にする。**

facet の第一関門「会議のスピードに入力が追いつくか」（rev 11章）に加え、シーケンス固有の検証がある——**問いスロットの未定義表示が、会議で「考慮漏れの発見」として実際に機能するか**。問いスロットが無いとただのシーケンス図エディタであり、facet として持ち込む意味を検証できない。ゆえに logic-tree M1 より1歩広く「ステップ入力＋個別の問い」までを M1 とする。

## 含むもの（IN SCOPE）

### 1. データとファイル

- `sequence` の JSON Schema（スキーマが正、TypeScript 型は自動生成）
  - ID規約: `actor_` ／ `step_` プレフィクス ＋ 英数字62文字・10文字 nanoid（rev 5章）
  - `actors`: `{ id, name }` の配列。**配列順＝横の並びの正本**
  - `steps`: `{ id, kind, from, to?, label, awaitsReply?, failures? }` の配列。**配列順＝時系列の正本**
  - `kind`: `call` | `reply` | `self`。`self` は `to` を持たない。`awaitsReply` は `call` で必須・他で禁止
  - `failures`: 固定キー `failed` ／ `unknown`（内に `ifExecuted`）。スロット値は `{ decision: "handled" | "notApplicable", text }`（`handled` は `text` 必須）。**キー欠落＝未定義**
  - スキーマの `description` に「原因（エラー応答・接続不能・タイムアウト等）は列挙せず、答えの文中に書き分ける」を明記（AI への規律）
  - `schemaVersion` は `const: 1`
- エンベロープ（`type` / `schemaVersion` / `title`。既存モジュールと同形式）
- `singleton: false`、`outputs: []`、マイグレータの枠（初版につき恒等）
- **二段検証**
  - レベル1（スキーマ検証→拒否）: 構造・ID形式・enum・`handled` の `text` 必須
  - レベル2（整合性検証→受け入れて赤表示）: ①`from`/`to` の参照切れ ②ID重複（actor/step 各々） ③**立っていない問いへの答え**（導出テーブル外のスロットが埋まっている。エラー文言は「どの属性のせいで立たないか」まで言う） ④`self` なのに `to` がある／`call`・`reply` なのに `to` が無い
  - **`failures` のキー欠落は検証エラーではない**（未定義＝warning 表示のみ。赤と warning の強度差は既存規約に乗る）

### 2. 問いの導出（このツールの心臓部）

- `(kind, awaitsReply) → 立つ問いの集合` を返す**純関数**を `src/modules/sequence/` に置く（コアに置かない）
- 導出テーブルと問いの文言は [`sequence-design-notes.md`](sequence-design-notes.md) 論点3 が正
- reply 行のガターには一般文言「─ 応答の失敗は呼出側の『結果不明』が扱う」を薄く表示（空白にしない）

### 3. キーボード操作（rev 10章の階層・リスト系ファミリー標準、`hierarchical: false`）

- `Enter` = 直後にステップ追加。既定値: `from`＝前ステップの `to`、`kind: "call"`、`awaitsReply: true`
- `Tab` = セル間移動（from → to → kind/awaitsReply → ラベル → 答えスロット群、実機フィードバックで改訂。レール配置ではレール→図→ガターの視覚順が正。初期フォーカスはラベルのまま）
- `Alt+↑↓` = ステップ並び替え ／ 空欄で `Backspace` = ステップ削除
- `Alt+←→` = アクターの並び替え（ヘッダにフォーカスがあるとき）
- from/to セル: 頭文字インクリメンタル一致＋`↑↓` 候補切替。**未登録名の確定でその場で `actors` に追加**
- 答えスロットの3状態（未定義／handled／notApplicable）を**キーボードだけで行き来できる**こと（具体割当は実装時に決めてよいが、グローバル層・ファミリー標準との衝突禁止）
- `Esc`・`Ctrl+Z`/`Ctrl+Shift+Z` はグローバル層（額縁）のまま
- **IME 対応**: 変換確定の Enter がステップ追加に誤爆しないこと（`CellInput` を使う）
- 実装は共通フックに一元化（`src/core/keyboard/`）。**`←→` が `arrowsOwnedByField` を見ない件（open-issues 記載）は、from/to という select 系フィールドを持つ本ツールが最初に踏むため、この M1 で解消する**

### 4. 表示

- **測定層**: オフスクリーン `measureText`・同期・フォントトークン同一参照（logic-tree の方式。DOM 非依存＝ユニットテスト対象）
- **レイアウト層**: `(actors, steps, サイズマップ) → 座標Map` の純粋関数。X＝actors 配列順（列間隔は区間を跨ぐ矢印ラベルの最大幅から導出・最小間隔あり）、Y＝steps 配列順（行高＝max(ラベル高, ガタースロット群の高さ)）。スナップショットテスト対象
- **描画層**: 3レイヤ（背景＝ライフラインの縦線／エッジ＝SVG 矢印／ノード＝DOM）。矢印の形は導出（実線塗り矢頭・実線開き矢頭・破線開き矢頭）。self はライフライン上のボックス
- **ガター**: キャンバス内・図の右端。スロットセルの色は 未定義＝warning の面／handled＝ok 系／notApplicable＝弱い ok 系（具体は既存トークン規約に従う）。上部に「⚠ 未定義 N ／ ✓ 回答済 N ／ ─ 考慮不要 N」の集計
- **ビューポート**: d3-zoom（logic-tree の `useViewport` と同じ構成。`enabled` でモーダル中に停止）。新ステップへの自動追従パン
- 空状態: キャンバス中央の「クリックして開始」で最初のアクター＋最初のステップを作る動線（詳細は plan で設計。キーボードだけで開始できない状態を作らない）

### 5. 完了条件（動作で判定する）

1. 空の状態から、**会議1回分のシナリオ（アクター3〜6・ステップ15〜30）をキーボードだけで打ち切れる**
2. **日本語入力で、変換確定の Enter がステップ追加に誤爆しない** ← 最重要
3. 全ステップに導出どおりの問いが立ち、**未回答が warning、notApplicable が区別されて見える**
4. アプリを閉じて開き直すと、同じシーケンスが同じ形で出る
5. `Ctrl+Z` が期待どおり戻る（1操作1コミット）
6. 測定層・レイアウト層・問い導出関数のユニットテストが通る

**2 が通らなければ M1 は未完とする。**

## 含まないもの（OUT OF SCOPE）

### ゾーン（M2 の担当）

- `zone_` エンティティ、ステップ範囲への答えの束ね、背景レイヤの帯描画、範囲選択 UI

### マウス操作の一切

- ドラッグでのステップ並び替え・アクター並び替え、ホバーの「+」ハンドル、右クリックメニュー、矩形選択・複数選択、複製
- `Ctrl+C` / `Ctrl+V` に他の意味を割り当てないこと（logic-tree と同じ申し送り）

### 出力・連携

- Markdown / Mermaid 出力、クリップボード、.md 書き出し（`outputs: []` で開始）
- `errorRefs`（エラーカタログ参照）、`replyTo`、用語集参照（`term_`）
- 検索・フィルタ

### 表示の作り込み

- レイアウト変更時のアニメーション（M1 は瞬間移動でよい）
- アクターヘッダのスクロール固定、ガター集計の作り込み

### 禁止事項

- **`core/canvas` 等への共通化・抽象化を行わないこと。** logic-tree と重複するコードが出ても素直にシーケンスの中に書く（重複は記録する）。一般化は2本目完成後の別マイルストーン（rev4 の手順）。既存コア（`src/core/keyboard/`・`CellInput`・`list-ops` 等）の**利用**は当然行う
- **座標・幅・表示状態をデータ（JSON）に入れないこと**
- **キャンバスライブラリ（React Flow / tldraw / elkjs / dagre）を導入しないこと**（検討済み不採用。logic-tree tech-notes 論点2）
- **問いの類型をユーザーが増やせる機構を作らないこと**（設計の中核。design-notes 論点3）
