## 論点1: 異常系の表現（確定：問いと答え方式）

**決定**: 異常系（失敗時の挙動）の**流れを矢印で描かない**。図は正常系の骨格のまま保ち、各ステップが「ここで失敗したら？」の**問いのスロット**を持つ。未回答＝warning（未定義）、「考慮不要と決めた」＝ok——rev 3章「未定義と決めた上で無効を型で区別」がそのまま乗る。

**経緯**: 旧プロトタイプは失敗ゾーンをステップ範囲の帯（範囲＋失敗時挙動1つ）として図に重ねていたが、作者自身から2つの懸念が出た。

1. **視認性**: 帯が図に重なるとノイズになり、ゾーンが増えるほど正常系が読めなくなる
2. **シーケンス図は正常系前提**: 異常系を矢印で描き足すと図が爆発する（UML の alt/opt が読みにくい理由そのもの）

ここで「ここで失敗したらどうなる？を表現したい」という元の動機を見直すと、**価値は異常系を描写することではなく、答えていない箇所を可視化すること**にある（rev 3章「決めていないことを消せなくする」）。遷移表の赤セルのシーケンス版、というのがこのツールの正体である。

**退けた代替案**:

- **分岐フロー描画方式**（UML の alt/opt のように失敗の流れも矢印で描く）: 図が爆発し会議中の入力も遅くなる。上記懸念を正面から抱え込む
- **ゾーンのみ方式**（プロトタイプ通り、描いた範囲だけが失敗時挙動を持つ）: 強制がないので「考慮していないステップ」が可視化されず、網羅性の担保という中核価値が乗らない

## 論点2: 問いの粒度（確定：ステップ単位＋ゾーンで束ねる）

**決定**: 全ステップが問いを持つのが基本。ゾーン＝**連続するステップ範囲に1つの答えを与える束ね手段**（「この区間のどこで落ちても同じ扱い」——トランザクション境界の実務感覚）として後続マイルストーン（論点12。当初 M2 予定）で導入する。プロトタイプのゾーンはこの形で生き残る。

ステップ単位のみ（束ねなし）は「この区間は全部同じ」をステップ数ぶん書く重複を生み、ゾーン単位のみ（全ステップがゾーン所属必須）は1ステップだけの例外にもゾーンを切らせて会議中の入力を重くする。

## 論点3: 問いの類型（確定：知識状態で閉じる）

### 1答では足りない

「失敗したら？」に自由記述1答だと**「何か書けば緑」**になる。NG応答の対応だけ書いてタイムアウトを忘れていても、ツールからは回答済みに見える——網羅の担保が書き手の注意力に戻ってしまう。問いの類型を固定すれば、ツールが「結果不明のときは？」を**必ず立てる**ので、書き漏れが赤として残る。

### ユーザーに類型を作らせない

ユーザーがステップごとに類型を増やせる設計（自由なモードリスト）にした瞬間、「問いのセットが完成しているか」をツールが判定できなくなり、網羅の担保が消える。類型は**スキーマの固定キー**であり、どの問いが立つかはステップの意味属性から導出する。

### 類型は「原因」ではなく「呼び手の知識状態」に立てる

原因（エラー応答・接続拒否・DNS失敗・タイムアウト・応答消失…）を列挙し始めるとキリがない。落としどころは軸の変更である。呼び手が観測できる知識状態は論理的に3つしかない：

1. **成功と分かった** → 正常系。図そのものが担当
2. **失敗と分かった**（`failed`）→ エラー応答も接続拒否も送信不能も全部ここ。「実行されなかった／失敗したことが**確定**している」
3. **分からない**（`unknown`）→ タイムアウト、応答消失、相手のハング。「**実行済みかもしれない**」

応答は「来る（成功か失敗）」か「来ない」しかないので、この分割は**構造的に閉じている**。新しい例外を思いついたら「失敗が確定しているか？結果不明か？」の一問で必ずどちらかに落ちる。類型が増えるのは第4の知識状態が見つかったときだけで、それはまず起きない。

そして原因の違いが対応に効く唯一のポイントが「相手が実行済みかもしれない」であり、それが `unknown` の下位問い **`ifExecuted`（実行済みだったら？）** である。リクエスト消失なら未実行確定＝安全にリトライ、応答消失なら実行済み＝冪等性が要る——呼び手には見分けられないから、必ず問う。`ifExecuted` は `awaitsReply: true` なら**境界（domain）に関係なく常に立つ**（自社内の非同期でも状態不明は起きる）。

**原因の書き分けは答えの自由記述の仕事**。「与信NGなら画面にエラー、接続不能なら1回だけ再試行」のように、そのプロジェクトで対応が分かれるぶんだけ文中に書く。**閉じたものは型に、開いたものは文に。** スキーマの `description` にもこの規律を明記し、AI（Skill）にも同じ線引きを効かせる。

### 導出テーブル

| ステップ | `failed` | `unknown` | `unknown.ifExecuted` |
| --- | --- | --- | --- |
| `self`（内部処理） | ✓ 処理失敗したら？ | ─（実行者自身に不明は無い） | ─ |
| `call` + `awaitsReply: true` | ✓ 失敗が確定したら？ | ✓ 結果不明だったら？ | ✓ 実行済みだったら？ |
| `call` + `awaitsReply: false` | ─（観測しないので確定しない） | ✓ 届かなくてよいか？ | ─（未実行こそがリスク。下位問い不要） |
| `reply` | ─ | ─ | ─ |

- キーは2つ（＋下位1つ）だが、**問いの文言はステップ種別ごとに変える**（表のとおり）
- 導出は `src/modules/sequence/` 内の**純関数**に置く（コアではない。rev 6章の責務分担——3本目のツールが問いスロットを欲しがったら、そのとき初めてコアへ引き上げる）
- 投げっぱなし（`awaitsReply: false`）が1問なのも同じ原則の帰結：応答を観測しない以上、知識状態は常に「不明」一色
- **スキーマに問いを足すと過去ファイル全部に赤が生える**（新キーが全ステップで欠落＝未定義になる）。これは欠陥ではなく機能——考慮漏れの検出が過去の仕様書に遡って効く。schemaVersion 改訂＋マイグレータで行う

### reply に問いを立てない（二重計上の防止）

「応答が届かない」は対になる呼出側の `unknown` が、「応答がエラー」は呼出側の `failed` が既に問うている。reply にも問いを立てると同じ考慮を2箇所に書かせることになり、答えが食い違ったときどちらが正か分からなくなる。

- reply 行のガターには一般文言「─ 応答の失敗は呼出側の『結果不明』が扱う」を薄く表示する（空白だと「ツールの問い忘れ」と見分けがつかない）
- どの呼出かの**名指しはしない**——`replyTo` フィールドは M1 では持たない。対応関係の明示（ホバーで対の呼出をハイライト等）が欲しくなったら実使用後に判断

## 論点4: データモデル（確定）

```jsonc
{
  "schemaVersion": 1,
  "type": "sequence",
  "title": "注文確定（在庫あり）",

  "actors": [
    { "id": "actor_Xp2mQ9rT4k", "name": "画面", "domain": "自社" },
    { "id": "actor_Bv7nW3jL8s", "name": "API",  "domain": "自社" },
    { "id": "actor_Kd4hR6yU1c", "name": "決済", "domain": "決済会社" }
  ],

  "steps": [
    {
      "id": "step_Ab3xK9mP2q",
      "kind": "call",              // call | reply | self（矢印の形の分類）
      "from": "actor_Bv7nW3jL8s",
      "to": "actor_Kd4hR6yU1c",
      "label": "与信依頼",
      "awaitsReply": true,         // kind: call のとき必須（明示させる）
      "failures": {
        "failed":  { "decision": "handled", "text": "画面にエラー表示して中断" },
        "unknown": {
          "decision": "handled", "text": "リトライする",
          "ifExecuted": { "decision": "handled", "text": "取引IDで冪等性を担保" }
        }
      }
    }
  ]
}
```

- **配列順が正本**（rev 5章）: `actors` の配列順＝横の並び（左→右）、`steps` の配列順＝時系列（上→下）。座標・行番号・幅は持たない
- **ID プレフィクス**: `actor_` ／ `step_`（ゾーン導入時に `zone_`）。英数字62文字・10文字 nanoid（rev 5章）。レジストリの重複検査対象
- **`domain` は任意**。隣接する参加者間で `domain` が異なる位置に**境界線を描く**（導出。境界そのものはデータに持たない）
- **`failures` のキー欠落＝未定義（warning）**。正規化で欠落キーを補完しない（欠落こそが「まだ決めていない」の表現）
- スロット値は `{ decision: "handled" | "notApplicable", text }`。`handled` は `text` 必須（何が起きるか）、`notApplicable` は任意（理由をメモできる）
- `kind: "self"` は `to` を持たない。`kind: "reply"` は `awaitsReply` を持たない
- **`label` の明示改行は許容し永続化**（logic-tree 論点7 と同じ扱い）
- `singleton: false`（機能ごとにシーケンスを分けるのが普通の使い方。ハブではない）
- 用語集参照（`term_`）は初版に入れない（logic-tree M1 と同じ判断）

### `crossesBoundary` をステップに持たない理由

検討過程で「ステップに `crossesBoundary` を明示する」案があったが、**境界跨ぎはメッセージの属性ではなく参加者のトポロジーの属性**である。ステップごとに持つと (1) 同じ参加者ペア間で値が食い違える（意味を成さない状態がデータとして書ける）、(2) 参加者の帰属から導出できる情報の複製（rev 3章「正となるデータは一つ」に反する）、(3) 参加者を他社に変えたとき全ステップの追従修正が要る。`from.domain !== to.domain` で毎回導出する。

なお `ifExecuted` を境界に関係なく常に立てると決めたため、**境界は問いの導出に一切関与しない**。`domain` の用途は境界線の描画のみ（「時系列＋責任境界」の看板は描画で残る）。

## 論点5: エラーカタログとの関係（確定：設計だけして後回し）

エラーカタログの `occurrence` は「参照している側（シーケンスの失敗ゾーン）から逆引きして導出すべき」と error-catalog セッションで既に予定されている。本設計はその受け口を**スロット粒度**で用意する：

- 将来、各スロットに `errorRefs`（`error_` 参照の配列、0..n）を足す。類型1つ ⇔ エラー0..n件の対応
- 効果は双方向：シーケンス側は答えの実体をカタログに寄せて二重管理を防ぎ、カタログ側は `occurrence` の逆引き導出と**幽霊エラー**（どこからも参照されないエラー）の検出を得る
- **参照は答えの唯一の形にはしない**。「リトライで透過回復、ユーザーには見えない」のようにカタログに載る「エラー」ではない答えが実在するため、自由記述が基本で参照は任意の添え物
- M1 に入れない理由: クロスファイル参照機構は用語集向けですら未実装（logic-tree M1 も用語参照を外した）。インライン登録は open-issues 記載の `ensureFileOfType` 競合を踏む。「手入力→導出」の移行は schemaVersion 改訂＋マイグレータで舗装済み

## 論点6: 分岐の扱い（確定：直列に徹する）

1ファイル＝1本の直列シナリオ。正常系の条件分岐（在庫あり／取り寄せ等）はシーケンスを別ファイルに分ける（rev 5章が「機能ごとにシーケンスを分ける」を想定済み）。**分岐の網羅はロジックツリーの担当**という役割分担。ステップの文言に「（在庫ありの場合）」と書くのは自由。

alt/opt フラグメント（入れ子分岐ブロック）は採らない——データモデル・レイアウト・キー操作の全部が一気に複雑化し、「問いと答え」の未定義可視化も分岐ごとに分裂する。

## 論点7: 表示（確定：キャンバス内ガター）

**決定**: 問いのスロット列を**キャンバス内の図の右端**に、各ステップ行と同じ高さで並べる（ガター）。ズーム・パンと一緒に動く。

**根拠**:

1. 行と答えが同じ高さで並ぶので **Tab の入力動線が一直線**
2. ズームアウトすると文字は読めなくなるが赤の分布だけが残り、**「考慮漏れヒートマップ」**として会議の投影で機能する
3. 図の本体（正常系）には1文字も混ざらない

**退けた代替案**: 固定サイドパネル（ズーム非依存で常に読めるが、視線とフォーカスが図とパネルを往復し、行との対応もハイライト頼み）／矢印の下にインラインチップ（対応は一目瞭然だがプロトタイプの帯と同じ視認性問題を引き継ぐ）。

**画面の全体像**（editor-vision モックで確認済み）: 問いの数がステップの意味から決まるため、応答を待つ呼出は3スロット、内部処理は1スロット、応答はゼロ——**問いの数自体が「このステップの失敗の考えどころの数」を語る**。ガター上部に「⚠ 未定義 N ／ ✓ 回答済 N ／ ─ 考慮不要 N」の集計を出す。

## 論点8: レイアウトと描画（確定：logic-tree の構成を踏襲）

rev 10章「全キャンバス系ツール共通」の構成に乗る。キャンバスライブラリ不採用の判断も含めて [`../logic-tree/logic-tree-canvas-tech-notes.md`](../logic-tree/logic-tree-canvas-tech-notes.md) 論点2〜4 を引き継ぐ。

- **自動レイアウト**。レイアウト関数は `(actors, steps, サイズマップ) → 座標Map` の**純粋関数**（スナップショットテスト対象）。ツリーの Reingold–Tilford のような再帰は不要で、X・Y とも単純な積み上げで済む
- **3レイヤ**: 背景レイヤ（**境界線**。ゾーン導入時はその帯もここ——logic-tree が枠だけ確保していた層が初めて使われる）／エッジレイヤ（SVG: 矢印）／ノードレイヤ（絶対配置 DOM: 参加者ヘッダ・ステップラベル・self ボックス・ガターのセル。いずれも編集対象なので `CellInput` が載る DOM 側）。3レイヤに同一 transform
- **X軸**: `actors` 配列順。**列間隔は、その区間を跨ぐ矢印ラベルの最大幅から導出**（最小間隔あり）。ラベル幅は測定層（オフスクリーン `measureText`。測定と描画は同一フォントトークン参照——rev 9章の確定事項）
- **Y軸**: `steps` 配列順。**行高 = max(矢印ラベルの高さ, ガターのスロット群の高さ)**
- **矢印の形は導出**: `call`+待つ＝実線・塗り矢頭／`call`+待たない＝実線・開き矢頭／`reply`＝破線・開き矢頭。UML 慣習に一致し、Mermaid の `->>` `-)` `-->>` にも将来そのまま写る
- ガターの x 位置＝参加者列の右端＋マージン（導出）
- レイアウト変更のアニメーションは M1 では無し（瞬間移動。logic-tree M1 と同じ）
- 表示上の折り返しは測定層が確定し、データの明示改行と混同しない（logic-tree 論点4・7）

## 論点9: 操作言語（確定）

**`KeyContext.hierarchical: false`**——シーケンスはフラットなステップ列で「子」という意味を持たない。Tab はファミリー標準どおり**セル間移動**（用語集と同じ側）。

- **Enter** ＝ 直後にステップ追加。既定値: `from` ＝ 前ステップの `to`（会話は続くものだから）、`kind: "call"`、`awaitsReply: true`（最頻値。トグルで変える方が打鍵が少ない）
- **Tab** ＝ from → to → kind/awaitsReply → ラベル → 答えスロット群、と右へ移動（実機フィードバックで改訂。レール配置ではレール→図→ガターの視覚順が正。初期フォーカスはラベルのまま）
- **Alt+↑↓** ＝ ステップの並び替え（配列＝時系列の正本を直接編集）
- **空欄で Backspace** ＝ ステップ削除。Esc・Ctrl+Z 系はグローバル層のまま（額縁が握る）
- **from/to の入力**（**sequence M3 で反転**。旧: 頭文字のインクリメンタル一致＋`↑↓` で候補切替のコンボ的セルで、未登録の名前を打って確定するとその場で `actors` に追加していた）: **選択専用のドロップダウン**（マウス）＋ **`↑↓` で `actors` 配列順の即時切替**（キーボード）。**インライン作成は廃止した**。参加者を作る経路は「ヘッダの `Enter`」と「ツールバーの『参加者を追加』ボタン」の2本に一本化した
  - **反転した理由**: 実使用の観察で、補完（インクリメンタル一致）の出番が少なく、その場で参加者を作る必要も無かった。M1 の実機確認チェックリスト自体が「『決』＋Enter で参加者『決』ができる挙動」を危険として見に行っており（[`../history/sequence-m1-keyboard-editor.md`](../history/sequence-m1-keyboard-editor.md)）、この整合を取った形になる。詳細は [`../history/sequence-m3-mouse-and-output.md`](../history/sequence-m3-mouse-and-output.md)「M1 の確定事項2件を反転した」
- **参加者の操作**: ヘッダも `CellInput` で改名可。並び替えは **Alt+←→**（横並びのリストなので、ファミリー標準 Alt+↑↓ の方向を回転しただけ。新キーの発明ではなく拡張規則の範囲）
- **答えスロットの3状態**（未定義／handled／notApplicable）は**キーボードだけで行き来できること**を要件とする。具体のキー割当は実装時に調整（デファクトが無い領域なので、設計段階で発明を確定させない）
- 新ステップへの自動追従パン、ズーム・パンは d3-zoom でキーボード経路なし——logic-tree M1 の判断を踏襲
- 答えスロットは飛ばしてよい——赤が残ることが「あとで決める」の記録になる。正常系を打ち切ってから赤を上から潰す会議の進め方を想定する

**既知の地雷（実装計画に含めること）**: open-issues「`←→` が `arrowsOwnedByField` を見ないのに、コメントは『↑↓ と同じ規則』」は、**select 系フィールド（from/to/kind）を持つツールが現れた瞬間に踏む**と明記されている。シーケンスがその1本目になる。

## 論点10: 検証（確定）

**レベル1（スキーマ検証。不合格＝開けない）**: 構造の正しさのみ。`type`／`schemaVersion`／ID形式（`^actor_[A-Za-z0-9]{10}$` 等）／enum 値／`decision: "handled"` に `text` 必須、など。

**レベル2（整合性検証。受け入れて赤表示）**——シーケンスモジュールの提供物:

1. **参照切れ**: `from`／`to` が `actors` に実在しない（logic-tree の `missing-parent` に相当）
2. **ID重複**: `actor_`／`step_` それぞれ
3. **立っていない問いへの答え**: 導出テーブルに無いスロットが埋まっている（例: `awaitsReply: false` の `failed`、`reply` の `failures`）。エラー文言は**どの属性のせいで立たないかまで言う**（「ID が重複しています」だけでは直し方が読めなかった logic-tree の教訓）
4. **`self` なのに `to` がある／`call`・`reply` なのに `to` が無い**: 構造として読める限りレベル2で受ける（レベル1拒否は修正に外部エディタを強いるため）

**未定義（`failures` のキー欠落）は検証エラーではない**——正常な「まだ決めていない」状態で、warning 色の表示のみ。エラー（赤）と未定義（warning の面）の強度差は用語集・エラーカタログの規約（rev 9章）に乗る。

## 論点11: 出力（確定：sequence M3 で実装済み）

M1 は `outputs: []` で開始（rev 6章の「0本以上」規約。額縁が無改修で受けることは logic-tree M1 で実証済み）。着手条件だった rev 11章「会議で使うと確定してから」を満たし、**sequence M3 で以下を実装した**（`src/modules/sequence/markdown.ts` / `mermaid.ts` / `output-labels.ts`）:
