# 仕様整理ツール詰め合わせ：全体方針ドキュメント

全ツールに共通する設計判断の「正」。個別ツールの詳細仕様は `docs/<tool>/` にある。

## 1. 背景と目的

文字だけの仕様書は、分岐・時系列・状態・用語という多次元の情報を一次元の文章に直列化している。読むたびに脳内でグラフ構造を再構築することになり、ワーキングメモリを消耗する。

これを解くため、「人間は構造化されたUIで入力し、ツールが網羅性の担保・描画・構造化テキスト出力を担う」会議用ツール群を作る。利用者は作者本人と、**ツールの利用者として設計に含める AI（Claude）**である（4章）。

普及戦略は、会議で実際に使う姿を見せることを最良のデモと考える。狙いは、PdM とエンジニアが共に読める「中間言語」としての価値である。

## 2. ツール一覧

**ツールは増える前提**で作り、追加を「コアの改修」ではなく「モジュールの追加」で済ませる規約を6章に定める。

1. **ロジックツリーエディタ** — 分岐・パターンを網羅する木を作る。（エディタ・登録 Skill・Markdown 出力・Miro のマインドマップとのクリップボード交換まで実装済み）
2. **シーケンスエディタ** — 時系列の直列シナリオと、全ステップに立つ「失敗したら？」の問いを扱う。異常系は矢印で描かず、呼び手の知識状態で閉じた問いのスロットとして立てる。（エディタ・登録 Skill・Markdown 出力まで実装済み。詳細は [`sequence/sequence-design-notes.md`](sequence/sequence-design-notes.md)）
3. **状態遷移エディタ** — 状態×イベントの網羅とテスト導出を行う。（未実装）
4. **用語集エディタ** — 用語の型定義と表記ゆれ検知を担う、他ツールが参照するマスタデータ。（エディタ・登録 Skill・Markdown 出力まで実装済み。詳細は [`glossary/session-notes.md`](glossary/session-notes.md)）
5. **エラーカタログエディタ** — エラーの一覧と対応方法を整理する。読み手も出力先も他ツールと異なるので独立モジュールとする。（エディタ・登録 Skill・Markdown 出力まで実装済み。詳細は [`error-catalog/error-catalog-session-notes.md`](error-catalog/error-catalog-session-notes.md)）
6. **課題ツリーエディタ** — PoC で「試さないと分からないこと」を分解し、仮説と検証の結果を記録する。仮説の判断は未決・支持・棄却・保留・見送りの5語で、未決は判断イベントが0件であることから導出するため保存しない。（エディタ・登録 Skill・俯瞰の表現まで実装済み。出力は未実装。詳細は [`issue-tree/仮説検証モジュール-設計ノート.md`](issue-tree/仮説検証モジュール-設計ノート.md)）

**PRD のような自由記述中心の文書はツール化の対象にしない**（構造化度が低く、会議速度で入力して下流の仕様から指される形にならない）。課題ツリーがこの理由に当たらないのは、「課題 → 仮説 → 検証 → 結論」という構造がもともと存在するからである。

既存のプロトタイプ（`.jsx` 4本）はイメージ確認用であり、データ構造・実装とも実用版には引き継がない（5章・7章）。引き継ぐのは、UI・操作の実装差が観察されたという教訓だけである。

## 3. 全ツール共通の設計思想（変更する場合は理由を明記すること）

**入力速度最優先。** 会議の議論は秒単位で流れ、入力がもたつくと「後でまとめよう」となってツールは使われなくなる。共通の操作言語（10章）で全ツールの操作を揃え、AI活用（4章）で入力そのものを省略する方向へ拡張する。

**網羅性の担保はツールの仕事。** 未定義・未決定の箇所が物理的に見える構造にする（ツリーの葉数バッジ、遷移表の赤セル、用語チェックの赤ハイライト）。機械的チェックの上に、どの未定義が実務上危ないかというAIの意味的チェックを重ねる（4章）。

**「未定義」と「決めた上で無効」を型で区別する。** 文章仕様書ではどちらも「書いてない」に潰れる。デザイン上もこの区別を色の意味論として維持する（9章）。

**正となるデータは一つ。図は導出。** 状態遷移エディタが典型で、編集できるのは表だけ、図は自動生成の読み取り専用にする。この思想はDB不採用の判断（5章）、読み手ごとの出力の出し分け（6章）、キャンバスの配置方式の判断基準（10章）にも適用する。

**状態も導出する。** 導出元のない手動ステータスは更新忘れで嘘をつくため、ミュータブルな状態フィールドをデータに持たず、イベント列の最新要素から毎回導出する。祖先の見送りによる配下の警告抑制のような派生状態も、同じ理由で保存しない。

**構文は人に覚えさせない。構文は交換形式である。** 人間は直感的UIで入力し、ツールが Markdown / Mermaid を吐く。スキーマ定義された JSON は出力にとどまらず AI との双方向の交換形式であり、人間には見せず機械同士は構造化データで話す。

## 4. AI活用方針

### 基本構造：AIはアプリの外で動き、接点はファイルのみ

- AI（Claude）はアプリに組み込まない。**APIの呼び出し・アプリ内AI機能は作らない。**
- ただしAIを起動する場所は提供する。facet は端末のホストであって、AIの対話相手ではない。
- 判断基準は「**Claudeの出力を読んで何かを決める**」実装が現れたら原則の違反、というもの。端末タブの名前を会話内容から付けないのはこの帰結。
- 端末ペインへ渡すのはファイルの参照文字列（`@相対パス`、プロジェクト外なら絶対パス）だけ。渡す口は、選択中ファイルを開いたとき・一覧の `@` ボタン・ドラッグ＆ドロップの3つ。
- **facet はファイルの中身も会話の内容も読まない。** 「Claudeに渡す前に中身を見て何かを決める」も作らない。
- AIは Claude Code / Claude Desktop 上で動き、フォルダ内のJSONを直接読み書きする。責務は「アプリ＝人間用の高速エディタ＋検証器＋描画器、AI連携＝Skill群という別の成果物」と分ける。
- **MCP的な書き込みツールは作らない。** ファイル直書き経路は塞げず二段検証は結局要るので、経路の多重化と第三の成果物を足すだけになる。

この構造はスキーマの自己記述性・二段検証・プロジェクト＝フォルダ（いずれも5章）に支えられている。

### Skill群：AIを対話的な共同作成者にする

用途は4つ。ヒアリングしながらデータを組み立てる対話的データ作成（登録 Skill）、会議メモや文章仕様書からの下書き生成、網羅漏れ・到達不能状態・優先度のレビュー、ルールベース照合の上にAI層を重ねる用語チェックの二層化である。**AIが担うのは「どの未定義が危ないか」。**

**Skill には2種類ある。** 登録 Skill はプロジェクトフォルダの JSON を作り、接点はファイルだけという構造に乗る。`palette-retheme` はアプリ自身のソース（`src/styles/palette.css`）を触る側で、検証はアプリのテストが行う。

#### 同梱スクリプト

ID捏造・不正データの予防として、各Skillに ID採番と書き込み前検証のスクリプトを同梱する。

- ID採番は英数字62文字・10文字の nanoid（5章）。**手順書に「IDは必ずこれで採番せよ」と明記する。**
- 各 Skill は `schemas/<名前>.schema.json` に原本のバイト一致コピーを持ち、一致をテストで強制する。**配布されるのは `.claude/skills/` だけで、リポジトリの `schemas/` は出荷先に届かないため。**
- スキーマの差し替え経路（引数・環境変数・上向き探索）は持たない。検証は ajv の standalone 生成物に焼き付いており、差し替えても効かない。

#### アプリのロジックを Skill と共有する標準

同梱 Skill はコピーされて実行されるので実行時に `src/` は無く、手で複製すると追従漏れが残る。したがって**値 import を持たないファイルに限り、原本からビルド時に `.mjs` を生成して同梱する。**

- 生成は `scripts/gen-skills.mjs` が型注釈を落として `.claude/skills/<skill>/scripts/generated/` へ書き出す。契機は `pretest` / `prebuild` / `predev` / `prepare` で、生成物は追跡しない。
- 原本の制約は「値 import・相対 import・消去できない構文を持たない」。遵守は `scripts/gen-skills.test.mjs` が検査する。
- どの Skill がどの共有ソースを要るかは手書きの表 `SKILL_SOURCES` で宣言し、**`BUNDLED_SKILLS` から導出しない**（導出は恒真式になる）。
- 変換の健全性は**出力の一致**で見る。生成物を import してアプリ側と同じ結果を返すこと、CJS の `require(` が残らないことを確かめる。
- **JSON Schema だけは生成の対象ではない**（実行時にそのまま読む JSON だから）。
- 共有している原本は `src/core/canonical.ts` と、ツール固有の導出3本（`src/modules/sequence/questions.ts`、`src/modules/issue-tree/derive.ts`、`src/core/canvas/flat-tree-core.ts`）。原本がどの層にあるかは要件ではない。
- **新しいツールの登録 Skill では導出ロジックを手で複製せず、この形に寄せる。** 導出ロジックは制約の下で書き、同梱予定である旨と制約を原本の JSDoc に書いておく。
- **予定が立っていないファイルを共有したくなったら、原本を曲げず、共有が要る部分を純粋な下層として切り出す**（`flat-tree-core.ts` がその形）。
- 書き出しスクリプトが配列順を正規化するかは、並べ替えロジックを共有できるかで決まる。共有できれば持たせ、できないツールは配列順を触らない。
- **整合性と未記入の報告は「アプリが開くことになるファイル」の並びで行う**（警告は配列位置でノードを指すため）。契約は「出力を `--check` へ戻したら同じ位置を同じ言葉で言う」。

#### 共有できないロジックは実行結果の突き合わせで縛る

整合性検証（`src/modules/<tool>/consistency.ts`）は値 import を持つため同梱できず、各 Skill の書き出しスクリプトが判定ごと手で複製している。

- 縛りは実行 smoke テスト。書き出しスクリプトを `--check` で spawn し、アプリ側の `message` が stdout に逐語で現れることを検査する。
- **契約は「アプリの message が現れること」**で、独自の警告を足すのは妨げない。複製は消えないので `consistency.ts` の改訂には各スクリプトの書き替えが要る。
- 縛りは `rule` 名の集合だけでなく `message` の件数にも掛ける（同じ `rule` を2箇所で出すツールがある）。
- 導出ロジックを共有している Skill では、集計結果の逐語一致も併せて固定する（`message` の一致は共有物が空でも通る）。

#### Skillの配布と同期

同梱 Skill はアプリの resources に入っており、**プロジェクトフォルダを開いたときに1回**（端末タブを開くたびではない）`.claude/skills/` へ置き直される。

- 同梱物をすべて読み終えてから消す。読み出しに失敗すれば何も消さない。
- 読み出しは `node_modules` へ降りない（`src/core/skill-sync.ts`）。非 UTF-8 な依存が1つ混じるだけで読み出しごと throw するため。
- 消すのは同梱する名前のディレクトリの中身だけで、ユーザーが足したSkillも `node_modules` / `package-lock.json` も消さない。
- **消せない要素が1つあっても中断しない**（1件の消し残しより Skill 全体を失うほうが重い）。
- `.gitignore` は同期対象に含める。mac ではこれを書くために `allow_skill_dir`（`src-tauri/src/lib.rs`）が要る（7章）。
- Skill群は正式な成果物としてバージョン管理し、**スキーマ変更時はSkillも追従させる。**

### 読み方ガイド：静的な README-for-AI.md を配る

「空欄・`undecided` は未決の意思表示であり埋めてはいけない」といったJSONに書かれていない読み方の規約は、ユーザーのフォルダには無い。これを、**AIがフォルダを読みに行った瞬間に目に入る静的な配布物**として配る。

- プロジェクトフォルダ直下に `README-for-AI.md` を置く。原本は `src/core/reading-guide.md`。
- 原本はTauriのresourcesではなく Vite の `?raw` importでバンドルへ取り込む（二重管理を増やさないため）。
- フォルダを開いたときにべき等に書き出す（無ければ作る／一致していれば触らない／不一致なら上書き）。契機を Skill 同期と分けるのは、外部の Claude Code から読まれる経路があるため。
- **アプリはこのファイルを読まない。書くだけ。**

### アプリ側への要件：外部変更への対応

- アプリの開いているファイルを外部の書き手が書き換えることを前提とする。これは**外部エディタ一般への対応**であり、AI固有の結合ではない。
- 監視はファイル単位ではなくフォルダ単位とする（外部でのリネームも検知するため）。
- **自己書き込みの除外は「台帳との内容比較」で行う。** 最後に読み書きした内容をパスごとに保持し、再走査で読んだ生バイトと1バイトも違わなければ自分の書き込みと判定する。
  - 時間窓やフラグは使わない（遅れて届くイベントで誤検知し、速いイベントを取りこぼす）。
  - 監視イベントの種類やパスは一切見ず、「何か起きた」だけを契機に再走査する。
- 未保存編集がなければ再読み込みしてトーストで知らせ、**このときUndo履歴は破棄する**（残すと Ctrl+Z が外部の変更を巻き戻す）。
- 取り込み前の内容は一時退避し、トーストに「取り込み前に戻す」アクションを付ける。
- 未保存編集があれば二択ダイアログ「自分の編集で上書き」／「外部変更を取り込む」を出す。**VSCode級のマージUIは作らない**（退避とGitという復元手段があるため）。
- 二択ダイアログが守るのはデバウンス窓の数秒間だけで、衝突の定義はタイムスタンプの前後ではなくデバウンス窓の重なりとする。

## 5. データモデルと永続化

### ファイル構成：プロジェクト＝フォルダ

- 1つの仕様書プロジェクト＝1フォルダとし、その中にツールごとのJSONファイルを置く。
- **紐付けは「同じフォルダにある＝同じプロジェクト」という物理配置で表し、設定ファイルによるパス管理を持たない。** マスタ参照は「同一フォルダ内の該当 `type` のファイルを見る」で閉じる。
- 同種ツールの複数ファイルを許すが、**単一性を宣言したツールはプロジェクトにつき1つ。** 該当は他ツールから参照されるハブ、すなわち `glossary` と `errorCatalog`。ロジックツリーと課題ツリーは論点ごとに分けるのが普通の使い方なので `singleton: false`。
- どの type が単一かはコアにハードコードせず、モジュール側の宣言として持つ（6章）。3つ目の単一マスタが出たときにコアを触らずに済ませるため。
- **ファイル名は識別子にしない**（用語集を含め例外なし）。フォルダ内JSONを走査して中身の `type` で種別を判別するので、自由にリネームしても壊れない。

### スキーマ：JSON Schema を正とする

- 各ツールのデータ形式は JSON Schema で定義し、TypeScript 型はそこから自動生成する。**手書きの二重管理はしない。**
- スキーマはAIへの生成指示と読み込み時の機械検証に直接使うため、自己記述性を持たせる（キー名は省略しない、種別は enum で明示）。
- スキーマの実体はアプリと同梱 Skill で共有し、バイト一致はテストで強制する（理由と機構は4章）。
- **同梱コピーは検証の入力ではない**（検証は ajv の standalone 生成物に焼き付いている）。実行時に読まれるのは、`serialize` が正規形のキー順を `properties` の記載順から導出するため。
- プロトタイプの state 構造は叩き台にせずゼロから設計する（構造は信用しない）。
- 全ファイル共通のエンベロープ（必須フィールド）：
  - `schemaVersion`：スキーマの版。**版は type ごとに独立して進める**ので、移行判定とSkillの追従管理（4章）は `type` × `schemaVersion` の組で行う。共通エンベロープの改訂は全ツールスキーマの改訂を含意する。
  - `type`：ツール種別の enum（`logicTree` / `sequence` / `stateMachine` / `glossary` / `errorCatalog` / `issueTree`。ツール追加で増える）。旧アプリにとって未知の値になり得るが、受け皿は6章の前方互換の規定。
  - `title`：表示名。プロジェクトを開いたときの一覧表示に使う。

### バージョン互換とマイグレーション

- 既知 type だが未知の新しい `schemaVersion` のファイルは、**未知 type と同じ扱い**（一覧表示のみ・編集不可）にしレベル1拒否にはしない。知らないツールは一覧に出るのに知っているツールの少し新しいファイルは開けない、という逆転を避けるため。
- 既知 type × 旧 `schemaVersion` のファイルは読み込み時に**メモリ上で**自動移行して開き、ファイルへの反映は最初の編集保存時とする（閲覧しただけでは旧版のまま残る）。
- 移行は検証を飛ばさない。`src/core/load.ts` が `module.migrate(record, version)` を呼び、その結果をスキーマ検証に掛ける。マイグレータの側は形を見ない（見ると検証の規則が2箇所に生える）。
- マイグレータは各ツールモジュールの提供物（6章）。
- **移行は「旧版のファイルが必ず開くこと」を保証しない。** 語彙を落とす改訂では、廃止した値を持つファイルが移行後の検証で弾かれる。
- **語彙を落とす改訂では、読み替えを移行に持たせるか拒んで書き直させるかを明示的に選ぶこと。** 読み替えを足すと「もう無い区別」がデータの中に生き残るため、既定は拒む側。
- 未公開の版は版番号を上げずに定義を差し替えてよいが、**一度出荷した版に対してはしてはならない。**
- 古いSkillが旧版スキーマで書いたファイルもアプリが移行して開けるので、Skill追従の失敗は「移行で吸収される遅れ」に格下げされる。ただしこれが効くのは改訂が「足す」側のときだけで、語彙を落とす改訂では開けない事故に戻る。

### ID規約（全エンティティ共通）と用語参照

- 形式は `<entityPrefix>_<id>`。`entityPrefix` は小文字英字のみでエンティティ種別を表し、各ツール内の分類enumとは別レイヤー。
- ID本体は nanoid の `customAlphabet` で**英数字62文字（A-Za-z0-9）・10文字固定。** 標準アルファベットの `_` `-` は区切り文字と衝突し、自己記述性とスキーマ検証の正規表現（`^term_[A-Za-z0-9]{10}$`）を汚すため。62の10乗はおよそ 8.4×10^17 通りで、数百レコード規模で衝突の余地はない。
- プレフィクスの粒度はエンティティ単位とし、ツール単位で `node_` に統一しない（状態遷移なら `state_` / `event_`）。具体命名は各ツールの管轄。
- 各ツールの JSON Schema がプレフィクスを正規表現パターンとして宣言し、コアのモジュールレジストリが登録時に重複を検査する。スキーマに書かれていればAIも正しいIDを生成できる。
- **連番IDは禁止。** アプリとAIが並行して要素を追加する設計（4章）では、双方が同じIDを振る衝突が必発する。
- **用語参照**：用語集の各用語に不変ID（`term_` プレフィクス）を振り、他ツールはIDで参照して表示時に名前を解決する。マジックストリング禁止・定数参照のみ、をデータに適用したもの。

### 二段検証

原則は「人間が直せる状態で見せる」で、**拒否は解釈不能な場合に限る**（拒否すると修正に外部エディタが要るため）。

1. **スキーマ検証**（JSON Schema）：構造の正しさ。不合格はレベル1（拒否）＝開けない。
2. **整合性検証**（アプリ実装）：スキーマで表せない、外部キー検証に相当するもの。不合格はレベル2（受け入れて赤表示）＝可視のエラーとして表示し、必要な機能のみ縮退する。編集は可能なので人間がアプリ内で直せる。

レベル2の項目は、参照切れ（発生原因を問わず同一扱いで参照箇所を赤表示）、ID重複、`name` の重複、単一性違反である。

- `name` の重複を整合性検証で受けるのは、同名2件が宣言としての矛盾でありながら、IDが異なるためスキーマの `uniqueItems` では防げないから。判定は NFKC 正規化＋英字大文字小文字同一視で行い、alias 照合と規則を揃える。
- 単一性違反では**そのファイルの解決を伴う操作を停止する**（どちらを正とするかは人間にしか判断できない）。
- **用語集が0個の状態は正常**で、初めて用語登録が発生した時点でアプリが用語集ファイルを自動生成する。用語集不在のまま参照だけあれば参照切れとして赤表示する。
- **検証は全経路共通とする。** 自動保存も外部由来ファイルも同じ検証を通り、経路によって信頼度を変えない。
- **検証スコープはプロジェクト全体とする。** 開いた時点で全ファイルを走査してエラーを一覧に赤バッジで表示し、以後はファイル変更を契機に再検証する。
- **用語削除は即時削除**とし、トーストで参照切れ数を通知する（Undoで復元可）。確認ダイアログも削除ブロックも採らない。参照切れは防ぐものではなく赤く見せるものだから。

### 保存：自動保存＋Git

- 編集はデバウンス付き自動保存でファイルへ書き込み、会議中の保存忘れをゼロにする。
- 「試しにいじって捨てる」の受け皿はGit（コミット＝チェックポイント）とし、アプリ内Undoは直近操作の取り消しに専念する二層構造にする。
- **Git前提のためシリアライズは決定的にする。** diffのノイズを排除して変更履歴を仕様の変更履歴として読めるようにするためで、Skill 側の書き出しとも完全に一致させる。一致は回帰テストで担保する。

#### 正規形の定義（全ツール共通）

| 項目 | 値 |
| --- | --- |
| キー順 | **各スキーマの `properties` 記載順**。ハードコードせず、実行時に `Object.keys(schema.properties)` を読んで並べ替える（`$defs` 配下の入れ子も同様） |
| インデント | 半角スペース2 |
| 区切り | キーと値は `": "`、要素間は `",\n"`（`JSON.stringify(v, null, 2)` 準拠）。空配列は `[]`、空オブジェクトは `{}` を1行で |
| 非ASCII | エスケープしない（`\uXXXX` にしない） |
| 改行コード | LF |
| 末尾改行 | あり（1つ） |
| エンコーディング | UTF-8（BOMなし） |
| 配列順 | 書き換えない（UIの並び順が正） |

- キー順の「正」はスキーマファイル一つに置く。properties を並べ替えれば正規形も自動追従する。
- 改行コードは**プロジェクトフォルダ雛形に `.gitattributes`（`*.json text eol=lf`）を同梱して担保する。** これがないと `core.autocrlf=true` の環境でCRLF化し、書き戻すたび全行diffになる。雛形生成はプロジェクト作成機能の責務。
- 参照実装は `JSON.stringify(reorder(value, schema), null, 2) + "\n"` の UTF-8 バイト列。他言語で書く場合もこれに一致させる。
- **正規化の責務はアプリが持ち、タイミングは「書き込み時」とする。** 自分が書くときは必ず正規形で書き、読み込み・閲覧では書き戻さない（閲覧だけでGit diffが出ると目的自体を毀損する）。
  - 帰結として、外部の書き手の生ファイルは次の保存まで非正規のまま残り、最初の意味的編集のdiffに正規化差分が混ざる。これは許容する。
  - Skill側の出力仕様にも正規形を含めるが、それは緩和策であり保証はアプリ側にある（「書き手を信用せず受け口で保証する」原則）。

### DBを採用しない理由（再検討時のために残す）

- AIとのラウンドトリップが前提である限り交換形式としてのJSONとスキーマ定義は消えず、DB採用は「DB⇄JSON変換層」を追加するだけになる。
- DBの外部キー制約が守るのはDB内部のデータであり、AI生成物の読み込み時検証は結局アプリ側で書くことになる。
- このツールのデータは「アプリの状態」ではなく「文書」である。フォルダコピーで持ち運べる・Gitで差分が見える可搬性を優先し、規模（1プロジェクト数百レコード程度）にもDBの必然性がない。
- 将来、全プロジェクト横断検索等の要求が出たら、正はJSONのままSQLiteを検索用インデックス（導出データ）として足す。

## 6. アーキテクチャ：統合形態

### 決定：単一アプリ（ファイルベース統合）

1つのTauriアプリがプロジェクトフォルダを開き、中のJSON一覧から任意のファイルを開いて編集する。エディタ部分はファイルの `type` に応じて切り替わる。**別アプリに分けて配布する方式は採らない。** 用語集のID解決・整合性検証・共通コンポーネントは全ツール共有のロジックであり、分けると同じコードを何度も配布・更新する保守不利だけが残るためである。

ファイル一覧の額縁機能：

- **新規作成**（`type` を選ぶ）。衝突しないファイル名の判定はディスクに問い合わせる。走査時のスナップショットで決めると、走査後に外部で増えたファイルを黙って上書きするため。
- **削除**（OSのゴミ箱へ移動し、完全削除はしない）。単一性違反（5章）等の解消をアプリ内で完結させるため。
- **検証エラーの赤バッジ表示**（5章）。
- **選択中ファイルの `title` の編集。** 名前の帯は額縁が持ち、モジュールのエディタは `title` を描かない（キャンバス系には置き場所が無く、モジュールごとに実装すると散る）。名前の実体は JSON の `title` でファイル名は変えず、書けないファイルでは読み取り専用にする。
- **一覧の行は主が `title`、副がファイル名**（`title` が空なら `(無題)`、読めないファイルはファイル名に落ちる）。
- **一覧は種類ごとにまとめる。** 見出しの順はレジストリの登録順、未登録の type はその後ろに type 文字列の昇順、読めないものは最後。グループ内は `title` の日本語ロケール順で、五十音順ではない（読みはデータに無い）。
- **用語のインライン登録**を共通コンポーネント要件とする。他ツールのエディタで用語参照を入力する場面から、その場で新規用語を登録できるようにする。

### 拡張要件：ツールは増える前提で作る

新ツールの追加を「コアの改修」ではなく「モジュールの追加」にする。各ツールは次の8点を提供する。

1. `type` 識別子（enumへの追加）
2. JSON Schema（ID規約のプレフィクス宣言を含む。5章）
3. エディタコンポーネント
4. 整合性検証ルール（スキーマで表せない検証）
5. 出力ロジック（`outputs`：`OutputProfile` の配列）
6. マイグレータ（旧 `schemaVersion` から新版への変換。5章）
7. 単一性フラグ（5章）
8. 表記ゆれ検知の対象フィールドパス一覧（検知の実行はコア）

加えて**空文書の雛形 `createEmpty(title)` を提供する**（額縁の新規作成は `type` からモジュールを引くため、置ける場所はモジュール側しかない）。表示名とアイコン（`displayName` / `icon`）もセットで持ち、`icon` は `ComponentType<{ className?: string }>` で受けて `LucideIcon` 型は書かない（コアを lucide に依存させないため）。

#### 出力プロファイル（規約5）

- `OutputProfile` は `id` / `label` / `fileSuffix` / `toMarkdown` を持つ。`fileSuffix` を `label` から導出しないのは、表示名は画面の都合で変わるのに対しファイル名はGitに残る側だから。
- **`toMarkdown` は副作用を持たない純関数とする。** 額縁がコピーと `.md` 書き出しの両方に同じ関数を使うため、モジュール側がファイルやクリップボードに触ってはならない。
- **規約は「0本以上」で、出力を後の段階に回すツールは `outputs: []` を宣言する。** 額縁は `outputs[0]` が `undefined` なら書き出し・コピーの両ボタンを `disabled` にする。
- **読み手ごとにファイルを分けず、1つのデータから出し分ける**（分けた瞬間に二重管理が発生する）。
- 複数プロファイルを持つツールが宣言するのはフィールドの並び1本で、画面の列と出力の列はそこから導出する。列セットを2箇所に書くと片方だけ直したときに黙ってずれるため、`OutputProfile` には列を持たせない。
- 形式ごとにプロファイルを割らない（シーケンスもロジックツリーも図と表を1本の Markdown にまとめる）。

#### 任意スロット

規約の点数を増やさずに足せる任意スロットが3つある。**宣言しないツールに義務は生じず、額縁はスロットの有無だけでボタンの活性を決めてツールの `type` を名指ししない。**

- `describeIssueEffect`（`OutputProfile` の任意メンバ）：整合性エラーがあるまま出力したとき何が起きるかを述べる1文を返す（帰結はツールごとに違い額縁が文面を持てない）。額縁はレベル2の赤があるファイルの出力時に確認ダイアログを挟み、この関数があれば文面を本文に足す。
- `clipboardExchanges`：外部ツールとのクリップボード交換で、各交換は `toClipboard` / `canImport` / `fromClipboard` の3点を持つ。`OutputProfile` に乗らないのは、出力が2形式になり、入力（貼り付けからの取り込み）の口が規約に無いため。
- `tableExport`：表形式コピー。`options`（ダイアログに出す設定項目の宣言）と `variants`（読み手ごとの出し分け）を持ち、各 `TableVariant` は `toTable: (data, options) => Table` を持つ。`OutputProfile` に乗らないのは、出力が TSV と HTML の2つで1本の文字列に収まらず、`.md` 書き出しに意味が無く、設定を引数に取るので `toMarkdown` という名前が嘘になるため。
  - `Table` は `header` / `rows` の2つの `readonly string[]` だけの形とし、TSV 変換と HTML 変換はコアが1つずつ持つ（`src/core/table-tsv.ts` / `src/core/table-html.ts`）。クリップボードへは両方を同時に載せ、貼り先が自分で選ぶ。

**クリップボードコピーは画面の絞り込みに追従し、`.md` の書き出しは全件のまま変えない。** クリップボードは一時的な動線だが、ファイル書き出しは成果物を残す動線であり、絞り込んだままの `.md` は一見完全な成果物の顔で Git に残るためである。報告は `EditorProps` の任意コールバック `onVisibleIds` で行い、間引きは額縁ではなく出力関数の内側（`visible?: VisibleRows` 引数）で行う。額縁が先に間引くと、データ配列の位置で振る `No` が振り直されて画面と食い違うためである。

#### コアが持つもの、モジュールが持つもの

- **整合性検証の指摘の一覧は額縁が出し、モジュールは出さない**（`src/components/IssueBanner.tsx`）。モジュールが `issues` を受け取るのはセル・行・ノードの赤表示のため。額縁がエディタの外に出すので、指摘が増えても図や表が押し下げられるだけで覆われない。3件までを出し、超えたぶんは「他 N 件を表示」で畳む。
- **列を持つツールの共通機械はコアに置く**（`src/core/list-editor/` と `src/core/duplicate.ts`）。モジュールが持つのは列データとフィールド宣言だけ。抽象の粒度は純関数＋小さなフック1本とし、「列定義を渡すと全部返す」1本には集約しない。
- **表のセルのエスケープ規則は照合規則と同じくアプリ内で1つだけ**とし、ツールごとに書き直さない（`src/core/markdown-table.ts`）。食い違うと「あるツールの出力だけ表が割れる」ことになる。
- **キャンバス系ツールの共通土台は `src/core/canvas/` に置く。** 対象はビューポート・測定層・フォント読み取り・平坦木の組み立て・木のレイアウト（`layoutTree`）・エッジのパス生成（`edgePath`）の6点。
  - 木のレイアウトは「木を描くツールのための関数」としてコアに置く。シーケンスの積み上げ型レイアウトは性質が異なるので各モジュールに残す。
  - **モジュールに残るのは、箱の寸法定数とそれに対応するクラス定数、そのツール固有の畳み方、エッジの SVG レイヤ。** 課題ツリーは課題を1つのブロックとして畳んで寸法を `layoutTree` に渡し、`edgePath` は課題ノードの矩形に対して呼ぶ。
  - 抑制された枝は破線にし、**色は `stroke-rule` のまま変えない**（`stroke-grid` はキャンバスの地を塗るトークンなので、その色の線は地と見分けられなくなる）。半透明にする案も採らない。背景の模様のトークンを前景の構造に借りない、という線引きである。
- **表記ゆれ検知はコア機能とする。** ルールベース検知（name / aliases の照合、NFKC正規化、suggestion 区分）の実装はコアに1つだけ置き、モジュールが提供するのは検知対象フィールドの宣言のみ。実装をモジュールに置くと正規化やマッチ強度がぶれ、ツールによって指摘が出たり出なかったりする。
  - 用語集モジュールの役割は照合データの提供であって、検知の実行主体ではない。自由テキストと備考の切り分けは各モジュールの判断とする。
- 整合性検証の責務内訳は、自ファイル内で完結する検証が各モジュール、単一ファイルでは判定できない検証（例：単一性違反）がコア、参照切れ検証が「参照する側」のモジュール。参照される側（用語集）は参照切れ検証を持たない。
- コアはモジュールのレジストリを持ち、`type` からモジュールを引いてエディタ・検証・出力を呼ぶだけにする。レジストリは登録時にIDプレフィクスの重複を検査する（5章）。
- **前方互換**：未知の `type` のJSONに遭遇してもクラッシュせず、「このバージョンでは編集できないファイル」として一覧に表示だけする。古いアプリで新しいプロジェクトを開く事故に備える。

## 7. 技術スタック

### 決定：Tauri＋TypeScript＋Tailwind/shadcn

- **配布形態はTauriデスクトップアプリ（Windows想定）。** 社内でのWeb公開はホスティングの手間が大きいため採らない。チーム展開時に配布方法（社内配布手段、SmartScreen警告への対処）を再検討する。
- **Rustは原則書かない。** ロジックはすべてフロントのTypeScriptに置き、TauriはネイティブAPI（fs, dialog等の標準プラグイン）の提供層としてのみ使う。根拠は3つ。
  1. Rustを要する仕事（重い計算、バイナリ処理）が存在しない。実体は「JSON読み書き＋UI＋検証」で規模は数百レコード。
  2. 実装をAIに委譲してもレビューとデバッグの責任は人間に残る。読めない言語の層は監査不能なブラックボックスになる。
  3. TSとRustに分かれるとIPC境界が生まれ、境界をまたぐバグは診断が難しい。
- 「原則」は禁止ではなくデフォルト。実証された必要（例：数千ノードのレイアウト計算がUIをブロックする）が出た場合は例外を認める。
- プラグインの登録（`lib.rs` の `.plugin(...)` 1行とCargo依存1行）はこの原則の例外ではない。判断もロジックも持たないため。
- **ブラウザ標準の `navigator.clipboard` は使わない。** 権限が欠けたときに実行時に静かに失敗しテストでも検出できないのに対し、プラグイン側なら権限の欠落が capabilities で確認できる。
- **クリップボードの読み取り権限はテキスト（`clipboard-manager:allow-read-text`）だけを与え、HTML の読み取り権限は与えない。** テキストは端末ペインの右クリック貼り付けに要り、HTML は例外5の自前コマンドを通す。

認めた例外は5件。

1. **OSのゴミ箱への移動**（`move_to_trash`）。fsプラグインは完全削除しか持たず、6章の「削除はゴミ箱へ移動」を満たせないため。
2. **PTYのコマンド4本**（`pty_spawn` / `pty_write` / `pty_resize` / `pty_kill`）。端末ペインが本物の端末を要件とし、`tauri-plugin-shell` では raw mode の TUI を成立させられないため。
3. **Skill配置のための fs scope 許可**（`allow_skill_dir`）。fs の実行時 scope は unix既定の `require_literal_leading_dot: true` によりドット始まりの要素に一致しないため。
4. **プロジェクトフォルダの fs scope 再付与**（`allow_project_dir`）。ダイアログが入れる scope はセッション限りで、起動時の復元がダイアログを経由しないため。
5. **クリップボードの HTML 読み取り**（`read_clipboard_html`）。プラグインが HTML の読み取り API を持たないため。

**どの例外も判断を一切置かない。** 実行ファイル名・引数・作業ディレクトリ・対象パス・Skill名一覧はすべてTypeScript側が決めて渡し、Rustの仕事はバイト列と結果を右から左へ流すことに尽きる（Rust側のコードに `claude` という文字列は現れない）。

- 型はJSON Schemaから自動生成する（5章）。**スタイリングはTailwind CSS＋shadcn/ui** とし、デザイントークン（9章）はTailwindの設定に定義してデザインシステムと1対1対応させる。
- **shadcnの適用範囲は「額縁」に限定する**（モーダル、ドロップダウン、ファイル一覧、トースト等）。土台のRadixがフォーカストラップ・キーボード制御の実戦済み実装を持ち、モーダル周りの厄介な挙動をこの層ごと吸収できるため。
- **各ツールのエディタ本体は完全自作する。** 操作言語に合う既製品は存在せず、入力体験のリスクはライブラリでは消えないので設計で抑える（10章）。
- **プロジェクト雛形はリポジトリに `.gitattributes`（`*.json text eol=lf`）を置く。** これが無いと autocrlf 環境で JSON が CRLF へ変換され、決定的シリアライズの LF 指定（5章）が Git 上で無意味になる。

### 決定：配布は GitHub Releases、自動更新は Windows のみ

- 配布は GitHub Releases とし、**Windows のみ updater プラグインで自動更新する**（エンドポイントは `releases/latest/download/latest.json`）。
- **mac を対象にしないのは updater の制約ではなく、未署名の `.app` が Gatekeeper に弾かれる現状が updater の手前にあるため。** 署名は別の意思決定になる。
- **minisign の秘密鍵は1台にしか置かない**（失うと以後どのバージョンからも自動更新できない）。手順は [`release.md`](release.md)。
- 更新の適用はアプリを終了させる（Windows の制約）ので、**利用者が押したときにしか走らせない。**

## 8. 出力・入力戦略

### 入力（インポート）は独立機能を持たない

保存形式がスキーマ定義されたJSONファイルなので、「AIの生成物を取り込む」は「JSONファイルをプロジェクトフォルダに置いて開く」で完結する。**専用のインポート機能は作らない。** ただし読み込み経路には必ず二段検証（5章）を通し、経路による信頼度の差を作らない。

### 出力はMarkdown（Mermaid込み）

- 第一の出力先はNotePMとし、**クリップボードコピーとファイル書き出し（`.md`）の両方**を用意する（コピーは議事録へ貼る最短動線、ファイルはGitに成果物を残す用途）。
- **出力先は必ずしもNotePMではない。** エラーカタログのサポート向け出力は、サポートチームが手書きでサポートサイトを作るための下書きとして渡る。
- **インポート連携はしない。** 更新は自動伝播しないが、前回渡したコミットとの差分をGitで取れば変更行は特定できるので運用で吸収する。
- 出力ロジックはツールモジュールの提供物（6章。0本以上のプロファイルを返す、副作用を持たない純関数）。どういうMarkdownを出すかは各ツールの設計で詰め、本章では枠と共通規約だけを定める。

見出しと並びの規約（用語集・エラーカタログで共通）：

- `##` はエンベロープの `title`、`###` はグループの見出し。**h1は使わない**（NotePMのページタイトルと階層が衝突し、目次はh1〜h3を収載するため）。
- **グループ順は種別 enum の定義順に固定し、スキーマから実行時に導出する。** ハードコードすると enum 改訂時に静かにずれ、順が揺れるとGit上で無意味な差分になる。
- 空のグループは見出しごと省略し、グループ内はデータ配列順に並べる。
- **`No` はデータ配列の位置（`index + 1`）**で、グループごとに振り直さない。画面のNoと出力のNoが食い違うと、会議中に口頭で指す目印として使えなくなる。
- 空フィールドは `（未定義）`、`undecided` は `未分類` として出力し、**負債を出力にも残す**（サポート向け出力でも `未分類` を省略しない）。備考のような検知対象外の自由メモの空欄だけは `（未定義）` にしない。
- 用語集の列は 名称／種別／定義／別名／備考でIDは出さず、エラーカタログの列は `No` ＋ プロファイルの宣言からグルーピング軸を除いたもの。

**表のセルは書き手を信用せずエスケープする。** `\` を先に、次に `|` をエスケープし（順序が逆だと自分が入れた `\` を二重エスケープする）、改行は `<br>` にする。自由記述欄にWindowsパスや正規表現、複数行の値が入ると表が途中で割れて1件まるごと読めなくなるためで、見出しに使う文字列も同様に扱う。

- 状態遷移のJSONは保存形式そのものがC#パラメタライズドテストのデータソースになり得る（「表＝実行可能な仕様」）。専用のテスト用出力を作るかは状態遷移エディタの設計で判断する。
- 出力実装の着手順は、ドッグフーディングで「使う」と確定したツールからとする。

- **二層構造**：コード・AI・以降のセッションが参照するのは役割トークン（意味の名前）のみ。色値（パレット）は差し替え可能な下敷き。色値の直書きは禁止（プロトタイプ4本で実装差が出た原因の再発防止。M7 では `src/styles/conventions.test.ts` がソースを走査してこれを機械検査する）。

  - 面（無彩色）：`canvas`（地。方眼を敷く）／`surface`（作業する面）／`surface-muted`（**一段沈んだ面**。選択中タブ・ファイル一覧の種類見出し・端末のアクティブタブと選択面・見送りの箱と**その配下**（M25——配下が白いままだと「まだ生きている枝」に見える、という実機の観察で配下も塗ることにした。誰が掲げたかは文字の濃さとバッジが運ぶ。`docs/issue-tree/仮説検証モジュール-設計ノート.md` D8 の M25 追記）。M8 の `surface-accent` の後継で、緑を捨て役割を「見出し」から「沈んだ面」に改めた——**テーブルのカラム名もこの面に載せる**。M21 の実機確認で「面なし（`text-ink-muted` ＋ `tracking-wide` のラベルだけ）では見出しの行がデータ行に溶ける」と出たので、無彩色の沈んだ面を敷く。緑帯の代替は「彩度のない面」であって「面なし」ではない）
  - 文字（無彩色）：`ink`／`ink-muted`／`ink-faint`（非アクティブ。3:1。**本文に使わない**。`opacity-*` の代わりに使う）
  - 線（無彩色）：`rule`（セル境界・入力枠。3:1）／`rule-muted`（表の罫線・弱い境界。要件の対象外。**M27 で `grid` から分離**——ダークでは canvas と surface が線を挟むため、方眼と罫線は1値で両立しない）／`grid`（方眼専任。要件の対象外）。境界は「情報を伝えるか否か」で引く
  - **欠落軸** `missing` ＋ `missing-face`（黄）：未定義・未分類・空セル・未回答・未決・仮説なし・保留。**淡い面**（`missing-face`）**＋線＋文字**。線種で段を分ける——破線＝まだ見ていない／実線＝見たが決められない（課題ツリーの語彙を全体へ）。白地で 4.5:1 を満たす黄は黄土色になる。これは仕様（付箋の黄）。**どのデータが欠落か・ヘッダでの集計・行番号での指し方は [`docs/missing-semantics.md`](missing-semantics.md) が規約として持つ**（M22。判定源は `src/core/reading-guide.md` と一対一）
  - **無効軸** `invalid` ＋ `invalid-face`（赤）：重複・参照切れ・整合性違反・スキーマ違反・読めないファイル。**淡い面＋線＋文字**（実線）。表記ゆれの「指摘（suggestion）」は波線下線（弱形。実装はまだ無い）。**黄と赤は D型色覚で色相では分かれないので明度で分ける**——`invalid` は `missing` より一段暗い
  - **着信軸** `pending` ＋ `pending-face`（青）：外から届いた入力に返答していない状態。いまは課題ツリーの「FB待ち」（文言のある問い `asks` に FB `feedbacks` が1件も無い。issue-tree-m4 で「未判断」`pendingNotes` から改名・改構造した）だけ。**淡い面＋線＋文字**
  - **淡い面 `*-face` は同じ軸の色と同じ色相の、白（ダークは黒）へ寄せた面**（ライト L 0.93〜0.95、ダーク 0.26〜0.30。ダークの値は M27 で吟味した——UI ノート D20）。その上に `ink` / `ink-muted` / **枠に使う色**が載ることを `FACE_REQUIREMENTS` が課す（4.5:1。枠が `rule` の `judge-yes-face` だけは非テキストの 3:1）。**枠に使う色は面によって違う**——欠落・無効・着信は同じ軸の線色、判断は `rule` である。**`judge-yes-face` だけ `ink-faint` も課す**——この面は「解決した課題の箱」の地であり、その中の仮説行は自分の旗で抑制されて `ink-faint` になるからで、**淡い面のうち唯一「地」として使われている**ことの帰結である。**淡い面どうしの色差（ΔE 0.05 前後）に識別を負わせない**——欠落・無効・着信・判断を分けるのは線の色と線種と濃い面で、`DISTINCT_PAIRS` に淡い面は入っていない（判断の緑が黄・赤・青と紛れないことは、濃い側の `judge-yes` の3組が3色覚ぶん見ている）
  - **判断軸**：`judge-yes`＋`judge-yes-fg`（支持の**濃い面**。明るい青緑）／`judge-no`＋`judge-no-fg`（棄却の**濃い面**。チャコール）／`judge-yes-face`（**淡い緑**。issue-tree-m5 で追加）。課題の旗（見送り・解決の2種。issue-tree-m4 で `resolved` が増えた）は、**バッジは判断軸の群を借りる**——解決＝`judge-yes` の濃い面（支持と同じ緑）、見送り＝`surface-muted` の面＋`rule` の枠＋`ink-muted` の文字。**箱の面は種別で分かれる**——解決＝`judge-yes-face`（淡い緑）、見送り＝`surface-muted`。**issue-tree-m5 の実機確認まで「意味が逆でも面は分けない」だった**が、実機で「一目で『解決方針が決まった課題』＝これ以上考えなくてよい とわかる」ことが優先され、反転した（`docs/issue-tree/仮説検証モジュール-設計ノート.md` D8 の m5 追記）。**祖先由来の抑制が勝つ優先順位は変わっていない**——旗を掲げた枝の配下は、自分が解決を掲げていても `surface-muted` ＋ `ink-faint` に落ちる

課題の旗の**集計は要対応と別枠**（M25。UI ノート D17）——旗配下の問いは要対応に数えず、旗を掲げた課題の数だけを帯のグレーのチップが種別ごとに持つ（`見送り N` ／ `解決 N`。`docs/missing-semantics.md` 規約4）。**issue-tree-m4 で旗が `deferred`（見送り）1種から `resolved`（解決）を加えた2種になった**——実効（配下を抑制する）は同じだが意味は逆で、別枠も種別ごとに独立して数える（同時に立つこともある）。
  - **規約6条**：(1) 色を持つのは意味だけ——分類・ボタン・見出し・選択状態は彩度を持たない。(2) **開いているものは淡い面と線、決着したものは濃い面。** 線色そのものを面にしない（`bg-missing` / `bg-invalid` / `bg-pending` を作らない。面は `bg-*-face` の側が持つ）。緑の線も作らない（`conventions.test.ts` が両方を弾く）。淡い面と濃い面は明度で分かれるので、「開いている」と「決着した」の区別は面の側にも残る。**例外は `judge-yes-face`（決着したものに付く淡い面。issue-tree-m5）**——濃い面は「支持」「解決」を**点で**示すバッジのためのもので、箱1つの地として敷くと図の中で強すぎる。「決着＝濃い」の読み取りはバッジの側が保つ。(3) 判断軸で彩度を持つのは支持のみ。棄却・見送りは明度差（白黒でも判別。`FACE_PAIRS` が 3:1 を課す）。(4) **5色目は作らない**。新しい意味は4軸のどれかに入れるか、色以外のチャネル（線種・形・位置）で表す。(5) 削除だけはホバー時に `invalid` を借りる。常時は `ink-muted`。これ以外に借用を作らない。(6) 無彩色とは C ≤ 0.01（`ACHROMATIC` が弾く）
  - 意味色4つは標準・P型・D型のすべてで OKLab 色差 ≥ 0.10（`DISTINCT_PAIRS`。M7 は印字だけだったが M21 で門番にした。満たせなければ 0.08 まで下げてよいが、理由を `palette-requirements.ts` に書く）
  - **「未決を面で塗らない」（issue-tree-m3 → M21 で全モジュールの規約2に昇格）は、M21 の実機確認で反転した。** 27型 WQHD・ライトで実物を見た結果、1px の輪郭だけではテーブルのセル・ガターのスロット・バッジが方眼と罫線に埋もれて拾えなかった。**バッジも含めて淡い面を持つ。** issue-tree-m3 の「全部が塗られて一面になる」懸念は、**面を淡く（L 0.93〜0.95）して判断軸の濃い面と明度で分けること**で受ける——塗られていること自体は情報のままで、濃さが「開いている／決着した」を区別する
- **ライト／ダークモード対応**。同じ役割トークンにモードごとのパレットを割り当てる方式。反転による自動生成はしない（警告色が背景に沈む等の破綻を招く）。
- 実装はshadcnの標準規約（CSS変数による役割名定義＋モード切替）にそのまま乗る。7章の決定の帰結として土台が手に入る。

### 確定要素

- **方眼紙背景は M8 で実装した。** `src/index.css` の `bg-grid-paper` ユーティリティ（`var(--grid)` の `linear-gradient` 2本を `background-size: var(--grid-size)` で敷き詰める）で、マス目は 24px。**行高との一致は M23〜M26 の間だけの話である**——M23 では複数行段の行高（16px × 1.5 ＝ 24px）とちょうど一致していた（それより前は `text-sm` の 14px × 1.65 ＝ 23.1px との近似）が、**M26 で入力値を 14px へ下げたので行高は 21px になり、一致は失われた**。**それでも `--grid-size` は動かさない**——人間が 21px の行と 24px の升が並ぶ画面を実機で見て問題なしと判定した（M26 の実機確認）。方眼は行の罫線ではなく紙の地なので、文字行と1対1で噛み合う必要はない（段を3度作り直しても `--grid-size` を動かしていないのはこの理由による）。マス目のサイズは `index.css` 側に置く（`palette.css` は色値だけを持つ）。**`repeating-linear-gradient` に戻さないこと（mac の実機で判明）。** WebKit（macOS の WKWebView / Linux の WebKitGTK）は繰り返し勾配を「面の端から端までの1本の勾配」として標本化するため、24px 周期の 1px 線がほとんど落ちる——実機では横線の間隔が 24/72/96px とばらつき、縦線は画面全体で2本しか出ていなかった。Chromium（Windows の WebView2）は正しく敷き詰めるので**Windows では見えない**。1周期ぶんの絵を敷き詰める形にすると勾配の長さがマス目1つに閉じるため、標本化の誤差が出ない（`palette.test.ts` が形を固定している）。**要点は「地は方眼、作業する面は無地」**——`canvas` と `surface` を明度差ではなく**模様の有無**で見分けさせる。ライトでは両者の L 差が 0.04（1.13:1）しかなく、明度で分けようとすると破綻していた。地（`main`）に方眼を敷き、ヘッダ・サイドバー・テーブルは `surface` の無地の面にする。グリッド線の濃度はモード別に持ち、**M8 の実機確認でライトを `canvas` 上 1.36:1 から 1.17:1 へ薄めた**（会議で投影したときにうるさくない濃さが基準。**ダークは M27 の実機確認で 1.20:1 から 1.06:1 へ薄めた**——`rule-muted` の分離で `grid` が方眼専任になったため、罫線の見えやすさと引っ張り合わずに薄くできた）。
- **端末（xterm）の中の面・文字・カーソル・選択は、役割トークンから流し込むが常にダーク固定にする**（M17 で「役割トークンに合わせる」と確定し、**M28 の実機確認で「ダーク固定」へ反転した**——人間の判断で、ライトのアプリの中でも端末だけは黒いままの方が読みやすいとされた。端末は facet の面ではなく「端末の面」という位置づけになる）。流し込むのは**面（`surface`）・文字（`ink`）・カーソル（文字と同色。その上に乗る文字は面と同色）・選択の面（`surface-muted`）の4系統**だけで、**ANSI の16色は持たない**——役割トークン（20個）に対応物が無く、持つと「配色を差し替える」作業が「16色を選び直す」作業になり、`palette-retheme` Skill の前提（**20個の役割トークンのうち7個は外部テーマの変数から機械的に拾い、対応物が無い残る13個だけを候補から人が選ぶ**——上の M7 の項）も壊れるため。ライトの面で既定の16色が読めるかは xterm 自身の `minimumContrastRatio`（**本文と同じ 4.5:1**）に任せる。**色値はソースに現れない**——`palette.css` の `.dark` が持つトークンの値を実行時に読んで sRGB へ変換する（`src/core/terminal/theme.ts`。xterm は `oklch()` を解釈しないため。変換式は `src/styles/contrast.ts` の既存のものを使い、**同じ式を2本持たない**）。**「`.dark` の値」を読む手段は、非表示の使い捨て要素に `className = 'dark'` を付けて `document.body` へ一時的に挿し、`getComputedStyle` で読んでから外すこと**（`src/components/TerminalTab.tsx` の `buildDarkTerminalTheme`）——カスタムプロパティは継承するため、アプリがライトのときでも `.dark` を付けた要素からはダーク側の値が読める。**この読み方は `palette.css` の `.dark` が素のクラスセレクタであることに依存する**——`:root.dark` のような詳細度の高い形へ変えると、`document.body` の子に付けた `.dark` はトークンを再定義しなくなり、端末の配色が黙ってライトへ戻る（[`open-issues.md`](open-issues.md) 参照）。**トークンが1つでも読めなければ配色を渡さず xterm の既定に落とす**——半端に流し込むと面だけ変わって文字が読めない端末になる。**アプリのライト／ダーク切り替えにはもう追従しない**（M28 の反転の帰結——ダーク固定の値を毎回読み直すだけなので、`TerminalTab` / `TerminalPane` からアプリのモードを渡す `dark` props の連鎖は削除した）。**端末のフォントも同じ扱いで M26 に流し込んだ**（こちらはモードに依存しないので反転の対象外）——`--font-mono`（Plex Mono）を `getComputedStyle` で読んで `term.options.fontFamily` に入れる。**ただし読み込みが済んでから入れること**——xterm はセル寸法を `fontFamily` を代入した時点のフォントで測るので、届く前に入れると**フォールバック書体の寸法で固まる**。`document.fonts.ready` では足りない（「使われたフォント」しか待たず、その時点で Plex Mono はまだ1文字も描かれていない）ので、`document.fonts.load` で通常と太字の両方を明示的に読み込み、その完了後に代入して `fit()` する（700 は ANSI 太字用に同梱してある）。**トークンが読めなければ何も入れず xterm の既定のまま**——色と同じ「半端に流し込まない」。**隠れているタブでは代入も `fit()` も遅らせる**（`pendingFontRef` に覚えて可視化時の既存経路に任せる）——`display: none` の端末は 0×0 で、そこで測ると開き直したときに表示が崩れる。
- **ボタンのラベルの行間は要素セレクタで一律に揃える**（`src/index.css` の `@layer base` の `button { --tw-leading: 1.2 }`）。本文向けに広げた行間（M8 当時の `text-sm` の 1.65。M23 で段を作り直した後は複数行段の 1.5 が同じ役回りにあたる）がボタンに効くと、和文フォントの縦メトリクスの非対称でラベルが上へ寄る。個々のボタンで直すと「実装のたびに同じ指摘が出る」ので、新しく作ったボタンにも自動で効く形にする。**`line-height` を直接書かないこと**——Tailwind の `text-*` は utilities レイヤーで `line-height: var(--tw-leading, <既定>)` を生成し、cascade layers では後に宣言された utilities が base に勝つため届かない。utilities 側が普段設定しない `--tw-leading` へ逃がせば衝突自体が起きない。
- **フォントの書体は M26 で同梱に切り替えた（M7 の決定の反転。UI ノート E ＝ D6〜D8）。** `--font-sans` は `'IBM Plex Sans Variable', 'IBM Plex Sans JP', 'Yu Gothic UI', 'Hiragino Sans', sans-serif`、`--font-mono` は `'IBM Plex Mono', ui-monospace, 'Cascadia Mono', Consolas, monospace`（`--font-mono` の新設自体は M7。ファイルパス・件数・ID 用）。**M7 が確定した Geist は外した**——OS 環境からの導出（ラテンだけ Geist、和文は Yu Gothic UI / Hiragino Sans へフォールバック）は、**字面の比率が揃わず和欧混植がずれ、和文のウェイト段が環境依存で出ない**（UI ノート D6〜D8）。3書体を IBM Plex の同一設計で揃えると、混植のズレは構造的に起きず `size-adjust` の補正も要らない（U1 の決着＝案A）。**フォールバック列（Yu Gothic UI / Hiragino Sans / sans-serif）は残す**——同梱が何かの理由で届かなかったときに MS UI Gothic まで落ちないための保険で、正常時は使われない。同梱の作法は4点:
  - **fontsource の3パッケージ**を npm 依存で入れる（`@fontsource-variable/ibm-plex-sans` ＝ 可変 wght ／ `@fontsource/ibm-plex-sans-jp` ＝ static 400/500/600。**JP に variable 版は npm に存在しない** ／ `@fontsource/ibm-plex-mono` ＝ static 400/700。700 は端末の ANSI 太字用）。**Tauri の `resources` には置かない**——`@font-face` の `url()` が dist の資産を指せば実行形へ入るので、実行時のパス解決が要らない。
  - **素の fontsource の import をしないこと。** static 版の CSS は woff2 と woff を**両方**参照しており、素で `@import` すると旧形式の woff まで dist に入る（JP だけで数MB）。`src/index.css` が読むのは生成物 `src/styles/fonts.css` で、これは `scripts/gen-fonts-css.mjs` が fontsource の CSS から woff の参照だけを落として作る。**`fonts.css` は生成物だがコミットする。直に編集せず、fontsource の版を上げたら `node scripts/gen-fonts-css.mjs` で作り直す**——形と参照先の実在は `src/styles/fonts.test.ts` が固定し、版上げでファイル名が変わったときの番人になる。
  - **woff2 を data URI にインライン化しない**（`vite.config.ts` の `assetsInlineLimit` を `.woff2` にだけ `false` にする）。JP のスライスには 4KB を割るものがあり、Vite の既定（4096）だと CSS 内の `data:` URI になる。**`src-tauri/tauri.conf.json` の CSP は `font-src 'self'` で `data:` を許していない**ので、そのスライスだけが静かにブロックされ**珍しい漢字が豆腐になる**。**CSP を緩める側ではなく、インライン化を止める側で塞ぐ。**
  - **同梱量は 385本・計 4.41MB**（JP 369本＝123分割×3ウェイトで 4.16MB／Sans 可変 6本／Mono 10本。`npx vite build` 後の `dist/assets` 実測）。インストーラは 3.67MB → 8.19MB（**+4.52MB**）。**字数サブセットはしない**——ユーザーが入力する漢字を事前に決められないため（`docs/glossary/scope.md` M7 節の当時の論拠のうち、ここは生きている）。全字収録のまま unicode-range で割るので、使われないスライスは**そもそも取得されない**。
- **段と行間は M23 で作り直した（3サイズ4段）。M26 で入力値が抜けて 3サイズ5段になった**（UI ノート B ＝ D11・D12。設計スペック `docs/superpowers/plans/2026-08-24-m23-core-typography-design.md`）。出所は D11 の確定スケールで、その基準値は **D12 の 96 → 109 PPI 正規化**（27型 WQHD・100% スケーリング。`14 × 109 / 96 ≒ 16`）である。**サイズは 14 / 16 / 22px の3つのまま**で、増えたのは行間の組み合わせの側である。**M26 の部分反転は「何が `text-base` に載るか」を変えた**（下の各段に織り込んである。UI ノート D11「M26 での部分反転」）——**入力値（データの文字）だけを一段下げて 14px にし、UI ラベル側と「アプリが書いた文章」は 16px のまま据え置いた**。理由は D7 の字面差が逆向きに効いたこと（IBM Plex は仮想ボディに対する字面が Yu Gothic UI より大きく、同じ 16px 指定で体感サイズが上がった）で、人間が実機を見て裁定した（2026-08-26）。**14px は D11 の下限そのものなので下限は割っておらず、「小さくするときは薄くしない」も維持している**（濃度は変えていない）。**行間まで据え置いたのは複数行の 1.5 だけで、単行の入力値は 1.25 から 1.3（`text-sm` の既定）へ動いている**:
  - **`text-sm` 14px / 行間 1.3**——補助**と、単行の入力値**。補助側は `KeyHints` の操作ヒント・バッジ（`src/components/badge-styles.ts`。`leading-none` を明示するので実際は 1.0）・シーケンスのガターの問いラベル列（`SequenceEditor.tsx` の `LABEL_FONT_CLASS`）・課題ツリーの行の中の節見出し（`HypothesisRow.tsx` の `sectionLabelClass`。`leading-none`）。**M26 でここに単行の入力値が入った**——用語集の用語名・別名・種別と エラーカタログのエラー名・対応レベル（`<table className="... text-sm">` から継承するだけで、セル側は `leading-*` を明示しない）、シーケンスの種別セル（`StepShapeCell`）と参照セル（`ActorRefCell`）。**種別・参照は `<button>` なので `@layer base` の `--tw-leading: 1.2` を受け、行間は 1.3 ではなく 1.2 になる**（下の「ボタンのラベルの行間」の項）。単行の入力値の行間は M23 の 1.25 から 1.3 へ動いている——**据え置いたのは複数行の 1.5 だけである**
  - **`text-base` 16px / 1.25**——**UI ラベル既定**。テーブルのカラム名・ボタンのラベル（shadcn `Button` の既定サイズの箱は `h-9` ＝ 36px、アイコンボタンは `size-9`）・絞り込みの検索欄・ファイル一覧の行と種類見出し・キャンバスの帯の集計文言（`SequenceEditor.tsx` の `回答済 N ／ 考慮不要 N`）・`MissingTally`・空状態の1行（`App.tsx` の「ファイルを選ぶとここで編集できます。」「{reason}」）・アプリ全体の通知の帯（`App.tsx` の `BANNER_ORDER`）・端末のエラー行（`TerminalTab.tsx`）。**M26 で「セル・入力欄」がここから抜けた**——`text-base` が受け持つのは「アプリが出す文字」であって「利用者が打った文字」ではなくなった
  - **`text-base` ＋ `leading-normal` 16px / 1.5**——**読ませる短い塊**。トースト（`Toast.tsx`）・`IssueBanner` の指摘リスト・空状態の説明文（`App.tsx` の「このプロジェクトにはまだ用語集がありません…」、開けないファイルのエラー一覧と「外部エディタで修正してから…」）。**この段は M23 のまま動いていない**——M26 が下げたのは入力値だけで、**アプリが書いた文章はサイズも行間もそのままである**
  - **`text-sm` ＋ `leading-normal` 14px / 1.5**——**複数行の入力値とキャンバスの折り返しテキスト。M26 で新しく開いた段である**（M23 の 3サイズ4段は、これで**3サイズ5段**になった）。用語集の定義・備考、エラーカタログの `name` / `resolutionLevel` を除く全列（どちらも `CellInput` に `leading-normal` を明示している）、シーケンスのアクター名（`SequenceEditor.tsx` の `ACTOR_BOX_CLASS` のセル）・ステップの文言・ガターの答えスロット（`GutterSlot`）・`GhostSlot`、ロジックツリーのノード（`NODE_FONT_CLASS` / `NodeBox`）、課題ツリーの仮説・由来・根拠・FB（`BODY_FONT_CLASS` / `HypothesisRow`）と課題タイトル（`TITLE_FONT_CLASS`。`font-semibold` は維持）。**M23 ではこれらが `text-base` ＋ `leading-normal`（16px / 1.5）に載っていた**——M26 でサイズだけ 14px へ下げ、行高の比率 1.5 は据え置いた（実高は 24px → 21px）。**明示が付くのはこの側である**——`text-sm` の既定行間 1.3 では読ませるには詰まりすぎるので、`leading-normal` で 1.5 に広げる。この「**同じ 14px で行間だけ違う**」2段が並ぶことが、**キャンバスの測定見本（probe）を補助段と複数行段で別に持つ理由**である（1本で兼ねると片方の行高を見誤る。`SequenceEditor.tsx` の `SEQ_FONT_CLASS` / `LABEL_FONT_CLASS`、`IssueTreeEditor.tsx` の `BODY_FONT_CLASS` / `SMALL_FONT_CLASS`）
  - **`text-xl` 22px / 1.3 / `font-medium`**——文書タイトル（`FileHeader` のファイル名）とアプリ名（`App.tsx` の `<h1>facet</h1>`）。同段・同扱いで、アプリ名の bold は 500 に落ちた
  - ウェイトは**段の既定が 400**。`font-medium`（500）になるのは `text-xl`（タイトル・アプリ名）・セクション見出し・バッジ・課題ツリーの行の中の節見出しと、**すべての `<Button>` のラベル**（`src/components/ui/button.tsx` の base が `font-medium` を持つ。生成物の側なので自作コードのクラスには現れない——**ボタンが 400 だと読まないこと**）・`AlertDialogTitle`（`ui/alert-dialog.tsx:124`。生成物の側の `text-base font-medium`）・`DropdownMenuLabel`（`ui/dropdown-menu.tsx:171`。生成物の側の `text-xs font-medium`）。それより重いのは**課題ツリーの課題タイトル**（`font-semibold` ＝ 600。`src/modules/issue-tree/measure.ts` の `TITLE_FONT_CLASS`。**太字は幅が変わるのでキャンバスの測定器を独立に持つ**）と、ファイルが開けないときの見出し（`App.tsx` の `font-bold text-invalid`）だけ——**M26 でここは `font-bold`（700）から `font-semibold` 相当の 600 に落ちた**（唯一の 700 のために Mono 以外でもう1段を積まない。UI ノート §4.3・D8 の M26 の決着）。**ウェイトの階層は M26 で実体化した。** Yu Gothic UI のフォールバックでは和文のウェイト段が出ない環境があるという予約は、**IBM Plex Sans JP の static 400/500/600 を同梱したことで解消した**——D8 の3層（ヘッダ = Medium 500 ／ 本文 = Regular 400 ／ 補助 = Regular＋グレー）は**追加変更なしでそのまま実体化している**。**「E が入ったらセクション見出しの階層をウェイトへ移せる」という予約は、「移さない」と決めて閉じた**（M26）——カラム名は `font-medium`＋`tracking-wide`＋`text-ink-muted`＋`bg-surface-muted` の4チャネルのままである。字間・グレー・面を外して「ウェイトだけ」に痩せさせる案は、**M21 の実機確認で出た「面なしでは見出しの行がデータ行に溶ける」という観察と衝突する**（4チャネルが過剰に見えるかは M26 の実機確認で人間が見る）
  - **使ってよいのは `sm` / `base` / `xl` の3段だけ。** `text-xs`（12px）は D11 の **14px 下限**で廃止、`text-lg`（18px）は**実使用 0 件**のまま閉鎖（rev の「画面タイトル」は名目だけだった）、`text-2xl`（24px）はアプリ名を 22px へ統合して閉鎖した——M7 が `text-xl` を開けなかった理由（**2px 差の段はどちらを使うか決められない**）は 22 と 24 の並びにもそのまま当たるので、**2px 差の段を体系に残さない**。**`--text-xl: 22px` は `src/index.css` の `@theme` で再定義する**（Tailwind 既定は 20px）。`xs` / `lg` / `2xl` / `3xl` 以上と任意値 `text-[...]` は `src/styles/conventions.test.ts` が弾く（走査から外すのは shadcn の生成物 `src/components/ui/` だけ——改造は自由だが、段の規約は自作コードの側に課す）
  - **行間は詰めた値を既定にし、広げる側だけを明示する**（D11「密度は行高で稼ぎ、サイズでは稼がない」）。既定は `@theme` が持つ（`--text-sm--line-height: 1.3` / `--text-base--line-height: 1.25` / `--text-xl--line-height: 1.3`）。**クラスで明示してよい `leading-*` は `leading-none`（バッジと課題ツリーの節見出し）と `leading-normal`（複数行の欄）の2つだけ**で、`leading-5` のような数値指定と任意値 `leading-[...]` は `conventions.test.ts` が弾く——**行の高さをクラスで固定する書き方は、段を再定義したときに静かに取り残される**（issue-tree-m1 が「2件目が出たら書き方を決める」と予告し、M23 で許可リストとして決着した）
  - **セクション見出し（テーブルのカラム名・ファイル一覧の種類見出し）は `text-base` ＋ `font-medium` ＋ `tracking-wide` ＋ `text-ink-muted` ＋ `bg-surface-muted`。** **M23 の時点ではセルと同じ 16px** で、セルとの区別はサイズではなく**字間・グレー・面の3チャネル**が運んでいた（**Medium(500)・字間・グレー・面は M21 の決着のままで、M23 が変えたのはサイズだけ**——`text-xs` 12px からセルと同じ 16px へ上げた）。**M26 でセル側が 14px へ下がったので、いまはサイズ差（16 対 14）も区別に加わっている**——ただし**カラム名を下げる判断は明示的にしていない**（人間の指示は「カラム名とかボタンとかバッジのフォントサイズはそのままでいんだけど、入力値だけ小さくしたい」）ので、3チャネルはそのまま据え置く。**見出しの行間 130% は 125% に畳んだ**——16px では差が 0.8px しかなく、単行のラベルでは視認できないので、段を分ける値打ちが無い
  - **`KeyHints` は「小さいまま、薄さを外した」。** D11 が名指しする「小さい＋薄いグレー」の**二重減衰**の解消で、`text-sm`（14px）のまま `text-ink-muted` → `text-ink` にした。帯の中の強弱は濃度ではなく `KeyHints` の並びが運ぶ
- **表示環境は 27型 WQHD・100% スケーリング（約 109 PPI）を基準に取り、正規化はズームではなく基準値（フォントサイズ）の側で行う**（UI ノート D12・D13。**D13 の「ズーム 100% 固定」は M23 で一部修正した**——UI ノート D13 の rev.4 訂正）。**既定のズームは 100%** で、ボーダー・方眼線は文字サイズが変わっても **1px 固定**（非整数倍率でヘアラインが滲み、隣り合う線で太さが揃わなくなるため追従させない）。**ただし手動ズーム（Ctrl+± / Ctrl+0。`src-tauri/tauri.conf.json` の `zoomHotkeysEnabled: true`）は逃げ道として残す**——2026-08-16 に人間が「アプリの拡大縮小を可能に」として入れたもので D13 と矛盾していたが、2026-08-24 に人間が**残す**と裁定した。**ズーム中に 1px 罫線が滲むことは代償として受ける。** D13 の将来制約（ルート `font-size` ではなく WebView ズームを使う／倍率と基準フォントサイズを Git 管理下のプロジェクト JSON に保存しない）は生きたままで、`zoomHotkeysEnabled` はまさに WebView ズームであり倍率をどこにも保存しないので、両方を満たしている。**ズーム倍率の保存とズーム UI は引き続き YAGNI。**
- **数字は等幅**（UI ノート D9。`index.css` の `body { font-variant-numeric: tabular-nums }`。テーブルの No 列は右揃え）。件数・ID・No のような**桁で読む数字**が縦に並ぶ場所で、プロポーショナルな数字は桁位置が揃わず、差分を目で拾えない。`body` に1行置けば全画面に効くので、**個々の要素で当て直さない**。
- **角丸は2段＋円**（M25。UI ノート §1.1）。部品・セル・チップ・バッジ・ボタン＝`rounded-sm`／浮遊面（メニュー・ダイアログ）＝`rounded-md`／意図した円（トグルのつまみ・ドット）だけ `rounded-full`。実効値は `src/index.css` の `--radius: 0.625rem` ×倍率（sm＝6px・md＝8px）で、**基準値は M25 では動かしていない**（吟味はダークと同じ持ち越し）。裸の `rounded`（倍率制の外の固定 4px）・任意値・他の段は `src/styles/conventions.test.ts` の許可リスト検査が弾く——**この検査だけは shadcn の生成物（`src/components/ui/`）も走査対象に含む**（段・行間の検査が ui/ を除外する理由はタイポグラフィの話で、角丸は ui/ を意図して改造したため。shadcn を更新したとき `rounded-lg` が黙って戻るのを捕まえる）。`sm` と `md` の使い分け（部品か浮遊面か）は機械では判定できないので、そこはレビューと実機が守る。帯の `⚠` は M25 で `CircleAlert`（lucide）になった——絵文字は色が「色を持つのは意味だけ」の管理の外にあり、SVG なら `text-missing` を明示できる（端末に出す `tallyLine` は `⚠` のまま）
- **キャンバス系ツールでは、測定層と描画層が同一のフォントトークンを参照しなければならない**（logic-tree M1 で確定）。ノードの幅・高さ・折り返し位置は、DOM に触れないオフスクリーン `<canvas>` の `measureText` が**描画前に**確定させる（1パスで描くため。`docs/logic-tree/logic-tree-canvas-tech-notes.md` 論点4）。測定に使うフォント指定が実際に描画されるフォントとずれると、**全ノードのサイズが一斉に狂い、文言が枠から切れる**。実装は `getComputedStyle` でノードの実効フォント（`font-family` / `font-size` / `line-height`）を読み、それを測定器の鍵に混ぜる形（`src/core/canvas/canvas-font.ts`。**M20 でコア化し、ロジックツリー・シーケンス双方がここを参照する**）。**Web フォントの読み込み完了（`document.fonts.ready`）で測り直す**ことも要る——最初の1フレームはフォールバックのメトリクスで測っているため。**M26 から、契機は `ready` だけでは足りない。`loadingdone`（遅延スライスの到着）でも測り直す。** 同梱した和文フォントは unicode-range で 123 に分割されており、**珍しい漢字が初めて画面に出た瞬間に該当スライスだけが後から届く**（`font-display: swap` なので、その一瞬はフォールバックで描かれている）。`ready` は初回にしか解決しないので、これを拾わないと**後から届いた字の幅・高さが古いまま残る**。実装は `src/core/canvas/use-font-generation.ts` の `useFontGeneration()` に**一本化**した——2つの契機を「世代」として数え、その番号を測定器の鍵に混ぜる。**フォントの同一性では測り直しを起こせない**からこの形になっている: `getComputedStyle` が返すのは宣言されたファミリ**列**だけで、どのフェイスに解決されたかは映らないため、値を比べても変化を検出できない。ready の直後に `loadingdone` も発火して2回進み得るが、再測定が2回走るだけで結果は同じ（冪等）なので重複は取り除いていない。**キャンバス3本（ロジックツリー・シーケンス・課題ツリー）だけでなく、テーブルの `CellInput` の行数も同じ契機で追従する**——スライスが遅れて届くと折り返し位置が変わるので、`scrollHeight` から出している行数を測り直さないと欄の高さが古いまま残る。**M24 で、課題ツリー・ロジックツリーのノード幅は固定になった**（`BOX_WIDTH` / `NODE_WIDTH` ＝ どちらも 320。UI ノート D3）。**フォントに追従するのは高さ（行数）だけで、幅は動かない。** 幅を内容から導出していたころは、長文ノードだけ幅が3倍になって木の骨格が読めず、右上のバッジの右端が列の中で散って「どれが未決か」を全ノード読まないと拾えなかった。**シーケンスだけは扱いが違う**——`LABEL_MAX_WIDTH`（320）・`ACTOR_MAX_WIDTH`（240）は**上限**のままで、答えセルとガターだけが「幅を導出しない」（`ANSWER_WRAP` は `maxWidth === minWidth`）。**値が同じ 320 でも意味が違うので、3つを共有定数に束ねていない。** この帰結として、**フォントの測り直しを幅で観測するテストは成立しなくなった**——`LogicTreeEditor.font.dom.test.tsx` の観測点は M24 で `style.height` へ移してある（幅で観測したままにすると、番人が黙って何も検証しなくなる）。**高さに上限は無い——M24 が一度入れて実機で撤回した。** 「閉じた箱に出る文章を3行で打ち切る」を実装したが、**`overflow: hidden` の `textarea` はキャレットに追従してスクロールしない**ことが実機で判明し、打ち切った箱は4行目以降を**編集できない**箱になった（`docs/history/m24-core-node-width-lock.md` の「実機確認の所見」）。**`textarea` を上限行数で切るなら、「溢れた行をどう編集させるか」を先に用意しなければならない**——`text-overflow: ellipsis` も `line-clamp` もフォームコントロールには効かないので、省略記号を出す道も「非フォーカス時だけ `<span>` に差し替える」（`HypothesisRow` の畳まれた行と同じ作法）しか無い。**有力な逃げ道は、フォーカス中だけ `overflow-y: auto` にし、スクロールバーを `scrollbar-width: none` で消すこと**——`auto` は確実にキャレットへ追従し、バーを消せばレイアウト幅を食わないので測定の前提が崩れない（M24 は `overflow-y: auto` を「スクロールバーが幅を食う」の1点で退けており、この逃げ道を検討していなかった）。
- 共通コンポーネント（ツールバー、バッジ、モーダル、チップ）の仕様化は、色確定後ではなくトークン確定後に着手できる（役割名で実装できるため）。個別の仕様は各ツールセッションまたは実装時に詰める。**M8 で最初の1枚として `src/components/button-styles.ts` の `buttonBase` を置いた**——shadcn の `Button` を使うほどでない生の `<button>`（フィルタのチップ、一覧の行、トーストの操作）が共通で敷く土台で、用途ごとの差分（余白・文字サイズ・色）は各所に残す。**新しいボタンもここを通す。** 自前のレイアウトを持つ要素（ファイル一覧の行のように、中で `flex` を組んでいるもの）に土台を敷くと壊れるので、そこは例外としてコメントに理由を書く。**M21 で `Badge`（`src/components/Badge.tsx`。意味を variant で受け、形は部品が持つ）と `Chip`（`src/components/Chip.tsx`。選択トグル。選択は黒塗りではなく `surface-muted` の面と `ink` の枠）を置いた。** 状態のバッジを新しく描くときは `Badge` を通す。課題ツリーの語彙と部品の variant の対応は `src/modules/issue-tree/badge-variant.ts` が持ち、部品は語彙を知らない。**部品のファイルは部品だけを export する**——variant の型・クラスの導出・寸法の定数は隣の `src/components/badge-styles.ts`（`BadgeVariant` / `badgeClass` / `BADGE_BOX_HEIGHT`）に置く。`KeyHints.tsx` と `hint-text.ts` と同じ分け方で、oxlint の `react(only-export-components)` を 0 に保つための構造である。
- **塗りつぶしたボタン（`default` variant）は使わない（M21。UI ノート D19）。** エディタの主操作はセルに文字を打つことでボタンではないので、ツールバーは全部 `outline`（Secondary）。**`ghost`（Tertiary）は許可するが現状使用は0件で、アイコンだけのボタン（Undo/Redo。`src/App.tsx` の `size="icon"`）も `outline` である。** `conventions.test.ts` が `variant` 無しの `<Button>` を弾く。**例外はモーダルのダイアログ（`ConfirmDialog` / `ChoiceDialog` の `AlertDialogAction`）だけ**——モーダルの本体はそのボタンで、主操作が1つだけ存在する（UI ノート D19 の論理そのもの）。黒塗りは M21 でトグル（状態）から外したので「押すもの」の意味に専有されている。`conventions.test.ts` の検査は `<Button` だけを見るので、この例外は検査の外にある。M8 の『1画面に1つ』はこれで置き換わる。**許可する variant は `outline` と `ghost` の2つだけで、shadcn が持つ `destructive` も使わない**——色の紐付けは済んでいる（`index.css` の `--destructive: var(--invalid)`。`palette.test.ts` が検査する）が、**`destructive` variant が使うのは透過の面**（`src/components/ui/button.tsx` の `bg-destructive/10` ／ `hover:bg-destructive/20` ／ `focus-visible:ring-destructive/20` ／ ダークの `/20` `/30` `/40`）で、**規約2（無効が持つ面は淡い面 `invalid-face` だけで、`invalid` そのものを面にしない）と M21 の透過全面禁止の両方に触れる。** 生成物を手で整形して直すこともできる（7章のとおりソースコピー方式なので改造は自由）が、**使用が0件である以上、直すより「使わない」と決める方が安い。**削除は生の `<button>` に**常時 `text-ink-muted`・ホバーで `text-invalid`**（`src/components/FileList.tsx`。規約5の借用そのもの）。
- **セルの「無効」「欠落」は淡い面だけで示す**（M21。`src/core/list-editor/cell-face.ts` の `CELL_FACE_CLASS`。**規約2の例外**）。用語集・エラーカタログのセルは **無効＝`invalid-face`・欠落＝`missing-face`** の面だけで、輪郭を引かない。経緯は2段——最初は輪郭だけで作り、実機確認で「方眼と罫線に埋もれて拾えない」と出て淡い面を足し、次の一巡で「表の中では輪郭がテーブルの罫線と競合してノイズになる」と出て輪郭を外した（2026-08-24）。欠落と無効の区別は面の色相（黄／赤）が運ぶ。バッジは線種（破線＝まだ見ていない／実線＝保留）が情報を運ぶので線を残しており、セルとは扱いが違う。`CellFace` は1セルにつき1つしか返さず淡い面も不透明なので、M8 が避けていた「半透明の二重塗り」は構造的に起きない。行全体に掛かる指摘は行の帯ではなく**先頭セルに1つ**出す（`rowAnchor`）。シーケンスも同じ形に揃え、**行の帯を廃して `#N` の通し番号に無効を出す**——面が二重に重なる構造そのものが無くなった。**`outline-dashed` を使うときは、そのユーティリティが生成 CSS に載っていることを確かめること**——Tailwind v4 は `outline-style` を `@property --tw-outline-style`（初期値 `solid`）経由で当てるので、実線しか使っていないうちは破線の宣言が出力に現れない。
- **フォーカスは面の塗り替え（`focus:bg-*`）ではなくリング（`focus:ring-2 focus:ring-inset focus:ring-ring`）で示す。** 面の色は変わりうる（`bg-surface` になった瞬間 `focus:bg-surface` はコントラスト比1.00:1で消える）ためで、**M21 でこの規約はもう一つの根拠を得た**——状態の表示の主役が輪郭になったので、**無効・欠落の淡い面（`bg-invalid-face` 等）と輪郭（`outline-invalid` 等）はリングと独立であり、フォーカスで消えない**（リングは枠の内側に重なるだけで、面も輪郭も塗り替えない。M8 の用語集エディタで発覚した「面を塗り替えると警告表示ごと消える」欠陥は、これで構造的に起きなくなった。ロジックツリー・シーケンス・状態遷移の各エディタも同じ構造に当たる）。
- **`KeyHints`（`src/components/KeyHints.tsx`）を M14 で共通部品として置いた。** 操作ヒントの修飾キーは文中に `$mod` / `$alt` というプレースホルダで書き、`hint-text.ts` の解決関数が実行時のプラットフォームに応じて `Ctrl`/`Cmd`・`Alt`/`Option` へ置き換える。**画面に `Ctrl` と直接書かないこと**——macOS では主修飾キーが `Cmd` なので、文字列を直書きすると誤った操作説明になる。シーケンス・ロジックツリーの両キャンバスがこの部品でヒント帯を出している。帯の面は不透明の `bg-surface`（M21 で透過を外した）。
- **帯（ヘッダーやキャンバスの操作帯）の中で伸縮を引き受ける要素は1つに限る。** 長くなりうる要素（フォルダパス、ファイルタイトル等）だけを `min-w-0`／`truncate` で伸縮させ、アイコンボタンや操作ヒントなど他の要素は `shrink-0` で幅を固定する。**M14** はヘッダーの `flex` 子要素すべてが既定の `min-width: auto` を持っていたため、長いフォルダパスが縮まずに右側の操作群を画面外へ押し出す欠陥を踏んだ。伸縮する要素を1つに絞り、他を `shrink-0` にすることで再発を防ぐ。

## 10. 操作言語（キーボード＋マウス）

### 位置づけと原則

- キーボードとマウスは役割の違う両輪。**キーボード＝入力する速さ**、マウス＝構造を操作する自然さ（動かす、並べ替える、俯瞰する、画面共有で指し示す）である。
- **操作は発明しない。デファクトスタンダードに従う**（独自ジェスチャは学習コストと不具合の温床）。参照先はUIの構造で決まり、キャンバス系は Miro / Figma、表系は Excel / スプレッドシート、リスト系は一般的なリストUIに準拠する。

### キャンバス

- **ロジックツリーとシーケンスはキャンバス**（ズーム・パンする自由な面）として作る。横に伸びる構造は通常スクロールでは破綻するため。
- 標準操作は、Ctrl+ホイール＝カーソル中心ズーム、Space+ドラッグまたは中ボタン＝パン、空白ドラッグ＝矩形選択、Shift+クリック＝追加選択、ドラッグ＝移動、ダブルクリック＝テキスト編集、右クリック＝コンテキストメニュー。
- **自動レイアウト（データに座標を持たない）か自由配置かはツールごとに決め、自由配置は安易に選ばない**（「図は導出」の思想とGit diffのノイズに関わる）。ロジックツリーは自動レイアウトで、座標・幅・折りたたみ状態のいずれもデータに持たない。
- **マウスドラッグは座標の編集とは限らず、構造の編集を入力するジェスチャとして使える**（親の付け替えで書き換わるのは `parentId` と配列インデックスだけ）。したがって「マウスで動かしたいから自由配置にする」は理由にならず、自由配置が要るのは位置そのものに人間が意味を込める場合に限る。
- **ノードの中のテキスト編集は「ダブルクリックで編集モードに入る」形にしなくてよい。** 入力欄を常に `<textarea>` にしフォーカス＝編集中とする（会議のスピードでは1手が邪魔）。帰結として Space（パン）はノードにフォーカスがある間は文字入力に取られる。
- 状態遷移の図は読み取り専用の導出物とし、編集面は表とする。用語集はリスト。

### キーボード操作：二層構造

「全ツールで操作を揃える」の実態は「**同じ構造には同じ操作**」であり、層を分けて優先規則を明確にする。

グローバル層（全ツール厳守。UIの構造に依存しない）：

- **Undo/Redo**：Ctrl+Z ／ Ctrl+Shift+Z（Windows/Linux では Ctrl+Y も Redo、macOS は Cmd+Shift+Z のみ）。履歴は開いているファイル単位・メモリ内のみで、それ以前への復帰はGitの担当（5章）。
- **Esc**：編集中は編集キャンセル、非編集は選択解除。

構造依存層（追加・削除・移動・並び替えの意味をどのキーで提供するかはUI構造に依存する）：

- **階層・リスト系の標準**：Enter＝兄弟／直後に追加、Tab＝子追加、空欄でBackspace＝削除、Alt+↑↓＝並び替え、矢印＝ノード間フォーカス移動。ロジックツリー、シーケンス、用語集はこれに従う。
- **表系（遷移表）はExcel準拠が優先**で、共通セットのキーをExcelのデファクトと衝突する形で持ち込まない。
- **各ツールが提供すべきは意味の集合**（追加・削除・移動・並び替え）で、キー割当は属する構造ファミリーの流儀に従う。自ツールに存在しない意味は提供しない（用語集はフラットなので Tab はセル間移動）。
- **この分岐は共通フックの `KeyContext.hierarchical` として持ち、ツール側で分岐させない**（置いた瞬間、一元化が名目だけになる）。真なら `Tab`＝子追加・`←`＝親へ移動・`→`＝子へ移動、偽なら `Tab`＝セル移動・`←→`＝キャレット移動のまま。
- **`hierarchical` は「キャンバスかどうか」ではなく「子という意味があるかどうか」**（シーケンスはキャンバス系だがフラットなので `false`）。`←→` はキャレットが端にあるときだけ構造の移動に切り替え、加えて `arrowsOwnedByField` を見る。
- **`Shift+Tab` には意味を与えない**（キャンバスから Tab 順で抜ける経路として空けておくため）。
- **横に並ぶリストは `KeyContext.horizontal` で扱う**（`Alt+←→`＝並び替え、素の `←→`＝キャレット端で隣へ移動、`↑↓` は関与しない）。`hierarchical` と同時に `true` にしない。
- **主修飾キー＋`Enter` は `toggle-item-state`（欄の状態トグル）。** 写像はツールごとに違ってよく、コアが解決するのはコマンド名まで、意味はツール側の `runCommand` が決める。
- **コマンドの語彙をコアに増やす案は採らない**（意味の集合を決めるのはツール側という原則に反する）。写像を足すツールは画面のヒント（`KeyHints`）も足すこと。
- **構造依存層の写像はコアを触らずツール側で足せる。** 「移動先が無ければ生やす」のような拡張はツール側が意味を足すだけで、`resolveCommand` は変更しない。
- **`Shift+Enter` / `Alt+Enter` が「アプリは関与しない」（＝ブラウザ既定のセル内改行が生きる）ことは不変条件**（用語集の定義・備考がそこに乗っている）。縛るのは `resolveCommand` であって、「どの欄でも必ず改行できる」ことまでは約束しない。
  - 複数行を許すと版組が破れる欄はツール側が `e.key` を見て改行を止めてよいが、**明示的な例外なので適用範囲と理由を書き残すこと**（現在の唯一の例外は課題ツリーの仮説タイトル）。
- **導出表示（ソート・フィルタ適用中）では、表示順とデータ順の対応が崩れる操作を無効化する。** 並び替えだけでなく行の追加も含む（挿入した行が絞り込みに掛からず、見えないまま増えるため）。
- **キーでしか到達できない「意味」を残さない。** 追加・削除・並び替えにはマウスの入口も用意する（追加ボタンは常時出し、押した行は末尾に足す）。
- **例外として、マウスでしか到達できない意味を明示的に許すツールがある。** 課題ツリーの仮説側の欄は `resolveCommand` を通らない。課題の追加・削除・移動は反射的に打つ操作だが、仮説は主張をゆっくり言葉にする作業で、打鍵数より目的の欄に迷わず届くことが効くためである。

### 実装規約

- **キーボード・マウス処理は共通フック／モジュールに一元化し、ツールごとのハンドラ自前実装を禁止する**（キーボードは `src/core/keyboard/`、マウスは `src/core/column-resize.ts`）。挙動差の構造的再発防止であり、修正も1箇所で済む。
- マウス側は**純関数（値の計算）とフック（ポインタの配線）を分け、ツール側は `getHandleProps(index)` を貼るだけ**にする。ドラッグは `pointerdown` で `setPointerCapture` を取り、window にリスナーを張り替えない。
- **ポインタ操作を作ったらキーボードからも同じ操作を提供する**（列幅は ←→ で16px刻み、Home で既定に戻す）。アクセシビリティのためであり、jsdom はレイアウトも `setPointerCapture` も持たないのでキーボード経路が値の反映を検証できる唯一の入口になるためでもある。
- **例外：キャンバスのズーム・パンは d3-zoom に委ねる**（ホイール・ピンチの正規化と倍率を保った座標変換という規約の外側の仕事を持つ）。この例外はビューポートの `{x, y, k}` に限り、値の編集のドラッグは引き続き `setPointerCapture` を取る。
- **キャンバスのズーム・パンにはキーボード経路を作らない。** 代替は新しいノードへの自動追従で、キーボードだけで打っている限り視点は自ら動く。ズーム倍率は閲覧の都合なので、要ると分かった時点で同じ関数を呼ぶ2つ目の入口として足す。
- **キャンバス系ツールの実装構成は全ツール共通。ノードは絶対配置の DOM、エッジは SVG、ビューポートは d3-zoom。** 3レイヤ（背景／エッジ／ノード）に同一の `translate(x, y) scale(k)` を当てるので、座標系のズレは原理的に発生しない。
- **キャンバス（描画・操作）ライブラリ（React Flow / tldraw 等）は採用しない。** イベント系を乗っ取るライブラリが操作言語の一元化規約と衝突すること（Space がパンに、Backspace が削除に食われる）と、自動レイアウトを採る以上ライブラリの中心価値が不要になることの2点による。
- **レイアウト計算ライブラリ（elkjs / dagre）は別の話で、不採用の理由も別。** ロジックツリーで採らなかったのは、どちらも任意の有向グラフ向けで厳密な木にはその強みが要らないことと、elkjs がバンドル1MB超・Web Worker 前提の非同期APIであることの2点である。
  - **任意グラフを描くツール、とりわけ状態遷移図では再検討の余地がある。** 「ロジックツリーが採らなかった」を「facet では使わない」と読まないこと。全文は [`logic-tree/logic-tree-canvas-tech-notes.md`](logic-tree/logic-tree-canvas-tech-notes.md) 論点2。
- **ノードの中を SVG にしない**（`foreignObject` を使わない）。Windows のブラウザで IME の変換候補ウィンドウの位置ズレ・フォーカス喪失が起きるため。
- **IME対応**：変換中のキーイベントは操作言語の対象外とする。変換確定のEnterが「追加のEnter」に誤爆する問題は日本語入力アプリ最大の地雷であり、仕様として明記する。
  - **`isComposing` だけでは足りない。** WebKit は composition 系のイベントを keydown より先に投げるため、変換を確定した Enter は `isComposing: false` で届く（Windows の WebView2 は仕様どおり）。
  - **主たる判別材料は `keyCode === 229`**（IME が食った打鍵の予約値で、離した keyup は本来の 13 に戻る）。`src/core/keyboard/ime.ts` が持ち、操作言語の入口が `isComposing` へ畳み込むので各ツールのセルも額縁も一度に守られる。
  - 補助として `CellInput` が「直前の `compositionend` から前後 100ms」の窓も見る。**この窓は絶対値で見ること**（keydown の時刻は compositionend より古いことがある）。
  - **各ツールの keydown ハンドラに同じ判定を撒かないこと**（次に増えるツールが落とす）。
- **境界規則（端末ペイン）**：端末ペインの中で発生したキー入力は操作言語の管轄外とし、`keydown` ハンドラの先頭で発生元を見て早期returnする（これが無いと端末の `Ctrl+Z` がfacetのUndoを横取りする）。帰結として、端末ペインの開閉・フォーカス脱出にショートカットは割り当てない。
- **境界規則の裏返し（右クリック）**：ペイン内の右クリックは facet が握り、OS の既定メニューを止めて、選択があればコピー・無ければ貼り付けの1動作に置き換える。止める範囲はペインの中だけで、エディタ側のテキスト欄では何も変えない。
- **境界規則（モーダル）**：モーダルが開いている間はエディタの操作言語を停止し、キーはモーダル側が取る（Escの取り合いを構造的に排除）。停止の対象はポインタ操作も含み、フックに `enabled` を渡す形にしてキー監視と d3-zoom の `filter` の両方が見る。
- **境界規則の例外（セルのドロップダウン）**：セルが開くドロップダウンはモーダルに数えず、キャンバス停止を掛けない。代わりに同時に1つのセルしか開けない構造にし、キー入力の遮断は `FocusScope` 単層に任せる（アプリ側の防御を持たないことは既知のトレードオフ）。
- **境界規則（テキスト編集中）**：編集中はキーイベントを編集対象が取り、操作言語は停止する。例外は編集境界キー（Enter／Tab／Esc／空欄Backspace）と Undo/Redo で、これらは操作言語が解釈する。
  - Undo/Redoを編集中もアプリの履歴が取るのは、制御された入力欄ではブラウザ標準のUndoがReactの再レンダリングと食い違うため。Space・矢印・Alt+↑↓は編集対象のものとする。
- **拡張規則**：ツール固有キーの追加は可。グローバル層および自ファミリーの標準キーと衝突する再定義は禁止。

## 11. 検証の観点（ドッグフーディング）

- **第一関門：会議のスピードに入力が追いつくか。** 操作言語（10章）とキャンバス操作の使用感を含めて評価する。
- **AI連携の価値検証。** Skill（4章）による下書き生成・ヒアリング型データ作成・レビューが「ゼロから入力するより速く・漏れが減る」かを確認する。文章校正系（用語チェックのAI層）は費用対効果が高い着手候補。
- **成果物が仕様書として機能するか。** 貼り付けたMarkdown/Mermaid出力（8章）が実際の仕様書として読まれ・使われるかを確認する。出力実装は「使う」と確定したツールから着手する。
- **色の識別性。** P型・D型色覚での意味色の色差は機械検査で担保しているので、残る検証は実機で黄（欠落）と赤（無効）が分かれて見えるかと、会議で投影したときの読みやすさの2つ（9章）。
- **チーム展開はクオリティ確認後。** 展開時には配布方法（7章）を再検討する。
