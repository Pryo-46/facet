# 仕様整理ツール詰め合わせ：全体方針ドキュメント

全ツールに共通する設計判断の「正」。個別ツールの詳細仕様は `docs/<tool>/` にある。

## 1. 背景と目的

文字だけの仕様書は、分岐・時系列・状態・用語という多次元の情報を一次元の文章に直列化している。読むたびに脳内でグラフ構造を再構築することになり、ワーキングメモリを消耗する。

これを解くため、「人間は構造化されたUIで入力し、ツールが網羅性の担保・描画・構造化テキスト出力を担う」会議用ツール群を作る。利用者は作者本人と、**ツールの利用者として設計に含める AI（Claude）**である（4章）。

普及戦略は、会議で実際に使う姿を見せることを最良のデモと考える。狙いは、PdM とエンジニアが共に読める「中間言語」としての価値である。

## 2. ツール一覧

1. **ロジックツリーエディタ** — 分岐・パターンを網羅する木を作る。（エディタ・登録 Skill・Markdown 出力・Miro のマインドマップとのクリップボード交換まで実装済み）
2. **シーケンスエディタ** — 時系列の直列シナリオと、全ステップに立つ「失敗したら？」の問いを扱う。異常系は矢印で描かず、呼び手の知識状態で閉じた問いのスロットとして立てる。（エディタ・登録 Skill・Markdown 出力まで実装済み。詳細は [`sequence/sequence-design-notes.md`](sequence/sequence-design-notes.md)）
3. **状態遷移エディタ** — 状態×イベントの網羅とテスト導出を行う。（未実装）
4. **用語集エディタ** — 用語の型定義と表記ゆれ検知を担う、他ツールが参照するマスタデータ。（エディタ・登録 Skill・Markdown 出力まで実装済み。詳細は [`glossary/session-notes.md`](glossary/session-notes.md)）
5. **エラーカタログエディタ** — エラーの一覧と対応方法を整理する。読み手も出力先も他ツールと異なるので独立モジュールとする。（エディタ・登録 Skill・Markdown 出力まで実装済み。詳細は [`error-catalog/error-catalog-session-notes.md`](error-catalog/error-catalog-session-notes.md)）
6. **課題ツリーエディタ** — PoC で「試さないと分からないこと」を分解し、仮説と検証の結果を記録する。仮説の判断は未決・支持・棄却・保留・見送りの5語で、未決は判断イベントが0件であることから導出するため保存しない。（エディタ・登録 Skill・俯瞰の表現まで実装済み。出力は未実装。詳細は [`issue-tree/仮説検証モジュール-設計ノート.md`](issue-tree/仮説検証モジュール-設計ノート.md)）

**PRD のような自由記述中心の文書はツール化の対象にしない**（構造化度が低く、会議速度で入力して下流の仕様から指される形にならない）。課題ツリーがこの理由に当たらないのは、「課題 → 仮説 → 検証 → 結論」という構造がもともと存在するからである。

既存のプロトタイプ（`docs/issue-tree/仮説検証モック.jsx`）はイメージ確認用であり、データ構造・実装とも実用版には引き継がない（5章・7章）。

## 3. 全ツール共通の設計思想（変更する場合は理由を明記すること）

**入力速度最優先。** 会議の議論は秒単位で流れ、入力がもたつくと「後でまとめよう」となってツールは使われなくなる。共通の操作言語（10章）で全ツールの操作を揃え、AI活用（4章）で入力そのものを省略する方向へ拡張する。

**網羅性の担保はツールの仕事。** 未定義・未決定の箇所が物理的に見える構造にする（ツリーの葉数バッジ、遷移表の赤セル、用語チェックの赤ハイライト）。機械的チェックの上に、どの未定義が実務上危ないかというAIの意味的チェックを重ねる（4章）。

**「未定義」と「決めた上で無効」を型で区別する。** 文章仕様書ではどちらも「書いてない」に潰れる。デザイン上もこの区別を色の意味論として維持する（9章）。

**正となるデータは一つ。図は導出。** 状態遷移エディタが典型で、編集できるのは表だけ、図は自動生成の読み取り専用にする。この思想はDB不採用の判断（5章）、読み手ごとの出力の出し分け（6章）、キャンバスの配置方式の判断基準（10章）にも適用する。

**状態も導出する。** 導出元のない手動ステータスは更新忘れで嘘をつくため、ミュータブルな状態フィールドをデータに持たず、イベント列の最新要素から毎回導出する。祖先の見送りによる配下の警告抑制のような派生状態も、同じ理由で保存しない。

**構文は人に覚えさせない。構文は交換形式である。** 人間は直感的UIで入力し、ツールが Markdown / Mermaid を吐く。スキーマ定義された JSON は出力にとどまらず AI との双方向の交換形式であり、人間には見せず機械同士は構造化データで話す。

## 4. AI活用方針

### 基本構造：AIはアプリの外で動き、接点はファイルのみ

- AI（Claude）はアプリに組み込まない。**APIの呼び出し・アプリ内AI機能は作らない。**
- ただしAIを起動する場所は提供する。facet は端末のホストであって、AIの対話相手ではない。
- 判断基準は「**Claudeの出力を読んで何かを決める**」実装が現れたら原則の違反、というもの。端末タブの名前を会話内容から付けないのはこの帰結。
- 端末ペインへ渡すのはファイルの参照文字列（`@相対パス`、プロジェクト外なら絶対パス）だけで、**facet はファイルの中身も会話の内容も読まない。** 渡す口は、選択中ファイルを開いたとき・一覧の `@` ボタン・ドラッグ＆ドロップの3つ。
- AIは Claude Code / Claude Desktop 上で動き、フォルダ内のJSONを直接読み書きする。責務は「アプリ＝人間用の高速エディタ＋検証器＋描画器、AI連携＝Skill群という別の成果物」と分ける。
- **MCP的な書き込みツールは作らない。** ファイル直書き経路は塞げず二段検証は結局要るので、経路の多重化と第三の成果物を足すだけになる。

この構造はスキーマの自己記述性・二段検証・プロジェクト＝フォルダ（いずれも5章）に支えられている。

### Skill群：AIを対話的な共同作成者にする

用途は4つ。ヒアリングしながらデータを組み立てる対話的データ作成（登録 Skill）、会議メモや文章仕様書からの下書き生成、網羅漏れ・到達不能状態・優先度のレビュー、ルールベース照合の上にAI層を重ねる用語チェックの二層化である。**AIが担うのは「どの未定義が危ないか」。**

**Skill には2種類ある。** 登録 Skill はプロジェクトフォルダの JSON を作り、接点はファイルだけという構造に乗る。`palette-retheme` はアプリ自身のソース（`src/styles/palette.css`）を触る側で、検証はアプリのテストが行う。

#### 同梱スクリプト

ID捏造・不正データの予防として、各Skillに ID採番と書き込み前検証のスクリプトを同梱する。

- ID採番は英数字62文字・10文字の nanoid（5章）。**手順書に「IDは必ずこれで採番せよ」と明記する。**
- 各登録 Skill は `<Skill>/schemas/<名前>.schema.json` に原本のバイト一致コピーを持ち、一致は `src/core/skill-schema-copy.test.ts` が強制する。**配布されるのは `.claude/skills/` だけで、リポジトリの `schemas/` は出荷先に届かないため。**
- スキーマの差し替え経路（引数・環境変数・上向き探索）は持たない。検証は ajv の standalone 生成物に焼き付いており、差し替えても効かない。

#### アプリのロジックを Skill と共有する標準

同梱 Skill はコピーされて実行されるので実行時に `src/` は無く、手で複製すると追従漏れが残る。したがって**値 import を持たないファイルに限り、原本からビルド時に `.mjs` を生成して同梱する。**

- 生成は `scripts/gen-skills.mjs` が型注釈を落として `.claude/skills/<skill>/scripts/generated/` へ書き出す。契機は `pretest` / `prebuild` / `predev` / `prepare` で、生成物は追跡しない。
- 原本の制約は「値 import・相対 import・消去できない構文を持たない」。遵守は `scripts/gen-skills.test.mjs` が検査する（判定は `src/core/import-analysis.ts`）。
- どの Skill がどの共有ソースを要るかは手書きの表 `SKILL_SOURCES` で宣言し、**`BUNDLED_SKILLS` から導出しない**（導出は恒真式になる）。
- 変換の健全性は**出力の一致**で見る。生成物を import してアプリ側と同じ結果を返すこと、CJS の `require(` が残らないことを確かめる。
- **JSON Schema だけは生成の対象ではない**（実行時にそのまま読む JSON だから）。
- 共有している原本は `src/core/canonical.ts` と、ツール固有の導出3本（`src/modules/sequence/questions.ts`、`src/modules/issue-tree/derive.ts`、`src/core/canvas/flat-tree-core.ts`）。原本がどの層にあるかは要件ではない。
- **新しいツールの登録 Skill では導出ロジックを手で複製せず、この形に寄せる。** 導出ロジックは制約の下で書き、同梱予定である旨と制約を原本の JSDoc に書いておく。
- **予定が立っていないファイルを共有したくなったら、原本を曲げず、共有が要る部分を純粋な下層として切り出す**（`flat-tree-core.ts` がその形）。
- 書き出しスクリプトが配列順を正規化するかは、並べ替えロジックを共有できるかで決まる。共有できれば持たせ、できないツールは配列順を触らない。
- **整合性と未記入の報告は「アプリが開くことになるファイル」の並びで行う**（警告は配列位置でノードを指すため）。契約は「出力を `--check` へ戻したら同じ位置を同じ言葉で言う」。

#### 共有できないロジックは実行結果の突き合わせで縛る

整合性検証（`src/modules/<tool>/consistency.ts`）は値 import を持つため同梱できず、各 Skill の書き出しスクリプトが判定ごと手で複製している。

- 縛りは実行 smoke テスト。書き出しスクリプトを `--check` で spawn し、アプリ側の `message` が stdout に逐語で現れることを検査する。
- **契約は「アプリの message が現れること」**で、独自の警告を足すのは妨げない。複製は消えないので `consistency.ts` の改訂には各スクリプトの書き替えが要る。
- 縛りは `rule` 名の集合だけでなく `message` の件数にも掛ける（同じ `rule` を2箇所で出すツールがある）。
- 導出ロジックを共有している Skill では、集計結果の逐語一致も併せて固定する（`message` の一致は共有物が空でも通る）。

#### Skillの配布と同期

同梱 Skill はアプリの resources に入っており、**プロジェクトフォルダを開いたときに1回**（端末タブを開くたびではない）`.claude/skills/` へ置き直される。

- 同梱物をすべて読み終えてから消す。読み出しに失敗すれば何も消さない。
- 読み出しは `node_modules` へ降りない（`src/core/skill-sync.ts`）。非 UTF-8 な依存が1つ混じるだけで読み出しごと throw するため。
- 消すのは同梱する名前のディレクトリの中身だけで、ユーザーが足したSkillも `node_modules` / `package-lock.json` も消さない。
- **消せない要素が1つあっても中断しない**（1件の消し残しより Skill 全体を失うほうが重い）。
- `.gitignore` は同期対象に含める。mac ではこれを書くために `allow_skill_dir`（`src-tauri/src/lib.rs`）が要る（7章）。
- Skill群は正式な成果物としてバージョン管理し、**スキーマ変更時はSkillも追従させる。**

### 読み方ガイド：静的な README-for-AI.md を配る

「空欄・`undecided` は未決の意思表示であり埋めてはいけない」といったJSONに書かれていない読み方の規約は、ユーザーのフォルダには無い。これを、**AIがフォルダを読みに行った瞬間に目に入る静的な配布物**として配る。

- プロジェクトフォルダ直下に `README-for-AI.md` を置く。原本は `src/core/reading-guide.md`。
- 原本はTauriのresourcesではなく Vite の `?raw` importでバンドルへ取り込む（二重管理を増やさないため）。
- フォルダを開いたときにべき等に書き出す（無ければ作る／一致していれば触らない／不一致なら上書き）。契機を Skill 同期と分けるのは、外部の Claude Code から読まれる経路があるため。
- **アプリはこのファイルを読まない。書くだけ。**

### アプリ側への要件：外部変更への対応

- アプリの開いているファイルを外部の書き手が書き換えることを前提とする。これは**外部エディタ一般への対応**であり、AI固有の結合ではない。
- 監視はファイル単位ではなくフォルダ単位とする（外部でのリネームも検知するため）。
- **自己書き込みの除外は「台帳との内容比較」で行う。** 最後に読み書きした内容をパスごとに保持し、再走査で読んだ生バイトと1バイトも違わなければ自分の書き込みと判定する。
  - 時間窓やフラグは使わない（遅れて届くイベントで誤検知し、速いイベントを取りこぼす）。
  - 監視イベントの種類やパスは一切見ず、「何か起きた」だけを契機に再走査する。
- 未保存編集がなければ再読み込みしてトーストで知らせ、**このときUndo履歴は破棄する**（残すと Ctrl+Z が外部の変更を巻き戻す）。
- 取り込み前の内容は一時退避し、トーストに「取り込み前に戻す」アクションを付ける。
- 未保存編集があれば二択ダイアログ「自分の編集で上書き」／「外部変更を取り込む」を出す。**VSCode級のマージUIは作らない**（退避とGitという復元手段があるため）。
- 二択ダイアログが守るのはデバウンス窓の数秒間だけで、衝突の定義はタイムスタンプの前後ではなくデバウンス窓の重なりとする。

## 5. データモデルと永続化

### ファイル構成：プロジェクト＝フォルダ

- 1つの仕様書プロジェクト＝1フォルダとし、その中にツールごとのJSONファイルを置く。
- **紐付けは「同じフォルダにある＝同じプロジェクト」という物理配置で表し、設定ファイルによるパス管理を持たない。** マスタ参照は「同一フォルダ内の該当 `type` のファイルを見る」で閉じる。
- 同種ツールの複数ファイルを許すが、**単一性を宣言したツールはプロジェクトにつき1つ。** 該当は他ツールから参照されるハブ、すなわち `glossary` と `errorCatalog`。ロジックツリーと課題ツリーは論点ごとに分けるのが普通の使い方なので `singleton: false`。
- どの type が単一かはコアにハードコードせず、モジュール側の宣言として持つ（6章）。3つ目の単一マスタが出たときにコアを触らずに済ませるため。
- **ファイル名は識別子にしない**（用語集を含め例外なし）。フォルダ内JSONを走査して中身の `type` で種別を判別するので、自由にリネームしても壊れない。

### スキーマ：JSON Schema を正とする

- 各ツールのデータ形式は JSON Schema で定義し、TypeScript 型はそこから自動生成する。**手書きの二重管理はしない。**
- スキーマはAIへの生成指示と読み込み時の機械検証に直接使うため、自己記述性を持たせる（キー名は省略しない、種別は enum で明示）。
- スキーマの実体はアプリと同梱 Skill で共有し、バイト一致はテストで強制する（理由と機構は4章）。
- **同梱コピーは検証の入力ではない**（検証の実体は4章）。実行時に読まれるのは、`serialize` が正規形のキー順を `properties` の記載順から導出するため。
- プロトタイプの state 構造は叩き台にせずゼロから設計する（構造は信用しない）。
- 全ファイル共通のエンベロープ（必須フィールド）：
  - `schemaVersion`：スキーマの版。**版は type ごとに独立して進める**ので、移行判定とSkillの追従管理（4章）は `type` × `schemaVersion` の組で行う。共通エンベロープの改訂は全ツールスキーマの改訂を含意する。
  - `type`：ツール種別の enum（`logicTree` / `sequence` / `stateMachine` / `glossary` / `errorCatalog` / `issueTree`。ツール追加で増える）。旧アプリにとって未知の値になり得るが、受け皿は6章の前方互換の規定。
  - `title`：表示名。プロジェクトを開いたときの一覧表示に使う。

### バージョン互換とマイグレーション

- 既知 type だが未知の新しい `schemaVersion` のファイルは、**未知 type と同じ扱い**（一覧表示のみ・編集不可）にしレベル1拒否にはしない。知らないツールは一覧に出るのに知っているツールの少し新しいファイルは開けない、という逆転を避けるため。
- 既知 type × 旧 `schemaVersion` のファイルは読み込み時に**メモリ上で**自動移行して開き、ファイルへの反映は最初の編集保存時とする（閲覧しただけでは旧版のまま残る）。
- 移行は検証を飛ばさない。`src/core/load.ts` が `module.migrate(record, version)` を呼び、その結果をスキーマ検証に掛ける。マイグレータの側は形を見ない（見ると検証の規則が2箇所に生える）。
- マイグレータは各ツールモジュールの提供物（6章）。
- **移行は「旧版のファイルが必ず開くこと」を保証しない。** 語彙を落とす改訂では、廃止した値を持つファイルが移行後の検証で弾かれる。
- **語彙を落とす改訂では、読み替えを移行に持たせるか拒んで書き直させるかを明示的に選ぶこと。** 読み替えを足すと「もう無い区別」がデータの中に生き残るため、既定は拒む側。
- 未公開の版は版番号を上げずに定義を差し替えてよいが、**一度出荷した版に対してはしてはならない。**
- 古いSkillが旧版スキーマで書いたファイルもアプリが移行して開けるので、Skill追従の失敗は「移行で吸収される遅れ」に格下げされる（効くのは改訂が「足す」側のときだけ）。

### ID規約（全エンティティ共通）と用語参照

- 形式は `<entityPrefix>_<id>`。`entityPrefix` は小文字英字のみでエンティティ種別を表し、各ツール内の分類enumとは別レイヤー。
- ID本体は nanoid の `customAlphabet` で**英数字62文字（A-Za-z0-9）・10文字固定。** 標準アルファベットの `_` `-` は区切り文字と衝突し、自己記述性とスキーマ検証の正規表現（`^term_[A-Za-z0-9]{10}$`）を汚すため。62の10乗はおよそ 8.4×10^17 通りで、数百レコード規模で衝突の余地はない。
- プレフィクスの粒度はエンティティ単位とし、ツール単位で `node_` に統一しない（状態遷移なら `state_` / `event_`）。具体命名は各ツールの管轄。
- 各ツールの JSON Schema がプレフィクスを正規表現パターンとして宣言し、コアのモジュールレジストリが登録時に重複を検査する。スキーマに書かれていればAIも正しいIDを生成できる。
- **連番IDは禁止。** アプリとAIが並行して要素を追加する設計（4章）では、双方が同じIDを振る衝突が必発する。
- **用語参照**：用語集の各用語に不変ID（`term_` プレフィクス）を振り、他ツールはIDで参照して表示時に名前を解決する。マジックストリング禁止・定数参照のみ、をデータに適用したもの。

### 二段検証

原則は「人間が直せる状態で見せる」で、**拒否は解釈不能な場合に限る**（拒否すると修正に外部エディタが要るため）。

1. **スキーマ検証**（JSON Schema）：構造の正しさ。不合格はレベル1（拒否）＝開けない。
2. **整合性検証**（アプリ実装）：スキーマで表せない、外部キー検証に相当するもの。不合格はレベル2（受け入れて赤表示）＝可視のエラーとして表示し、必要な機能のみ縮退する。編集は可能なので人間がアプリ内で直せる。

レベル2の項目は、参照切れ（発生原因を問わず同一扱いで参照箇所を赤表示）、ID重複、`name` の重複、単一性違反である。

- `name` の重複を整合性検証で受けるのは、同名2件が宣言としての矛盾でありながら、IDが異なるためスキーマの `uniqueItems` では防げないから。判定は NFKC 正規化＋英字大文字小文字同一視で行い、alias 照合と規則を揃える。
- 単一性違反では**そのファイルの解決を伴う操作を停止する**（どちらを正とするかは人間にしか判断できない）。
- **用語集が0個の状態は正常**で、初めて用語登録が発生した時点でアプリが用語集ファイルを自動生成する。用語集不在のまま参照だけあれば参照切れとして赤表示する。
- **検証は全経路共通とする。** 自動保存も外部由来ファイルも同じ検証を通り、経路によって信頼度を変えない。
- **検証スコープはプロジェクト全体とする。** 開いた時点で全ファイルを走査してエラーを一覧に赤バッジで表示し、以後はファイル変更を契機に再検証する。
- **用語削除は即時削除**とし、トーストで参照切れ数を通知する（Undoで復元可）。確認ダイアログも削除ブロックも採らない。参照切れは防ぐものではなく赤く見せるものだから。

### 保存：自動保存＋Git

- 編集はデバウンス付き自動保存でファイルへ書き込み、会議中の保存忘れをゼロにする。
- 「試しにいじって捨てる」の受け皿はGit（コミット＝チェックポイント）とし、アプリ内Undoは直近操作の取り消しに専念する二層構造にする。
- **Git前提のためシリアライズは決定的にする。** diffのノイズを排除して変更履歴を仕様の変更履歴として読めるようにするためで、Skill 側の書き出しとも完全に一致させる。一致は回帰テストで担保する。

#### 正規形の定義（全ツール共通）

| 項目 | 値 |
| --- | --- |
| キー順 | **各スキーマの `properties` 記載順**。ハードコードせず、実行時に `Object.keys(schema.properties)` を読んで並べ替える（`$defs` 配下の入れ子も同様） |
| インデント | 半角スペース2 |
| 区切り | キーと値は `": "`、要素間は `",\n"`（`JSON.stringify(v, null, 2)` 準拠）。空配列は `[]`、空オブジェクトは `{}` を1行で |
| 非ASCII | エスケープしない（`\uXXXX` にしない） |
| 改行コード | LF |
| 末尾改行 | あり（1つ） |
| エンコーディング | UTF-8（BOMなし。読み込み時は除去する） |
| 配列順 | 書き換えない（UIの並び順が正） |

- キー順の「正」はスキーマファイル一つに置く。properties を並べ替えれば正規形も自動追従する。
- 改行コードは**プロジェクトフォルダ雛形に `.gitattributes`（`*.json text eol=lf`）を同梱して担保する。** これがないと `core.autocrlf=true` の環境でCRLF化し、書き戻すたび全行diffになる。雛形生成はプロジェクト作成機能の責務。
- 参照実装は `JSON.stringify(reorder(value, schema), null, 2) + "\n"` の UTF-8 バイト列。他言語で書く場合もこれに一致させる。
- **正規化の責務はアプリが持ち、タイミングは「書き込み時」とする。** 自分が書くときは必ず正規形で書き、読み込み・閲覧では書き戻さない（閲覧だけでGit diffが出ると目的自体を毀損する）。
  - 帰結として、外部の書き手の生ファイルは次の保存まで非正規のまま残り、最初の意味的編集のdiffに正規化差分が混ざる。これは許容する。
  - Skill側の出力仕様にも正規形を含めるが、それは緩和策であり保証はアプリ側にある（「書き手を信用せず受け口で保証する」原則）。

### DBを採用しない理由（再検討時のために残す）

- AIとのラウンドトリップが前提である限り交換形式としてのJSONとスキーマ定義は消えず、DB採用は「DB⇄JSON変換層」を追加するだけになる。
- DBの外部キー制約が守るのはDB内部のデータであり、AI生成物の読み込み時検証は結局アプリ側で書くことになる。
- このツールのデータは「アプリの状態」ではなく「文書」である。フォルダコピーで持ち運べる・Gitで差分が見える可搬性を優先し、規模（1プロジェクト数百レコード程度）にもDBの必然性がない。
- 将来、全プロジェクト横断検索等の要求が出たら、正はJSONのままSQLiteを検索用インデックス（導出データ）として足す。

## 6. アーキテクチャ：統合形態

### 決定：単一アプリ（ファイルベース統合）

1つのTauriアプリがプロジェクトフォルダを開き、中のJSON一覧から任意のファイルを開いて編集する。エディタ部分はファイルの `type` に応じて切り替わる。**別アプリに分けて配布する方式は採らない。** 用語集のID解決・整合性検証・共通コンポーネントは全ツール共有のロジックであり、分けると同じコードを何度も配布・更新する保守不利だけが残るためである。

ファイル一覧の額縁機能：

- **新規作成**（`type` を選ぶ）。衝突しないファイル名の判定はディスクに問い合わせる。走査時のスナップショットで決めると、走査後に外部で増えたファイルを黙って上書きするため。
- **削除**（OSのゴミ箱へ移動し、完全削除はしない）。単一性違反（5章）等の解消をアプリ内で完結させるため。
- **検証エラーの赤バッジ表示**（5章）。
- **選択中ファイルの `title` の編集。** 名前の帯は額縁が持ち、モジュールのエディタは `title` を描かない（キャンバス系には置き場所が無く、モジュールごとに実装すると散る）。名前の実体は JSON の `title` でファイル名は変えず、書けないファイルでは読み取り専用にする。
- **一覧の行は主が `title`、副がファイル名**（`title` が空なら `(無題)`、読めないファイルはファイル名に落ちる）。
- **一覧は種類ごとにまとめる。** 見出しの順はレジストリの登録順、未登録の type はその後ろに type 文字列の昇順、読めないものは最後。グループ内は `title` の日本語ロケール順で、五十音順ではない（読みはデータに無い）。
- **用語のインライン登録**を共通コンポーネント要件とする。他ツールのエディタで用語参照を入力する場面から、その場で新規用語を登録できるようにする。

### 拡張要件：ツールは増える前提で作る

新ツールの追加を「コアの改修」ではなく「モジュールの追加」にする。各ツールは次の8点を提供する。

1. `type` 識別子（enumへの追加）
2. JSON Schema（ID規約のプレフィクス宣言を含む。5章）
3. エディタコンポーネント
4. 整合性検証ルール（スキーマで表せない検証）
5. 出力ロジック（`outputs`：`OutputProfile` の配列）
6. マイグレータ（旧 `schemaVersion` から新版への変換。5章）
7. 単一性フラグ（5章）
8. 表記ゆれ検知の対象フィールドパス一覧（検知の実行はコア）

加えて**空文書の雛形 `createEmpty(title)` を提供する**（額縁の新規作成は `type` からモジュールを引くため、置ける場所はモジュール側しかない）。表示名とアイコン（`displayName` / `icon`）もセットで持ち、`icon` は `ComponentType<{ className?: string }>` で受けて `LucideIcon` 型は書かない（コアを lucide に依存させないため）。

#### 出力プロファイル（規約5）

- `OutputProfile` は `id` / `label` / `fileSuffix` / `toMarkdown` を持つ。`fileSuffix` を `label` から導出しないのは、表示名は画面の都合で変わるのに対しファイル名はGitに残る側だから。
- **`toMarkdown` は副作用を持たない純関数とする。** 額縁がコピーと `.md` 書き出しの両方に同じ関数を使うため、モジュール側がファイルやクリップボードに触ってはならない。
- **規約は「0本以上」で、出力を後の段階に回すツールは `outputs: []` を宣言する。** 額縁は `outputs[0]` が `undefined` なら書き出し・コピーの両ボタンを `disabled` にする。
- **読み手ごとにファイルを分けず、1つのデータから出し分ける**（分けた瞬間に二重管理が発生する）。
- 複数プロファイルを持つツールが宣言するのはフィールドの並び1本で、画面の列と出力の列はそこから導出する。列セットを2箇所に書くと片方だけ直したときに黙ってずれるため、`OutputProfile` には列を持たせない。
- 形式ごとにプロファイルを割らない（シーケンスもロジックツリーも図と表を1本の Markdown にまとめる）。

#### 任意スロット

規約の点数を増やさずに足せる任意スロットが3つある。**宣言しないツールに義務は生じず、額縁はスロットの有無だけでボタンの活性を決めてツールの `type` を名指ししない。** 後ろの2つが `OutputProfile` に乗らないのは、あちらが「Markdown 1本を返す純関数」＋ `.md` 書き出しを前提にしているためである。

- `describeIssueEffect`（`OutputProfile` の任意メンバ）：整合性エラーがあるまま出力したとき何が起きるかを述べる1文を返す（帰結はツールごとに違い額縁が文面を持てない）。額縁はレベル2の赤があるファイルの出力時に確認ダイアログを挟み、この関数があれば文面を本文に足す。
- `clipboardExchanges`：外部ツールとのクリップボード交換で、各交換は `toClipboard` / `canImport` / `fromClipboard` の3点を持つ。出力が HTML とプレーンテキストの2つになり、入力（貼り付けからの取り込み）の口が規約に無い。
- `tableExport`：表形式コピー。`options`（ダイアログに出す設定項目の宣言）と `variants`（読み手ごとの出し分け）を持ち、各 `TableVariant` は `toTable: (data, options) => Table` を持つ。出力が TSV と HTML の2つで1本の文字列に収まらず、`.md` 書き出しに意味が無く、設定を引数に取るので `toMarkdown` という名前が嘘になる。
  - `Table` は `header` / `rows` の2つの `readonly string[]` だけの形とし、TSV 変換と HTML 変換はコアが1つずつ持つ（`src/core/table-tsv.ts` / `src/core/table-html.ts`）。クリップボードへは両方を同時に載せ、貼り先が自分で選ぶ。

**クリップボードコピーは画面の絞り込みに追従し、`.md` の書き出しは全件のまま変えない。** クリップボードは一時的な動線だが、ファイル書き出しは成果物を残す動線であり、絞り込んだままの `.md` は一見完全な成果物の顔で Git に残るためである。報告は `EditorProps` の任意コールバック `onVisibleIds` で行い、間引きは額縁ではなく出力関数の内側（`visible?: VisibleRows` 引数）で行う。額縁が先に間引くと、データ配列の位置で振る `No` が振り直されて画面と食い違うためである。

#### コアが持つもの、モジュールが持つもの

- **整合性検証の指摘の一覧は額縁が出し、モジュールは出さない**（`src/components/IssueBanner.tsx`）。モジュールが `issues` を受け取るのはセル・行・ノードの赤表示のため。額縁がエディタの外に出すので、指摘が増えても図や表が押し下げられるだけで覆われない。3件までを出し、超えたぶんは「他 N 件を表示」で畳む。
- **列を持つツールの共通機械はコアに置く**（`src/core/list-editor/` と `src/core/duplicate.ts`）。モジュールが持つのは列データとフィールド宣言だけ。抽象の粒度は純関数＋小さなフック1本とし、「列定義を渡すと全部返す」1本には集約しない。
- **表のセルのエスケープ規則は照合規則と同じくアプリ内で1つだけ**とし、ツールごとに書き直さない（`src/core/markdown-table.ts`）。食い違うと「あるツールの出力だけ表が割れる」ことになる。
- **キャンバス系ツールの共通土台は `src/core/canvas/` に置く。** 対象はビューポート・測定層・フォント読み取り・平坦木の組み立て・木のレイアウト（`layoutTree`）・エッジのパス生成（`edgePath`）の6点。
  - 木のレイアウトは「木を描くツールのための関数」としてコアに置く。シーケンスの積み上げ型レイアウトは性質が異なるので各モジュールに残す。
  - **モジュールに残るのは、箱の寸法定数とそれに対応するクラス定数、そのツール固有の畳み方、エッジの SVG レイヤ。** 課題ツリーは課題を1つのブロックとして畳んで寸法を `layoutTree` に渡し、`edgePath` は課題ノードの矩形に対して呼ぶ。
  - 抑制された枝は破線にし、**色は `stroke-rule` のまま変えない**（`stroke-grid` はキャンバスの地を塗るトークンなので、その色の線は地と見分けられなくなる）。半透明にする案も採らない。背景の模様のトークンを前景の構造に借りない、という線引きである。
- **表記ゆれ検知はコア機能とする。** ルールベース検知（name / aliases の照合、NFKC正規化、suggestion 区分）の実装はコアに1つだけ置き、モジュールが提供するのは検知対象フィールドの宣言のみ。実装をモジュールに置くと正規化やマッチ強度がぶれ、ツールによって指摘が出たり出なかったりする。
  - 用語集モジュールの役割は照合データの提供であって、検知の実行主体ではない。自由テキストと備考の切り分けは各モジュールの判断とする。
- 整合性検証の責務内訳は、自ファイル内で完結する検証が各モジュール、単一ファイルでは判定できない検証（例：単一性違反）がコア、参照切れ検証が「参照する側」のモジュール。参照される側（用語集）は参照切れ検証を持たない。
- コアはモジュールのレジストリを持ち、`type` からモジュールを引いてエディタ・検証・出力を呼ぶだけにする。レジストリは登録時にIDプレフィクスの重複を検査する（5章）。
- **前方互換**：未知の `type` のJSONに遭遇してもクラッシュせず、「このバージョンでは編集できないファイル」として一覧に表示だけする。古いアプリで新しいプロジェクトを開く事故に備える。

## 7. 技術スタック

### 決定：Tauri＋TypeScript＋Tailwind/shadcn

- **配布形態はTauriデスクトップアプリ（Windows想定）。** 社内でのWeb公開はホスティングの手間が大きいため採らない。チーム展開時に配布方法（社内配布手段、SmartScreen警告への対処）を再検討する。
- **Rustは原則書かない。** ロジックはすべてフロントのTypeScriptに置き、TauriはネイティブAPI（fs, dialog等の標準プラグイン）の提供層としてのみ使う。根拠は3つ。
  1. Rustを要する仕事（重い計算、バイナリ処理）が存在しない。実体は「JSON読み書き＋UI＋検証」で規模は数百レコード。
  2. 実装をAIに委譲してもレビューとデバッグの責任は人間に残る。読めない言語の層は監査不能なブラックボックスになる。
  3. TSとRustに分かれるとIPC境界が生まれ、境界をまたぐバグは診断が難しい。
- 「原則」は禁止ではなくデフォルト。実証された必要（例：数千ノードのレイアウト計算がUIをブロックする）が出た場合は例外を認める。
- プラグインの登録（`lib.rs` の `.plugin(...)` 1行とCargo依存1行）はこの原則の例外ではない。判断もロジックも持たないため。
- **ブラウザ標準の `navigator.clipboard` は使わない。** 権限が欠けたときに実行時に静かに失敗しテストでも検出できないのに対し、プラグイン側なら権限の欠落が capabilities で確認できる。
- **クリップボードの読み取り権限はテキスト（`clipboard-manager:allow-read-text`）だけを与え、HTML の読み取り権限は与えない。** テキストは端末ペインの右クリック貼り付けに要り、HTML は例外5の自前コマンドを通す。

認めた例外は5件。

1. **OSのゴミ箱への移動**（`move_to_trash`）。fsプラグインは完全削除しか持たず、6章の「削除はゴミ箱へ移動」を満たせないため。
2. **PTYのコマンド4本**（`pty_spawn` / `pty_write` / `pty_resize` / `pty_kill`）。端末ペインが本物の端末を要件とし、`tauri-plugin-shell` では raw mode の TUI を成立させられないため。
3. **Skill配置のための fs scope 許可**（`allow_skill_dir`）。fs の実行時 scope は unix既定の `require_literal_leading_dot: true` によりドット始まりの要素に一致しないため。
4. **プロジェクトフォルダの fs scope 再付与**（`allow_project_dir`）。ダイアログが入れる scope はセッション限りで、起動時の復元がダイアログを経由しないため。
5. **クリップボードの HTML 読み取り**（`read_clipboard_html`）。プラグインが HTML の読み取り API を持たないため。

**どの例外も判断を一切置かない。** 実行ファイル名・引数・作業ディレクトリ・対象パス・Skill名一覧はすべてTypeScript側が決めて渡し、Rustの仕事はバイト列と結果を右から左へ流すことに尽きる（Rust側のコードに `claude` という文字列は現れない）。

- 型はJSON Schemaから自動生成する（5章）。**スタイリングはTailwind CSS＋shadcn/ui** とし、デザイントークン（9章）はTailwindの設定に定義してデザインシステムと1対1対応させる。
- **shadcnの適用範囲は「額縁」に限定する**（モーダル、ドロップダウン、ファイル一覧、トースト等）。土台のRadixがフォーカストラップ・キーボード制御の実戦済み実装を持ち、モーダル周りの厄介な挙動をこの層ごと吸収できるため。
- **各ツールのエディタ本体は完全自作する。** 操作言語に合う既製品は存在せず、入力体験のリスクはライブラリでは消えないので設計で抑える（10章）。
- **プロジェクト雛形はリポジトリに `.gitattributes` を置く**（指定と理由は5章の正規形）。

### 決定：配布は GitHub Releases、自動更新は Windows のみ

- 配布は GitHub Releases とし、**Windows のみ updater プラグインで自動更新する**（エンドポイントは `releases/latest/download/latest.json`）。
- **mac を対象にしないのは updater の制約ではなく、未署名の `.app` が Gatekeeper に弾かれる現状が updater の手前にあるため。** 署名は別の意思決定になる。
- **minisign の秘密鍵は1台にしか置かない**（失うと以後どのバージョンからも自動更新できない）。手順は [`release.md`](release.md)。
- 更新の適用はアプリを終了させる（Windows の制約）ので、**利用者が押したときにしか走らせない。**

## 8. 出力・入力戦略

### 入力（インポート）は独立機能を持たない

保存形式がスキーマ定義されたJSONファイルなので、「AIの生成物を取り込む」は「JSONファイルをプロジェクトフォルダに置いて開く」で完結する。**専用のインポート機能は作らない。** ただし読み込み経路には必ず二段検証（5章）を通し、経路による信頼度の差を作らない。

### 出力はMarkdown（Mermaid込み）

- 第一の出力先はNotePMとし、**クリップボードコピーとファイル書き出し（`.md`）の両方**を用意する（コピーは議事録へ貼る最短動線、ファイルはGitに成果物を残す用途）。
- **出力先は必ずしもNotePMではない。** エラーカタログのサポート向け出力は、サポートチームが手書きでサポートサイトを作るための下書きとして渡る。
- **インポート連携はしない。** 更新は自動伝播しないが、前回渡したコミットとの差分をGitで取れば変更行は特定できるので運用で吸収する。
- 出力ロジックはツールモジュールの提供物である（6章）。どういうMarkdownを出すかは各ツールの設計で詰め、本章では枠と共通規約だけを定める。

見出しと並びの規約（用語集・エラーカタログで共通）：

- `##` はエンベロープの `title`、`###` はグループの見出し。**h1は使わない**（NotePMのページタイトルと階層が衝突し、目次はh1〜h3を収載するため）。
- **グループ順は種別 enum の定義順に固定し、スキーマから実行時に導出する。** ハードコードすると enum 改訂時に静かにずれ、順が揺れるとGit上で無意味な差分になる。
- 空のグループは見出しごと省略し、グループ内はデータ配列順に並べる。
- **`No` はデータ配列の位置（`index + 1`）**で、グループごとに振り直さない。画面のNoと出力のNoが食い違うと、会議中に口頭で指す目印として使えなくなる。
- 空フィールドは `（未定義）`、`undecided` は `未分類` として出力し、**負債を出力にも残す**（サポート向け出力でも `未分類` を省略しない）。備考のような検知対象外の自由メモの空欄だけは `（未定義）` にしない。
- 用語集の列は 名称／種別／定義／別名／備考でIDは出さず、エラーカタログの列は `No` ＋ プロファイルの宣言からグルーピング軸を除いたもの。

**表のセルは書き手を信用せずエスケープする。** `\` を先に、次に `|` をエスケープし（順序が逆だと自分が入れた `\` を二重エスケープする）、改行は `<br>` にする。自由記述欄にWindowsパスや正規表現、複数行の値が入ると表が途中で割れて1件まるごと読めなくなるためで、見出しに使う文字列も同様に扱う。

- 状態遷移のJSONは保存形式そのものがC#パラメタライズドテストのデータソースになり得る（「表＝実行可能な仕様」）。専用のテスト用出力を作るかは状態遷移エディタの設計で判断する。

## 9. デザインシステム

### 診断の原則

- **差をつける場所と揃える場所を逆にしない。** 角丸・ボーダー・部品の形は徹底的に揃え、意図した少数の差だけで情報階層を作る。
- **強調の重みは使用頻度に一致させる。** 起動時に1回押すだけの操作を最強調にせず、常時参照する警告の側を強く出す。
- **彩度の予算は意味色にだけ使う。** 地色・見出しの帯・分類ラベルが彩度を主張すると、欠落を示す色の情報量がそのぶん薄まる。
- **密度は行高で稼ぎ、文字サイズでは稼がない。** 行間は削っても情報が失われないが、文字サイズは削ると可読性が直接落ちる。

### 役割トークンとパレットの分離

- **二層構造にする。** 参照するのは役割トークン（意味の名前）だけで、色値は差し替え可能な下敷きである。色値の直書きと役割トークンへの透過は `src/styles/conventions.test.ts` が弾く。
- **配色は `src/styles/palette.css` 1ファイルの書き換えで差し替えられる。** 差し替え後も `src/styles/palette.test.ts` がコントラスト要件（本文 4.5:1、罫線 3:1 等）を検証する。要件の表は `src/styles/palette-requirements.ts`、計算式は `src/styles/contrast.ts` が1本だけ持つ。
- 差し替えの手順は `.claude/skills/palette-retheme/` が持つ。外部テーマから機械的に拾えるのは7つで、残りは候補から人が選ぶ。
- **役割トークンは 20個で、色を持つのは意味だけである。** 面・文字・線は無彩色（C ≤ 0.01）に保つ。
  - 面：`canvas`（地。方眼を敷く）／`surface`（作業する面）／`surface-muted`（一段沈んだ面。選択中タブ・カラム名・旗を掲げた枝）
  - 文字：`ink`／`ink-muted`／`ink-faint`（非アクティブ。3:1。本文に使わず `opacity-*` の代わりに使う）
  - 線：`rule`（セル境界・入力枠。3:1）／`rule-muted`（表の罫線・弱い境界）／`grid`（方眼専任）
  - 欠落軸：`missing` ＋ `missing-face`（黄）。未定義・空セル・未決・仮説なし・保留。白地で 4.5:1 を満たす黄は黄土色になり、それは意図した見た目である。
  - 無効軸：`invalid` ＋ `invalid-face`（赤）。重複・参照切れ・整合性違反・スキーマ違反。表記ゆれの「指摘（suggestion）」は波線下線（弱形）で示す。
  - 着信軸：`pending` ＋ `pending-face`（青）。外から届いた入力に返答していない状態
  - 判断軸：`judge-yes` ＋ `judge-yes-fg`（支持の濃い面）／`judge-no` ＋ `judge-no-fg`（棄却の濃い面）／`judge-yes-face`（決着した課題の箱に敷く淡い緑）
- **淡い面 `*-face` は同じ軸の色と同じ色相の、白（ダークは黒）へ寄せた面である。** その上に載る文字と枠のコントラストは `FACE_REQUIREMENTS` が課し、淡い面どうしの色差には識別を負わせない。課すのは本文・抑えた文字・枠の3色で 4.5:1。`judge-yes-face` だけは枠が自軸の線ではなく `rule` なので 3:1 とし、抑制された行に出る `ink-faint` にも 3:1 を課す。
- 意味色4つは標準・P型・D型のすべてで OKLab 色差 ≥ 0.10 を満たす（`DISTINCT_PAIRS`）。下げるときは 0.08 までで、理由を `palette-requirements.ts` に書く。

**規約6条**:

1. 色を持つのは意味だけ。分類・ボタン・見出し・選択状態は彩度を持たない
2. 開いているものは淡い面と線、決着したものは濃い面。線色そのものを面にしない（面は `bg-*-face` 側が持つ）。例外は `judge-yes-face` だけ
3. 判断軸で彩度を持つのは支持のみ。棄却・見送りは明度差で分け、`FACE_PAIRS` が 3:1 を課す
4. 5色目は作らない。新しい意味は4軸のどれかに入れるか、色以外のチャネル（線種・形・位置）で表す
5. 削除だけはホバー時に `invalid` を借りる。常時は `ink-muted`。これ以外に借用を作らない
6. 無彩色とは C ≤ 0.01（`ACHROMATIC` が弾く）。半透明の面は持たない

### 決定

#### D1. 未定義の視覚表現を全モジュールで単一化する

空セルは空のまま描画し、色と枠だけで警告する。「未定義」「別名なし」のような文字列をUIが埋めない。表現は `src/core/list-editor/cell-face.ts` の `CELL_FACE_CLASS` に一元化する。

#### D2. 1つの色に1つの意味だけを割り当てる

色を持つのは意味だけで、装飾には使わない。**テーブルヘッダの帯の代替はセクション見出しの4チャネル**（`font-medium` ＋ `tracking-wide` ＋ `text-ink-muted` ＋ `bg-surface-muted`）で、面を外すと見出しの行がデータ行に溶ける。

#### D3. レイアウトが内容に支配される構造をやめる

レイアウトが先に決まり、内容がそこへ収まる形にする。キャンバスのノード幅は固定にし（`src/modules/logic-tree/measure.ts`）、バッジが縦一列に揃うことで列をなぞるだけでスキャンできる。**高さに上限は無い。** `overflow: hidden` の `textarea` は溢れた行を編集できない箱になる。

#### D4. 警告メッセージは「件数」と「位置」で表現する

同じ文字列を並べず、`「新しい用語」が4件重複しています` のように件数で表す。行番号があるモジュールでは行番号で指し示し、該当行へのジャンプを提供する。文言の規約は [`missing-semantics.md`](missing-semantics.md) が持つ。

#### D5. 警告は「問題のあるセル」だけを染める

染めるのは問題のあるセルだけにし、行全体を染めない。行に掛かる指摘は帯ではなく先頭セルに1つ出す（`rowAnchor`）。表の中では輪郭が罫線と競合するので、セルは淡い面だけで示す。

#### D6. フォントをOS環境からの導出ではなく、バンドルによる固定にする

書体をOS環境に委ねず、同梱して固定する。`src/index.css` が読むのは生成物 `src/styles/fonts.css` で、素の `@import` は旧形式の woff まで dist に入れる。**woff2 を data URI にインライン化しないこと。** CSP の `font-src 'self'` が `data:` を許さず、珍しい漢字が豆腐になる。字数サブセットはしない。利用者が入力する漢字を事前に決められないためで、全字収録のまま `unicode-range` で割れば使われないスライスは取得されない。

#### D7. 和欧混植のズレを、フォント選定によって解消する

仮想ボディに対する字面の比率が違う書体を混植させない。`--font-sans` の欧文と和文、`--font-mono` を同一設計の書体族で揃える（`src/index.css`）。フォールバック列は保険として残す。

#### D8. ウェイトを9段階持つフォントに移行し、階層をウェイトで作る

ヘッダ＝Medium(500)／本文＝Regular(400)／補助＝Regular＋グレーの3層を組む。段の既定は 400 で、500 は文書タイトル・セクション見出し・バッジ・すべての `<Button>` のラベル（`src/components/ui/button.tsx`）。**それより重いのは 600 までとし、700 は積まない。**

#### D9. 数字を等幅（tabular-nums）にする

`src/index.css` の `body { font-variant-numeric: tabular-nums }` で全画面に効かせ、個々の要素で当て直さない。テーブルの数値列は右揃えにする。

#### D10. 等幅フォントを「機械が所有する文字列」に割り当てる

ファイルパス・スキーマのキー名・ID のような機械が所有する文字列には `--font-mono`（`src/index.css`）を割り当て、人間が書いた文字と見た目で分ける。

#### D11. タイポグラフィスケールを固定する

サイズは 14 / 16 / 22px の3つだけで、**14px を下限とする。** 密度は行高で稼ぎサイズでは稼がず、小さくするときは薄くしない。

- `text-sm` 14px / 1.3：補助と、単行の入力値
- `text-sm` ＋ `leading-normal` 14px / 1.5：複数行の入力値とキャンバスの折り返し
- `text-base` 16px / 1.25：UIラベル既定。カラム名・ボタン・バッジ・帯・ファイル一覧
- `text-base` ＋ `leading-normal` 16px / 1.5：アプリが書いた文章。トースト・指摘・空状態
- `text-xl` 22px / 1.3 / `font-medium`：文書タイトルとアプリ名（Tailwind 既定の 20px を `src/index.css` で 22px へ上書きする）

行間は詰めた値を `@theme` の既定に持ち、明示してよいのは `leading-normal`（広げる側）と `leading-none`（バッジ・節見出し）の2つだけとする。段の逸脱・数値指定の行間・任意値は `src/styles/conventions.test.ts` が弾く。

#### D12. 表示環境に基づき基準値を正規化する

基準の表示環境は 27型 WQHD・表示スケーリング 100%（約 109 PPI）とする。CSS の `px` は 96 PPI 基準の仮想単位なので、基準値そのものを引き上げて正規化する（`14 × 109 / 96 ≒ 16`）。所在は原則のみで、導出した基準値は D11 のスケールに現れる。

#### D13. ズームではなく基準値で解決し、ボーダーは1pxで固定する

正規化はズームではなく基準値（フォントサイズ）の側で行い、既定のズームは 100% とする。**ボーダーと方眼線は文字サイズが変わっても 1px 固定にする。** 非整数倍率ではヘアラインが滲む。手動ズーム（`src-tauri/tauri.conf.json` の `zoomHotkeysEnabled`）は逃げ道として残すが、倍率は保存しない。

#### D14. 判断軸と欠落軸を、別の視覚チャネルに分離する

欠落軸と判断軸に色相を奪い合わせない。**開いているものは淡い面＋線＋文字、決着したものは濃い面**という面の濃さで分ける。欠落軸の中の段は線種が運ぶ（破線＝まだ見ていない／実線＝見たが決められない）。軸から見た目への写像は `src/modules/issue-tree/badge-variant.ts` が1箇所で持ち、部品はツールの語彙を知らない。

#### D15. 判断軸の配色

支持は `judge-yes` ＋ `judge-yes-fg` の濃い面、棄却は `judge-no` ＋ `judge-no-fg` の濃い面、見送りは `surface-muted` の面＋`rule` の枠＋`ink-muted` の文字。彩度を持つのは支持だけで、棄却・見送りは無彩色の明度差で分ける。**棄却に取り消し線は使わない。** 棄却は失敗ではなく正当な結論だからである。値は `src/styles/palette.css`、3者の写像は `src/components/badge-styles.ts` が持つ。

#### D16. 分類には色を付けない

用語集の種別やエラーカタログの解決レベルのような分類に色相を割り当てない。分類は増え続け、存在しない序列を示唆し、いずれ意味色と衝突する。所在は原則のみで、検査は `src/styles/conventions.test.ts` の色値直書き禁止が担う。

#### D17. 見送り配下の未決は、要対応から外し別枠で集計する

旗（見送り・解決）を掲げた枝の配下の問いは要対応に数えず、旗を掲げた課題の数だけをグレーのチップが種別ごとに持つ。グレーアウトと赤い警告を同じノードに同時に出さないが、**存在は消さない。** 集計の規約は [`missing-semantics.md`](missing-semantics.md) が持つ。

#### D18. 見送り配下は祖先から導出する。フィールドを持たない

祖先に1つでも旗があれば、そのノードは配下として抑制される。これは導出で、子にフラグを複製しない。正は `src/modules/issue-tree/derive.ts` の `suppressedIssueIds` が持つ。

#### D19. ボタン階層を3段階に固定する

Primary（塗り）／Secondary（枠線のみ）／Tertiary（枠なしアイコン）の3段で設計する。**facet では Primary を使わない。** ツールバーは全部 `outline` で揃え、`src/styles/conventions.test.ts` は `<Button>` に `variant="outline"` か `"ghost"` を要求する。`default`（Primary）と `destructive` は使わず、検査が見ない例外はモーダルの `<AlertDialogAction>` だけである。

#### D20. ダークパレット

同じ役割トークンにモードごとの値を割り当て、ライトの値を機械的に裏返して作らない。**ダークもライトと同じ輝度順にする**（`surface-muted` < `canvas` < `surface`）。ダークでは `canvas` と `surface` が線を挟むため方眼と罫線を1値で兼ねられず、`grid` を方眼専任、`rule-muted` を罫線に割り当てる（`src/styles/palette.css`）。

### その他の規約

- **方眼紙背景は地にだけ敷く。** `src/index.css` の `bg-grid-paper`（マス目 24px）を `canvas` に当て、`surface` は無地にする。両者は明度差ではなく模様の有無で見分けさせる。方眼は紙の地なので、段を作り直しても `--grid-size` は動かさない。
  - **`repeating-linear-gradient` は使わない。** WebKit は繰り返し勾配を面の端から端までの1本として標本化するため、24px 周期の 1px 線がほとんど落ちる。
- **端末（xterm）の中の面・文字・カーソル・選択は常にダーク固定にし、この4系統だけを流し込む。** ANSI の16色は役割トークンに対応物が無いので持たない。
  - 色値はソースに現れず、`palette.css` の `.dark` の値を実行時に読んで sRGB へ変換する（`src/core/terminal/theme.ts`）。使い捨ての非表示要素に `className = 'dark'` を付けて読むので、`.dark` は素のクラスセレクタのままにする。
  - **トークンが1つでも読めなければ配色を渡さず xterm の既定に落とす。** 半端に流し込むと面だけ変わって文字が読めない端末になる。
  - 端末のフォントも同じく `--font-mono` を実行時に読んで `term.options.fontFamily` へ渡す。**代入は `document.fonts.load` で読み込みを待ってから行う**（xterm は代入した時点の書体でセル寸法を測るため）。
- **ボタンのラベルの行間は要素セレクタで一律に揃える**（`src/index.css` の `@layer base` の `button { --tw-leading: 1.2 }`）。本文向けに広げた行間がボタンに効くと、和文フォントの縦メトリクスの非対称でラベルが上へ寄る。
  - **`line-height` を直接書かないこと。** Tailwind の `text-*` は utilities レイヤーで `line-height: var(--tw-leading, <既定>)` を生成し、後に宣言された utilities が base に勝つため届かない。
- **角丸は2段＋円。** 部品・セル・チップ・バッジ・ボタン＝`rounded-sm`／浮遊面＝`rounded-md`／意図した円だけ `rounded-full`。裸の `rounded`・任意値・他の段は `src/styles/conventions.test.ts` が弾く。
  - **この検査だけは shadcn の生成物（`src/components/ui/`）も走査対象に含む。** 更新で `rounded-lg` が黙って戻るのを捕まえるためである。
- **キャンバス系ツールでは、測定層と描画層が同一のフォントトークンを参照する。** 折り返し位置はオフスクリーン `<canvas>` の `measureText` が描画前に確定させるので、指定がずれると全ノードのサイズが一斉に狂う（`src/core/canvas/canvas-font.ts`）。
  - **測り直しの契機は `document.fonts.ready` だけでは足りず、`loadingdone` も要る。** 和文フォントは `unicode-range` で分割され、珍しい漢字が初めて出た瞬間に該当スライスが後から届く（`src/core/canvas/use-font-generation.ts`）。追従するのは高さだけで幅は動かない。
- **フォーカスは面の塗り替え（`focus:bg-*`）ではなくリング（`focus:ring-2 focus:ring-inset focus:ring-ring`）で示す。** 面を塗り替えると警告の淡い面ごと表示が消えるが、リングは枠の内側に重なるだけなので面も輪郭も消えない。
- **操作ヒントは共通部品 `KeyHints`（`src/components/KeyHints.tsx`）が描く。** 修飾キーは文中に `$mod` / `$alt` というプレースホルダで書き、`src/core/keyboard/hint-text.ts` の解決関数が実行時のプラットフォームに応じて置き換える。
  - **主修飾キーは Windows では `Ctrl`、macOS では `Cmd` であり、`$mod` がこれを描く。** 画面に `Ctrl` と直接書くと macOS で誤った操作説明になる。
  - `KeyHints` は小さいまま、薄さを外す。14px のまま `text-ink` を使い、二重減衰を作らない。
- **帯の中で伸縮を引き受ける要素は1つに限る。** 長くなりうる要素（フォルダパス等）だけを `min-w-0`／`truncate` で伸縮させ、他は `shrink-0` で幅を固定する。`flex` の子要素は既定が `min-width: auto` なので、放置すると長いパスが操作群を画面外へ押し出す。
- **共通の見た目は部品に寄せる。** 生の `<button>` の土台は `src/components/button-styles.ts` の `buttonBase`、状態のバッジは `src/components/Badge.tsx`、選択トグルは `src/components/Chip.tsx` を通す。部品のファイルは部品だけを export し、variant の型と定数は隣に置く（`src/components/badge-styles.ts`）。

## 10. 操作言語（キーボード＋マウス）

### 位置づけと原則

- キーボードとマウスは役割の違う両輪。**キーボード＝入力する速さ**、マウス＝構造を操作する自然さ（動かす、並べ替える、俯瞰する、画面共有で指し示す）である。
- **操作は発明しない。デファクトスタンダードに従う**（独自ジェスチャは学習コストと不具合の温床）。参照先はUIの構造で決まり、キャンバス系は Miro / Figma、表系は Excel / スプレッドシート、リスト系は一般的なリストUIに準拠する。

### キャンバス

- **ロジックツリーとシーケンスはキャンバス**（ズーム・パンする自由な面）として作る。横に伸びる構造は通常スクロールでは破綻するため。
- 標準操作は、Ctrl+ホイール＝カーソル中心ズーム、Space+ドラッグまたは中ボタン＝パン、空白ドラッグ＝矩形選択、Shift+クリック＝追加選択、ドラッグ＝移動、ダブルクリック＝テキスト編集、右クリック＝コンテキストメニュー。
- **自動レイアウト（データに座標を持たない）か自由配置かはツールごとに決め、自由配置は安易に選ばない**（「図は導出」の思想とGit diffのノイズに関わる）。ロジックツリーは自動レイアウトで、座標・幅・折りたたみ状態のいずれもデータに持たない。
- **マウスドラッグは座標の編集とは限らず、構造の編集を入力するジェスチャとして使える**（親の付け替えで書き換わるのは `parentId` と配列インデックスだけ）。したがって「マウスで動かしたいから自由配置にする」は理由にならず、自由配置が要るのは位置そのものに人間が意味を込める場合に限る。
- **ノードの中のテキスト編集は「ダブルクリックで編集モードに入る」形にしなくてよい。** 入力欄を常に `<textarea>` にしフォーカス＝編集中とする（会議のスピードでは1手が邪魔）。帰結として Space（パン）はノードにフォーカスがある間は文字入力に取られる。
- 状態遷移の図は読み取り専用の導出物とし、編集面は表とする。用語集はリスト。

### キーボード操作：二層構造

「全ツールで操作を揃える」の実態は「**同じ構造には同じ操作**」であり、層を分けて優先規則を明確にする。

グローバル層（全ツール厳守。UIの構造に依存しない）：

- **Undo/Redo**：Ctrl+Z ／ Ctrl+Shift+Z（Windows/Linux では Ctrl+Y も Redo、macOS は Cmd+Shift+Z のみ）。履歴は開いているファイル単位・メモリ内のみで、それ以前への復帰はGitの担当（5章）。
- **Esc**：編集中は編集キャンセル、非編集は選択解除。

構造依存層（追加・削除・移動・並び替えの意味をどのキーで提供するかはUI構造に依存する）：

- **階層・リスト系の標準**：Enter＝兄弟／直後に追加、Tab＝子追加、空欄でBackspace＝削除、Alt+↑↓＝並び替え、矢印＝ノード間フォーカス移動。ロジックツリー、シーケンス、用語集はこれに従う。
- **表系（遷移表）はExcel準拠が優先**で、共通セットのキーをExcelのデファクトと衝突する形で持ち込まない。
- **各ツールが提供すべきは意味の集合**（追加・削除・移動・並び替え）で、キー割当は属する構造ファミリーの流儀に従う。自ツールに存在しない意味は提供しない（用語集はフラットなので Tab はセル間移動）。
- **この分岐は共通フックの `KeyContext.hierarchical` として持ち、ツール側で分岐させない**（置いた瞬間、一元化が名目だけになる）。真なら `Tab`＝子追加・`←`＝親へ移動・`→`＝子へ移動、偽なら `Tab`＝セル移動・`←→`＝キャレット移動のまま。
- **`hierarchical` は「キャンバスかどうか」ではなく「子という意味があるかどうか」**（シーケンスはキャンバス系だがフラットなので `false`）。`←→` はキャレットが端にあるときだけ構造の移動に切り替え、加えて `arrowsOwnedByField`（欄が矢印を使っているか）を見る。
- **`Shift+Tab` には意味を与えない**（キャンバスから Tab 順で抜ける経路として空けておくため）。
- **横に並ぶリストは `KeyContext.horizontal` で扱う**（`Alt+←→`＝並び替え、素の `←→`＝キャレット端で隣へ移動、`↑↓` は関与しない）。`hierarchical` と同時に `true` にしない。
- **主修飾キー＋`Enter` は `toggle-item-state`（欄の状態トグル）。** 写像はツールごとに違ってよく、コアが解決するのはコマンド名まで、意味はツール側の `runCommand` が決める。
- **コマンドの語彙をコアに増やす案は採らない**（意味の集合を決めるのはツール側という原則に反する）。写像を足すツールは画面のヒント（`KeyHints`）も足すこと。
- **構造依存層の写像はコアを触らずツール側で足せる。** 「移動先が無ければ生やす」のような拡張はツール側が意味を足すだけで、`resolveCommand` は変更しない。
- **`Shift+Enter` / `Alt+Enter` が「アプリは関与しない」（＝ブラウザ既定のセル内改行が生きる）ことは不変条件**（用語集の定義・備考がそこに乗っている）。縛るのは `resolveCommand` であって、「どの欄でも必ず改行できる」ことまでは約束しない。
  - 複数行を許すと版組が破れる欄はツール側が `e.key` を見て改行を止めてよいが、**明示的な例外なので適用範囲と理由を書き残すこと**（現在の唯一の例外は課題ツリーの仮説タイトル）。
- **導出表示（ソート・フィルタ適用中）では、表示順とデータ順の対応が崩れる操作を無効化する。** 並び替えだけでなく行の追加も含む（挿入した行が絞り込みに掛からず、見えないまま増えるため）。
- **キーでしか到達できない「意味」を残さない。** 追加・削除・並び替えにはマウスの入口も用意する（追加ボタンは常時出し、押した行は末尾に足す）。
- **例外として、マウスでしか到達できない意味を明示的に許すツールがある。** 課題ツリーの仮説側の欄は `resolveCommand` を通らない。課題の追加・削除・移動は反射的に打つ操作だが、仮説は主張をゆっくり言葉にする作業で、打鍵数より目的の欄に迷わず届くことが効くためである。

### 実装規約

- **キーボード・マウス処理は共通フック／モジュールに一元化し、ツールごとのハンドラ自前実装を禁止する**（キーボードは `src/core/keyboard/`、マウスは `src/core/column-resize.ts`）。挙動差の構造的再発防止であり、修正も1箇所で済む。
- マウス側は**純関数（値の計算）とフック（ポインタの配線）を分け、ツール側は `getHandleProps(index)` を貼るだけ**にする。ドラッグは `pointerdown` で `setPointerCapture` を取り、window にリスナーを張り替えない。
- **ポインタ操作を作ったらキーボードからも同じ操作を提供する**（列幅は ←→ で16px刻み、Home で既定に戻す）。アクセシビリティのためであり、jsdom はレイアウトも `setPointerCapture` も持たないのでキーボード経路が値の反映を検証できる唯一の入口になるためでもある。
- **例外：キャンバスのズーム・パンは d3-zoom に委ねる**（ホイール・ピンチの正規化と倍率を保った座標変換という規約の外側の仕事を持つ）。この例外はビューポートの `{x, y, k}` に限り、値の編集のドラッグは引き続き `setPointerCapture` を取る。
- **キャンバスのズーム・パンにはキーボード経路を作らない。** 代替は新しいノードへの自動追従で、キーボードだけで打っている限り視点は自ら動く。ズーム倍率は閲覧の都合なので、要ると分かった時点で同じ関数を呼ぶ2つ目の入口として足す。
- **キャンバス系ツールの実装構成は全ツール共通。ノードは絶対配置の DOM、エッジは SVG、ビューポートは d3-zoom。** 3レイヤ（背景／エッジ／ノード）に同一の `translate(x, y) scale(k)` を当てるので、座標系のズレは原理的に発生しない。
- **キャンバス（描画・操作）ライブラリ（React Flow / tldraw 等）は採用しない。** イベント系を乗っ取るライブラリが操作言語の一元化規約と衝突すること（Space がパンに、Backspace が削除に食われる）と、自動レイアウトを採る以上ライブラリの中心価値が不要になることの2点による。
- **レイアウト計算ライブラリ（elkjs / dagre）は別の話で、不採用の理由も別。** ロジックツリーで採らなかったのは、どちらも任意の有向グラフ向けで厳密な木にはその強みが要らないことと、elkjs がバンドル1MB超・Web Worker 前提の非同期APIであることの2点である。
  - **任意グラフを描くツール、とりわけ状態遷移図では再検討の余地がある。** 「ロジックツリーが採らなかった」を「facet では使わない」と読まないこと。全文は [`logic-tree/logic-tree-canvas-tech-notes.md`](logic-tree/logic-tree-canvas-tech-notes.md) 論点2。
- **ノードの中を SVG にしない**（`foreignObject` を使わない）。Windows のブラウザで IME の変換候補ウィンドウの位置ズレ・フォーカス喪失が起きるため。
- **IME対応**：変換中のキーイベントは操作言語の対象外とする。変換確定のEnterが「追加のEnter」に誤爆する問題は日本語入力アプリ最大の地雷であり、仕様として明記する。
  - **`isComposing` だけでは足りない。** WebKit は composition 系のイベントを keydown より先に投げるため、変換を確定した Enter は `isComposing: false` で届く（Windows の WebView2 は仕様どおり）。
  - **主たる判別材料は `keyCode === 229`**（IME が食った打鍵の予約値で、離した keyup は本来の 13 に戻る）。`src/core/keyboard/ime.ts` が持ち、操作言語の入口が `isComposing` へ畳み込むので各ツールのセルも額縁も一度に守られる。
  - 補助として `CellInput` が「直前の `compositionend` から前後 100ms」の窓も見る。**この窓は絶対値で見ること**（keydown の時刻は compositionend より古いことがある）。
- **境界規則（端末ペイン）**：端末ペインの中で発生したキー入力は操作言語の管轄外とし、`keydown` ハンドラの先頭で発生元を見て早期returnする（これが無いと端末の `Ctrl+Z` がfacetのUndoを横取りする）。帰結として、端末ペインの開閉・フォーカス脱出にショートカットは割り当てない。
- **境界規則の裏返し（右クリック）**：ペイン内の右クリックは facet が握り、OS の既定メニューを止めて、選択があればコピー・無ければ貼り付けの1動作に置き換える。止める範囲はペインの中だけで、エディタ側のテキスト欄では何も変えない。
- **境界規則（モーダル）**：モーダルが開いている間はエディタの操作言語を停止し、キーはモーダル側が取る（Escの取り合いを構造的に排除）。停止の対象はポインタ操作も含み、フックに `enabled` を渡す形にしてキー監視と d3-zoom の `filter` の両方が見る。
- **境界規則の例外（セルのドロップダウン）**：セルが開くドロップダウンはモーダルに数えず、キャンバス停止を掛けない。代わりに同時に1つのセルしか開けない構造にし、キー入力の遮断は `FocusScope` 単層に任せる（アプリ側の防御を持たないことは既知のトレードオフ）。
- **境界規則（テキスト編集中）**：編集中はキーイベントを編集対象が取り、操作言語は停止する。例外は編集境界キー（Enter／Tab／Esc／空欄Backspace）と Undo/Redo で、これらは操作言語が解釈する。
  - Undo/Redoを編集中もアプリの履歴が取るのは、制御された入力欄ではブラウザ標準のUndoがReactの再レンダリングと食い違うため。Space・矢印・Alt+↑↓は編集対象のものとする。
- **拡張規則**：ツール固有キーの追加は可。グローバル層および自ファミリーの標準キーと衝突する再定義は禁止。

## 11. 検証の観点（ドッグフーディング）

- **第一関門：会議のスピードに入力が追いつくか。** 操作言語（10章）とキャンバス操作の使用感を含めて評価する。
- **AI連携の価値検証。** Skill（4章）による下書き生成・ヒアリング型データ作成・レビューが「ゼロから入力するより速く・漏れが減る」かを確認する。文章校正系（用語チェックのAI層）は費用対効果が高い着手候補。
- **成果物が仕様書として機能するか。** 貼り付けたMarkdown/Mermaid出力（8章）が実際の仕様書として読まれ・使われるかを確認する。出力実装は「使う」と確定したツールから着手する。
- **色の識別性。** P型・D型色覚での意味色の色差は機械検査で担保しているので、残る検証は実機で黄（欠落）と赤（無効）が分かれて見えるかと、会議で投影したときの読みやすさの2つ（9章）。
- **チーム展開はクオリティ確認後**（展開時の配布方法は7章）。
