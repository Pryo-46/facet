## 1. 背景と目的

文字だけの仕様書は、多次元の情報（分岐・時系列・状態・用語）を一次元の文章に直列化しているため、読むたびに脳内でグラフ構造を再構築する必要があり、ワーキングメモリを消耗する。これを解決するため、「人間は構造化されたUIで入力し、ツールが網羅性の担保・描画・構造化テキスト出力を担う」という思想の会議用ツール群を作る。

利用者はまず作者本人（ドッグフーディングによる検証）。加えて、**AI（Claude）もツールの利用者**として設計に含める（4章）。将来的には、PdMとエンジニアの融合という組織方針の中で、両者が共に読める「中間言語」としての価値を狙う。会議で実際に使う姿を見せることが最良のデモになる、という普及戦略を取る。

## 2. ツール一覧

当初の5ツールに、6番目として課題ツリーが加わった。**ツールは今後増える前提**であり、追加を「モジュールの追加」で済ませる規約を6章に定める。

1. ロジックツリーエディタ — 分岐・パターンの網羅
2. シーケンスエディタ — 時系列の直列シナリオ＋全ステップに立つ「失敗したら？」の問い（**詳細仕様は sequence/sequence-design-notes.md で確定済み**。異常系は矢印で描かず、呼び手の知識状態で閉じた問いのスロットとして立てる。責任境界は参加者の `domain` から導出する縦線として残る）。**出力（Markdown 表＋Mermaid、1プロファイル）は M3 で実装済み**
3. 状態遷移エディタ — 状態×イベントの網羅とテスト導出
4. 用語集エディタ — 用語の型定義と表記ゆれ検知（他ツールが参照するマスタデータ。5章。**詳細仕様は glossary/session-notes.md で確定済み**）
5. エラーカタログエディタ — エラーの一覧と対応方法の整理（サポートチームへの引き渡しが第一の動機。**詳細仕様は error-catalog/error-catalog-session-notes.md で確定済み**）
6. 課題ツリーエディタ — PoC で「試さないと分からないこと」の分解と、仮説・検証の履歴（**詳細仕様は issue-tree/仮説検証モジュール-設計ノート.md で確定済み**。判断 D1〜D11）。**エディタは issue-tree-m1 で、登録 Skill（`issue-tree-register`）とお手本は issue-tree-m2 で、俯瞰の表現と語彙は issue-tree-m3 で実装済み**（出力は後続）——俯瞰は「**箱は課題だけ・仮説は箱の中の1行・判断は行末のバッジ1つ**」で、由来・根拠・FB はフォーカスした仮説だけ展開する（D10）。**判断の語彙は5語ちょうど**——未決／支持／棄却／保留／見送り。**保存される `kind` はこのうち4つ**（`supported` / `rejected` / `onHold` / `deferred`）で、**未決は `events` が0件であることからの導出**なので enum に席を持たない。「検証したか、実験なしで決めたか」も「本開発へ送るか」も `kind` では区別せず `note` に書く（**issue-tree-m3 で D5・D6 を反転して確定**。人間が実機の画面を見た直後の判断で、細かい区別は選ぶ側の迷いだけを増やし、俯瞰の読みを変えなかった）

**6番目の追加経緯**：エピック開発の流れが「PoC で検証 → 作るものを決めて本開発」になり、**仮説検証の記録が本開発の仕様書の上流入力**になったことによる。かつて PRD を不採用にした理由（自由記述中心で構造化度が低い）はここには当てはまらない——「課題 → 仮説 → 検証 → 結論」という構造が自然に存在し、会議速度で入力され、結論が下流の仕様から「なぜこの設計か」の形で指される。**既存5ツールと軸が違うのは「時間とともに増える追記専用の履歴を持つ」点**で、仮説の現在ステータスは**イベント列の最新要素から導出**し、ミュータブルな状態フィールドをデータに持たない（**追記専用が及ぶのは仮説の `events` だけである**——課題の見送りは issue-tree-m3 の後追いで入り切りのトグルになり、戻すときに最新1件を消す。1語しか無い種別を1択のドロップダウンで選ばせる意味が無くなったため。設計ノート D2 の反転節。**状態フィールドを持たない・最新から導出する、という芯は動いていない**）（導出元のない手動ステータスは更新忘れで嘘をつくため。3章「正となるデータは一つ、図は導出」の適用先が、図・出力に続いて**状態**にも及んだ形になる）。同じ理由で、祖先の見送りによる配下の warning 抑制も保存せず毎回導出する。

**5番目の追加経緯**：サポートチームへ「どんなエラーがあり、ユーザーは何をすべきか」を表で渡す要求から発生。既存4ツールのどれとも軸が異なる（読み手が開発者・PdMではなくサポート担当であり、出力先が仕様書ではなく運用ドキュメント）ため、独立モジュールとした。あわせて、**用語集に次ぐ2つ目の「単一ファイルのマスタ」**が現れたことで、用語集の特例として書かれていた規定がいくつか一般化された（5章・6章）。

既存のプロトタイプ（.jsx 4本）はイメージ確認用であり、データ構造・実装とも実用版には引き継がない（5章・7章）。UI・操作の実装差の観察結果（挙動を揃える必要性）だけを教訓として引き継ぐ。

## 3. 全ツール共通の設計思想（変更する場合は理由を明記すること）

**入力速度最優先。** 会議の議論は秒単位で流れる。入力がもたつくと「後でまとめよう」となりツールは使われなくなる。共通の操作言語（10章）で全ツールの操作を揃える。さらにAI活用（4章）により、AIとの対話でデータを作る＝入力そのものを省略する方向へ拡張する。

**網羅性の担保はツールの仕事。** 未定義・未決定の箇所が物理的に「見える」構造にする（ツリーの葉数バッジ、遷移表の赤セル、用語チェックの赤ハイライト）。「決めていないこと」を消せなくするのが本質的価値。機械的チェックの上に、AIによる意味的チェック（どの未定義が実務上危ないか）を重ねる（4章）。

**「未定義」と「決めた上で無効」を型で区別する。** 文章仕様書ではどちらも「書いてない」に潰れる。遷移表の「─ 何も起きない」が代表例。デザイン上もこの区別を色の意味論（warning / ok）として維持する（9章）。

**正となるデータは一つ。図は導出。** 状態遷移エディタが典型で、編集できるのは表のみ、図は自動生成の読み取り専用。表と図の乖離を構造的に防ぐ。この思想はDB不採用の判断（5章）やキャンバスの配置方式の判断基準（10章）にも適用する。

**構文は人に覚えさせない。構文は交換形式である。** Mermaid等の構文を人に覚えさせず、人間は直感的UIで入力し、ツールがMarkdown/Mermaidを吐く（旧「構文は出力形式に降格」）。AI活用により、スキーマ定義されたJSONは出力にとどまらず**AIとの双方向の交換形式**となった。人間には見せない・機械同士は構造化データで話す、という役割分担。

## 4. AI活用方針

### 基本構造：AIはアプリの外で動き、接点はファイルのみ

- AI（Claude）はアプリに組み込まない。**APIの呼び出し・アプリ内AI機能は作らない。**
- **例外（M11 で明記）**：アプリ内AI機能は作らないが、**AIを起動する場所は提供する**。facetは端末のホストであって、AIの対話相手ではない。この線引きは実装の判断基準として使える——**「Claudeの出力を読んで何かを決める」実装が現れたら、それはこの原則の違反である**（M11 決定1。端末ペインのタブ名を会話内容から自動で付けない設計はこの基準の直接の帰結）。
- AIはClaude Code / Claude Desktop上で動き、プロジェクトフォルダ内のJSONファイルを直接読み書きする。アプリとの接点はファイルだけ。
- 責務分離：**アプリ＝人間用の高速エディタ＋検証器＋描画器。AI連携＝Skill群という別の成果物。** アプリはAIの存在を知らなくてよい。
- **MCP的な書き込みツール（用語登録APIの提供等）は作らない**（handoff-04で決定）。ファイル直書き経路は塞げないため二段検証は結局必要になり、MCPは「検証を通る経路の多重化」と「第三の成果物（スキーマ追従が必要なコードベース）の追加」にしかならない。予防的な品質向上は下記の同梱スクリプトで回収する。

### Skill群：AIを対話的な共同作成者にする

単発の「校正依頼」にとどまらず、ユースケースごとのSkillを整備する。想定：

- **対話的データ作成**：例：用語登録Skill。ユーザーにヒアリングしながら用語集ファイルを組み立てる。ゼロから入力する代わりにAIとの対話でデータができる——「入力速度最優先」を入力自体の省略で実現する方向。
- **下書き生成**：会議メモや既存の文章仕様書からロジックツリー/遷移表/シーケンスの初期データを生成。人間は会議でAIの下書きを修正・確定する。
- **レビュー**：完成データの網羅漏れの意味的指摘（「辞退後の差し戻しが未定義。実務ではあり得ないか？」）、到達不能状態・デッドエンド検出、未定義箇所の実務的な優先度付け。ツールの機械的チェック（赤セル）が「未定義の存在」を示すのに対し、AIは「どの未定義が危ないか」を担う。
- **用語チェックの二層化**：ルールベース層（アプリ内：決定的・高速。aliases 照合）の上に、AI層（未登録の揺れの発見、定義と使われ方の矛盾検出）を重ねる。

**Skill には2種類ある。** 上記はいずれも**ユーザーのデータ**（プロジェクトフォルダの JSON）を作る Skill で、アプリとの接点はファイルだけという構造に乗る。これとは別に、**アプリ自身のソースを触る Skill** がある——`palette-retheme`（`src/styles/palette.css` の配色を差し替える）がそれで、接点はリポジトリのファイルであり、検証はアプリのテストが行う。同梱スクリプトが**ロジックを手で複製しない**（原本を参照するか、バイト一致のコピーをテストで縛る）点は共通だが、**参照先がスキーマではなく `src/styles/` のテスト専用コードである**。

**Skillへの同梱スクリプト（handoff-04で追加）**：ID捏造・不正データの予防策として、各Skillに以下を同梱する。

- **ID採番スクリプト**：英数字62文字カスタムアルファベット・10文字の nanoid を出力（5章のID規約準拠）。Skillの手順書に「IDは必ずこれで採番せよ」と明記する。
- **書き込み前検証スクリプト**：アプリと同一の JSON Schema ファイルを参照してバリデーションする。**スキーマは各 Skill が `schemas/<名前>.schema.json` にバイト一致のコピーを持つ**（当初は「正は一つ。コピーを同梱しない」としていたが、**facet のチェックアウトを持たないマシン——つまり出荷先のすべて——で当時の3本とも最初の書き込みが `die(2)` する**ため改めた。アプリが配布するのは `.claude/skills/` だけで、リポジトリの `schemas/` は届かない。`--schema` / 環境変数という逃げ道も、指す先の実体が無ければ使えない）。当初の懸念（正が2つあると片方だけ古いまま検証が通る）は、下記の**バイト一致＋テストで強制**する機構が引き受ける。

**アプリのロジックを同梱スクリプトから使う方法（sequence-m4で確定、M15で全Skillへ拡張）**：同梱 Skill はプロジェクトフォルダへ**コピーされて実行される**ため、実行時に `src/` は存在せず、アプリのソースを import できない。かといって手で複製すると、追従漏れが**どちらも独立に動くまま**残る。したがって、**値 import を持たないファイルに限り、バイト一致のコピーを同梱し、一致をアプリのユニットテストで強制する**——ズレた瞬間にテストが赤くなるので、手複製とは質が違う。`src/core/canonical.ts`（正規形の書き出し）のバイト一致コピーは、登録4 Skill 全て（`glossary-term-register` / `error-catalog-register` / `sequence-register` / `issue-tree-register`）が持つ（M15 で旧2本を揃え、issue-tree-m2 で4本目が加わった）。**この一致検査は1箇所ではなく3ファイルに分かれている**——旧2本（`glossary-term-register` / `error-catalog-register`）は `src/core/skill-canonical-copy.test.ts` が、`sequence-register` は `src/modules/sequence/skill-copy.test.ts` が、`issue-tree-register` は `src/modules/issue-tree/skill-copy.test.ts` が検査する（後の2本は、下段の「そのツール固有の導出ロジック」のコピーと同じテストが一緒に見ているため）。**どの Skill のコピーがどのテストに載っているかを網羅で縛るアサーションは、どこにも無い**（スキーマ側の `skill-schema-copy.test.ts` には `BUNDLED_SKILLS` との `toEqual` がある）——5本目が `canonical.ts` のコピーを持ちながら検査を書き忘れても緑で通るので、**Skill を増やす人が自分で足すこと**。代償は `.mjs` から `.ts` を読むための Node の型ストリップ依存だが、**消去できない構文が生えたことも同じテストが検知する**（検査は「バイト一致」と「値 import を持たない」の2本立て）。**同じ機構を JSON Schema にも適用している**——4本の Skill はそれぞれ `schemas/<名前>.schema.json` に原本のバイト一致コピーを持ち、一致は `src/core/skill-schema-copy.test.ts` が強制する（コピーが要る理由は上記のとおり、配布先にリポジトリの `schemas/` が届かないため）。

**この形は「導出ロジックを Skill と共有する」標準である（issue-tree-m2 で確定）**：`canonical.ts`（全ツール共通の正規形）に加えて、**そのツール固有の導出ロジックそのもの**をバイト一致コピーで共有した例が2つになった——`sequence-register` の `src/modules/sequence/questions.ts`（問いの導出。sequence-m4。一致検査は `src/modules/sequence/skill-copy.test.ts`）と、`issue-tree-register` の `src/modules/issue-tree/derive.ts`（問いの導出・要対応の集計・見送りによる抑制・表示ラベル。一致検査は `src/modules/issue-tree/skill-copy.test.ts`）である。**issue-tree-m3 で問いが4種（仮説なし／未決／保留／未判断）になり、集計の見出しが「要対応」になったが、打ち直したのは `derive.ts` の定数だけで済んだ**（同じマイルストーンの後半で**判断の語彙を5語に畳んだとき**も同様で、アプリ側で動いたのはスキーマと `derive.ts` の表であり、Skill 側は `cp` が追いついた）——語彙を1箇所に置いた効き目が、アプリと Skill の両方に同時に出る形で確かめられた。**1例では方式、2例で規約になる**——新しいツールに登録 Skill を作るときは、導出ロジックを手で複製せず、この形に寄せる。**帰結として、導出ロジックは書く時点から「値 import・相対 import・enum を持たない」制約の下で書く。** `derive.ts` は issue-tree-m1 の時点でこの制約を JSDoc に明記して書かれていたため、issue-tree-m2 での持ち込みが `cp` 1回で済んだ（守られていなければ再設計になっていた）。**Skill へコピーする予定のファイルは、その旨と制約を原本の JSDoc に書いておくこと。**

**バイト一致コピーにできないロジックは、実行結果の突き合わせで縛る（M15で確定）**：整合性検証（`src/modules/<tool>/consistency.ts`）は値 import と `@/` エイリアスを持つため、`canonical.ts` と同じ形のバイト一致コピーができない。各 Skill の書き出しスクリプトはこれを判定ロジックごと手で複製しており、実際にエラーカタログ Skill で警告文言・計上規則がアプリと食い違っていた（M15 着手前の棚卸しで実測）。塞いだ形は、**各 Skill の `*-write.mjs --check` を実際に spawn し、アプリの `checkXxxConsistency` が返す `message` がその stdout に逐語で（部分文字列として）現れることを検査する実行 smoke テスト**（`src/modules/<tool>/skill-write.smoke.test.ts`。同種の疎通確認である `src/styles/palette-fit.smoke.test.ts` と同型）。契約は「アプリの message が現れること」であり、スクリプト側が独自の警告（単一性違反等）を足すことは妨げない。**縛られるのは「一致していること」であって「複製そのものが無くなること」ではない**——`consistency.ts` を改訂するたびに4スクリプト（issue-tree-m2 で `issue-tree-register` が加わった）の書き替えは要るが、追従漏れは次の `npm test` で検知される。**縛りは `rule` 名の集合だけでなく `message` の件数にも掛ける**（issue-tree-m2）——同じ `rule` を2箇所で出すツールがあり（課題ツリーの `duplicate-id` は課題側と仮説側の2箇所。`rule` 5種類に対し `message` は6ブロック）、集合だけでは片方を落としても緑のままになるため。**導出ロジックのコピー（上段）を持つ Skill では、集計結果の逐語一致も併せて固定する**——`message` の一致はコピーが「読めた」ことしか担保せず、整合性検証は手複製の側なのでコピーが空でも通ってしまう。**ただしこれは issue-tree-m2 で書いた規約であり、いま従っているのは `issue-tree-register` だけである**（`src/modules/issue-tree/skill-write.smoke.test.ts` が `derive.ts` の `tallyLine` との逐語一致を1本の `it` で固定している）。**先行例の `sequence-register` は未適用**——`src/modules/sequence/skill-write.smoke.test.ts` は `message` の一致と「欠陥の無いファイルは exit 0」の2本だけで、`questions.ts` 由来の集計を突き合わせる検査を持たない（遡って適用する話は残件として [`open-issues.md`](open-issues.md) に載せてある）。

**Skillの配布と同期（M11で実装。sequence-m4・M15で改訂）**：同梱 Skill はアプリの resources に入っており、**プロジェクトフォルダを開いたときに1回**（端末タブを開くたびではない）`.claude/skills/` へ置き直される。順序は**同梱物をすべて読み終えてから消す**——読めなければ何も消さないので、読み出しの失敗でプロジェクト側の Skill を失うことがない。読み出し自体も**`node_modules` へは降りない**（M15。`shouldDescendSkillDir`、`src/core/skill-sync.ts` の純関数）——ビルド機で Skill ディレクトリに `npm install` 済みだと、開くたびに数百ファイルを読んで捨てるうえ、非 UTF-8 な依存が1つ混じるだけで読み出しごと throw して Skill が消える。消すのは facet が同梱する名前のディレクトリの**中身だけ**で（ユーザーが自分で足したSkillは消さない）、そのうち **`node_modules` と `package-lock.json` は消さない**（各Skillの手順書が初回の `npm install` を指示するため。その `package.json` も同梱物として置く）。**消せない要素が1つあっても中断しない**（mac の `.DS_Store` は fs scope の外にあり消せない）——1件の消し残しより Skill 全体を失うことのほうが重い、という優先順位で、消せなかったものは警告に残して置き直しを続ける。**`.gitignore` は同期対象に含める**（M15）——書かないと `npm install` が作る `node_modules` が利用者のリポジトリで未追跡のまま残る。mac ではこれを書くために `allow_skill_dir`（`src-tauri/src/lib.rs`）が Skill ごとの `.gitignore` を `allow_file` で literal に許可する必要がある（fs scope の glob 判定が unix既定で `require_literal_leading_dot: true` のため、`<dir>/.claude/**` はドット始まりの要素に一致しない。7章）。

Skill群はアプリ本体と並ぶ正式な成果物としてバージョン管理する。Skillはスキーマを参照するため、**スキーマ変更時はSkillも追従させる**（依存関係として管理）。

### 読み方ガイド：静的な README-for-AI.md を配る（M12で実装確定）

Skill群が対話的な共同作成者であるのに対し、**読み方ガイドはAIがフォルダを読みに行った瞬間に必ず目に入る静的な配布物**である。JSONの構造はスキーマの自己記述性（5章）で読めるが、「空欄・`undecided`は未決の意思表示であり埋めてはいけない」「単一性フラグを持つツールは1ファイルずつ」といった**JSONに書かれていない読み方の規約**は、facet開発リポジトリのdocsにしかなくユーザーのプロジェクトフォルダには無い。

- プロジェクトフォルダ直下に `README-for-AI.md` を、facetが自動管理する静的な読み方ガイドとして配る。原本は `src/core/reading-guide.md`。
- **原本はTauriのresourcesではなく、Viteの `?raw` importでバンドルへ取り込む**（スペック設計2の「resourcesに同梱」からの変更）。ガイドは単一のテキストファイルであり、`tauri.conf.json` の `bundle.resources` と定数（`BUNDLED_SKILLS` の「一致していなければならない」制約）の二重管理を増やさないため。原本が同じリポジトリでバージョン管理され、アプリが書き出すという意図は維持している。
- **フォルダを開いたときにべき等に書き出す**（無ければ作る／原本と一致していれば触らない・mtimeも変えない／不一致なら原本で上書き）。書き出し契機を**Skill同期（端末を開く直前）とは分けて「開いたとき」にする**——実装リポジトリ同居のユースケースでは、facetの端末を経由せず外部のClaude Codeから読まれるため
- **アプリはこのファイルを読まない。書くだけ。**「Claudeの出力を読んで何かを決める」実装を作らない（M11決定1）のと同じ線であり、エディタ・検証・描画の対象外

### 既存決定との接続（この構造が成立する根拠）

- スキーマの自己記述性（5章）：AIがJSON Schemaを読んで生成・検証できる。
- 二段検証（5章・8章）：AI生成物も自動保存と同じ検証を通る。AIは存在しないIDを捏造しがちなので整合性検証が防波堤になる。
- プロジェクト＝フォルダ（5章）：AIに渡すコンテキストが「フォルダごと」で完結する。

### アプリ側への要件：外部変更への対応

- アプリの開いているファイルを外部の書き手（Claude Code / Desktop、テキストエディタ等）が書き換えることを前提とする。これは**外部エディタ一般への対応**であり、AI固有の結合ではない（責務分離は維持される）。
- **ファイルの外部変更検知を初期実装に含める**。監視は**ファイル単位ではなくフォルダ単位**とする（外部でのリネームも検知するため。ファイル名非依存の原則とパス監視の間の穴を塞ぐ）。挙動：
  - **自己書き込みの除外**：アプリ自身の書き込み（自動保存・正規化・新規作成・削除）は外部変更として扱わない。検知ループの構造的排除。**具体的な機構は「台帳との内容比較」**（M5 で確定）：アプリが最後に読み書きしたディスクの内容をパスごとに保持し、再走査で読んだ生バイトと1バイトも違わなければ自分の書き込みと判定する。**時間窓（「書いてから N ms は無視」）やフラグは使わない**——遅れて届くイベントで誤検知し、速く届くイベントを取りこぼすため。この方式なので、監視イベントの**種類やパスは一切見ない**（notify のイベント表現は OS ごとに違い、リネームは2イベントに割れる）。「何か起きた」だけを契機にフォルダを再走査する。
  - アプリ側に未保存編集がない → 再読み込みし、非モーダル通知（トースト）で「外部変更を読み込んだ」ことを知らせる。**このときUndo履歴は破棄する**——履歴を残すと、Ctrl+Zが外部（AI）の変更を黙って巻き戻す意図しない破壊操作になるため。
  - **取り込み前の内容は一時退避し、トーストに「取り込み前に戻す」アクションを付ける**（初期実装要件）。Undo履歴破棄後もアプリ内で復元手段が残る。「問題は消せなくして見せる」思想を、消えた編集にも適用する受け皿。
  - アプリ側に未保存編集がある（デバウンス中に外部変更が来た）→ 二択ダイアログ「自分の編集で上書き」／「外部変更を取り込む（自分の編集は破棄）」。VSCode級のマージUIは作らない——データが会議単位の小さなJSONであり、退避とGitという復元手段があるため、実装コストに見合わない。
- **保護範囲の明示**：自動保存下では「未保存編集がない」がほぼ常態のため、二択ダイアログが守るのはデバウンス窓の数秒間だけである。この仕様の衝突定義は「タイムスタンプの前後」ではなく「デバウンス窓の重なり」であり、外部の書き手が古い内容を基に書き戻せば直前の自動保存分は上書きされる（退避からの復元は可能）。
- **衝突は上記の外部変更検知がそのまま受ける（M11で運用推奨を撤回）**：未保存編集が無ければ再読み込み＋トーストでUndo履歴を破棄、あれば二択ダイアログ。かつての運用推奨「AIに作業させる間は対象ファイルをアプリで閉じる」は、この受け皿が既に完成していることを根拠に撤回した（M11 決定2）——Claude Codeペインは隣に並べて使うために作るものであり、「作業中は閉じる」という推奨とは正面から矛盾するため。
- **将来の発展先**：IDがランダムで衝突しない（5章）ため、「双方の追加分を合併する」スマートマージは構造的に成立可能。ドッグフーディングで二択ダイアログが苦痛と判明した場合の選択肢として残す。

## 5. データモデルと永続化

### ファイル構成：プロジェクト＝フォルダ

- 1つの仕様書プロジェクト＝1フォルダ。その中にツールごとのJSONファイルを置く。
- 「同じフォルダにある＝同じプロジェクト」という物理配置で紐付けを表現し、設定ファイルによるパス管理を持たない。マスタ参照は「同一フォルダ内の該当 `type` のファイルを見る」という規約で閉じる（ファイル名には依存しない）。
- 同種ツールの複数ファイルを許す（例：機能ごとにシーケンスを分ける）。ただし**単一性を宣言したツールはプロジェクトにつき1つ**。現時点の該当は **`glossary`（ハブ）と `errorCatalog`**。単一性は整合性検証で担保する（後述）。**ロジックツリーは `singleton: false`**（logic-tree M1 で確定）——論点ごとに木を分けるのが普通の使い方であり、用語集・エラーカタログのようなハブ（他ツールから参照される単一のマスタ）ではないため。**課題ツリーも同じ理由で `singleton: false`**（issue-tree-m1）——PoC のテーマごとに1本作る。
  - **改訂理由（エラーカタログセッション）**：単一なのは用語集だけ、という前提が崩れたため。「どの type が単一か」をコアにハードコードせず、**モジュール側の宣言**として持つ（6章のモジュール規約に単一性フラグを追加）。ツールは増える前提なので、3つ目の単一マスタが出たときにコアを触らずに済む形にする。
- ファイル名は識別子にしない（用語集含め例外なし）。アプリはフォルダ内JSONを走査し、中身の `type` で種別を判別する。人間やツールが自由にリネームしても壊れない。

### スキーマ：JSON Schema を正とする

- 各ツールのデータ形式は JSON Schema で定義し、TypeScript 型はそこから自動生成する（json-schema-to-typescript 等）。手書きの二重管理はしない。
- JSON Schema はAIへの生成指示（「このスキーマに従って生成せよ」）と読み込み時の機械検証に直接使う。
- **スキーマの実体はアプリと同梱 Skill で共有する**：各登録 Skill（issue-tree-m2 時点で4本）が `schemas/<名前>.schema.json` に原本のバイト一致コピーを持ち、一致は `src/core/skill-schema-copy.test.ts` が強制する（コピーを持つ理由と機構は4章）。**スキーマを改訂したらコピーの追従が要り、漏れは次の `npm test` で赤くなる。**
- スキーマは自己記述性を持たせる：キー名は省略しない、種別は enum で明示（handoff-05 のAI活用要求を継承）。
- 個別ツールのスキーマ設計は各ツールセッションで行う。プロトタイプの state 構造は叩き台にせずゼロから設計する（プロトタイプはイメージ確認用であり構造は信用しない）。用語集は確定済み（glossary.schema.json）。
- 全ファイル共通のエンベロープ（必須フィールド）：
  - `schemaVersion`: スキーマの版。**版は type ごとに独立して進められ、移行判定・Skillの追従管理（4章）は `type` × `schemaVersion` の組で行う**（ツールは増える前提のため、あるツールのスキーマだけ改訂される事態は通常運転）。共通エンベロープは各ツールスキーマが参照する共有定義であり、エンベロープの改訂は全ツールスキーマの改訂を**含意**する（このとき全 type の版が上がるのは独立性の否定ではなく包含関係の帰結）。
  - `type`: ツール種別の enum（初期値：logicTree / sequence / stateMachine / glossary / errorCatalog。ツール追加で増え、**issue-tree-m1 で `issueTree` が加わった**）。旧バージョンのアプリにとって未知の値になり得るが、その受け皿は前方互換の規定（6章：未知typeは編集不可として一覧表示のみ）。
  - `title`: 表示名。プロジェクトを開いたときの一覧表示に使う。

### バージョン互換とマイグレーション

- **新しすぎるファイル**（既知 type だが自分の知らない新しい schemaVersion）：**未知 type と同じ扱い**（一覧表示のみ・編集不可）。レベル1拒否にはしない——「まったく知らないツールのファイルは一覧に出るのに、知っているツールの少し新しいファイルは開けない」という逆転を避け、旧アプリ×新プロジェクトの事故への備え（6章の前方互換）に一貫させる。
- **古いファイル**（既知 type × 旧 schemaVersion）：読み込み時に**メモリ上で**自動移行して開く。ファイルへの反映は最初の編集保存時（「読み込み・閲覧では書き戻さない」原則の適用。正規化と同じタイミング規則）。閲覧しただけでは旧版のまま残る。**issue-tree の 1 → 2 が初の実例である**（issue-tree-m3。`judgementEvent.kind` の語彙を5語に確定した改訂——`onHold` を足し、検証の有無の区別と本開発送りを落とした）。**この 2 は同じマイルストーンの中で一度「再定義」されている**——`onHold` を足した時点で 2 に上げ、その後の反転で3語を落としたが、版番号は 3 へ上げずに 2 のまま定義を差し替えた。**未公開の版には壊すべき契約が無いから許される操作**であり、**一度出荷した版に対してはしてはならない。** **あわせて確定した規則: 移行は「旧版のファイルが必ず開くこと」を保証しない。** 1 → 2 の移行は版番号を書き換えるだけで、**廃止した種別を持つファイルは移行後の検証で弾かれる**（＝開けない）。互換の読み替えを足す道は採らなかった——足すと「もう無い区別」がデータの中に別の顔で生き残るためで、**移行で吸収するか、検証で拒むかは、語彙を落とすときの設計判断である。**`src/core/load.ts` が `module.migrate(record, version)` を呼び、**移行した結果をスキーマ検証に掛ける**——移行は検証を飛ばさない（移した結果が不正なら `rejected`）。マイグレータの側は形を見ない（見ると検証の規則が2箇所に生える）。この経路は issue-tree-m3 まで**コメントだけが置かれた空席**だった。
- マイグレータ（旧版→新版の変換）は各ツールモジュールの提供物とする（6章のモジュール規約参照）。
- Skillとの関係：古いSkillが旧版スキーマで書いたファイルも、アプリがマイグレータで移行して開ける。Skill追従（4章）の失敗は「開けない事故」ではなく「移行で吸収される遅れ」に格下げされる。**ただしこの格下げが効くのは、改訂が「足す」側のときだけである**——語彙を落とす改訂（issue-tree の `judgementEvent.kind` を5語に畳んだ例）では、旧Skillが書いた廃止済みの値を持つファイルは移行後の検証で弾かれ、**開けない事故に戻る。** **語彙を落とす改訂を決めるときは、読み替えを移行に持たせるか、拒んで書き直させるかを明示的に選ぶこと**（issue-tree-m3 は後者を選んだ。読み替えを足すと「もう無い区別」がデータの中に生き残るため）。

### ID規約（全エンティティ共通）と用語参照

**ID規約はツール横断のメタ規約とする**（handoff-04で一般化。旧「用語参照：ID参照（nanoid）」の改訂）：

- **形式**：`<entityPrefix>_<id>`。`entityPrefix` は小文字英字のみで、エンティティ種別（用語・ノード・状態…テーブル名に相当）を表す。各ツール内の分類enum（カラム値に相当）とは別レイヤー。
- **ID本体**：nanoid の `customAlphabet` で**英数字62文字（A-Za-z0-9）・10文字固定**。
  - **改訂理由**：nanoid の標準アルファベットは `_` `-` を含み、区切り文字と衝突して自己記述性（目視・AI読解で「これは何の参照か」分かる）とスキーマ検証の正規表現（`^term_[A-Za-z0-9]{10}$` の型で一行検証できる）を汚すため。62¹⁰ ≒ 8.4×10¹⁷ 通りあり数百レコード規模で衝突の余地はない。
- **プレフィクスの粒度はエンティティ単位**（ツール単位で `node_` に統一しない。状態遷移なら `state_` / `event_` 等）。具体命名は各ツールセッションの管轄。
- **宣言と衝突防止**：各ツールの JSON Schema がプレフィクスを正規表現パターンとして宣言し、コアのモジュールレジストリが**登録時にプレフィクス重複を検査**する。スキーマに書かれていればAIもそれを読んで正しいIDを生成できるため、Skill側への伝達も自動的に済む。
- **連番IDは禁止。** アプリとAIが並行して要素を追加する設計（4章）では、連番だと双方が「次の番号」として同じIDを振る衝突が必発する。ランダムIDなら並行する書き手同士がIDで衝突することは構造的にない。

**用語参照**：用語集の各用語に不変ID（`term_` プレフィクス）を振り、他ツールはIDで参照する。表示時に用語集ファイルから名前を解決する。マジックストリング禁止・定数参照のみ、の思想をデータに適用したもの。

- 検証は二段構えで、結果は**2レベル**に分かれる。原則は「人間が直せる状態で見せる」——拒否すると修正に外部エディタが要るため、拒否は解釈不能な場合に限る：
  1. **スキーマ検証**（JSON Schema）：構造の正しさ。不合格は**レベル1（拒否）**＝開けない。構造が解釈できないデータはエディタに載せようがない。
  2. **整合性検証**（アプリ実装）：スキーマで表せない検証。外部キー検証に相当。不合格は**レベル2（受け入れて赤表示）**＝可視のエラーとして表示し、必要な機能のみ縮退する。編集は可能なので人間がアプリ内で直せる。項目：
     - **参照切れ**（参照IDが用語集に実在しない）：発生原因を問わず同一扱い（用語の削除起因でも、AIによるID捏造起因でも）。参照箇所を赤表示する。
     - **ID重複**：赤表示。
     - **name** の重複：赤表示。用語集は「この語を正式名として扱う」という宣言であり、同名2件は宣言としての矛盾。IDが異なるためスキーマの uniqueItems では防げず、追記が繰り返されるほど発生確率が上がるため、整合性検証で受け止める。（判定は NFKC 正規化＋英字大文字小文字同一視で行い、alias 照合と規則を揃える）
     - **単一性違反**：単一性を宣言した `type`（現時点では `glossary` / `errorCatalog`）のファイルがフォルダ内に2つ以上ある場合はエラー提示し、**そのファイルの解決を伴う操作を停止する**（解消するまで）。用語集なら用語解決、エラーカタログならエラー参照の解決。どちらを正とするかは人間にしか判断できないため、アプリが勝手に選ばない。
     - **用語集が0個**の状態は正常（新規プロジェクト）。初めて用語登録が発生した時点でアプリが用語集ファイルを自動生成する。用語集不在のまま参照だけ存在する場合（AI生成物の取り込み等）は参照切れとして赤表示。
- 検証は**全経路共通**（自動保存も外部由来ファイルも同じ検証を通る。8章）。AI起因で起きやすい問題（存在しないIDの捏造等）だからこそ検証の価値が高いが、経路によって検証や信頼度を変えることはしない。
- **検証スコープはプロジェクト全体**：プロジェクトを開いた時点でフォルダ内全ファイルを走査・検証し、エラーはファイル一覧に赤バッジで表示する。以後はファイル変更（自己編集・外部変更とも）を契機に再検証する。「フォルダに置かれただけで開かれていない壊れたファイル」も開かずに見える。規模（数百レコード）なら全走査は一瞬。
- **用語削除時の挙動**：**即時削除**し、トーストで参照切れ数を通知する（Undoで復元可）。確認ダイアログは挟まない——会議中の入力速度を削ぐため。削除ブロック（DBのRESTRICT相当）も採らない。参照側はレベル2の参照切れとして赤表示され、「問題は消せなくして見せる」というこのツールの思想に照らせば、参照切れは防ぐものではなく赤く見せるもの。

### 保存：自動保存＋Git

- 編集はデバウンス付き自動保存でファイルへ書き込む。会議中の保存忘れをゼロにする。
- 「試しにいじって捨てる」の受け皿はGit（プロジェクトフォルダをリポジトリ管理し、コミット＝チェックポイント）。アプリ内Undoは会議中の直近操作の取り消しに専念する二層構造。
  - **申し送り（実装時に検討）**：会議中に手でコミットするのは摩擦になる。会議・編集開始時の自動チェックポイント等、コミット操作を意識させない仕組みを検討する。
- Git前提のためシリアライズは決定的にする。diffのノイズを排除し、変更履歴を仕様の変更履歴として読めるようにする。具体値は以下で確定（用語登録Skillセッションにて決定。Skill側 glossary-write.mjs の実装と完全一致させること）：
  - キー順：JSON Schema の properties 記載順から実行時に導出する（アプリ側にハードコードしない。「スキーマが正」を正規化にも貫き、フィールド追加時に正規化ロジックの修正を不要にするため。$ref の解決を含む導出が必要）
  - インデント：スペース2 ／ 改行コード：LF ／ 末尾改行：あり ／ BOM：なし（読み込み時は除去する） ／ 非ASCII：エスケープしない
  - 配列順：UIの並び順を正とする
  - この一致は回帰テストで担保する（Skillが書いたファイルをアプリが読み→保存してバイト単位で不変であること）。プロジェクト最大のリスク箇所。

#### 正規形の定義（全ツール共通・2026-08-01 確定）

| 項目             | 値                                                                                                                                                             |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| キー順           | **各スキーマの `properties` 記載順**。ハードコードせず、正規化処理が実行時に `Object.keys(schema.properties)` を読んで並べ替える（`$defs` 配下の入れ子も同様） |
| インデント       | 半角スペース2                                                                                                                                                  |
| 区切り           | キーと値は `": "`、要素間は `",\n"`（`JSON.stringify(v, null, 2)` 準拠）。空配列は `[]`、空オブジェクトは `{}` を1行で                                         |
| 非ASCII          | エスケープしない（日本語をそのまま出力。`\uXXXX` にしない）                                                                                                    |
| 改行コード       | LF                                                                                                                                                             |
| 末尾改行         | あり（1つ）                                                                                                                                                    |
| エンコーディング | UTF-8（BOMなし）                                                                                                                                               |
| 配列順           | 書き換えない（UIの並び順が正）                                                                                                                                 |

- キー順の「正」はスキーマファイル一つに置く。スキーマの properties を並べ替えれば正規形も自動追従し、二重管理が発生しない（スキーマ実体をアプリとSkillで共有する方針と一貫させる）。
- 改行コードは**プロジェクトフォルダ雛形に `.gitattributes`（`*.json text eol=lf`）を同梱して担保する**。これがないと `core.autocrlf=true` の環境でチェックアウト時にCRLF化し、アプリがLFで書き戻すたび全行diffになり、決定的シリアライズの目的が無効化されるため。雛形生成はプロジェクト作成機能の責務に含める。
- 参照実装は `JSON.stringify(reorder(value, schema), null, 2) + "\n"` を UTF-8 で書き出したバイト列。他言語で書く場合もこのバイト列に一致させる（Python なら `json.dumps(v, ensure_ascii=False, indent=2)` 相当）。
- **正規化の責務はアプリが持ち、タイミングは「書き込み時」とする。** アプリは自分が書くとき必ず正規形で書く。**読み込み・閲覧では書き戻さない**（開いただけでファイルが変わると、閲覧だけでGit diffが発生し「変更履歴を仕様の変更履歴として読める」という目的自体を毀損するため）。
  - 帰結：外部の書き手（Claude Code等）の生ファイルは、次にアプリで編集・保存されるまで非正規のまま残り、最初の意味的編集のdiffに正規化差分が混ざる。これは許容する。
  - Skill側の出力仕様にも正規形を含めるが、これは非正規ファイルがGit履歴に入る瞬間を減らす緩和策であり、保証はアプリ側（「書き手を信用せず受け口で保証する」原則。JSON Schemaはキー順を規定できないため、スキーマ検証では担保されない）。
  - **申し送り（実装時に検討）**：diffを綺麗に保ちたい場合向けに、明示操作としての「プロジェクト一括正規化」コマンドを検討する。

### DBを採用しない理由（再検討時のために残す）

- AIとのラウンドトリップが前提である限り交換形式としてのJSONとそのスキーマ定義は消えず、DB採用は「DB⇄JSON変換層」を追加するだけになる。
- DBの外部キー制約が守るのはDB内部のデータであり、AI生成物の読み込み時検証は結局アプリ側で書く。
- このツールのデータは「アプリの状態」ではなく「文書」。フォルダコピーで持ち運べる・Gitで差分が見える可搬性を優先する。規模（1プロジェクト数百レコード程度）にもDBの必然性がない。
- 将来、全プロジェクト横断検索等の要求が出たら、正はJSONのままSQLiteを検索用インデックス（導出データ）として足す。「正となるデータは一つ、図は導出」の応用。

## 6. アーキテクチャ：統合形態

### 決定：単一アプリ（ファイルベース統合）

- 1つのTauriアプリがプロジェクトフォルダを開き、中のJSON一覧から任意のファイルを開いて編集する。エディタ部分はファイルの `type` に応じて切り替わる（VSCodeがファイル種別でエディタを変えるのと同じ構造）。
- **ファイル一覧の額縁機能**：
  - **新規作成**（type を選んで作成）。**衝突しないファイル名の判定はディスクに問い合わせる**（M5 で確定）——走査時のメモリ上スナップショットだけで決めると、走査後に外部で増えたファイル（Skill が書いた用語集など）を確認もエラーも出さずに切り詰めて上書きする。外部変更検知が入っても監視は取りこぼしうるため、この確認は監視とは別に要る。
  - **削除**（OSのゴミ箱へ移動。完全削除はしない）。用語集の単一性違反（5章）等の解消をアプリ内で完結させるため——「拒否は修正に外部エディタを強いるので最小限に」の原則を、ファイル操作にも適用する。
  - 検証エラーの赤バッジ表示（5章の検証スコープ参照）。
  - **選択中ファイルの `title` の編集**（M13 で確定）。エディタ領域の直上に名前の帯を置き、**モジュールのエディタは `title` を描かない**——キャンバス系（ロジックツリー・シーケンス）はエディタ側に置き場所が無く、モジュールごとに実装すると5箇所に散るため、額縁に置くことで5ツールが同じ形を得る。**名前の実体は JSON の `title` であってファイル名は変えない**（ファイル名は識別子ではない。5章）——エクスプローラでリネームされれば連動は破れるので、アプリ内で「名前は1つ」に見せない。書けないファイル（`rejected` / `listOnly`）では読み取り専用にする。
  - **一覧の行は主が `title`、副がファイル名**（M13 で確定）。ファイル名は識別子ではない（5章）のだから、大きく出すのは人間がつけた名前の方。`title` が空なら `(無題)`、読めないファイルはファイル名に落ちる。
  - **一覧は種類ごとにまとめる**（M13 で確定）。見出しの順はレジストリの登録順（新規作成ボタンと同じ順）、未登録の type はその後ろに type 文字列の昇順、type が読めないものは最後。グループ内は `title` の `localeCompare('ja')` 順で、**五十音順ではない**（漢字は ICU の照合順。読みはデータに無い）。
- **用語のインライン登録**を共通コンポーネント要件とする：他ツールのエディタで用語参照を入力する場面から、その場で新規用語を登録できる（用語集エディタへの往復を不要にする）。会議中に用語を増やしながら進める使い方の核であり、入力速度最優先の適用。用語集ファイルの自動生成（5章）はこの動線が発火点となる。詳細仕様（新規登録／既存用語の別名として登録の2アクション）は glossary/session-notes.md 論点6で確定。
- handoff-05の選択肢では「(b) 独立ツール＋共通データ形式」をデータ層で採り、アプリの皮だけ統合した形。懸念だった「会議で1ツールだけサッと開ける手軽さ」は、実体が「フォルダを開いてファイルを選ぶ」操作なので損なわれない。
- 用語集のID解決・整合性検証・共通コンポーネントは全ツール共有のロジックであり、単一アプリならコードを1箇所に置ける。別アプリ4本方式は同じコードを4回配布・更新する保守不利のみが残るため不採用。

### 拡張要件：ツールは増える前提で作る

- 新ツールの追加を「コアの改修」ではなく「モジュールの追加」にする。各ツールは以下を1セット提供するモジュールとして実装する（ツールモジュール規約）：
  1. `type` 識別子（enumへの追加）
  2. JSON Schema（データ形式の定義。ID規約のプレフィクス宣言を含む。5章）
  3. エディタコンポーネント（Reactコンポーネント）
  4. 整合性検証ルール（用語参照チェック等、スキーマで表せない検証）
  5. 出力ロジック（Markdown/Mermaid等への変換）。**複数の出力プロファイルを返せる**こと（下記）。加えて**副作用を持たない純関数とする**——額縁がクリップボードコピーと `.md` 書き出しの両方に同じ関数を使うため、モジュール側がファイルやクリップボードに触ってはならない（M6で確定）。**M9で `outputs`（`OutputProfile` の配列）として実装が確定した**。プロファイルは `id` / `label` / `fileSuffix` / `toMarkdown` を持つ。`fileSuffix` を `label` から導出しないのは、表示名が画面の都合で変わるのに対し、書き出したファイル名はGitに成果物として残る側だから。**0本を許す**（logic-tree M1 で確定）——出力をまだ作っていないツールの正しい状態であり、額縁（`ExportMenu`）は `outputs[0]` が `undefined` なら書き出し・コピーの両ボタンを `disabled` にする。**規約は「1つ以上」ではなく「0本以上」であり、出力を後の段階に回すツールは `outputs: []` を宣言する。**
     **`OutputProfile` は sequence M3 で任意の `describeIssueEffect`（整合性エラーがあるまま出力しようとしたとき、出力に何が起きるかを述べる1文を返す関数）を追加した。** 何が起きるかはツールごとに違う（用語集の ID 重複と、シーケンスの参照切れでは出力の帰結が別）ので額縁が文面を持てず、モジュール側の任意スロットとした。**規約の点数（7点＋`createEmpty`）は増えていない**——M9 が規約5を複数プロファイルへ拡張したのと同じ層の拡張として扱う。あわせて、**額縁は整合性エラー（レベル2の赤）があるファイルを出力（コピー／書き出し）しようとしたとき、確認ダイアログを挟む**（sequence M3 で実装）。気づかずに参照切れ等を含んだまま出力する事故を防ぐのが目的で、`describeIssueEffect` があればその文面を確認ダイアログの本文に足し、無ければ汎用文だけになる。
  6. マイグレータ（旧schemaVersion→新版への変換。5章のバージョン互換参照）
  7. **単一性フラグ**（このtypeがプロジェクトに1つだけかどうか。5章のファイル構成参照）
  8. **表記ゆれ検知の対象フィールドパス一覧**（検知の実行はコア。下記）
- 規約8点に加えて、**空文書の雛形**（`createEmpty(title)`）をモジュールが提供する。額縁の新規作成は `type` からモジュールを引いてファイルを作るため、雛形を置ける場所はモジュール側しかない。
- **表示名とアイコンはセットで持つ**（`displayName` / `icon`。**M14 で `icon` を追加**）。一覧に出す以上、両方が要る——サイドバーの「新規作成」ボタンやツール切替がアイコン付きの一覧としてツールを並べるため、名前だけでは足りない。`icon` は `ComponentType<{ className?: string }>` で受け、`LucideIcon` 型は書かない（コアを lucide に依存させないため。lucide のアイコンはこの型に代入できる）。
- **整合性検証の指摘の一覧は額縁が出す。モジュールは出さない**（`src/components/IssueBanner.tsx`。**M14 で確定**）。モジュールが `issues` を受け取るのは**セル・行・ノードの赤表示のため**であって、一覧の描画のためではない。M14 以前は4つのエディタと額縁の計5箇所が同じ `<ul>` を持っており、面も余白もばらついていた。さらにキャンバス系（シーケンス・ロジックツリー）は絶対配置の帯の中に置いていたため、**指摘が増えるほど図を覆う**——赤が出ているファイルほど図を触りたいのに、その図が隠れるという逆向きの挙動になっていた。額縁がエディタの外（通常フローの兄弟）に出すことで、指摘が増えたぶんだけ下の領域が縮む＝図や表が押し下げられて重ならない。**3件までを出し、超えたぶんは「他 N 件を表示」で畳む**（件数を言わないと畳まれていること自体に気づけない）。
- **列を持つツールの共通機械はコアに置く（M9で確定）**：セルの面の判定・列幅添字の写像・Tabのセル移動・行操作とフォーカス予約・重複検出は `src/core/list-editor/` と `src/core/duplicate.ts` にある。**モジュールが持つのは列データ（`COLUMNS`）とフィールド宣言（`FIELD_ORDER` / `FIELD_LABELS`）だけで、それを動かす機械はコアが持つ。** 抽象の粒度は純関数＋小さなフック1本とし、「列定義を渡すと全部返す」1本のフックには集約しない——引数が肥大し、実例2本目で決めるには早すぎる抽象になるため。
  **M10 で Markdown 表の整形（`src/core/markdown-table.ts`：セルのエスケープ・行と区切り行の組み立て・見出しの改行潰し）も加わった。** 表のセルのエスケープ規則は `normalizeForMatch`（照合規則）と同じく**アプリ内で1つだけ**——ツールごとに書き直すと、順序や改行の扱いが食い違って「あるツールの出力だけ表が割れる」という最悪の挙動になる。
- **キャンバス系ツールの共通土台は `src/core/canvas/` へ引き上げた（M20 で確定）**：対象はビューポート（d3-zoom の配線）・測定層（折り返し）・フォント読み取り・平坦木の組み立て・木のレイアウト（`layoutTree`）・エッジのパス生成（`edgePath`）の6点で、**3本目のキャンバスツール（課題ツリー）が来ることが判断の契機になった**——モジュール規約の境界（コア／各ツールモジュール）は跨がないため、新ツールから既存モジュールを import する選択肢は無い。sequence M1 が「一般化は2本目完成後の別マイルストーンで判断する」と保留した宿題（[`open-issues.md`](open-issues.md)）は、この2本目（sequence）と3本目（課題ツリー）が揃った時点で判断が下りた形になる。**木のレイアウトそのものは「木を描くツールのための関数」としてコアに置いた**——ロジックツリー・課題ツリーは Reingold–Tilford 型の再帰（部分木を畳んで親を中心に置く）で性質が揃うのに対し、**シーケンスの積み上げ型レイアウト（X も Y も単純な積み上げ。列間隔は区間を跨ぐラベルの最大幅から、行高は `max(ラベル高, スロット群の高さ)` から決まる）は性質が異なるため各モジュールに残した。** **レイアウトのほかに**各モジュールに残るのは、**箱の寸法定数**（`NODE_*` / `LABEL_*` 等）とそれに対応するクラス定数（`NODE_BOX_CLASS` 等）、**そのツール固有の畳み方**（寸法定数を測定層の関数へ渡す薄い包み。sequence では加えてラベル文字列の組み立て `gutterLabelText`）、そしてエッジの SVG レイヤ（`TreeEdges.tsx` / `SequenceEdges.tsx`）である。シーケンスの積み上げ型レイアウト本体（`sequence/layout.ts`）は上の「積み上げ型レイアウトは各モジュールに残した」で述べたコードそのものを指す。「測定層と描画層が同一のフォントトークンを参照すること」（9章）という規約自体は変わらない。
  - **その3本目（課題ツリー）が issue-tree-m1 で実際にコアへ載り、引き上げの範囲が正しかったことが確かめられた。** 新しいモジュールが持ったのは箱の寸法定数（`ISSUE_*` / `BADGE_*` / `PANEL_*` などと、それに対応する `ISSUE_BOX_CLASS` / `PANEL_BOX_CLASS`）と、**そのツール固有の畳み方**だけである——課題ツリーは**課題を1つのブロックとして畳み、そのブロックの寸法を `layoutTree` に渡す**（木のレイアウトはブロックの中身を知らない）。**issue-tree-m3 でブロックの中身を作り替えたが、コアは1行も動いていない**——「課題ノード＋ぶら下がる仮説カードの束」だった中身は「箱1つ（中に仮説を1行ずつ畳み、判断は行末のバッジ1つ）＋展開した仮説だけの内側パネル」になり、寸法定数は総入れ替えになったが、`layoutTree` に渡すのが「ブロックの寸法」であることは変わらないので、**変更はモジュールの中で閉じた**。境界が正しいことの2度目の確認になっている。**俯瞰の表現（何を箱にし、何を行にし、何をバッジ1つに畳むか）の「正」は設計ノートの D10**である。**この形は「モジュールが持つのは寸法とツール固有の畳み方だけ」という上の線引きの、コアを1行も触らずに済んだ実例になっている。** エッジは `IssueTreeEdges.tsx`（SVG レイヤはモジュール）が `edgePath` を**課題ノードの矩形**に対して呼ぶ（ブロックの矩形から引くと、線が課題ではなくカードの束を指す）。抑制された枝は**破線**（`strokeDasharray`）にし、**色は `stroke-rule` のまま変えない**。`stroke-grid`（`--grid`）へ落とす案は採らない——それは方眼紙の線のトークンで、`bg-grid-paper` がキャンバスの地を同じ値で塗っているため、**その色で引いた線は地と見分けられなくなる**（抑制された課題の箱は `bg-surface` の面のまま描かれ続け、薄くなるのは枠と文字だけなので——`border-ink-faint bg-surface text-ink-faint`。issue-tree-m3 で確定——線だけが消えると「見送った枝」ではなく「親を持たない箱の群れ」に見える）。`stroke-rule` を半透明にする案も採らない——検算していない濃さを作らないためで、面の側で `opacity` を使わない判断と同じ理由である。**背景の模様のトークンを前景の構造に借りない**というのが、この2つに共通する線引きである。
- **出力は複数プロファイルを持てる（エラーカタログセッションで判明）**：同じデータでも読み手によって出すべき列が違う。エラーカタログはサポート向け（業務レベルの原因＋対応）と開発向け（仕様レベルの説明を含む全列）の2種を出す。
  - 一般化：**「正となるデータは一つ、図は導出」の適用先が図だけでなく出力にも及ぶ**。読み手ごとにファイルを分けるのではなく、1つのデータから出し分ける。分けた瞬間に二重管理が発生し、文章仕様書の問題（読み手に関係ない情報まで直列で読ませる／コピーが分岐する）が再生産されるため。
  - 用語集は現時点で1プロファイル、ロジックツリーとシーケンスは0本（それぞれ M2 以降で足す）。規約上は「**0本以上**の出力プロファイル」に統一する。
  - **M10 で2プロファイルの実例が実装確定した**：モジュールが宣言するのは**フィールドの並び1本**（`profiles.ts`）で、画面の列（`No` ＋ `fields`）と出力の列（`No` ＋ `fields` から グルーピング軸を除いたもの）を**そこから導出する**。列セットを2箇所に書くと片方だけ直したときに黙ってずれるため、`OutputProfile`（コアの契約）には列を持たせず、列の関心はモジュール内に閉じる。
- **表記ゆれ検知はコア機能（エラーカタログセッションで確定）**：ルールベース検知（用語集の name / aliases に対する照合、NFKC正規化、suggestion 区分）の**実装はコアに1つだけ置く**。各モジュールが提供するのは「自分のどのフィールドを検知対象とするか」の宣言のみ。
  - 理由：検知は全ツールが必要とするため、モジュール側に実装を置くと正規化の有無やマッチ強度がツールごとにぶれ、「ツールによって指摘が出たり出なかったりする」という最悪の挙動になる（プロトタイプ4本で実装差が出た件の再発防止）。
  - 用語集モジュールの役割は**照合データの提供（参照される側）**であって、検知の実行主体ではない。この整理は用語集セッションの分担を変えるものではなく、実行主体をコアと明示するもの。
  - 備考：**自由テキストと備考の切り分けは各モジュールの判断**。用語集が `notes` を検知対象外としたのと同様、モジュールごとに宣言する。
- **整合性検証の責務内訳（handoff-04で明確化。規約の変更ではなく解像度の向上）**：
  - **モジュール内検証**：自ファイル内で完結する検証（例：用語集の alias 重複）→ 各モジュールの提供物（上記4）。
  - **コア横断検証**：単一ファイルでは判定できない検証（例：単一性違反）→ コアの仕事。
  - **参照切れ検証**：「参照する側」の各ツールモジュールの提供物。参照される側（用語集）はこの検証を持たない。
- コア側はモジュールのレジストリを持ち、`type` からモジュールを引いてエディタ・検証・出力を呼び出すだけにする。レジストリはモジュール登録時にIDプレフィクスの重複を検査する（5章）。
- **前方互換**：未知の `type` のJSONに遭遇してもクラッシュせず、「このバージョンでは編集できないファイル」として一覧に表示だけする。古いアプリで新しいプロジェクトを開く事故に備える。

## 7. 技術スタック

### 決定：Tauri＋TypeScript＋Tailwind/shadcn

- **配布形態はTauriデスクトップアプリ（Windows想定）**。社内でのWeb公開はホスティングの手間が大きいため採らない。インストールの一手間は当面利用者が作者のみなので許容し、チーム展開時に配布方法（社内配布手段、SmartScreen警告への対処）を再検討する。
- **Rustは原則書かない**。ロジックはすべてフロントのTypeScriptに置き、TauriはネイティブAPI（fs, dialog等の標準プラグイン）の提供層としてのみ使う。根拠：
  1. このアプリにRustを要する仕事（重い計算、バイナリ処理等）が存在しない。実体は「JSON読み書き＋UI＋検証」で規模は数百レコード、ファイルアクセスは標準プラグインが提供済み。書いても得るものがない。
  2. 実装をAIに委譲しても、レビューとデバッグの責任は人間に残る。読めない言語の層は監査不能なブラックボックスになる。AI委譲開発では人間の役割が「書く」から「検証する」に移るため、検証可能な言語に寄せる。
  3. ロジックがTS/Rustに分かれるとIPC境界が生まれ、境界をまたぐバグ（シリアライズの型ズレ、非同期タイミング）は単一言語内のバグより診断が難しい。バグの温床を構造的に増やさない。
  - 「原則」は禁止ではなくデフォルト。実証された必要（例：数千ノードのレイアウト計算がUIをブロックする）が出た場合は例外を認める。
  - なお**プラグインの登録**（`lib.rs` の `.plugin(...)` 1行とCargo依存1行）はこの原則の例外ではない。判断もロジックも持たず、ネイティブAPIの提供層を有効にするだけだから。M6でクリップボード書き込み（`tauri-plugin-clipboard-manager`）を同じ形で追加した。**ブラウザ標準の `navigator.clipboard` を使わなかった理由**は、権限が欠けたときに実行時に静かに失敗する経路になり、テストでも検出できないため——プラグイン側なら `clipboard-manager:allow-write-text` の欠落がcapabilitiesで確認できる（読み取り権限は与えない）。
  - 実際に認めた例外は4件：
    1. **OSのゴミ箱への移動**。fsプラグインは完全削除（`remove`）しか持たず、6章の「削除はOSのゴミ箱へ移動。完全削除はしない」をプラグインだけでは満たせないため、自前のTauriコマンド `move_to_trash` を1本だけ持つ。判断は一切置かず `trash` クレートを呼ぶだけにし、ロジックはTS側に残す。
    2. **PTY（擬似端末）のコマンド4本**（`pty_spawn` / `pty_write` / `pty_resize` / `pty_kill`。M11 決定3）。Claude Codeの端末ペインが「本物の端末」を要件とし、`tauri-plugin-shell` の標準出力ストリームでは raw mode の TUI を成立させられないため`portable-pty` を自前コマンドとして持つ。1件目と同じ根拠で例外を認める——**判断は一切置かない**。実行ファイル名・引数・作業ディレクトリはすべてTypeScript側が決めて渡し、Rust側のコードに `claude` という文字列は現れない。Rustの仕事はバイト列を左右へ流すことに尽きる。
    3. **Skill配置のための fs scope 許可**（`allow_skill_dir`。M11で追加、M15で拡張）。fsプラグインの実行時 scope はフォルダ選択ダイアログ由来のパターン許可（`<フォルダ>/**`）を持つが、unix既定の `require_literal_leading_dot: true` によりドット始まりの要素（`.claude`・Skillごとの `.gitignore`）に一致しない。`.claude` ディレクトリの許可と、Skill直下 `.gitignore` の literal 許可を1本のコマンドで行う。1件目・2件目と同じ根拠で例外を認める——判断は一切置かず、対象のディレクトリ名・Skill名一覧はTypeScript側（`skill-resources.ts`・`BUNDLED_SKILLS`）が決めて渡す。
    4. **プロジェクトフォルダの fs scope 再付与**（`allow_project_dir`。M18で追加）。フォルダ選択ダイアログが入れる実行時 scope はセッション限りで次回起動には引き継がれない。起動時に前回開いていたフォルダを自動で復元する機能はダイアログを経由しないため、`allow_skill_dir` と同じ形で scope を明示的に取り直すコマンドを1本持つ。1〜3件目と同じ根拠で例外を認める——判断は一切置かず、対象のパスはTypeScript側（`App.tsx` の起動時復元 effect）が決めて渡す。
- **TypeScript化**。型はJSON Schemaから自動生成する（5章参照）。
- **スタイリングはTailwind CSS＋shadcn/ui**。デザイントークン（9章）はTailwindの設定ファイルに定義し、デザインシステムと1対1対応させる。
- **shadcnの適用範囲は「額縁」に限定**：モーダル、ドロップダウン、ファイル一覧、トースト等の汎用UI。土台のRadixがフォーカストラップ・キーボード制御の実戦済み実装を持ち、自作アプリで苦戦しがちな「モーダル周りのバグっぽい挙動」をこの層ごと吸収する。コンポーネントはソースコピー方式なので朱／インクのデザインへの改造も自由。
- **各ツールのエディタ本体は完全自作**。Enter/Tab/Backspaceの操作言語に合う既製品は存在しない。この領域の入力体験リスクはライブラリでは消えないため、設計で抑える（キーボード処理の一元化とIME対応。10章参照）。
- 実装はAIに任せる前提。Tailwind＋shadcnはAIのコード生成が最も流暢な組み合わせであり、この前提とも整合する。
- プロジェクト雛形の必須要素：リポジトリに .gitattributes を置き、*.json text eol=lf を指定する。Windows の autocrlf 環境では、これが無いと commit 時に JSON が CRLF へ変換され、決定的シリアライズの LF 指定（5章）が Git 上で無意味になり毎回全行 diff が出る。正規化の努力を成立させる前提条件。

### 決定：配布は GitHub Releases、自動更新は Windows のみ（M19）

- 配布は GitHub Releases。**Windows のみ Tauri の updater プラグインで自動更新する**（エンドポイントは `releases/latest/download/latest.json`）。
- **mac を対象にしないのは updater の制約ではなく、未署名の `.app` が Gatekeeper に弾かれる現状が updater の手前にあるため。** 署名（Apple Developer Program）は別の意思決定。
- **minisign の秘密鍵は1台にしか置かない。** 失うと以後どのバージョンからも自動更新できなくなる。手順は `docs/release.md`。
- 更新の適用はアプリを終了させる（Windows の制約）ので、**利用者が押したときにしか走らせない**。

## 8. 出力・入力戦略

### 入力（インポート）は独立機能として消滅した

- 5章の決定により保存形式＝スキーマ定義されたJSONファイルとなったため、「AIの生成物を取り込む」＝「JSONファイルをプロジェクトフォルダに置いて開く」で完結する。専用のインポート機能は作らない。
- ただし読み込み経路には必ず二段検証（スキーマ検証＋整合性検証。5章参照）を通す。自動保存したファイルも外から来たファイルも同じ検証を通る構造にし、経路による信頼度の差を作らない。

### 出力はNotePM向けMarkdown（Mermaid込み）

- 第一の出力先はNotePM。出力形態は**クリップボードコピーとファイル書き出し（.md）の両方**を用意する。コピーは「会議直後に議事録へ貼る」最短動線、ファイルはGitに成果物を残す用途。
- どういうMarkdownを出すかは各ツールセッションで個別に詰める。本章では枠のみ定める。用語集は確定済み（種別グルーピングの表形式、h2/h3の見出し階層。glossary/session-notes.md 論点7）。エラーカタログも確定済み（サポート向け／開発向けの2プロファイル。`resolutionLevel` 別グルーピング、見出し階層は用語集と同じ。error-catalog/error-catalog-session-notes.md）。
- **用語集の出力仕様（M6で実装し確定）**：`##`＝エンベロープの `title`、`###`＝種別グループ。**h1は使わない**（NotePMのページタイトルと階層が衝突する。目次はh1〜h3収載）。グループ順は**種別enumの定義順に固定**し、**スキーマから実行時に導出する**（ハードコードすると enum 改訂時に静かにずれる。出力のたびに順が揺れるとGit上で無意味な差分になる）。空の種別は見出しごと省略、グループ内はデータ配列順。列は 名称／種別／定義／別名／備考でIDは出さない。`definition` 空は `（未定義）`、`undecided` は `未分類`（負債を出力にも残す。rev 5章）。
- **エラーカタログの出力仕様（M10で実装し確定）**：見出し階層は用語集と同じ（`##`＝エンベロープの `title`、`###`＝`resolutionLevel` のグループ、h1不使用）。グループ順は**enumの定義順をスキーマから実行時に導出**、空のグループは見出しごと省略、グループ内はデータ配列順。列は `No` ＋ プロファイルの宣言から `resolutionLevel` を除いたもの（サポート向け7列／開発向け9列）。**`No` はデータ配列の位置（index+1）**であり、グループごとに振り直さない——画面のNoと出力のNoが食い違うと、会議中に口頭で指すための目印として使えなくなる。空フィールドは `（未定義）`、`undecided` は `未分類` グループとして**サポート向け出力でも省略しない**。備考の空欄だけは `（未定義）` にしない（検知対象外の自由メモ。用語集の備考と同じ扱い）。
- **表のセルは書き手を信用せずエスケープする**：`\` を先に、次に `|` をエスケープし（順序が逆だと自分が入れた `\` を二重エスケープする）、改行は `<br>` にする。定義・備考は自由記述欄であり、Windowsパスや正規表現、外部が書いた複数行の定義が入ると表が途中で割れて1件まるごと読めなくなる。**見出しに使う文字列も同様に扱う**（`title` はスキーマ上ただの `string` なので、外部が書いた改行入りの値でh1が混入しうる）。
- **出力先は必ずしもNotePMではない**：エラーカタログのサポート向け出力は、サポートチームが**手書きでサポートサイトを作るための下書き**として渡る。インポート連携はしない（そのぶん更新は自動伝播しないが、「前回渡したコミットとの差分」をGitで取れば変更行は特定できるため、専用機能は作らず運用で吸収する）。
- 出力ロジックはツールモジュールの提供物（6章のモジュール規約の一つ。**0本以上の出力プロファイル**を返す、**副作用を持たない純関数**）。
- 状態遷移のJSONは保存形式そのものがC#パラメタライズドテストのデータソースになり得る（「表＝実行可能な仕様」）。専用のテスト用出力を作るかは状態遷移エディタのセッションで判断する。
- 出力実装の着手順は、ドッグフーディングで「使う」と確定したツールから（handoff-00の方針を継承）。

## 9. デザインシステム

### 決定：役割トークンとパレットの分離

- **M7 で色値を確定し、M21 で体系を作り直した。** M7 は [Morphos](https://morphos.ameyanagi.com) の `morphous-basalt` を下敷きにしたが、M21 で面・文字・線を無彩色に作り直した（設計スペック `docs/superpowers/plans/2026-08-23-m21-design-tokens-v2-design.md`。M7 当時の経緯は `docs/superpowers/plans/2026-08-09-m7-design-tokens-design.md`）。**`src/styles/palette.css` 1ファイルの書き換えだけで配色を差し替えられる構造は変わらない。** 差し替え後も `src/styles/palette.test.ts` がコントラスト要件（本文4.5:1、罫線3:1 等）を機械的に検証する。計算そのもの（sRGB への変換・コントラスト比・P型/D型のシミュレート）は `src/styles/contrast.ts` が1本だけ持ち、`palette.test.ts`・`palette-retheme` Skill・端末の配色（`src/core/terminal/theme.ts`）が同じ式を共有する。**M21 で半透明の面は廃止した**（`OVERLAYS` は無い。役割トークンへの透過は `conventions.test.ts` が弾く）——M8 は `bg-warning/20` のような面に載る文字をアルファ合成のまま測っていたが、面そのものを持たなくなったので測る対象が消えた。**差し替えの手順は `.claude/skills/palette-retheme/` が持つ。** 外部テーマの31変数のうち facet が使うのは7つだけで（残りは `index.css` が役割トークンから導出している）、対応物がない残る11個——`missing` / `pending` / `judge-yes` / `judge-yes-fg` / `judge-no` / `judge-no-fg` / `grid` / `ink-faint` と、淡い面3つ `missing-face` / `invalid-face` / `pending-face`（線色と同じ色相からの派生）——は候補から人が選ぶ。**拾う7つのうち `invalid` を除く6つは明度（L）だけを拾い、C は 0 にする**（面・文字・線は無彩色。下の規約6）。**`invalid` だけはテーマの赤の色相・彩度をそのまま保つ**——テーマの「雰囲気」を facet に持ち込めるのは意味色4つだけ、というのがこの Skill の設計である。要件を割った色は**色相と彩度を保ったまま明度だけ**動かす。要件の表そのものは `src/styles/palette-requirements.ts` にあり、**配色を差し替えても変わらない**。
- **二層構造**：コード・AI・以降のセッションが参照するのは役割トークン（意味の名前）のみ。色値（パレット）は差し替え可能な下敷き。色値の直書きは禁止（プロトタイプ4本で実装差が出た原因の再発防止。M7 では `src/styles/conventions.test.ts` がソースを走査してこれを機械検査する）。
- **役割トークンは 18個（M21。当初 15個に、実機確認で淡い面3つを足した）。色を持つのは「意味」だけで、面・文字・線は無彩色（C ≤ 0.01）**：
  - 面（無彩色）：`canvas`（地。方眼を敷く）／`surface`（作業する面）／`surface-muted`（**一段沈んだ面**。選択中タブ・ファイル一覧の種類見出し・端末のアクティブタブと選択面・見送りの箱。M8 の `surface-accent` の後継で、緑を捨て役割を「見出し」から「沈んだ面」に改めた——**テーブルのカラム名もこの面に載せる**。M21 の実機確認で「面なし（`text-ink-muted` ＋ `tracking-wide` のラベルだけ）では見出しの行がデータ行に溶ける」と出たので、無彩色の沈んだ面を敷く。緑帯の代替は「彩度のない面」であって「面なし」ではない）
  - 文字（無彩色）：`ink`／`ink-muted`／`ink-faint`（非アクティブ。3:1。**本文に使わない**。`opacity-*` の代わりに使う）
  - 線（無彩色）：`rule`（セル境界・入力枠。3:1）／`grid`（方眼と薄い装飾罫。要件の対象外）。境界は「情報を伝えるか否か」で引く
  - **欠落軸** `missing` ＋ `missing-face`（黄）：未定義・未分類・空セル・未回答・未決・仮説なし・保留。**淡い面**（`missing-face`）**＋線＋文字**。線種で段を分ける——破線＝まだ見ていない／実線＝見たが決められない（課題ツリーの語彙を全体へ）。白地で 4.5:1 を満たす黄は黄土色になる。これは仕様（付箋の黄）
  - **無効軸** `invalid` ＋ `invalid-face`（赤）：重複・参照切れ・整合性違反・スキーマ違反・読めないファイル。**淡い面＋線＋文字**（実線）。表記ゆれの「指摘（suggestion）」は波線下線（弱形。実装はまだ無い）。**黄と赤は D型色覚で色相では分かれないので明度で分ける**——`invalid` は `missing` より一段暗い
  - **着信軸** `pending` ＋ `pending-face`（青）：外から届いた入力に返答していない状態。いまは課題ツリーの「未判断」（`pendingNotes` が空でない）だけ。**淡い面＋線＋文字**
  - **淡い面 `*-face` は線色と同じ色相の、白（ダークは黒）へ寄せた面**（ライト L 0.93〜0.95、ダーク 0.30）。その上に `ink` / `ink-muted` / 同じ軸の線色が 4.5:1 で載ることを `FACE_REQUIREMENTS` が課す。**淡い面どうしの色差（ΔE 0.05 前後）に識別を負わせない**——欠落・無効・着信を分けるのは線の色と線種で、`DISTINCT_PAIRS` に淡い面は入っていない
  - **判断軸**：`judge-yes`＋`judge-yes-fg`（支持の**面**。明るい青緑）／`judge-no`＋`judge-no-fg`（棄却の**面**。チャコール）。見送りは専用トークンを持たず `surface-muted` の面＋`rule` の枠＋`ink-muted` の文字
  - **規約6条**：(1) 色を持つのは意味だけ——分類・ボタン・見出し・選択状態は彩度を持たない。(2) **開いているものは淡い面と線、決着したものは濃い面。** 線色そのものを面にしない（`bg-missing` / `bg-invalid` / `bg-pending` を作らない。面は `bg-*-face` の側が持つ）。緑の線も作らない（`conventions.test.ts` が両方を弾く）。淡い面と濃い面は明度で分かれるので、「開いている」と「決着した」の区別は面の側にも残る。(3) 判断軸で彩度を持つのは支持のみ。棄却・見送りは明度差（白黒でも判別。`FACE_PAIRS` が 3:1 を課す）。(4) **5色目は作らない**。新しい意味は4軸のどれかに入れるか、色以外のチャネル（線種・形・位置）で表す。(5) 削除だけはホバー時に `invalid` を借りる。常時は `ink-muted`。これ以外に借用を作らない。(6) 無彩色とは C ≤ 0.01（`ACHROMATIC` が弾く）
  - 意味色4つは標準・P型・D型のすべてで OKLab 色差 ≥ 0.10（`DISTINCT_PAIRS`。M7 は印字だけだったが M21 で門番にした。満たせなければ 0.08 まで下げてよいが、理由を `palette-requirements.ts` に書く）
  - **「未決を面で塗らない」（issue-tree-m3 → M21 で全モジュールの規約2に昇格）は、M21 の実機確認で反転した。** 27型 WQHD・ライトで実物を見た結果、1px の輪郭だけではテーブルのセル・ガターのスロット・バッジが方眼と罫線に埋もれて拾えなかった。**バッジも含めて淡い面を持つ。** issue-tree-m3 の「全部が塗られて一面になる」懸念は、**面を淡く（L 0.93〜0.95）して判断軸の濃い面と明度で分けること**で受ける——塗られていること自体は情報のままで、濃さが「開いている／決着した」を区別する
- **ライト／ダークモード対応**。同じ役割トークンにモードごとのパレットを割り当てる方式。反転による自動生成はしない（警告色が背景に沈む等の破綻を招く）。
- 実装はshadcnの標準規約（CSS変数による役割名定義＋モード切替）にそのまま乗る。7章の決定の帰結として土台が手に入る。

### 確定要素

- **方眼紙背景は M8 で実装した。** `src/index.css` の `bg-grid-paper` ユーティリティ（`var(--grid)` の `linear-gradient` 2本を `background-size: var(--grid-size)` で敷き詰める）で、マス目は 24px——`text-sm` の行高（14px × 1.65 ＝ 23.1px）とほぼ一致させ、方眼と文字行が揃って見えるようにしている。マス目のサイズは `index.css` 側に置く（`palette.css` は色値だけを持つ）。**`repeating-linear-gradient` に戻さないこと（mac の実機で判明）。** WebKit（macOS の WKWebView / Linux の WebKitGTK）は繰り返し勾配を「面の端から端までの1本の勾配」として標本化するため、24px 周期の 1px 線がほとんど落ちる——実機では横線の間隔が 24/72/96px とばらつき、縦線は画面全体で2本しか出ていなかった。Chromium（Windows の WebView2）は正しく敷き詰めるので**Windows では見えない**。1周期ぶんの絵を敷き詰める形にすると勾配の長さがマス目1つに閉じるため、標本化の誤差が出ない（`palette.test.ts` が形を固定している）。**要点は「地は方眼、作業する面は無地」**——`canvas` と `surface` を明度差ではなく**模様の有無**で見分けさせる。ライトでは両者の L 差が 0.04（1.13:1）しかなく、明度で分けようとすると破綻していた。地（`main`）に方眼を敷き、ヘッダ・サイドバー・テーブルは `surface` の無地の面にする。グリッド線の濃度はモード別に持ち、**M8 の実機確認でライトを `canvas` 上 1.36:1 から 1.17:1 へ薄めた**（会議で投影したときにうるさくない濃さが基準。ダークは変更していない）。
- **端末（xterm）の中も役割トークンに合わせる**（M17 で確定）。流し込むのは**面（`surface`）・文字（`ink`）・カーソル（文字と同色。その上に乗る文字は面と同色）・選択の面（`surface-muted`）の4系統**だけで、**ANSI の16色は持たない**——役割トークン（18個）に対応物が無く、持つと「配色を差し替える」作業が「16色を選び直す」作業になり、`palette-retheme` Skill の前提（**18個の役割トークンのうち7個は外部テーマの変数から機械的に拾い、対応物が無い残る11個だけを候補から人が選ぶ**——上の M7 の項）も壊れるため。ライトの面で既定の16色が読めるかは xterm 自身の `minimumContrastRatio`（**本文と同じ 4.5:1**）に任せる。**色値はソースに現れない**——`palette.css` のトークンを実行時に読んで sRGB へ変換する（`src/core/terminal/theme.ts`。xterm は `oklch()` を解釈しないため。変換式は `src/styles/contrast.ts` の既存のものを使い、**同じ式を2本持たない**）。**トークンが1つでも読めなければ配色を渡さず xterm の既定に落とす**——半端に流し込むと面だけ変わって文字が読めない端末になる。ライト／ダークの切り替えには、色ではなく「読み直す合図」を渡す。
- **ボタンのラベルの行間は要素セレクタで一律に揃える**（`src/index.css` の `@layer base` の `button { --tw-leading: 1.2 }`）。本文向けに広げた行間（`text-sm` の 1.65）がボタンに効くと、和文フォントの縦メトリクスの非対称でラベルが上へ寄る。個々のボタンで直すと「実装のたびに同じ指摘が出る」ので、新しく作ったボタンにも自動で効く形にする。**`line-height` を直接書かないこと**——Tailwind の `text-*` は utilities レイヤーで `line-height: var(--tw-leading, <既定>)` を生成し、cascade layers では後に宣言された utilities が base に勝つため届かない。utilities 側が普段設定しない `--tw-leading` へ逃がせば衝突自体が起きない。
- **フォントは M7 で確定した。** `--font-sans` は `'Geist Variable', 'Yu Gothic UI', 'Hiragino Sans', sans-serif`（和文フォールバックを明示。Geist は日本語グリフを持たず、フォールバック無しでは環境依存で字面が崩れる）。ファイルパス・件数・ID 用に `--font-mono`（`ui-monospace, 'Cascadia Mono', Consolas, monospace`）を新設した。フォントサイズは `text-xs`（12px）／`text-sm`（14px・本文既定）／`text-base`（16px・節見出し）／`text-lg`（18px・画面タイトル）／`text-2xl`（24px・アプリ名。額縁の看板だけに使う。M14 で追加）の5段に限定し、それ以外の段と任意値 `text-[...]` は自作コードで使わない。**`text-xl` は開けていない**——段は使う役割があるぶんだけ持つ約束で、`text-lg` との差が 2px しかない段はどちらを使うか決められないため。行間は日本語向けに `1.5` / `1.65` / `1.5` / `1.4` を明示した（Tailwind 既定の英文基準では複数行の定義文が詰まって読みにくいため）。
- **数字は等幅**（UI ノート D9。`index.css` の `body { font-variant-numeric: tabular-nums }`。テーブルの No 列は右揃え）。件数・ID・No のような**桁で読む数字**が縦に並ぶ場所で、プロポーショナルな数字は桁位置が揃わず、差分を目で拾えない。`body` に1行置けば全画面に効くので、**個々の要素で当て直さない**。
- **キャンバス系ツールでは、測定層と描画層が同一のフォントトークンを参照しなければならない**（logic-tree M1 で確定）。ノードの幅・高さ・折り返し位置は、DOM に触れないオフスクリーン `<canvas>` の `measureText` が**描画前に**確定させる（1パスで描くため。`docs/logic-tree/logic-tree-canvas-tech-notes.md` 論点4）。測定に使うフォント指定が実際に描画されるフォントとずれると、**全ノードのサイズが一斉に狂い、文言が枠から切れる**。実装は `getComputedStyle` でノードの実効フォント（`font-family` / `font-size` / `line-height`）を読み、それを測定器の鍵に混ぜる形（`src/core/canvas/canvas-font.ts`。**M20 でコア化し、ロジックツリー・シーケンス双方がここを参照する**）。**Web フォントの読み込み完了（`document.fonts.ready`）で測り直す**ことも要る——最初の1フレームはフォールバックのメトリクスで測っているため。
- 共通コンポーネント（ツールバー、バッジ、モーダル、チップ）の仕様化は、色確定後ではなくトークン確定後に着手できる（役割名で実装できるため）。個別の仕様は各ツールセッションまたは実装時に詰める。**M8 で最初の1枚として `src/components/button-styles.ts` の `buttonBase` を置いた**——shadcn の `Button` を使うほどでない生の `<button>`（フィルタのチップ、一覧の行、トーストの操作）が共通で敷く土台で、用途ごとの差分（余白・文字サイズ・色）は各所に残す。**新しいボタンもここを通す。** 自前のレイアウトを持つ要素（ファイル一覧の行のように、中で `flex` を組んでいるもの）に土台を敷くと壊れるので、そこは例外としてコメントに理由を書く。**M21 で `Badge`（`src/components/Badge.tsx`。意味を variant で受け、形は部品が持つ）と `Chip`（`src/components/Chip.tsx`。選択トグル。選択は黒塗りではなく `surface-muted` の面と `ink` の枠）を置いた。** 状態のバッジを新しく描くときは `Badge` を通す。課題ツリーの語彙と部品の variant の対応は `src/modules/issue-tree/badge-variant.ts` が持ち、部品は語彙を知らない。**部品のファイルは部品だけを export する**——variant の型・クラスの導出・寸法の定数は隣の `src/components/badge-styles.ts`（`BadgeVariant` / `badgeClass` / `BADGE_BOX_HEIGHT`）に置く。`KeyHints.tsx` と `hint-text.ts` と同じ分け方で、oxlint の `react(only-export-components)` を 0 に保つための構造である。
- **塗りつぶしたボタン（`default` variant）は使わない（M21。UI ノート D19）。** エディタの主操作はセルに文字を打つことでボタンではないので、ツールバーは全部 `outline`（Secondary）。**`ghost`（Tertiary）は許可するが現状使用は0件で、アイコンだけのボタン（Undo/Redo。`src/App.tsx` の `size="icon"`）も `outline` である。** `conventions.test.ts` が `variant` 無しの `<Button>` を弾く。**例外はモーダルのダイアログ（`ConfirmDialog` / `ChoiceDialog` の `AlertDialogAction`）だけ**——モーダルの本体はそのボタンで、主操作が1つだけ存在する（UI ノート D19 の論理そのもの）。黒塗りは M21 でトグル（状態）から外したので「押すもの」の意味に専有されている。`conventions.test.ts` の検査は `<Button` だけを見るので、この例外は検査の外にある。M8 の『1画面に1つ』はこれで置き換わる。**許可する variant は `outline` と `ghost` の2つだけで、shadcn が持つ `destructive` も使わない**——色の紐付けは済んでいる（`index.css` の `--destructive: var(--invalid)`。`palette.test.ts` が検査する）が、**`destructive` variant が使うのは透過の面**（`src/components/ui/button.tsx` の `bg-destructive/10` ／ `hover:bg-destructive/20` ／ `focus-visible:ring-destructive/20` ／ ダークの `/20` `/30` `/40`）で、**規約2（無効が持つ面は淡い面 `invalid-face` だけで、`invalid` そのものを面にしない）と M21 の透過全面禁止の両方に触れる。** 生成物を手で整形して直すこともできる（7章のとおりソースコピー方式なので改造は自由）が、**使用が0件である以上、直すより「使わない」と決める方が安い。**削除は生の `<button>` に**常時 `text-ink-muted`・ホバーで `text-invalid`**（`src/components/FileList.tsx`。規約5の借用そのもの）。
- **セルの「無効」「欠落」は淡い面だけで示す**（M21。`src/core/list-editor/cell-face.ts` の `CELL_FACE_CLASS`。**規約2の例外**）。用語集・エラーカタログのセルは **無効＝`invalid-face`・欠落＝`missing-face`** の面だけで、輪郭を引かない。経緯は2段——最初は輪郭だけで作り、実機確認で「方眼と罫線に埋もれて拾えない」と出て淡い面を足し、次の一巡で「表の中では輪郭がテーブルの罫線と競合してノイズになる」と出て輪郭を外した（2026-08-24）。欠落と無効の区別は面の色相（黄／赤）が運ぶ。バッジは線種（破線＝まだ見ていない／実線＝保留）が情報を運ぶので線を残しており、セルとは扱いが違う。`CellFace` は1セルにつき1つしか返さず淡い面も不透明なので、M8 が避けていた「半透明の二重塗り」は構造的に起きない。行全体に掛かる指摘は行の帯ではなく**先頭セルに1つ**出す（`rowAnchor`）。シーケンスも同じ形に揃え、**行の帯を廃して `#N` の通し番号に無効を出す**——面が二重に重なる構造そのものが無くなった。**`outline-dashed` を使うときは、そのユーティリティが生成 CSS に載っていることを確かめること**——Tailwind v4 は `outline-style` を `@property --tw-outline-style`（初期値 `solid`）経由で当てるので、実線しか使っていないうちは破線の宣言が出力に現れない。
- **フォーカスは面の塗り替え（`focus:bg-*`）ではなくリング（`focus:ring-2 focus:ring-inset focus:ring-ring`）で示す。** 面の色は変わりうる（`bg-surface` になった瞬間 `focus:bg-surface` はコントラスト比1.00:1で消える）ためで、**M21 でこの規約はもう一つの根拠を得た**——状態の表示の主役が輪郭になったので、**無効・欠落の淡い面（`bg-invalid-face` 等）と輪郭（`outline-invalid` 等）はリングと独立であり、フォーカスで消えない**（リングは枠の内側に重なるだけで、面も輪郭も塗り替えない。M8 の用語集エディタで発覚した「面を塗り替えると警告表示ごと消える」欠陥は、これで構造的に起きなくなった。ロジックツリー・シーケンス・状態遷移の各エディタも同じ構造に当たる）。
- **`KeyHints`（`src/components/KeyHints.tsx`）を M14 で共通部品として置いた。** 操作ヒントの修飾キーは文中に `$mod` / `$alt` というプレースホルダで書き、`hint-text.ts` の解決関数が実行時のプラットフォームに応じて `Ctrl`/`Cmd`・`Alt`/`Option` へ置き換える。**画面に `Ctrl` と直接書かないこと**——macOS では主修飾キーが `Cmd` なので、文字列を直書きすると誤った操作説明になる。シーケンス・ロジックツリーの両キャンバスがこの部品でヒント帯を出している。帯の面は不透明の `bg-surface`（M21 で透過を外した）。
- **帯（ヘッダーやキャンバスの操作帯）の中で伸縮を引き受ける要素は1つに限る。** 長くなりうる要素（フォルダパス、ファイルタイトル等）だけを `min-w-0`／`truncate` で伸縮させ、アイコンボタンや操作ヒントなど他の要素は `shrink-0` で幅を固定する。**M14** はヘッダーの `flex` 子要素すべてが既定の `min-width: auto` を持っていたため、長いフォルダパスが縮まずに右側の操作群を画面外へ押し出す欠陥を踏んだ。伸縮する要素を1つに絞り、他を `shrink-0` にすることで再発を防ぐ。

## 10. 操作言語（キーボード＋マウス）

### 位置づけと原則

- キーボードとマウスは役割の違う両輪。**キーボード＝入力する速さ**（会議のスピードにテキスト入力が追いつく）、**マウス＝構造を操作する自然さ**（動かす、並べ替える、俯瞰する、画面共有で指し示す）。
- **操作は発明しない。デファクトスタンダードに従う。** 独自ジェスチャは学習コストと不具合の温床。参照先はUIの構造で決まる：
  - **キャンバス系** → Miro / Figma 準拠
  - **表系**（遷移表）→ Excel / スプレッドシート準拠
  - **リスト系**（用語集）→ 一般的なリストUI準拠

### キャンバス化の決定

- **ロジックツリーとシーケンスはキャンバス**（ズーム・パンする自由な面）として作る。横に伸びる構造のため、通常スクロールでは破綻する。
- キャンバスの標準操作：Ctrl+ホイール＝カーソル中心ズーム、Space+ドラッグまたは中ボタン＝パン、空白ドラッグ＝矩形選択、Shift+クリック＝追加選択、ドラッグ＝移動、ダブルクリック＝テキスト編集、右クリック＝コンテキストメニュー。
- **各ツールセッションへの申し送り**：ノード配置を「自動レイアウト（データに座標を持たない）」にするか「自由配置（座標がデータに入る）」にするかはツールごとに要決定。自由配置は「図は導出」の思想およびGit diffのノイズに関わるため、安易に選ばないこと。
  - **ロジックツリーは自動レイアウトで確定した**（logic-tree M1 で実装。座標・幅・折りたたみ状態のいずれもデータに持たず、レイアウト関数が毎回導出する）。
  - **判断の一般則：マウスドラッグは座標の編集とは限らない。構造の編集を入力するジェスチャとして使える。** ノードを掴んで別の親の下に落とす操作で書き換わるのは `parentId` と配列インデックスだけであり、離せば自動レイアウトに吸着する（エクスプローラのファイル移動と同じ構造）。したがって**「マウスで動かしたいから自由配置にする」は自由配置を選ぶ理由にならない。** 自由配置が要るのは、位置そのものに人間が意味を込める場合（＝図が導出物でなくなる場合）に限る。
- **ノードの中のテキスト編集は「ダブルクリックで編集モードに入る」形にしなくてよい。** ロジックツリーは入力欄を常に `<textarea>` にし、**フォーカスされている＝編集中**とした（logic-tree M1）。会議のスピードで打つには「選択してから編集に入る」の1手が邪魔であり、IME・ドラフト・Undo 反映を持つ共通部品（`CellInput`）をそのまま載せられる利点もある。**帰結として、キャンバスの標準操作のうち Space（パン）はノードにフォーカスがある間は文字入力に取られる**——これは境界規則（後述）どおりの正しい挙動である。
- 状態遷移の図は従来どおり読み取り専用の導出物（編集面は表）。用語集はリスト。

### キーボード操作：二層構造

共通セットには性質の違う2種のキーがあるため、層を分けて優先規則を明確にする。「全ツールで操作を揃える」の実態は「**同じ構造には同じ操作**」である。

**グローバル層（全ツール厳守。UIの構造に依存しない）**：

- **Undo/Redo**：Ctrl+Z ／ Ctrl+Shift+Z。Windows/LinuxではCtrl+YもRedoに充てる（macOSはCmd+Shift+Zのみ。Cmd+YをRedoとする慣習が無いため）。履歴は開いているファイル単位・メモリ内のみ。それ以前への復帰はGitの担当（5章の二層構造）。
- **Esc**：編集中→編集キャンセル、非編集→選択解除。
- 境界規則・IME対応（後述の実装規約）。

**構造依存層（追加・削除・移動・並び替えの意味をどのキーで提供するかはUI構造に依存。構造ファミリーごとにデファクトが勝つ）**：

- **階層・リスト系の標準**：Enter＝兄弟／直後に追加、Tab＝子追加、空欄でBackspace＝削除、Alt+↑↓＝並び替え、矢印＝ノード間フォーカス移動。ロジックツリー、シーケンス、用語集はこれに従う。
- **表系（遷移表）**：Excel準拠が優先（Enter＝下のセルへ移動、矢印＝セル移動等）。「追加・削除・並び替え」という**意味**は表系の流儀のキーで提供し、具体割当は状態遷移エディタのセッション（handoff-03）で決める。共通セットのキーをExcelのデファクトと衝突する形で持ち込まない。
- 各ツールが提供すべきは**意味の集合**（追加・削除・移動・並び替え）であり、キー割当は属する構造ファミリーの流儀に従う。自ツールに存在しない意味（遷移表の「子追加」等）は提供しない。適用例：用語集はフラットなリストで「子」が存在しないため、Tabはファミリー標準の「子追加」ではなくセル間移動に充てる（glossary/session-notes.md 論点6）。
- **この分岐は共通フックの中に `KeyContext.hierarchical` として持つ（logic-tree M1 で実装確定）。** 「子」という意味を持つ構造（ツリー・アウトライン）では **`Tab`＝子追加、`←`＝親へ移動、`→`＝子へ移動**になり、フラットなリストでは `Tab`＝セル移動・`←→`＝キャレット移動のままになる。**ツール側で分岐させないこと**——分岐を各エディタのハンドラに置いた瞬間、操作言語の一元化（後述の実装規約）が名目だけになる。`←→` は `↑↓` と同じく**キャレットが端にあるときだけ**構造の移動に切り替える（端でないときは文字カーソルの移動が優先）。なお `Shift+Tab` に「親にする」を割り当てていないのは意図的で、意味を与えないことでキャンバスから Tab 順で抜ける経路として残している。
  - **`hierarchical` は「キャンバスかどうか」ではなく「子という意味があるかどうか」である。** シーケンスはキャンバス系だがフラットなステップ列なので `hierarchical: false` で、`Tab` は用語集と同じセル間移動になる（sequence M1 で実装確定）。**キャンバス＝階層と読まないこと。**
  - **構造依存層の写像はコアを触らずツール側で足せる。** ステップ 0 件のときだけ、末尾アクターの `Tab` が「次の欄が無い」で終わらず、最初のステップを生やして from へ移す（sequence M2）。`resolveCommand` は変更していない——シーケンスは全欄で `hierarchical: false` なので `Tab` は既存どおり `focus-next-field` に解決され、「移動先が無ければ生やす」はツール側の `runCommand` が意味を足しただけである。**意味の解決はコアのまま、写像だけツール側**という構造依存層の性質どおりの適用例になっている。同じ検討で、アクター行の割当て（`Enter`=追加・`Tab`=欄移動）自体は**変えなかった**——ヘッダは横並びのリストだが「`Tab`=追加・`Enter`=移動」に替える案はファミリー標準（本章）と衝突するため退けた。
  - **横に並ぶリストは `KeyContext.horizontal` で扱う（sequence M1 で実装確定）。** シーケンスの参加者ヘッダが実例で、**`Alt+←→`＝並び替え、素の `←→`＝キャレット端で隣へ移動、`↑↓` は関与しない**。ファミリー標準（縦のリスト）を90度回しただけであり、下の拡張規則に収まる新キーではない。`hierarchical` と同時に `true` にしない。
  - **`←→` は `arrowsOwnedByField`（欄が矢印を使っているか）を見る**（sequence M1 で解消）。`↑↓` は当初からこの規則だったが `←→` は見ていなかったため、**select 系の欄を持つツールが現れた瞬間に規則が割れる**穴として残っていた。from / to の参照欄（`↑↓` で候補を切り替える）を持つシーケンスが1本目の踏み手になり、`hierarchical` 側の親子移動・`horizontal` 側の隣移動の両方にガードを入れて揃えた。
  - **主修飾キー＋`Enter` は `toggle-item-state`（欄の状態トグル）** に割り当てた（sequence M1）。シーケンスの答えスロットが「考慮不要」に倒すのに使う。意味を持たないツールは無視してよい。**`Shift+Enter` / `Alt+Enter` が「アプリは関与しない」（＝ブラウザ既定のセル内改行が生きる）ことは不変条件として残す**——用語集の定義・備考がそこに乗っているため。
  - **`toggle-item-state` の写像はツールごとに違ってよい（issue-tree-m1 で確定）。** コアが解決するのは「主修飾キー＋`Enter` は `toggle-item-state` である」ところまでで、**それが何を意味するかはツール側の `runCommand` が決める**。シーケンスは答えスロットを「考慮不要」に倒す（sequence M1）が、**課題ツリーは「そのセルの主たる副操作」に写した**——課題セル＝仮説を追加／仮説セル＝判断イベントの種類のドロップダウンを開く／メモセル＝最新イベントの根拠へ移す／由来・イベントの根拠＝何も起きない。`src/core/keyboard/keymap.ts` は変更していない。**上のシーケンスの `Tab`（移動先が無ければ生やす）と同じく「意味の解決はコアのまま、写像だけツール側」の適用例**であり、構造依存層ではこれが正しい層である。**コマンドの語彙をコアに増やす案は退けた**——そのコマンドを持たないツールが増えるだけで、意味の集合を決めるのはツール側という原則に反する。**`Shift+Tab` へ割り当てる案も退けた**（上のとおり、キャンバスから Tab 順で抜ける経路として空けてある）。**代償として、写像がツールごとに違う以上「このキーが何をするか」は画面のヒント（`KeyHints`）でしか分からない**——写像を足すツールはヒントも足すこと。
- **ツール固有キーの適用例（用語集）**：定義・備考は複数行を入力できるため、**Shift+Enter / Alt+Enter をセル内改行に充てる**（Enter は行追加のまま）。ファミリー標準およびグローバル層のキーと衝突しない拡張であり、後述の拡張規則に収まる。Enter が確定・Shift+Enter が改行という関係は Notion・Slack と同じ流儀で、Alt+Enter は Excel のセル内改行の手癖に当たる。**実装としては何も足していない**——`resolveCommand` は修飾キー付きの Enter に `null`（アプリは関与しない）を返すので、入力欄を `<textarea>` にした時点でブラウザ既定の改行が生きる。止める方が余計なコードを書く側である。
- 導出表示（ソート・フィルタ適用中）では、データ順と表示順が食い違うため、**表示順とデータ順の対応が崩れる操作**を無効化する（同 論点4）。並び替え（Alt+↑↓）だけでなく行の追加も含む——挿入した行が絞り込みに掛からず、見えないまま増えるため。
- **キーでしか到達できない「意味」を残さない。** 用語集は長らく行の追加が Enter だけで、「用語を追加」ボタンは0件の空状態にしか出さなかったため、**マウスだけで操作する人には行を増やす手段が無かった**（M8 の実機確認で発覚）。「マウス＝構造を操作する自然さ」は、キーボードで提供した追加・削除・並び替えにマウスの入口も用意することを含む。ボタンは常時出し、押した行は**末尾**に足す（一覧の一番下にボタンがあるので、そこから生える位置が直感に合う）。導出表示中に出さないのは、Enter を止めているのと同じ理由である。

### 実装規約

- **キーボード・マウス処理は共通フック／モジュールに一元化**し、全ツールがそれを使う。ツールごとのハンドラ自前実装を禁止（プロトタイプで発生した挙動差の構造的再発防止。修正も1箇所で済む）。キーボード側は `src/core/keyboard/`、マウス側は M8 の列幅ドラッグ（`src/core/column-resize.ts`）が最初の1本で、**純関数（幅の計算）とフック（ポインタの配線）を分け、ツール側は `getHandleProps(index)` を貼るだけ**にしてある。ドラッグは `pointerdown` で `setPointerCapture` を取る形にし、window にリスナーを張り替えない。**ポインタ操作を作ったらキーボードからも同じ操作を提供する**（列幅は ←→ で16px刻み、Home で既定に戻す）——アクセシビリティのためであると同時に、jsdom はレイアウトも `setPointerCapture` も持たないので、**キーボード経路が「値が反映されること」を検証できる唯一の入口になる。**
  - **例外：キャンバスのズーム・パンは d3-zoom に委ねる**（logic-tree M1 で確定）。d3-zoom はドラッグ中のリスナーを `event.view`（window）へ張り替える実装であり、上の `setPointerCapture` 規約に従わない。それでも自前に置き換えないのは、ホイール・ピンチ・ドラッグの正規化と**倍率を保った座標変換**という、この規約が守ろうとしている範囲の外側の仕事を持っているためである。**この例外はビューポートの `{x, y, k}` に限る**——ノードの移動・列幅のような「値の編集」のドラッグは引き続き `setPointerCapture` を取る。
  - **同じくキャンバスのズーム・パンにはキーボード経路を作っていない**（logic-tree M1 の判断）。代替は**新しいノードへの自動追従**で、キーボードだけで打っている限り視点は必要な位置へ自ら動くため、「キーでしか到達できない意味」も「マウスでしか到達できない意味」も生じない。**ズーム倍率だけはキーボードから変えられない**が、これは値の編集ではなく閲覧の都合であり、データにも操作の意味にも影響しない。会議で拡大縮小が要ると分かった時点で `Ctrl` + `+`/`-`/`0` を足す（そのときは上の規約どおり、同じ関数を呼ぶ2つ目の入口として作る）。
- **キャンバス系ツールの実装構成（全ツール共通。logic-tree M1 で確定）**：**ノードは絶対配置の DOM、エッジは SVG、ビューポートは d3-zoom**。3レイヤ（背景／エッジ／ノード）に同一の `translate(x, y) scale(k)` を当てるので、座標系のズレは原理的に発生しない。**sequence M1 で2本目の実装が同構成で確定した**（背景＝責任境界の破線とライフラインの実線、エッジ＝矢印、ノード＝参加者ヘッダ・ステップの編集セル・ガターのスロット。logic-tree が枠だけ確保していた背景レイヤが初めて使われた）。**M20 でビューポート・エッジのパス生成（`edgePath`）を含む土台が `src/core/canvas/` の共有物になった**（6章）——ノードの DOM（`.tsx`）とエッジの SVG レイヤ（`TreeEdges.tsx` / `SequenceEdges.tsx`）は引き続き各モジュールが描き、コアは純関数とフックだけを提供する（`src/core/` にコンポーネントを置かない規約）。**「3レイヤに同一の transform を当てる」という規約自体は変わらない**——共有元が1つになったことで、むしろズレが構造的に起きなくなった。
  - **キャンバス（描画・操作）ライブラリ（React Flow / tldraw 等）は採用しない。** 第一の理由は、**イベント系を乗っ取るライブラリが操作言語の一元化規約と衝突する**こと——Space がパンに、Backspace が削除に食われ、`nodrag` / `nokey` のようなクラスで個別に殺す運用になる。上のIME対応と境界規則を他人のイベント系の上に再構築することになり、規約が名目化する。第二に、自動レイアウトを採る以上ライブラリの中心価値（座標ドラッグ・ハンドル接続）が不要になる。
  - **レイアウト計算ライブラリ（elkjs / dagre）は別の話で、不採用の理由も別である。** これらはイベントに触らず、自動レイアウトこそが中心価値なので、上の2つの理由は当てはまらない。ロジックツリーで採らなかったのは (1) どちらも**任意の有向グラフ向け**で、単一親の厳密な木にはその強みが要らない、(2) elkjs はバンドル1MB超・Web Worker 前提の**非同期API**であり、会議中に Enter を押すたび非同期レイアウトを待つ構造を避けたい、の2点。**任意グラフを描くツール——とりわけ状態遷移図——では再検討の余地がある。「ロジックツリーが採らなかった」を「facet では使わない」と読まないこと。** 検討の全文は `docs/logic-tree/logic-tree-canvas-tech-notes.md` 論点2。
  - **ノードの中を SVG にしない**（`foreignObject` を使わない）。Windows のブラウザで IME の変換候補ウィンドウの位置ズレ・フォーカス喪失が起きる。下の「日本語入力アプリ最大の地雷」と明記しておきながら、その地雷原の上に実装基盤を置かない。
- **IME対応**：変換中のキーイベントは操作言語の対象外（composition イベントで判定）。変換確定のEnterが「追加のEnter」に誤爆する問題は日本語入力アプリ最大の地雷であり、仕様として明記する。**`isComposing` だけでは足りない（mac の実機で判明）。** WebKit（macOS の WKWebView / Linux の WebKitGTK）は composition 系のイベントを keydown より先に投げるため、変換を確定した Enter は `isComposing: false` で届く（WebKit bug 165004。2016年の報告から2026年に main で直るまで開いていた）。**Windows の WebView2＝Chromium だけが仕様どおりなので、Windows で開発している限り決して踏まない。** 実物の `CellInput` で採った実測（2026-08-15）:

  ```
  50 compositionend                         Δ 409.0
  51 keydown  Enter  keyCode=229  isComposing=false  Δ -12.0  ← 確定。行追加に化けていた
  52 keyup    Enter  keyCode=13   isComposing=false  Δ  72.0
  53 keydown  Enter  keyCode=13   isComposing=false  Δ1561.0  ← 本物。ここは行が増える
  ```

  **主たる判別材料は `keyCode === 229`**（IME が食った打鍵の予約値。実在のキーには割り当てられず、同じ物理キーでも離した keyup は本来の 13 に戻る）。`src/core/keyboard/ime.ts` の `isImeProcessingKey` が持ち、**操作言語の入口 `toKeyEventLike` が `isComposing` へ畳み込む**ので、各ツールのセルも額縁のグローバル層も一度に守られる。補助として `CellInput` が「直前の `compositionend` から前後 100ms」の窓も見る（`isCompositionTail`）——229 を出さない WebKit の版に備えた二段目で、キーを離した時点で記録を捨てることで Chromium 側の誤爆を防ぐ。**この窓は絶対値で見ること**——実測のとおり keydown の時刻は compositionend より*古い*ことがあり、「後に届いたのだから時刻も後」と決めつけた最初の実装はこの尾を取り逃がした。各ツールの keydown ハンドラに同じ判定を撒かないこと（次に増えるツールが落とす）。
- **境界規則（端末ペイン。M11 で追加）**：端末ペイン（Claude Codeの端末）が開いている間、そのペインの中で発生したキー入力は操作言語の管轄外とする。モーダルが開いている間に操作言語を止めるのと同じ扱いで、判定はグローバルの `keydown` ハンドラの先頭でイベントの発生元がペインの中かを見て早期returnする（M11 決定11）。xtermは隠しtextareaで入力を受けるため、これが無いと端末での `Ctrl+Z` がfacetのUndoを横取りし、編集中の図を勝手に巻き戻す。**帰結として、端末ペインの開閉・フォーカス脱出にショートカットは割り当てていない**——xtermが `Tab` を消費するため一度端末をクリックするとキーボードだけでは本体へ戻れないが（[`open-issues.md`](open-issues.md) 参照）、キーの割り当てを増やさない判断を優先した。
- **境界規則（モーダル）**：モーダル（shadcn/Radix。額縁のモーダル・削除の確認ダイアログ等）が開いている間はエディタの操作言語を停止し、キーはモーダル側が取る。Escの取り合いを構造的に排除。**停止の対象はキーだけでなくポインタ操作も含む**——モーダルの裏でキャンバスがズーム・パンすると、閉じたときに視点が変わっている。実装はフックに `enabled` を渡して外から止められる形にする（`useViewport(ref, enabled)`）。**logic-tree M1 時点では `enabled` が止めているのはキー監視（Space）だけで、d3-zoom の `filter` はホイール・ドラッグを止めていなかった（ポインタ側が未達）。sequence M3 で `filter` 側も `enabled` の ref を見るよう logic-tree・sequence 両方の `useViewport.ts` を修正し、キー監視だけでは足りない分を塞いだ（キー監視のみでは、たとえばモーダルにフォーカスが無い経路でズーム・パンが素通りする）。**
- **境界規則の例外（セルのドロップダウン。sequence M3 で確定）**：`StepShapeCell` / `ActorRefCell` が開くドロップダウン（Radix `DropdownMenu`）は、上の「モーダル」には数えない——**額縁由来のキャンバス停止（`useViewport` の `enabled`）を掛けない。** 代わりに、同時に1つのセルしかドロップダウンを開けない構造（`SequenceEditor` の `openCell: string | null` と `menuPropsFor` ヘルパによる制御コンポーネント化）にし、キー入力の遮断は Radix の `FocusScope` 単層に任せる。当初はドロップダウンでもキャンバスのズーム・パンを止めていたが、実機確認（sequence M3 実機確認）を経て「ズームの制御は不要」という人間の判断で外した——実害だったのは「複数開いたまま1つ閉じるとキャンバスが復活する」ことで、対策は複数オープンを構造的に禁止する側で足りた。**モーダルは止める／セルのドロップダウンは止めない（focus trap に任せる）、という線引きになる。** **この例外はキー入力の遮断についても多重防御を持たない。** モーダルは `enabled`／`modalOpen` を経由してアプリ側の `handleKey`/`resolveCommand` 自体がキーを弾く（アプリ側の防御＋ブラウザ標準のフォーカストラップの二重）のに対し、**セルのドロップダウンはアプリ側の防御を持たず、Radix の `FocusScope` 1本のみでキー漏れを防ぐ。** 実ブラウザの通常操作では有効（DOM テストで確認済み）だが、`FocusScope` が唯一の防御線であることは設計上の既知のトレードオフとして記録する。
- **境界規則（テキスト編集中）**：インラインテキスト編集中はキーイベントを編集対象が取り、操作言語は停止する。例外は**編集境界キー**（Enter／Tab／Esc／空欄Backspace）と**Undo/Redo**で、これらは操作言語が解釈する（Enter＝確定して兄弟追加、のように編集の終了と操作が連動するため）。Undo/Redoを編集中もアプリの履歴が取るのは、制御された入力欄ではブラウザ標準のUndoがReactの再レンダリングと食い違うためで、履歴をアプリ側に一本化する。Space・矢印・Alt+↑↓は編集対象のもの（Spaceは文字入力、矢印はカーソル移動）。パン誤爆・ノード移動誤爆を構造的に排除する。
- **拡張規則**：ツール固有キーの追加は可。グローバル層および自ファミリーの標準キーと衝突する再定義は禁止。

## 11. 検証の観点（ドッグフーディング）

- **第一関門：会議のスピードに入力が追いつくか。** 操作言語（10章）とキャンバス操作の使用感を含めて評価する。
- **AI連携の価値検証。** Skill（4章）による下書き生成・ヒアリング型データ作成・レビューが、実際の仕様検討で「ゼロから入力するより速く・漏れが減る」かを確認する。文章校正系（用語チェックのAI層）は費用対効果が高い着手候補。
- **成果物が仕様書として機能するか。** NotePMに貼ったMarkdown/Mermaid出力（8章）が、実際の仕様書として読まれ・使われるかを確認する。出力実装は「使う」と確定したツールから着手する。
- **色・デザインは M7 で確定し、用語集エディタの塗り分けと操作性は M8 で確定し、役割トークンの体系は M21 で作り直した**（9章）。実機確認（`npm run tauri dev` によるライト・ダーク両モードの一巡）を M7 で1周、M8 で2周行った。**テーブルの行の密度（`py-1`・`text-sm` の行間 `1.65`）は M8 の実機確認で「このままでよい」と決着した**ので、検証項目から外す。**P型・D型色覚での識別性は、M21 で OKLab の色差（意味色4つの総当たり × 3色覚）を `DISTINCT_PAIRS` が機械検査するようになった**ので、**数値としては担保済み**である。残る検証は2つ——**実機で黄（欠落）と赤（無効）が本当に分かれて見えるか**（色差 0.10 は「同じ色の濃淡に見え始める」境目であって、読めることの保証ではない。`open-issues.md` の候補6）と、会議で投影したときの読みやすさ。どちらもドッグフーディングを経てから見る。
- **チーム展開はクオリティ確認後。** 展開時には配布方法（7章の但し書き）を再検討する。
