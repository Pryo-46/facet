# 仕様整理ツール詰め合わせ：全体方針ドキュメント（rev3）

作成日: 2026-08-01 ／ handoff-04（用語集セッション）の決定事項を反映した正のドキュメント。以降の個別ツールセッション・Skillセッションはこれに従う。

## 1. 背景と目的

文字だけの仕様書は、多次元の情報（分岐・時系列・状態・用語）を一次元の文章に直列化しているため、読むたびに脳内でグラフ構造を再構築する必要があり、ワーキングメモリを消耗する。これを解決するため、「人間は構造化されたUIで入力し、ツールが網羅性の担保・描画・構造化テキスト出力を担う」という思想の会議用ツール群を作る。

利用者はまず作者本人（ドッグフーディングによる検証）。加えて、**AI（Claude）もツールの利用者**として設計に含める（4章）。将来的には、PdMとエンジニアの融合という組織方針の中で、両者が共に読める「中間言語」としての価値を狙う。会議で実際に使う姿を見せることが最良のデモになる、という普及戦略を取る。

## 2. ツール一覧

初期実装は以下の4ツール。**ツールは今後増える前提**であり、追加を「モジュールの追加」で済ませる規約を6章に定める。

1. ロジックツリーエディタ — 分岐・パターンの網羅
2. シーケンスエディタ — 時系列＋責任境界（失敗ゾーン）
3. 状態遷移エディタ — 状態×イベントの網羅とテスト導出
4. 用語集エディタ — 用語の型定義と表記ゆれ検知（他ツールが参照するマスタデータ。5章。**詳細仕様は glossary-session-notes.md で確定済み**）

既存のプロトタイプ（.jsx 4本）はイメージ確認用であり、データ構造・実装とも実用版には引き継がない（5章・7章）。UI・操作の実装差の観察結果（挙動を揃える必要性）だけを教訓として引き継ぐ。

## 3. 全ツール共通の設計思想（変更する場合は理由を明記すること）

**入力速度最優先。** 会議の議論は秒単位で流れる。入力がもたつくと「後でまとめよう」となりツールは使われなくなる。共通の操作言語（10章）で全ツールの操作を揃える。さらにAI活用（4章）により、AIとの対話でデータを作る＝入力そのものを省略する方向へ拡張する。

**網羅性の担保はツールの仕事。** 未定義・未決定の箇所が物理的に「見える」構造にする（ツリーの葉数バッジ、遷移表の赤セル、用語チェックの赤ハイライト）。「決めていないこと」を消せなくするのが本質的価値。機械的チェックの上に、AIによる意味的チェック（どの未定義が実務上危ないか）を重ねる（4章）。

**「未定義」と「決めた上で無効」を型で区別する。** 文章仕様書ではどちらも「書いてない」に潰れる。遷移表の「─ 何も起きない」が代表例。デザイン上もこの区別を色の意味論（warning / ok）として維持する（9章）。

**正となるデータは一つ。図は導出。** 状態遷移エディタが典型で、編集できるのは表のみ、図は自動生成の読み取り専用。表と図の乖離を構造的に防ぐ。この思想はDB不採用の判断（5章）やキャンバスの配置方式の判断基準（10章）にも適用する。

**構文は人に覚えさせない。構文は交換形式である。** Mermaid等の構文を人に覚えさせず、人間は直感的UIで入力し、ツールがMarkdown/Mermaidを吐く（旧「構文は出力形式に降格」）。AI活用により、スキーマ定義されたJSONは出力にとどまらず**AIとの双方向の交換形式**となった。人間には見せない・機械同士は構造化データで話す、という役割分担。

## 4. AI活用方針

### 基本構造：AIはアプリの外で動き、接点はファイルのみ

- AI（Claude）はアプリに組み込まない。**APIの呼び出し・アプリ内AI機能は作らない。**
- AIはClaude Code / Claude Desktop上で動き、プロジェクトフォルダ内のJSONファイルを直接読み書きする。アプリとの接点はファイルだけ。
- 責務分離：**アプリ＝人間用の高速エディタ＋検証器＋描画器。AI連携＝Skill群という別の成果物。** アプリはAIの存在を知らなくてよい。
- **MCP的な書き込みツール（用語登録APIの提供等）は作らない**（handoff-04で決定）。ファイル直書き経路は塞げないため二段検証は結局必要になり、MCPは「検証を通る経路の多重化」と「第三の成果物（スキーマ追従が必要なコードベース）の追加」にしかならない。予防的な品質向上は下記の同梱スクリプトで回収する。

### Skill群：AIを対話的な共同作成者にする

単発の「校正依頼」にとどまらず、ユースケースごとのSkillを整備する。想定：

- **対話的データ作成**：例：用語登録Skill。ユーザーにヒアリングしながら用語集ファイルを組み立てる。ゼロから入力する代わりにAIとの対話でデータができる——「入力速度最優先」を入力自体の省略で実現する方向。
- **下書き生成**：会議メモや既存の文章仕様書からロジックツリー/遷移表/シーケンスの初期データを生成。人間は会議でAIの下書きを修正・確定する。
- **レビュー**：完成データの網羅漏れの意味的指摘（「辞退後の差し戻しが未定義。実務ではあり得ないか？」）、到達不能状態・デッドエンド検出、未定義箇所の実務的な優先度付け。ツールの機械的チェック（赤セル）が「未定義の存在」を示すのに対し、AIは「どの未定義が危ないか」を担う。
- **用語チェックの二層化**：ルールベース層（アプリ内：決定的・高速。aliases 照合）の上に、AI層（未登録の揺れの発見、定義と使われ方の矛盾検出）を重ねる。

**Skillへの同梱スクリプト（handoff-04で追加）**：ID捏造・不正データの予防策として、各Skillに以下を同梱する。

- **ID採番スクリプト**：英数字62文字カスタムアルファベット・10文字の nanoid を出力（5章のID規約準拠）。Skillの手順書に「IDは必ずこれで採番せよ」と明記する。
- **書き込み前検証スクリプト**：アプリと同一の JSON Schema ファイルを参照してバリデーションする（スキーマの正は一つ。コピーを同梱しない）。

Skill群はアプリ本体と並ぶ正式な成果物としてバージョン管理する。Skillはスキーマを参照するため、**スキーマ変更時はSkillも追従させる**（依存関係として管理）。

### 既存決定との接続（この構造が成立する根拠）

- スキーマの自己記述性（5章）：AIがJSON Schemaを読んで生成・検証できる。
- 二段検証（5章・8章）：AI生成物も自動保存と同じ検証を通る。AIは存在しないIDを捏造しがちなので整合性検証が防波堤になる。
- プロジェクト＝フォルダ（5章）：AIに渡すコンテキストが「フォルダごと」で完結する。

### アプリ側への要件：外部変更への対応

- アプリの開いているファイルを外部の書き手（Claude Code / Desktop、テキストエディタ等）が書き換えることを前提とする。これは**外部エディタ一般への対応**であり、AI固有の結合ではない（責務分離は維持される）。
- **ファイルの外部変更検知を初期実装に含める**。監視は**ファイル単位ではなくフォルダ単位**とする（外部でのリネームも検知するため。ファイル名非依存の原則とパス監視の間の穴を塞ぐ）。挙動：
  - **自己書き込みの除外**：アプリ自身の書き込み（自動保存・正規化・新規作成・削除）は外部変更として扱わない。検知ループの構造的排除。**具体的な機構は「台帳との内容比較」**（M5 で確定）：アプリが最後に読み書きしたディスクの内容をパスごとに保持し、再走査で読んだ生バイトと1バイトも違わなければ自分の書き込みと判定する。**時間窓（「書いてから N ms は無視」）やフラグは使わない**——遅れて届くイベントで誤検知し、速く届くイベントを取りこぼすため。この方式なので、監視イベントの**種類やパスは一切見ない**（notify のイベント表現は OS ごとに違い、リネームは2イベントに割れる）。「何か起きた」だけを契機にフォルダを再走査する。
  - アプリ側に未保存編集がない → 再読み込みし、非モーダル通知（トースト）で「外部変更を読み込んだ」ことを知らせる。**このときUndo履歴は破棄する**——履歴を残すと、Ctrl+Zが外部（AI）の変更を黙って巻き戻す意図しない破壊操作になるため。
  - **取り込み前の内容は一時退避し、トーストに「取り込み前に戻す」アクションを付ける**（初期実装要件）。Undo履歴破棄後もアプリ内で復元手段が残る。「問題は消せなくして見せる」思想を、消えた編集にも適用する受け皿。
  - アプリ側に未保存編集がある（デバウンス中に外部変更が来た）→ 二択ダイアログ「自分の編集で上書き」／「外部変更を取り込む（自分の編集は破棄）」。VSCode級のマージUIは作らない——データが会議単位の小さなJSONであり、退避とGitという復元手段があるため、実装コストに見合わない。
- **保護範囲の明示**：自動保存下では「未保存編集がない」がほぼ常態のため、二択ダイアログが守るのはデバウンス窓の数秒間だけである。この仕様の衝突定義は「タイムスタンプの前後」ではなく「デバウンス窓の重なり」であり、外部の書き手が古い内容を基に書き戻せば直前の自動保存分は上書きされる（退避からの復元は可能）。だからこそ次の運用推奨が実質的な防御線になる。
- **運用推奨**：AIに作業させる間は対象ファイルをアプリで閉じる（衝突の発生自体を避ける）。
- **将来の発展先**：IDがランダムで衝突しない（5章）ため、「双方の追加分を合併する」スマートマージは構造的に成立可能。ドッグフーディングで二択ダイアログが苦痛と判明した場合の選択肢として残す。

## 5. データモデルと永続化

### ファイル構成：プロジェクト＝フォルダ

- 1つの仕様書プロジェクト＝1フォルダ。その中にツールごとのJSONファイルを置く。
- 「同じフォルダにある＝同じプロジェクト」という物理配置で紐付けを表現し、設定ファイルによるパス管理を持たない。用語集参照は「同一フォルダ内の `type: glossary` のファイルを見る」という規約で閉じる（ファイル名には依存しない）。
- 同種ツールの複数ファイルを許す（例：機能ごとにシーケンスを分ける）。ただし**用語集はプロジェクトにつき1つ**（ハブなので単一）。単一性は整合性検証で担保する（後述）。
- ファイル名は識別子にしない（用語集含め例外なし）。アプリはフォルダ内JSONを走査し、中身の `type` で種別を判別する。人間やツールが自由にリネームしても壊れない。

### スキーマ：JSON Schema を正とする

- 各ツールのデータ形式は JSON Schema で定義し、TypeScript 型はそこから自動生成する（json-schema-to-typescript 等）。手書きの二重管理はしない。
- JSON Schema はAIへの生成指示（「このスキーマに従って生成せよ」）と読み込み時の機械検証に直接使う。
- スキーマは自己記述性を持たせる：キー名は省略しない、種別は enum で明示（handoff-05 のAI活用要求を継承）。
- 個別ツールのスキーマ設計は各ツールセッションで行う。プロトタイプの state 構造は叩き台にせずゼロから設計する（プロトタイプはイメージ確認用であり構造は信用しない）。用語集は確定済み（glossary.schema.json）。
- 全ファイル共通のエンベロープ（必須フィールド）：
  - `schemaVersion`: スキーマの版。**版は type ごとに独立して進められ、移行判定・Skillの追従管理（4章）は `type` × `schemaVersion` の組で行う**（ツールは増える前提のため、あるツールのスキーマだけ改訂される事態は通常運転）。共通エンベロープは各ツールスキーマが参照する共有定義であり、エンベロープの改訂は全ツールスキーマの改訂を**含意**する（このとき全 type の版が上がるのは独立性の否定ではなく包含関係の帰結）。
  - `type`: ツール種別の enum（初期値：logicTree / sequence / stateMachine / glossary。ツール追加で増える）。旧バージョンのアプリにとって未知の値になり得るが、その受け皿は前方互換の規定（6章：未知typeは編集不可として一覧表示のみ）。
  - `title`: 表示名。プロジェクトを開いたときの一覧表示に使う。

### バージョン互換とマイグレーション

- **新しすぎるファイル**（既知 type だが自分の知らない新しい schemaVersion）：**未知 type と同じ扱い**（一覧表示のみ・編集不可）。レベル1拒否にはしない——「まったく知らないツールのファイルは一覧に出るのに、知っているツールの少し新しいファイルは開けない」という逆転を避け、旧アプリ×新プロジェクトの事故への備え（6章の前方互換）に一貫させる。
- **古いファイル**（既知 type × 旧 schemaVersion）：読み込み時に**メモリ上で**自動移行して開く。ファイルへの反映は最初の編集保存時（「読み込み・閲覧では書き戻さない」原則の適用。正規化と同じタイミング規則）。閲覧しただけでは旧版のまま残る。
- マイグレータ（旧版→新版の変換）は各ツールモジュールの提供物とする（6章のモジュール規約参照）。
- Skillとの関係：古いSkillが旧版スキーマで書いたファイルも、アプリがマイグレータで移行して開ける。Skill追従（4章）の失敗は「開けない事故」ではなく「移行で吸収される遅れ」に格下げされる。

### ID規約（全エンティティ共通）と用語参照

**ID規約はツール横断のメタ規約とする**（handoff-04で一般化。旧「用語参照：ID参照（nanoid）」の改訂）：

- **形式**：`<entityPrefix>_<id>`。`entityPrefix` は小文字英字のみで、エンティティ種別（用語・ノード・状態…テーブル名に相当）を表す。各ツール内の分類enum（カラム値に相当）とは別レイヤー。
- **ID本体**：nanoid の `customAlphabet` で**英数字62文字（A-Za-z0-9）・10文字固定**。
  - **改訂理由**：nanoid の標準アルファベットは `_` `-` を含み、区切り文字と衝突して自己記述性（目視・AI読解で「これは何の参照か」分かる）とスキーマ検証の正規表現（`^term_[A-Za-z0-9]{10}$` の型で一行検証できる）を汚すため。62¹⁰ ≒ 8.4×10¹⁷ 通りあり数百レコード規模で衝突の余地はない。
- **プレフィクスの粒度はエンティティ単位**（ツール単位で `node_` に統一しない。状態遷移なら `state_` / `event_` 等）。具体命名は各ツールセッションの管轄。
- **宣言と衝突防止**：各ツールの JSON Schema がプレフィクスを正規表現パターンとして宣言し、コアのモジュールレジストリが**登録時にプレフィクス重複を検査**する。スキーマに書かれていればAIもそれを読んで正しいIDを生成できるため、Skill側への伝達も自動的に済む。
- **連番IDは禁止。** アプリとAIが並行して要素を追加する設計（4章）では、連番だと双方が「次の番号」として同じIDを振る衝突が必発する。ランダムIDなら並行する書き手同士がIDで衝突することは構造的にない。

**用語参照**：用語集の各用語に不変ID（`term_` プレフィクス）を振り、他ツールはIDで参照する。表示時に用語集ファイルから名前を解決する。マジックストリング禁止・定数参照のみ、の思想をデータに適用したもの。

- 検証は二段構えで、結果は**2レベル**に分かれる。原則は「人間が直せる状態で見せる」——拒否すると修正に外部エディタが要るため、拒否は解釈不能な場合に限る：
  1. **スキーマ検証**（JSON Schema）：構造の正しさ。不合格は**レベル1（拒否）**＝開けない。構造が解釈できないデータはエディタに載せようがない。
  2. **整合性検証**（アプリ実装）：スキーマで表せない検証。外部キー検証に相当。不合格は**レベル2（受け入れて赤表示）**＝可視のエラーとして表示し、必要な機能のみ縮退する。編集は可能なので人間がアプリ内で直せる。項目：
     - **参照切れ**（参照IDが用語集に実在しない）：発生原因を問わず同一扱い（用語の削除起因でも、AIによるID捏造起因でも）。参照箇所を赤表示する。
     - **ID重複**：赤表示。
     - **name** の重複：赤表示。用語集は「この語を正式名として扱う」という宣言であり、同名2件は宣言としての矛盾。IDが異なるためスキーマの uniqueItems では防げず、追記が繰り返されるほど発生確率が上がるため、整合性検証で受け止める。（判定は NFKC 正規化＋英字大文字小文字同一視で行い、alias 照合と規則を揃える）
     - **用語集の単一性違反**：`type: glossary` のファイルがフォルダ内に2つ以上ある場合はエラー提示し、用語解決を伴う操作を停止する（解消するまで）。どちらを正とするかは人間にしか判断できないため、アプリが勝手に選ばない。
     - **用語集が0個**の状態は正常（新規プロジェクト）。初めて用語登録が発生した時点でアプリが用語集ファイルを自動生成する。用語集不在のまま参照だけ存在する場合（AI生成物の取り込み等）は参照切れとして赤表示。
- 検証は**全経路共通**（自動保存も外部由来ファイルも同じ検証を通る。8章）。AI起因で起きやすい問題（存在しないIDの捏造等）だからこそ検証の価値が高いが、経路によって検証や信頼度を変えることはしない。
- **検証スコープはプロジェクト全体**：プロジェクトを開いた時点でフォルダ内全ファイルを走査・検証し、エラーはファイル一覧に赤バッジで表示する。以後はファイル変更（自己編集・外部変更とも）を契機に再検証する。「フォルダに置かれただけで開かれていない壊れたファイル」も開かずに見える。規模（数百レコード）なら全走査は一瞬。
- **用語削除時の挙動**：**即時削除**し、トーストで参照切れ数を通知する（Undoで復元可）。確認ダイアログは挟まない——会議中の入力速度を削ぐため。削除ブロック（DBのRESTRICT相当）も採らない。参照側はレベル2の参照切れとして赤表示され、「問題は消せなくして見せる」というこのツールの思想に照らせば、参照切れは防ぐものではなく赤く見せるもの。

### 保存：自動保存＋Git

- 編集はデバウンス付き自動保存でファイルへ書き込む。会議中の保存忘れをゼロにする。
- 「試しにいじって捨てる」の受け皿はGit（プロジェクトフォルダをリポジトリ管理し、コミット＝チェックポイント）。アプリ内Undoは会議中の直近操作の取り消しに専念する二層構造。
  - **申し送り（実装時に検討）**：会議中に手でコミットするのは摩擦になる。会議・編集開始時の自動チェックポイント等、コミット操作を意識させない仕組みを検討する。
- Git前提のためシリアライズは決定的にする。diffのノイズを排除し、変更履歴を仕様の変更履歴として読めるようにする。具体値は以下で確定（用語登録Skillセッションにて決定。Skill側 glossary-write.mjs の実装と完全一致させること）：
  - キー順：JSON Schema の properties 記載順から実行時に導出する（アプリ側にハードコードしない。「スキーマが正」を正規化にも貫き、フィールド追加時に正規化ロジックの修正を不要にするため。$ref の解決を含む導出が必要）
  - インデント：スペース2 ／ 改行コード：LF ／ 末尾改行：あり ／ BOM：なし（読み込み時は除去する） ／ 非ASCII：エスケープしない
  - 配列順：UIの並び順を正とする
  - この一致は回帰テストで担保する（Skillが書いたファイルをアプリが読み→保存してバイト単位で不変であること）。プロジェクト最大のリスク箇所。

#### 正規形の定義（全ツール共通・2026-08-01 確定）

| 項目             | 値                                                                                                                                                             |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| キー順           | **各スキーマの `properties` 記載順**。ハードコードせず、正規化処理が実行時に `Object.keys(schema.properties)` を読んで並べ替える（`$defs` 配下の入れ子も同様） |
| インデント       | 半角スペース2                                                                                                                                                  |
| 区切り           | キーと値は `": "`、要素間は `",\n"`（`JSON.stringify(v, null, 2)` 準拠）。空配列は `[]`、空オブジェクトは `{}` を1行で                                         |
| 非ASCII          | エスケープしない（日本語をそのまま出力。`\uXXXX` にしない）                                                                                                    |
| 改行コード       | LF                                                                                                                                                             |
| 末尾改行         | あり（1つ）                                                                                                                                                    |
| エンコーディング | UTF-8（BOMなし）                                                                                                                                               |
| 配列順           | 書き換えない（UIの並び順が正）                                                                                                                                 |

- キー順の「正」はスキーマファイル一つに置く。スキーマの properties を並べ替えれば正規形も自動追従し、二重管理が発生しない（スキーマ実体をアプリとSkillで共有する方針と一貫させる）。
- 改行コードは**プロジェクトフォルダ雛形に `.gitattributes`（`*.json text eol=lf`）を同梱して担保する**。これがないと `core.autocrlf=true` の環境でチェックアウト時にCRLF化し、アプリがLFで書き戻すたび全行diffになり、決定的シリアライズの目的が無効化されるため。雛形生成はプロジェクト作成機能の責務に含める。
- 参照実装は `JSON.stringify(reorder(value, schema), null, 2) + "\n"` を UTF-8 で書き出したバイト列。他言語で書く場合もこのバイト列に一致させる（Python なら `json.dumps(v, ensure_ascii=False, indent=2)` 相当）。
- **正規化の責務はアプリが持ち、タイミングは「書き込み時」とする。** アプリは自分が書くとき必ず正規形で書く。**読み込み・閲覧では書き戻さない**（開いただけでファイルが変わると、閲覧だけでGit diffが発生し「変更履歴を仕様の変更履歴として読める」という目的自体を毀損するため）。
  - 帰結：外部の書き手（Claude Code等）の生ファイルは、次にアプリで編集・保存されるまで非正規のまま残り、最初の意味的編集のdiffに正規化差分が混ざる。これは許容する。
  - Skill側の出力仕様にも正規形を含めるが、これは非正規ファイルがGit履歴に入る瞬間を減らす緩和策であり、保証はアプリ側（「書き手を信用せず受け口で保証する」原則。JSON Schemaはキー順を規定できないため、スキーマ検証では担保されない）。
  - **申し送り（実装時に検討）**：diffを綺麗に保ちたい場合向けに、明示操作としての「プロジェクト一括正規化」コマンドを検討する。

### DBを採用しない理由（再検討時のために残す）

- AIとのラウンドトリップが前提である限り交換形式としてのJSONとそのスキーマ定義は消えず、DB採用は「DB⇄JSON変換層」を追加するだけになる。
- DBの外部キー制約が守るのはDB内部のデータであり、AI生成物の読み込み時検証は結局アプリ側で書く。
- このツールのデータは「アプリの状態」ではなく「文書」。フォルダコピーで持ち運べる・Gitで差分が見える可搬性を優先する。規模（1プロジェクト数百レコード程度）にもDBの必然性がない。
- 将来、全プロジェクト横断検索等の要求が出たら、正はJSONのままSQLiteを検索用インデックス（導出データ）として足す。「正となるデータは一つ、図は導出」の応用。

## 6. アーキテクチャ：統合形態

### 決定：単一アプリ（ファイルベース統合）

- 1つのTauriアプリがプロジェクトフォルダを開き、中のJSON一覧から任意のファイルを開いて編集する。エディタ部分はファイルの `type` に応じて切り替わる（VSCodeがファイル種別でエディタを変えるのと同じ構造）。
- **ファイル一覧の額縁機能**：
  - **新規作成**（type を選んで作成）。**衝突しないファイル名の判定はディスクに問い合わせる**（M5 で確定）——走査時のメモリ上スナップショットだけで決めると、走査後に外部で増えたファイル（Skill が書いた用語集など）を確認もエラーも出さずに切り詰めて上書きする。外部変更検知が入っても監視は取りこぼしうるため、この確認は監視とは別に要る。
  - **削除**（OSのゴミ箱へ移動。完全削除はしない）。用語集の単一性違反（5章）等の解消をアプリ内で完結させるため——「拒否は修正に外部エディタを強いるので最小限に」の原則を、ファイル操作にも適用する。
  - 検証エラーの赤バッジ表示（5章の検証スコープ参照）。
- **用語のインライン登録**を共通コンポーネント要件とする：他ツールのエディタで用語参照を入力する場面から、その場で新規用語を登録できる（用語集エディタへの往復を不要にする）。会議中に用語を増やしながら進める使い方の核であり、入力速度最優先の適用。用語集ファイルの自動生成（5章）はこの動線が発火点となる。詳細仕様（新規登録／既存用語の別名として登録の2アクション）は glossary-session-notes.md 論点6で確定。
- handoff-05の選択肢では「(b) 独立ツール＋共通データ形式」をデータ層で採り、アプリの皮だけ統合した形。懸念だった「会議で1ツールだけサッと開ける手軽さ」は、実体が「フォルダを開いてファイルを選ぶ」操作なので損なわれない。
- 用語集のID解決・整合性検証・共通コンポーネントは全ツール共有のロジックであり、単一アプリならコードを1箇所に置ける。別アプリ4本方式は同じコードを4回配布・更新する保守不利のみが残るため不採用。

### 拡張要件：ツールは増える前提で作る

- 新ツールの追加を「コアの改修」ではなく「モジュールの追加」にする。各ツールは以下を1セット提供するモジュールとして実装する（ツールモジュール規約）：
  1. `type` 識別子（enumへの追加）
  2. JSON Schema（データ形式の定義。ID規約のプレフィクス宣言を含む。5章）
  3. エディタコンポーネント（Reactコンポーネント）
  4. 整合性検証ルール（用語参照チェック等、スキーマで表せない検証）
  5. 出力ロジック（Markdown/Mermaid等への変換）
  6. マイグレータ（旧schemaVersion→新版への変換。5章のバージョン互換参照）
- 規約6点に加えて、**空文書の雛形**（`createEmpty(title)`）をモジュールが提供する。額縁の新規作成は `type` からモジュールを引いてファイルを作るため、雛形を置ける場所はモジュール側しかない。
- **整合性検証の責務内訳（handoff-04で明確化。規約の変更ではなく解像度の向上）**：
  - **モジュール内検証**：自ファイル内で完結する検証（例：用語集の alias 重複）→ 各モジュールの提供物（上記4）。
  - **コア横断検証**：単一ファイルでは判定できない検証（例：用語集の単一性違反）→ コアの仕事。
  - **参照切れ検証**：「参照する側」の各ツールモジュールの提供物。参照される側（用語集）はこの検証を持たない。
- コア側はモジュールのレジストリを持ち、`type` からモジュールを引いてエディタ・検証・出力を呼び出すだけにする。レジストリはモジュール登録時にIDプレフィクスの重複を検査する（5章）。
- **前方互換**：未知の `type` のJSONに遭遇してもクラッシュせず、「このバージョンでは編集できないファイル」として一覧に表示だけする。古いアプリで新しいプロジェクトを開く事故に備える。

## 7. 技術スタック

### 決定：Tauri＋TypeScript＋Tailwind/shadcn

- **配布形態はTauriデスクトップアプリ（Windows想定）**。社内でのWeb公開はホスティングの手間が大きいため採らない。インストールの一手間は当面利用者が作者のみなので許容し、チーム展開時に配布方法（社内配布手段、SmartScreen警告への対処）を再検討する。
- **Rustは原則書かない**。ロジックはすべてフロントのTypeScriptに置き、TauriはネイティブAPI（fs, dialog等の標準プラグイン）の提供層としてのみ使う。根拠：
  1. このアプリにRustを要する仕事（重い計算、バイナリ処理等）が存在しない。実体は「JSON読み書き＋UI＋検証」で規模は数百レコード、ファイルアクセスは標準プラグインが提供済み。書いても得るものがない。
  2. 実装をAIに委譲しても、レビューとデバッグの責任は人間に残る。読めない言語の層は監査不能なブラックボックスになる。AI委譲開発では人間の役割が「書く」から「検証する」に移るため、検証可能な言語に寄せる。
  3. ロジックがTS/Rustに分かれるとIPC境界が生まれ、境界をまたぐバグ（シリアライズの型ズレ、非同期タイミング）は単一言語内のバグより診断が難しい。バグの温床を構造的に増やさない。
  - 「原則」は禁止ではなくデフォルト。実証された必要（例：数千ノードのレイアウト計算がUIをブロックする）が出た場合は例外を認める。
  - 実際に認めた例外は1件のみ：**OSのゴミ箱への移動**。fsプラグインは完全削除（`remove`）しか持たず、6章の「削除はOSのゴミ箱へ移動。完全削除はしない」をプラグインだけでは満たせないため、自前のTauriコマンド `move_to_trash` を1本だけ持つ。判断は一切置かず `trash` クレートを呼ぶだけにし、ロジックはTS側に残す。
- **TypeScript化**。型はJSON Schemaから自動生成する（5章参照）。
- **スタイリングはTailwind CSS＋shadcn/ui**。デザイントークン（9章）はTailwindの設定ファイルに定義し、デザインシステムと1対1対応させる。
- **shadcnの適用範囲は「額縁」に限定**：モーダル、ドロップダウン、ファイル一覧、トースト等の汎用UI。土台のRadixがフォーカストラップ・キーボード制御の実戦済み実装を持ち、自作アプリで苦戦しがちな「モーダル周りのバグっぽい挙動」をこの層ごと吸収する。コンポーネントはソースコピー方式なので朱／インクのデザインへの改造も自由。
- **各ツールのエディタ本体は完全自作**。Enter/Tab/Backspaceの操作言語に合う既製品は存在しない。この領域の入力体験リスクはライブラリでは消えないため、設計で抑える（キーボード処理の一元化とIME対応。10章参照）。
- 実装はAIに任せる前提。Tailwind＋shadcnはAIのコード生成が最も流暢な組み合わせであり、この前提とも整合する。
- プロジェクト雛形の必須要素：リポジトリに .gitattributes を置き、*.json text eol=lf を指定する。Windows の autocrlf 環境では、これが無いと commit 時に JSON が CRLF へ変換され、決定的シリアライズの LF 指定（5章）が Git 上で無意味になり毎回全行 diff が出る。正規化の努力を成立させる前提条件。

## 8. 出力・入力戦略

### 入力（インポート）は独立機能として消滅した

- 5章の決定により保存形式＝スキーマ定義されたJSONファイルとなったため、「AIの生成物を取り込む」＝「JSONファイルをプロジェクトフォルダに置いて開く」で完結する。専用のインポート機能は作らない。
- ただし読み込み経路には必ず二段検証（スキーマ検証＋整合性検証。5章参照）を通す。自動保存したファイルも外から来たファイルも同じ検証を通る構造にし、経路による信頼度の差を作らない。

### 出力はNotePM向けMarkdown（Mermaid込み）

- 第一の出力先はNotePM。出力形態は**クリップボードコピーとファイル書き出し（.md）の両方**を用意する。コピーは「会議直後に議事録へ貼る」最短動線、ファイルはGitに成果物を残す用途。
- どういうMarkdownを出すかは各ツールセッションで個別に詰める。本章では枠のみ定める。用語集は確定済み（種別グルーピングの表形式、h2/h3の見出し階層。glossary-session-notes.md 論点7）。
- 出力ロジックはツールモジュールの提供物（6章のモジュール規約の一つ）。
- 状態遷移のJSONは保存形式そのものがC#パラメタライズドテストのデータソースになり得る（「表＝実行可能な仕様」）。専用のテスト用出力を作るかは状態遷移エディタのセッションで判断する。
- 出力実装の着手順は、ドッグフーディングで「使う」と確定したツールから（handoff-00の方針を継承）。

## 9. デザインシステム

### 決定：役割トークンとパレットの分離。色値は仮置き

- 現行デザインは正式採用**しない**。色は未確定であり、ドッグフーディング後に決める。ただし構造だけ先に確定させ、色の差し替えをパレット定義1ファイルの書き換えで済むようにする。
- **二層構造**：コード・AI・以降のセッションが参照するのは役割トークン（意味の名前）のみ。色値（パレット）は差し替え可能な下敷き。色値の直書きは禁止（プロトタイプ4本で実装差が出た原因の再発防止）。
- **役割トークンは3系統のアクセント＋無彩色系で10個前後**：
  - アクセント3系統：`ink`（文字・線・ヘッダ）、`warning`（警告・削除・未定義）、`ok`（応答・結果・確定）。この3つが設計思想「未定義と無効の型区別」の視覚表現を運ぶため、色値が変わってもこの意味論の構造は維持する。
  - 無彩色系：背景、面（カード・モーダル）、罫線、抑えた文字など。ライト／ダークで最も差が出る部分。
  - 注記：表記ゆれの「指摘（suggestion）」区分は warning 系統の弱い表現（波線下線等）で表し、レベル2の赤表示と強度で区別する（glossary-session-notes.md 論点5）。具体はトークン確定時に詰める。
- **ライト／ダークモード対応**。同じ役割トークンにモードごとのパレットを割り当てる方式。反転による自動生成はしない（警告色が背景に沈む等の破綻を招く）。
- 実装はshadcnの標準規約（CSS変数による役割名定義＋モード切替）にそのまま乗る。7章の決定の帰結として土台が手に入る。
- 初期値として現行3色（#22303C / #C73E3A / #2C7A6E）をライトモード側パレットに流用してよいが、あくまで仮置きであることをコード上も明示する。

### 確定要素

- **方眼紙背景は採用**。グリッド線の色・濃度はトークン化し、モード別に持つ。
- **フォントはツール内で統一**。具体のフォント指定は仮置き（現行のシステムフォント系）とし、トークン（font-family変数）経由で参照する。
- 共通コンポーネント（ツールバー、バッジ、モーダル、チップ）の仕様化は、色確定後ではなくトークン確定後に着手できる（役割名で実装できるため）。個別の仕様は各ツールセッションまたは実装時に詰める。

## 10. 操作言語（キーボード＋マウス）

### 位置づけと原則

- キーボードとマウスは役割の違う両輪。**キーボード＝入力する速さ**（会議のスピードにテキスト入力が追いつく）、**マウス＝構造を操作する自然さ**（動かす、並べ替える、俯瞰する、画面共有で指し示す）。
- **操作は発明しない。デファクトスタンダードに従う。** 独自ジェスチャは学習コストと不具合の温床。参照先はUIの構造で決まる：
  - **キャンバス系** → Miro / Figma 準拠
  - **表系**（遷移表）→ Excel / スプレッドシート準拠
  - **リスト系**（用語集）→ 一般的なリストUI準拠

### キャンバス化の決定

- **ロジックツリーとシーケンスはキャンバス**（ズーム・パンする自由な面）として作る。横に伸びる構造のため、通常スクロールでは破綻する。
- キャンバスの標準操作：Ctrl+ホイール＝カーソル中心ズーム、Space+ドラッグまたは中ボタン＝パン、空白ドラッグ＝矩形選択、Shift+クリック＝追加選択、ドラッグ＝移動、ダブルクリック＝テキスト編集、右クリック＝コンテキストメニュー。
- **各ツールセッションへの申し送り**：ノード配置を「自動レイアウト（データに座標を持たない）」にするか「自由配置（座標がデータに入る）」にするかはツールごとに要決定。自由配置は「図は導出」の思想およびGit diffのノイズに関わるため、安易に選ばないこと。
- 状態遷移の図は従来どおり読み取り専用の導出物（編集面は表）。用語集はリスト。

### キーボード操作：二層構造

共通セットには性質の違う2種のキーがあるため、層を分けて優先規則を明確にする。「全ツールで操作を揃える」の実態は「**同じ構造には同じ操作**」である。

**グローバル層（全ツール厳守。UIの構造に依存しない）**：

- **Undo/Redo**：Ctrl+Z ／ Ctrl+Shift+Z。Windows/LinuxではCtrl+YもRedoに充てる（macOSはCmd+Shift+Zのみ。Cmd+YをRedoとする慣習が無いため）。履歴は開いているファイル単位・メモリ内のみ。それ以前への復帰はGitの担当（5章の二層構造）。
- **Esc**：編集中→編集キャンセル、非編集→選択解除。
- 境界規則・IME対応（後述の実装規約）。

**構造依存層（追加・削除・移動・並び替えの意味をどのキーで提供するかはUI構造に依存。構造ファミリーごとにデファクトが勝つ）**：

- **階層・リスト系の標準**：Enter＝兄弟／直後に追加、Tab＝子追加、空欄でBackspace＝削除、Alt+↑↓＝並び替え、矢印＝ノード間フォーカス移動。ロジックツリー、シーケンス、用語集はこれに従う。
- **表系（遷移表）**：Excel準拠が優先（Enter＝下のセルへ移動、矢印＝セル移動等）。「追加・削除・並び替え」という**意味**は表系の流儀のキーで提供し、具体割当は状態遷移エディタのセッション（handoff-03）で決める。共通セットのキーをExcelのデファクトと衝突する形で持ち込まない。
- 各ツールが提供すべきは**意味の集合**（追加・削除・移動・並び替え）であり、キー割当は属する構造ファミリーの流儀に従う。自ツールに存在しない意味（遷移表の「子追加」等）は提供しない。適用例：用語集はフラットなリストで「子」が存在しないため、Tabはファミリー標準の「子追加」ではなくセル間移動に充てる（glossary-session-notes.md 論点6）。
- 導出表示（ソート・フィルタ適用中）では、データ順と表示順が食い違うため、**表示順とデータ順の対応が崩れる操作**を無効化する（同 論点4）。並び替え（Alt+↑↓）だけでなく行の追加も含む——挿入した行が絞り込みに掛からず、見えないまま増えるため。

### 実装規約

- **キーボード・マウス処理は共通フック／モジュールに一元化**し、全ツールがそれを使う。ツールごとのハンドラ自前実装を禁止（プロトタイプで発生した挙動差の構造的再発防止。修正も1箇所で済む）。
- **IME対応**：変換中のキーイベントは操作言語の対象外（composition イベントで判定）。変換確定のEnterが「追加のEnter」に誤爆する問題は日本語入力アプリ最大の地雷であり、仕様として明記する。
- **境界規則（モーダル）**：モーダル（shadcn/Radix）が開いている間はエディタの操作言語を停止し、キーはモーダル側が取る。Escの取り合いを構造的に排除。
- **境界規則（テキスト編集中）**：インラインテキスト編集中はキーイベントを編集対象が取り、操作言語は停止する。例外は**編集境界キー**（Enter／Tab／Esc／空欄Backspace）と**Undo/Redo**で、これらは操作言語が解釈する（Enter＝確定して兄弟追加、のように編集の終了と操作が連動するため）。Undo/Redoを編集中もアプリの履歴が取るのは、制御された入力欄ではブラウザ標準のUndoがReactの再レンダリングと食い違うためで、履歴をアプリ側に一本化する。Space・矢印・Alt+↑↓は編集対象のもの（Spaceは文字入力、矢印はカーソル移動）。パン誤爆・ノード移動誤爆を構造的に排除する。
- **拡張規則**：ツール固有キーの追加は可。グローバル層および自ファミリーの標準キーと衝突する再定義は禁止。

## 11. 検証の観点（ドッグフーディング）

- **第一関門：会議のスピードに入力が追いつくか。** 操作言語（10章）とキャンバス操作の使用感を含めて評価する。
- **AI連携の価値検証。** Skill（4章）による下書き生成・ヒアリング型データ作成・レビューが、実際の仕様検討で「ゼロから入力するより速く・漏れが減る」かを確認する。文章校正系（用語チェックのAI層）は費用対効果が高い着手候補。
- **成果物が仕様書として機能するか。** NotePMに貼ったMarkdown/Mermaid出力（8章）が、実際の仕様書として読まれ・使われるかを確認する。出力実装は「使う」と確定したツールから着手する。
- **色・デザインの確定（9章）** はドッグフーディングの使用感を経てから行う。
- **チーム展開はクオリティ確認後。** 展開時には配布方法（7章の但し書き）を再検討する。
