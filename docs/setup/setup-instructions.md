# 環境構築指示書（M0：足場作り）

対象: Claude Code
位置づけ: **実装計画（writing-plans）に入る前の足場作り。** 計画フレームワークは「リポジトリが存在し、テストがグリーンで通る状態」を出発点に想定するため、ここを先に済ませる。
関連: `impl-scope-glossary.md`（実装スコープ）/ `overview-rev.md`（設計方針）/ `glossary.schema.json`（スキーマ）

**このタスクではアプリの機能を一切実装しません。** 用語集の画面もエディタもまだ作らない。「空の Tauri アプリが起動し、テストが通り、スキーマから型が生成される」ところまでが範囲です。

## 1. 技術スタック（決定済み。変更しない）

| 層       | 選定                            | 備考                                              |
| -------- | ------------------------------- | ------------------------------------------------- |
| アプリ框 | Tauri（Windows ターゲット優先） |                                                   |
| 言語     | TypeScript                      | **Rust は原則書かない**（後述）                   |
| スタイル | Tailwind CSS                    | 色値の直書き禁止（後述）                          |
| UI部品   | shadcn/ui                       | **額縁のみ**。エディタ本体には使わない            |
| スキーマ | JSON Schema                     | TypeScript 型の正。手書きの型定義と二重管理しない |

### Rust を書かない方針について

Tauri は fs / dialog 等の標準プラグインを提供する層としてのみ使い、**ロジックは全て TypeScript 側に置きます**。理由は3つ:

1. このアプリに Rust を要する仕事（重い計算、バイナリ処理）が存在しない。実体は「JSON 読み書き＋UI＋検証」で数百レコード規模
2. 実装をAIに委譲してもレビューとデバッグの責任は人間に残る。読めない言語の層は監査不能になる
3. TS/Rust に分かれると IPC 境界が生まれ、境界をまたぐバグ（型ズレ、非同期タイミング）は診断が難しい

セットアップ時に生成される Rust 側の雛形コードはそのままで構いません。**新規に Rust のコマンドを追加しないでください。** ファイルアクセスは Tauri の標準プラグイン（fs / dialog）で足ります。必要な権限（capabilities）の設定はこの段階で通しておいてください。

## 2. やること

### 2-1. リポジトリの初期化

- Tauri + TypeScript のプロジェクトを作成（フロントは Vite ベース。React を使う）
- `npm run tauri dev` で空のウィンドウが起動することを確認

### 2-2. Tailwind CSS と shadcn/ui

- Tailwind をセットアップ（公式手順を確認すること）
- shadcn/ui を初期化し、**動作確認用に Button を1つだけ**追加する。他のコンポーネントはこの段階では入れない
- **役割トークンの枠だけ作る**（値は仮置き）:
  - `ink`（文字・線・ヘッダ）/ `warning`（警告・削除・未定義）/ `ok`（応答・結果・確定）＋無彩色系（背景・面・罫線・抑えた文字）
  - ライト/ダークで別パレットを持てる構造にする（**反転による自動生成はしない**。警告色が背景に沈むため）
  - ライト側の仮値: `ink: #22303C` / `warning: #C73E3A` / `ok: #2C7A6E`。**コード上に「仮置き。ドッグフーディング後に確定」とコメントを残すこと**
- **コンポーネントに色値を直書きしない**。必ず役割トークン経由。この規約はここで作った構造が守らせる

### 2-3. テストランナー

- Vitest を導入（Vite ベースのため相性が良い）
- **空のテストを1本書き、グリーンで通ることを確認**する。これが以降の計画フェーズの出発点になる
- `npm test` で実行できるようにする

### 2-4. スキーマ → TypeScript 型の自動生成

- `glossary.schema.json` をリポジトリに配置する。**置き場所は1箇所のみ**（例: `schemas/glossary.schema.json`）
  - Skill 側の `glossary-write.mjs` は親ディレクトリを遡って `glossary.schema.json` または `schemas/glossary.schema.json` を探すか、環境変数 `FACET_GLOSSARY_SCHEMA` で指定を受ける。**コピーを作らないこと**（正は一つ）
- json-schema-to-typescript 等で型を生成する npm script を用意する（例: `npm run gen:types`）
- 生成された型がビルドを通ることを確認する
- **生成物をコミットするかは判断して報告してください。** コミットする場合は「手で編集しない」旨をファイル冒頭に明記すること

### 2-5. `.gitattributes`（必須）

リポジトリルートに以下を含む `.gitattributes` を作成:

```
*.json text eol=lf
```

**これは省略できません。** Windows の autocrlf 環境では、これが無いと commit 時に JSON が CRLF へ変換され、アプリが LF で書き出す正規形が Git 上で無意味になり、毎回全行 diff が出ます。「変更履歴を仕様の変更履歴として読める」という設計目的が壊れます。

`.gitignore` も併せて整備してください（node_modules、Tauri のビルド成果物、生成型をコミットしない選択をした場合はそれも）。

### 2-6. 動作確認用のサンプルデータ

`glossary.schema.json` に適合する用語集ファイルを1つ、作業用フォルダに置いてください（M1 以降の動作確認に使います）。**IDは自分で書かず** `new-id.mjs` で採番してください。`glossary-write.mjs --check` で検証が通ることを確認します。

- **shadcn コンポーネントの大量導入**（必要になった時点で足す）
- **色値の確定**（ドッグフーディング後に決める。今回は仮置き）
- **ディレクトリ構成の作り込み**。この段階では最小限でよく、本格的な構成は実装計画フェーズで決める
