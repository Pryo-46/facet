# 計画立案の教訓

> **追記する文書。** マイルストーンごとに「計画そのものに含まれていた誤り」が出るので、そこから**次の計画に適用できる形**に一般化してここへ足す。個別の出来事は各マイルストーンの [`history/`](history/) に残っており、本書はそこから抽出した**規則**だけを持つ。
>
> **実装計画を書く前に、必ず本書を読むこと。**

## 大原則

**計画のコードは検証済みの正ではない。レビューを通す前提の下書きとして扱う。**

M3・M4・M5・M6 と4マイルストーン連続で、計画に完全なコードを書いても実装・レビューの段で誤りが出た。「完全なコードを載せる」ことの限界はもう疑う余地がない。したがって:

- **実装者は、計画の指示が矛盾していたら辻褄を合わせずに「計画の矛盾」として報告する。** M4 Task 5（テスト件数の数え間違い）、M5 Task 2・Task 3、M6 Task 7・Task 8・Task 10 で実際にそうされ、いずれも正しい対応だった。計画にこの指示を明記しておくことは機能している。**ただし M7 Task 5 はこの指示だけでは機能しなかった反例である。** 計画は同じ指示を明記していたにもかかわらず、実装者は JSDoc の `oklch` 例と色値直書き検査のパターンが衝突するのに遭遇した際、報告せずドキュメントを薄める方向で辻褄を合わせた。さらに次の fix round で、実行していない revert を「完了した」と報告した（controller が `git diff` で確認して発覚）。**指示を書くだけでは足りない。検証コマンドとその出力を報告に貼らせることで、初めて「やっていない作業をやったと報告する」経路が塞がる。** M7 では fix round 2 でこの形にして解決した
- **計画に完全なコードを載せると、そのコードの設計上の欠陥まで忠実に実装される。** M4 では同じ9行を2箇所に書けと指示してしまい、重複が「計画通りに書いた」結果として生まれた
- **ライブラリの内部挙動は計画時点では未検証である。** M4 の `ConfirmDialog` は Radix の内部 close 発火を踏み、計画のコードのままではテストが落ちた

## 設計判断の扱い

- **決定済みの設計判断を蒸し返さない。** MCP不採用 / DB不採用 / tags除外 / condition保留 / 自動保存＋Git の二層構造は決定済み（理由は [`overview-rev.md`](overview-rev.md) と [`glossary/session-notes.md`](glossary/session-notes.md)）
- **ディレクトリ構成・状態管理方式・コンポーネント分割は計画側で決めてよい。** ただしモジュール規約の境界（コア / 各ツールモジュール）は跨がないこと

## テストの設計

- **テストを書く価値が特に高い箇所**: 正規形のバイト一致、スキーマ検証の合否判定、整合性検証の各ルール、マイグレータの恒等性、**副作用の順序**。いずれも期待値が完全に決定的で、かつ人間の目視では確認しにくい
- **計画にテストコードを載せるなら、「実装を壊したときに落ちるか」を計画時点で自問する。** M6 の最終レビューが見つけた Critical はこれだった——自己書き込み除外のテストが `not.toContain('toast')` しか見ておらず、**壊れたときの実症状（二択ダイアログ）とは別の事象を検証していた**ので、壊しても緑のままだった。**症状を取り違えたテストは、無いテストより危険である**（緑が保証に見える）
- **順序を固定するテストを書いたら、対応する実装を1行壊して落ちることを必ず確認する。** M6 ではこの手順で複数の「守っていないテスト」を摘出した
- **すべての分岐にテストを書けるわけではない。** black-box で観測差が出ないもの（M6 の `knownDisk.clear()` / `retain()` はハウスキーピングで正しさの判定に接続していなかった）に「守っていないテスト」を足さない。**書かない判断をしたら、なぜ書けないかを記録する**
- **DOM テストは「壊れても画面は一見正常」な回帰に絞る**（IME 誤爆・制御入力の巻き戻り・フォーカス移動・Undo の表示反映）。要素は role とアクセシブル名で引き、レイアウトやクラス名に依存させない
- **計画に機械検査（ソースを regex 等で走査するテスト）を含めるときは、その計画自身が書くコード・コメント・テストがその検査に引っかからないかを計画段階で確かめる。** M7 は Task 1 で `contrast.ts` の JSDoc に `oklch(0.921 0.012 96.4)` という説明例を書かせ、Task 5 で `oklch(` を色値直書きの禁止パターンにする検査を作った——同じ計画の中に衝突を仕込んでいた。正しい解決は検査側でコメントを除去することで、`palette.test.ts` に既に同じ前例（`stripComments`）があったのに、実装者はそれを見ずに JSDoc の例を削って辻褄を合わせた

## 状態と時間の扱い（React 層）

- **状態変数の「共有」を計画時に列挙する。** M5 の Critical は「1つの状態を2つの機構が使っている」ことの見落としだった（`ask` 分岐で saver を dispose すると `hasUnsaved()` の信号が消える）。計画に「この状態を読むのは誰か／変えるのは誰か」の表を1つ入れる
- **`ref` で「過去の値を保持する」設計を書いたら、それが本当に凍結されるかを確認する。** レンダごとに代入する ref は「最新値の読み取り口」であって「スナップショット」ではない。**正解は「判断に使う値を、判断を起動する関数の中で引いて引数で渡す」**（M5 の誤り2）
- **表示用の値を判断材料にしない。** M6 でコントローラをコアへ切り出した際、状態をクロージャ変数で持ち `AppHost` に getter を1つも生やさないことで、この種の誤りを構造的に消した
- **非モーダルな UI 要素（トースト）の寿命と、それを押せる文脈を計画に書く。** 「自動で消えない」と決めた時点で「いつ・どの状態で押されうるか」が仕様になる（M5 の誤り4）
- **モーダルの閉じ方を列挙するとき、アプリの外側の閉じ方を数え落とさない**（OS のタイトルバーの ×）。M5 で実際に落とした

## タスク分割

- **次のタスクが即消すスタブを置く分割は、分割線そのものが間違っている。** M4 で指摘され、**M6 の計画で同じ形を再発させた**（着手前のスキャンで発見・修正）。タスクを分けたら「後のタスクが前のタスクの成果物を捨てないか」を1回確認する
- **タスクの継ぎ目を疑う。** M6 の Important 2件はどちらも継ぎ目にあった（削除と外部変更が `pendingAsk` を共有していた／自己書き込み除外のテストと二択の分岐）。単体では両方とも正しく見える
- **サブエージェントは GUI を操作できない。** 実機確認は人間の作業として計画に明記する

## 検証手順

- **検証手順の対象を絞らない。** 「このタスクに関係するテストだけ回す」は、依存の見落としをそのまま隠す。M6 の fixture 移設は、対象を絞って回していたら2ファイルの取り残しを見逃していた
- **計画が書いた「確認コマンド」自体を1回自分で実行してみる。** grep のパターンは特に、自分が指示した配線にヒットしないかを確かめる（M6 Task 8 で実際に矛盾した）
- **テストの件数を計画に書かない。** M4・M5 で2回とも数え間違えた。期待値は「このファイルの `it` がすべて緑」と書く

## ドキュメントの更新

- **`overview-rev.md` への反映は当該マイルストーンの完了コミットで済ませ、申し送りに TODO として残さない。** 次の計画者は rev を「正」として読むため、反映漏れは設計と実装の食い違いとして伝播する（M4 の教訓。M3 の反映漏れが M4 完了時まで残っていた）
