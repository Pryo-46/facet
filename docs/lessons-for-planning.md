# 計画立案の教訓

実装計画を書く前に読む。1規則1行。追記も1行で、エピソードは PR の本文に書く。

## 大原則

- 実装者は、計画の指示が矛盾していたら辻褄を合わせずに「計画の矛盾」として報告する。
- 計画に完全なコードを載せると、そのコードの設計上の欠陥まで忠実に実装される。
- ライブラリの内部挙動は計画時点では未検証である。
- 同じイベントが2つの経路を通る UI 部品を計画に書いたら、どちらが打鍵を消費するかを明示する。
- ライブラリの既定値を計画に書くなら、`node_modules` にある実物で確かめる。
- ライブラリの既定値が OS で反転していないかを、計画時点で1回問う。
- 設定で塞げるのは、その設定が届く範囲だけである。同じ既定値が複数のインスタンスに配られていないかを確かめる。
- 既存の実装と一致しなければならないもの（文言・計上規則・ディレクトリ規約・出力の形）を計画に書くなら、実物から逐語で写し、どのファイルから取ったかを書く。
- 破壊的な処理の粒度を細かくする修正は、「途中で失敗した状態」を新しく作る。分割したら、途中で失敗したときにどうするか（続行するか・巻き戻すか）を計画で決める。
- 画面座標で位置を決めるポップアップ（Radix 等）をキャンバスに載せるときは、開いている間に親（キャンバス）の操作を止める必要があるかを計画時点で1回問う。
- 計画にコード断片を貼るときは、その断片が触るファイルに、同じ操作を条件付きで行っている既存箇所が無いかを1回見る。断片単体では正しくても、ファイルが既に守っている不変条件を破る。
- 計画が実物の挙動を2箇所で述べていたら、着手前に突き合わせる。食い違っていたら、実物のコードに当たるまでどちらも書かない。
- 「前のマイルストーンで実装済み」という状態の主張は `grep` の網に掛からない。計画が実装済みと信じている機能ほど、着手前に実物で1件ずつ裏取りする。

## 設計判断の扱い

- 決定済みの設計判断を蒸し返さない。
- ディレクトリ構成・状態管理方式・コンポーネント分割は計画側で決めてよい（ただしモジュールの境界は跨がない）。
- 「錠前の粒度を直す」計画を書いたら、そもそも競合しうる主体が2つ以上いるかを1回問う。
- 計画に「実物の何行目に何がある」と書くなら、その範囲を実際に開いて、主張した事実がそこに含まれることを確かめる。計画が断定した細部は、再導出されずにそのまま転記される。
- 色相を増やす判断を書いたら、P型・D型で分かれるかを計画時点で検算する。色相で分かれないなら明度で分ける。
- 「区別を1つ増やす」判断のうち、費用が入力の瞬間にしか現れないものは、紙の上で決着させない。実機で一巡してから `enum` に入れる。

## デバッグの進め方

- 実機でしか再現しない不具合は、修正を試す前に「どこまで到達しているか」を可視化する仕掛けを先に入れる。
- パラメータを持つエスケープシーケンスを、生バイト列の完全一致で探さないこと。

## テストの設計

- テストを書く価値が特に高いのは、正規形のバイト一致・スキーマ検証の合否判定・整合性検証の各ルール・マイグレータの恒等性・副作用の順序である（期待値が完全に決定的で目視確認しにくい）。
- 計画にテストコードを載せるなら、「実装を壊したときに落ちるか」を自問するだけでなく、実際に実装を壊して赤くなることを確認する。
- すべての分岐にテストを書けるわけではない。書かないと決めたら理由を記録する。
- 検証の集合に何を入れるかは設計判断である（対象を広げると、選べなくなる値が出る）。
- DOM テストは「壊れても画面は一見正常」な回帰に絞り、要素は role とアクセシブル名で引く（レイアウトやクラス名に依存させない）。
- テストの期待値を閾値ちょうどに置かない。
- `aria-label` を足したら、既存テストの前方一致クエリと衝突しないか確かめる。
- `expect(fn).not.toHaveBeenCalled()` は、その関数を呼ぶ前に例外が飛んだ場合も真になる。
- 区別したい2つの実装が同じ答えを返す入力を、テストデータに選ばない。
- 計画のテストコードにコメントで終わり `expect` を持たない一節が無いか、着手前に確認する。
- 「この環境ではテストできない」という申し送りを、確かめずに書かない。
- 計画のテストコードが既存のフィクスチャ／ヘルパを名指しするなら、そのヘルパが作る世界に、検証したい経路が存在するかを確かめる。
- 既存の機械検査（ソースを走査するテスト）は、走査の母集合を「今あるファイルの形」で決めた瞬間に嘘になる。
- 「ここは複製するしかない」と計画で結論したら、その複製を機械検査で固定できる形にできないかを1回問う。
- 計画に機械検査（ソースを regex 等で走査するテスト）を含めるときは、その計画自身が書くコード・コメント・テストがその検査に引っかからないかを計画段階で確かめる。
- 定数を固定値に変える変更は、その定数を観測点にしているテストを黙って殺す。観測点の移設を、殺す変更より前のタスクに置き、現行コードのまま緑になる形で書き換えること。
- ブラウザの挙動に関する前提を、実機で確かめずに設計判断の土台にしないこと。
- 一つの理由で代案を退けたら、その理由に逃げ道が無いかを一度疑うこと。

## 状態と時間の扱い（React 層）

- 状態変数の「共有」を計画時に列挙する（複数の機構が同じ状態を使う見落としを防ぐ）。
- `ref` で「過去の値を保持する」設計を書いたら、それが本当に凍結されるかを確認する。
- 表示用の値を判断材料にしない（実際の状態と乖離しうる）。
- 非モーダルな UI 要素（トースト）の寿命と、それを押せる文脈を計画に書く。
- モーダルの閉じ方を列挙するとき、アプリの外側の閉じ方（OS のタイトルバーの×等）を数え落とさない。
- 計画が「この変数のこの位置に置く」とコードの挿入場所を指定するときは、そこで参照する識別子がその時点で既に宣言されているかを確認する（TDZ）。

## タスク分割

- 次のタスクが即消すスタブを置く分割は、分割線そのものが間違っている。
- タスクの継ぎ目を疑う（単体では正しく見えても継ぎ目に欠陥が潜む）。
- サブエージェントは GUI を操作できない（実機確認は人間の作業として計画に明記する）。
- 人間が実機で観察した「困りごと」の言葉を、実装者が別の問題に翻訳してしまうことがある。対策が症状ではなく元の困りごとを消しているか確認する。
- 実機確認と「ドキュメント反映」を同じタスクに束ねない（未実施が完了報告に埋没する）。

## 検証手順

- 検証手順の対象を絞らない（絞ると依存の見落としを隠す）。
- 計画が書いた「確認コマンド」自体を1回自分で実行してみる。
- 「この機構を使っている箇所は N 箇所」と書くなら、その N は grep の出力から取る。
- 「無い」ことの根拠に、出力が打ち切られた検索を使わない。
- 計画が「既存の機械検査はこう振る舞う」と書くなら、その検査の実装を読んでから書く。
- 「同じ種類のものを1つ増やす」計画を書いたら、その一覧を配列リテラルで固定しているテストも改修箇所に数える。
- enum に値を1つ足す計画を書いたら、その値が並ぶ場所を「型が網羅を強制するもの」と「手書きの配列」に仕分ける。赤くなるのは前者だけである。
- JSON Schema に `maxItems` を1つ足す改訂は「JSON の1行」ではない。生成される TypeScript がタプル（`[] | [T]`）になり、その配列を組み立てている側が一斉に落ちる。
- テストの件数を計画に書かない。
- 成果物が利用者に「これを実行しろ」と指示しているなら、それを実行した後の状態でもう一度アプリを動かすところまでを実機確認の手順に書く。
- CSS のカスケードに依存する変更は、生成 CSS を見るまで検証したことにならない。
- worktree を作ったら、最初のコミットを積む前に基底 SHA を確認する。
- `git diff --numstat` が `-`（ハイフン）2つを返さないことは、「ファイルに NUL バイトが混入していない」の証明にならない。
- スキーマ改訂のように「型エラーの波」を複数タスクへ分けて閉じる計画では、『このタスクで完全に緑になる』と書く境界を、赤の原因（どのタスクの変更がどのファイルを赤くしているか）まで実際に辿ってから確定する。
