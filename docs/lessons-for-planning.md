# 計画立案の教訓

> **追記する文書。** マイルストーンごとに「計画そのものに含まれていた誤り」が出るので、そこから**次の計画に適用できる形**に一般化してここへ足す。個別の出来事は各マイルストーンの [`history/`](history/) に残っており、本書はそこから抽出した**規則**だけを持つ。
>
> **実装計画を書く前に、必ず本書を読むこと。**

## 大原則

**計画のコードは検証済みの正ではない。レビューを通す前提の下書きとして扱う。**

M3・M4・M5・M6 と4マイルストーン連続で、計画に完全なコードを書いても実装・レビューの段で誤りが出た。「完全なコードを載せる」ことの限界はもう疑う余地がない。したがって:

- **実装者は、計画の指示が矛盾していたら辻褄を合わせずに「計画の矛盾」として報告する。** M4 Task 5（テスト件数の数え間違い）、M5 Task 2・Task 3、M6 Task 7・Task 8・Task 10 で実際にそうされ、いずれも正しい対応だった。計画にこの指示を明記しておくことは機能している。**ただし M7 Task 5 はこの指示だけでは機能しなかった反例である。** 計画は同じ指示を明記していたにもかかわらず、実装者は JSDoc の `oklch` 例と色値直書き検査のパターンが衝突するのに遭遇した際、報告せずドキュメントを薄める方向で辻褄を合わせた。さらに次の fix round で、実行していない revert を「完了した」と報告した（controller が `git diff` で確認して発覚）。**指示を書くだけでは足りない。検証コマンドとその出力を報告に貼らせることで、初めて「やっていない作業をやったと報告する」経路が塞がる。** M7 では fix round 2 でこの形にして解決した
- **計画に完全なコードを載せると、そのコードの設計上の欠陥まで忠実に実装される。** M4 では同じ9行を2箇所に書けと指示してしまい、重複が「計画通りに書いた」結果として生まれた
- **ライブラリの内部挙動は計画時点では未検証である。** M4 の `ConfirmDialog` は Radix の内部 close 発火を踏み、計画のコードのままではテストが落ちた
- **ライブラリの既定値を計画に書くなら、`node_modules` にある実物で確かめる。** logic-tree M1 の計画は「d3-zoom の既定 `filter` は Ctrl+ホイールを弾く」と書いたが、それは v2 の挙動で、入っている v3 の既定は逆に通す。**ライブラリの既定値は、Web 上の解説記事も自分の記憶も、たいてい一つ前のメジャー版を指している。** 幸い差し替えの必要性は別の理由（素のホイールでズームさせない・素の左ドラッグをパンにしない・中ボタンを通す）から独立に成立していたのでコードは正しかったが、**「その既定だから差し替える」という一本足の根拠を書いていたら、実装者は差し替えごと落としていた。** 既定値に依存する判断を書くときは、根拠を1つに絞らない

## 設計判断の扱い

- **決定済みの設計判断を蒸し返さない。** MCP不採用 / DB不採用 / tags除外 / condition保留 / 自動保存＋Git の二層構造は決定済み（理由は [`overview-rev.md`](overview-rev.md) と [`glossary/session-notes.md`](glossary/session-notes.md)）
- **ディレクトリ構成・状態管理方式・コンポーネント分割は計画側で決めてよい。** ただしモジュール規約の境界（コア / 各ツールモジュール）は跨がないこと

## テストの設計

- **テストを書く価値が特に高い箇所**: 正規形のバイト一致、スキーマ検証の合否判定、整合性検証の各ルール、マイグレータの恒等性、**副作用の順序**。いずれも期待値が完全に決定的で、かつ人間の目視では確認しにくい
- **計画にテストコードを載せるなら、「実装を壊したときに落ちるか」を計画時点で自問する。** M6 の最終レビューが見つけた Critical はこれだった——自己書き込み除外のテストが `not.toContain('toast')` しか見ておらず、**壊れたときの実症状（二択ダイアログ）とは別の事象を検証していた**ので、壊しても緑のままだった。**症状を取り違えたテストは、無いテストより危険である**（緑が保証に見える）
- **順序を固定するテストを書いたら、対応する実装を1行壊して落ちることを必ず確認する。** M6 ではこの手順で複数の「守っていないテスト」を摘出した
- **すべての分岐にテストを書けるわけではない。** black-box で観測差が出ないもの（M6 の `knownDisk.clear()` / `retain()` はハウスキーピングで正しさの判定に接続していなかった）に「守っていないテスト」を足さない。**書かない判断をしたら、なぜ書けないかを記録する**
- **検証の集合に何を入れるかは設計判断である。** 「あらゆる要素が載りうる汎用の面」と「特定の要素しか載らない限定的な面」を同じ集合で扱うと、**後者の制約が前者へ伝染して、選べる値が消える。** M8 は見出し用の淡い色を、他の色すべてが要件を満たすことを前提にした背景集合へ入れてしまい、その色自体が成立しなくなった（実装者がトークンを動かさず「計画の誤り」として報告したので、確定済みの配色は壊れずに済んだ）。**集合を1つ増やすより、対象を広げる方が安く見えるが、代償は「もう選べない値」という形で後から現れる。** 限定的な面は、実際に載るものだけを個別に検証する
- **DOM テストは「壊れても画面は一見正常」な回帰に絞る**（IME 誤爆・制御入力の巻き戻り・フォーカス移動・Undo の表示反映）。要素は role とアクセシブル名で引き、レイアウトやクラス名に依存させない
- **テストの期待値を閾値ちょうどに置かない。** M7 の「閾値ちょうどの色値を置かない」は色に限った話ではなく、**丸めや量子化の境界に乗る期待値すべて**に効く。M8 Task 1 は変換結果の期待値を `#808080` にしたが、これは 0..255 への丸めで **127.5 ちょうど**の位置だった。実装者は共有関数側に `+1e-9` を入れて通そうとした——**悪い期待値に合わせて共有関数を歪める**のは、その関数を使う全箇所に影響が及ぶ。正しい対処は期待値を境界から外すこと（線形値で `toBeCloseTo` する形に変えた）。**計画にテストの期待値を書くときは、その値が丸めの境界に乗っていないかを一度確かめる**
- **`aria-label` を足したら、既存テストの前方一致クエリと衝突しないか確かめる。** M8 Task 6 は列幅ハンドルに `aria-label="名称の列幅を変更"` を足し、既存の `getByLabelText(/^名称/)` 10箇所を一斉に曖昧にした。**新しい要素の文言が確定事項なら、直すのは既存テストの正規表現の側である**（`/^名称（/` のように絞る）。アクセシブル名を増やす計画は、その名前で始まる既存クエリを1回 grep すること
- **区別したい2つの実装が同じ答えを返す入力を、テストデータに選ばない。** logic-tree M1 は11タスク中7タスクで「変異させても全緑」の穴が出た。**同じ形が繰り返し出ている**——`Enter`（兄弟追加）のテストが葉の直後で足していたため `Tab`（子追加）に差し替えても配列位置もラベルも一致した／上方向の移動のテストが葉2兄弟の入れ替えだったため補正式を下方向のものに差し替えても偶然一致した／並び替えのテストが兄弟ちょうど2つだったため「隣」を「常に先頭」「常に末尾」に差し替えても通った。いずれも**退化ケース（要素2つ、深さ1、端、空）をテストデータに選んだこと**が原因である。計画にテストを書いたら、期待値ごとに「**隣の実装でも同じ値になるか**」を1回問い、なるなら入力を1段複雑にする（兄弟3つ、途中の子、キャレットを端に置く）。既存の「実装を壊したときに落ちるか」の自問を、**具体的に「どの実装と取り違えられるか」まで降ろした形**として運用する
- **「この環境ではテストできない」という申し送りを、確かめずに書かない。** logic-tree M1 では2回書かれ、2回とも誤りだった——「Web フォント読み込み後の測り直しは観測点が内部状態しかない」は実際にはノード矩形の `style.width` に出ていた（レビュアーがテストを書いて反証）／「d3-zoom の配線は jsdom ではテストが難しい」は実際には既定の `wheelDelta` の10倍も素の左ドラッグのパンも DOM に出ており17本書けた。**観測点は実装の内部にではなく、実装が最終的に触る DOM・返り値・呼び出し引数に探す。** 直接の結果が見えないときは別の窓を探す（`preventDefault` は「スクロールしないこと」を jsdom で観測できないが、`fireEvent` の**戻り値**が既定動作の抑止を返す）。それでも書けないなら、**なぜ書けないかを「どの観測点を当たったか」まで含めて記録する**（「すべての分岐にテストを書けるわけではない」の但し書きとして運用する）
- **既存の機械検査（ソースを走査するテスト）は、走査の母集合を「今あるファイルの形」で決めた瞬間に嘘になる。** M10 は `palette.test.ts` が `GlossaryEditor.tsx` を決め打ちしていたため2本目のエディタを検査していなかった。走査化して直した直後の logic-tree M1 で、今度は `*Editor.tsx` という母集合が**表を持たないツール**を取りこぼした——赤表示の面を当てているのがエディタ本体ではなく部品（`NodeBox.tsx`）だったため、部品側に検算を通っていない濃さを書き放題だった。**同じ穴が2回続いている。** 規則は2つ: (1) 走査の母集合は**役割ではなくディレクトリ**で取る（`src/modules/` 配下の `.tsx` 全部）。役割で絞ると、次のツールが役割の形を変えたときに黙って外れる。(2) **新しいツール・新しい種類のコンポーネントを足す計画には、既存の機械検査がそれを走査対象に含むかを確かめる手順を1つ入れる。** なお、検査を通すためだけに使わない定数を新ファイルへ置くのは**検査を騙す行為**であり、直すべきは検査の側である
- **計画に機械検査（ソースを regex 等で走査するテスト）を含めるときは、その計画自身が書くコード・コメント・テストがその検査に引っかからないかを計画段階で確かめる。** M7 は Task 1 で `contrast.ts` の JSDoc に `oklch(0.921 0.012 96.4)` という説明例を書かせ、Task 5 で `oklch(` を色値直書きの禁止パターンにする検査を作った——同じ計画の中に衝突を仕込んでいた。正しい解決は検査側でコメントを除去することで、`palette.test.ts` に既に同じ前例（`stripComments`）があったのに、実装者はそれを見ずに JSDoc の例を削って辻褄を合わせた

## 状態と時間の扱い（React 層）

- **状態変数の「共有」を計画時に列挙する。** M5 の Critical は「1つの状態を2つの機構が使っている」ことの見落としだった（`ask` 分岐で saver を dispose すると `hasUnsaved()` の信号が消える）。計画に「この状態を読むのは誰か／変えるのは誰か」の表を1つ入れる
- **`ref` で「過去の値を保持する」設計を書いたら、それが本当に凍結されるかを確認する。** レンダごとに代入する ref は「最新値の読み取り口」であって「スナップショット」ではない。**正解は「判断に使う値を、判断を起動する関数の中で引いて引数で渡す」**（M5 の誤り2）
- **表示用の値を判断材料にしない。** M6 でコントローラをコアへ切り出した際、状態をクロージャ変数で持ち `AppHost` に getter を1つも生やさないことで、この種の誤りを構造的に消した
- **非モーダルな UI 要素（トースト）の寿命と、それを押せる文脈を計画に書く。** 「自動で消えない」と決めた時点で「いつ・どの状態で押されうるか」が仕様になる（M5 の誤り4）
- **モーダルの閉じ方を列挙するとき、アプリの外側の閉じ方を数え落とさない**（OS のタイトルバーの ×）。M5 で実際に落とした

## タスク分割

- **次のタスクが即消すスタブを置く分割は、分割線そのものが間違っている。** M4 で指摘され、**M6 の計画で同じ形を再発させた**（着手前のスキャンで発見・修正）。タスクを分けたら「後のタスクが前のタスクの成果物を捨てないか」を1回確認する
- **タスクの継ぎ目を疑う。** M6 の Important 2件はどちらも継ぎ目にあった（削除と外部変更が `pendingAsk` を共有していた／自己書き込み除外のテストと二択の分岐）。単体では両方とも正しく見える
- **サブエージェントは GUI を操作できない。** 実機確認は人間の作業として計画に明記する
- **実機確認と「ドキュメント反映」を同じタスクに束ねない。** logic-tree M1 は最終タスクにこの2つを入れたため、ドキュメントだけが完了してコミットされ、実機確認は未実施のまま残った。**申し送りが書かれてコミットが積まれた状態は「終わった」ように見える**ので、束ねると未実施が静かに埋没する。分けたうえで、実機確認タスクの結果が出るまで**申し送りには「未実施」と明記し、確認項目のチェックリストを空のまま残す**（[`open-issues.md`](open-issues.md) にも1項目として載せる。`history/` にだけ書くと幽霊になる）

## 検証手順

- **検証手順の対象を絞らない。** 「このタスクに関係するテストだけ回す」は、依存の見落としをそのまま隠す。M6 の fixture 移設は、対象を絞って回していたら2ファイルの取り残しを見逃していた
- **計画が書いた「確認コマンド」自体を1回自分で実行してみる。** grep のパターンは特に、自分が指示した配線にヒットしないかを確かめる（M6 Task 8 で実際に矛盾した）
- **「この機構を使っている箇所は N 箇所」と書くなら、その N は grep の出力から取る。** logic-tree M1 は共通のキー処理コンテキストを組んでいる箇所を3つと数えたが、実際は4つあった（別名チップの入力欄が別に組んでいた）。**数え落とした1箇所は、たいてい「エディタ本体」ではない周辺の部品**である——実装者が気づいて報告したので事故にはならなかったが、気づかなければ改修漏れとして残る。件数を書かない選択肢もある（テストの件数は書かないと決めてある）が、**改修対象の列挙は網羅そのものが指示なので、件数ではなくファイルパスの一覧で書く**のが安全
- **テストの件数を計画に書かない。** M4・M5 で2回とも数え間違えた。期待値は「このファイルの `it` がすべて緑」と書く
- **CSS のカスケードに依存する変更は、生成 CSS を見るまで検証したことにならない。** `npm test` も `tsc` も `lint` も、この種の欠陥を**原理的に**捕まえない（テストは DOM を見るがスタイルの解決結果を見ず、型検査と lint は文字列としてのクラス名しか見ない）。M8 は `@layer base` に書いた `line-height` が実質すべてのボタンに届いていないのに、3つとも緑のまま「直った」と報告された（cascade layers では後に宣言された utilities レイヤーが特異性に関係なく base に勝つ）。**スタイルの解決順序・レイヤー・変数の既定値に関わる変更を計画に書いたら、検証手順に `npx vite build` で生成 CSS を読む手順を入れる。** あわせて、**カスケードの争いに「勝つ」形の解決を疑う**——勝ち負けが順序に依存する以上、順序が変われば静かに戻る。M8 の正解は、相手が普段設定しない変数（`--tw-leading`）へ逃がして**衝突自体を起こさない**ことだった
