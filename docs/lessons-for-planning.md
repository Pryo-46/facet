# 計画立案の教訓

実装計画を書く前に読む。1規則1行。追記も1行で、エピソードは PR の本文に書く。

## 大原則

- 実装者は、計画の指示が矛盾していたら辻褄を合わせずに「計画の矛盾」として報告する。
- 指示を書くだけでは足りない。検証コマンドと出力を貼らせて、初めて「やっていない作業をやった」報告を防げる。
- 計画に完全なコードを載せると、そのコードの設計上の欠陥まで忠実に実装される。
- ライブラリの内部挙動は計画時点では未検証である。
- 同じイベントが2経路を通る UI 部品は、意味を持った打鍵を部品側で消費し親へ渡さない（順序調整に頼らない）。同じキーの奪い合いが無いか問い、消費条件をコメントに書く。
- ライブラリの既定値は `node_modules` の実物で確かめる（解説記事は旧メジャー版を指しがちで、根拠を1つに絞らない）。
- ライブラリの既定値が OS で反転していないか計画時点で問う。パス・隠しファイル・大小文字・改行を扱う機能は OS 分岐を実物で確かめ、異なる OS の実機確認を明記する。
- 設定で塞げるのは、その設定が届く範囲だけである。同じ既定値が複数のインスタンスに配られていないか確かめる。
- 既存の実装と一致すべきもの（文言・計上規則・ディレクトリ規約等）は実物から逐語で写し出典を書く。「ブリーフが正」の計画では「一致すべきは実物が正」も明記する。
- 破壊的な処理を細かく分割する修正は「途中で失敗した状態」を新しく作る。失敗時の対応（続行か巻き戻しか）を決め、守りたい性質は具体名でなく一般形で書く。
- 画面座標で位置を決めるポップアップ（Radix 等）をキャンバスに載せるときは、開いている間に親の操作を止める必要があるか計画時点で問う。
- 計画にコード断片を貼るときは、そのファイルに同じ操作を条件付きで行う既存箇所が無いか見る（不変条件を破りうる）。既存のガードには合流させ、条件を複製しない。
- 計画が実物の挙動を2箇所で述べたら着手前に突き合わせ、食い違えば実物に当たるまで書かない。利用者向け文言は根拠のコードパスを併記し、「後で整う」説明は経路を辿る。
- 「前のマイルストーンで実装済み」という主張は `grep` の網に掛からない。信じている機能ほど着手前に実物で裏取りする。

## 設計判断の扱い

- 決定済みの判断を蒸し返さない。
- ディレクトリ構成・状態管理方式・コンポーネント分割は計画側で決めてよい（ただしモジュールの境界は跨がない）。
- 「錠前の粒度を直す」計画を書いたら、競合しうる主体が2つ以上いるか問う。
- 「Aを直せば症状Bが消える」と書くときは、AB間に因果があるか実物で確かめる。直し方は消える欠陥と増える失敗モードを並べて書く。
- 計画に「実物の何行目に何がある」と書くなら、その範囲を開いて事実を確かめる（断定した細部は転記される）。利用者に実行させる手順は直後まで通しで読む。
- 色相を増やす判断を書いたら、P型・D型で分かれるかを計画時点で検算する。色相で分かれないなら明度で分ける。
- 「区別を1つ増やす」判断のうち、費用が入力の瞬間にしか現れないものは、紙の上で決着させない。実機で一巡してから `enum` に入れる。
- 区別を足す判断は「何が違うか」でなく、誰が・いつ・何回選ばされるか、その選択が後で何を変えるかで書く。
- 観察が済むまでは、区別を `enum`（`kind`）でなく自由記述（`note`）に置く。
- 見た目が成果物のマイルストーンでは、実機確認をスキーマ凍結の後ろに置かない。

## デバッグの進め方

- 実機でしか再現しない不具合は、修正前に「どこまで到達しているか」を可視化する仕掛けを先に入れる。推測修正が1回外れたら計測に切り替える。
- パラメータを持つエスケープシーケンスを生バイト列の完全一致で探さない。

## テストの設計

- テストの価値が特に高いのは、正規形のバイト一致・スキーマ検証の合否・整合性検証の各ルール・マイグレータの恒等性・副作用の順序（目視確認しにくい）。
- 計画にテストコードを載せるなら「壊したら落ちるか」を自問するだけでなく、壊して赤くなるか確認する（症状違いのテストは無いより危険）。
- すべての分岐にテストを書けるわけではない。書かないと決めたら理由を記録する。
- 検証の集合に何を入れるかは設計判断である（対象を広げると、選べなくなる値が出る）。
- DOM テストは「壊れても画面は一見正常」な回帰に絞り、要素は role とアクセシブル名で引く（レイアウトやクラス名に依存させない）。
- テストの期待値を閾値ちょうどに置かない（合わせるために共有関数を歪めない）。
- `aria-label` を足したら、既存テストの前方一致クエリと衝突しないか確かめる（文言が確定なら直すのは既存テストの正規表現の側）。
- `expect(fn).not.toHaveBeenCalled()` は、その関数を呼ぶ前に例外が飛んだ場合も真になる。
- 区別したい2つの実装が同じ答えを返す入力を、テストデータに選ばない（要素2つ・深さ1・端・空等の退化ケースに注意する）。
- 計画のテストコードにコメントで終わり `expect` を持たない一節が無いか、着手前に確認する。
- 「この環境ではテストできない」と確かめずに書かない。観測点は内部でなく、最終的に触る DOM・返り値・呼び出し引数に探す。書けないなら当たった観測点も記録する。
- 計画のテストコードが既存のフィクスチャ／ヘルパを名指しするなら、そのヘルパが作る世界に、検証したい経路が存在するかを確かめる。
- 既存の機械検査（ソース走査テスト）は、母集合を「今あるファイルの形」で決めた瞬間に嘘になる。母集合は役割でなくディレクトリで取り、新ツールの計画に含むか確かめる手順を入れる。
- 「ここは複製するしかない」と結論したら、その複製を機械検査で固定できないか問う（手複製とバイト一致コピーは、ズレたとき赤くなるかで質が違う）。
- 計画に機械検査（regex 等でソースを走査するテスト）を含めるときは、計画自身が書くコード・コメント・テストがその検査に引っかからないか確かめる。
- 定数を固定値に変える変更は、それを観測点にするテストを殺す。移設は殺す変更の前に置き、現行コードで緑になる形で書く。期待値も実測から導出し、破壊テストで実効性を確かめる。
- ブラウザの挙動の前提を、実機で確かめず設計の土台にしない。「偽なら設計をやり直す」前提は記録せず着手前に潰す。潰せないなら依存部分を独立コミットに分ける。
- 一つの理由で代案を退けたら、その理由に逃げ道が無いかを一度疑うこと。
- 計画に「ここに番人を置く」と書くときは、置く場所だけでなくどの変異で赤くなるかを1行添える。添えられないなら設計未了である。

## 状態と時間の扱い（React 層）

- 状態変数の「共有」を計画時に列挙する（同じ状態を複数機構が使う見落としを防ぐ）。
- `ref` で「過去の値を保持する」設計は、凍結されるか確認する（判断に使う値は、起動する関数の中で引いて引数で渡す）。
- 表示用の値を判断材料にしない（実際の状態と乖離しうる）。
- 非モーダルな UI 要素（トースト）の寿命と、それを押せる文脈を計画に書く。
- モーダルの閉じ方を列挙するとき、アプリの外側の閉じ方（OS のタイトルバーの×等）を数え落とさない。
- 計画が挿入場所を「この変数の近く」と指定するときは、識別子がその時点で宣言済みか確認する（TDZ。`tsc -b` は初期化順序を検査しない）。

## タスク分割

- 次のタスクが即消すスタブを置く分割は、分割線が間違っている。
- タスクの継ぎ目を疑う（単体では正しく見えても継ぎ目に欠陥が潜む）。
- サブエージェントは GUI を操作できない（実機確認は人間の作業として計画の検証手順に明記する）。
- 人間が実機で観察した「困りごと」を、実装者が別の問題に翻訳してしまうことがある。対策が元の困りごとを消しているか確認する。

## 検証手順

- 検証手順の対象を絞らない（依存の見落としを隠す）。
- 人間の実機確認と文書への反映を同じタスクに束ねない（反映が人間待ちで止まる。依頼は PR 本文で行う）。
- 計画が書いた「確認コマンド」自体を自分で実行してみる。
- 「この機構を使っている箇所は N 箇所」と書くなら N は grep の出力から取る。改修対象は件数でなくファイルパスの一覧で書く。
- 「無い」ことの根拠に打ち切られた検索を使わない（上限を外すか `-c` で数えて確かめる）。
- 計画が「既存の機械検査はこう振る舞う」と書くなら検査の実装を読んでから書く。「何を許すか」は条件式を引用し、走査型の検査は母集合が計画ファイルを含まないか確かめる。
- 「同じ種類のものを1つ増やす」計画は、その一覧を配列リテラルで固定するテストも改修箇所に数える。
- enum に値を1つ足す計画は、値の並ぶ場所を「型が網羅を強制するもの」と「手書きの配列」に仕分ける（赤くなるのは前者だけ）。「両方に足す」前に両方で許されるか実物で確かめる。
- JSON Schema に `maxItems` を1つ足す改訂は「JSON の1行」ではない（生成型がタプルになり組み立て側が落ちる）。改修は配列を作る全箇所と見積もり、型の変化を `npm run gen:types` で確かめる。
- テストの件数を書かない。
- 成果物が利用者に「これを実行しろ」と指示するなら、実行後の状態でアプリを動かすところまで実機確認の手順に書く。
- CSS のカスケードに依存する変更は `npx vite build` で生成 CSS を読むまで検証にならない。カスケードで「勝つ」解決より衝突を起こさない解決を優先する。
- worktree を作ったら、最初のコミット前に基底 SHA を確認する。
- `git diff --numstat` がハイフン2つを返すことは「NUL バイト混入なし」の証明にならない（判定はブロブの先頭だけ走査する）。検証手順にはバイト単位の走査を別途加える。
- 「型エラーの波」を複数タスクへ分けて閉じる計画では、『ここで緑になる』境界を、赤の原因（どの変更がどのファイルを赤くしたか）まで辿ってから確定する。
