**検証を2度空振りさせた罠**（次に確認する人が同じ時間を失わないように記録する）:

### 実装で確定した事項（計画の前提に昇格）

- **自己書き込みの除外は「台帳との内容比較」1箇所で成立する**（`src/core/known-disk.ts` の `KnownDisk`）: アプリが最後に読み書きしたディスクの生バイトをパスごとに保持し、再走査で読んだテキストと比較する。**アプリからの書き込みは必ず `App.tsx` の `writeAndRecord` を通す**（write の成功直後に同期で台帳へ記録する）のが唯一の前提条件で、`writeProjectFile` を直接呼ぶ経路を作ると台帳がずれて自分の書き込みが外部変更として跳ね返る（実害は「Undo 履歴が勝手に破棄される」）。台帳は **React の state ではなく ref に置く**——記録が再レンダリングを待つと、その隙に走った再走査が誤検知する
- **`hasUnsaved()` は in-flight write と失敗して再試行待ちの状態も true に含める**（`src/core/autosave.ts`。`latest !== lastSaved` で、`lastSaved` は write の解決後にしか進まない）。**これが reload と ask の分岐を決める載荷点である**——in-flight write があるときに `reload` へ倒れると、`selectFile` の読み込み後に write が着地して「表示 ≠ ディスク」なのに台帳だけ一致し、**二度と検知されない永続的な食い違い**が開く。`hasUnsaved` を「pending の有無」等へ簡潔化するとこの穴が無言で開くので、定義を変えるときはこの経路を再検証すること（最終レビューで指摘された、コードにコメントとして残っていない不変条件）
- **`flush()` は chain が静止するまで繰り返し、削除経路は `settle()` を使う**: `flush()` の「静止判定（`chain === target`）」と「戻り値の意味（`pending === null`）」は別物で、1つの式に混ぜると失敗した write を同一 flush 内で5回書き直し、M4 が確定した「再試行は次の flush／タイマー」の意味論を壊す。`trashFile` が `flush()` を使うと、失敗して復元された pending を書き直して**ゴミ箱へ移したファイルをディスク上に作り直す**ので、待ち専用の `settle()`（何も書かずに進行中の write の完了だけを待つ）に分けてある。**`settle()` を `flush()` に戻さないこと**
- **取り込みは `selectFile` に合流させる（`applyEdit` ではない）**: M3 の申し送りは「取り込みは `applyEdit` の4本目の経路になる」と予告していたが、`applyEdit` は「自動保存へ渡す」＋「履歴に record」なので取り込みには合わない（ディスクから読んだ内容を書き戻し、履歴も破棄でなく追加になる）。M1 で確定した「ファイル選択時は必ずディスクから読み直す」経路が、読み直し・`computeIssues`・saver の張り直し・`createHistory`（＝**Undo 履歴の破棄そのもの**）を1本で揃える。**`applyEdit` の4本目になったのは二択ダイアログの「自分の編集で上書き」側**
- **退避（「取り込み前に戻す」）は生バイトをそのまま書き戻す**: 編集データを再シリアライズすると、非正規形のまま開いていたファイルで全行 diff が出る（rev 5章が壊れる）。生バイトなら `git diff` が空に戻り、取り込みでファイルが `rejected` になった場合も同じ経路で戻せる
- **外部変更を検知した時点で、選択中ファイルの自動保存を止める**（`dispose()`）: 取り込むか上書きするかを決める前にディスクが動くと判断の前提が壊れる。再開は確定時（取り込み＝`selectFile` が張り直す／上書き＝`attachSaver` に**検知したディスクの内容を baseline として**張り直す。古い baseline のままだと同内容判定で「書かない」に落ちて外部の内容が残る）
- **回答待ちの二択は `pendingAskRef` に `{ path, module }` で持つ**: (1) `ask` の分岐で saver を dispose するので `hasUnsaved()` だけでは「未保存編集あり」の信号が消え、**回答前の2度目の外部変更が `reload` に落ちてユーザーの編集を持つ履歴を置き換える** (2) モジュールを一緒に持つのは、2度目の検知では一覧が既に1度目の適用後（`rejected` になっているかもしれない）を指すため、再導出すると `undefined` になって「自分の編集で上書き」が何も書けなくなるから。**「レンダごとに代入する ref」では変更前の値を凍結できない**（`setFiles` はダイアログの回答を待たずに反映される）ことが実装時に判明した
- **回答待ちの間はウィンドウを閉じさせない**: 検知時に saver を null にするので、`interceptClose` の「saver が無ければ閉じてよい」がそのまま成立してしまい、**二択で守るはずの編集を無言で捨てて閉じる**（M4 までは × が編集を flush する挙動だったので、M5 で意味が反転していた）。`pendingAskRef` が立っている間はトーストで理由を出して閉じない
- **通知トーストには必ず `key` を付ける**（`external:<path>`）: 付けないと、action 付きトースト（「取り込み前に戻す」）が新しい外部変更の通知で置き換わらず、**古い退避テキストで新しい外部変更を無言で潰せる**。`planExternalChange` の `notices` が `{ key, message }[]` を返すのはこのため
- **トーストはモーダルより前面に出し（`z-60`。ダイアログの overlay / content は `z-50`）、モーダル中は表示だけにする**（`src/components/Toast.tsx`）: 実機確認で、二択ダイアログ表示中に出る「選ぶまで閉じられません」の通知が**オーバーレイのぼかしの下に描画されて読めなかった**——閉じられない理由を伝える唯一の手段が、それを出す場面でだけ読めないという壊れ方をしていた（トースト自体は出ていたので、コードを読むだけでは気付けない類）。前面へ出すと今度は操作が押せてしまう（Radix は body の `pointer-events` を切るが、トーストの行が `pointer-events-auto` で復活する）ので、`modalOpen` を受け取って行の `pointer-events` とボタンの `disabled` を切り替える。**回答待ちの二択の裏で古い「取り込み前に戻す」を押せると、二択の前提が崩れる**
- **トーストは時間では消さない。閉じるまで残す**（`src/components/Toast.tsx`）: 当初は操作の無い通知だけ6秒で自動消去していたが、実機確認で「見逃したのか出ていないのか」が区別できず検証を妨げた（上記「実機確認の結果」の罠を参照）。会議中に画面から目を離していれば6秒は確実に見逃す時間で、「外部が仕様ファイルを書き換えた」は見逃してよい出来事ではない——**問題は消せなくして見せる**（rev 5章）を通知にも適用する。溜まり過ぎは `MAX_TOASTS`（3件）と、同じファイルの通知を `key` で置き換える仕組みで抑える。**追い出しでは「押し込んだ通知（末尾）」と「操作付き」を落とさない**（前者は出来事を知らせないまま消えるため、後者は Undo 履歴破棄後の唯一の復元手段のため）
- **監視は `watch` の Cargo feature と `fs:allow-watch` の両方が要る**（`src-tauri/Cargo.toml` / `capabilities/default.json`）: 片方でも欠けると**実行時に静かに動かない**（feature が無ければコマンド自体が存在せず、権限が無ければ ACL 拒否）。パスの scope はダイアログの `allow_directory` がフォルダ自身も許可するので追加不要。`recursive: false`（走査も直下だけ）、プラグイン側デバウンス 300ms ＋ JS 側の束ね 150ms（1回の保存で複数イベントが来るため2枚要る）
- **読めなかったファイルを「消えた」と混ぜない**（`ScanResult.unreadable`）: 一時的なロックで開いているファイルを勝手に閉じてしまう。台帳にも残す（`retain` に渡す）
- **M5 で追加したコアの部品は、2本目のツールでもそのまま使える形にしてある**: `scanFolder`/`toProjectFile`（走査の1本化）、`KnownDisk`（台帳）、`planExternalChange`（判断の純関数）、`createCoalescer`（イベントの束ね）、`modal-queue`（モーダルのキュー。`key` で置き換える）、`toasts`。いずれも Tauri も React も知らない
- **`computeIssues` の呼び出し経路は6本**（フォルダ走査／ファイル選択／編集／作成／削除／外部変更の取り込み）

### M6 で扱うもの

M3・M4 の申し送りの M6 項目（出力ロジックが規約6点セットの最後の空きスロット／種別の日本語ラベルは `src/modules/glossary/kind-labels.ts` を使い回す）は引き続き有効。M5 で新たに積んだものを以下に足す。

- **【M6 の必須タスク。Markdown 出力と並べて計画に入れること】`src/App.tsx` の「副作用の順序」を検証できる形に切り出し、テストを付ける。** scope の実装順の M6 にも同じことを書いた（M6 の計画者が最初に読むのはそちらなので）。

  **なぜ据え置きにしないか**: M5 の最終レビューが見つけた配線バグ6件は**すべて `App.tsx`**（唯一自動テストが無いファイル）にあり、さらに実機確認でしか出ないバグが1件出た。計画の設計決定11で「App のテストハーネスは作らず、コアへの切り出しを進める」と判断したが、切り出せたのは**判断**（`planExternalChange`）であって**順序**（`dispose` → `setFiles` → トースト/ダイアログ → `attachSaver`）ではない。M4 の申し送りの残件「App に配線レベルのテストが1件も無い」を据え置いたのは今回で2回目で、**2マイルストーン連続で同じ層にバグが残った**。3回目を許すと「レビューで拾えばよい」が常態化する。

  **切り出す形**: 注入した io とコールバックで順序を検証できるコントローラ（例: `createExternalChangeController({ scan, read, write, exists, trash }, { onList, onToast, onModal, onSelect, ... })`）。テストで固定したいのは次の順序と条件である——検知時に saver を dispose してから一覧を差し替える／取り込みはディスクを読み直して履歴を作り直す（`applyEdit` を通さない）／外部削除は flush せず dispose する／回答待ちの間は `hasUnsaved` 相当の信号を保持する／削除は「入力を切る → 進行中の write を待つ → ゴミ箱へ移す」の順。**いずれも今は読解でしか担保されていない**（＝完了条件2・6・9・11 が実機確認と読解に依存している理由そのもの）。

  **範囲の線引き**: React の描画までテストしようとしないこと（M3 で確立した DOM テストの方針どおり、DOM テストは「壊れても画面は一見正常」な回帰に絞る）。狙いは副作用の**順序と有無**をコアで固定することで、`App.tsx` に残るのは「コントローラを state に繋ぐ」だけにする
- **モーダルキューに `dropModal(queue, key)` / `clearModals()` を足す**: `openFolder` はキューにも `pendingAskRef` にも触らないので、前のフォルダの二択要求が残ったまま新しい一覧が出る（現状はダイアログのオーバーレイが操作を塞ぐので UI からは到達しにくいが、防御が無い）。`handleSelectedGone` も消えたファイルの二択要求を残す（どちらを押しても no-op か読み込みエラーに退化する）。生産者が4人目になる時点で必ず要る
- **`ioError` の単一スロットの意味論**: 「フォルダの監視を開始できませんでした」は継続する状態なのに、その後の `selectFile` / `openFolder` の `setIoError(null)` で消える（設計決定7の「バナー＝いま続いている状態」に反する）。逆に再走査の失敗バナーは、その後の再走査が成功しても消えない。バナーを状態ごとに分けるか、種別を持たせるかを決める
- **`ensureGlossary` の早期 return が無言**: `handleExternalChange()` が `null` を返す4つの原因のうち、`ioError` が出るのは `scanFolder` の失敗だけ。フォルダ切替中に「用語集を作る」を押すと何も起きない
- **`overwriteWithMine` の `selectedPathRef` 不一致時が無言 return**（モジュール欠落側はバナーを出すので非対称）
- **`askExternalChange` は古い `external:<path>` トーストを消さない**: 同じファイルを以前に取り込んでいた場合、その「取り込み前に戻す」が残ったまま二択が出る（押すと古い退避を書く）。`notices` 側は M5 で key を付けて塞いだが、`ask` の経路は残っている
- **`overwriteWithMine` が `saveError` をクリアしない**（他の経路は消している。新しい saver の `onSuccess` で結果的に消えるが、書く内容が同一だと write が起きず残る）
- **ページのリロードで Rust 側の watcher が leak する**: `projectDir` は state なのでリロードで消え、JS 側は監視を張り直さない（フォルダを開き直すまで）。一方 Rust 側の watcher はリソーステーブルに残り、死んだコールバックへイベントを送り続けて `[TAURI] Couldn't find callback id ...` の警告を出す。開発中の HMR でしか起きない（本番のアプリはリロードしない）が、**検証を著しく混乱させる**ので、リロード後は必ずフォルダを開き直すこと。塞ぐなら、ウィンドウの `beforeunload` で `unwatch()` を呼ぶか、Rust 側で webview ごとの watcher を1つに制限する
- **`sample-project/` はテストの fixture であり、動作確認の遊び場にしてはいけない**: `src/core/canonical.test.ts` の最重要の回帰テスト（バイト一致）が `sample-project/glossary.json` を読んでいる。削除や内容の差し替えで `npm test` が落ちる（M5 の実機確認で2回落とした）。**fixture を専用の場所へ移すか、確認手順を「リポジトリ外の空フォルダ」に固定するかを決めること**（計画の Task 11 には後者を書いた）

### 設計上の限界（受け入れて記録するもの。直そうとしないこと）

計画の「設計上の決定12」で挙げた限界に、実装とレビューで見つかった2件を追記する。

- **取り込みと in-flight write の競合は残る**（計画に既記載）: 外部が書いた直後・監視イベントが届く前にアプリの write が着地すると、外部変更はその時点で既に上書きされており、再走査は自分の内容を読む（差分ゼロで何も起きない）。ファイルロックが無い以上避けられず、二択の「自分の編集で上書き」と同じ結末なので、失われるのは「どちらを残すか選ぶ機会」だけ
- **外部削除と in-flight write の競合でファイルが復活しうる**（新規）: `handleSelectedGone` は `dispose()` するが、既に飛んだ write は止められない。着地すると `writeAndRecord` が台帳も更新するので、次の再走査では `added` として「ファイルが増えました」と通知される（**無言ではない**）。完了条件6の「flush しない」は満たしている
- **台帳の記録が write の解決後なので、遅い FS では誤検知しうる**（新規）: write の IPC 解決が監視のデバウンス（300ms）＋束ね（150ms）より遅れると、再走査が「新しいディスク内容 ≠ 古い台帳」を見る。ただし in-flight なので `hasUnsaved()` が true になり `ask` に倒れるだけで、データ喪失にはならない（上記「`hasUnsaved` が載荷点」の性質）

### いつでもよいが、忘れると実害化する残件

M5 で新たに見つかったもの。**レビューの記録は作業ワークスペースと一緒に消えるので、残すならここに書く**——本節が唯一の恒久的な記録である。

- **`close` の脱出口が `dispose()` の後に `saverRef.current` を null にしない**（`src/App.tsx`。M4 からの既存挙動）: `forceClose()` が失敗した場合のみ到達し、破棄済みの saver を掴んだままアプリが開き続ける（そのとき `ioError` は出ている）
- **`switchingFolderRef` が boolean でカウンタでない**: `openFolder` が2重に走ると先の `finally` が後の切替中にフラグを消す（同時に2つのフォルダ選択ダイアログが必要なので到達は困難）
- **`FLUSH_MAX_ROUNDS` の打ち切りパスに直接テストが無い**（戻り値は安全側の false なので後回し可）
- **`fileExists` に専用の単体テストが無い**（`exists` への1行委譲で、意味のある挙動は `file-ops.test.ts` が押さえている。`moveFileToTrash` と同じ判断）
- **`ChoiceDialog` のオーバーレイクリックのテストが無い**（`onOpenChange` を渡さないことで構造的に担保され、同じ機構を Esc のテストが固定している）
- **選択中でないファイルが外部変更でスキーマ違反になっても「外部の変更を読み込みました」と出る**（赤バッジは出るので致命的ではない）

M2〜M4 の申し送りからの継続（M5 では手を付けていない）: **編集1打鍵ごとに全ファイルの `checkConsistency` を再実行している**／**定義セル・種別セルが `mark(index, field)` を参照していない**／**`@testing-library/user-event` が未使用**／**`resolveCommand` の細かい非対称**（macOS の `Ctrl+Backspace` / `Alt+Shift+↑↓`）／**`CellInput` の `caretAtStart` / `caretAtEnd` は collapsed なキャレットのみ true**／**`file-naming.ts` の `ILLEGAL` が Windows の予約デバイス名を弾かない**（ユーザー入力が届く経路は M5 でも増えていない）／**`FileList` の行ボタンのアクセシブル名が固定**（`aria-describedby` で補うのが筋）／**`ConfirmDialog.dom.test.tsx` が見出しを `getByText` で引いている**（新設した `ChoiceDialog.dom.test.tsx` は最初から `getByRole('heading')` で書いた）／**`move_to_trash` が同期コマンドなので削除中にウィンドウが固まる**

### 実装計画そのものに含まれていた誤り（次回の計画立案への教訓）

計画（`docs/superpowers/plans/2026-08-07-m5-external-change-detection.md`）は M3・M4 の申し送りの教訓（**計画のコードは検証済みの正ではなく、レビューを通す前提の下書きとして扱う**）を明記した上で書いたが、それでも次の7件が実装・レビューの段で出た。**M3・M4 と同じ形の再現であり、「完全なコードを載せる」ことの限界がもう疑う余地なく示された**と考えるべきである。

1. **`flush()` のループ条件が2つの意味を混ぜていた**（Task 1。`pending === null && chain === target`）: 「静止したか」と「書き残しがあるか」を1つの式にしたため、恒久的な書き込み失敗で同一 flush 内5回リトライになり、M4 が確定した意味論を変えた。**既存テスト（`onError` は1回）が壊れて発覚**——実装者はテストを実装に合わせて書き換えたが、正しい対応は「実装の条件を直してテストの期待値を戻す」だった（コントローラが裁定）
2. **`selectedModuleRef` で「変更前のモジュール」を凍結しようとしていた**（Task 8。Critical）: レンダごとに代入する ref では、`setFiles` がダイアログの回答を待たずに反映されるため凍結できない。**ref という道具の選択自体が誤り**で、正解は「判断に使う値を、判断を起動する関数の中で引いて引数で渡す」だった
3. **`ask` の分岐で saver を dispose すると `hasUnsaved()` の信号が消えることを見落としていた**（Task 8。Critical）: 計画は「検知時に自動保存を止める」と「未保存編集ありなら二択」を別々に正しく設計していたが、**その2つが同じ状態変数を共有していることに気付いていなかった**
4. **`revertImport` が「いま開いているファイル」の saver を無条件に dispose していた**（最終レビュー。Critical）: 計画は「取り込み後の内容を書きに行かせない」意図だけを書き、**action 付きトーストが自動で消えない＝別のファイルを開いた後に押されうる**という自分で決めた仕様との相互作用を追っていなかった
5. **二択ダイアログ中のウィンドウ × を考慮していなかった**（最終レビュー）: 「Esc でもオーバーレイでも閉じない」と決めたのに、OS のタイトルバーが最も押しやすい「編集を捨てる」経路として残っていた。**モーダルの閉じ方を列挙するとき、アプリの外側の閉じ方を数え落とした**
6. **`notices` に `key` を付けていなかった**（最終レビュー）: 「同じ key の通知は置き換える」機構を作った当人が、選択中ファイル以外の通知だけキー無しにしていた
7. **テスト件数の記述ミス**（Task 2。「PASS（9件）」に対し実際は7件）と**未使用 import の指示**（Task 3 の `type ScanResult`。`noUnusedLocals` でビルドエラー）。どちらも実装者が「計画の矛盾」として報告し、辻褄合わせをしなかった——**これが正しい対応**であり、計画にその指示を明記しておいたことは機能した

**次回への具体的な処方**（M6 の計画立案時に適用すること）:

- **状態変数の「共有」を計画時に列挙する**: 誤り3は「dispose が hasUnsaved を壊す」という**1つの状態を2つの機構が使っている**ことの見落としだった。計画に「この状態を読むのは誰か／変えるのは誰か」の表を1つ入れる
- **`ref` で「過去の値を保持する」設計を書いたら、それが本当に凍結されるかを確認する**（誤り2）。レンダごとに代入する ref は「最新値の読み取り口」であって「スナップショット」ではない
- **非モーダルな UI 要素（トースト）の寿命と、それを押せる文脈を計画に書く**（誤り4）。「自動で消えない」と決めた時点で「いつ・どの状態で押されうるか」が仕様になる
- **`src/App.tsx` に配線が増えるタスクでは、計画時点で「この順序を固定するテストをどう書くか」を決める**（上記 M6 の最重要項目）
