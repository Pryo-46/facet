## 何を作ったか

- **見送りの別枠集計。** `derive.ts` に `deferredIssueCount(issues)`（見送りを掲げた課題自身の数。配下の抑制は数えない。入れ子の見送りもそれぞれ1と数える）・`deferralLine(count)`（`見送り N`）・`DEFERRAL_NOTE`（`見送り配下の問いは要対応に数えません`）を追加した。**要対応から外す側（`poseQuestions` が抑制配下では問いを立てない）は既に実装済みだった**——M25 が足したのは「存在は消さない」別枠の側だけである。帯には `MissingTally` の隣にグレーのチップ（`badgeClass('deferred')`＋`StickyNoteOff`）が並び、0件では描かない。押すと `nextDeferredTarget`（`listDeferredTargets` を巡回）で見送りを掲げた課題の箱へ視点が飛ぶ。同梱 Skill（`issue-tree-write.mjs --check`）の報告も同じ `見送り N` の行と `DEFERRAL_NOTE` を出す。
- **帯の `⚠` をアイコン化した。** `MissingTally` の絵文字 `⚠` を `CircleAlert`（lucide、`size-4`・`text-missing`）に差し替えた。**端末に出す `tallyLine`（Skill の報告・`derive.ts` の関数）は `⚠` のまま**——SVG は端末に出せないため、画面と端末で表現が分岐した。
- **U4（破線エッジの意味）を文書として決着させた。** 実装（`IssueTreeEdges.tsx` の `SUPPRESSED_DASH`）は変更していない——課題ツリーのエッジはすべて親子関係で、破線は「祖先の見送りで抑制された配下へ入る線」だけに付き、見送りを掲げた当の箱へ入る線は実線のままという既存の挙動を、UI ノート・rev 9章・`missing-semantics.md` に書き起こした。
- **ネイティブ `<select>` の置換。** `src/components/CellSelect.tsx` を新設し、用語集の種別列・エラーカタログの対応レベル列に配線した。開閉は既存の `DropdownMenu`（Radix）——課題ツリーの判断ピッカー（`KindMenu`）と同じ土台。**キーボード契約はネイティブ select の挙動を維持する**——素の ↑↓ は部品が消費して値を切り替え（端で止まる。循環しない）、Space・クリックで開き、Enter は開かずセルの操作言語（`onCellKeyDown`）へ渡す。Alt+↑↓・Tab は素通り。
- **角丸を2段＋円に統一した。** `rounded-sm`（6px。部品・セル・チップ・バッジ・ボタン）／`rounded-md`（8px。浮遊面＝メニュー・ダイアログ）／`rounded-full`（意図した円）の3語（＋方向付き）だけを許可し、裸の `rounded`（4px。倍率制の外）・任意値・他の段は `src/styles/conventions.test.ts` の許可リスト検査が弾く。**この検査だけは shadcn の生成物（`src/components/ui/`）も走査対象に含む**——段・行間の検査が `ui/` を除外する理由（タイポグラフィの規約は自作コードに課す）は角丸には当てはまらない。角丸は M25 で `ui/` を意図して改造したので、将来 shadcn を更新したときに `rounded-lg` が黙って戻るのをこの検査が捕まえる。**基準値（`--radius: 0.625rem` と倍率）そのものは動かしていない**——揃えるのが M25 の仕事で、基準の吟味はダークの吟味と同じく実機確認へ持ち越した。
- **文書。** [`../facet-UI設計ノート.md`](../facet-UI設計ノート.md) の U4・D17・D18 に決着の追記小節を置き、§5 未確認事項と §8 の実施状況・着手条件を書き換えた。[`../missing-semantics.md`](../missing-semantics.md) 規約4 に見送りの別枠の2項と、帯の表現が `CircleAlert` になったことを足した。[`../overview-rev.md`](../overview-rev.md) 9章に、見送りの集計が要対応と別枠であることと、角丸2段＋円の規約を追記した。[`../open-issues.md`](../open-issues.md) は「デザイン」の F の項を消し、「次に手を付ける候補」へ M25 の実機確認未実施を7件目として足した。[`../README.md`](../README.md) の地図は UI ノートの行を「残るは D の高さ・E」に書き換え、マイルストーン表に M25 の行を足した。

## 実装で確定した事項

計画との差分3件（すべて着手前スキャンで実装が既に答えを持っていた、または実装中のレビューで裁定した事項）。

### (1) 「端で止まる」テストが正のアサーションを欠いていた——レビューで指摘され、直した

Task 6 Step 1 が計画に逐語で書いたテスト（`CellSelect.dom.test.tsx` の「端で止まる」）は、当初 `expect(onPick).not.toHaveBeenCalled()` **単独**に依存していた。これは `docs/lessons-for-planning.md` が既に名指ししている既知の穴と同型——`not.toHaveBeenCalled()` は「何も起きなかったこと」しか見ないので、部品が壊れて `onPick` 以外の何かを壊しても、あるいはテストの前提（初期値）が崩れても、緑のまま通り得る。**最終ブランチレビューでこの穴が指摘され、正のアサーション（`trigger.textContent` が動いていないことの確認）と、両端（先頭・末尾）の検証に直した**（`e8e39b8`）。計画のブリーフが逐語で命じたコードに対し、教訓（スペック側の既知の穴）を勝たせた裁定である。

### (2) Radix の `defaultPrevented` フォールバックは不要だった

計画 Task 6 Step 3 は「素の ↓ でメニューが開かない」テストが落ちた場合の代替実装（`onKeyDownCapture` ＋ `stopPropagation()` で強制的に食わせる形）を用意していた——**Radix が `defaultPrevented` を無視する版だった場合の保険**である。実装では `preventDefault()` だけで期待どおり動き、この保険は使わずに済んだ。設計スペックの前提（Radix はユーザーの `onKeyDown` を先に呼び、`defaultPrevented` を尊重する）がそのまま成立した。

### (3) select セルの Enter が「行追加」に解決されることを実測で確認した

Task 1 の着手前スキャン（計画の確認事項6）で、`GlossaryEditor.tsx` / `ErrorCatalogEditor.tsx` の `resolveCommand` が select セルの context（`editing: false` ほか）で Enter をどう解決するか実物を読んだ。**Enter は行追加に解決される**——ネイティブ select が Windows で Enter で開かないのと同じ形で、`CellSelect` が Enter を Radix の「開く」既定に食わせず親（セルの操作言語）へ渡す設計がそのまま効く。Space が操作言語側で別の意味を持っていないことも確認済みで、計画の前提と矛盾は無かった。

## 直さずに残したもの

このマイルストーンの中では直さないと決めたもの。台帳（[`../open-issues.md`](../open-issues.md)）にも新しい項は起こしていない——F の決着で1件消し、実機確認の未実施を1件足しただけである。

- **見送り配下の凍結中の問いの内訳・総数は出さない。** 確定仕様（UI ノート D17）が書いていた `見送り 1（未決 2件）` のような内訳表示は、**人間の裁定で実装していない**——別枠は「誰が何を落としたか」の件数だけの台帳であり、出す画面が無い。必要になれば `poseQuestions` を抑制なしで回す形で足せる。
- **角丸の基準値そのもの（6px / 8px）は吟味していない。** M25 の仕事は「揃える」であって「基準の吟味」ではなく、吟味はダークモードの吟味と同じく実機確認へ持ち越した。
- **`sm` と `md` の使い分け（部品か浮遊面か）は機械では判定できない。** 許可リスト検査が守るのは「3語（＋方向付き）以外が現れないこと」だけで、使い分けの当否はレビューと実機が守る。

## 実機確認の先行所見——シーケンスの集計の帯をツールバー行へ移した（2026-08-25）

マージ前に人間が一度画面を見て、計画外修正が1件入った（M23 の「実機確認の先行所見」と同じ扱い。下のチェックリストの一巡そのものではない）。

- **人間の言葉**: 「シーケンスの要対応たちがシーケンス図の要素の一部になっちゃってます」
- **症状**: シーケンスの集計の帯（`⚠ 要対応 N` ＋チップ＋`回答済 N ／ 考慮不要 N`）は M22 以来**キャンバスの transform 層の中**（ガターの x・参加者ヘッダの高さ）にあり、チップ（破線黄・淡い面・`rounded-sm`）が**空の参加者ボックスと同じ高さ・同じ角丸・同じ破線黄**で横に並んで、図の要素として読めてしまう。**配置そのものは design-notes 論点7 の確定設計であって M25 の退行ではない**——ただし M21 の淡い面と **M25 の角丸統一（チップと参加者ボックスが同じ 6px になった）・`⚠` 絵文字の廃止（UI 側の異物という手がかりが減った）**が、もともとあった混同の余地を実害に変えた。
- **対処（人間の裁定）**: 帯を**ツールバー行**（「＋参加者を追加」と操作ヒントの間。キャンバスの transform の外）へ移した。検討して採らなかった代案は「位置はそのままに不透明の面（`bg-surface`）を敷いて UI に見せる」——論点7 の根拠（ズームアウト時に集計が凡例として一緒に縮む）を守れるが、人間はツールバー行を選んだ。これで**5モジュールの帯の置き場が揃った**（課題ツリーと同じ配置）。
- **反転したのは集計の帯の位置だけ**である——ガターのスロット列はキャンバス内のまま（論点7 の根拠1・2 は生きている）。design-notes 論点7 に反転の追記を置いた。
- テストは1件も落ちなかった（帯のテストは role とアクセシブル名で引いており、位置に依存しない——DOM テストの設計方針どおり）。
