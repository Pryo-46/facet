## 実装で確定した事項

- **原本の同梱方式をスペックから変更した。** スペック設計2は「原本はアプリの resources に同梱（Skill 群と同じ場所）」としていたが、実装は **Vite の `?raw` import でバンドルへ取り込む**方式に変えた（`src/core/reading-guide.ts` が `src/core/reading-guide.md` を `import guideText from './reading-guide.md?raw'` で読む）。理由: ガイドは単一のテキストファイルで、Skill 群のような「ディレクトリを再帰的に集めて置き直す」機構が不要であり、`tauri.conf.json` の `bundle.resources` と定数の二重管理（`BUNDLED_SKILLS` が抱える「一致していなければならない」制約）を増やさないため。スペックの意図（原本が同じリポジトリでバージョン管理され、アプリが書き出す）は維持している。
- **同期ロジックは3分岐**（`src/core/reading-guide.ts` の `syncReadingGuide`）: ファイルが無ければ書く／原本とバイト一致すれば**何もしない（mtime も変えない）**／不一致（旧版・ユーザー編集）なら原本で上書きする。判定は「原本とプロジェクト内ファイルのバイト一致」で、フォルダ watcher の再走査や Git のノイズを毎回の起動で増やさないための設計。
- **アプリはこのファイルを書くだけで読まない。** 「Claude の出力を読んで何かを決める」実装を作らない、という M11 決定1の原則と同じ線を踏襲している。アプリの走査は `.json` しか一覧しない（`src/fs/project-fs.ts`）ため、ガイドがファイル一覧や外部変更検知に現れることもない。
- **書き出し契機はフォルダを開いたとき。** Skill 同期（`syncBundledSkills`）が端末起動を契機にするのに対し、ガイドは実装リポジトリ同居のユースケースで facet の端末を経由せず外部の Claude Code から読まれるため、端末起動を契機にできない。`App.tsx` は `controller.openFolder` 成功後にガイドを同期する `openProject` ヘルパを新設し、既存2箇所（`switchFolder` 内／`openFolder` の非確認分岐）の `controller.openFolder` 直接呼び出しをこのヘルパに集約した。ガイドを書けなくても開くこと自体は成立させる（Skill 同期と同じ姿勢。トーストで通知するだけで失敗させない）。
- **`App.dom.test.tsx` では `userEvent` の代わりに既存テストと同じ `fireEvent` を使った。** `userEvent` は依存に無く、計画のテスト雛形をそのまま貼ると通らないため、実装者が既存テストの作法に合わせて調整した（計画が明示的に許可した調整）。

### 素読みで実際に起きた読み違い（ガイドが直したもの）

1. **フォルダの性格の誤認**（q1）: 仕様の正であることを読み取れず「サンプル置き場」と推測 → 冒頭宣言が直した
2. **シーケンスの問い導出の誤解**（q4・q5）: `failures` を開いた列挙と見なし、`unknown` / `ifExecuted` という固定スロットの存在を知らないまま「timeout エントリ追加」を提案 → ツール別セクション（シーケンス）が直した
3. **エラーカタログの空欄規約の誤解**（q7）: resolutionLevel と連動した「書く必要がないので空」を「未決かも」と誤読 → ツール別セクション（エラーカタログ）が直した
4. **未決を埋めにいく振る舞い**（q4）: 「追記しましょうか？」と提案 → ガイドありは「私の提案であって仕様ではない」と一線を引いた

### 剪定の判断

**削った記述: なし。** 判断基準はスペック（設計3）の二重基準——各記述は「実際に起きた読み違い」か「起きたら発見が遅れる読み違い」のどちらかに対応していること。

- 実際の読み違いに対応: 冒頭宣言／シーケンスの問い導出／エラーカタログの空欄規約／「未決を埋めない」
- 今回の質問では発火しなかったが「起きたら静かに壊れる」系として存置: 単一性（複数ファイルの黙ったマージ）／ID捏造禁止／aliases 照合／「書き込みたくなったら」（Skill 経由の誘導）
- logicTree セクション: 実験対象外（ファイル無し）だが、スペック設計1「存在しないツールのセクションも消さない」により存置

**計画 Task 4 Step 3 の文言「素読みが全問読み違えなかった規約の記述を削る」を字義通り適用すると、未検証の静かに壊れる系（単一性・ID捏造等）まで削ることになり、スペックの二重基準と矛盾する。** スペックを正として二重基準で判断した（計画はスペックから導出された下書きであり、字義と元のスペックが食い違う場合はスペックを優先する）。

### 発見: ガイドの発見性の限界（q2）

ガイドは**AI がフォルダを読みに行った場合にだけ**効く。q2「『応募者』とはどういう意味？」のようにプロジェクト固有に聞こえない質問では、AI はファイルを一切読まずに一般知識で答えるため、ガイドの有無に関係なく用語集に到達しない。文面の改善では直らない（読まれないファイルはどう書いても読まれない）。

スペックの受け入れ基準2「ガイドありで読み違いが消えること」は q2 についてだけ未達。**人間の裁定でこの限界は「限界として記録」に確定した**（`docs/open-issues.md` へ追加）。対応候補として facet がユーザーのプロジェクトの `CLAUDE.md` にも誘導を書く案が挙がったが、ユーザーのファイルを触る侵襲性があるため、今回は実装せず将来の検討候補として記録のみ残す。
