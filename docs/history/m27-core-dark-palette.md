## 確定した事項

- **動かした値は2つだけ**: `--invalid-face` L 0.30 → **0.28**（`invalid` on face 4.52 → 4.83。唯一の MARGIN 割れの解消）、`--judge-yes` C 0.10 → **0.08**（P型の `missing` との ΔE 0.101 → 0.107。閾値ちょうどの解消）。他 16 個は**吟味のうえ据え置き**（根拠は D20）
- **P型 ΔE 0.101 は計画の着手前スキャンでの新発見**——open-issues には `invalid` on `invalid-face` の 4.52 しか載っていなかった。閾値ちょうどの脆さは MARGIN（コントラスト側）だけでなく `DISTINCT_MIN`（色差側）にもあった
- **ダークでは意味色4軸が全部「明るい色」側に集まる**（D20 の知見）。`judge-yes` の L を下げる余地は彩度との交換でしか得られず（C 0.07 以下に薄めても canvas 比は 9:1 止まり——D20）、「浮きすぎ」の将来調整は識別・彩度との綱引きになる
- 検算は `contrast.ts` の既存の道具だけで行い、新しいコードは足していない。契約（`palette-requirements.ts`）に MARGIN をテストとして課すことも見送った——テストは配色の差し替え（palette-retheme）にも使われ、外部テーマに 1.03 の余裕まで課すと選べる値が消える

## 実機確認の一巡目（2026-08-26）——面の序列を作り直し、`rule-muted` を分離した

**マージ前に、人間が Windows 実機（ダーク・課題ツリーと用語集）で一巡した。** 上の本文の「動かした値は2つだけ」は机上吟味の時点の記録であり、追記専用の原則どおり書き換えていない。以下がその続きである。

### 出たこと

1. **無彩色の面の序列が反転していた。** ライトは muted（0.91）< canvas（0.95）< surface（0.985）の輝度順（沈んだ面 < 地 < 作業面）だが、ダークは canvas < surface < muted で、**凍結を示す見送りの箱が3面で最も浮いて見えた**（人間の言葉:「見送りのほうが白くて直感的じゃない」）。机上吟味は無彩色3面に「構図の翻訳」を適用しておらず、これは実機でしか出ない類の欠陥だった
2. **`surface` を上げたら表の罫線が消えた。** 罫線（当時 `border-grid`）が面と同明度（1.03:1）になった。ダークでは canvas と surface が線を挟むため、**方眼（canvas 上）と罫線（surface 上）は1値で両立しない**

### 決めたこと

- **ダークの面もライトと同じ輝度順にする**: `surface` 0.205 → **0.24**、`surface-muted` 0.27 → **0.13**（地より暗い側へ）
- **`rule-muted` を19個目のトークンとして分離**（表の罫線・弱い境界。`border-grid` の使用6箇所——用語集・エラーカタログの行と列・ファイル一覧の行・別名バッジの枠——をすべて移した。方眼だけが `grid` に残る）。ダーク **0.40**（surface 上 1.79:1）、ライトは `grid` と同値 **0.89**（ライトの見た目は変えない）。要件は課さない（`grid` と同じ装飾扱い。`palette-requirements.ts` の `TOKENS` / `ACHROMATIC` に追加）
- **`grid` は方眼専任として 0.20 へ**（canvas 上 1.06:1。0.28・0.33 も実機で試し、罫線と分離した後は薄い方を人間が選んだ）
- 変更後も契約のコントラスト33検査は MARGIN 込みで全緑（沈む方向・浮く方向とも要件に余裕があった）
