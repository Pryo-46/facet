## 何を作ったか

- **IBM Plex 3書体の同梱。** `@fontsource-variable/ibm-plex-sans`（可変 wght）／`@fontsource/ibm-plex-sans-jp`（static 400/500/600。**JP に variable 版は npm に存在しない**）／`@fontsource/ibm-plex-mono`（static 400/700。700 は端末の ANSI 太字用）を npm 依存で入れた。**Tauri の `resources` には置いていない**——`@font-face` の `url()` が dist の資産を指せば実行形へ入るので、実行時のパス解決が要らない。
- **woff2 だけを参照する生成 CSS。** `scripts/gen-fonts-css.mjs` が fontsource の CSS から woff（旧形式）の参照を落とし、`url()` をリポジトリ相対に書き換えて `src/styles/fonts.css` を作る。**素の `@import` をすると woff まで dist に入る**（static 版の CSS は両参照。JP だけで数MB）。**`fonts.css` は生成物だがコミットする**——直に編集せず、fontsource の版を上げたら `node scripts/gen-fonts-css.mjs` で作り直す。`src/styles/fonts.test.ts` の3本（woff2 以外の参照が無い／3書体と必要ウェイトが揃っている／**参照している woff2 がすべて `node_modules` に実在する**）が形と参照先を固定し、版上げでファイル名が変わったときの番人になる。
- **woff2 の data URI 化の停止。** `vite.config.ts` の `assetsInlineLimit` を `.woff2` にだけ `false` にした。JP のスライスには 4KB を割るものがあり、Vite の既定（4096）だと CSS 内の `data:` URI になる——**`src-tauri/tauri.conf.json` の CSP は `font-src 'self'` で `data:` を許していない**ので、そのスライスだけが静かにブロックされ珍しい漢字が豆腐になる。**CSP を緩める側ではなく、インライン化を止める側で塞いだ。**
- **トークンの差し替え。** `--font-sans` は `'IBM Plex Sans Variable', 'IBM Plex Sans JP', 'Yu Gothic UI', 'Hiragino Sans', sans-serif`、`--font-mono` は `'IBM Plex Mono', ui-monospace, 'Cascadia Mono', Consolas, monospace`。**フォールバック列は残した**——同梱が届かなかったときに MS UI Gothic まで落ちないための保険で、正常時は使われない。
- **端末（xterm）への Plex Mono の配線。** `document.fonts.load` で通常と太字の両方を明示的に読み込み、**その完了後に** `--font-mono` を `getComputedStyle` から読んで `term.options.fontFamily` に入れて `fit()` する。**`document.fonts.ready` では足りない**——「使われたフォント」しか待たず、その時点で Plex Mono はまだ1文字も描かれていない。トークンが読めなければ何も入れず xterm の既定のまま（`theme.ts` の「半端に流し込まない」と同じ判断）。
- **遅延スライスの到着で測り直す仕組み。** `src/core/canvas/use-font-generation.ts` の `useFontGeneration()` を新設し、`document.fonts.ready` と **`loadingdone`（遅延スライスの到着）**の2つを「世代」として数えて測定器の鍵に混ぜる。**フォントの同一性では測り直しを起こせない**——`getComputedStyle` が返すのは宣言されたファミリ**列**だけで、どのフェイスに解決されたかは映らないため。キャンバス3本（`LogicTreeEditor` / `SequenceEditor` / `IssueTreeEditor`）をこのフックに**一本化**し、テーブルの `CellInput` も同じ契機（`loadingdone`）で行数を測り直すようにした。
- **Geist の除去と `font-bold` → 600。** `src/index.css` の Geist の `@import` を消し、唯一の `font-bold`（`App.tsx` の「ファイルが開けない」見出し）を `font-semibold`（600）に落とした。**1箇所のために Mono 以外でもう1段（700）を積まない**（UI ノート §4.3 への答え）。`THIRD-PARTY-NOTICES.md` のフォントの表も3書体へ差し替えた。
- **実験ページ。** `font-probe.html`（dev サーバのルート直下）。可変ウェイトの描き分け（`wght` 400/450/500/600 の字幅）・遅延スライスの測定影響（`RARE` の幅の before/after と `loadingdone`）・`--font-mono` の実行時到達を1枚で測る。**実装の一部ではなく、前提を実測するための道具である。**
- **文書。** UI ノートの D6・D7・D8 に M26 の追記小節、§7 の U1 に数値の訂正、U2・U3 に決着の小節を置き、§8 の実施状況と着手条件を書き換えた。rev 9章は**書体の項を全面改訂**（Geist の反転・同梱の作法4点）し、ウェイトの項の E 待ちの予約を解消し、測定層の項に `loadingdone` を、端末の項にフォントの流し込みを足した。`docs/glossary/scope.md` の M7 節に反転の訂正注記、`docs/README.md` は地図の UI ノートの行とマイルストーン表を更新した。

## 実装で確定した事項

計画との差分3件。**うち2件はレビューが検出した計画の誤りである。**

### (1) 計画の端末コード断片に hidden ガードが欠けていた

計画 Task 2 が逐語で書いた端末のフォント読み込みコードは、`fonts.load` の完了後に無条件で `term.options.fontFamily` を代入して `fit.fit()` を呼ぶ形だった。**隠れたタブ（`display: none` で 0×0）でこれをすると、0×0 の寸法で測ってしまい、開き直したときに表示が崩れる。**

**同じファイル（`src/components/TerminalTab.tsx`）は、既に2箇所でこのパターンを守っていた**——可視化時に `fit()` をやり直す effect が、まさにこの理由で存在する。計画の断片は、**そのファイルが既に守っている不変条件を単体では正しく見える形で破っていた。**

直したのは `b806ae7`: 見えていれば即適用、隠れていれば `pendingFontRef` に覚えて**可視化時の既存経路**で適用＋`fit()`。「`fontFamily` だけ先に代入する」形も採らなかった——次に `fit()` が呼ばれるまでの間、実際に使っているフォントと違う寸法のまま表示される隙ができる。

**この件は一般化して [`../lessons-for-planning.md`](../lessons-for-planning.md) の「大原則」に足した。**

### (2) 計画の「`CellInput` の行数変化は jsdom で観測できない」は誤りだった

計画 Task 5 は `CellInput` の遅延追従について「jsdom では行数の変化を観測できないので番人は立てない」と書いていた。**レビューが実物を確かめて誤りと判定した**——同ファイルの `autoSize` を検査している既存の節が、`scrollHeight` のスタブと `lineHeight` の差し込みで**まさにその観測をしている**。同じ差し込みを使えば `loadingdone` での行数変化も観測できる。

`3cf1a4a` で「`loadingdone` で rows が 5 → 7 になる」という番人を立てた。

**これは新しい教訓ではなく、既存の教訓（「すべての分岐にテストを書けるわけではない」の裏——書けないと判断したら**なぜ**書けないかを確かめて記録する）を計画自身が踏んだ形である。** だから `lessons-for-planning.md` に新しい規則は足していない。「テストできない」は、確かめずに書くと**番人を1つ黙って落とす**。

### (3) 数え違いの訂正2件——U1 が書いた分割数とサイズが過大だった

**決定（案A ＝ IBM Plex 全面移行）は変わらない。記録の精密化である。**

- **「unicode-range の 124分割」は誤りで、正しくは 123分割／ウェイト。** 124 は `node_modules/@fontsource/ibm-plex-sans-jp/files/` の**ファイル数**を数えたもので、**CSS から一度も参照されない一体型の `japanese-*-normal.woff2` を1本余計に含んでいた**（実装者が実物で検出。計画の訂正コミット `d4b076b`）。
- **同じ理由で「JP 約6.8MB」「配布サイズ増は合計約8.2MB」も過大だった。** 実測は次のとおり。

### 実測サイズ（前提③）

`npx vite build` 後の `dist/assets`:

- **`.woff` が 0本**（生成 CSS が woff の参照を落としている）
- **`.woff2` が 385本・計 4.41MB**——JP 369本 4.16MB（**123分割 × 3ウェイト**）／Sans 可変 6本 0.15MB／Mono 10本 0.10MB
- CSS に `data:font` / `data:application/octet-stream` の埋め込みが **0件**
- **`--font-mono` は生成 CSS に現れる**（`--font-mono:"IBM Plex Mono", ui-monospace, …`）。**計画 Task 2 が用意していた「トークンが落ちていたら `:root` で上書きする」という保険は不要だった**——`@theme inline` からそのまま出力に載っている。実行時に読めるかの最終確認は実機（前提④）
- **NSIS インストーラは 8.19MB**。同梱前のベースライン 3.67MB に対し **+4.52MB** で、woff2 の合計とほぼ整合する（計測は Geist 除去前に行ったので約 0.07MB 過大）
- `npm run tauri build` は**バンドル生成まで成功し、最後のアップデータ署名ステップだけ exit 1** になった（`TAURI_SIGNING_PRIVATE_KEY` がこの環境に無い。フォントとは無関係の既知の環境差で、インストーラ本体は署名の手前で生成済み）

**U1 記載の 8.2MB との差（約 3.8MB）の内訳は、上の数え違い（一体型ファイルを含めた見積もり）と、JP の実スライスが見込みより小さかったことの両方である。** 差の全額を分解してはいない——**実測値をそのまま記録し、辻褄を合わせていない。**

### CSP × インライン化の罠

**この欠陥は静的検査を1つも通らない。** `npm test` も `tsc` も `lint` も緑のまま、**本番ビルドでだけ、珍しい漢字を含むスライスが1本だけ静かにブロックされる**（コンソールに CSP 違反は出るが、症状は「一部の字が豆腐になる」という、フォント選定の失敗にしか見えない形で出る）。計画が着手前にこれを見越して `assetsInlineLimit` の指定を用意していたのが効いた。**「設定で塞げるのは、その設定が届く範囲だけ」の系統**——CSP を緩める側で塞ぐと、`data:` を許した CSP が以後ずっと残る。

## 実機確認の先行所見——入力値を一段下げて 14px にした（2026-08-26）

マージ前に人間が画面を見て、計画外修正が1件入った（M23・M25 の「実機確認の先行所見」と同じ扱い）。**下のチェックリストの一巡そのものとは別の一見である。**

- **人間の言葉**: 「フォント大きく見えるな？ウェイトは変えてないんでしょ？1段くらい下げるのありだな。カラム名とかボタンとかバッジのフォントサイズはそのままでいんだけど、入力値だけ小さくしたいよな。試しに一段下げてみる？」——試行を見て「OK」（採用）。
- **症状**: IBM Plex は**仮想ボディに対する字面（じづら）の比率が Yu Gothic UI より大きい**ため、`font-size` を1つも変えていないのに体感サイズが上がった。ウェイトは M26 で変えていない（`font-bold` → `font-semibold` の1箇所を除く）ので、太さのせいではない。**UI ノート D7 が「同じ指定サイズでも Noto Sans JP / IBM Plex Sans JP なら明確に大きく見えるため、フォント差し替えだけでサイズ指定を変えずに体感サイズが上がる」と予告していたことの、逆向きの帰結である**——D7 は「小さく見えるのが直る」利点として書いていたが、実機では上がりすぎた。
- **対処（人間の裁定）**: **入力値（データの文字）だけを一段下げて 14px（`text-sm`）にし、UI ラベル側は 16px のまま据え置いた。** 下げたのは——用語集・エラーカタログの `<table>`／シーケンスの `SEQ_FONT_CLASS`・参加者名・ステップの文言・種別セル・参照セル・答えスロット・`GhostSlot`／ロジックツリーの `NODE_FONT_CLASS` と `NodeBox`／課題ツリーの `BODY_FONT_CLASS`・`TITLE_FONT_CLASS`（`font-semibold` は維持）・`HypothesisRow`。**キャンバスの測定見本（probe）と描画は揃えて変えてある**（rev 9章「測定と描画は同一の情報源を見る」——片方だけ変えると全ノードの寸法が静かに狂う）。据え置いたのは——カラム名（`<th>` は自前の `text-base` を持つので表側を下げても影響を受けない）・ボタン・バッジ・帯・絞り込みの検索欄・ファイル一覧・文書タイトル 22px。
- **下限は割っていない。** 14px は D11 の規約「14px を下限とする」の下限そのもので、ちょうど接している。**「小さくするときは、薄くしない」（D11）も維持**——濃度（`text-ink`）は一切変えておらず、二重減衰は起きていない。行高の比率（複数行 1.5）も据え置いた。
- **テストは1件も落ちなかった**（1801 件すべて緑）。DOM テストは role とアクセシブル名で引いており、jsdom は版組を持たないのでサイズを主張しているテストが無い。**主張が反転して書き直したテストはゼロ件である。**
- **副作用が2つある。** ①**方眼のマス目 24px と複数行段の行高の一致が失われた**（16×1.5＝24 → 14×1.5＝21）。`--grid-size` は動かさない——人間が 21px の行と 24px の升が並ぶ画面を見て問題なしと判定した。②シーケンスの `ANSWER_NOT_APPLICABLE_PREFIX_PAD_X`（`pl-18` ＝ 72px）は「考慮不要」4字×16px＝64px ＋ `left-2` の 8px から導いた値だったが、14px では実幅が 56px になり 8px 余る。**狭すぎて重なる向きの誤りではない**ので値は動かさず、註だけ更新した。
- **反映先は4箇所**——[`../facet-UI設計ノート.md`](../facet-UI設計ノート.md) D11 の「M26 での部分反転」小節、[`../overview-rev.md`](../overview-rev.md) 9章の段の項・方眼の項・セクション見出しの項、`src/index.css` の段の註と `--grid-size` の註、および測定側のコメント（`SequenceEditor.tsx` の `LABEL_FONT_CLASS` は**サイズではなく行間**（1.5 と 1.3）で別測定器である理由へ書き直し、`canvas-font.ts` の `FALLBACK_CANVAS_FONT` は**値 16px を据え置いたまま**「jsdom の導出安定のためで、実ブラウザは `readCanvasFont` が実効値を読む」旨へ更新）。

**D12 の 16px 導出は読み直せる。** `14 × (109 / 96) ≒ 16` の 14px は**字面の小さい書体を前提にした体感**の上に立っていた。書体を字面の大きい Plex へ替えれば、同じ体感に必要な指定サイズは下がる。**計算式そのものは訂正していない**——PPI 補正の論理は正しく、変わったのは入力側の前提である。
