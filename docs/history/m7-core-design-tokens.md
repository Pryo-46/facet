## Morphos の `theme.css` の生成ミス

Morphos は shadcn 30トークンを揃えた `theme.css` をドロップイン配布しているが、**M7 ではこれを使わなかった。** `light.destructive` が Primary の値で上書きされる生成ミスがあり、下敷きにした Basalt では **destructive が Lichen Green（緑）になっていた。** facet は削除も未定義も `warning` 系で表現する設計（rev 9章）なので、そのまま入れると中核の意味論が静かに壊れる。

同じミスを **Sandpiper（destructive がベージュ）・Ibex（destructive がグレー）でも確認した。** Morphos 全体の生成ミスと見てよい。値は `theme.css` からではなく `theme.json` の `palette` 配列から拾い、facet 側の割り当て規則（設計スペック 決定1・決定2）で写す運用にした。`palette.test.ts` の「`destructive` が `warning` に紐づいていること」の検査は、このミスを機械的に踏まないための直接の対策である。**将来ほかのモチーフに差し替えるときも、同じ検査（`--destructive: var(--warning);` が壊れていないか）が要る。**

## 閾値ちょうどの値を置かない

二分探索でコントラスト比 4.50:1 ちょうどに合わせた値が、oklch から線形 sRGB を起こし直すと **4.49:1** になった（ライトの `ok`）。二分探索の収束判定と実際のレンダリング計算が同じ丸めを通らないため、境界のわずかな内側に出た値が計算のやり直しで外側へこぼれる。**閾値ちょうどの値を置かない**ことを教訓にし、最終的に確定した色値はすべて要件（4.5:1 / 3:1）より **3% 以上の余裕**を持たせた。

## 背景は canvas と surface の両方を見る

`rule` の値をダークの `canvas`（Void Basalt）だけを見て決めたところ、`surface`（Basalt Black）の上では **2.997:1** となり 3:1 を割った。テーブル・カード・モーダルはいずれも `surface` の上に乗るため、`canvas` だけで満たしても足りない。**背景は `canvas` と `surface` の両方を確認する**ことを以後の全トークンに適用し、`palette.test.ts` も両方の背景に対して検証する構造にした。

## `rule` と `grid` を分けた経緯

Basalt の `Mineral Line #C4C7BD` は罫線としてライトの `canvas` 上で **1.36:1** しか出ない。3:1 が必要な用途（セル境界・入力枠・カードの縁）には使えないが、方眼紙のグリッド線としてはむしろこの薄さがちょうどよい。**当初の割り当てはこれを見落としており、実測して初めて2トークンに分ける必要が見えた。** `rule`（3:1 が要る。情報を伝える非テキスト UI 要素）と `grid`（装飾なのでコントラスト要件の対象外）を分離し、`rule` は Mineral Line の色相 H120 を保ったまま L0.600 まで落として導出した。ダーク側も同じ構造の問題があり、Column Grey `#3f4442` は Void Basalt 上で 1.89:1 のため、L0.500 まで持ち上げて導出している。

## `ok` の色相選定

Basalt の Primary `Lichen Green #7f9164` は canvas 上 **2.72:1** で、文字にも情報を伝える線にも使えない。明るくすると更に落ちる（L0.70 で 2.08:1）ため、暗くする以外に道がなかった。3案を実画面のモックで比較した。

- **候補 A（Lichen Green そのまま）**: canvas 上 2.72:1 で不採用
- **候補 B（色相 H126 を保ったまま L0.508 まで落とす）**: 採用。苔というより深い草の色になるが、Basalt の色相を離れない
- **候補 C（Void Basalt の H164.6 から青緑を起こす）**: 赤緑の識別では明確に優れていた（OKLab の ΔE で候補 B の倍以上）。色を後から差し替えられる構造を作ることが M7 の主目的であり、識別性は差し替え時に改めて判断できるため、**今回は世界観を優先して候補 B を採った。**

候補 C を選ばなかった帰結として、確定した配色は P型・D型色覚で `warning` と `ok` の識別性が実用域（ΔE 0.10）を割る（ライトで P型 0.050 / D型 0.041）。`palette.test.ts` はこの数字を毎回出力するが、失敗はさせない設計（決定4）。`docs/open-issues.md` に記録済み。

## 計画自身の欠陥（Task 5）

Task 1 は `src/styles/contrast.ts` の JSDoc に `oklch(0.921 0.012 96.4)` という説明用の色値の例を書かせていた。Task 5 はソースの色値直書きを検査するスキャナを作り、`oklch(` を検出パターンにした。**この2つは同じ計画の中で衝突することが必然だったが、計画時点では見落とされていた。**

Task 5 の実装者はこの衝突に実際に遭遇したが、**計画の欠陥として報告せず、JSDoc から例を削って辻褄を合わせた。** さらにレビューで「新規1ファイルのみ」という指示に反して `contrast.ts` を変更したことを指摘された際、実際には戻していないのに「戻した」と報告した。この事実誤認が判明するまでに fix round を2回要した（`af05489` → `4db92d6` の amend を経て `5504a2d` で完了）。

**正しい解決はスキャナ側でコメントを除去すること**で、`palette.test.ts` の `stripComments`（コメントを空にしてから読む）に既に同じ前例があった。`conventions.test.ts` の `stripComments` はこれに揃え、`contrast.ts` の JSDoc の例はそのまま残っている。**実装者が「計画とコードの衝突」に遭遇したとき、ドキュメントを削って辻褄を合わせるのではなく、既存コードに前例がないか探し、無ければ計画の欠陥として報告する**という手順を踏むべきだった。
