### 参照切れの表示を空から「（未解決）」に変えた

ドロップダウン化でセルがボタンになったため、参照が指す参加者が見つからないとき「空のボタン」になってしまう。空のボタンは押す場所が見えないため、Mermaid/Markdown 出力と同じ語「（未解決）」をボタンの表示テキストとして使うことにした。

### 「（未解決）」参加者と確認ダイアログは守る相手が違う

- **「（未解決）」の参加者表示**は、貼られた先（NotePM 等）の**読み手**を守る——空欄や壊れた図ではなく、何が欠けているかが読み取れる形で出力される。
- **整合性エラーがあるファイルを出力しようとしたときの確認ダイアログ**は、**押した本人（操作者）**を守る——気づかずに参照切れのまま出力・コピーしてしまうことを防ぐ。
- 同じ「参照切れ」という事象に対する2つの機構だが、対象読者が違う設計として意図的に両方入れた。

### `readSlot` を export して4本目の複製を作らなかった

出力（Mermaid/Markdown）が答えスロットの値を読む必要があったが、`commands.ts` の非公開関数 `readSlot` を `export` して再利用し、4本目の同型ロジックを増やさなかった。**3本の重複（`readAnswer` / `readSlot` / `consistency.ts` の自前実装）は sequence M2 から解消されずに残っている**（意図的な非対応。今回のスコープではない）。

### `describeIssueEffect` を `ToolModule` ではなく `OutputProfile` に足した

整合性エラーがあるまま出力しようとしたときに「出力に何が起きるか」を1文で述べる関数 `describeIssueEffect` は、`ToolModule` ではなく `OutputProfile`（`src/core/registry.ts`）に足した。ツールごとに複数の出力プロファイルを持てる以上、「出力に何が起きるか」はプロファイル単位で変わりうるため。**任意スロットとして追加し、モジュール規約の点数（7点＋`createEmpty`）は増やしていない**——M9 が規約5を複数プロファイル対応へ拡張したのと同じ層の拡張として扱った。

### `useViewport` の `filter` 修正を logic-tree と sequence の両方に入れた（Task 6）

open-issues に残っていた「モーダルが開いている間もキャンバスのホイール／ドラッグが生きている」（rev 10章の境界規則に対する未達。d3-zoom の `filter` が `enabled` を見ていなかった）を、**logic-tree と sequence の `useViewport.ts` 両方に同じ形で修正を入れて解消した**。これは「キャンバスの土台が2本に複製されている」という**複製規約の遵守**（直すときは両方を直す）であって、**複製そのものの解消ではない**——2本立てたまま同じ差分を両方に適用した。修正後、`git diff --no-index` で両ファイルの差分がヘッダのコメント3〜4行のみであることをレビュアーが独立に確認済み。

## 実機確認で見つかった欠陥と、そこから起きた計画外の作業2本

Task 11（人間による実機確認）で、計画に無い欠陥が1件見つかった。

**発見された欠陥**: 1ステップの from / to / 種別の3つのドロップダウンを**同時に開いたままにできる**。`SequenceEditor.tsx` の `menuOpen` が単一の `boolean` で、全セルの `onOpenChange` が同じ `setMenuOpen` を共有していたため、**3つ開いた状態で1つを閉じると `setMenuOpen(false)` が走り、残り2つが開いたままキャンバスのズーム・パンとキーボード操作言語が復活する**現象を起こしていた。これは Task 6・7 が防ごうとしていた「開いたままズームすると Radix が transform を追わずズレる」状態そのものだった。DOM テストで実害（Escape で1つ閉じた直後の `Ctrl+ホイール` で背景の `transform` が変化する／2つ開いたままラベル欄へ `Enter` を送るとステップが増える）を実証した。

### Task 11a: `menuOpen` のカウンタ化 → 意図の取り違えだった

人間の最初の判断は「(A) カウンタ化だけ今直す」だった。これを受けて `menuOpen: boolean` を `openMenuCount: number` に変え、`nextMenuOpenCount(count, open) = open ? count+1 : Math.max(0, count-1)` という純関数で「1つ閉じても他が開いていればキャンバスを復活させない」形にした（`3801148` → lint 対応で `19b69a3`）。

**しかしこれは人間の意図の取り違えだった。** 実機で観察された「困りごと」は**「複数開けること自体が邪魔」**という意味であり、実装者（およびその前段の判断）はこれを**「複数開いた状態で1つ閉じるとズームが復活する実害」**という別の問題に翻訳してしまっていた。カウンタ化はその翻訳後の問題（ズームの誤復活）は正しく塞いだが、人間が本来困っていた「同時に3つも開けてしまうこと」自体は何も解決していなかった。

### Task 11b: 同時に1つだけ開く構造に巻き戻し

人間が訂正: 「複数開けるのがおかしい（邪魔）。ズームの制御は不要」。これを受けて Task 11a を巻き戻し、`SequenceEditor` に `openCell: string | null` を持たせ、`menuPropsFor` ヘルパで from/to/種別の3箇所に `open={openCell === 該当セル値}` / `onOpenChange` を配る**制御コンポーネント化**に変更した（`5e0cc7a`）。**同時に1つのセルしかドロップダウンが開けない**構造になったことで、複数オープンの実害（ズームの誤復活・キー入力の漏れ）は構造的に発生しなくなった。

- `menu-open-count.ts` / `.test.ts` と Task 11a が追加した `describe` は削除した。
- セル部品（`StepShapeCell.tsx` / `ActorRefCell.tsx`）の `open` prop は optional なので、渡さなければ Radix の非制御モードのまま動く。**`StepShapeCell.dom.test.tsx` / `ActorRefCell.dom.test.tsx` は差分ゼロ**（既存テスト無改変）。
- `anyModalOpen`（キャンバスのズーム・パン停止に使う変数）は Task 7 以前の形（`modalOpen || confirmTarget !== null`）へ復元した。**メニューが開いていること自体はキャンバスの停止条件から外れた。**

**この取り違えの経緯そのものが記録の価値である。** 人間が実機で観察した「困りごと」の言葉（「複数開けるのが邪魔」）が、実装の都合で観測しやすい別の症状（「ズームが復活する」）に翻訳されてしまうことがある、という実例として残す。

### 個別の判断（実機で観察・確認された事項）

- **`Ctrl+↓` / `Shift+↓` でメニューが開く件（Task 7 parked）は、実機で観察したうえで人間が「別に問題ない」と判断した。塞いでいない。** Radix の内部実装（`node_modules/@radix-ui/react-dropdown-menu/dist/index.mjs`）が `ArrowDown` を修飾キーの状態を見ずに判定して開く挙動によるもので、計画が掲げていた不変条件「トリガーはポインタでだけ開く」には反するが、実害として体感されなかったため直さない判断となった。`Alt+↓` ではメニューが開かず並び替えができることも確認された（正常）。
- **キーボードの操作言語の抑止を、セルのドロップダウンに対して掛けないことも人間が確認済み。** Task 11b の結果、メニューが開いている間のキー入力の遮断は Radix の `FocusScope` 単層に任せる形になった（`anyModalOpen` はメニューの開閉を見ない）。DOM テストで「1つ開いた状態で `Enter` は漏れない」ことを確認済みであり、この状態（`Enter` の挙動は現状のまま。額縁由来の追加の抑止は掛けない）でよい、という人間の判断が確定している。
