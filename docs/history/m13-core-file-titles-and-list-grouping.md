## 実装で確定した事項

### 名前の実体は JSON の `title` であり、ファイル名は変えない

「ファイル名を変えると Claude がファイルを見失う」という懸念は成立しない——`src/core/reading-guide.md` も登録 Skill も**中身の `type` で種類を判別**し、ファイル間の参照はすべて ID 経由で、パスを持つ箇所が1つも無い（rev「設定ファイルによるパス管理を持たない」）。したがって採否はリネームの危険では決まらず、決め手は次の2つだった。

1. **実装コストが桁で違う。** ファイル名変更には `fs:allow-rename` の capability 追加、`src/fs` への関数追加、自動保存の `dispose()` → `flush()` → rename の順序制御（M4 の削除で踏んだ罠と同型）、**パスごとに内容を持つ外部変更検知の台帳**に対する旧パス消滅・新パス出現の自己書き込み除外、`selectedPath` の張り替えと `handleSelectedGone` との競合が要る。対して `title` の編集は既存の `onChange` 経路（`record` + `applyEdit`）に乗るだけで、**Tauri 側の変更がゼロ**で済む。
2. **連動させても外から壊れる。** エクスプローラでリネームされたとき `title` は追従しない。ファイル名は自由であるという原則を採っている以上、アプリ内で「名前は1つ」に見せるのは**外の世界がいつでも破れる嘘**になる。

スキーマは変更していない（`title` は全4スキーマの既存の必須 string で、`schemaVersion` は上がらない）。判定は `titleOf`（`src/core/load.ts`）に一本化し、`classifyFile` と `applyEdit` の両方がそこを通る。

### `title` の編集は額縁が持つ。モジュールのエディタは `title` を描かない

`FileHeader`（`src/components/FileHeader.tsx`）をエディタ領域の直上に置き、**4ツール全部が自動で得る**形にした。キャンバス系2本（ロジックツリー・シーケンス）はエディタ側に `title` の置き場所が無く、モジュールごとに実装すると4箇所に散るため。用語集・エラーカタログのエディタが持っていた `<h2>{data.title}</h2>` は削除し、帯に一本化した。

帯は表示だけを担い、状態も I/O も持たない（`FileList` と同じ規約。配線は App）。`rejected` / `listOnly` では読み取り専用にして、**データを書けないファイルに書き込む入口を作らない**。

### 帯は種類名を出さない（同じことを2箇所で言わない）

**種類は一覧の見出しが既に示しているので、帯では言わない**（実機確認での人間の裁定。`97bb3cd`）。帯に出るのは `title` の入力欄とファイル名の副表示だけである。

この形に落ち着くまでに一度往復している。最終レビューの指摘5 は「`typeLabel` が `rejected` / `listOnly` で null になる（`selectedModule` は `editable` のときしか決まらない）ので、一覧が『用語集』の見出しの下に置いているファイルの帯だけが無名になり、**一覧と帯が食い違う**」というもので、fix 波（`653c812`）は**`type` が読めているなら status を問わずレジストリから引く**形で解いた。実機で見た人間はそこで、そもそも帯に種類を出すこと自体を却下した。

**これは差し戻しではなく、同じ指摘の別の解き方である。** 指摘5 が言っていたのは「一覧と帯が種類について食い違う」であり、**帯が種類を言わなければ食い違いようがない**。撤去は表示だけでなく `FileHeader` の `typeLabel` prop・`App.tsx` の `selectedTypeLabel`・関連テストにまで及んでいるので、死んだコードは残っていない。`App.dom.test.tsx` の該当テストは `not.toContain('用語集')` に反転させたうえで、**残る価値のある主張（「スキーマ検証に落ちたファイルの帯は読み取り専用のまま」）の方を軸に据え直した**——反転した否定だけを残すと、何を守っているのか分からないテストになる。

### 空の `title` は許し、表示と出力の両方で `(無題)` に落とす

空欄＝未決という原則（rev 5章「拒否は最小限に」）なので、`title` を空にする入力は拒否せずそのまま保存する。落とすのは表示側の責務で、一覧の主表示（`displayTitle`）と帯の placeholder に加えて、**Markdown 出力にも同じ判断が要る**ことが最終レビューで分かった——空 `title` は `## ` だけの行として書き出されていた。3ツールに同じ判断を3回書かないよう、`## ` の組み立てごと `documentHeading`（`src/core/markdown-table.ts`）に持ち上げてある。**`headingText` 自体には入れない**——種別ラベル等の空文字まで `(無題)` に化けるため。logic-tree は Markdown 出力を持たないので対象外。

### `UNKNOWN_TYPE_KEY` は衝突しないことを保証していない

`type` が読めないファイルを入れるグループのキー `'__unknown__'`（`src/core/file-grouping.ts`）について、計画のコメントは「type 文字列と衝突しない形にする」と書いていたが、**保証していない**。`type` はスキーマ上ただの文字列なので、`"type": "__unknown__"` と書かれたファイルは自分のグループではなく「種類不明」に混ざる。**防御機構は足さず、コメントを正直に書き換えた**（最終レビュー指摘9）——見た目を前置き記号で飾って「衝突しない」と称するより、起きうることを書いておく方が次に読む人を誤らせない。

## 見つかった欠陥: `applyEdit` が `result.title` を引き直していなかった

`src/core/app-controller.ts` の `applyEdit` は `result.data` を差し替えるのに `result.title` を放置していた。

## `localeCompare('ja')` は五十音順ではない（スペック決定5の根拠が漢字では成立しない）

スペック決定5とその実装コメント・テスト名は、グループ内の並びを「`title` の五十音順」と称していた。**誤りである。** `localeCompare('ja')` は漢字を **ICU の照合順（部首・画数）**で並べるので、読みの順にはならない。

実測して固定した例（`file-grouping.test.ts`）:

| | 順 |
| --- | --- |
| 実際（`localeCompare('ja')`） | 受注 → 返品 → 問合せ |
| 読み（五十音）ならこうなるはず | 受注 → 問合せ → 返品 |

**読みはデータに無いので求めようがない。** `title` に読み仮名のフィールドを足す設計は採っていないし、今回のスコープでもない。並び順は決定的であり一覧としては足りるので、**挙動はそのままとし、コメントとテスト名の側を実態に合わせて直した**（最終レビュー指摘2）。

**その帰結として、スペック決定5が挙げた根拠「画面に大きく出ているもので並ぶので、順の根拠が見て分かる」は、漢字の `title` については達成されていない。** かな・英数字の `title` なら見て分かるが、漢字が先頭に来る名前（実運用ではこちらが多い）では、並びの根拠は画面から読み取れない。決定そのもの（`title` で並べる）は維持しているが、**根拠として書かれた一文は漢字には及ばない**——次にこの並びに触る人はそこを織り込むこと。
