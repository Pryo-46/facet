## 何を作ったか

計画が置いた前提（批評セッション 2026-08-23 の決定）と、実装で変わった点。

**1. キャンバスは残す。** 壊れていたのは骨組み（M20 のキャンバス基盤・エッジ）ではなく載せ物だった——仮説カードに文言・由来・メモ・イベント全件を積んだため、俯瞰したいもの（課題の木と、どの仮説が生き残ったか）と読みたいもの（根拠の文章）が同じ面で場所を取り合っていた。

**2. 物の種類を形の種類に対応させた。** 課題＝**箱**（エッジが出入りする唯一の物）／仮説＝箱の中の**1行**（左に点、右端にバッジ）／判断＝行末の**バッジ1つ**／見送り＝課題タイトル右のバッジ＋理由の行／由来・根拠・FB・以前の判断＝**展開した仮説だけ**の内側パネル。`HypothesisCard.tsx` は消え、`IssueBox.tsx` と `HypothesisRow.tsx` になった。

**3. 仮説の5語。** バッジは **支持／棄却／保留／未決／見送り**の5語で、正確な種別（7種）は展開したときだけ出る。支持＝`ok` の塗り、棄却＝`ink` の塗り（反転。棄却は失敗ではなく入力なので叫ばない）、保留＝`warning` の**実線**の枠、未決＝`warning` の**破線**の枠、見送り＝`ink-muted` の枠。課題側の「仮説なし」は未決と同じ破線バッジ。

**4. 判断は1つ、FB は複数——表現として。データは分けたまま。** 展開では「判断」（最新1件・根拠が編集できる）／「以前の判断」（2件目以降・薄く読み取り専用）／「由来」／「FB」（`pendingNotes`）の順。**`pendingNotes` を `events` に統一する案は採らない**（ユーザー決定。D9 の選別の余地を残す）。

**5. 色を足さない。明度の段を1つ足した。** 意味を持つ色相は `warning` と `ok` の2つのまま。抑制された配下は `opacity` ではなく新しい役割トークン `ink-faint` で薄くする。

**6. 設計ノートの文を画面に出さない。** `SUPPRESSED_NOTE`（「祖先の見送りにより問いは立たない（導出。子に値は持たない）」）は実装者の語彙だったので消した。薄ければ文は要らない。

**7. 俯瞰からの動線。** 帯の集計をチップにし、押すと次の要対応（仮説なし／未決／保留／未判断）へ視点が飛ぶ。**アウトラインには作れない、キャンバスを選んだ側だけの武器。**

**8. 誤操作の穴は直していない。** 「同じ判断を続けて付けてしまう」「最新以外を消せない」は批評で挙がったが、**FB の枠組みが入って意味が変わった**ので実機で再観察してから決める（[`../open-issues.md`](../open-issues.md) に記録）。

**9. `schemaVersion` を 2 にした。** スキーマ自身が「enum の拡張は schemaVersion の改訂として扱う」と書いているため。**このリポジトリで初めての版上げである。**

**10. 語の確認。** 合計の見出し「要対応」と問いの名詞形「仮説なし／未決／保留／未判断」は計画者の仮置きだったので、Task 2 の着手前にユーザーが読んで**そのまま確定**した。

### 実装で変わった点（計画から動いたもの）

- **`lastCell` は `FocusTarget` ではなく `{cell, key}` の鍵で持った。** 配列位置で持つと、フォーカスの通知を伴わないデータ差し替え（Undo/Redo・外部変更）の後に**別の行を指す**。「課題の鍵」と「行き先」を2つに分けないこと自体も規律で、分けると片方だけが古くなり、帯の「仮説を追加」が直前に触った課題とは**別の課題**へ足す（画面には何も出ない）。
- **帯のチップに `buttonBase` を敷かなかった。** `buttonBase` の `rounded-sm` とバッジの `rounded` を並べると、勝つのは生成 CSS の順（同レイヤ・同特異性で後に出るほう）で `rounded-sm` になり、**真似したはずのバッジと違う丸みになる**。同じファイルの `TRIGGER_FACE` が M8 の教訓としてまさにこの組み合わせを禁じている。落ちたものは無い（`buttonBase` はフォーカスリングを持たず、`inline-flex items-center` は `badgeClass` の土台が持つ）。
- **パネルの字下げは計画の 24px ではなくモックの 12px。** 計画は「モックが見え方の正」と書いているので、食い違ったらモックが勝つ。`.row{padding-left:12}` と `.panel{margin-left:12}` が同じ原点を共有し、**パネルの左端が行の文字の左端に揃う**のがモックの意図だった。
- **`ROW_GAP` は 4 → 3。** 課題ツリー側の `measure.ts` の定数だけ。シーケンス側にも同名の定数があるが（`src/modules/sequence/layout.ts:16` の `ROW_GAP = 8`）**共有していない**ので触っていない。

## 実装で確定した事項

### 継ぎ目: 畳んだ行の `onFocus` → `pendingFocus` → 展開後の `<textarea>`

**畳まれた行の `<button>` と、展開後の `<textarea>` は同じ `data-cell` を名乗る。** これが成立するのは `HypothesisRow` が**両方を同時に描かない**からで（早期 return による構造的な排他）、`expandRow(key)` は `setExpandedKey(key)` と `setPendingFocus(...)` を並べて呼ぶだけでよい——予約を当てる effect は描画後に `querySelector` するので、当たるのは開いた後の textarea になる。

**行の `<button>` の `onFocus` が `onExpand` を呼ぶ**ので、`Tab` でも `Shift+Tab` でも「行に着いた瞬間に開いて文言の欄に入る」。**逆向きでも展開するのは意図どおり**だが、**1回の打鍵でフォーカスが2回動く**ことになる（[`../open-issues.md`](../open-issues.md) のアクセシビリティ節に記録。スクリーンリーダの読み上げは実機で聞くまで分からない）。

`pendingFocus` の effect は `focus({ preventScroll: true })` を使う。**画面外の要素にフォーカスするとブラウザが祖先の `scrollLeft`/`scrollTop` を動かすが、位置は transform で持っており `panIntoView` はスクロール量を勘定に入れていない**（二重に動いて以後ずれ続け、`overflow-hidden` にはスクロールバーが無いので UI から戻せない）。土台は `src/modules/logic-tree/LogicTreeEditor.tsx` からの写しで、**測るフォントが2種類（`text-sm` / `text-xs`）に増えた**ぶんだけ広げてある。

### `ink-faint` の最終値と実測比

| | 値 | canvas 上 | surface 上 |
| --- | --- | --- | --- |
| ライト | `oklch(0.58 0.007 170)` | **3.38:1** | **3.81:1** |
| ダーク | `oklch(0.55 0.007 170)` | **3.89:1** | **3.71:1** |

要件は `src/styles/palette-requirements.ts` の `min: 3.0`、目標は 3.2。**4条件すべてで満たし、明度の段としてもライト／ダークで正しい向きに動く**（実装者とレビュアが `palette-fit.mjs` を別々に走らせて同じ数字を得た）。

**色相はライトとダークで別の扱いになった。** ライトの `ink-faint`（H170.1/C0.007）は同じくライトの `ink-muted` と同系統だが、**ダークの `ink-muted` は Grey Lichen（H120/C0.042）で別系統**なので、ダークの `ink-faint` は `ink-muted` の色相を引き継いでいない。`palette.css` のコメントは一度この点を誤って書いており、修正ラウンドで実物の値に合わせて直した（**次に配色を差し替える人が読む場所なので、値ではなくコメントが誤っていることの害が大きい**）。

**`ink-faint` はアクティブな本文に使ってはならない。** 3:1 は WCAG 1.4.3 が非アクティブ要素を免除する範疇に収めた値であり、読ませる文章に当てると本文の 4.5:1 を割る。いま `text-ink-faint` / `border-ink-faint` / `bg-ink-faint` が出るのは6箇所（`badge-styles.ts:46`、`HypothesisRow.tsx:130` / `:132` / `:160` / `:185`、`IssueBox.tsx:67`）で、**6箇所とも `suppressed` の分岐の中**だが、**それを縛っているのはレビューだけである**（機械検査は無い。[`../open-issues.md`](../open-issues.md) に記録）。

### `load.ts` の移行フックが初めて動いた

`src/core/load.ts` には「既知の旧版が生まれたら `module.migrate` による移行をここに挟む」というコメントだけが置かれた**空席**があった。issue-tree の 1 → 2 が**初の実例**である。

- 移行は `module.migrate(record, version)` を呼び、**移した結果をスキーマ検証に掛ける**——移行は検証を飛ばさない（結果が不正なら `rejected`）。
- **マイグレータの側は形を見ない。** `migrateIssueTree` は `schemaVersion` を 2 に書き換えるだけで、検証しない（すると検証の規則が2箇所に生える）。1 の正しいファイルは 2 の正しいファイルである（`onHold` は enum の**追加**なので）。
- `module.test.ts` の「マイグレータは恒等」というテストは**もう真ではない**ので書き直した。
- **ファイルへの反映は最初の編集保存時**（rev 5章）。閲覧しただけでは旧版のまま残る——**この保存側を見るテストが無い**（[`../open-issues.md`](../open-issues.md) に記録。実機確認の項目9でもある）。
- 移行フックを通すテストは、`src/core/load.test.ts` に**専用の偽モジュール**を1本足して書いた（`schemaVersion: 2`・本物の `schemas/issue-tree.schema.json`・1→2 を上げる `migrate`）。**既存の `makeRegistry()` は触っていない**——「未知の新しい schemaVersion は listOnly」のテストが、その偽モジュールが schemaVersion 1 のままであることに依存しているため。**帰結として、実物の `issueTreeModule` を v1 のファイルで通す経路はどこにも無い**（[`../open-issues.md`](../open-issues.md) に記録）。

### 入れ子の見送りは「**祖先**が抑制の集合に居るか」で判定する——一度退行を踏んだ

**配下を薄くするかどうかは `parentId !== null && suppressedIds.has(parentId)` で決める。** 「自分が見送っていないか」（`events.length === 0`）では**代用できない**。

修正ラウンド1で「見送りを掲げた箱自身は薄くしない」を直したとき、`issueSuppressed[i] && node.events.length === 0` という式を書いてしまい、**A → B(見送り) → C(見送り) → D で C だけが濃く戻る**退行を作った——薄い箱の間に濃い箱が1つ挟まる。**既存のテストは見送りが1段のものばかりだったので、緑のまま通った。** 修正ラウンド2で `parentId` を見る形に直し、3段の入れ子のテストを足した。

確定した規則: **見送った祖先の下では、部分木ぜんぶが対象外である**（そこに含まれる C 自身の見送りの判断も、もはや意味を持たない）。したがって **B は普通に描かれ**（B が見送りを掲げており、その親 A は抑制されていない）、**C と D が薄い**。エッジは A→B が実線、B→C と C→D が破線。**見送りを掲げた箱と、その見送りバッジ・理由の行を薄くしないのは、そのバッジが「なぜ配下が薄いのか」を説明する役だから**である——説明ごと薄くすると理由が読めない。

**この規則は設計ノート D8 に書いた。** 経緯がコードのコメントにしか無い状態では、設計ノートだけを読んだ人が同じ退行をもう一度入れられる。

### 語彙を `derive.ts` の定数1箇所に置いた効き目

問いが4種になり合計の見出しが「要対応」になったが、**打ち直したのは `derive.ts` の定数だけ**で済んだ。`derive.ts` は `.claude/skills/issue-tree-register/scripts/derive.ts` へ**バイト一致コピー**されるので、同じ変更がアプリと Skill の両方に同時に効く。`EVENT_KIND_LABELS: Record<JudgementKind, string>` が網羅を型で強制するため、`onHold` の追加は `tsc` が即座に要求した。

**ただし手書きの配列は守られない**（次節）。

## 見つかった欠陥

**Critical に相当したのは1件**（設計ノートに実装の判断が1つも書かれていなかったこと。Task 7）。以下はレビューで捕まえて**このブランチの中で直したもの**である。

1. **`JUDGEMENT_KINDS` が手書きの配列で、`onHold` が落ちていた**（Task 1 のレビュー → Task 4 で修正）。`EVENT_KIND_LABELS` は型が網羅を強制するので `tsc` が足させたが、同じ意味の一覧である `IssueTreeEditor.tsx` の配列は**足し忘れても緑**で、**スキーマが受け付ける判断を UI から入力できない**状態になっていた。
2. **計画は `DEFERRAL_KINDS` にも `onHold` を足せと書いていた**（採用せず）。保留は**仮説にだけ付く**判断で、`$defs.deferralEvent` は受け付けない——足せば「選ぶと保存できないメニュー項目」になる。
3. **見送りを掲げた箱が自分自身を薄くしていた**（Task 4）。`suppressedIssueIds` は最新イベントがある時点でその課題自身を集合に入れるので、**見送った課題は自分の抑制集合に入っていた**。`badgeClass('deferred', false)` が到達不能になっているのが兆候だった。
4. **入れ子の見送りの退行**（上記。Task 4 の修正が作り、次の修正ラウンドで直した）。
5. **展開した本文を weight 400 で測って `font-medium` で描いていた**（Task 4）。`fonts.title` という別の測定器を作ったのはまさにこのためで、**textarea は固定高さ＋`overflow-hidden` なので、はみ出しても静かに切れる**。
6. **ホバーで出る「見送り」のトリガーに幅が予約されていなかった**（Task 4）。長いタイトルの上に重なり、「仮説なし」バッジとも衝突した。右上に**常に1枠**空ける形にした（バッジがあるときだけ空ける形にすると、普通の箱でホバー中にボタンがタイトルに被る）。
7. **書き出しスクリプトが `保留` を内訳から落としていた**（Task 2）。合計は保留を数えるのに列挙に出ないので、**数と並びが食い違う**。同じスクリプトが合計の見出しを `未決` と直書きしてもいた（`D.TALLY_TOTAL_LABEL` を使うよう直した）。
8. **`palette-fit.smoke.test.ts` のフィクスチャ CSS が `--ink-faint` を欠いて落ちた**（Task 3）。トークンを全部列挙する形なので、増えたら足りなくなる。
