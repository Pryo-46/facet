## 何を作ったか

`.claude/skills/sequence-register/` は既存2本（`glossary-term-register` / `error-catalog-register`）と同じ骨格を持つ:

- `SKILL.md` — 手順書。2フェーズ構成（**A: 図を起こす**／**B: 問いを詰める**）
- `scripts/new-id.mjs` — ID 採番（既定 `step`、`--prefix actor`）
- `scripts/sequence-write.mjs` — スキーマ検証・正規形の書き出し・整合性検証・未定義の集計
- `scripts/questions.ts` / `scripts/canonical.ts` — **アプリのソースのバイト一致コピー**（後述）
- `evals/`（`evals.json` / `grade.mjs` / `fixtures/`）・`package.json`（`ajv`）

**既存2本と違うところは3つある。**

1. **材料が会話そのものである。** 用語集は「用語」、エラーカタログは「エラーメッセージ一覧や問い合わせ実績」という外部の材料を構造化するが、この Skill の材料は直前までの会話で、そこには既に AI の発言が混ざっている。したがって `failures`（失敗したら？の答え）の転記は3段に分けて規律化した——**ユーザーが言った／AI が提案しユーザーが同意した**は転記する、**AI が提案しただけ・議論に出ていない**は空にする（キーを置かない＝未定義）。
2. **`singleton: false` である。** 用語集・エラーカタログは「プロジェクト内の当該 `type` を探して追記」が既定だったが、シーケンスは**新規作成が既定**。既存への書き足しはユーザーが名指ししたときだけで、単一性の警告は出さない（複数本あるのが正常）。
3. **フェーズA に確認ゲートを置かない。** エラーカタログ Skill は「登録するエラーを確定させる」往復を持つが、それは**入れるのは1往復・消すのは後で何度も**という非対称があるため。シーケンスにこの非対称は無く、外れならファイル1本を捨てるだけで、しかも**図にすれば一目で分かる**。テキストで骨格を読み合わせるより、書いてアプリで見るほうが速い。

フェーズB（立っている問いをまとめて聞いて埋める）は、エラーカタログ Skill の明文の禁止——「**『出力が未定義だらけなので埋めましょう』と AI が言わない**」——と衝突しかける。**書き出した直後に1回だけ提案し、断られたら繰り返さない。既存ファイルを開いて未定義の件数を数えて回らない**という線引きで分けた——禁じられているのは催促（ファイルの状態を見て「不完全だから埋めろ」と言うこと）であり、フェーズB は会話が続いている文脈での作業の続きの提案である。

## 実装で確定した事項

### 同梱 Skill は `src/` を import できない——バイト一致コピー＋機械検査という解法

**これがこのマイルストーンで最も効いた設計判断である。**

`BUNDLED_SKILLS` に載った Skill は、アプリがユーザーのプロジェクトフォルダの `.claude/skills/` へ**コピーする**。したがってスクリプトは `<プロジェクト>/.claude/skills/sequence-register/` から実行され、**そこに `src/modules/sequence/` は無い**。`palette-retheme` が `src/styles/contrast.ts` を直接 import できているのは、あれが facet 自身のソースを触る**非同梱**の Skill だからで、データ作成 Skill はこの手を使えない。

残る選択肢は2つしかない。

- **手で複製する**（既存2本がやっていること）。エラー登録 Skill について open-issues が記録しているとおり、**追従漏れがあっても双方は独立に動くため、テストでは検知されない**
- **バイト一致のコピーを同梱し、一致を機械検査で強制する**

後者を採った。`.claude/skills/sequence-register/scripts/questions.ts` は `src/modules/sequence/questions.ts` の、`scripts/canonical.ts` は `src/core/canonical.ts` の**バイト一致コピー**（どちらも `cp` で作り、手書きしていない）で、`src/modules/sequence/skill-copy.test.ts` が2本立ての検査を持つ:

1. **バイト一致していること**
2. **値 import を持たないこと**（＝コピー側で解決できない依存が生えていないこと。`enum` やコンストラクタのパラメータプロパティのような**消去できない構文**の検査も同じファイルにある）

**手複製との質の差はここにある。** ズレたらテストが赤くなる。しかも `src/core/canonical.ts` のヘッダは以前から「Skill 側の `glossary-write.mjs` とバイト単位で同一の出力を返すこと」を要求していたので、**コピーにすればその要求が（少なくともこの Skill については）構造的に満たされる**。

コピーできる根拠は実測で確かめてある——`questions.ts` の import は `import type { SequenceStep } from '@/types/sequence'` の1本だけで、型 import は型ストリップで消えるため `@/` エイリアスの解決が要らない。`canonical.ts` は import を1本も持たない。対照的に `consistency.ts` は `from './questions'`（拡張子なし）を持つため Node から直接読めない——**`consistency.ts` 側の import を `./questions.ts` に直す案は却下した**。アプリのソースを Skill の都合で曲げることになるため。整合性検証の5ルールのうち**手実装は4つ**（参照切れ・ID重複・`to` の過不足・`from`==`to`。いずれも構造検査）で、残る「立っていない問いへの答え」は `Q.unposedAnswers` の import で済んでいる——**コピー方式が効いているのはまさにここ**である（`sequence-write.mjs` のヘッダにこの内訳が書いてある）。

代償は open-issues が `palette-fit.mjs` について記録しているのと同じ「Node の型ストリップへの依存」で、これは残る（`.mjs` から `.ts` を import している）。ただし**こちらは生えた瞬間にテストが赤くなる**点が違い、その差は open-issues の当該項目に併記した。

**`canonical.ts` のコピーは計画に無かった。** 当初は `reorder` / `deref` を既存2本の Skill から手で複製する計画で、着手前のスキャンで `canonical.ts` が import を持たないことを実測し、**人間に諮って**コピー方式へ変えた（`3c8d3b2`）。結果として、正規形を作る実装が**3本の Skill で2方式に分かれた**——既存2本は手複製のままである。これは open-issues に繰り越した。

### `readSlot` を `questions.ts` へ移した（4本目の複製を作らないため）

未定義の集計（⚠ 未定義 N ／ ✓ 回答済 N ／ ─ 考慮不要 N）を**アプリのガターと同じ規則で**出すには、答えスロットを読む関数が要る。`unknown` が下位の `ifExecuted` を内包する形なので素直なプロパティアクセスにならず、**この読み方はコードベースで既に3本に複製されていた**（sequence M2 からの既知の負債）。sequence M3 は `commands.ts` の `readSlot` を export して4本目を作らずに済ませ、**その旨のコメントを残していた**。

Skill が `commands.ts` を import することはできない（値 import を持つ）。そこで **`readSlot` を `questions.ts` へ移し**（Task 1、`ca7aa7f`）、`commands.ts` / `markdown.ts` / `SequenceEditor.tsx` がそこを見るようにした。`SequenceEditor.tsx` のローカル複製 `readAnswer` はこのとき消えている。**Skill は「4本目の複製」ではなく、集約先そのもののバイト一致コピーを持つ。**

後方互換の再輸出は置かなかった（`markdown.ts` が直接 `./questions` を見るようになるため死んだコードになる。これは着手前のスキャンで計画から削った2件のうちの1件）。

### 答えスロットのキー順を書き出し側で揃える（`normalizeSlots`）

正規形のキー順はスキーマの `properties` 記載順から実行時に導出するが、**`answerSlot` は `oneOf` なのでキー順が導出できない**——下書きのキー順がそのまま残ることを実測で確認した。アプリは常に `decision` → `text` の順で書くので、揃えないと**同じ内容のファイルがバイト列で食い違う**。`sequence-write.mjs` に `normalizeSlots()` を置いて、書き出し前に答えスロットのキー順を直している。これも計画に無く、実測から足した。

### `evals/grade.mjs` の自己位置解決を3本で揃えた

用語集版の `grade.mjs` は `SKILL` / `SCHEMA` を主チェックアウトの絶対パス（`C:/Dev/Projects/facet/...`）で持っており、worktree では動かなかった（open-issues に「3本目の Skill を作るときか、用語集版に触る機会に揃える」と条件付きで残っていた項目。3本目の `palette-retheme` は evals を持たないため機会にならなかった、という但し書きまで付いていた）。**evals を持つ3本目が本 Skill なので、ここで揃えた**——3本とも `path.resolve(fileURLToPath(import.meta.url), "../..")` 起点になり、`C:/Dev` は0件。open-issues の当該項目は本マイルストーンで削除した。

### `skill-sync.ts` のコメントが実態より古かった

`BUNDLED_SKILLS` のコメントは「`src-tauri/tauri.conf.json` の `bundle.resources` と一致していなければならない」と書いていたが、実際の `resources` は `"../.claude/skills": "skills"` と**ディレクトリごと同梱**なので、Skill を1本足しても `tauri.conf.json` の追従は要らない。コメントを実態に合わせて書き換えた（Task 8）。**なお書き換え後のコメントは resources のキーを `".claude/skills"` と引用しており、実際の `"../.claude/skills"` と1段ずれている**（主張の内容は正しい）。計画由来の写し間違いで、実害が無いため直していない。

## 実機確認（Task 9）が掘り当てた3段階の欠陥

**このマイルストーンで最も重要な記録はここである。** 計画の Task 1〜8 はすべてレビューを通って緑だったが、**アプリは Skill を1度も正しく配置できていなかった。** 実機で動かすまで1件も見つかっておらず、**見つかった1件を直す過程で残りが芋づるで出た**——`npm test` も `tsc` も `lint` も、この3件のどれ1つ捕まえない。

### 段階1（Task 8b）: `npm install` した `node_modules` を同期しようとして落ちる

実機の症状:

```
Skill をプロジェクトへ配置できませんでした（Skill 無しで起動します）: forbidden path:
<projectDir>/.claude/skills/sequence-register/node_modules/json-schema-traverse/.eslintrc.yml
```

**壊れたファイルの出どころを取り違えないこと**——これは**同梱物**であって、利用者のフォルダにあるものではない。連鎖はこうである:

1. `tauri.conf.json` の `bundle.resources` は `"../.claude/skills": "skills"`。**ビルド時点でリポジトリの `.claude/skills/` にあったものが丸ごと同梱される**
2. Task 4 の検証で、**開発者がリポジトリの `.claude/skills/sequence-register/` で `npm install` を実行していた**（スクリプトが `ajv` を要るので、開発中は必ずこうなる）。その `node_modules` が同梱物に入った
3. `readBundled`（`src/fs/skill-resources.ts`）は `resolveResource('skills/<名前>')` の配下を無条件に再帰収集し、「何を置くか」の判断を `shouldSyncSkillFile` に完全に委ねている
4. その `shouldSyncSkillFile` は `evals/` と直下の `package.json` / `.gitignore` しか除外していなかったので、数千ファイルの依存をプロジェクトフォルダへ書きに行き、許可スコープ外のドットファイルで落ちた

**利用者が置いた先で `npm install` しても、それが読まれることはない**（読み出し元は同梱リソースだけ）。したがって**引き金は「ビルド前に開発者がリポジトリの Skill ディレクトリで `npm install` している」ことである**。既存2本のディレクトリで同じことをしていれば同じ結果になったはずで（今のリポジトリで `node_modules` があるのは `sequence-register` だけ）、**3本目を作って初めて条件が揃った潜在欠陥**である。`node_modules` を同期対象から外して解決した（`3ad2925`）。

### 段階2（Task 8c の3件）: 同期のタイミング・`node_modules` の削除・「読む前に消す」

段階1 を直した実装者が、**直したことで新しく成立する問題**を報告した——`syncBundledSkills` は Skill ディレクトリを丸ごと消して置き直すので、`node_modules` を「置かない」だけにすると、**同期のたびにユーザーの `npm install` が消えて復元されない**。しかもその同期は `openTerminal` から呼ばれており、**端末タブの「＋」を押すたびに走る**。Skill はプロジェクトに属するものであって端末セッションに属するものではない。

同じ削除処理に集まる3件として、M11 から open-issues に載っていた**読む前に消す**（`readBundled` が失敗するとプロジェクト側の Skill が消えたまま復旧しない）も併せて直した（`3c0d40b`〜`96b0314`）:

1. 同期を `projectDir` の effect へ移した（フォルダ1つにつき1回。`openFolder` / `switchFolder` / 将来の起動時復元がすべて自動的に1本にまとまる）
2. 削除を**直下の要素ごと**にし、`node_modules` を保護した（`SKILL_DEPS_DIR` 定数1つを「置かない」と「消さない」の両方が参照する。片方だけだと `npm install` が毎回巻き戻る）
3. **読んでから消す**順に反転した（`readBundled` → `exists` → `listEntries` → `removeEntry` → `mkdir`/`writeText`）

新しい順序では、**削除より前に失敗しても同期前より悪くならない**。悪化しうるのは「削除に成功したあとに失敗した」場合だけで、削除と書き込みの間には新しい失敗要因が無い（同梱物は削除より前に全件メモリへ読み終えている）。**「書いてから消す」への反転は検討して採らなかった**——削除の目的は「Skill の更新でファイルが減ったときに古いファイルを取り残さない」ことで、入れ子の掃除が要る以上、書いた後に消すには「新しい同梱物に含まれないもの」の再帰的な差分計算が要るうえ、残る窓（削除成功→書き込み失敗）が消えるわけでもない。それを本当に閉じるには一時ディレクトリへ書いて入れ替えるしかなく、範囲を超える。

### 段階3（Task 8c の修正ラウンド）: `.DS_Store` ——削除を1件ずつにしたら、同型の破壊が一段先で再現した

**この件が本マイルストーンで最も学びが大きい。**

「読む前に消す」を直すために、削除を「root を丸ごと」から「直下を1件ずつ」に変えた。ところが `src-tauri/src/lib.rs` の `allow_skill_dir` 自身の説明が書いているとおり、**Tauri の fs scope の glob 判定は unix で `require_literal_leading_dot: true`** である（だから `.claude` を literal で足している）。つまり `<dir>/.claude/**` は**ドット始まりの要素に一致しない**。

**踏む条件は「Skill ディレクトリの直下にドット始まりの要素があること」**である——`<projectDir>/.claude/skills/<名前>/.DS_Store` や、除外前の版が置いた同じ階層の `.gitignore` がそれに当たる。プロジェクトフォルダの直下にある `.DS_Store` はこのループに入らないし、`scripts/` の中のドットファイルは親ごと再帰削除されるので個別の判定を通らない。**直下の1件だけが問題になる。** そこで例外 → ループ中断 → 書き戻し無し。**「読む前に消す」を直した処理が、同じ「Skill が消えたまま残る」形を一段先で再現していた。**

**採った形は「1件ごとの削除失敗を握りつぶして続行する」。** 「ドット始まりの名前を消さない」案は退けた。理由は2つある:

- **守りたい性質は「何であれ消せない要素が1つあっても Skill は置き直される」**であって、ドットに限った特別扱いでは権限やロックで消せない一般のケース（EPERM、掴まれているファイル）を取りこぼす
- **Windows では同じ `.gitignore` を実際に消せる。** 名前で門前払いすると、**消せる環境でも古い残骸が永久に残る**。「消せるなら消す・消せなくても進む」のほうが両プラットフォームで正しい

削除は掃除であって目的ではない。消し残しは余分なファイルが1つ残るだけで、次の書き込みが同名を上書きする。**Skill を失うより明確に軽い。** その代わり「置いた Skill が同梱物と一致している」は best-effort に落ちたので、これは open-issues に繰り越した（消せなかったものは `console.warn` に残るが、画面には何も出ない。`.DS_Store` が消せないのは mac では正常なので、実バグと同じトーストで驚かせない判断）。

**握りつぶしは別の窓を開けた。** 中断しなくなったぶん、同じフォルダの同期が2本走ると「片方の削除ループが、もう片方が書いた直後の `scripts/` を消す」が成立する。`skillSyncInFlight`（フォルダ名 → 走行中の Promise）で重複排除し、**同期の完了前に別フォルダへ切り替えて戻ると2本になる**経路をテストで固定した。なお実装者はここで「StrictMode の二重実行で2本になる」というレビューの前提を実測で否定している（StrictMode が二重に起こすのはマウント時の effect だけで、マウント時点の `projectDir` は `null`。よって同期は1回しか走らない）。**重複排除自体は入れた**——UI から到達できる経路が別にあり、将来「起動時に前回のフォルダを復元する」を足すとマウント時に `projectDir` が入って StrictMode が本当に効くようになるため。

### `package.json` が同期されていなかった——3本すべての潜在欠陥

段階3 のレビューでもう1件出た。`shouldSyncSkillFile` は Skill 直下の `package.json` を「evals の依存宣言」として除外していたが、**3本とも `ajv` を `dependencies`（`devDependencies` ではない）に宣言しており、書き出しスクリプトは実行時に `require("ajv/dist/2020.js")` を通る。**
