## キャンバス（見え方の正）と実装が食い違った2点

デザインキャンバスは「m5 の見え方の正」だが、**後の判断が優越する箇所が2つあった**（Task 4・Task 5 が発見し、Task 9 が設計ノートに書き起こした）。

1. **パネルに判断ごとの面を敷かない。** キャンバスは `.panel.yes { background: var(--judge-yes-face) }` / `.panel.no { background: var(--surface-muted) }` と判断ごとに面を変えて描いているが、採らなかった。理由は2つ——`judge-yes-face` は facet の役割トークンに存在しない（`palette-requirements.ts` の淡い面は `missing-face` / `invalid-face` / `pending-face` の3つだけで、足すにはパレットの検算をやり直す必要があり m5 の範囲外）。かつ `surface-muted` は「見送りの箱」の面として既に使われており、棄却に敷くと計画の前提7が名指しで避けた「**抑制（祖先が見送った枝）と見分けがつかなくなる**」がそのまま起きる。棄却は前提7どおり閉じた行の文言を `text-ink-muted` にすることだけで表す。
2. **FB待ちバッジの variant は `pending`（着信の青）のまま、`open`（破線）にしない。** キャンバスの「バッジ語彙」アートボードは `FB待ち` を `.b-open`（破線・欠落の面）で描いているが、`derive.ts` の `toMissingTally` は「FB待ちは着信の青——欠落ではなく、返事を待っている。M22 でここに一本化」と定めており、畳まれた行も帯のチップも既に `pending` である。キャンバスは M22 前の描き分け（`--pending` を変数として宣言しながら `.b-pending` というクラス自体を持たない）だった。同じ語が開閉で色を変えるのを避け、理由が明記されている実装側を採った。

いずれも「キャンバスは実装済みの規約を知らない時点の静止画であり、後から確定した設計判断（rev 9章・M22）が優越する」という同じ構造の食い違いである。

## 実装で確定した事項

- **展開の単位が「フォーカスした仮説1件」から「課題ノード」になった。** 開くと、その課題にぶら下がる仮説がまとめて1つのパネル群を持ち、その課題の箱だけ幅が `BOX_WIDTH`（320）から `EXPANDED_BOX_WIDTH`（780）に広がる。理由は比較のしやすさ——課題1件に複数の仮説がぶら下がる場面で、仮説単位の開閉では隣の仮説を見ながら詰めるという比較そのものができなくなるため（Task 2、設計ノート D8 改訂）。
- **フォーカスによる自動展開をやめた。** `HypothesisRow` から `onFocus={props.onExpand}` を外し、`onClick` でのみ開く。発散のフェーズ（仮説をどんどん足す）と収束のフェーズ（判断・根拠・FB を詰める）で画面の振る舞いを変える判断であり、副産物として「畳まれた行に `Tab` で入ると1回で2回フォーカスが動く」旧来の症状も消えた（Task 2）。
- **幅 780・展開の3節構成が確定した。** 展開パネルは「ソリューション仮説（タイトル・詳細）／価値仮説／検証結果（判断バッジ・日付・理由）」の3節に「以前の判断（判断2件以上）」「FB」を続け、DOM 順＝y の順で並ぶ。展開中の「頭部」（タイトルの二重描画）は brief の指示より踏み込んで排除し、`HypothesisPlacement` を判別子つきの合併型にして `row` と `expanded` を型で排他にした（Task 4）。
- **キーの4つへの整理。** 課題ツリーの操作言語のうち、仮説側に割り当てていたキー処理（判断メニューを開く・根拠へ移す等）を全廃し、`ISSUE_TREE_HINTS` を4件に絞った。仮説側は `onKeyDown` を一切持たず、コアの `resolveCommand` を通らない——課題側（追加・削除・移動）だけがキーの管轄になった（Task 3）。
- **判断バッジのトリガー化。** 「判断を追加」「判断を変える」という文言のボタンを消し、状態バッジそのものをドロップダウンのトリガーにした（見る場所と変える場所を1つにする）。共通部品（`Badge` / `badge-styles.ts`）は1文字も変えていない（Task 6）。
- **問いと FB の入れ子。** 聞きたいこと（`asks`）ごとにブロックを作り、その問いへの FB をぶら下げる形にした。「どの問いにも紐づかない FB」はブロック自体は残しつつ固定文の見出しで別枠にする。FB待ちの帯の集計（`tallyQuestions`）とパネルに出るバッジの数が恒等に保たれることをレビューが検算した（Task 5）。
- **要対応の不変条件の回復。** m4 が残していた「FB待ちのチップの数と巡回列の長さが一致しない」非対称（決定Bの既知の帰結）を、問いごとに固有のセル（`{cell:'ask', index, askIndex}`）を新設して解消した。巡回の起点 `LastCell` に `{cell:'ask'}` を追加し、`rects` に `ask` の登録を足す（レビュー時点で欠けていたのを実装者が見つけて直した）ことで、画面外の問いへ飛んだときも `ensureVisible` が効くようにした（Task 8）。
- **仮説の追加・削除・問いの削除をマウスの動線に置いた。** 帯の「仮説を追加」ボタン（最後に触った課題に足す）、節末の「＋ 仮説を追加」（開いている課題の末尾に足す。仮説0本の課題では出ない）、ゴミ箱アイコン、問いの削除ボタンをそれぞれ新設した。仮説0本の課題に末尾ボタンが出ないのは、Task 2 の「仮説を持たない課題は展開しない」判断の帰結である（Task 7）。

## jsdom では守れない箇所

**`onCloseAutoFocus` の抑止**（`IssueTreeEditor.tsx` の `KindMenu`）は、Task 6 のレビューで「原理的にテストで守れない」ことが判明した。判断を選んだ直後に根拠の欄へフォーカスを移す仕掛け（`picked` ref が Radix の「トリガーへフォーカスを戻す」既定動作を `onCloseAutoFocus` の `preventDefault` で抑止する）は、選択の確定（`onSelect`）がその中で先に `onOpenChange(false)` を呼んで閉じる作りになっている。**jsdom ではこの経路で Radix の `FocusScope` によるフォーカス復帰そのものが走らない**ため、抑止（`preventDefault`）を外す変異を入れても `IssueTreeEditor.dom.test.tsx`（42件）は赤くならない——赤くなるのは機械のもう半分（`onSelect` が先に閉じる処理）を切ったときだけである。

これは「まだテストを書いていない」のではなく「**jsdom というテスト環境の構造上、この半分は検査しようがない**」という違う種類の欠落であり、`open-issues.md` と設計ノート D13 の両方に明記した（次にこのコードを触る人が「使われていないコード」として `picked` ref や抑止を消さないため）。実機でしか守れないので、Task 12 の実機確認の項目（「検証結果のバッジを押して判断を変えられ、直後に理由が打てる」）がこの機構そのものを踏む。
