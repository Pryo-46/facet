# sequence-m5 申し送り: 問いの文言に主語を足し、UI の語彙を `actors`＝「アクター」へ寄せる

> **追記専用。** そのとき何が起きたかの記録であり、以後変えない。**いま開いている残件は [`../open-issues.md`](../open-issues.md) を見ること**——本書に書かれた残件は当時の状態を指す。

sequence-m5 は「**ガターの問いラベルを自然な日本語に言い直し、具体例をツールチップで添え、あわせて画面に残っていた寸法と語彙のずれを片付ける**」マイルストーン。着手前の設計メモは `docs/sequence/question-label-redesign.md`。**主チェックアウトに未追跡のまま置かれていたもので、この worktree には存在しない**——内容は本書と design-notes へ移したので、マージ後に主チェックアウト側で消す。

**計画ファイルは作っていない。** 4件とも既存コードの範囲の定まった変更で、`docs/superpowers/plans/` に置くほどの分量が無かった——直前の domain 廃止（PR #17）と同じ扱いである。設計はチャット上で合意し、件ごとにコミットを分けた。

最終検証は4コマンドとも緑である: `npm test`（1807件）・`npx tsc -b`（出力なし）・`npm run lint`（oxlint。指摘なし）・`cargo test`（Rust は1行も触っていないが慣例どおり回した）。**実機確認は5項目すべて実施済み**（下記）。

## 何を作ったか

### 1. 問いのラベルに主語を足した

| 種別 | path | 旧 | 新 |
| --- | --- | --- | --- |
| `self` | `failed` | `処理失敗したら？` | **`処理が失敗したら？`** |
| `call` + `awaitsReply: true` | `failed` | `失敗が確定したら？` | **`呼出が失敗したら？`** |
| 〃 | `unknown` | `結果不明だったら？` | **`結果がわからなかったら？`** |
| 〃 | `ifExecuted` | `実行済みだったら？` | **`既に実行されていたら？`** |
| `call` + `awaitsReply: false` | `unknown` | `届かなくてよいか？` | **`応答が届かなくてもよいか？`** |

**主語はステップ種別が務める。** 旧文言は「処理失敗」のような複合名詞や「確定」「結果不明」「実行済み」といったステータスラベルをそのまま疑問文にした形で、日本語として不自然なうえ、何を書けばよいかも伝えていなかった。`届かなくてよいか？` は「ても」が抜けた非文でもあった。

### 2. 具体例をツールチップで添えた（`questionHints()`）

`questionLabels()` と対になる `questionHints()` を新設し、`GutterSlot` / `GhostSlot` のラベル列に `title` 属性で出す。

**ラベルを抽象のまま保てるのはこの関数があるからである。** 問いは原因ではなく知識状態に立てる（design-notes 論点3）ので、「エラー応答・接続拒否・タイムアウト」といった原因の例示をラベルに書くと類型が壊れる。**抽象のラベルと具体のヒントを別の関数に分けたことで、この線引きがコードの形になった。**

`title` 属性（ブラウザ既定）を選び Radix Tooltip を採らなかったのは、ラベル列がキャンバスの `transform` 層にあり portal の座標合わせが要るのに対し、これは「初めての人が一度確認する」用途で、**見た目の統一より確実に出ることが優先する**ため。不満が出たら Radix へ切り替える（`StepShapeCell` の DropdownMenu が同じ層で動いているので、機構としては通る見込みがある）。

戻り値を `questionLabels()` に混ぜて `{text, hint}` にしなかったのは、ラベルの型を変えると呼び出し側（描画・測定・ゴーストスロット）が全部動くため。**ヒントは画面専用で、出力（Markdown / Mermaid）には現れない。**

### 3. 寸法を2つ広げた

- **`QUESTION_LABEL_WIDTH` 180 → 220。** 最長の `└ 既に実行されていたら？` が 191px（「└ 」21 ＋ 11文字 154 ＋ 字下げ 16）要る
- **`RAIL_SHAPE_WIDTH` 88 → 136**（`RAIL_WIDTH` 348 → 396）。4値のうち一番長い `呼出（応答なし）` は 126px（8文字 112 ＋ `px-1.5` 12 ＋ 枠 2）要るのに 88 のままで、**折り返して `MIN_ROW_HEIGHT` 44 から食み出していた**

### 4. 「参加者」→「アクター」（177箇所・37ファイル）

**データのキーは `actors`、スキーマも `actors`、Mermaid の出力も `participant`** なのに、画面と指摘文と文書だけが「参加者」という別の語を使っていた。UI の語彙をデータの側へ寄せる。**キー名は変えていない**——もともと英語で、今回それに UI を寄せるのが目的である。

置換対象は UI 文字列・`aria-label`・整合性検証の指摘文・出力前の警告・スキーマの `description`・コメント・テスト・`SKILL.md` と、正の文書（`overview-rev` / `sequence-design-notes` / `missing-semantics` / UI設計ノート / `open-issues` / `reading-guide` / `README` / `sequence-m1-scope`）。**`docs/history`・`docs/superpowers/plans`・`docs/superpowers/specs`・`lessons-for-planning` は不変の記録なので触っていない**（当時の語で書かれたまま残る）。

`sequence-m1-scope.md` を「生きた文書」として扱ってよいかは、直前の domain 廃止コミット（`9dd4580`）が同じファイルを編集している先例で判断した。

### 5. 図の下の「ステップを追加」を実線にした

`SequenceEditor.tsx` の末尾ボタンだけが `border-dashed` だった。**rev 9章の欠落軸は線種に意味を与えている**（破線＝まだ見ていない／実線＝見たが決められない）ので、破線のボタンはキャンバス上で図の欠落要素に見える。M25 が破線チップをガターから帯へ移したのも同じ理由だった。副次であることは `text-ink-muted` で示したまま、枠だけ実線にした。

## 実装で確定した事項

### 設計メモのラベル案は2つが幅に収まらなかった——「文字数」欄が誤っていた

`question-label-redesign.md` の案の表は `既に実行されていたら？` と `応答が届かなくてもよいか？` をどちらも「9文字」と書いていたが、実際は 11文字・13文字である。推定測定器（全角＝フォントサイズちょうど。`wrap.ts:86`）で当てると、当時の `QUESTION_LABEL_WIDTH` 180 に対する上限は**非インデント12文字・インデント10文字**で、**両方とも溢れる**。

着手前にこれを検算したので、実装は「先に案を検算し、収まらないぶんを列幅で吸収する」順で進められた。**`questions.test.ts` の「立つ問いはラベル列で1行に収まる」検査が、実際にラベルだけ変えた時点で赤くなり、幅を上げた時点で緑に戻っている**（TDD の赤→緑がそのまま設計判断の検算になった珍しい例）。

### `RAIL_SPAN` はコメントが名指すだけで実体が無かった

`SequenceEditor.tsx:155` は「合計が layout の `RAIL_WIDTH` と一致していることは下の `RAIL_SPAN` で押さえる」と書いていたが、**`RAIL_SPAN` は定義も検査も存在しなかった**。レールの内訳は描画側（`SequenceEditor.tsx`）が持ち、図の左端は測定側（`layout.ts`）が `RAIL_WIDTH` で決めるので、片方だけ動かせばセルが図に侵入するか右に隙間が空く。

**今まさに両方を動かす回だったので、コメントが約束していた検算を実体化した**——`RAIL_SPAN` を内訳の積み上げとして定義し、`SequenceEditor.dom.test.tsx` で `RAIL_WIDTH` との一致を検算する。**`RAIL_WIDTH` を 395 にして赤を確認してから戻してある。**

これは M23 の「旧段を現在形で断言するコメント7行」と同型の負債である——**現在形で書かれたコメントが事実でない状態は、それ自体が実害**であり、このモジュールは「測定層と描画層が同じ寸法を持つこと」をコメントの規律で保っている。

### `GHOST_QUESTION_LABEL` は literal の複製をやめた

種別切替の残骸を出すグレースロットは「元の種別が分からないので call-sync の文言を汎用として使う」という方針で、その文言を**literal の複製**として持っていた。今回ラベルを変えるにあたり、`questionLabels({ kind: 'call', awaitsReply: true })` の戻り値そのものに置き換えた。**コメントが述べていた意図が、複製ではなくコードとして書かれている状態になった**（ヒント側の `GHOST_QUESTION_HINT` も同じ形）。

### reply 行の一般文言は「短縮して回避」に倒した

`gutterWidth = QUESTION_LABEL_WIDTH + 258` で、reply 行の一般文言はこの幅で折り返す。新ラベルを埋め込むと旧文言は 525px になり、220 でも収まらない（1行に収めるには列幅 267 以上が要り、短いラベルの右に 150px の空白が空く）。

**文言を短縮する側に倒した**: `─ 応答が返らないケースは、呼び出した側の「結果不明だったら？」に書く` → **`─ 応答が返らないときは呼出側の「結果がわからなかったら？」に書く`**（455px）。

**この一文の高さが行高に入らないこと自体は直していない**（`SequenceEditor.tsx` のコメントが以前から明記していた既知の穴）。今回作った穴ではないが、**実際に折り返して次の行へ食い込むところまで来た**ので `open-issues.md` へ立てた。`layout.ts` の `QUESTION_LABEL_WIDTH` のコメントにも「この幅は一般文言の折り返しも決める」を書き足してある。

`npm run tauri dev` で起動し、`Documents\facet\testa…` の `シーケンス.json`（4種別・11ステップ・ゴーストスロットあり）を開いて確認した。

| 確認項目 | 結果 |

| 5つの問いラベルが全て1行に収まる | ✅ `処理が失敗したら？` / `呼出が失敗したら？` / `結果がわからなかったら？` / `└ 既に実行されていたら？` / `応答が届かなくてもよいか？` すべて1行 |
