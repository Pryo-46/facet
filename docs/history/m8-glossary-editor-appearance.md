## プレースホルダの色を `text-warning` にできなかった

設計スペックの決定12は当初「`placeholder:text-warning/70` の `/70` に設計上の意味はないので外して不透明にする」だった。**実装計画を書く前にアルファ合成を実際に計算したところ、これが成立しないと分かり、着手前に決定12ごと差し替えた**（`0c15bec`）。

- `text-warning` を `warning/10` の面の上に置くと **4.59:1**。4.5 は超えるが、M7 が課した3%の余裕（4.635:1）に届かない
- **素の `surface` の上ですら 5.28:1** しかない。つまり面に少しでも色が付いた時点で余地が無い

**決着は `text-ink-muted`。** 役割トークンの定義がそのまま「抑えた文字」であり、プレースホルダはまさにそれである。「未定義を負債として可視化する」（rev 5章）は**セルの面が warning 色を持つこと**で担われているので、文字色まで warning にする必要はない。同系色の上に同系色を重ねることになり、WCAG の数値以前に読みにくい。

**合成モデルの妥当性は、既存の実測値を再現することで裏付けた。** 現行の `placeholder:text-warning/70` を同じモデル（sRGB で `fg × a + bg × (1 − a)`）で測ると **2.80:1** となり、`open-issues.md` が M7 の時点で実測として記録していた「約 2.8:1」と一致した。この一致があったので、以降の濃さの決定（`errorCell` = `/20`、`warnCell` = `/10`）をモデルの計算だけで確定してよいと判断できた。**`/25` はダークの `surface` 上で `ink-muted` が 4.58:1 に落ちるため採れない**——これが現行値を動かした直接の理由である。

この計算は `src/styles/contrast.ts` に入り、`palette.test.ts` が16通り（`{ink, ink-muted} × {warning/20, warning/10} × {canvas, surface} × {ライト, ダーク}`）を毎回検証する。半透明が機械検証の外にあった状態は M8 で終わった。

## `surface-accent` を新設し、検証集合を分けた

実機確認1周目で「カラム名の面が地味」という指摘が出て、テーブルの見出しに淡い緑を敷くことになった。**`ok`（Lichen Green）は流用していない。** カラム名は「確定・応答」ではないので、流用すると意味論が壊れる——rev 9章の「Lichen Green は `ok` 以外に使わない」の趣旨は、意味を持つ緑を装飾へ流用しないことにある。役割トークンは10個から**11個**になった（`--surface-accent`。ライト `oklch(0.87 0.04 126)` / ダーク `oklch(0.28 0.04 126)`）。

**ここで計画が誤った。** 新トークンを `palette.test.ts` の `BACKGROUNDS`（「あらゆる役割トークンが載りうる汎用の面」の集合）に足す指示を書いたため、`rule` / `warning` / `ok` がこの淡い緑の上で 3:1 / 4.5:1 を割り、テストが5件赤くなった。**実装者はトークンの値を動かさずに報告してきた**（計画どおりの正しい対応。値をいじって通していたら M7 が確定した配色が静かに壊れていた）。

正しい形は、**汎用の面と限定的な面を同じ集合で扱わないこと**である。`surface-accent` の上に載るのはカラム名の文字（`ink` / `ink-muted`）だけなので、その2つだけを個別に検証する describe を足した。汎用の面に入れてしまうと、この面の上でも要件を満たす色しか選べなくなり——**淡い緑という選択肢そのものが消える。**

## 最終レビューが継ぎ目で見つけた3件

実装11本を終えた時点の最終レビュー（`d9518bb..4e5fb37` の21コミット）は、**個々のタスクの中には欠陥を見つけなかった**。決定1〜17と残件13件はすべて実装済みで、色値の直書きもフォントサイズの逸脱も無く、レビューもすべて通っていた。それでも Important が3件出た。**すべてタスクの継ぎ目にあり、単体では3つとも正しい。**

1. **別名パネルが切り取られて到達不能になる。** Task 3 がテーブルを `overflow-hidden` で包んだ（`border-collapse` のまま角丸を切るため）。別名セルのパネルはこの div を包含ブロックとする絶対配置で、高さが行の高さを必ず上回る。**最終行で開くとパネルが下端で切れる**——横方向も、別名列と備考列を最小幅まで狭めると右端を越える。角丸は装飾で別名パネルは機能なので、**角丸をあきらめて直角にした**
2. **列幅を変えても textarea の行数が再計算されない。** Task 4 の高さ計算は value の変化を依存に取っていたが、Task 5・6 が列幅可変を足したので、**幅が変われば同じ value でも必要な行数が変わる**。列を狭めると文字が隠れる
3. **フォーカスが見えない。** Task 7 がテーブルの面を `bg-surface` にしたので、セルの `focus:bg-surface` が面の上で **1.00:1** になった。フォーカス位置が完全に消える。面の塗り替えではなく `focus:ring` に変えた——エラー・未定義セルは `bg-warning/20` `/10` の面を警告として持っているので、**フォーカスで背景を塗り替えるとその警告表示ごと消える**という理由もある

構図としては `lessons-for-planning.md` の「タスクの継ぎ目を疑う」がそのまま出た形で、M6 に続いて2回目である。**タスク単位のレビューが全部 clean でも、継ぎ目は誰も見ていない。**

## ボタンの行間の修正が、最初は何も直していなかった

実機確認1周目の指摘「ボタンのラベルが上に寄る」に対し、Task 14 は `src/index.css` の `@layer base` に `button { line-height: 1.2 }` を書かせた。**これは実質すべてのボタンに届いていなかった。** Tailwind の `text-*` は utilities レイヤーで `line-height: var(--tw-leading, <既定>)` を生成し、**cascade layers では後に宣言されたレイヤーが特異性に関係なく勝つ**ので、base に書いた宣言は `text-sm` / `text-xs` を持つボタン（＝ほぼ全部。shadcn の `Button` を含む）に一切効かない。

**`npm test` も `npx tsc -b` も `npm run lint` も緑だった。** この種の欠陥は、テスト・型検査・lint のいずれもが原理的に捕まえられない。見つけたのはレビュアーが Tailwind の実コンパイラを呼んで生成 CSS を読んだからで、コントローラも `npx vite build` の出力で裏を取った（`button{--tw-leading:1.2}` が出ていること、`.text-sm` が変数参照のままであること、直接指定が0件であること）。

**直し方は「勝つ」ことではなく「衝突させない」ことだった。** utilities 側が普段は設定しない `--tw-leading` へ逃がせば、右辺の変数として拾われるので順序争いが起きない。`leading-*` を明示したボタンは utilities 側が同じ変数を上書きするので、個別指定も従来どおり効く。

なお、この修正の初版のコメントは理由を「クラスセレクタが要素セレクタに勝つため」と書いていた。**動く直し方に、間違った説明が付いていた**ので Task 15 で直した（次に触る人が誤った理解のまま触る）。

## jsdom で検証できなかったもの

計画は「書かない判断をしたら、なぜ書けないかを記録する」（`lessons-for-planning.md`）に従い、検証できないものを事前に列挙した。結果として3種類あった。

- **5行上限（決定5）**: 高さの計算が `scrollHeight` と `getComputedStyle` の `line-height` に依存し、**jsdom はレイアウトを持たないので `scrollHeight` が常に 0** になる。実機確認に回した。実装中、`line-height` が `px` で読めない環境では折り返しが**無言で効かなくなる**ことが分かったので、実機確認の項目を「2行目が出るか」から見る形に強めた
- **ポインタドラッグ（決定8）**: jsdom は `setPointerCapture` を実装していない。**ただし担保されないのは「ポインタイベントの配線」だけである**——決定10でキーボード操作（←→ で16px刻み、Home で既定へ）を足したことで、**幅が実際に反映される経路は jsdom で検証できるようになった。** アクセシビリティのために足した機能が、副次的に唯一のテスト入口になった。この関係は rev 10章に規約として書いた
- **CSS のカスケード**: 前節のとおり。生成 CSS を読む以外に検証手段が無い

## 実機確認（人間の作業）で確定したこと

実機確認は**2周行った**。1周目で動作系（IME・列幅ドラッグ・折り返し・セル内改行・削除中に固まらないこと）はすべて問題なしと判定され、見た目と操作性で8件の指摘が出た。これを Task 14（色と共通スタイル）・Task 15（レイアウトと操作）として計画に追加し、2周目で「用語を追加」の件（Task 16）が出て、その後 OK になった。

- **テーブルの行の密度は `py-1` のまま確定した。** rev 11章が M7 から残していた検証項目で、これで決着した（rev から落とした）
- **ライトの方眼紙は濃かった。** `--grid` を canvas 上 1.36:1 から **1.17:1** へ薄めた。ダークは変更なし。`grid` は装飾なのでコントラスト要件の対象外であり、上限ではなく「うるさくないか」で決まる値である
- **ヘッダ・サイドバー・カラム名を固定した。** `App.tsx` の `min-h-screen` を `h-screen` にするのが要点——`min-h-screen` では中身が伸びるとページ全体が伸び、`<section>` の `overflow-auto` より先に body がスクロールする。`h-screen` にすればスクロールは `<section>` の中だけで起き、ヘッダとサイドバーは**何もしなくても固定される**。カラム名は `<th>` に `sticky top-0 z-10`（`border-collapse` では `<tr>` の sticky が効かない）
- **ウィンドウの最小サイズを決めた**（`minWidth: 1000` / `minHeight: 600`、初期値も 800×600 から 1280×800 へ）。固定4列の合計 736px ＋ サイドバー 256px で、**1030px 付近から備考列が切れ始める**。初期値が 800 のままだと起動した瞬間に崩れた状態から始まる。値は [`../project-setup.md`](../project-setup.md) に記録した
- **「定義｜別名」の境界が掴めなかった。** 定義列は幅を持たない（残りを埋める）ので、右端にハンドルが無かった。`getHandleProps` に `invert` オプションを足し、**幅を持たない列の右端に置くハンドルは右隣の列を逆向きに動かす**形にした——右へ引けば定義が広がる、という見た目どおりの操作になる
- **種別フィルタのボタンが透過で見えなかった。** ヘッダ領域が `bg-surface` になったので `hover:bg-surface` が同色で効かなくなっていた。非アクティブ時に `bg-canvas` を敷き、文字色を `ink-muted` から `ink` へ上げた（`ink-muted` は「抑えた文字」で、押せるものには弱い）
- **マウスだけで行を増やせなかった**（2周目）。「用語を追加」ボタンが0件の空状態にしか出ておらず、行の追加手段が Enter だけだった。常時表示にし、押した行は**末尾**に足す（`insertRowAfter(data.terms.length - 1)`。0件なら `-1` になるので従来と同じ）。導出表示中に出さないのは Enter を止めているのと同じ理由

## 繰り越した Minor の扱い

レビューで Minor として繰り越したものが9件あり、うち1件（方眼紙の機械検査が `[\s\S]*` でファイル末尾まで見ており空洞化していた）は最終レビューの fix でマージ前に直した。残る8件のうち **`open-issues.md` へ足したのは2件**（列幅ハンドルの `aria-valuenow` 欠落、`<th>` の `sticky` と `relative` の同居）で、残りは足していない。

足さなかったものと理由:

- **`drag.current` が `pointerId` を保持していない**: `setPointerCapture` がイベントを要素に固定するので、単一ポインタでは実害が無い
- **`contrast.test.ts` が `surface` / `warning` をローカルの oklch リテラルで持っている**: このテストは「合成モデルが当時の実測 2.80:1 を再現するか」を固定するもので、**過去の測定の再現である以上リテラルで正しい**（パレットを参照すると、色を差し替えたときに再現テストの意味が消える）
- **「作り直しても幅が残る」テストが単独では要件を捕まえない**: 同じ describe の他2件が先に落ちるので、要件自体は覆われている
- **`useLayoutEffect` が `multiline=false` でも呼ばれる**: `areaRef` が null で即 return する
- **テストのコメントの記述と、JSDoc の文末の言い回し**: 記録する価値が無い（幽霊残件を増やす）
