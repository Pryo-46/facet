## 実装で確定した判断

### 主修飾キー＋`Enter` を「そのセルの主たる副操作」に写像した

コアの `resolveCommand` は主修飾キー＋`Enter` を `toggle-item-state` に解決する（sequence M1 で確定）。シーケンスではこれが答えスロットの「考慮不要」に当たるが、課題ツリーには「トグルする欄」が無い。**意味の解決はコアのまま、写像だけツール側の `runCommand` に置いた**（rev 10章。sequence M2 が `Tab` の「移動先が無ければ生やす」で作った前例と同じ層）:

| セル | 主修飾キー＋`Enter` |
| --- | --- |
| 課題 | 仮説を追加 |
| 仮説の文言 | 判断イベントの種類のドロップダウンを開く |
| メモ | 最新イベントの根拠へ移す（イベント0件なら何も起きない） |
| 由来・イベントの根拠 | 何も起きない |

**退けた代替案は2つある。**

- **`Shift+Tab` に割り当てる案。** rev 10章が「`Shift+Tab` に『親にする』を割り当てていないのは意図的で、意味を与えないことでキャンバスから Tab 順で抜ける経路として残している」と明記している。ここに意味を与えると、キャンバスからキーボードで抜ける経路が消える
- **コアにコマンドを増やす案。** `src/core/keyboard/keymap.ts` に新しい語彙を足せば写像は要らなくなるが、**そのコマンドを持たないツールが3本増える**。構造依存層は「意味の集合はツールが決め、キーの解決はコアが持つ」形で、写像をツール側に置くのが規約どおりの層である

### モックの色分けを採らなかった

参考として渡された [`../issue-tree/仮説検証モック.jsx`](../issue-tree/仮説検証モック.jsx) は、イベント種別を emerald / rose / stone / sky / indigo のチップで塗り分けていた。**採らなかった理由は2つあり、どちらか片方でも成立する。**

1. **Tailwind 標準パレットは配色差し替えに追従しない。** facet の色は役割トークン（`src/styles/palette.css`）を経由し、`palette-retheme` Skill がテーマごと差し替える。`bg-rose-600` のような直書きはその外に出るので、`src/styles/conventions.test.ts` が機械的に弾く
2. **D8 が「色は使わない」と決めている。** 赤＝未定義という意味論を汚染しないための判断で、`warning` を「棄却」に流用すると**未決と棄却が同じ赤になる**——このツールが見せたい「まだ決めていない」が読めなくなる

代わりに、イベントの種類は文字ラベル（支持／棄却／自明に成立／検証せず棄却／今回見送り／本開発送り）で区別し、面は無地にした。`EVENT_KIND_LABELS` が唯一の出所で、画面・DOM テストの欄名の両方がそこを引く。

### 抑制の見せ方を「薄くする」ではなく「地の色に落とす」にした

祖先の見送りで抑制された配下は「いま作業する面ではない」ことを見せる必要がある。モックの案（`opacity` で薄くする）は採らなかった——**`opacity` は検算したコントラストを割る。** `palette.css` の役割トークンは 4.5:1 を実測して決めてあり、その上から不透明度を掛けた瞬間、保証の外に出る（同じ問題は `text-ink-muted/70` の1件として `open-issues.md` に既に載っている）。

採ったのは面の切り替えで、抑制された箱は `border-rule bg-canvas text-ink-muted`——**作業する面（`bg-surface`）ではなく地（`bg-canvas`）に落とす。** rev 9章の「地は方眼、作業する面は無地」の意味論をそのまま使っており、コントラストは検算済みのトークンのまま保たれる。面は3種類しかない（未決＝`bg-warning/10`、整合性エラー＝`bg-warning/20`、抑制＝`bg-canvas`）。

### 編集できるのはイベント列の最新要素の `note` だけにした

イベントは追記専用（D2）で、過去の要素を書き換えない・削除しない・並べ替えない。**そのままだと「追記した直後に根拠を書く」ができない**ので、`setEventNote` は**最新イベントに限って** `note` の編集を通す（`commands.test.ts` が、最新以外を指した編集が跳ね返されることを固定している）。描画側も、`data-cell` を持つのは最新イベントの根拠だけである。

誤った追記の取り消しは Undo（1操作1コミット）に委ねた。**「直せる範囲を最小にして、取り消しは履歴の仕組みに任せる」**という分け方で、イベント列が「そのとき何を根拠に決めたか」の記録であり続けることを構造で守っている。

### 仮説カードの幅を導出せず固定（320px）にした

カードの中には文言・由来・メモ・イベントの根拠という**性質の違う文章が縦に積まれる**。一番長い行に幅を合わせると、短い仮説と長い仮説でカード幅がばらつき、木が階段状に見える。**シーケンスがガター幅を導出しないと決めた**（`sequence/sequence-design-notes.md` 論点7）のと同じ判断で、`CARD_WIDTH = 320` を固定にした。代償（長い仮説は縦に伸びる）は `open-issues.md` に載せてある。

### 編集の実装をエディタ側に生やさなかった

Task 7 の実装者は、メモの `Alt+↑↓`（並び替え）に対応する関数が `commands.ts` に無かったため、同じ形の純関数 `movePendingNote` をエディタのモジュール直下に置いて報告した。**コントローラの裁定で `commands.ts` へ移した**（`359df91`）——計画の File Structure が `commands.ts` の責務を「構造編集（課題・仮説・**メモ**）とイベント追記」と定めており、編集レイヤをエディタ側に割るのは計画自身の構造と矛盾する。**エディタに残っているのは写像だけで、編集の実装は1つも無い。**

### 仮説を消したときの行き先を「持ち主の課題」にした

`deleteHypothesis` は「同じ課題に前の仮説が無い」とき `focus: null` を返す＝UI に行き先が無い。エディタは**持ち主の課題のセル**へ送っている。その課題の最後の仮説を消したときに次に打つのは、別の仮説を足すか課題そのものを書き直すかのどちらかで、宙に浮かせると続けて打ったキーがどこにも入らない。

### 削除でも並びを正規化し、根の追加ではフォーカスを参照同一性で引き直した（Task 3 の2つの裁定）

- **`deleteIssueSubtree` を `normalizeOrder` に通した。** 計画 Step 4 の逐語コード片は正規化の導入前に書かれており、「残る課題の相対順は変わらない」という前提が正規化前の入力に対して成り立たない（レビューが実データで反証した）。**スキーマが `hypotheses` の配列順を課題順と定めている以上、それを破る文書を吐く経路は残せない**——スキーマが計画のコード片に優先する
- **`addRootIssue` のフォーカスを参照同一性で引き直した。** 出力側正規化を入れたことで、循環を含むファイルのとき `focus.index` が別の実在ノードを指す退行が生まれた（移植元の `logic-tree/addRoot` には無い経路）。`null` を指すより悪い——**ユーザーが循環ノードに打ち込んでしまう**

### 見送りの行と抑制の1文はエディタのキャンバス層が描く

`layout.ts` は `IssuePlacement.deferrals`（見送りイベント1件につき1つ）と `suppressedNote` のために縦を予約するが、`IssueBox` は `rect` しか受け取らないので描けない。**Task 6 の時点で「どのタスクにも描画側の担当が割り当てられていない」という計画の欠陥**として見つかり（下記）、エディタのノードレイヤが `IssuePlacement` から直接、絶対配置で描く形に決めた。見送り行は上段が `EVENT_KIND_LABELS[kind]` を `BADGE_HEIGHT`（20px）ちょうどで、下段が `event.note`。抑制の1文は `SUPPRESSED_NOTE` を**import して**出しており（打ち直していない）、文言の出所は1つである。

### 見送りイベントの理由（課題側の `note`）を打つ経路は M1 では足さなかった

`appendDeferral` は `{kind, note: ''}` を作るが、**課題側イベントの `note` setter は無い**（仮説側の `setEventNote` だけがある）。計画の Task 3 Produces は明示的な列挙で、これを含んでいなかった。**スコープを広げずに見送る**裁定を下している。

ただし**描く側は完成している**——見送り行は `event.note` を逐語で出し、`layout.ts` が note の実測高さで行を測る（改行入りでも伸びる）。DOM テスト「見送りイベントの行を種別ラベルと理由で描く」が、`note` の入ったファイルを描いてラベルと理由の両方が画面に出ることを見ている。**次のマイルストーンの登録 Skill が書いたファイルは、そのまま正しく表示される。** 足りないのは入力の口だけで、これは `open-issues.md` に載せた。

### 計画どおりに据え置いた2件（着手前のスキャンでの裁定）

- **幾何の primitive（`Rect` / `Point` / `Size`）の再編は行わなかった。** M20 の申し送りは「課題ツリーを書き始める前に、1ファイルへ寄せるか `Rect = Point & Size` にするかを決める値打ちがある」としていたが、M20 が心配した「3本目も `edgePath({...from, ...size})` のスプレッド組み立てを書くことになる」は本計画では起きない——`layout.ts` が `Rect` リテラルを直接組み立て、`IssuePlacement.rect` をそのまま `edgePath` に渡せる。加えて型の再編は core / logic-tree / sequence を横断する変更で、本計画のどのタスクにも属さない。`open-issues.md` の `[M20]` の項は据え置いた
- **`layout.ts` の `plans: (CardPlan | null)[]` の到達不能な分岐は計画のまま実装した。** `plans` は `hypotheses` と添字を揃える配列で、「ぶら下がり先が図に無い仮説は null」という将来の拡張余地を型が表している。締めるなら実装を締める側で決める

## レビューが見つけた実際の欠陥（最も重い1件）

**判断のドロップダウンで種類を選んだあと、予約したフォーカスが `<body>` に落ちていた。**

Task 7 のレビューが「ドロップダウンのフォーカスの行き先にテストが無い」と指摘し、**アサーションを1行足した瞬間に両方の経路が赤くなった**——`document.activeElement` が `<body>` だった。原因は Radix の順序である:

> Radix の「選んだら閉じる」は**選択イベントの後に走る**ので、それまでは `FocusScope` が `focusin` を捕まえてメニューの中へ引き戻す。予約したフォーカスが当たった直後に奪われ、続いてメニューが消えるので行き場を失う。

実装が持っていた `onCloseAutoFocus` の抑止は「閉じた後にトリガーへ戻す」既定しか塞いでおらず、**開いている間の focus trap の方は塞げていなかった**。修正は `KindMenu` の `onSelect` で**先に自分で閉じる**こと（`onOpenChange(false)` を `onPick(kind)` の前に呼ぶ）。同じ更新の中で閉じれば、レイヤの撤去と `FocusScope` の後始末（レイアウト効果）が先に済み、フォーカスの予約（パッシブ効果）が最後に当たる。再レビュアーが Radix の実ソース（`react-focus-scope/index.mjs`）まで降りて、この順序が構造的に保証されることを確認している。

**テストを足さなければ実機確認まで生き残っていた欠陥である。** 実装者自身も報告に「キーボードだけで『開く→選ぶ→根拠を打つ』が通しで動くかは実機で見たい」と書いていた——つまり**「実機で見たい」と書かれた懸念が、DOM テストで捕まる範囲に入っていた**。`Cannot verify from diff` として実機へ送る前に、アサーションを1行足せないかを問う値打ちがある。

## 計画の欠陥として見つかったもの

**5件あり、いずれも実装ではなく計画が誤っていた。**

1. **Step 6 の変異チェックが、計画のテストのままでは落ちなかった**（Task 5）。「カードの高さが兄弟の間隔に効く」ことを確かめる変異を計画が指定していたが、**兄弟のテストに仮説が無く、カード積みのテストに兄弟が無い**ため、その性質を誰も見ていなかった。実装者がテストを1本足して塞ぎ、レビュアーが数値を手で再現して裏を取った。**変異チェックを書くときは、その変異を殺すテストが実在するかを1度確かめる**という教訓の実例
2. **`IssuePlacement.deferrals` と `suppressedNote` に、描画側の担当がどのタスクにも割り当てられていなかった**（Task 6 で発覚）。`layout.ts` は両方に縦の場所を予約しているのに、`IssueBoxProps`（計画が逐語で与えた形）にスロットが無い。放置すると**見送った課題が「説明のない空白」として描かれ、抑制の理由文が画面に一度も出ない**。Task 6 の修正ループには入れず、Task 7 の明示的な要件として引き継いだ（描く場所は他に無い）
3. **メモの並び替えの関数が Task 3 の Produces から漏れていた**（Task 7 で発覚）。写像表は「メモの並び替え」を求めているのに、対応する関数が `commands.ts` の産出物一覧に載っていない。**表と産出物の突き合わせが計画内で取れていなかった**形で、実装者は正しく報告し、裁定で `commands.ts` へ寄せた
4. **ブリーフのテスト例が、存在しない依存を import していた**（Task 6）。`import userEvent from '@testing-library/user-event'` と書かれていたが、**このリポジトリに user-event は入っていない**（`@testing-library/react` のみ）。逐語に従うとコンパイルできない。実装者は既存の dom テストの流儀（`fireEvent`）に正しく合わせた
5. **Task 10 Step 5 の grep の期待値が、4ファイル中2ファイルについて原理的に成立しなかった**（本タスクで発覚）。計画は `issueTree` が「4ファイルすべてに1件以上」出ることを期待していたが、**`README.md` と `docs/README.md` は type 識別子を1つも書かない文書である**——`logicTree` も `errorCatalog` も `sequence` も出てこず、ツールはどちらも日本語名で紹介されている。grep を通すためだけに `issueTree` を書き足すのは、読み手のための文書に機械検査の都合を持ち込むことなので**しなかった**。実際に効く確認は「課題ツリーの節・表の行・履歴の行があること」で、そちらで確かめた。**なお同じ grep が `overview-rev.md` については実際の反映漏れを1件掘り当てた**——5章の `type` enum の列挙に `issueTree` が無く、計画の Step 3 の表（2章・6章・10章）にもその欄は無かった。**計画が指定した章だけを直すと、enum の列挙は古いまま残っていた。** [`../lessons-for-planning.md`](../lessons-for-planning.md) の「計画が書いた確認コマンドを1回自分で実行してみる」の裏返しで、**期待値が外れた grep でも、外れ方を1行ずつ読めば別の穴が見つかる**

**同種の記録**: Task 1 のレビューが「兄弟の `logic-tree/schema.test.ts` にある正規形（`serialize` のキー順）テストが無い」と指摘したが、これは計画が Task 8 の `module.test.ts` に担当させていたもので穴ではなかった。Task 8 のレビュアーが `core/canonical.ts` の `reorder` まで降りて、実際に塞がれていることを確認している。**「兄弟にあるテストが無い」という指摘は、別のタスクが担当していないかを先に確かめる。**
