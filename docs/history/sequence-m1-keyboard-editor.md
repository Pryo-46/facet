## 実装で確定した事項

### 参照セルの `Enter` は「確定」と「行追加」の二役を持てない

`ActorRefCell`（from / to の参照セル）は、**ドラフトがある状態の `Enter` は確定だけして親のキー処理へ渡さない**（`preventDefault` して return）。ドラフトが無い `Enter` は従来どおり委譲するので、参照セルからの行追加の経路は塞がっていない。`Tab` はドラフトがあっても委譲する（確定して次の欄へ抜けるため）。

この形にしたのはレビューが実データ喪失を見つけたためである。1つの `Enter` が (1) 部品内の `commit()`（`onSelect` / `onCreate`）と (2) 操作言語の `insert-item-after` の**2経路**を通り、後者が**確定前の古い `data`** から新しいステップを作って onChange するので、先に届いた確定を丸ごと上書きしていた。未登録名を打った場合は、その場で生えた参加者ごと消えた。

**同じイベントが「部品の中で意味を持つ経路」と「操作言語の経路」を両方通るとき、順序ではなく所有権で決める**（消費したなら渡さない）というのが結論で、これは参照セルに限らない形なので [`../lessons-for-planning.md`](../lessons-for-planning.md) にも一般則として足した。

### 同じピクセルに `warning` の面を2枚重ねない（背景の帯とセルを排他にする）

行全体の指摘（`row` レベル）は背景に `bg-warning/20` の帯を敷くが、その上に文言セルの面とガターの未回答スロットの面が重なると、**検算していない濃さが画面にできる**（M8「面は片方だけ」）。排他にした形は2つ:

- **帯はガターの手前で止める**（`width: gutterX - DIAGRAM_MARGIN - CELL_GAP * 2`）。ガターのセルは3状態の面を自分で持つ層なので、行の赤はそこへ侵入しない
- **文言セルは行が赤いとき面を降りる**（`bg-canvas` → `bg-transparent`）。重ねれば2枚、`bg-canvas` のままなら帯に穴が開くので、透かして帯の1枚だけを見せる

`failures` の赤は塗りの無い枠（`border-warning`）で出すので、面の枚数に勘定しない。**帯の右端がガターのスロットの左端以下であること**は DOM の style から実測するテストで固定した。

### ガターの枠は全不透明の `border-warning`

`GutterSlot` の未回答状態は当初 `border-warning/40` だったが、これは**検算していない濃さ**であり、`palette.test.ts` の網（`bg-warning/α` しか走査していなかった）を素通りしていた。リポジトリの他の「warning の枠」（`NodeBox` の invalid、`ActorRefCell`、`SequenceEditor` の参照セル）はすべて**枠は全不透明・面だけ半透明**で揃っているので、そちらに合わせた。面の強度差（未定義 `bg-warning/10` ／ エラー `bg-warning/20`）は検算済みのまま残っている。

### 編集セル群は矢印線を中心に上下へ振り分け、ガターの手前でクランプする

from / to / 形のセルは**レイアウト層が高さを取っていない足場**である（行高は `max(ラベル高, ガタースロット群の高さ)` で決まり、編集セルのぶんを含まない）。計画どおり `arrowY + 4` から置くと、1行ラベルの行（`arrowY - top = 36`、行の帯 44）では約 21px が**次の行のラベル領域に食い込む**。矢印線を中心に上下へ振り分ける形（`top = arrowY - CONTROL_HEIGHT / 2`）に変え、こぼれる重なりを自分の行の中に収めた。代償として矢印の上のラベルと最大 7px 重なる。

X 方向は、右端の参加者が起点のステップでセル群（幅 276）がガターに被って**答えのセルが押せなくなる**ため、`gutterX - 8 - controlWidth` でクランプした。参照切れ（インデックスが引けない）のときは `DIAGRAM_MARGIN` に置く。

**レイアウトの純関数に偽の `labelHeight` を渡して行を太らせる案は採っていない**——呼び出し側からレイアウトの契約を歪めることになる。行の帯に編集セルのぶんを取るかは M2 以降のレイアウト側の判断として残す。

### 背景レイヤは境界線とライフラインの2種類を持つ

計画は背景レイヤに責任境界（`domain` の切れ目の破線）しか置いていなかったが、**ライフライン（参加者ヘッダから下へ伸びる縦線）を描く層が他に無い**（エッジレイヤは矢印だけ、self ボックスは「ライフライン上に置く」前提）。線が無いとシーケンス図にならないので実線（`border-l border-rule`）で背景レイヤに足した。破線／実線で見分けが付く。

### `awaitsReply` の欠落は `true` 扱い（問いが多く立つ側へ倒す）

スキーマ上 `awaitsReply` は `kind: "call"` で必須だが、`poseQuestions` は欠落を `true` と見なす。**安全側＝問いが多く立つ側**であり、「答えていない箇所を可視化する」というツールの目的と向きが同じである。

あわせて `questionLabels` は `reply` に**明示分岐**を置いた（3キーとも空文字を返す。空文字は「表示するラベルが無い」の意）。既定分岐へ落として3問ぶんの文言を返していると、問いがゼロの `poseQuestions` と食い違い、後続が文言だけ参照したときに幽霊の問いが出る。

### `notApplicable` は `text` キー自体を作らない

答えスロットの値は `{ decision, text }` だが、`notApplicable` で理由を書かなかったときに `text: ''` を残さない（キーを作らない）。**「キー欠落＝未定義」という表現がデータ形式の中核**なので、答えの中でも同じ規律を通す。`handled` 側は `text` 必須のまま。

### 範囲外の index では何も起きない（編集コマンド全体で揃えた）

`setActorName` / `setActorDomain` / `setStepLabel` / `setStepActor` / `setStepShape` / `createActorAndAssign` に `if (… === undefined) return d` を足し、`setAnswerText` / `toggleNotApplicable` が既に持っていた防御と揃えた（`@/core/list-ops` の方針）。ガードが無いと、分割代入が `undefined` を踏んで **TypeError** になるか、`{...undefined, name}` が **必須フィールドを欠いたレベル1違反データを静かに書き込む**。`createActorAndAssign` は**参加者を足す前**に止める——`setStepActor` 側のガードだけに任せると「参加者は生えたがステップには反映されない」半端な更新になる。

削除後のフォーカスは、参加者もステップも**前 →（先頭なら）次 → 無し**の同じ規則にした。

### 測定のキャッシュ鍵には「箱の種別」を混ぜる

同じ文字列でも、参加者ヘッダ・矢印ラベル・self ボックス・答えセルでは折り返し幅も余白も違うので、結果が違う。鍵は `` `${box}:${text}` ``（`box` は `actor` / `label` / `self` / `answer`）＋ フォントと世代。**区切り文字は `:` である。当初これを生の NUL バイトで書いてしまい、事故になった**（後述）。

### 額縁は2行の登録だけで4本目のツールを受け入れた

`src/modules/index.ts` に import 1行と `appRegistry.register(sequenceModule)` 1行。M10・logic-tree M1 に続いて3回目の実証で、`outputs: []`（出力は後の段階）・`singleton: false`（機能ごとにシーケンスを分ける）も無改修で通った。

### モジュール内に一切のクロス依存を作っていない

`grep -rn "logic-tree" src/modules/sequence/` の出力は**複製の記録コメントだけ**。`seq-font.ts` は初版が `../logic-tree/measure` を import していたが、レビューで `./measure` に直した（scope の禁止事項「共通化・抽象化を行わない」は、**裏返して依存を張ることも禁じている**——複製と依存が混ざると、あとで一般化するときにどちらが正か分からなくなる）。

## コアに入れた変更

M1 のスコープは「`core/canvas` 等への共通化・抽象化を行わない」を明示的に禁じている。それでもコアに入れたのは次の2件で、いずれも**既存の一元化された機構に意味を足す**もので、新しい抽象を作ってはいない。

### 1. `src/core/keyboard/keymap.ts` に3点（Task 5）

**(1) `KeyContext.horizontal`。** 横に並ぶリスト（シーケンスの参加者ヘッダ）で、`Alt+←→` が並び替え・素の `←→` がキャレット端で隣への移動になり、**`↑↓` は関与しない**。`hierarchical` と同時に `true` にしない。rev 10章の「同じ構造には同じ操作」を、ファミリー標準（縦のリスト）を90度回した形で満たすもので、新キーの発明ではない。

**(2) `Command` に `'toggle-item-state'`（主修飾キー＋`Enter`）。** 答えスロットの「考慮不要」が使う。意味を持たないツールは無視してよい。

**(3) `←→` が `arrowsOwnedByField` を見るようになった。** これは open-issues に「将来の機能を作った瞬間に踏む」として載っていた既知の穴で、**from / to という select 系フィールドを持つ本ツールが1本目の踏み手になった**。`hierarchical` 側の親子移動と `horizontal` 側の隣移動の**両方**にガードが要る。コメントだけが「↑↓ と同じ規則」と言っていた状態は解消し、実態が追いついた。

**既存テストとの衝突を実装者が握り潰さずに報告し、裁定した。** `keymap.test.ts` の `it('修飾つき Enter は取らない')` は `Ctrl+Enter → null` を固定しており、(2) と同じ入力で真っ向から矛盾する。裁定は「**計画が正、既存テスト側を新仕様に更新**」——根拠は、rev 10章に `Ctrl+Enter` を意図的にリザーブした記述が無く、当該アサーションは「未割当キーは null」の一般的な回帰ガードとして書かれたものであること、`Ctrl+Enter` はブラウザ既定でも何もしないので既存ツールの挙動が壊れないこと。ただし条件付きで、**`Shift+Enter` / `Alt+Enter` が `null` のままであること（用語集のセル内改行が生きる）は不変条件として残す**。テストは2本に分割され、その形で固定されている。

**`KeyContext` を組んでいる箇所は grep の実出力で5箇所**（計画は4箇所と書いていた。`src/App.tsx` が抜けていた）。logic-tree M1 でも同じ形の数え落としが起きており（3と書いて実際は4）、**計画に件数で書くと必ず外れる**という教訓が2回連続で実証された。

### 2. `src/styles/palette.test.ts` の走査パターン拡張（Task 12）

「検算していない濃さを使っていない」の検査が `bg-warning/(\d+)` しか見ておらず、**枠線や文字も半透明の warning を名乗りうる**ことを取りこぼしていた（`GutterSlot.tsx` の `border-warning/40` が実際に素通りしていた）。`(?:bg|border|text)-warning\/(\d+)` に広げた。

**使う側（`GutterSlot`）と検査の側の両方を直した。** 使う側だけ直すと今回の穴は塞がるが、次に誰かが `text-warning/xx` を書けば同じ形で抜ける。検査の側だけ広げると `border-warning/40` が未検算として赤くなり、どのみち実装を直すことになる。

**この穴は3回連続で同じ形をしている**（M10: `GlossaryEditor.tsx` 決め打ち → logic-tree M1: `*Editor.tsx` という母集合が部品を取りこぼす → sequence M1: `bg-` という**属性の母集合**が枠と文字を取りこぼす）。母集合をファイルの側で広げても、**プロパティの側にまだ狭い母集合が残っていた**。

なお `palette.test.ts` / `conventions.test.ts` が sequence 配下のファイルを実際に走査していることは、走査関数を直接呼んで**ファイル名の一覧を出力させて**確認した（計画に「確かめる手順を入れる」と書いてあった箇所で、実際に穴が見つかった）。

## 計画の誤りとして報告されたもの

[`../lessons-for-planning.md`](../lessons-for-planning.md) の「実装者は、計画の指示が矛盾していたら辻褄を合わせずに報告する」が今回も機能した。

1. **`validateAgainstSchema(schema, data)` という関数は存在しない**（Task 1、Task 10 で**2度**）。実物は `createSchemaValidator(schema)` を呼んで検証関数を得るファクトリで、先例（`logic-tree/schema.test.ts`）もその形。戻り値の `{ ok, errors }` は計画どおりだったので、呼び出し形だけを実物に合わせた。**同じ誤りが計画の別々の箇所に2回書かれていた**ため、Task 1 で直しても Task 10 が再び踏んだ
2. **`removeActor` のフォーカス式が `removeStep` と非対称だった**（Task 4）。計画は `Math.min(index, actors.length - 1)`（＝消した位置と同じインデックス）で、真ん中の参加者を消すテストと食い違った。`removeStep` の「前 →（先頭なら）次」に揃えた
3. **`writeSlot` が `notApplicable` にも `text: slot.text ?? ''` を当てていた**（Task 4）。`{decision:'notApplicable', text:''}` という、キーは在るが空という値ができ、「キー欠落＝未定義」の原則に反する。`buildAnswerSlot` ヘルパに寄せた
4. **`KeyContext` を組んでいる箇所は4ではなく5**（Task 5。上記「コアに入れた変更」）
5. **`createSeqMeasurer` は `null` を返さない**（Task 11）。計画は「null なら `createEstimateMeasurer` に落とす」と書いていたが、`seq-font.ts`（複製元の `node-font.ts` と同一）は canvas の 2d コンテキストが取れないとき**自分で概算器を返す**。エディタ側に二重のフォールバックを書くと到達不能コードになり、未使用 import で lint も落ちる
6. **編集セルの y 位置 `arrowY + 4` は次の行に食い込む**（Task 11。上記「実装で確定した事項」）
7. **`@testing-library/jest-dom` がリポジトリに無い**（Task 9 の `toHaveTextContent`、Task 11 の `toBeInTheDocument`）。既存の DOM テストは一貫して「`getBy*` が投げること＋ `toBeDefined()` / `.textContent`」で書かれている。**アサーションの強度は変わらない**（`getBy*` は見つからなければ throw し、戻り値が null になる経路は無い）ので既存の作法に合わせた
8. **`React.KeyboardEvent` に `isComposing` は無い**（Task 9）。`nativeEvent` 側と同様のキャストで解消。挙動は変えていない。**IME 対応が絡む部品を `CellInput` の外に書くと毎回踏む**
9. **計画の変異確認の想定が実挙動と食い違った**（Task 7）。計画は「`need` の割り算 `/(hi - lo)` を消せば区間分配のテストが落ちる」と書いていたが、そのテストは `gap01 === gap12`（等値）しか見ておらず、割り算を消しても等値は崩れないので**全緑のまま**だった。実装者がレビュー前に自分で見つけて絶対値のアサーションを足した

## 挿話: ソースに NUL バイトが1つ混入していた

Task 11 の修正をコミットした直後、`git show --stat` が `SequenceEditor.tsx | 1704 +++---`（＝全行差分）を出した。原因は測定キャッシュの鍵 `` `${box}\x00${text}` `` に**生の NUL（U+0000）が1バイト**入っていたこと。

- `git ls-files --eol` が `i/-text w/-text` を返す（＝git が**バイナリ判定**している）。他のファイルは全部 `i/lf`
- バイナリは正規化の対象外なので `.gitattributes` の `* text=auto eol=lf` が効かず、編集ツールが CRLF で書き戻したぶんがそのまま index に入って全行差分になっていた

区切りを `:` に直して解決（`box` は `actor` / `label` / `self` / `answer` のいずれかで `:` を含まないため一意）。**症状は「差分がおかしい」という形でしか出ず、テストも `tsc` も lint も緑のまま**である。実装者は初回コミットを amend して取り込んだ（未 push・レビュー前・残せば 1704 行の差分がレビューの邪魔になるだけ、という理由。SHA は `fc4abce` → `313a622` に変わっている）。
