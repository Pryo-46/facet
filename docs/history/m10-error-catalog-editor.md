M10 は計画12タスク（実装10本、実機確認、本ドキュメント）を完了した。目的はエラーカタログエディタ（列を持つリストエディタの2本目の実例）を作り、M9 で引き上げた共通機械が実例2本目に耐える抽象だったかを検証すること。設計判断の全体は `docs/superpowers/plans/2026-08-09-m9-m10-error-catalog-design.md` 第 II 部（決定8〜18）にあり、本書はそこから**実装・レビュー・実機確認で新たに確定した事実だけ**を拾う。

## M9 の5つの機械を2本目がどう使ったか

`duplicate` / `cell-face` / `columns` / `field-step` / `use-list-rows` はいずれもコア版をそのまま呼び、写像やロジックの再実装は無い（Task 3・4・8）。

**`stepField` だけは用語集と扱いが違う。** 用語集は `nextWidthIndex`（1引数）と `stepField`（2引数、`glossary/fields.ts`）を、自分のテーブル・順序を束ねたラッパーとして`glossary`側に残した（M9）。エラーカタログは `nextWidthIndex` は同じ形でラッパーを持つ（`PROFILE_COLUMNS[profile.id].nextWidthIndex`）が、**`stepField` はラッパーを作らず、`ErrorCatalogEditor.tsx` から3引数のコア版を直接呼んでいる**（コアのシグネチャは `stepField(order, field, direction)` [`src/core/list-editor/field-step.ts`]、実際の呼び出しは `stepField(profile.fields, at.field, 1)`）。理由は、Tab の移動先（フィールドの並び）が**プロファイルによって変わる**ため——サポート向けと開発向けで `profile.fields` の中身が違い、束ねて1引数に固定できる「1つの並び」がそもそも存在しない。ラッパーを作るとすれば、`order` の位置に固定の並びの代わりに現在のプロファイルを渡す形になり、それはコア版に薄い衣を着せるだけで抽象を増やす意味がない。この非対称は「モジュール側が自分のデータを束ねられるときだけ引数を減らす」という M9 の設計判断が、実例2本目でも一貫して機能した結果である。

## Markdown 表の整形をコアへ引き上げた

着手前スキャンでMarkdownのセル整形3関数（`cell` / `row` / `heading`）の複製が見つかり、人間の裁定で「コアへ引き上げる」と決まった（計画の Global Constraints と Task 6 にその裁定が反映されている）。Task 6 で `src/core/markdown-table.ts`（`escapeCell` / `row` / `dividerRow` / `headingText` の4関数）を新設し、用語集の `src/modules/glossary/markdown.ts` を委譲へ載せ替えた。

**用語集の `markdown.test.ts` は1バイトも変えずに緑のままだった**（`git diff d216705..HEAD -- src/modules/glossary/markdown.test.ts` の差分ゼロ）。これは M9 の5つの機械と同じ検証方法で、引き上げが振る舞いを保っていることの裏付けになる。コア版は列・フィールドの知識を一切持たない純関数のみで、`ErrorField` や `Term` 等の型を import していない。

## プロファイル宣言1本から画面と出力の列を導出する形が実装で成立した

`profiles.ts` はフィールドの並び（`SUPPORT_PROFILE.fields` / `DEV_PROFILE.fields`）だけを宣言する。画面の列（`columns.ts` の `PROFILE_COLUMNS`）は `['no', ...profile.fields]`、出力の列（`markdown.ts` の `markdownFields`）は `profile.fields` から `resolutionLevel` を除いたものとして、どちらも `profiles.ts` から導出している。列セットを2箇所に書く経路は存在せず、`OutputProfile`（コアの契約）自体は列を持たない。ずれは見つからなかった。

## 列幅ストアをプロファイルごとに2本持った帰結

`column-widths.ts` の `errorColumnWidths` はサポート向け・開発向けで別々の `createColumnWidthStore` を持つ（プロファイルごとに列数が違うため、幅配列の添字が別の列を指してしまう問題を避ける）。この設計は Task 8 の最終レビューで一度「テストが実装を固定していない」形で穴が見つかった（後述）。

**No 列にはハンドルを出さない判断も同じ設計の帰結として確定した。** `no` は編集対象ではない導出列（データ配列の `index + 1`）で、既定幅は56px（`columns.ts` の `FIXED_WIDTH.no`）。一方 `MIN_COLUMN_WIDTH` は88px（`src/modules/error-catalog/column-widths.ts`。**コアではなくモジュール側の定数**——`src/modules/glossary/column-widths.ts` にも同じ値が独立に定義されており、用語集の分とは複製の関係にある。コアの `useColumnResize`（`src/core/column-resize.ts`）はこの値を持たず、`ColumnResizeOptions.minWidth` としてモジュール側から受け取るだけ）。`resizeColumns` はクランプを `Math.min(Math.max(current + delta, minWidth), upper)` で行うため、No 列にハンドルを出せば、初回操作の向きにかかわらず56pxから88pxへ一気に跳ぶ（用語集も同じ仕組みで、この挙動自体は計画のTask 8にも「ハンドルを出すと初回操作で幅が跳ねる」と書かれている）。そのため `ErrorCatalogEditor.tsx` は `no` 列にだけハンドルを出さない分岐を明示している（`<th>` に `relative` を付けない、テーブルを包む `div` に `overflow` を付けない、という用語集の重複も再生産していない）。

## テストが実装を固定していなかった箇所が3回見つかった

いずれも「変異させたら赤くなるか」を確かめて初めて分かったもので、機械的なレビューだけでは見えなかった。

1. **Task 7（検索）**: `matches()` 内でエントリ側の値の `normalizeForMatch` を外す変異を入れても、ブリーフ記載のテスト8件は全部緑のままだった。原因はテストデータのエントリ側フィールドに大文字小文字・全角半角の揺れが無く、クエリ側の正規化だけで通ってしまうため。コントローラの裁定でエントリ側を正規化前と後で区別する固定テスト1件を追加し（`04c7620`）、変異で赤くなることを確認した。
2. **Task 8（列幅ストア）**: `ErrorCatalogEditor.tsx` の `store: errorColumnWidths[profile.id]` を `store: errorColumnWidths.support` に固定しても、既存の「プロファイルごとに幅が独立している」テストは通ってしまった。プロファイルを一度も切り替えないテストだったため、dev側が「本当に引き分けているから既定値のまま」なのか「1本固定で dev を触っていないだけ」なのか区別できていなかった。レビュー指摘を受けてプロファイルを切り替えてから両ストアの状態を確認するテストを1本追加し（`0319569`）、変異で新テストだけが赤くなること・他24件は影響を受けないことを確認した。
3. **最終レビュー（`palette.test.ts`）**: 半透明の濃さ（`errorCell` / `warnCell`）の検算テストが `GlossaryEditor.tsx` を決め打ちで読んでおり、`ErrorCatalogEditor.tsx` の同種の宣言を検査していなかった。**2本目の列を持つエディタが増えたことで、既存の機械検査が「列を持つエディタ全部」ではなく「用語集だけ」しか守らなくなっていた**という性質の穴——単体では気づきにくく、実例が2本になって初めて顕在化した。修正（`b150f31`）は `src/modules/` 配下を走査して `*Editor.tsx` を集める形にし、`ErrorCatalogEditor.tsx` の `warnCell` を意図的に変異させて赤くなることを確認した上で戻した。同時に `columns.test.ts` の2本（`widthIndex` / `nextWidthIndex`）も `support` 固定のループから `PROFILES` 全体をループする形へ揃えた（こちらは既存実装に不整合が無かったため赤くなる変異は無し）。

## `CellInput` の8行化にテストを書かなかった理由と実機確認の結果

Task 10 は `MAX_ROWS` を5から8に上げる1行の変更で、テストを追加していない。理由は jsdom がレイアウトを持たないため、`scrollHeight` に依存する行数の挙動（何行で内部スクロールに切り替わるか）をテストで観測できないこと——値を assert するテストを書いても実装値の写経にしかならず、5→8の変更を検証したことにならない。この判断は Task 10 の時点で据え置き、Task 11 の実機確認に委ねられた。

**実機確認（Task 11）は12項目すべて問題なしだった。** 行数上限8（決定17）については、長文（100文字程度）を入れて8行まで伸びてから内部スクロールに切り替わることを確認し、**初回マウントの体感（行数ぶんの強制リフロー。`open-issues.md` 性能の項）の悪化は無かった**。他の主要項目（No列が検索で動かないこと・warningの見え方・赤の指摘・プロファイル切替での列増減と横スクロール無し・**各プロファイルの列幅が独立して保持されること**（上記の列幅ストア2本構成の観測に対応）・書き出しのファイル名2種・用語集の非改修確認・単一性違反・外部変更の取り込み）もすべて問題なし。

## 決定14（画面の黄色）と決定15（出力の未定義）の食い違い、および人間の裁定

最終レビューが Important として指摘した設計上の食い違い:

- **決定14**（`isWarnCell`。画面のセルの黄色）は「関与しないレベルの Action は警告にしない」——`resolutionLevel: user` のエラーなら「サポートの対応」「エンジニアの対応」は空でも黄色くならない。根拠は「ほとんどのエラーは1レベルしか関与しないので、全部を警告にすると信号が死ぬ」こと。
- **決定15**（`errorCatalogToMarkdown`。出力の空欄）は空フィールドを一律 `（未定義）` にする。**関与しないレベルの例外規定が無い。** そのため決定14の論拠（信号を殺さない）は出力には適用されておらず、サポート向け出力は行の大半が `（未定義）` を2つ抱える結果になる。
- 画面のプレースホルダ（`CellInput` の `placeholder`）も同様に、`notes` 以外の空欄すべてに「未定義」を出す実装で、決定14が黄色くしないセルにもプレースホルダの「未定義」だけは出る。

Task 11 で人間がこの3点セット（セルの黄色・画面のプレースホルダ・サポート向け出力の `（未定義）`）を実機で並べて確認した上で、**(a) 現状のまま**を選んだ（画面と出力を割る変更はしない）。片方だけ直すと画面と出力がずれるため、3つを1つの判断として扱っている。この裁定により、`resolutionLevel: user` の行の「サポートの対応」「エンジニアの対応」は今後も**黄色くならないが `（未定義）` を出力する**という状態が意図した仕様として確定した。次にこの表を見て「なぜ出力が `（未定義）` だらけなのか」と疑問に思ったら、これが未対応ではなく実機確認済みの裁定であることをここで確認できる。
