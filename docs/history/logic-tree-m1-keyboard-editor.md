## 実装で確定した事項

### データ形式は「平坦な `nodes` 配列 ＋ `parentId`」にした

スコープは当初ノードのフィールドを `id` / `text` / `children` と書いていたが、実装では **`children` の入れ子をやめ、`nodes` を平坦な配列にして親を `parentId` で指す**形に決めた（`schemas/logic-tree.schema.json`）。理由:

- **兄弟順の正本を配列順に一本化できる**（rev 5章「配列順が表示順の正」）。入れ子にすると「配列順」が階層ごとに分かれ、並び替え（`Alt+↑↓`）の実装が親を辿る形になる
- **既存のコア部品がそのまま使える。** 用語集・エラーカタログの行操作（`src/core/list-ops.ts` の `insertAt` / `removeAt` / `moveItem`）はフラットな配列を前提にしており、平坦なら同じ関数で足りる
- **壊れたファイルが表現できる。** 循環・多重ルート・親の参照切れは入れ子の JSON では**構造上書けない**——書けないということは、外部（AI・手書き）が壊したファイルを読み込めず**レベル1拒否**に倒れるということである。平坦なら受け入れて赤表示（レベル2）にできる（rev 5章「拒否は解釈不能な場合に限る」）

代償は「木の形が JSON を上から読んでも分からない」ことで、これは次項の正規化で埋めた。

### 配列は編集のたび DFS 行きがけ順へ正規化する

`orderNodes`（`src/modules/logic-tree/commands.ts`）が、編集コマンドの中で毎回配列を**深さ優先の行きがけ順**へ並べ替える（兄弟の相対順は変えない）。得たものは2つ:

- **JSON を上から読むと木の形が追える。** 平坦化の代償を消す
- **挿入位置の規則が1本になる。** 行きがけ順では「参照ノードの部分木の直後」が、兄弟追加の位置でも末尾の子の位置でもある。`subtreeEnd()` 1つで `addChild` / `addSiblingAfter` / `moveSibling` の全部が書ける

**循環して根から到達できないノードは、末尾に元の順で残す。消さない**——ファイルにあるものが黙って減るのが一番たちが悪いため。

### 入力欄は常に `<textarea>`（「フォーカスされている＝編集中」）

ノードは「表示モードとダブルクリックで入る編集モード」を持たない。`NodeBox` は常に `CellInput`（用語集のセルと同じ部品）を置き、フォーカスがある状態がそのまま編集中である。IME・ドラフト・Undo の反映は `CellInput` が1箇所で持つ（rev 10章 IME 対応）。

副作用として、キャンバスの `Space+ドラッグ` は**ノードにフォーカスがある間は文字入力に取られる**（`useViewport` の `isTextEntry` 判定）。これは rev 10章 境界規則（テキスト編集中は Space が文字）そのままの帰結で、意図どおり。

### ルートの上の `Enter` は兄弟ではなく子を足す

`addSiblingAfter` はルート（`parentId === null`）に対しては `addChild` へ委譲する。ルートに兄弟を作ると多重ルートになり、「単一ルートの木」という制約と両立しないため。空状態でルートを1つ作った直後に `Enter` を押す動作は会議中の典型であり、ここで何も起きないと止まる。

### 空欄 `Backspace` は部分木ごと消す（確認ダイアログなし）

葉に限らない。M1 にはドラッグも右クリックも無いため、削除を葉だけに限ると**誤って作った枝を消す手段が消える**。確認ダイアログは挟まない（rev 5章。会議中の入力速度を削ぐため）——1操作1コミットの Undo が受け皿である。フォーカスの行き先は削除**前**の位置で決める（前の兄弟 → 親 → 無し）。

### 整合性検証に `missing-parent` を足した（スコープからの意図的な追加）

スコープが挙げた3つ（ID重複・循環・ルートの単一性）に加え、**親の参照先が実在しない**ケースを別コードで足した。循環と参照切れは原因も直し方も違うのに、どちらも「根から到達できない」で同じメッセージになると、画面を見た人が何を直せばよいか分からないため。

### 出力プロファイルは0本（コードを1行も足さずに成立した）

`logicTreeModule.outputs` は `[]`。Markdown / Mermaid 出力は M2 の担当である。**額縁側は無改修で正しく振る舞った**——`ExportMenu` は `outputs.length > 1` でなければ `outputs[0]` を取り、`undefined` なら両ボタンを `disabled` にする既存の分岐を持っており、0本のモジュールでは押せるボタンが出ない。M9 の規約5（`outputs` の配列化）が「まだ出力を作っていないツール」まで含めて成立していたことの裏付けになる。

`singleton: false`（プロジェクトにロジックツリーは何本あってもよい。用語集・エラーカタログと違いハブではない）。

### 額縁は2行の登録だけで新ツールを受け入れた

`src/modules/index.ts` に import 1行と `appRegistry.register(logicTreeModule)` 1行。M10（エラーカタログ）と同じ結果で、rev 6章「新ツールの追加はコアの改修ではなくモジュールの追加」が**図系という別ファミリーのツールでも**成立した。

## コアに入れた変更

M1 のスコープは「`core/canvas` 等への共通化・抽象化を行わない」を明示的に禁じている。それでもコアに入れたのは次の4件で、いずれも**既存の一元化された機構に意味を足す**もので、新しい抽象を作ってはいない。

### 1. `KeyContext.hierarchical`（`src/core/keyboard/keymap.ts`）

rev 10章の「階層・リスト系ファミリー標準」のうち、**`Tab`＝子追加と `←→`＝親子移動は「子」という意味を持つ構造でしか成立しない**。用語集はフラットなリストなので `Tab` はセル移動である。この分岐を各ツールの自前ハンドラに置くと操作言語の一元化規約（rev 10章 実装規約）が崩れるため、`KeyContext` に真偽値を1つ足して `resolveCommand` の中で分けた。

**計画は `KeyContext` を組んでいる箇所を3つと数えていたが、実際は4つあった**——`src/modules/glossary/AliasCell.tsx` が別名チップの入力欄で独自に組んでいた。`hierarchical: false` を渡す形で対応し、レビューでこの判断が正しいことを確認した（`true` にすると `Tab` が `focus-next-field` を奪い、別名パネルから Tab で抜けられなくなる）。

`Shift+Tab` に「親にする」を割り当てなかったのも確定事項である。意味を与えないことで、キャンバスから Tab 順で抜ける経路として残る。

### 2. `CellInput.autoSize`（`src/components/CellInput.tsx`）

`CellInput` は `scrollHeight` を読んで自分で `rows` を決める。ロジックツリーは**測定層が幅と行数を先に確定させている**（1パスで描くための前提。tech-notes 論点4）ので、再計測されると測定層の結論が上書きされる。呼び出し側が高さを決められるよう `autoSize?: boolean`（既定 `true`）を足し、`NodeBox` は `autoSize={false}` を渡して高さを CSS で当てる。

### 3. `src/styles/palette.test.ts` の検査の作り直し

半透明の濃さ（`errorCell` / `warnCell`）の検算テストが `src/modules/**/*Editor.tsx` だけを走査していたため、ロジックツリーで2つの穴が同時に開いた:

- ロジックツリーは**表を持たない**ので「セル」という単位が無く、赤表示の面を当てているのはエディタ本体ではなく `NodeBox.tsx`（部品側）である。`LogicTreeEditor.tsx` に定数が無いだけでテストが落ちた
- その結果、対になる検査「検算していない濃さを使っていない」が `NodeBox.tsx` を**一度も見ない**。部品側に `bg-warning/35` のような未検算の濃さを書いても素通りする

走査対象を `src/modules/` 配下の `.tsx` 全部（テストを除く）へ**広げ**、定数の束縛検査のほうは「宣言しているファイル」に限定した上で `declaring.length > 0` を足した。**検査を通すためだけに使わない定数を `LogicTreeEditor.tsx` へ置く道は取っていない**——それは検査を騙す行為であり、`noUnusedLocals` で `tsc` も落ちる。

M10 でも同じ性質の穴が出ている（`palette.test.ts` が `GlossaryEditor.tsx` を決め打ちしていた）。**実例が増えるたびに、既存の機械検査の走査基準が「全部」ではなく「今あるものだけ」を意味していたことが露見する**という形が2回続いた。

### 4. `src/core/registry.ts` の JSDoc

`outputs` が0本でもよいこと（＝出力を作っていないツールの正しい状態）を明記しただけで、コードは変えていない。

## 計画の誤りとして報告されたもの

`docs/lessons-for-planning.md` の「実装者は、計画の指示が矛盾していたら辻褄を合わせずに報告する」が今回も機能した。実装者が握り潰さず報告したものは次のとおり。

1. **d3-zoom の既定 `filter` の記述が v2 時代のものだった**（Task 11）。計画は「既定の filter は Ctrl+ホイールを弾く」と書いていたが、v3.0.0 の既定は `(!event.ctrlKey || event.type === 'wheel') && !event.button` で、**Ctrl+ホイールは既定でも通る**。差し替え自体は別の3つの理由（素のホイールでズームさせない・素の左ドラッグをパンにしない・中ボタンを通す）で必要だったのでコードは正しく、JSDoc だけを直した。なお「既定の `wheelDelta` が ctrl 付きに10倍を掛ける」（1ノッチで4倍になる）は今も真である
2. **`Enter` / `Tab` のテストが `addChild` との差を検出できなかった**（Task 10）。計画のテストは葉の直後に足す形だったため、`addSiblingAfter` を `addChild` に差し替えても**配列位置もラベルも一致してしまい**、緑のままだった。`parentId` を見る形へ直した
3. **`↓`・`→` のテストがキャレット端に無く、実装後も落ちたままだった**（Task 10）。jsdom は selection を 0 に初期化し、React の同値代入では動かない。`setSelectionRange` を明示して端に置く必要があった
4. **`useViewport` のシグネチャが Interfaces と食い違った**（Task 11）。計画は `useViewport(ref)` だったが、rev 10章の境界規則（モーダル中は操作言語を停止）を満たすには外から止められる必要があり、`useViewport(ref, enabled)` にした
5. **`KeyContext` を組んでいる箇所が3つではなく4つだった**（Task 7。上記「コアに入れた変更」参照）
6. **`CellInput.autoSize` の JSDoc に書かせた「5行上限」が誤り**（Task 8）。`MAX_ROWS` は M10 で8に変わっている。計画本文の古い記述をそのまま引き継いだもので、**誤った数値がソースにコミットされたまま M1 を終えた**（`open-issues.md` に移した）
7. **計画が `palette.test.ts` の存在を織り込んでいなかった**（Task 9）。落ちると予告されていたのは `FileList` / `App` / `registry` / `conventions` で、実際に落ちたのはそのどれでもなかった

| Task 10 | `preventDefault` が消えても全緑／`caretAtStart` を `true` 固定にしても全緑／`Shift+Enter` の改行と `move-item-down`・`focus-prev` が無検証 |
| Task 11 | キャンバス内のボタンの Space が潰れていた／`focus()` がコンテナをスクロールさせ transform と二重に動く恐れ／`enabled` で d3 が張り直される変異が捕まらない |

**「jsdom ではテストできない」という申し送りは、2回とも誤りだった。**

- Task 9 の「`document.fonts.ready` の測り直しはテストできない（観測点が内部状態しかない）」→ レビュアーが実際に書いて反証した。観測点はノード矩形の `style.width` にあった（`LogicTreeEditor.font.dom.test.tsx`）
- Task 11 のブリーフは「d3-zoom の配線はユニットテストが難しい」としていたが、実装者が先に観測点を探した結果17本書けた。`new MouseEvent({ view: window })` が jsdom で弾かれる（`window === globalThis` で jsdom の `Window` インスタンスではない）という環境の穴だけを `Object.defineProperty` で埋めれば、既定の `wheelDelta` の10倍も素の左ドラッグのパンも DOM に出る

`preventDefault` は特殊で、**jsdom では結果（スクロールしないこと）を観測できない**。窓は別にあり、`fireEvent` の戻り値（`false` ＝ 既定動作が抑止された）を見る。
