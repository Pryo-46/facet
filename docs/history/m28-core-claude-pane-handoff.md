# M28 申し送り: Claude Code ペインへのファイル受け渡しと右クリック

> **追記専用。** そのとき何が起きたかの記録であり、以後変えない。**いま開いている残件は [`../open-issues.md`](../open-issues.md) を見ること**——本書に書かれた残件は当時の状態を指す。

M28 は、Claude Code の端末ペインへファイル参照を渡す動線を3本（起動時の自動差し込み・ファイル一覧の `@` ボタン・エクスプローラからのドラッグ＆ドロップ）作り、端末の右クリックを OS（WebView2）の既定メニューからコピー／貼り付けの1動作へ置き換えたマイルストーンである。設計の中心は「4つのトリガーをすべて `term.paste(文字列)` という1本の口へ集約する」ことで、判断そのものは [`../superpowers/plans/2026-08-29-m28-claude-pane-handoff-design.md`](../superpowers/plans/2026-08-29-m28-claude-pane-handoff-design.md) と [`../overview-rev.md`](../overview-rev.md) にある。**本書には書かない**（設計の再掲はしない）——ここに書くのは実装・レビュー・実機確認で**新たに確定した事実**だけである。

## 実装で確定した事項

### 1. `ESC[?2004h` は「貼り付けを受け付ける準備ができた」の合図ではなかった

M28 最大の落とし穴で、決着までに4回の実機確認と3回の外れた推測を要した。

1. **設計の見通し**: 設計文書 §2.1 は「`term.paste()` を通せば bracketed paste（`ESC[200~`…`ESC[201~`）で囲まれ、`@` のファイル検索ポップアップに食われる懸念が減る」としていた。§4.3 は「まず `spawn` 解決直後に書く素朴版を実装し、消えたら『最初の出力から N ms 静穏』へ差し替える」という見通しだった。
2. **1回目の実機確認**: **起動時の差し込みだけ**末尾のスペースが消えた。会話中に押す `@` ボタン経由では起きない——**この非対称が最初の手がかりだった**。xterm が貼り付けを囲むのは、アプリが DECSET 2004（bracketed paste 有効化）を送った**後だけ**（`node_modules/@xterm/xterm/lib/xterm.js` を実読して確認）。起動時の差し込みは `claude` の TUI が立ち上がる前なのでこの条件を満たさず、1文字ずつ打たれたのと同じに見えて `@` の補完に食われる。
3. **1回目の修正（`bfd2a63`。外れ）**: PTY の生バイト列から `ESC[?2004h` を探し、見つかってから起動時の差し込みを流す形にした（5秒の上限つき）。**直らなかった。**
4. **2回目の修正（`c893eb5`。外れ）**: 直前の修正は起動時の差し込みにしか効いておらず、起動中（約1秒）に `@` ボタンを押した会話中insertionは2004を待たずにそのまま流れていた。保留を単一のスロットから順序つきの列に変え、2004 を見るまでは `initialText` と `insertion` の両方をそこへ積む形にした。**それでも直らなかった。**
5. **3回目の修正（`4eed1c5`。外れ）**: 自前でバイト列一致を取っていたのが構造的に誤りだと判明した——DEC private mode は `CSI ?1049;2004h` のように**複数パラメータをまとめて送られる**ことがあり、パラメータ付きエスケープシーケンスをバイト列の完全一致で探すのは原理的に取り逃がす。xterm は解析済みの `modes.bracketedPasteMode`（`typings/xterm.d.ts` の公開 API）を持っているので、`term.write(bytes, callback)` の callback（パーサが処理し終えた合図）でそれを読む形に変え、自前検出（`BRACKETED_PASTE_ENABLE` / `containsSequence` / `concatBytes` / `tailBytes` 等）を全て削除した。**それでも直らなかった。**
6. **診断（`472f63c`）**: 「差し込みを試していない」のか「試しているが Claude 側に残らない」のかを切り分けるため、差し込みの経路の節目ごとに一時的な診断トースト（`M28診断:` 接頭辞。既存の `onError` の口を再利用）を仕込んだ。**1回の実機テストで、`term.paste()` は呼ばれているのに Claude の入力欄に残らないことが確定した。**
7. **真因（`2db4cfb`）**: `claude` は端末を raw mode にする**初期化の一環として** bracketed paste を有効にする。これは REPL の入力欄を作るより**前**に起きる。つまり `ESC[?2004h` は「端末の設定を済ませた」を示すだけで、**必要条件ではあっても十分条件ではなかった**。
8. **決着**: 「2004 を見た**かつ**出力が **500ms**（`INSERTION_QUIET_MS`）途切れた（＝描き終えて入力待ちになった）」で流す。上限は 5 秒から **8 秒**（`INSERTION_MAX_WAIT_MS`）へ延ばした。定数はどちらも `src/components/TerminalTab.tsx` にある。右クリックの貼り付けはこのゲートに通さない——それは人が「いま貼る」と決めた操作で、上限まで黙って遅らせる方が消えるより悪いという判断（`c893eb5`）。
9. **後始末（`a63a73e`）**: 実機で3ケース（起動時・起動中の `@`・通常の会話中の `@`）とも解決を確認し、診断トーストを削除した。

**次にこの周辺を触る人が同じ経路を辿り直さずに済むよう、4と7が「なぜ間違いだったか」を明記した**——4は「パラメータ付きシーケンスを生バイト列の一致で探す」という**手法**の誤り、7は「2004＝準備完了」という**前提**の誤りで、質が違う。

### 2. 推測で3回直して3回とも外し、診断を1回入れて確定した

**これが本マイルストーン最大の教訓。** 実機でしか再現しない不具合に対し、原因の切り分け（計測）を後回しにして修正を重ねた結果、**人間に8回も実機で試させた**（設計段階の確認2回＋上記の1〜3回目の修正の再確認3回＋診断トーストでの確認1回＋最終修正の確認1回＋診断削除の確認1回）。診断トーストを1回入れただけで、「差し込みを試していない」のか「試しているが Claude 側に残らない」のかが即座に分かれ、真因（8-7）に到達した。詳細な教訓化は [`../lessons-for-planning.md`](../lessons-for-planning.md) へ追記した。

### 3. `dragDropEnabled` は既定 `true` のまま——facet は HTML5 D&D を1箇所も使っていない

実装・レビューの過程で `grep -rn "draggable\|dataTransfer\|DragEvent\|onDragStart\|onDrop" src/`（テストファイルを除く）が**0件**であることを確認した。Windows ではこれと Tauri のドロップイベントが排他（`dragDropEnabled: false` にしないと HTML5 D&D が効かない）なので、既定のままで失うものが無いという設計判断（設計 §6.1）は実装時点でも成立していた。

### 4. Tauri を触るコードは `src/fs/*` に置く規則が、テストによって守られた

設計文書は当初 `App.tsx` から `getCurrentWebview()` を直接呼ぶ記述だったが、jsdom には Tauri のグローバル（`window.__TAURI_INTERNALS__`）が無く**同期 throw** し、`App.dom.test.tsx` の既存テストが例外で落ちた。`src/fs/drag-drop.ts`（`src/fs/app-window.ts` と同じ形）へ寄せ、`onDragDrop` を `async` 関数にすることで解決した——**`async` 関数の中で throw させると同期 throw が拒否された Promise になり、呼び出し側の `.catch()` が普通に効く**（`a8279d9`。コントローラの裁定G）。

### 5. 終了済みのタブがアクティブなとき、`@` が死んだ PTY へ書きに行っていた（最終レビューで発見）

`markExited` / `markFailed` はセッションを台帳に残し `activeId` も指したままにするので、`activeId` の null 判定だけでは「アクティブなタブが実際に生きているか」を判定できない。設計 §5.2 の手順2「タブが**無ければ**新規に起こす」は、正しくは「**実行中のタブが無ければ**」だった。実装は `isSessionRunning` で判定する——**問いは「他に生きたタブがあるか」（`hasRunning`）ではなく「いま宛先にしようとしているタブが生きているか」**である。`hasRunning` を使うと、他のタブが実行中でもアクティブでなければ、渡した先が画面に出ていないタブになりうる。`351ce0e` で修正済み。

### 6. テスト用セレクタを DOM のクラス名で書いて失敗した

計画が指定した `container.querySelector('.min-h-0.flex-1')` は `TerminalTab` の外側ラッパにも一致し、文書順で先に来るそちらを掴んでいた。**`term.open()` が受け取った要素をモックで捕まえる**形（`src/components/TerminalTab.dom.test.tsx` の `hostEl`）へ変更した——クラス名や並び順ではなく、「xterm が実際に描画先として受け取った要素こそが端末の中身の定義そのもの」という実際の契約に結び付けた。壊れたときに静かに別要素を掴むのではなく、大きな声で落ちる形にした。

### 7. 端末の配色をダーク固定にした（M17 の反転）

人間が実機（ライトのアプリ）を見て、端末だけは黒いままの方が読みやすいと判断した（`bfd2a63`）。M17 で確定した「端末も facet の役割トークンに合わせる」を反転する形になる。実装は `.dark` を付けた非表示の使い捨て要素を `document.body` に一時的に挿し、`getComputedStyle` で読んでから外す（`src/components/TerminalTab.tsx` の `buildDarkTerminalTheme`）——カスタムプロパティは継承するため、アプリがライトのときでもダーク側の値が取れる。色の出所は `palette.css` のままで、**変換式（`src/styles/contrast.ts`）を2本持たない**という M17 の方針も維持している。アプリのライト／ダーク切り替えにはもう追従しないので、`TerminalTab` / `TerminalPane` からアプリのモードを渡す `dark` props の連鎖は削除した。**この読み方は `.dark` が「素のクラスセレクタ」であることに依存する**——`:root.dark` のような詳細度の高い形へ変えると、`document.body` の子に付けた `.dark` はトークンを再定義しなくなり、端末の配色が黙ってライトへ戻る（`palette.test.ts` はこの経路を検査していない）。

### 8. ドロップはペインが見えているときだけ効く。`@` ボタンは畳んでいても効く

`terminalPaneRef` は畳んだ状態だと `display: none` で矩形が 0×0 になり、`getBoundingClientRect()` による位置判定が**必ず「外」**と出るため、畳んだ状態からドロップだけでペインを開くことはできない（設計 §6.4 が「開いて起動するところまで面倒を見る」としていた見通しから動いた点）。一方 `@` ボタン（設計 §5.2）は、押した時点で `paneOpen` を true にしてから `insertion` / `openTerminal` を進めるので、矩形の有無に依存せず畳んでいても効く。**同じ「ファイルを渡す」動線なのに、トリガーによって「畳んでいても効くか」の規則が違う。**

### 9. `readClipboardText` は「空」と「失敗」を区別しない

`tauri-plugin-clipboard-manager` の `readText()` はクリップボードが空のときも読み取りに失敗したときも例外を投げ、メッセージ文字列を解析しないと両者を区別できない（非公開の文言への依存は新しい負債になるため、見分ける改修はしなかった。`351ce0e` でのコントローラの裁定）。`src/fs/clipboard.ts` の `readClipboardText` は `try/catch` で一律に空文字へ倒す。結果、`TerminalTab` の貼り付け失敗の経路（`onError` → トースト。設計 §7.3）は**本番では到達不能**になっている——`clipboard-manager:allow-read-text` が capabilities から外れると、右クリック貼り付けは**画面に何も出さないまま無反応になる**。

### 10. App レベルの DOM テストは、xterm モックの共有配列で差し込みを観測した

`App.dom.test.tsx` は `@xterm/xterm` を差し替え済みだが、`new Terminal()` は**タブごとに別のオブジェクトを返す**ため、そのままでは `term.paste()` の呼び出しを外から観測できない（`351ce0e` で「App レベルで会話中の差し込み経路を通るテストが1本も無い」ことが判明し追加）。`vi.hoisted(...)` の戻り値に共有配列 `pasted: string[]` を持たせ、xterm モックの `paste` がそこへ push する形で解決した。
