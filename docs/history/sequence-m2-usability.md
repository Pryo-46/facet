## 実装で確定した事項

### `Alt+↑↓` を止めていたのはコアではなく部品側の矢印消費だった

open-issues に「答えスロットで `Alt+↑↓` を押すとステップが並び替わる」「`StepShapeCell` で形を変えられるのは `↑↓` だけ」として残っていた2点は、**`src/core/keyboard/keymap.ts`（`resolveCommand`）側の問題ではなかった**。`keymap.ts` の `ArrowUp`/`ArrowDown` 判定は当初から `if (e.altKey) return ctx.reorderEnabled ? 'move-item-up' : null` という形で、**全セルに対して並び替えコマンドを返す**契約になっている。実際に並び替えを止めていなかったのは、`StepShapeCell.tsx` / `ActorRefCell.tsx` が `onKeyDown` の中で修飾キーの有無を見ずに `ArrowUp`/`ArrowDown` を丸ごと自前で消費し、`onFieldKeyDown`（親の `handleKey` 経由で `resolveCommand` に渡る経路）へ委譲していなかったことにある。

Task 4 の修正は2段構えにした: (1) 部品側の矢印判定に `!e.altKey && !e.ctrlKey && !e.metaKey && !e.shiftKey` を足し、修飾キー付きは委譲するようにする。(2) `SequenceEditor.tsx` の `handleKey` が組む `KeyContext` に、固定 `reorderEnabled: true` ではなく **セルの種類ごとに明示的な値**（actor/label/ref/shape → `true`、answer → `false`）を持たせる。**コア（`src/core/`）は一切変更していない**——「意味の解決はコアのまま、写像だけツール側」という構造依存層の適用例がここでも成立した。

### `Tab` の「次の欄が無い」ケースはツール側の写像で埋める

**ステップ0件のときだけ、末尾アクターの `Tab` が『最初のステップを生やして from へ』になる**（設計確定事項2）は、`src/core/keyboard/keymap.ts` に手を入れずに実装できた。シーケンスは全欄で `hierarchical: false` なので `Tab` は常に `focus-next-field` / `focus-prev-field` のどちらかに解決される（「子」を持つ構造ではないため、階層構造の `Tab`＝子追加の意味は最初から無い）。`SequenceEditor.tsx` の `runCommand` に `focus-next-field` の case を1つ足し、「末尾アクター かつ ステップ0件」という条件のときだけ `addStepLast` を呼んで from へフォーカスする形にした。**1件以上ステップがあるときは従来どおり DOM 順の Tab に任せ、この case は何もしない（`false` を返して消費しない）。**

アクター行の割り当て自体（`Enter`=追加・`Tab`=欄移動）は**変えなかった**。ブレストで「ヘッダは横並びなので `Tab`=追加・`Enter`=移動にしてはどうか」という案が出たが、ファミリー標準（rev 10章。階層・リスト系は `Enter`=追加・`Tab`=子/欄移動）との衝突があるため現状維持で決着した。sequence M1 の実機確認で出た同じ観察の再確認にとどまり、操作言語全体の議題としては持ち越したままである。

### brief の「ステップ2の答え」は reply でスロットが無く、テスト対象を読み替えた

Task 4 の brief は答えスロットからの `Alt+↑↓` 無効化テストの例に「ステップ2の答え」を挙げていたが、`doc()` フィクスチャのステップ2は `kind: 'reply'` で、reply の答えスロットは0件（sequence M1 で確定した「応答待ち呼出に3スロット・投げっぱなしに1・reply に0・self に1」の仕様どおり）。`getByLabelText(/ステップ2の答え/)` は存在しないため、答えスロットを持つ**ステップ1**（`call-sync` で3スロット）に読み替えて検証した。並び替え無効化という検査目的自体はどの行の答えスロットでも同じであり、実質的な逸脱ではないと判断した。

### `readAnswer` は `SequenceEditor.tsx` 内のローカル関数のまま統合しなかった

`readAnswer`（描画用）は `commands.ts` の `readSlot`（編集用、非公開）とほぼ同じロジックの重複だが、Task 1 の時点で既に存在していた既知の負債であり（sequence M1 の history に記録済み）、本マイルストーンのスコープ外として触れていない。`consistency.ts` も同じ読み方を自前で持っており、これで3本目の重複になる。負債を増やしてはいないが解消もしていない。

### ghost がある行では reply の一般文言を省略した（layout.ts 無改変の制約から）

Task 9 の brief は「立っていない答え」のグレースロット（ghost）と行の一般文言（reply の「─ 応答が返らないケースは…」等）の**共存/省略はどちらでもよいが選択を報告すること**としていた。実装は**省略**を選んだ。

理由: `layoutSequence`（`layout.ts`）は今回も無改変の契約であり、「一般文言の高さ」を一切知らない。一般文言は `row.top + GUTTER_HEADING_HEIGHT` の固定 top に描く一方、ghost の `y` は `row.slotTops[...]` から取るが、`row.slotTops[0]` も同じ `row.top + GUTTER_HEADING_HEIGHT` から始まる（`layout.ts` のスロット積み上げ規則）。**共存させると一般文言と1本目の ghost が同じ座標に重なる。** `layout.ts` を触らずに避ける方法は「一般文言の分だけ ghost の y をずらす」個別オフセットを `SequenceEditor.tsx` 側に持ち込むしかなく、brief が明示的に許した「省略」の方が実装・見た目とも単純で、`layout.ts` 無改変の制約とも整合すると判断した。

具体的には、`view.answers.length === 0` だった一般文言の表示条件を `view.answers.length === 0 && view.ghosts.length === 0` に変更した。ghost が1件でもあれば一般文言は出さず、ghost 自体（打ち消し線付きの問いラベル＋答え＋✕）がその行の唯一の説明になる。テストもこの形で固定した（`reply 行でも立っていない答えがグレースロットで出る（行内表示＝ブレスト決定7）`は、一般文言が出ないことを確認する形にアサーションを調整した）。

### 種別を戻すと答えは通常スロットに復活する（データは種別切替で消えない）

sequence M1 から確定していた「種別切替で `failures` を消さない」（黙って消さない。`↑↓` の巡回で答えが破壊されないため）という仕様の上に、Task 9 は「立っていない答え」をグレースロット（ghost）として可視化し、削除は `ConfirmDialog` の確認を挟む形にした。種別を元に戻すと、`unposedAnswers` が空集合になり ghost は消え、`readAnswer` 経由で元の答えが編集可能な通常スロットとして復活する。sequence M1 の open-issues に残っていた「種別を切り替えると『立っていない問いへの答え』の警告が出るが、その答えを画面から直接消す手段が無い」は、この機構で解消した。

### self の to-mismatch は行の帯（row）に統一した

reply の unposed-answer は上記の ghost 機構が行内で扱うため専用表示を作らなかった一方、**self ステップに `to` が残っている（to-mismatch）指摘には行内に対応するセルが無い**（self ステップは to セルを持たない）ため、行の帯（`stepHas(index, 'row')` の `border-warning` の帯）に指摘を落とす形にした。`invalidStepFields` の構築ループを `rawField` → `field` の2段判定に変え、`self` の `to` 指摘だけ `'row'` に読み替える形で実装した。

### 種別切替直後の行内の赤枠は廃止し、ghost 機構に一本化した

sequence M1 の「種別を切り替えると直前に打った自分の答えが即座に赤バナーになる」という弱さ（実機確認で判明）に対し、`stepHas(index, 'failures')` を条件にしていた行内の赤枠 `<div>`（`border-warning` の囲い）は削除した。`invalidStepFields` への `'failures'` の写像自体は残しているため、`stepHas(index, 'failures')` は呼び出し元がいなくなっただけで、単に `false` を返す到達不能な経路として残っている。切替直後の主表示はグレースロット（ghost）に一本化され、バナー（整合性検証）は引き続き別途出る。

## 計画の誤りとして報告されたもの

1. **Task 2 の「self-call の3本が落ちる」という想定は誤りだった。** brief は `consistency.test.ts` に追加する5本のテストのうち「self-call の3本が落ちる」と書いていたが、実際に落ちたのは新規追加した肯定アサーション1本のみ。残り2本（「from が参照切れのときは出さない」「self には出ない」）は self-call ルールが未実装の段階でも「self-call が出ない」ことを検証する**否定アサーション**であるため、実装前から論理的に自明に緑だった（何も実装していない状態で「出ない」ことを確認するテストは、実装前から通って当然である）。実装者はこれを計画の矛盾として報告しつつ、テスト設計上の言い回しの粗さと判断し、実装方針への影響は無いとした。
2. **Task 1 の brief のサンプルコードに型キャスト漏れがあった。** `presentAnswers(bare)` の呼び出しに `as SequenceStep` のキャストが付いておらず、`tsc -b` が TS2559（弱い型に対する構造的重なり無しの代入）で落ちた。`unposedAnswers(bare as SequenceStep)` 側の既存キャストと平仄を合わせ、`presentAnswers` 側にも同じキャストを追加して解消した。ロジックの変更ではなく機械的な修正。
