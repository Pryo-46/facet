## 実装で確定した事項

### 1. Tauri の同期コマンドは main thread で走る（Task 6）

`pty_write` が `sessions` の Mutex を握ったままブロッキング書き込みをする件は、**症状（「詰まった端末を殺せない」）は正しかったが、原因は錠前ではなくスレッドだった。**

`tauri-macros` 2.6.3 の `src/command/wrapper.rs` を読むと、コマンドの既定は `ExecutionContext::Blocking`（`:50` の `execution_context: ExecutionContext::Blocking`）で、`kind` は `"sync"` になる（`:266`）。**main thread の外へ出るのは `ExecutionContext::Async` の側だけ**で、そちらは `:249` から `body_async`（＝`respond_async_serialized`）へ行く——`(async)` を付けた同期関数が `"sync_threadpool"`（`:264`）、真の `async fn` が `"async"`（`:265`）と kind の名前が分かれるだけで、**どちらも同じ `body_async` を通る**（`:248-266` の2つの `match` を並べて読むこと）。**PTY のコマンド4本（`pty_spawn` / `pty_write` / `pty_resize` / `pty_kill`）はすべて既定の `Blocking` のまま**なので、そもそも IPC 側から同時に走ることがない——`sessions` の錠前は IPC の間では競合しない。

したがって Task 6 で消えたのは「`pty_write` と `pty_kill` が同じ錠前を取り合う」という**設計上の欠陥**であって、「**詰まった端末を必ず殺せる**」という保証ではない。書き込みが本当に返らなければ、後続の IPC ごと main thread で止まる。

**`#[tauri::command(async)]` は採らなかった。** 投げた瞬間に複数の `pty_write` が待たれずに撃たれるため、**打鍵の到着順の保証を失う**（`TerminalTab` は `void ptyIo.write(...)` で待たずに撃つ）。打鍵の並び替えは、塞ごうとしていた穴より重い。根治は「セッションごとの書き込みスレッド＋エラーを `Channel` で返す」だが、それは設計 決定13（書き込み失敗をタブの中に出す）の**同期的なエラー経路を作り替える**変更なので、本マイルストーンではやらず `open-issues.md` へ残す穴として書き直した。

実装は書き手を `Arc<Mutex<Box<dyn Write + Send>>>`（`SharedWriter`）へ隔離し、`sessions` の錠前は書き手を取り出した時点で外す形。`pty_kill` 側も `remove` の結果を先に束縛して、`killer.kill()` が錠前の外で走るようにした。

### 2. `killAllPtys` の取りこぼしは、世代と待ち合わせの両方が要る（Task 3）

`src/fs/pty.ts` の `live` への登録は `pty_spawn` の解決後なので、invoke が in-flight の間に全殺しが走ると素通りする。**片方だけでは足りない:**

- **世代（`generation`）だけ**だと、解決後に投げる kill が `killAllPtys` の解決より後になり、アプリ終了経路（`interceptClose` → `killAllPtys` → close）に**間に合わずに孤児が残る**。
- **in-flight の待ち合わせだけ**だと、待ち合わせが済んだ後に spawn 側が `live.add(id)` してしまい、**空にしたはずの台帳に1本だけ生き残る。**

両方入れた。kill を飛ばすのは `killAllPtys` の1箇所だけにして、spawn 側は「台帳へ入れない」だけにする（二重に飛ばさない）。`generation` は**単調増加のカウンタ**であって真偽値のフラグではない——全殺しはアプリ終了だけでなくフォルダ切替でも走るので、立てっぱなしにすると次のフォルダの端末が台帳に載らなくなる。

### 3. 計画が書いたテスト5本は、世代ゲートを丸ごと落としても全部緑のまま通った（Task 3・レビューが発見）

`pty_kill` が飛ぶという事実は**待ち合わせだけで満たされ**、「全殺しのあとに載る」形のテストは逐次実行なのでゲート無しでも通っていた。**識別力のあるテストを1本足した**（`7e3c0ec`）——レースのあともう一度 `killAllPtys()` を呼び、同じ id へ kill が飛ばないこと（＝台帳に幽霊が残っていないこと）を見る形で、`generation === startedAt` を一時的に外すとこのテストだけが落ちることを実測した。

### 4. `TerminalTab` の cleanup が kill するようになったことで、既存の M11 テストの assert が成立しなくなった（Task 2）

`src/App.dom.test.tsx` の「確認待ちの間にタブが自然終了しても壊れない（古い ptyId で kill を呼ばない）」は `expect(ptyKillMock).not.toHaveBeenCalled()` だったが、**呼び出し元が2つ（`closeTerminalNow` と cleanup）になったので「0回」は成立しない。** `expect(ptyKillMock.mock.calls).toEqual([[1]])`（ちょうど1回・id は 1）へ変えた（`642b64c`）——M11 の退行（controller が自然終了前の古い ptyId で殺す）が戻れば2回になるので、**識別力は保たれる。**

余分な kill が無害であることは確認済み: `pty_kill` は既に消えた id に対して `sessions.remove` が `None` を返すだけで何もせず、`next_id` は単調増加なので他人の PTY を殺すこともない。

**代替案「`onExit` で `ptyIdRef.current` を null にする」は退けた**——`send()` が書き込み先を失って入力を待ち行列へ溜め続け、終了後に打った文字のエラーがタブに出なくなる（設計 決定13 に反する）。

### 5. `src/styles/contrast.ts` の契約を変えた（Task 5）

JSDoc は「色の検証に使う計算。**アプリの実行時には使わない**（テストからのみ呼ぶ）」だったが、**xterm は `oklch()` を解釈しない**ため、役割トークンを sRGB の16進へ変換する必要がある。変換式を2本持たないために、契約のほうを「主な用途は色の検証だが、**実行時にも1箇所から呼ぶ**」へ書き替えた（`toHex` の「判定には使わない」という但し書きは残したまま、oklch を解釈しない相手へ色を渡す用途を追記）。

`contrast.ts` は `.claude/skills/palette-retheme/scripts/palette-fit.mjs` から Node の型ストリップで import されているが、**アプリ側の import が1本増えることはその制約（消去可能な構文しか書かない）に影響しない。**

### 6. 端末の ANSI 16色は持たない（Task 5）

流し込むのは**面（`--surface`）・文字（`--ink`）・カーソル（文字と同色／その上に乗る文字は面と同色）・選択の面（`--surface-accent`）の4系統**だけ。ANSI の16色は facet の役割トークン（11個）に対応物が無く、持つと「配色を差し替える」作業が「16色を選び直す」作業になり、`palette-retheme` Skill の前提も壊れる。代わりに xterm 自身の `minimumContrastRatio`（`TERMINAL_MIN_CONTRAST = 4.5`。rev 9章が本文に課している値と同じ）に任せた。

**トークンが1つでも読めなければ `buildTerminalTheme` は `null` を返し、xterm の既定に落ちる**——半端に流し込むと面だけ変わって文字が読めない端末になる。jsdom では `getComputedStyle` が空文字を返すので、**スタブを置かないテストはこの経路を通る**（配色を検査するテストは `window.getComputedStyle` を差し替えてトークンを返させている）。

ライト／ダークの切り替えは `dark` prop を「**読み直す合図**」として受け、色そのものは prop で渡さない（色は `palette.css` が持つ）。

### 7. フォルダ切替の後始末を `switchFolder` の1本に寄せた（Task 4）

`hasRunning`（`starting` / `running` しか見ない）は**確認ダイアログの要否だけ**に使い、後始末はどちらの経路も `switchFolder` を通す。**帰結として、端末を1本も使っていなくてもフォルダを切り替えるとペインが畳まれる**（`switchFolder` が `setPaneOpen(false)` を呼ぶため）——これは意図した変更である。

初回の「フォルダを開く」でも `killAllPtys()` / `closeAll()` を通ることになるが、レビューが実装を読んで無害であることを確認した（空の `live` / `inflight` では `invoke` が1本も飛ばない）。

### 8. このプロジェクト初の Rust テストを入れた（Task 6）

`src-tauri/src/pty.rs` に `#[cfg(test)] mod tests` を置いた。実物の `openpty()` で master を1つ作り（**子プロセスは起動しない**）、書き手（`BlockingWriter`）と killer（`FakeKiller`）は偽物にして、「書き込みが詰まっている間に `kill` が返るか」を見る。

**`cargo test` は `npm test` に含まれない**ので、明示的に回す必要がある（[`../../CLAUDE.md`](../../CLAUDE.md) の検証コマンドに1行足した）。

## 実装の過程で出たこと

- **計画のテストコードには Rust のコンパイルエラーが2件あった**（`move` 不足。E0373 / E0505）。実装者が機械的に修正した——`let state = &state;` を置いてから両方のクロージャを `move` にする形。
- **計画は「古い錠前の実装では2秒で FAIL する」と書いていたが、実際には無期限にハングした。** `std::thread::scope` は panic を伝播する前に spawn したスレッドの join を待つが、古い錠前ではその2本とも錠前待ちで畳めない。**退行したときに固まるテストは診断が読めない**ので、判定（`done_rx.recv_timeout`）を先に取り、`gate_tx.send(())` で書き込みを解放してから assert する形へ直した（`0414a4d`）。直した後、錠前を一時的に戻して**2.01秒で期待どおりのメッセージを出して落ちる**ことを実測した。

## レビューが挙げて deferred にした minor

いずれも実害が無いか到達性が低いと判断して直していない。以下の5件は**本書にのみ残す**（開いている残件ではなく、当時の判断の記録である）。

- `pendingRef` は StrictMode の2つの effect 実行で共有される。捨てられた側に打たれた打鍵が生き残った側の PTY へ流れうるが、**データを落とさない側に倒れている。**
- 通常のタブ閉じ経路でも kill が2回飛ぶ（`closeTerminalNow` と cleanup の両方）。冪等なので無害。
- exit 先着と `killAllPtys` の窓が重なると `pty_kill` が2箇所から飛ぶ。同じく冪等。
- `src/App.dom.test.tsx` の「確認待ちの間にタブが自然終了しても壊れない」の冒頭に置いた `ptyKillMock.mockClear()`（現 394 行）は冗長——同ファイルの `afterEach`（186 行）が既に clear している。
- 初回のフォルダ選択でも `closeAll` が新しいオブジェクト参照を作るので、1回だけ無駄に再レンダリングされる。

残る2件は**開いているテストの穴**だったので、本書だけに置かなかった（`docs/history/` にだけ書かれた残件は幽霊になる——[`../../CLAUDE.md`](../../CLAUDE.md)）:

- `src/core/terminal/theme.test.ts` の「1つでも読めなければ null」テストが、`--surface-accent` **単独**の欠落を踏んでいない件は、**最終レビューの fix wave で閉じた**（同テストに1ケース足し、`selectionBackground` を null ガードから外すと**そのケースだけが落ちる**ことを実測した）。
- 「二重に kill しても無害」（Task 2 が依存する性質）を**直接踏む Rust テストが無い**件は、`open-issues.md`「テストが無い箇所」へ `[M17]` として移した。現状の保証は `pty_kill` の実装（`sessions.remove` が `None` を返す）という構造だけである。

## 教訓

[`../lessons-for-planning.md`](../lessons-for-planning.md) の「設計判断の扱い」に1つ足した——「**錠前の粒度を直す計画を書いたら、そもそも競合しうる主体が2つ以上いるかを1回問う**」。上記「実装で確定した事項」1 を一般化したもので、**「Aを直せば症状Bが消える」と書くときは、AとBの間に本当に因果があるかを実物で1回確かめる**という規則にした。

**最終レビューの fix wave で、同じ節にもう1つ足した**——「**計画に『実物の何行目に何がある』と書くなら、その範囲を実際に開いて、主張した事実がそこに含まれることを確かめる**」。M17 で実装ではなく計画に由来した欠陥は2件（`CLAUDE.md` へ足させた `cd src-tauri` の一行が後続の手順を壊す／`wrapper.rs:248-266` という引用範囲にその事実が無い）で、どちらも**計画が断定した細部が再導出されないまま転記される**という同じ形だった。

Task 3 の「計画が書いたテスト5本が、ゲートを落としても全緑だった」件は**既存の教訓の再現**（「計画にテストコードを載せるなら、実装を壊したときに落ちるかを計画時点で自問する」／「区別したい2つの実装が同じ答えを返す入力を、テストデータに選ばない」）であり、新しい規則としては足していない。
