# 仮説検証モジュール 設計ノート

作成日: 2026-08-22（設計セッションの引き継ぎ文書）
ステータス: スキーマ確定（`issue-tree.schema.json`）・実装計画未着手

確定事項の補足: type は `issueTree`、IDプレフィクスは `issue_` / `hypothesis_`（略語なしで既存に揃えた）。イベントは `{kind, note}` のみでIDを持たない（参照の必要が観察されたら schemaVersion 改訂で後付け）。

---

## 背景と動機

エピック開発の流れが「PoCで検証 → 作るものを決めて本開発」という構造になった（組織のプロセスとして確定しつつある）。これにより、仮説検証の記録は単なるメモではなく**本開発の仕様書の上流入力**になる。

かつてPRDを不採用にした理由は「自由記述中心で構造化度が低く、facetの強みと合わない」だった。仮説検証は違う。「課題 → 仮説 → 検証 → 結論」という構造が自然に存在し、会議速度で入力され、結論が下流の仕様（ロジックツリー・エラーカタログ）から「なぜこの設計か」という形で指される。**PRDで満たせなかった "What" の構造化を、検証という事実ベースの形で部分的に実現する。**

モジュール採用の3基準はすべて満たす:

1. 参照グラフに参加する（課題・仮説は用語集を指せる／意思決定ログから指される予定）
2. 未決を自分で解決できる（ただし検証には実験のリードタイムが挟まる点は既存モジュールと性質が異なる）
3. 会議速度の入力制約が適用される（選定会議・スプリントレビューでのリアルタイム入力）

### 価値の整理（3本柱）

| # | 価値 | 効き始めるタイミング |
|---|------|-------------------|
| 1 | **PoC終了判定の根拠が構造で見える。** 結論のない課題（未決）が残っていれば判定材料が欠けている、と一覧で分かる | PoC終了判定時 |
| 2 | **本開発の仕様に「なぜ」の根が生える。** 本開発のロジックツリー等から棄却された仮説まで遡れる | 本開発開始後 |
| 3 | **会議中に検証の全体像を共有できる。** まだ光っている葉＝残タスク一覧 | 使い始めた瞬間 |

弱点として価値1・2は回収が遅いが、PoC開始が迫っているため、価値3だけでも今作る理由になる。

### 想定される運用サイクル

1. 課題の洗い出し（ツリーが伸びる。葉すべてに warning が立つが、これは正常な状態）
2. 課題に対する仮説出し（warning が仮説カードで埋まる）
3. いくつか課題を選んでPoC作成＆レビュー（選ばれなかった仮説には見送りイベントを追記）
4. リファインメントで検証結果を記録（追記型イベント）
5. 新たに浮上した課題・仮説を追加 → 1へループ

## 確定した設計判断

### D1. 仮説はどのノードにも付けられるが、「仮説は？」の問いが立つのは葉だけ（折衷案）

3案をモックで比較して決定:

- **A. 葉限定**: 中間ノードへの「当たりをつける」仮説が制約違反になり、形式的な子ノードを作る迂回入力を強いる。会議速度と相性が悪い → 不採用
- **B. どこでも可＋全ノードに問い**: 分解によって責務を子へ渡した中間ノードまで未決扱いになり、warning がノイズ化する → 不採用
- **C. 折衷**: warning の総数が「本当に埋めるべき穴の数」と一致する → **採用**

シーケンスの「どの問いが立つかは矢印の種類から決まる」パターンの応用。ここでは「子の有無」が問いの有無を決める。

### D2. 仮説はミュータブルな状態を持たない。単一の追記専用イベント列だけを持つ

当初「支持／棄却／検証中」のような状態フィールドを検討したが、導出元のない手動ステータスは更新忘れで嘘をつく。次に4値enum（検証せず棄却／自明に成立／今回見送り／本開発送り）を検討したが、「見送り理由は追記する」という運用実態から、**すべてを単一のイベント列に統合**した。

イベントの種類（**issue-tree-m3 で5語に畳んだ後の姿**。当初は下の表に「検証せず棄却」「自明に成立」「本開発送り」が並んでいた——なぜ落としたかは D5・D6 に書いた）:

| `kind` | 種類 | 由来 | 付随情報 |
|--------|------|------|---------|
| `supported` | 支持 | スプリントレビュー／選定会議 | 根拠（実測値でも経験知でもよい） |
| `rejected` | 棄却 | スプリントレビュー／選定会議 | 根拠（同上） |
| `onHold` | 保留 | スプリントレビュー | 判断できなかった理由（D11） |
| `deferred` | 見送り | 選定会議 | 理由（本開発へ送るつもりなら、その行き先も `note` に書く。D5） |

仮説の現在ステータスは**最新イベントから導出**。イベントがゼロ件なら未決（「検証結果は？」warning）。**未決は `kind` として保存されない**——0件であることからの導出であり、`enum` に席を持たない。

この統合が自動的に解決すること:

- **何回見送られたか** → イベント列を数えれば導出できる（今はビューを作らない。必要が観察されたら後付け）
- **判断の覆り** → 「棄却 → 半年後に新イベントで復活」が履歴を消さずに表現できる。永久確定をスキーマで強制しない
- **「今回も見送り、理由も同じ」** → 何も追記しない。触らないことがデフォルトで、それでデータが嘘をつかない

### D3. 課題ノードにも見送りイベントを付けられる。配下への抑制は導出

「親が見送りだから葉も見送り」は保存すべき値ではなく**導出**（`crossesBoundary` と同じ判断）。見送りは最上位の課題ノードに一度だけ付け、配下の warning 抑制は「祖先に見送りがあるか」から計算する。子に値をコピーすると、親の見送り解除時に子が取り残される（更新忘れの嘘の再発明）。

### D4. スプリント参照は持たない

スプリントは facet 内に実体がなく、参照させるにはスプリント管理エンティティの新設（スコープクリープ）か手入力文字列（検証されないラベル）しかない。時系列はイベントの**配列順**が既に持っており、厳密な日時は Git のコミット履歴が正の源。「スプリント横断ビュー」の需要が実際に観察されたら、スキーマバージョニングで後付けする。

### D5. ~~「今回見送り」と「本開発送り」は区別する~~ → **区別しない（issue-tree-m3 で反転）**

**当初こう決めた。** どちらも warning を消すが、**復帰するタイミングが違う**から `kind` を分ける:

- 今回見送り → 次のPoC選定会議で拾い直される
- 本開発送り → PoCフェーズ中は戻らない。**PoC終了時に本開発へ引き渡す宿題リストの材料**になる（価値2への接続点）

**issue-tree-m3 の実装が済み、人間が初めて実機の画面で一巡した直後に反転した。** `deferredToMainDev` は**データごと廃止**し、見送りは `deferred` の1語だけになった（`deferralEvent.kind` は `["deferred"]`、`judgementEvent.kind` は `["supported","rejected","onHold","deferred"]`）。**紙の上では「復帰のタイミングが違う」で十分な理由に見えたが、実際の画面では、見送りを付けるたびに2択を強いられる一方、俯瞰の読み——この枝はこのエピックの外——はどちらを選んでも同じだった。** 選ぶ側の迷いという費用が、区別から得られるものを上回った。

**替わりの記録先は `note` である。** 本開発へ引き渡すつもりの見送りも `kind` は `deferred` で、**行き先は `note` に書く**。価値2への接続点は失っていない——宿題リストを作るとき読むのが `kind` ではなく `note` になっただけであり、そもそも「どこへ・どんな条件で・誰に引き渡すか」は enum の1語では表せない情報だった。**再び `kind` へ昇格させるなら、その必要が実際に観察されてからにする**（D2 の「見送り回数のビュー」と同じ扱い）。

### D6. 未決の意味論は既存モジュールと同一（**ただし「検証不要と決めた」の型区別は issue-tree-m3 で反転**）

「未決は間違いではなく、その時点の正しい状態」。warning として見え続けるが出力は止めない。**この部分は変わっていない。**

**当初はここに続けてこう決めていた**——「検証不要と決めた（自明に成立／検証せず棄却）」は未検証と**型で区別された確定判断**であり、エラーカタログの `none` / `undecided` と同じ構造である、と。そのために `supportedWithoutTest` / `rejectedWithoutTest` を `kind` に置いていた。

**issue-tree-m3 で、この2語をデータごと廃止した**（D5 と同じく、人間が実機の画面を見た直後の判断）。**「実験して支持した」と「経験知で自明に成立とした」は、俯瞰で読みたいこと——この仮説は成り立つのか——が同じで、違うのは根拠の中身だけだった。** 根拠の中身は `kind` ではなく `note` に書くものである。したがって**検証の有無は型では区別されず、`note` に書かれた文章として残る。**

**それでもエラーカタログとの構造の対応は生きている。** `none` / `undecided` に当たる区別を持っているのは、いまも**イベントがあるか無いか**である——`events` が0件＝未決（`undecided` の側）、1件でもあれば確定判断（`none` の側）。**失われたのは確定判断の内側の細別だけ**で、「決めた／決めていない」を型で分ける構造そのものは動いていない。

### D7. 仮説に `rationale`（発想の由来、自由記述）を持たせる

発散フェーズで「なぜこの仮説が生まれたか」を残す。価値2（本開発から「なぜ」を遡る）の材料。**入力は必須にせず、空でも warning は立てない**——由来の欠落は仕様の穴ではないため。

### D8. 議論の焦点はデータに保存しない（色は意味の数だけ）

レビューで「いまどの課題を説明中か」の共有は、選択ハイライト＋フォーカスモード（選択サブツリー以外を薄くする）等の**純粋なビュー状態**で実現する。色相は足さない。意味を持つ色相は2つ——`warning`（注意が要る＝開いている）と `ok`（確定）——のまま、**判断の群は塗りと枠の形で分ける**: 支持＝`ok` の塗り／棄却＝`ink` の塗り（反転。棄却は失敗ではなく入力なので叫ばない）／保留＝`warning` の実線の枠／未決＝`warning` の破線の枠／見送り＝`ink-muted` の枠。未決を面で塗らない（新しい木は全部が未決なので、面で塗ると警告が情報を失う）。抑制された配下は `opacity` ではなく明度の段 `ink-faint`（3:1 を実測）で薄くする。見送りを掲げた課題自身の面とバッジ・理由の行は薄くしない——バッジが「なぜ配下が薄いか」を説明する役なので、説明ごと薄くすると理由が読めなくなる。見送り箱へ入るエッジも実線のまま、配下へ出るエッジだけを破線にする。**見送りが入れ子になっても（配下自身が見送りを掲げていても）、配下の判定は「祖先のいずれかに見送りがあるか」でのみ行う**——「自分が見送っていないか」では代用しない。自分の見送りの有無で判定すると、入れ子の内側で薄い配下の上に濃い箱が挟まる退行を招く（実装で一度実際に踏んだ）。（issue-tree-m3 で確定。それまでは「色を使わない」で、6種を文字ラベルだけで区別していた）なお、フォーカスモードの状態は JSON に保存しない（消し忘れフラグ＝嘘データの温床。座標を保存しないのと同じ判断）。

### D9. FBメモは「判断イベントの下書き」として `pendingNotes` に持つ

スプリントレビューはSH同席で成立・棄却をその場で判断する場。進行（全デモ→一件ずつ議論＆決定）は変わり得るため、**進行をデータ構造に焼き込まない**。データが持つのは進行非依存の最小事実のみ：

- 仮説は、まだ判断に紐づいていないメモ（`pendingNotes`）を持てる
- 判断イベントが下されるとき、メモは**選択的に**イベントの根拠へ移動し `pendingNotes` から消える（雑談メモを公式根拠に昇格させない選別の余地）
- `pendingNotes` が空でない仮説には warning が立つ＝**レビューの締め忘れ検出**
- 独立した `kind: "memo"` イベントは作らない（「最新イベントからステータス導出」の芯を壊すため）

メモは一時UI状態ではなく短命な永続データ（会議の中断・延期で持ち越すためJSONに書く）。

副次的な導出：「今日のレビューで判断すべき仮説」＝未決かつ見送られていない仮説。レビュー用アジェンダは既存データから導出でき、新しい状態は不要。

### D10. 俯瞰の表現——箱は課題だけ、仮説は行、判断は1つ、FB は複数

キャンバスに載る物の種類（課題・仮説・判断・見送り・由来／根拠／FB）を形の種類に対応させる: 課題＝箱（エッジが出入りする唯一の物）／仮説＝箱の中の1行（左に点、右端に判断のバッジ1つ）／見送り＝課題タイトル右のバッジ＋理由の行／由来・根拠・FB・以前の判断＝**展開した仮説だけ**の内側パネル。展開は純粋なビュー状態で、同時に1つ（JSON に書かない）。**「判断の履歴」という見出しは使わない**——判断は最新1つとして見せ、2件目以降は「以前の判断」。データは `events`（判断）と `pendingNotes`（FB）の2配列のまま（統一しない。issue-tree-m3 の批評で決定）。箱自体は見送りで薄くしないが（D8）、中の仮説行は自分の見送りを含めて薄くする——「この課題はもう追わない」は配下の仮説にも及び、未決の問いを立てないのと同じ理由による。

**俯瞰の語と展開の語は、いまは同じである。** 当初の作りでは「俯瞰のバッジは5語に畳み、展開した仮説では**正確な種別**（7種）を出す」という対比があった。**D5・D6 の反転で保存する種別が5語ちょうどになったので、この対比は消えた**——`EVENT_KIND_LABELS`（保存された `kind` → 語）と `BADGE_LABELS`（俯瞰のバッジ群 → 語）が同じ言葉しか持たず、展開したパネルの「以前の判断」の行にも、俯瞰のバッジと同じ語が出る。**それでも2つの定数は畳まず、別々に置いてある**——鍵が違い（`JudgementKind` と `BadgeGroup`。`未決` は保存されない導出値なので後者にしか席が無い）、**俯瞰と詳細をまた別の言葉に分けたくなったとき、片方だけ動かせるようにしておくため**である（課題側の `ISSUE_DEFERRED_LABEL` を別に置いているのと同じ理由）。**いまの一致は偶然であって統合ではない**ので、`derive.test.ts` に「一致が黙って崩れないこと」を見るテストを置いた——落ちたら、割るのか揃えるのかを決めてから検査を直す。

### D11. 「保留」は理由付きの判断イベント（`onHold`）

見たが判断できなかった、は誰かがそう決めた事実であり、イベント無し（未決）とは区別する。保留は仮説にだけ付く（課題の見送りとは別）。理由を `note` に書く——空の保留は次のレビューに何も渡さない。集計では未決と別に数える（問いは4種: 仮説なし／未決／保留／未判断）。**この判断そのものは D5・D6 の反転を受けていない**——`onHold` は5語のうちの1つとして残っている。

版番号については、**当初「enum の拡張だから」という理由で schemaVersion を 2 に上げた**（このリポジトリ初の版上げ。読み込み時の移行は `src/core/load.ts`）。その後 D5・D6 の反転が同じブランチの中で `supportedWithoutTest` / `rejectedWithoutTest` / `deferredToMainDev` を落としたので、**2 は「拡張」ではなく「語彙を5語に確定した改訂」になった**。版番号は上げ直さず **2 のまま再定義**してある——2 はこの未マージのブランチで作った版で、一度も公開されておらず**壊すべき契約が無い**ため。1 → 2 の移行は版番号を書き換えるだけのまま据え置き、**廃止した種別を持つファイルは移行後の検証で弾かれる**（＝開けない。読み替えを足すと「もう無い区別」がデータの中に別の顔で生き残る）。

## スコープ

### IN

- スキーマ定義（`schemas/` に追加、型生成パイプラインに乗せる）
- 課題ツリーの編集（ロジックツリーのキャンバス基盤を再利用: キーボード入力・導出レイアウト）
- 仮説＋イベントの入力UI
- 未決 warning（D1のルール＋D3の抑制導出）
- 登録用 Skill（既存3本の雛形に倣う: ID採番・スキーマ検証・正規形書き出し）
- **sample-project への追加** — 同じ採用題材で、わざと未決を残した `issueTree` ファイルを1本。「仕込んである未決」表への追記もセット
- **README-for-AI.md への追記** — スキーマに書けない読み方の規約をここに置く（未解決論点5の回答）:
  - 課題＝観測された事実・ギャップ／仮説＝支持・棄却を判定できる主張。ただし入力時は厳密に区別させない
  - `pendingNotes` は判断待ちの下書きであり、AIが勝手に判断イベントへ昇格させない

### OUT（観察後に判断）

- **Markdown出力** — 本当に必要になるのはPoC終盤（結果を意思決定の場に持ち込むとき）。それまでが観察期間
- **意思決定ログからの参照機構** — 指される側のデータが正規形で残っていれば後から張れる
- **見送り回数などの導出ビュー** — イベント列から導出可能。需要の観察待ち
- **スプリント横断ビュー** — 同上（D4）

## 未解決の論点（次セッションへ）

1. **スキーマの具体形。** ツリー構造の表現（ロジックツリーのスキーマとどこまで揃えるか）、イベントの `kind` enum の命名、理由フィールドの構造
2. **課題・仮説から用語集への参照。** ラベル内の用語をどう指すか（既存ツールの方式に従う想定だが未確認）
3. **意思決定ログとの分担の再確認。** 「検証結果（事実）」と「作るものを決める（意思決定）」は別工程。事実と決定が食い違うケース（棄却されたのに採用等）を表現できる分担にする——という方針は維持だが、意思決定ログ自体の設計はまだ
