# 仮説検証モジュール 設計ノート

作成日: 2026-08-22（設計セッションの引き継ぎ文書）
ステータス: スキーマ確定（`issue-tree.schema.json`）・実装計画未着手

確定事項の補足: type は `issueTree`、IDプレフィクスは `issue_` / `hypothesis_`（略語なしで既存に揃えた）。イベントは `{kind, note}` のみでIDを持たない（参照の必要が観察されたら schemaVersion 改訂で後付け）。

---

## 背景と動機

エピック開発の流れが「PoCで検証 → 作るものを決めて本開発」という構造になった（組織のプロセスとして確定しつつある）。これにより、仮説検証の記録は単なるメモではなく**本開発の仕様書の上流入力**になる。

かつてPRDを不採用にした理由は「自由記述中心で構造化度が低く、facetの強みと合わない」だった。仮説検証は違う。「課題 → 仮説 → 検証 → 結論」という構造が自然に存在し、会議速度で入力され、結論が下流の仕様（ロジックツリー・エラーカタログ）から「なぜこの設計か」という形で指される。**PRDで満たせなかった "What" の構造化を、検証という事実ベースの形で部分的に実現する。**

モジュール採用の3基準はすべて満たす:

1. 参照グラフに参加する（課題・仮説は用語集を指せる／意思決定ログから指される予定）
2. 未決を自分で解決できる（ただし検証には実験のリードタイムが挟まる点は既存モジュールと性質が異なる）
3. 会議速度の入力制約が適用される（選定会議・スプリントレビューでのリアルタイム入力）

### 価値の整理（3本柱）

| # | 価値 | 効き始めるタイミング |
|---|------|-------------------|
| 1 | **PoC終了判定の根拠が構造で見える。** 結論のない課題（未決）が残っていれば判定材料が欠けている、と一覧で分かる | PoC終了判定時 |
| 2 | **本開発の仕様に「なぜ」の根が生える。** 本開発のロジックツリー等から棄却された仮説まで遡れる | 本開発開始後 |
| 3 | **会議中に検証の全体像を共有できる。** まだ光っている葉＝残タスク一覧 | 使い始めた瞬間 |

弱点として価値1・2は回収が遅いが、PoC開始が迫っているため、価値3だけでも今作る理由になる。

### 想定される運用サイクル

1. 課題の洗い出し（ツリーが伸びる。葉すべてに warning が立つが、これは正常な状態）
2. 課題に対する仮説出し（warning が仮説カードで埋まる）
3. いくつか課題を選んでPoC作成＆レビュー（選ばれなかった仮説には見送りイベントを追記）
4. リファインメントで検証結果を記録（追記型イベント）
5. 新たに浮上した課題・仮説を追加 → 1へループ

## 確定した設計判断

### D1. 仮説はどのノードにも付けられるが、「仮説は？」の問いが立つのは葉だけ（折衷案）

3案をモックで比較して決定:

- **A. 葉限定**: 中間ノードへの「当たりをつける」仮説が制約違反になり、形式的な子ノードを作る迂回入力を強いる。会議速度と相性が悪い → 不採用
- **B. どこでも可＋全ノードに問い**: 分解によって責務を子へ渡した中間ノードまで未決扱いになり、warning がノイズ化する → 不採用
- **C. 折衷**: warning の総数が「本当に埋めるべき穴の数」と一致する → **採用**

シーケンスの「どの問いが立つかは矢印の種類から決まる」パターンの応用。ここでは「子の有無」が問いの有無を決める。

### D2. 仮説はミュータブルな状態を持たない。単一の追記専用イベント列だけを持つ（**課題側の旗だけは issue-tree-m3 で追記専用をやめ、issue-tree-m4 で2種になった**）

当初「支持／棄却／検証中」のような状態フィールドを検討したが、導出元のない手動ステータスは更新忘れで嘘をつく。次に4値enum（検証せず棄却／自明に成立／今回見送り／本開発送り）を検討したが、「見送り理由は追記する」という運用実態から、**すべてを単一のイベント列に統合**した。

イベントの種類（**issue-tree-m3 で5語に畳んだ後の姿**。当初は下の表に「検証せず棄却」「自明に成立」「本開発送り」が並んでいた——なぜ落としたかは D5・D6 に書いた）:

| `kind` | 種類 | 由来 | 付随情報 |
|--------|------|------|---------|
| `supported` | 支持 | スプリントレビュー／選定会議 | 根拠（実測値でも経験知でもよい） |
| `rejected` | 棄却 | スプリントレビュー／選定会議 | 根拠（同上） |
| `onHold` | 保留 | スプリントレビュー | 判断できなかった理由（D11） |
| `deferred` | 見送り | 選定会議 | 理由（本開発へ送るつもりなら、その行き先も `note` に書く。D5） |

仮説の現在ステータスは**最新イベントから導出**。イベントがゼロ件なら未決（「検証結果は？」warning）。**未決は `kind` として保存されない**——0件であることからの導出であり、`enum` に席を持たない。

この統合が自動的に解決すること:

- **何回見送られたか** → イベント列を数えれば導出できる（今はビューを作らない。必要が観察されたら後付け）
- **判断の覆り** → 「棄却 → 半年後に新イベントで復活」が履歴を消さずに表現できる。永久確定をスキーマで強制しない
- **「今回も見送り、理由も同じ」** → 何も追記しない。触らないことがデフォルトで、それでデータが嘘をつかない

**追記専用が及ぶ範囲は、issue-tree-m3 で仮説側だけに狭まった。** D5 が見送りを `deferred` の1語に畳んだ結果、**課題の見送りは「選ぶ」操作ではなく「入っているか／入っていないか」の操作**になった——1択のドロップダウンには意味が無い。人間が実機の画面を一巡した後にトグルへ作り替え、そこで「切る」の意味を決める必要が生まれた。

**採ったのは「最新の見送りイベントを消す」である**（`commands.ts` の `toggleDeferral`）。**取り消しを表すイベントを追記する案は退けた**——追記で表すと、課題の現在ステータスが「最新が `deferred` か」ではなく「列を畳んだ結果」になり、D3 の抑制（1件でもあれば配下を止める）と俯瞰のバッジが、列の中身に依存し始める。トグルという操作の見た目と、データの読み方が食い違うのが最も高くつく。

**失うものは自覚した上で受け入れた**：「一度見送って、また戻した」という事実と、そのとき書いた理由は残らない。人間にこの代償を示した上で、**人が期待するとおりに振る舞う単純さ**を採る判断が下りた。誤操作の取り消しは Undo（1操作1コミット）が受け持つ。

**仮説側（`events` に判断を追記する側）は1文字も変えていない。** 判断の覆りが履歴を消さずに表現できること——上の3つの帰結——はそのまま生きている。**この節を読む人が守るべき線引きは「追記専用なのは仮説の `events`／課題の `events` は 0 件か 1 件で入り切りする」である。**

**アプリが書く課題の `events` は高々1件になった。** 手書きのファイルは2件以上を持ちうるので、トグルは**最新の1件だけ**を消す（残っていればまだ見送り済みで、もう一度押せば次が消える）。全部消す形にすると、書いた人が見ていない過去の理由まで1押しで飛ぶ。

**課題の `events` に立つのは旗2種（`deferred` / `resolved`）になった。** 追記専用でないこと・列が 0 件か 1 件であること・トグルであることは変わらない。**差し替え（見送り → 解決）は、前の1件を消してから足す**——2件並べると「いまどちらか」が列の中身に依存し始め、D2 の芯（最新1件で決まる）が崩れる。

**イベントは `date` を持つようになった。** 「日時はデータに持たない（配列順が時系列の正、厳密な日時は Git 履歴が正）」という当初の註を**表示用の日付に限って改める**——**FB と判断の前後は会議中に画面で見える必要がある**（Git 履歴を開きに行けない）。**手で打たせない。アプリと Skill が追記時に入れる**——手入力の欄にすると更新忘れで嘘をつく（ミュータブルなステータス欄を捨てた D2 と同じ理屈）。**厳密な時刻は引き続き Git 履歴が正**であり、粒度は日に留める。

### D3. 課題ノードにも見送りイベントを付けられる。配下への抑制は導出

「親が見送りだから葉も見送り」は保存すべき値ではなく**導出**（`crossesBoundary` と同じ判断）。見送りは最上位の課題ノードに一度だけ付け、配下の warning 抑制は「祖先に見送りがあるか」から計算する。子に値をコピーすると、親の見送り解除時に子が取り残される（更新忘れの嘘の再発明）。

**この導出は、見送りがトグルになっても1行も変わっていない**（D2 の反転節）。判定は「祖先のいずれかで `events` が空でないか」であり、**その列がどう空でなくなった／空に戻ったかを見ていない**——付けたときは1件足り、戻したときは最新1件が消えるので、`suppressedIssueIds` からは同じ問いのままである。**打ち消しのイベントを追記する案を退けた理由の半分がこれ**で、そちらを採ると「1件でもあれば抑制」が成立しなくなり、ここが列の中身を数え始める。

### D4. スプリント参照は持たない

スプリントは facet 内に実体がなく、参照させるにはスプリント管理エンティティの新設（スコープクリープ）か手入力文字列（検証されないラベル）しかない。時系列はイベントの**配列順**が既に持っており、厳密な日時は Git のコミット履歴が正の源。「スプリント横断ビュー」の需要が実際に観察されたら、スキーマバージョニングで後付けする。

### D5. ~~「今回見送り」と「本開発送り」は区別する~~ → **区別しない（issue-tree-m3 で反転）**

**当初こう決めた。** どちらも warning を消すが、**復帰するタイミングが違う**から `kind` を分ける:

- 今回見送り → 次のPoC選定会議で拾い直される
- 本開発送り → PoCフェーズ中は戻らない。**PoC終了時に本開発へ引き渡す宿題リストの材料**になる（価値2への接続点）

**issue-tree-m3 の実装が済み、人間が初めて実機の画面で一巡した直後に反転した。** `deferredToMainDev` は**データごと廃止**し、見送りは `deferred` の1語だけになった（`deferralEvent.kind` は `["deferred"]`、`judgementEvent.kind` は `["supported","rejected","onHold","deferred"]`）。**紙の上では「復帰のタイミングが違う」で十分な理由に見えたが、実際の画面では、見送りを付けるたびに2択を強いられる一方、俯瞰の読み——この枝はこのエピックの外——はどちらを選んでも同じだった。** 選ぶ側の迷いという費用が、区別から得られるものを上回った。

**替わりの記録先は `note` である。** 本開発へ引き渡すつもりの見送りも `kind` は `deferred` で、**行き先は `note` に書く**。価値2への接続点は失っていない——宿題リストを作るとき読むのが `kind` ではなく `note` になっただけであり、そもそも「どこへ・どんな条件で・誰に引き渡すか」は enum の1語では表せない情報だった。**再び `kind` へ昇格させるなら、その必要が実際に観察されてからにする**（D2 の「見送り回数のビュー」と同じ扱い）。

### D6. 未決の意味論は既存モジュールと同一（**ただし「検証不要と決めた」の型区別は issue-tree-m3 で反転**）

「未決は間違いではなく、その時点の正しい状態」。warning として見え続けるが出力は止めない。**この部分は変わっていない。**

**当初はここに続けてこう決めていた**——「検証不要と決めた（自明に成立／検証せず棄却）」は未検証と**型で区別された確定判断**であり、エラーカタログの `none` / `undecided` と同じ構造である、と。そのために `supportedWithoutTest` / `rejectedWithoutTest` を `kind` に置いていた。

**issue-tree-m3 で、この2語をデータごと廃止した**（D5 と同じく、人間が実機の画面を見た直後の判断）。**「実験して支持した」と「経験知で自明に成立とした」は、俯瞰で読みたいこと——この仮説は成り立つのか——が同じで、違うのは根拠の中身だけだった。** 根拠の中身は `kind` ではなく `note` に書くものである。したがって**検証の有無は型では区別されず、`note` に書かれた文章として残る。**

**それでもエラーカタログとの構造の対応は生きている。** `none` / `undecided` に当たる区別を持っているのは、いまも**イベントがあるか無いか**である——`events` が0件＝未決（`undecided` の側）、1件でもあれば確定判断（`none` の側）。**失われたのは確定判断の内側の細別だけ**で、「決めた／決めていない」を型で分ける構造そのものは動いていない。

### D7. ~~仮説に rationale（発想の由来、自由記述）を持たせる~~ → **廃止し、文言を3つに割った（issue-tree-m4 で反転）**

**当初こう決めた。** 発散フェーズで「なぜこの仮説が生まれたか」を残す。価値2（本開発から「なぜ」を遡る）の材料。**入力は必須にせず、空でも warning は立てない**——由来の欠落は仕様の穴ではないため。

**由来という欄は無くなった。** 代わりに仮説の文言が3つに割れた——`title`（ソリューション仮説：何を作るか）／`detail`（その詳細）／`value`（価値仮説：なぜ効くと考えるか）。

**反転の理由**: 欄が1つしか無く、空欄に何を書けばよいかが画面から分からなかった。「何を作るか」と「なぜ効くか」は**別の主張**で、レビューで問われるのも別々である。由来（この仮説がどこから来たか）は価値仮説の中で書ける。

**どれも空を許し、warning にしない**という D7 の規律は3つとも引き継ぐ。

### D8. 議論の焦点はデータに保存しない（色は意味の数だけ）

レビューで「いまどの課題を説明中か」の共有は、選択ハイライト＋フォーカスモード（選択サブツリー以外を薄くする）等の**純粋なビュー状態**で実現する。色相は足さない。意味を持つ色相は rev 9章 M21 の4軸（欠落の黄・無効の赤・着信の青・支持の緑）のまま、**判断の群は塗りと枠の形で分ける**: 支持＝`judge-yes` の塗り／棄却＝`judge-no` の塗り（チャコール。棄却は失敗ではなく入力なので叫ばない）／保留＝`missing` の実線の枠／未決＝`missing` の破線の枠／FB待ち（**issue-tree-m4 で「未判断」から改名。D9**）＝`pending` の実線（着信。欠落ではなく受信箱）／見送り＝`surface-muted` の面と `rule` の枠。未決を面で塗らない（新しい木は全部が未決なので、面で塗ると警告が情報を失う）（**M21 の実機確認で反転。淡い面を持つ**——1px の枠だけでは方眼と罫線に埋もれて拾えなかった。「一面になる」懸念は面を淡く（L 0.93〜0.95）して判断軸の濃い面と明度で分けることで受ける。rev 9章）。抑制された配下は `opacity` ではなく明度の段 `ink-faint`（3:1 を実測）で薄くする。見送りを掲げた課題自身の面とバッジ・理由の行は薄くしない——バッジが「なぜ配下が薄いか」を説明する役なので、説明ごと薄くすると理由が読めなくなる。見送り箱へ入るエッジも実線のまま、配下へ出るエッジだけを破線にする。**見送りが入れ子になっても（配下自身が見送りを掲げていても）、配下の判定は「祖先のいずれかに見送りがあるか」でのみ行う**——「自分が見送っていないか」では代用しない。自分の見送りの有無で判定すると、入れ子の内側で薄い配下の上に濃い箱が挟まる退行を招く（実装で一度実際に踏んだ）。（issue-tree-m3 で確定。それまでは「色を使わない」で、6種を文字ラベルだけで区別していた）なお、フォーカスモードの状態は JSON に保存しない（消し忘れフラグ＝嘘データの温床。座標を保存しないのと同じ判断）。

**issue-tree-m3 の後続で、見送りを掲げた課題自身の箱に `bg-surface-accent` の塗りを足した。** 実機の画面で「見送りの箱だけ濃淡が無く、ほかと見分けが付きにくいのでは」と聞かれ、新しいトークンは増やさず既に検算済みの面（見出しの面。`palette-requirements.ts` の `HEADING_FACE`）を流用する案を選んだ。**上の2つの既存規則はどちらもこれを禁じない**：「未決を面で塗らない」は新しい木の大半を占める未決を塗ると警告が情報を失うという話で、見送りは稀で意図的な判断なのでこの理由は成り立たない。「抑制された配下を地の色に落とさない」は `bg-canvas`（方眼紙の地）の話で、`surface-accent` は `canvas` ではなく `surface` の仲間である。**塗るのは見送りを掲げた箱そのものだけ**——配下は従来どおり `bg-surface` に `ink-faint` のまま。ここも塗ると「配下も見送りを表明している」ように読めてしまう。**入れ子の場合も同じ優先順位で決まる**：祖先由来の抑制（上のパラグラフの規則）が勝つので、自分も見送りを掲げている配下（例の C）は祖先由来で薄いままで、塗りには進まない——「掲げた当人だけ塗る」を「自分の見送りの有無」で判定すると、上で退けたのと同じ形の退行（薄い配下の中に濃い塗りが挟まる）を再び招く。**`surface-accent` はこれで見出しの面と見送りの面の2役になった**——ダークでは `surface` より明るい面（L 0.28 対 0.205）だが、それを承知でトークンを増やさない判断を優先した。**枠は `border-rule` ではなく `border-ink-muted` にした**——`rule` は `surface-accent` の上で 3:1 を割る（実測: ライト 2.680:1・ダーク 2.502:1）。`GlossaryEditor.tsx` / `ErrorCatalogEditor.tsx` の見出し行は同じ `border-rule bg-surface-accent` の組を使っているが、あちらは `border-b`（セル間の下線）で効かなくても実害が小さい。この箱の枠は箱全体を囲って地から輪郭を切り出す役なので、同じ扱いはできない。`ink-muted` は `HEADING_FACE_FOREGROUNDS` で `surface-accent` に対し 4.5:1 以上が既に機械検証されており（実測: ライト 6.774:1・ダーク 5.427:1）、新しい測定なしで 3:1 を安全に上回る。見出し行2箇所の未測定は直さず `open-issues.md` に残した。**M21 で `surface-accent` は `surface-muted`（一段沈んだ面）に改まり、見送りの箱はその本来の役割で塗られる。** 流用ではなくなったので、「見出しの面を流用した」という上の経緯は歴史として読むこと（`rule` が面の上で 3:1 を割る問題も M21 で解消した——`surface-muted` は `rule` が 3:1 を満たすように置いてあるので、枠は他の箱と同じ `border-rule` に戻っている）。

**M25 で「塗るのは掲げた箱だけ」を反転し、配下も `surface-muted` で塗る。** 実機で見送りの枝を見た人間の観察は「後続（配下）の箱が白いままで、まだ生きている枝に見える」——上の段落が心配した「配下も塗ると『配下も見送りを表明している』ように読める」は、実際の画面では逆に働いた（白い面の方が嘘をつく）。反転後、**面が運ぶのは「表明の所在」ではなく「凍結の範囲」**である——見送りの枝はグレーの面でひとかたまりに括られ、**誰が掲げたか**は文字の濃さ（掲げた当人＝`text-ink`／配下＝`ink-faint`）とバッジ（当人＝実線／配下＝faint）と破線エッジが運ぶ。入れ子の優先順位（祖先由来の抑制が勝つ）は変わらない——面が同じになった今、優先順位が守るのは塗りではなく**文字と枠の濃さ**である。`ink-faint` は `BACKGROUNDS` 3面（`surface-muted` を含む）への 3:1 が `palette.test.ts` で機械検査済みなので、新しい測定は要らなかった。実装は `IssueBox.tsx` の `face`（suppressed 分岐）。

**m5 で、展開の単位が「フォーカスした仮説1件」から「課題ノード」に変わった。** 開くのは課題であって仮説1本ではない——開くと、その課題にぶら下がる仮説がまとめて1つのパネル群を持ち、**その課題の箱だけ**幅が `BOX_WIDTH`（320）から `EXPANDED_BOX_WIDTH`（780）に広がる（`measure.ts` / `layout.ts`）。同時に開けるのは相変わらず1件（今回は1課題）だけで、これも変わらずビュー状態のまま JSON には書かない——座標や旧来のフォーカスモードと同じ扱いである。単位を仮説から課題へ引き上げた理由は比較のしやすさにある——課題1件に複数の仮説がぶら下がる場面はざらにあり、仮説単位で開閉すると、隣の仮説の判断や根拠を見ながら別の仮説を詰める、という比較そのものができなくなる。

**あわせて、フォーカスによる自動展開をやめた。** `HypothesisRow` から `onFocus={props.onExpand}` を外し、押したとき（`onClick`）だけ開くようにした。理由は会議の速度にある——課題出しの最中は仮説をどんどん足していくが、そのたびに新しい行へフォーカスが移って課題の箱が開いたり閉じたりすると、伸び縮みする図そのものがノイズになる。**仮説を足すのは閉じたまま行い、詰める（判断を記録し、根拠や FB を書き込む）ときだけ開く**——発散のフェーズと収束のフェーズで画面の振る舞いを変える判断である。副産物として、畳まれた行に `Tab` で入った瞬間に開いて `textarea` へ移る旧来の形（1回の `Tab` でフォーカスが2回動く）も消え、キーボードで課題の木を歩くときの行き先が予測どおりになった。

### D9. ~~FBメモは「判断イベントの下書き」として pendingNotes に持つ~~ → **FB は属性を持つ記録であり、移動も昇格もしない（issue-tree-m4 で反転）**

**当初こう決めた。** スプリントレビューはSH同席で成立・棄却をその場で判断する場。進行（全デモ→一件ずつ議論＆決定）は変わり得るため、**進行をデータ構造に焼き込まない**。データが持つのは進行非依存の最小事実のみ：

- 仮説は、まだ判断に紐づいていないメモ（`pendingNotes`）を持てる
- 判断イベントが下されるとき、メモは**選択的に**イベントの根拠へ移動し `pendingNotes` から消える（雑談メモを公式根拠に昇格させない選別の余地）
- `pendingNotes` が空でない仮説には warning が立つ＝**レビューの締め忘れ検出**
- 独立した `kind: "memo"` イベントは作らない（「最新イベントからステータス導出」の芯を壊すため）

メモは一時UI状態ではなく短命な永続データ（会議の中断・延期で持ち越すためJSONに書く）。

副次的な導出：「今日のレビューで判断すべき仮説」＝未決かつ見送られていない仮説。レビュー用アジェンダは既存データから導出でき、新しい状態は不要。

**「根拠へ移す」（`promoteNote`）を廃止した。** 実際は複数の FB を踏まえて自分の言葉で理由を書くのに、FB の文言をそのまま理由欄へ移す操作は**分かりづらいわりに何も要約していない**。FB は移動も昇格もせず、記録としてその場に残る。

**これに伴い「まだ判断に紐づいていないメモ」という概念が消え、`pendingNotes` という名前も消えた**（`feedbacks`）。

**FB は属性を持つ**（`askId` / `by` / `sentiment` / `date`）。誰が言ったか・いつか・賛成か懸念か質問かが消えていると、判断の根拠を書くときに**SH の発言だったのか雑談だったのかが後から区別できない**。

**FB は削除できる。判断は追記専用のまま。** 打ち間違いが残るのは実務的でない一方、判断の履歴は「そのとき何を根拠に決めたか」の記録である。**この非対称のために配列を2本に分けている**——1本に混ぜると「追記専用」を配列単位で言えなくなる。

**「聞きたいこと」（`asks`）を持つようになった。** 仮説は「支持・棄却を判定できる主張」だと定義してある（D1）のに、**何をもって判定するかを書く場所が無かった**。レビュー前に問いを書いておくと、それがそのまま反証条件になる。問いは複数立つので配列で、**FB はどれかの問いにぶら下がるか、どこにも属さない**（`askId: null`）——**用意した問いの外から来る指摘こそ重いので、紐づけを強制しない**。

**「未判断」の問いは落とし、「FB待ち」を新設した。** v2 の「未判断」は「まだ拾っていない FB がある」を意味していたが、拾う操作（根拠へ移す）が無くなったので**解消手段が消えた**。代わりの定義（最新の判断より後に届いた FB がある）は**検討したうえで入れないと決めた**——日付を持つので、要望が出たら後から導出だけで足せる。

### D10. 俯瞰の表現——箱は課題だけ、仮説は行、判断は1つ、FB は複数

キャンバスに載る物の種類（課題・仮説・判断・旗・根拠／FB）を形の種類に対応させる: 課題＝箱（エッジが出入りする唯一の物）／仮説＝箱の中の1行（左に点、右端に判断のバッジ1つ）／見送り・解決＝課題タイトル右のバッジ＋理由の行（D12）／根拠・FB・以前の判断＝**展開した仮説だけ**の内側パネル。展開は純粋なビュー状態で、同時に1つ（JSON に書かない）。**「判断の履歴」という見出しは使わない**——判断は最新1つとして見せ、2件目以降は「以前の判断」。データは `events`（判断）と `feedbacks`（FB）の2配列のまま（統一しない。issue-tree-m3 の批評で決定。**`pendingNotes` という名は issue-tree-m4 で `feedbacks` に代わった。D9**）。箱自体は見送りで薄くしないが（D8）、中の仮説行は自分の見送りを含めて薄くする——「この課題はもう追わない」は配下の仮説にも及び、未決の問いを立てないのと同じ理由による。**由来（`rationale`）はここに現れない**——issue-tree-m4 で廃止された（D7）。

**俯瞰の語と展開の語は、いまは同じである。** 当初の作りでは「俯瞰のバッジは5語に畳み、展開した仮説では**正確な種別**（7種）を出す」という対比があった。**D5・D6 の反転で保存する種別が5語ちょうどになったので、この対比は消えた**——`EVENT_KIND_LABELS`（保存された `kind` → 語）と `BADGE_LABELS`（俯瞰のバッジ群 → 語）が同じ言葉しか持たず、展開したパネルの「以前の判断」の行にも、俯瞰のバッジと同じ語が出る。**それでも2つの定数は畳まず、別々に置いてある**——鍵が違い（`JudgementKind` と `BadgeGroup`。`未決` は保存されない導出値なので後者にしか席が無い）、**俯瞰と詳細をまた別の言葉に分けたくなったとき、片方だけ動かせるようにしておくため**である（課題側の `ISSUE_DEFERRED_LABEL` を別に置いているのと同じ理由）。**いまの一致は偶然であって統合ではない**ので、`derive.test.ts` に「一致が黙って崩れないこと」を見るテストを置いた——落ちたら、割るのか揃えるのかを決めてから検査を直す。

### D11. 「保留」は理由付きの判断イベント（`onHold`）

見たが判断できなかった、は誰かがそう決めた事実であり、イベント無し（未決）とは区別する。保留は仮説にだけ付く（課題の見送りとは別）。理由を `note` に書く——空の保留は次のレビューに何も渡さない。集計では未決と別に数える（問いは4種: 仮説なし／未決／保留／FB待ち。**「未判断」は issue-tree-m4 で「FB待ち」に代わった**——D9 を見よ）。**この判断そのものは D5・D6 の反転を受けていない**——`onHold` は5語のうちの1つとして残っている。

版番号については、**当初「enum の拡張だから」という理由で schemaVersion を 2 に上げた**（このリポジトリ初の版上げ。読み込み時の移行は `src/core/load.ts`）。その後 D5・D6 の反転が同じブランチの中で `supportedWithoutTest` / `rejectedWithoutTest` / `deferredToMainDev` を落としたので、**2 は「拡張」ではなく「語彙を5語に確定した改訂」になった**。版番号は上げ直さず **2 のまま再定義**してある——2 はこの未マージのブランチで作った版で、一度も公開されておらず**壊すべき契約が無い**ため。1 → 2 の移行は版番号を書き換えるだけのまま据え置き、**廃止した種別を持つファイルは移行後の検証で弾かれる**（＝開けない。読み替えを足すと「もう無い区別」がデータの中に別の顔で生き残る）。

### D12. 課題に「解決」の旗を立てる（人が押す旗であって、導出ではない）

**`resolved` は人の表明である。** 「この課題は出てきたソリューションで解決できる＝これ以上の検証は不要」を意味する。

**導出ではない。** 支持された仮説があることと、課題が解決したことは**別**である——支持＝主張が成り立つ、であって**作ると決めたわけではない**。

**見送りと同じく配下の問いを抑制する。** これが旗の実効で、押した瞬間に要対応の数が減る。**設計ノートの価値1（PoC 終了判定の根拠が構造で見える）はここで回収される。**

**意味は見送りと逆（追わない／答えが出た）なので、両方同時に立ってはならない。**

**D2 の「ミュータブルな状態を持たない」とは矛盾しない**——`resolved` は導出値の複製ではなく、**人が下した判断そのもの**である（見送りと同じ位置づけ）。

**面は見送りと同じ `surface-muted`。色を足さない**（D8 の規律）。運ぶのは「凍結の範囲」であって旗の種別ではなく、種別はバッジの文言（「見送り」／「解決」）が運ぶ。

**集計の別枠は「見送り N」と「解決 N」が並ぶ。** 実効は同じでも意味が逆なので、1つの数に混ぜると台帳として読めない。

### D13. キーボードは課題の追加・削除・移動だけ。仮説の入力・判断・FB はマウス

課題ツリーの操作言語（rev 10章）は「キーでしか到達できない意味を残さない」ことを求めている。**D13 はその裏返しとして、仮説側には「マウスでしか到達できない意味」を明示的に許す**という判断である。課題の追加・削除・兄弟間の移動はキーボードのコマンドだけで完結するが、仮説の追加・文言の編集・判断の記録・FB の追記は、行を押して展開パネルを開く・ボタンを押す・ドロップダウンを選ぶといった、クリック起点の操作でしか届かない。逆方向のキーボード経路（例えば矢印だけで判断のドロップダウンまで降りて選ぶ）は用意していない。

理由は仮説というものの性質にある。課題の追加・削除・移動は会議速度で反射的に打つ操作で、打鍵数の少なさがそのまま効く。一方、仮説は「支持・棄却を判定できる主張」（D1）を言葉にする作業で、**ゆっくり考えて言葉を選ぶ**性質のものである。ここでは打鍵数の少なさよりも、目的の欄に迷わずたどり着けることの方が効く——キーだけで課題の木を移動しながら仮説の判断メニューまで正確に降りるコマンド体系を作るコストは、それで得られる速度の上昇を上回る。rev 10章の規約は「キー入力に依存する人を締め出さない」ためのものだが、仮説側はそもそも会議速度で連打する対象ではないので、締め出す相手がいない。

**この例外の中にも、キーボードを完全には締め出していない箇所が1つある。** `HypothesisPanel.tsx` の `swallowEnter`（ソリューション仮説のタイトルの `textarea` に渡す）が、rev 10章「ツール側で `e.key` を見ない」の明示的な例外である（`swallowEnter` は m4 までは `HypothesisRow` にあったが、Task 4 で展開パネルが `HypothesisPanel.tsx` に分かれたとき、タイトルの `textarea` と一緒にそちらへ移った）。畳まれた行はこの文言を1行として測っており（`measure.ts`）、`textarea` で改行を許すと、開いているときだけ複数行で読める文が生まれて畳んだ行の見た目と食い違う。**Enter を潰しているのはコマンドへ写像するためではなく、1行に収める版組の都合であり**、キー処理をツール側が奪う一般的な理由（構造操作・移動）とは種類が違う。この事情は実装のコメントだけに置くと、次にキー処理を触る人が規約違反として消しかねないので、ここに明記しておく。

**マウスの動線のうち1つは、jsdom では番人を置けない。** 判断を選んだ直後に根拠の欄へフォーカスを移す仕掛け（`KindMenu` の `picked` ref が Radix の `onCloseAutoFocus` の既定動作——トリガーへフォーカスを戻す——を抑止する）は、選択の確定（`onSelect`）がその中で先に `onOpenChange(false)` を呼んで閉じる作りになっている。jsdom ではこの経路で Radix の `FocusScope` によるフォーカス復帰そのものが走らないため、`onCloseAutoFocus` 側の `e.preventDefault()`（抑止）を外す変異を入れてもテストは赤くならない——赤くなるのは機械のもう半分（`onSelect` の中で先に閉じる処理）を切ったときだけである。**ここは実機でしか守れない。** `npm test` が緑のままであることを根拠に、`picked` ref や `onCloseAutoFocus` の抑止を「使われていないコード」として消さないこと。
