## 変える理由（設計判断の要約）

デザイン検討で決まったことのうち、データに触るものだけを挙げる。**理由まで写してあるのは、実装中に「そこは前の形のほうが素直では」と思ったときに引き返せるようにするため。**

### 1. 仮説の文言を3つに割る（`text` → `title` / `detail` / `value`）

いまは1つのテキスト欄しかなく、空欄に何を書けばよいか画面から分からない。「ソリューション仮説（何を作るか）」と「価値仮説（なぜ効くと考えるか）」は**別の主張**で、レビューで問われるのも別々である。

### 2. 「聞きたいこと」を持つ（`asks`）

**仮説は「支持・棄却を判定できる主張」だと定義してある（設計ノート D1）のに、いまの UI には *何をもって判定するか* を書く場所がない。** レビュー前に問いを書いておくと、それがそのまま反証条件になる。

問いは複数立つので配列。**FB はどれかの問いにぶら下がるか、どこにも属さない**（用意した問いの外から来る指摘こそ重いので、紐づけを強制しない）。

### 3. FB が属性を持つ（`pendingNotes: string[]` → `feedbacks`）

誰が言ったか・いつか・賛成か懸念か質問かが消えていた。判断の根拠へ昇格させたとき、SH の発言だったのか雑談だったのかが後から区別できない。

### 4. 「根拠へ移す」をやめる（`promoteNote` の廃止）

**判断の理由は手で書く。** 実際は複数の FB を踏まえて自分の言葉で書くのに、FB の文言をそのまま理由欄へ移す操作は、分かりづらいわりに何も要約していない。FB は移動も昇格もせず、記録としてその場に残る。

これに伴い「まだ判断に紐づいていないメモ」という概念が消えるので、`pendingNotes` という名前も消える（`feedbacks`）。

### 5. FB は削除できる。判断は追記専用のまま

打ち間違いが残るのは実務的でない。ただし判断の履歴は「そのとき何を根拠に決めたか」の記録なので追記専用を守る。**この非対称のために配列を2本に分ける**（`events` は追記専用、`feedbacks` は追加・削除可）。1本に混ぜると「追記専用」を配列単位で言えなくなる。

### 6. 日付を持つ（`date`）

スキーマの現在の註は「日時はデータに持たない——配列順が時系列の正であり、厳密な日時は Git 履歴が正」だが、**FB と判断の前後は会議中に画面で見える必要がある**（Git 履歴を開きに行けない）。表示用の日付を持つ形へ改める。

**手で打たせない。アプリが追記時に入れる。** 粒度は日（`YYYY-MM-DD`）。手入力の欄にすると更新忘れで嘘をつく——ミュータブルなステータス欄を捨てた D2 と同じ理屈である。厳密な時刻は引き続き Git 履歴が正。

### 7. 課題に「解決」の旗が立つ（`resolved`）

**人が押す旗**で、「この課題は出てきたソリューションで解決できる＝これ以上の検証は不要」を表明する。導出ではない——支持された仮説があることと、課題が解決したことは別である（支持＝主張が成り立つ、であって、作ると決めたわけではない）。

見送りと同じく**配下の問いを抑制する**。これが旗の実効で、押した瞬間に要対応の数が減る。設計ノートの価値1（PoC 終了判定の根拠が構造で見える）はここで回収される。意味は見送りと逆（追わない／答えが出た）なので、**両方同時に立ってはならない**。

### 8. 由来（`rationale`）を廃止する

「聞きたいこと」に場所を譲る。由来（この仮説がどこから来たか）は価値仮説の中で書ける。

## v2 → v3 の差分

### `IssueNode`（課題）

| キー | v2 | v3 |
| --- | --- | --- |
| `id` `parentId` `text` | そのまま | そのまま |
| `events` | `{kind: "deferred", note}` の 0..1 件 | `{kind: "deferred" \| "resolved", note, date}` の **0..1 件**。`deferred` と `resolved` は排他 |

**`resolved` も見送りと同じトグル**（付けると1件足し、戻すと最新1件を消す。追記専用ではない）。旗を差し替えるとき（見送り → 解決）は、前の1件を消してから足す——列に2件並べない。

### `Hypothesis`（仮説）

| キー | v2 | v3 |
| --- | --- | --- |
| `id` `issueId` | そのまま | そのまま |
| `text` | 仮説の文言 | **`title` に改名**（ソリューション仮説のタイトル） |
| — | — | **`detail`**（ソリューション仮説の詳細。空文字可） |
| — | — | **`value`**（価値仮説。空文字可） |
| `rationale` | 由来 | **廃止** |
| — | — | **`asks`**: `{id, text}[]`（聞きたいこと。0件可） |
| `pendingNotes` | `string[]` | **`feedbacks`**: `{askId, text, by, sentiment, date}[]` |
| `events` | `{kind, note}[]` 追記専用 | `{kind, note, date}[]` 追記専用（`kind` の4語は据え置き） |

```ts
// 参考（json-schema-to-typescript が生成する形の見取り図。正はスキーマ）
interface Ask {
  id: string          // "ask_" ＋ 10文字。commands.ts の newId と同じ採番
  text: string        // 空文字＝未記入
}

interface Feedback {
  askId: string | null   // どの問いへの答えか。null ＝どの問いにも紐づかない
  text: string
  by: string             // 誰の発言か。空文字可
  sentiment: "like" | "concern" | "question" | "note"
  date: string           // "YYYY-MM-DD"。空文字可（移行で入った行）
}

interface JudgementEvent {
  kind: "supported" | "rejected" | "onHold" | "deferred"
  note: string
  date: string
}
```

**`Feedback` に id を持たせない。** 削除・並びは添字で足りる（`removePendingNote` の前例）。`Ask` は `Feedback` から指されるので id が要る。参照の必要が観察されるまで id を足さないのは、判断イベントが id を持たない理由と同じ。

### 導出（`derive.ts`）

| 問い | v2 | v3 |
| --- | --- | --- |
| 仮説なし | 子を持たない課題に仮説が無い | 変更なし |
| 未決 | 仮説の `events` が0件 | 変更なし |
| 保留 | 最新が `onHold` | 変更なし |
| 未判断 | `pendingNotes` が空でない | **廃止**（下記） |
| **FB待ち** | — | **新設**: `asks` のうち、`askId` がそれを指す `feedbacks` が0件のもの |

**「未判断」は落とす。** v2 では「まだ拾っていない FB がある」を意味していたが、拾う操作（根拠へ移す）が無くなったので解消手段が消える。**代わりの定義（最新の判断より後に届いた FB がある）は検討したうえで入れないと決めた**——日付を持つので、要望が出たら後から導出だけで足せる。

**抑制**（配下の問いを立てない）の条件に `resolved` を加える。祖先を遡る導出であることは変えない（子に値をコピーしない）。

集計の別枠は「見送り N」に加えて **「解決 N」** が並ぶ（`deferredIssueCount` と同じ形で数える。自分自身が旗を掲げている課題だけを数え、配下は数えない）。

## 移行（v2 → v3）

**v1 → v2 は「版番号を書き換えるだけ」で済んだが、今回は構造が変わるので実際に値を動かす。** `src/core/load.ts` の移行フックと `src/modules/issue-tree/migrate.ts` が対象。

| v2 | v3 |
| --- | --- |
| `hypothesis.text` | → `title` |
| — | `detail` は空文字 |
| `hypothesis.rationale` | → **`value` の先頭へ移す**（下記の論点1） |
| `hypothesis.pendingNotes[i]` | → `feedbacks[i]` = `{askId: null, text: <その文字列>, by: "", sentiment: "note", date: ""}` |
| — | `asks` は空配列 |
| `events[i]` | → `date: ""` を足す |
| `issue.events[i]` | → `date: ""` を足す（`kind` は `deferred` のまま） |

**移行後の検証を通ること。** 空文字と空配列で埋めるのは、スキーマが「全キー常在・欠損ではなく空の値で未記入を表現する」流儀だからである。

## 決めてから実装すること（論点）

計画を書く前にユーザーへ確認する。**どれも「実装しながら決める」と静かに間違える種類の判断である。**

1. **`rationale` の移行先。** 廃止するが、既存ファイルに書かれた文章を捨てるか、`value`（価値仮説）の先頭に移すか。**移す案を推す**——由来は「なぜこの仮説が有望か」の説明であることが多く、価値仮説に近い。捨てるなら、捨てることをユーザーが明示的に選んだ記録を残す
2. **`sentiment` の語。** 画面は3種のアイコン（賛成 `ThumbsUp` / 懸念 `AlertTriangle` / 質問 `HelpCircle`）を出す。移行で入る行はどれでもないので **`note`（ただのメモ）を4語目に置く案**を書いてある。3語に絞って移行行を `question` に寄せる手もあるが、嘘の分類が残る
3. **`date` が空の行の見せ方。** 移行で入った FB は日付を持たない。画面で「—」を出すか、何も出さないか（画面側の判断なので m5 でもよいが、空文字を許すかはスキーマの判断）
4. **`asks[].text` が空のときに問いを立てるか。** FB待ちは「問いに FB が0件」で立つと決まったが、**問いの文言そのものが空**のときにも立てると、`＋ 聞きたいこと` を押した瞬間に要対応が増える。空の問いは数えない案を推す

## 画面との境界（どこまでを m4 でやるか）

**m4 は「型が通り、`npm test && npx tsc -b && npm run lint` が全件緑」までを負う。** スキーマと `commands.ts` を変えた瞬間に `HypothesisRow.tsx` / `IssueTreeEditor.tsx` / `cell-keys.ts` / 既存の DOM テストが壊れるので、追随は避けられない。

ただし **m4 の追随は最小限でよい**——新しい欄が v2 と同じ見た目の並びで出ていれば足りる（`title` を旧 `text` の位置に、`feedbacks[].text` を旧 `pendingNotes` の位置に）。**`detail` / `value` / `asks` / `by` / `sentiment` / `date` を画面に出す設計は m5 が持つ**ので、m4 では出さないまま置いてよい（データとして入っていればよい）。**出さないと決めた欄を、暫定の見た目で置かないこと**——m5 がそれを剥がす手間と、剥がし忘れの両方が生まれる。

`promoteNote` の廃止（「根拠へ移す」ボタンとその `Ctrl+Enter`）は **m4 で消す**。関数が消えるので画面から呼べなくなるためで、m5 を待てない。

## Skill の更新（`.claude/skills/issue-tree-register/`）

**登録 Skill はアプリと独立にスキーマと導出のコピーを持つ。** 片方だけ直すと、アプリの画面と Skill の報告が食い違う。

- `schemas/issue-tree.schema.json` — `src/` 側からのコピー（`src/core/skill-schema-copy.test.ts` が見る）
- `scripts/derive.ts` — `src/modules/issue-tree/derive.ts` の**バイト一致コピー**（`src/modules/issue-tree/skill-copy.test.ts` が見る）。**手で書き写さず `cp` する。** 値 import・相対 import・enum を持てない（Node の型ストリップで読むため）
- `scripts/issue-tree-write.mjs` — ID の採番に `ask_` を足す。正規形の書き出し順（スキーマの properties 記載順）を新しいキーに合わせる
- `SKILL.md` — ヒアリングの流れに「聞きたいこと」「FB は誰の発言か」を足す。**集計結果の文言はアプリと逐語一致**（rev 4章。「FB待ち」が増える）
- `evals/` — **いま無い**（`open-issues.md` の既存項目）。足すかは別途

`sample-project/課題ツリー.json`（お手本）も v3 へ書き直す。**お手本は README から参照される追跡対象**なので、実機確認の痕跡と混ぜないこと（`CLAUDE.md` の後片付け手順）。

## この変更で消える open-issues の項目

実装後、[`../open-issues.md`](../open-issues.md) から**消せるようになる**もの。m4 の完了時に確認して消すこと（残すと幽霊になる）。

- **「根拠へ」ボタンの reveal 機構と `Shift+Tab` で届かない穴** — ボタンごと無くなる
- **`setHypothesisText` / `setRationale` に戻り値型注釈が無い** — `setRationale` は消え、`setHypothesisText` は `setHypothesisTitle` 等に置き換わる（新しい関数には最初から注釈を付ける）

**消えない**もの（据え置き）: 仮説を別の課題へ付け替える手段が無い／判断の誤操作（同じ種別を続けて付ける）／ID 重複ファイルで同じ行が両方の箱に描かれる。
