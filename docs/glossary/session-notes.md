## 決定済み

### 論点1: ID規約（全ツール共通のメタ規約に一般化）→ rev 5章へ反映予定

- **形式**: `<entityPrefix>_<id>`
- **ID本体**: nanoid `customAlphabet` で**英数字62文字（A-Za-z0-9）・10文字固定**
  - 理由: nanoid 標準アルファベットは `_` `-` を含み、区切り文字と衝突して自己記述性とスキーマ検証の正規表現を汚すため
  - スキーマ検証用正規表現の型: `^term_[A-Za-z0-9]{10}$`
- **プレフィクスの意味**: エンティティ種別（テーブル名に相当）。用語の種別enum（カラム値に相当）とは別レイヤー
- **粒度**: ツール単位でなくエンティティ単位（例: 状態遷移は `state_` / `event_`）。具体命名は各ツールセッション管轄
- **宣言と衝突防止**: 各ツールの JSON Schema がプレフィクスをパターンとして宣言。コアのモジュールレジストリが登録時にプレフィクス重複を検査

### AI連携方式の補強 → rev 4章へ反映予定

- Skill に以下を同梱する:
  - **ID採番スクリプト**（62文字アルファベット・10文字の nanoid を出力）
  - **書き込み前検証スクリプト**（アプリと同一の JSON Schema でバリデーション。スキーマの正は一つ）
- MCP的な書き込みツールの提供は**採らない**（接点はファイルのみ、の維持。経路の多重化と第三の成果物を避ける）

### 論点2: 用語のフィールド設計（確定）

**トップレベル構造**: エンベロープ直下は `terms: []` のみ。拡張は schemaVersion 改訂で対応（YAGNI）。

**フィールド構成**:

| フィールド   | 必須          | 意図                                    |
| ------------ | ------------- | --------------------------------------- |
| `id`         | ○             | `term_` + 10文字                        |
| `name`       | ○             | 正式表記。表記ゆれ検知の「正」側        |
| `kind`       | ○             | 種別enum（論点3で確定）                 |
| `definition` | ○（空文字可） | 空文字＝「未定義」として warning 可視化 |
| `aliases`    | ○（空配列可） | 別名リスト。表記ゆれ検知の照合データ    |
| `notes`      | ○（空文字可） | 備考。検知対象外の自由メモ              |

- 「必須だが空を許す」: 全キー常在・値で空を表現。決定的シリアライズと整合し、warning 判定が単純な値チェックになる
- **`tags` は初版から除外で確定**。理由: kind（排他・enum固定・ツールが解釈）とタグ（複数可・自由語彙・人間用）は構造が異なるが、運用上は同じ語彙が両方に発生して分類方針がぶれる。kind 一軸で始め、横断分類の実需が出てから実例で判断する

### 論点3: 種別enum（確定）

**初期値7つ**: `actor` / `state` / `event` / `screen` / `data` / `other` / `undecided`

- **`undecided` を enum に含め kind は必須のまま**: 「未分類」を欠損でなく明示的な値で持つ。キー常在方針と整合し、warning 判定は値チェックで済む
- **`undecided` と `other` の区別**: 前者=「まだ決めていない」(warning)、後者=「検討したがどれでもない」(ok)。「未定義と決めた上で無効の型区別」の enum 内での再現
- **`data` を追加**: データ・帳票名は表記ゆれの最頻発領域であり、検知という中核価値に直結するため
- **`condition` は保留**: 「条件」は名詞でなく命題であることが多く、用語集の登録単位か疑わしい。ロジックツリーのセッション（handoff-01）で分岐条件の用語参照要求が見えてから enum 拡張（schemaVersion 改訂）で対応
- enum 拡張は schemaVersion 改訂として扱う（handoff-04 の前提どおり）

### 論点4: 配列順の意味（確定）

- **データ仕様**: `terms` 配列の順＝UIの既定表示順（rev 5章の適用）
- **順を作る操作**: 登録順（末尾追加）＋手動並び替え（Alt+↑↓。階層・リスト系ファミリー標準キー）。リストに自然な「並び替え」の意味を取り上げない
- **五十音等のソート表示はUI側の導出**: データの配列順は書き換えない。閲覧目的の操作で Git diff を発生させない（「読み込み・閲覧では書き戻さない」原則の並び順版）
- **境界規則**: ソート・フィルタ表示中（導出順表示中）は Alt+↑↓ を無効化。表示順とデータ順が食い違う状態での並び替えは操作結果が予測不能になるため。既定表示に戻すと再有効化

### 論点5: 表記ゆれ検知・ルールベース層（確定）

**検知対象は2種類に分け、扱いを変える**:

- **(a) 他ツールの自由テキストフィールド**: テキスト中に用語の `aliases` の表現が出現したら指摘（本命の検知）
- **(b) 用語集の内部矛盾**（alias重複、aliasと他用語のname衝突）: 表記ゆれ検知ではなく**照合データ自体の矛盾**として、ID重複と同列の整合性検証（レベル2・赤表示）に分類。矛盾した照合データでは(a)の指摘が二義的になるため、検知機能の前提条件として整合性側で守る

**照合方式**:

- **文字列の部分一致（substring）**。日本語は分かち書きがなく単語単位の完全一致が構造的に成立しないため
- **照合キーは `aliases` のみ。`name` は照合しない**: aliasesは「この表現を見たら正式名に直すべき」という登録者の明示的意図であり、指摘の根拠になる。nameの部分一致照合は誤検知の温床（「受注データ」があるとき全ての「受注」を指摘してしまう）
- **未登録の揺れの発見はAI層の仕事**（rev 4章の役割分担）。ルールベース層は登録済みの揺れの機械照合に徹する
- **文字正規化はNFKC＋英字大文字小文字同一視のみ**。カナ同一視や送り仮名吸収は恣意性が入るため実施せず、必要な表現はaliasに登録する運用に倒す（判断をアルゴリズムでなくデータに置く）

**結果の表現**:

- **検証2レベルの外に第三の区分「指摘（suggestion）」を新設**。表記ゆれを含む自由テキストはデータとして壊れていない（直すかは人間の判断事項）ため、レベル2に含めるとファイル一覧の赤バッジが「直すべき矛盾」と「提案」の混合になりシグナル価値が薄まる
- 表示はwarningトークンの弱い表現（波線下線など。赤バッジ・赤ハイライトと区別）。3系統の色意味論の中に収めつつ強度で区分。具体はデザイントークン確定後
- **検知タイミング**: レベル2検証と同じ契機に相乗り（ファイル編集時＋プロジェクト全体走査時）。「検証と同じ契機で走る、ただし結果の区分だけ違う」

### 論点6: リストUI・インライン登録（確定）

**A. リストUI（用語集エディタ本体）**

- **列構成**: 名称／種別／定義／別名／備考の5列。IDは列に出さない（機械用の参照キーであり人間が常時見る情報ではない。行の詳細・コピー操作で参照可能）
- **warning可視化はセル単位**: `kind === "undecided"` は種別セル、`definition === ""` は定義セルに warning 表現。「どこが未定義か」と「埋める操作の場所」を一致させる
- **検索・フィルタ**: インクリメンタル検索（name / aliases / definition 横断）＋種別フィルタ。導出表示のため適用中は Alt+↑↓ 無効（論点4の境界規則）
- **キーボード**: 階層・リスト系ファミリー標準（Enter＝直後に行追加、空欄Backspace＝行削除、Alt+↑↓＝並び替え、矢印＝行間フォーカス移動）
- **Tabはセル間移動**: 用語集はフラットで「子」の意味が存在しないため「存在しない意味は提供しない」（rev 10章）を適用し、フォーム系デファクト（次フィールドへ）に譲る。標準キーの再定義ではなく、意味が存在しないキーの空き地の利用

**B. インライン登録コンポーネント（他ツールから呼ばれる共通コンポーネント）**

- **動線**: 用語参照フィールドで文字入力 → インクリメンタル候補表示（name / aliases 照合）→ 一致なしの場合、候補リスト末尾に2つのアクションを出す:
  1. **新規用語として登録**: `name`＝入力文字列、`kind`＝`undecided`、他は空で即登録。呼び出し元に発番IDが入る
  2. **既存用語の別名として登録**: 既存用語を選ぶと入力文字列がその alias に追加され、呼び出し元にはその用語のIDが入る
- **最小入力（名称のみ登録）を許可**: 会議の速度を止めない代わりに、未記入は用語集側で warning 可視化され「後で埋める」が消えずに見える（負債の可視化）
- **別名登録動線の意図**: 人間が表記ゆれに遭遇した瞬間を照合データ化する入口。ルールベース検知（aliases照合）の価値を会議の自然な流れの中で底上げする
- **用語集ファイルの自動生成**（用語集0個での初回登録時。rev 5章）はこのコンポーネントの責務に含める

### 論点7: NotePM向け出力（確定）

- **形式**: 種別ごとにグルーピングした表形式
  - 表形式の理由: 用語集は「上から読む」でなく「引く」文書であり、一覧性で見出し形式に勝る。定義文は会議中に書く1〜2文想定で表セルに収まる
  - グルーピングの理由: 読み手が種別を索引として引くため。順は enum 定義順で固定（出力のたびに順が揺れる Git ノイズを排除）。空の種別は見出しごと省略。グループ内はデータ配列順
- **見出し階層（NotePM の目次が h1〜h3 収載であることを踏まえる）**:
  - h1 は使わない（NotePM のページタイトルと階層衝突するため）
  - エンベロープ `title` を `##`（h2）で出力ブロックの起点に
  - 種別グループは `###`（h3）。文字サイズが適正で、目次収載の下限に収まり「種別が目次からの索引になる」
- **未定義を出力にも明示**: `definition` 空は定義セルに `（未定義）`、`undecided` は `### 未分類` グループとして出す。仕様書に貼った瞬間に未定義が見えなくなる（文章仕様書の悪癖の再生産）を防ぎ、「決めていないことを消せなくする」思想を出力物まで貫通させる。議事録に貼れば `（未定義）` が次回の宿題リストとして機能する
- **列構成**: 名称／種別／定義／別名／備考。`notes` は含める（備考も仕様の一部。「内部メモを分けたい」需要が実証されたらフィールド追加で対応）。ID は出さない（人間向け出力）
- **Mermaid はなし**（用語集に図は存在しない。モジュール規約の出力ロジックは Markdown のみで充足）
- **形態**: クリップボードコピー＋ .md 書き出しの両方（rev 8章決定済み）

**規約側への発見（rev 6章へ注記として反映）**: 整合性検証には責務の異なる2種がある。

- **モジュール内検証**: 自ファイル内で完結する検証（用語集の alias 重複等）→ 各モジュールの提供物
- **コア横断検証**: 単一ファイルでは判定できない検証（用語集の単一性違反）→ コアの仕事
- **参照切れ**は「参照する側」の各ツールモジュールの提供物（用語集モジュールは参照される側であり、この検証を持たない）

規約の変更ではなく責務内訳の明確化。

**スキーマ化に伴う微細決定**:

- `schemaVersion` は整数とし、初版は `1`。スキーマ上は `const: 1`（アプリは type / schemaVersion をスキーマ検証より先に読むため、新版ファイルの「一覧表示のみ」動線と矛盾しない）
- alias の重複は同一用語内の重複であっても JSON Schema の `uniqueItems` で拒否（レベル1）せず、整合性検証（レベル2）に倒す。「拒否は解釈不能な場合に限る」原則の適用——重複した alias は解釈可能であり、人間がアプリ内で直せる
- `name` は `minLength: 1`（名前のない用語は用語集エントリとして解釈不能）。UI側は空名称行を保存対象にしない
