# facet UI 設計ノート — 視覚言語の統一

---

## 0. この文書の位置づけ

現行UIに対する「安っぽく感じる」という主観的な違和感の原因を構造的に分解し、
修正方針を決定事項として固定するための文書。

**重要な前提**: 本件は美観の問題ではなく、**facetの中核機能の劣化**として扱う。

facetの核心価値は「未定義を物理的に見えるようにする」ことにある。
未定義の視覚表現がモジュール間で分裂している状態は、この価値そのものが
実装されきっていないことを意味する。以降の指摘は、すべてこの観点から導かれる。

---

## 1. 根本原因の診断

### 1.1 差をつける場所と、そろえる場所が逆転している

UIの品質感は、印刷物の版面設計と同じ仕組みで生まれる。すなわち
**「限られた数の差（コントラスト）を意図的に配置し、それ以外は徹底的に揃える」**。

安っぽく見える画面はたいてい逆であり、
「細部がバラバラなのに、情報階層は平坦」という状態になっている。
現行facetはまさにこれに該当する。

**そろっていない（本来そろえるべき）:**

| 対象 | 現状 |
|---|---|
| 角丸半径 | ボタン・入力欄・参加者ボックス・ツリーノードで全て異なる |
| ボーダー | パネル境界も入力欄も同じ1px同色。境界線に階層がない |
| セレクト要素 | 用語集「種別」列がOSネイティブのまま（shadcn/ui未適用） |

なお、ボタン形状の不統一（黒塗り／白＋枠／枠のみ／枠なしアイコンの4種混在）は
本項の一例ではなく独立した設計課題であるため、**D19** に分離した。

**平坦（本来差をつけるべき）:**

- タイポグラフィがほぼ1ウェイト。サイズ差のみで階層を作ろうとしている
- 太さ・色の濃度・字間が階層表現に使われていない

### 1.2 強調の重みと使用頻度が一致していない

`フォルダを開く` が黒塗り（=最強調）だが、これは起動時に1回押すだけの操作。
一方、常時参照される警告表示や未定義セルの方が弱い。

### 1.3 彩度の予算が分散している

これが最も深刻。

facetは「未定義は赤で見える化」を設計原則としている。
であれば**彩度の予算は赤が独占すべき**である。

しかし現状は以下が同時に主張している:

- クリーム地色
- テーブルヘッダーの緑帯（意味を担っていない純粋な装飾）
- 未解決チップのピンク
- 黒塗りボタン
- 方眼グリッド線
- ロジックツリーのノード文字の青

結果として、右パネルに「未定義」が何個並んでも目に飛び込んでこない。
**赤の情報量が装飾によって希釈されている。**

### 1.4 密度の稼ぎ方が定石と逆になっている ← rev.2 で追加

現行facetは「**フォントサイズが小さく、行間が広い**」という構成になっている。

日本語の業務システムにおける定石はこの逆である（§3 参照）。
密度は**行間を詰めることで稼ぎ、フォントサイズは削らない**。

情報密度の予算を、行間という「削っても情報が失われない部分」ではなく、
フォントサイズという「削ると可読性が直接落ちる部分」から取ってしまっている。
D3（レイアウトが内容に支配される）と同じ根から出た問題。

## 2. 決定事項

### D1. 未定義の視覚表現を全モジュールで単一化する

**現状の分裂（4通り）:**

| 場所 | 現在の表現 |
|---|---|
| シーケンス右パネル | 赤枠＋赤背景のセル |
| 用語集・定義列 | 「未定義」という**黒い文字列** |
| 用語集・別名列 | 「別名なし」という**別の文字列** |
| 用語集・備考列 | **完全な空欄**（警告なし） |
| ロジックツリー | **無色の空ノード**（警告ゼロ） |

用語集では「空＝赤」なのに、ツリーでは「空＝無害」に見える。
**単一権威ソースの発想がデータ層には適用されているのに、UI層には適用されていない。**

特にロジックツリーは空ノードが多数あるにもかかわらず視覚的警告が一切なく、
facetの中核機能が機能していない状態。

**さらに危険な点:**
「未定義」「別名なし」という文字列をセルに埋めるのは、
**データに存在しない値をUIが捏造している**構図である。
ユーザーが実際に「未定義」と入力した場合と区別がつかない。

→ **空セルは空のまま描画し、色と枠だけで警告する。**

### D2. 1つの色に1つの意味だけを割り当てる

現状、1つの見た目が複数の意味を持っている。

| 見た目 | 現在担っている意味 |
|---|---|
| 黒塗り | 主要アクション（フォルダを開く）／ 選択中トグル（サポート向け） |
| 緑ベタ | 意味なし（全テーブルヘッダーの装飾） |
| 青文字 | ロジックツリーの「テキストが入っているノード」のみ |
| ピンク | 警告（ただし薄ピンク行／濃ピンクセルの2段階が凡例なしで併存） |

**問題点:**

- 黒塗り: 「押すもの」と「状態を表すもの」が同じ見た目になっている
- 青文字: リンクでもないのに青は「クリックできる」と誤解を招く。かつ他画面に存在しない色
- 緑ベタ: 分類ラベルに彩度背景を敷くのは階層表現として最も安価な手段であり、
  90年代デスクトップアプリの記号として読まれる

**色が意味を持つUIでは、ユーザーが一度でも「色は当てにならない」と学習した瞬間、
警告機能は死ぬ。**

#### rev.3 での訂正

> rev.1〜2 の記述「無彩色ベースに振り切り、**彩度を持つのは赤のみ**とする」は誤り。
> 課題ツリーの判断軸（支持／棄却）に色が必要であることが判明したため、破棄する。

**D2の本質は「赤だけを使う」ではなく、以下である:**

> **色を持つのは「意味」だけ。「装飾」には一切使わない。**

この原則のもとで、彩度を持てるのは次の2軸に限られる（D14〜D16参照）。

| 軸 | 例 |
|---|---|
| 欠落軸 | 未定義 / 未決 / 仮説なし |
| 判断軸 | 支持 / 棄却 / 見送り |

→ **緑のテーブルヘッダー帯は廃止する。** この結論は変わらない。むしろ判断軸に緑を
　 割り当てる以上、装飾の緑は**必ず**消さなければならない（同じ緑が意味と装飾を兼ねてしまう）。
→ 緑帯の代替は、小さめ・グレー・字間広めのテキストラベル（D11参照）。
→ ボタンは彩度を持たない（D19参照）。
→ 分類は彩度を持たない（D16参照）。

### D3. レイアウトが内容に支配される構造をやめる

**現状:**

- 用語集: 備考列のテキスト量が行高を決めており、「役割トークン」行だけ突出して高い
- ロジックツリー: 長文ノードだけ幅が3倍になり、ツリーの骨格が読めない

高品質なUIは逆で、**レイアウトが先に決まっていて、内容がそこに収まる**。

→ テーブルは行高固定＋2行で省略
→ ツリーはノード幅固定＋省略記号、詳細は別パネルで表示

**根拠**: 会議中に構造を俯瞰するツールである以上、
全文表示よりも骨格の可読性が優先される。

#### rev.3 での再定義: ノード幅固定は「スキャン性」の要請である

課題ツリーの観察により、ノード幅固定のより重要な根拠が判明した。

現状、ノード幅がテキスト量で決まるため、**右寄せのステータスバッジがバラバラの位置に散る。**
結果として「どれが未決か」を知るには全ノードを個別に読む必要がある。

ノード幅を固定すればバッジが縦一列に揃い、**列を上から下へなぞるだけでスキャンできる。**

→ ノード幅固定は、可読性の問題であると同時に**スキャン性の問題**である。
　 会議中に俯瞰するツールとしては、後者の方が効く。
→ この根拠により、ノード幅固定の優先度を引き上げる。

### D4. 警告メッセージは「件数」と「位置」で表現する

**現状の問題:**

```
名称が重複しています:「新しい用語」と「新しい用語」と「新しい用語」と「新しい用語」
```

同じ文字列を4回並べても情報量はゼロ。

```
「新しいエラー」はユーザー対応としていますが、ユーザーの対応が空です
```

3行とも同名のため、どの行を指すのか特定できない。**No列があるのだから `#1` と書ける。**

→ 重複は `「新しい用語」が4件重複しています` と件数で表現
→ 該当行へのジャンプを提供する
→ 行番号が存在するモジュールでは必ず行番号で指し示す

### D5. 警告は「問題のあるセル」だけを染める

現状、名称の重複警告なのに**行全体**がピンクになっている。
行を染めると「この行は全部ダメ」に見え、実際の問題箇所が特定できない。

→ 染めるのは問題のあるセルのみ。

### D6. フォントをOS環境からの導出ではなく、バンドルによる固定にする

**現状の構造的問題:**

Tailwindのデフォルト `font-sans` は `ui-sans-serif, system-ui, ...` であるため、
上書きしていなければ WebView2 (Windows) 上では
**ラテン文字 = Segoe UI、日本語 = Yu Gothic UI** に解決される。

これはfacetの設計哲学と正面から衝突する。

> 実装ステータスはGitブランチ位置から導出、表示順は配列順から導出、
> 座標はレイアウトアルゴリズムから計算

というように単一権威ソースを徹底しているにもかかわらず、
**文字の見た目だけがOSのバージョンとインストール済みフォント次第という
非決定的な導出**になっている。

図面に例えれば、寸法だけミリで指定して、
線の太さは「印刷所にあるペンで適当に」と言っているのと同じ。

→ Tauriの `resources` にフォントを同梱し、ローカル `@font-face` で固定する。

**副次的効果**: 現在依存している Yu Gothic / Meiryo は**再配布が許諾されていない**。
OSに存在するものを参照しているだけなので現時点で違反ではないが、
「配れないフォントに依存している」状態ではある。OFLフォントへの移行は健全化にあたる。

### D7. 和欧混植のズレを、フォント選定によって解消する

Segoe UI と Yu Gothic UI は**仮想ボディに対する字面（じづら）の比率が異なる**。
Yu Gothicは字面が小さめ、Segoe UIは大きめ。
そのため同じ `font-size: 13px` を指定しても、
並べると日本語だけ一段小さく、ラテン文字だけ浮いて見える。

**該当箇所（facet内は混植だらけ）:**

- `glossary.json` / `シーケンス-3.json`
- `Enter: ステップ追加` / `Alt+↑↓: 並び替え`
- `type=glossary の JSON` / `definition が空文字の状態`
- `9 / 9 件` / `未定義 15`

特にキーボードヒント行は、ラテン部分だけ大きく明るく見え、行としてまとまっていない。

**これは配色やスペーシングでは直せず、フォント選定でしか直らない種類の粗さである。**

なお、字面が小さいことは**「文字が小さく感じる」体感の直接原因**でもある。
同じ指定サイズでも Noto Sans JP / IBM Plex Sans JP なら明確に大きく見えるため、
フォント差し替えだけでサイズ指定を変えずに体感サイズが上がる。

### D8. ウェイトを9段階持つフォントに移行し、階層をウェイトで作る

Yu Gothic UI は CSS の `font-weight` から実質 Regular / Bold の2段階しか到達できず、
中間がない。結果として:

- 弱すぎる → 階層が出ない
- Bold にする → 急に重くなる

の二択となり、テーブルヘッダーとセルが平坦化する。

さらに、ウェイトを持たない字形にBoldを指定すると WebView2 が
**疑似ボールド（合成太字）** を描画する。輪郭を太らせるだけの処理のため、
小サイズでは潰れて汚くなる。（例: `facet 動作確認用サンプル 用語集`）

→ Noto Sans JP / IBM Plex Sans JP はいずれも9ウェイトを持つ。
→ ヘッダー = Medium(500)、本文 = Regular(400)、補助 = Regular＋グレー の3層を組む。

**これが実現すれば、D2で廃止する緑のベタ塗り帯は不要になる。**

### D9. 数字を等幅（tabular-nums）にする

facetは**数字が意味を持つUI**である。

- `No` 列の 1, 2, 3
- ステップ番号 `#1`〜`#8`
- `9 / 9 件`
- `未定義 15 / 回答済 2 / 考慮不要 1`

プロポーショナル数字では `1` と `8` の幅が異なるため、桁が揃わず列が微妙に揺れる。
この揺れは意識に上らないまま、雑な印象だけを残す。

→ 数値表示箇所に `font-variant-numeric: tabular-nums` を適用する。
→ あわせて、**テーブル内の数値列は右揃え**とする（桁数を縦方向に比較できるようにするため。
　 SmartHR Design System の表スタイル規約と同じ思想）。

**優先度: 最高。1行で効く、投入コスト比で最も効果が大きい施策。**

### D10. 等幅フォントを「機械が所有する文字列」に割り当てる

これは装飾ではなく**意味の分離**である。

facetの画面には2種類の文字が混在している。

| 種別 | 例 |
|---|---|
| 人間が書いた文字 | 用語の名称、定義、備考 |
| 機械が生成・所有する文字 | `glossary.json`, `type=glossary`, `definition`, nanoid（`gl_` + 10文字）, JSON Schemaのキー名 |

現状これらが同じフォントで描かれているため、
備考欄に書かれた `definition` が、ただの英単語なのか
スキーマ上のフィールド名なのか、見た目から判別できない。

→ 等幅を割り当てることで、
**「これはあなたが決めた言葉ではなく、システムが持っている識別子です」**
という情報が、読まずに伝わる。

### D11. タイポグラフィスケールを固定する ← rev.2 で全面訂正

> **rev.1 の記述「サイズは4段階に固定（例: 11 / 13 / 15 / 19px）」は誤りのため破棄。**
> 11px は日本語の実用下限を割っている。§3 の調査結果に基づき、以下に差し替える。

現状、11〜14px前後が段階を決めずに混在している。
エラーカタログの「表示」「絞り込み」ラベルとチップの高さ違いは、この無管理の表面化。

**確定スケール（27型WQHD / 100%スケーリング環境を前提。根拠はD12）:**

| 用途 | サイズ | 行高 | ウェイト |
|---|---|---|---|
| 文書タイトル | 22px | 130% | Medium (500) |
| セクション見出し | 16px | 130% | Medium (500) ＋ 字間widen ＋ グレー |
| テーブルセル・入力欄（本文） | **16px** | **125%** | Regular (400) |
| 複数行テキスト（定義列・備考列） | 16px | 150% | Regular (400) |
| 補助・キーボードヒント | 14px | 130% | Regular (400) |

**規約:**

- **上記5段階以外のサイズを使わない。**
- **14px を下限とする。** これ未満は使用しない。
- **密度は行高で稼ぎ、サイズでは稼がない。**（本文125% ／ 読ませる箇所のみ150%）
- **小さくするときは、薄くしない。** 現状のキーボードヒントは「小さい＋薄いグレー」の
  二重減衰になっている。小ささと薄さは、どちらか一方だけにする。
- セクションラベルは字間を広げてグレーに。日本語は字間を空けると
  「見出し」ではなく「ラベル」に見える。D2で廃止する緑帯の代替として最も効く。

### D12. 表示環境に基づき基準値を正規化する ← rev.2 で新規追加

**前提となる実機環境: 27インチ WQHD（2560×1440）、Windows表示スケーリング 100%**

CSSの `px` は物理的な長さではなく、**96 PPI を基準とした仮想単位**である。
表示スケーリング100%のとき、この仮想値がそのまま実ピクセルに1:1で写される。

27型WQHDのパネル実効密度は **約109 PPI**。96 PPIより密であるため、

```
96 / 109 ≒ 0.88
```

つまり同じ `14px` でも、**物理的には基準比 約88%（= 12.4px相当）の大きさでしか届かない。**

これはD6と同じ構造の問題である。フォントがOSに依存していたのと同様に、
**寸法の物理的な現れがモニターのPPIに依存している。**

**対処: 基準値そのものを引き上げて正規化する。**

```
14 × (109 / 96) ≒ 15.9  →  16px
```

D11の本文16pxはこの計算から導かれている。
結果的に、デジタル庁デザインシステムおよびSmartHR Design Systemが
基準値としている16pxと一致する。

### D13. ズームではなく基準値で解決し、ボーダーは1pxで固定する ← rev.2 で新規追加

D12の正規化は、WebViewズーム（1.13倍）でも数値上は達成できる。**しかし採用しない。**

**理由: 倍率が非整数になり、ヘアラインが破綻する。**

ズームは画面全体を等倍で拡大するため、1pxのボーダーが1.13pxになる。
物理ピクセルは分割できないので、レンダラは1pxに丸めるか、
アンチエイリアスで薄く滲ませるかを選ぶ。結果として
**罫線がにじみ、隣り合う線で太さが揃わなくなる。**

facetは方眼グリッド・テーブル罫線・ツリーのエッジといった
**ヘアラインが画面を構成している比率が高い**ツールである。
ここが滲むことは、まさに「安っぽく見える」原因そのものになる。

**確定方針:**

| 項目 | 決定 |
|---|---|
| ズーム | 100%固定。D12の正規化はフォントサイズ側で吸収する |
| ボーダー・グリッド線 | **1pxで固定**。文字サイズが変わっても追従させない |

文字が大きくなっても罫線は1pxのままというのは、印刷物や
ネイティブアプリと同じ振る舞いであり、正しい挙動である。
相対的に線が細くなることで画面が締まる副次効果もある。

**将来ズームを提供する場合の制約（現時点では実装しない — YAGNI）:**

- ルート `font-size` ではなく WebView ズームを使うこと。
  `rem` ベースで文字だけ拡大すると、1pxボーダー・方眼・アイコンが追従せず比率が崩れる。
- ズーム値および基準フォントサイズは、**Git管理下のプロジェクトJSONに保存しない。**
  これは仕様ではなく機材固有の設定であり、別PCで開いたときに他人の環境設定が
  降ってくる。差分ノイズにもなる。Tauriのappデータ領域（ローカル設定）に置く。

**トークンの持ち方:**

サイズを直接 `16px` と書かず、`--font-base` を基準とした相対値で定義する。
将来96 PPIの機材や4Kで開いた際、基準値1つの差し替えで全体が追従する。

#### rev.4（M23）での訂正

> 上の表の「ズーム: **100%固定**」は誤り。**既定は100%**であり、**手動ズーム（Ctrl+± / Ctrl+0）は逃げ道として残す。**

**経緯:** 2026-08-16、人間が「アプリの拡大縮小を可能に」として
`src-tauri/tauri.conf.json` に `zoomHotkeysEnabled: true` を入れた（`2fa2785`）。
これは D13 の「100%固定」と真正面から矛盾しており、
M23（タイポグラフィスケール v2）で**どちらを正とするかを人間に裁定してもらった**。

**裁定（2026-08-24）: 残す。**

| 項目 | rev.2 の記述 | rev.4 での訂正 |
|---|---|---|
| ズーム | 100%固定 | **既定100%。手動ズームは残す** |
| 正規化の担い手 | フォントサイズ側 | **変更なし**（D12の正規化は基準値側で吸収する） |
| ボーダー・グリッド線 | 1px固定 | **変更なし** |

**ズーム中に1pxの罫線が滲むことは、代償として受ける。**
D13の理由（ヘアラインの破綻）は事実として正しく、取り下げていない。
訂正しているのは「だから機能を持たない」という帰結の方である——
**滲みを承知で拡大したい場面がある**という利用者の判断を、
設計側が先回りして塞ぐ必要はない。既定が100%である限り、
通常の利用でヘアラインが滲むことはない。

**将来制約（上の「将来ズームを提供する場合の制約」）は生きたままで、
`zoomHotkeysEnabled` は両方を満たしている**——WebView ズームそのものであり
（ルート `font-size` ではない）、倍率はどこにも保存されない
（プロジェクトJSONにも、appデータ領域にも）。
**ズーム倍率の保存とズームUIは、引き続きYAGNIとして持たない。**

なお rev 9章（`overview-rev.md`）にも、この訂正後の内容を規範として書いてある。

### D14. 判断軸と欠落軸を、別の視覚チャネルに分離する ← rev.3 で新規追加

facetの画面には、**直交する2つの軸**が同時に載っている。

| 軸 | 値 | 意味するもの |
|---|---|---|
| **欠落軸** | 未定義 / 未決 / 仮説なし | まだ埋まっていない |
| **判断軸** | 支持 / 棄却 / 見送り | 埋まった上で、どう決めたか |

**問題**: 両方に色相を割り当てると必ず衝突する。

とくに「棄却」に最も自然な色は赤だが、赤は欠落軸が持っている。
これを許すと**「決着済み」と「未着手」が同じ色になる**という、
意味としては正反対の最悪の混同が起きる。

**解決: 色相を奪い合わせず、そもそも別の視覚チャネルに載せる。**

| 軸 | チャネル | 表現 |
|---|---|---|
| 欠落軸 | **輪郭** | 赤の破線枠、**塗りなし** |
| 判断軸 | **面** | **塗りつぶし**、色相で区別 |

破線枠のチップと塗りチップは形状からして別種であるため、
色相が近くても混同しない。
地図が「行政区分は面の色、道路は線の色」と分けるのと同じ発想である。

**現状評価**: 課題ツリーは既に欠落軸を破線枠で表現できている。
**規約として明文化すれば足りる**状態にある（U3参照）。

### D15. 判断軸の配色 ← rev.3 で新規追加

**現状の問題**: `支持` が濃いオリーブ、`棄却` が黒。
**どちらも同じサイズ・同じ形・同じ塗り方の濃色チップ**であり、輝度差がほとんどない。

正反対の結論が同じ視覚的重みで置かれている。周辺視野では完全に同一に見え、
暗い環境やダークモードでは差がさらに縮まる。

構造的には、**色相という最も弱い識別チャネルだけに、最も重要な意味を載せている**状態。
人間の視覚は輝度差・形状差には敏感だが、小面積の色相差には鈍い。

これはD2の「1色1意味」より深刻で、**2つの意味が1つの見た目を共有している**ケースである。

**確定方針:**

| 状態 | 塗り | 意味の方向 |
|---|---|---|
| 支持 | 緑（明度高め・彩度あり） | 前進する |
| 棄却 | ダークグレー〜チャコール | 検討は閉じた |
| 見送り | ライトグレー（枠のみでも可） | 検討自体を先送り |

**規約:**

- **彩度を持つのは「支持」のみ。** 棄却・見送りは無彩色の明度差で分ける。
  3色すべてに彩度を与えると、どれも同じ強さで主張して結局読めなくなる。
  目的は「**前進しているものが一目で拾えること**」。
- **支持を明るく、棄却を暗く**することで、白黒印刷でも判別可能にする。
  現状の問題は色相の選択ではなく、支持のオリーブと棄却の黒の**輝度が近すぎること**だった。

**却下した案: 取り消し線（棄却）**

2つの理由により採用しない。

1. **意味の問題**: 取り消し線は「削除された」「無効になった」を含意する。
   しかし**棄却は失敗ではなく、検討した結果として正当な結論**である。
   仮説検証の文脈では、棄却できたこと自体が成果。削除と同じ記号で描くのは思想に反する。
2. **物理的な問題**: 小さいチップに取り消し線を引くと文字が潰れる。

### D16. 分類には色を付けない ← rev.3 で新規追加

用語集の種別（アクター／状態／イベント／画面／データ）や、
エラーカタログの解決レベルも色分けしたくなるが、**行わない。**

**理由:**

| 理由 | 内容 |
|---|---|
| 数が増える | 分類は増え続ける。増えるたびに色を追加すると、いずれ虹色になる |
| 順序の嘘をつく | 分類には優劣がない。色相は無意識に順序や重要度を示唆するため、存在しない序列を伝えてしまう |
| 必ず衝突する | 数が増えれば、いずれ赤系（欠落軸）・緑系（判断軸）に衝突する |

**規約:**

> **色を持つのは「判断」と「欠落」だけ。「分類」は持たない。**

この線引きがないと、半年後には元の状態に戻る。

### D17. 見送り配下の未決は、要対応から外し別枠で集計する ← rev.3 で新規追加

**現状の問題**: `需要がない` ノードは全体がグレーアウトされているが、
その中に `未決 2` の赤いチップが入っている。

グレーアウトは「注意を向けなくてよい」、赤は「注意を向けろ」という信号であり、
**同じノードが相反する2つの指示を同時に出している。**

さらにヘッダーの `要対応 4` には、このグレーアウトされた2件が算入されている。
「対応が必要」と集計しながら「見なくていい」と描画している。

**決定: グレーアウトは維持し、要対応カウントからは外す。**

ただし、単に外すと**そのノードは要対応から完全に消える**。
facetは「未定義を見えるようにする」ツールであるため、これは核心機能に穴を開ける。

また見送りは、棄却と違って**判断が保留されている状態**である。
前提が変われば戻ってくるため、そのとき存在を忘れていては記録した意味がない。

構造的には在庫と同じで、**倉庫にしまうことと、廃棄することは別**である。
しまったものは台帳に残さなければならない。

**確定仕様: カウントを2段構えにする。**

```
⚠ 要対応 2  未決 2       ← 見送り配下は含まない（現在の作業対象・赤）
   見送り 1（未決 2件）   ← 別枠（凍結中の在庫・グレー）
```

前者だけが赤、後者はグレー。
**視覚的な緊急度は下がるが、存在は消えない。**
グレーアウトの意図（今は見なくてよい）と、facetの原則（欠落は消さない）が両立する。

実装は、既存の集計ロジックに「見送り配下かどうか」の判定を足し、
2つの数値を返すだけでよい。**データ構造の変更は不要。**

### D18. 見送り配下は祖先から導出する。フィールドを持たない ← rev.3 で新規追加

D17の集計を成立させるには、「見送り配下」の判定ルールが必要。

**確定ルール:**

> **祖先に1つでも見送りがあれば、そのノードは見送り配下とみなす。**
> これは**導出**であり、子ノードに見送りフラグを持たせない。

**根拠**: facetの単一権威ソース原則。
「実装ステータスはGitブランチ位置から導出」「表示順は配列順から導出」と同じ思想であり、
子に見送りフラグを複製すると、親子で不整合が起きうる状態を作ってしまう。

**未確認事項**: 現状の画面では `需要がない`（見送り）と `認知されてない` が
**破線**で繋がっており、これが親子関係なのか別種の参照なのかが判別できない。
D18の判定は親子関係に依存するため、破線の意味を確定させる必要がある（§5参照）。

### D19. ボタン階層を3段階に固定する ← rev.3 で新規追加

**現状の問題**: 黒塗り／白＋枠／枠のみ／枠なしアイコンの4種が混在。
さらに `フォルダを開く` が黒塗り（=最強調）だが、これは**起動時に1回押すだけの操作**であり、
強調の重みと使用頻度が一致していない。

ボタンの見た目は装飾ではなく、
**「この画面で何が主要な操作か」という情報を運ぶ**。
形状の羅列ではなく、強調度で設計する。

**確定スケール:**

| 段階 | 見た目 | 用途 | facetでの例 |
|---|---|---|---|
| Primary | 塗り（無彩色のダーク） | 画面に1つだけ | （下記参照。現状は該当なし） |
| Secondary | 枠線のみ | 通常操作 | 課題を追加、仮説を追加、Markdownをコピー |
| Tertiary | 枠なし・アイコンのみ | 補助・低頻度 | undo/redo、右上のパネル切替 |

**規約:**

- **ボタンは彩度を持たない。** 色の予算は判断軸（緑）と欠落軸（赤）が使い切っている。
  ボタンは無彩色の明度差だけで階層を作る（D2・D16と同じ原則）。
- **破壊的操作（削除）も常時は赤にしない。** 赤は欠落軸が持っているため。
  ホバー時にのみ赤系に変化させるなど、常時表示しない形に留める。

**重要: facetでは Primary を使わない。**

エディタ画面の主操作は「セルに文字を打つ」ことであり、ボタンではない。
その場合、**3段階すべてを埋める義務はない。**

ツールバーが全てSecondaryで揃っていれば、それは
「ここに主要操作はない、本体はキャンバスだ」という**正しいメッセージ**になる。
無理に1つ黒く塗ると、そこが主役だと嘘をつくことになる。

## 3. タイポグラフィの一次情報調査（rev.2 で追加）

「文字が小さいのではないか」という問題提起を受けて、日本語UIの相場を調査した。

### 3.1 デジタル庁デザインシステム（最も参考になる）

業務システム・管理画面向けに **Dense** という専用テキストスタイルを定義している。
データテーブル内での情報提示など、表示領域に制約がある場合に使うもの。

| スタイル | サイズ | 行高 | 用途 |
|---|---|---|---|
| Dense (Dns) | 17 / 16 / **14px** | 120% or 130% | 業務システム・データテーブル |
| Standard (Std) | 16〜45px | 150〜175% | 一般的な読み物・本文 |
| Oneline (Oln) | 17 / 16 / 14px | 100% | ボタン等のUI要素（1行前提） |
| Mono | 17 / 16 / 14px | 150% | コード系コンテンツ |

**最重要の発見（2点）:**

1. **Denseの最小が14pxで止まっている。** サイズ全体の方針としても、
   14pxは領域的制約がある場合にのみ使うもので、
   **14px未満は原則として許容されないと明記されている。**
2. **密度はサイズではなく行間で稼いでいる。** Denseは行高を120〜130%まで詰めることで
   情報量を確保しており、フォントサイズは削っていない。

→ 現行facetは「サイズが小さく行間が広い」という**真逆の構成**になっている（§1.4）。

### 3.2 SmartHR Design System

- 基準値は **16px**
- `S`（13.71px）と `XS`（12px）は、**積極的な使用を避け、
  レイアウト上どうしようもない場合にのみ使う**と位置づけられている
- 表の数値列は、桁数を縦に比較できるよう右揃えにする規約がある（→ D9に反映済み）

### 3.3 Fluent 2（Microsoft / デスクトップ）

| トークン | サイズ | 行高 |
|---|---|---|
| Body1 | 14px | 20px |
| Caption1 | 12px | 16px |
| Caption2 | 10px | 14px |

デスクトップ前提のため一段小さい構成だが、**欧文基準のスケールであり
日本語にそのまま適用はできない。** 参考値として記録するに留める。

### 3.4 結論

日本語の業務系デスクトップツールとしては、
**本文14〜16px・行高120〜130%が定石**であり、
27型WQHD環境での正規化（D12）を加味して **本文16px** を採用する。

## 4. フォント候補とライセンス

### 4.1 ライセンス整理

| フォント | ライセンス | 商用 | アプリ同梱 |
|---|---|---|---|
| IBM Plex Sans / Sans JP / Mono | SIL OFL 1.1 | 可 | 可 |
| Noto Sans JP | SIL OFL 1.1 | 可 | 可 |
| Inter | SIL OFL 1.1 | 可 | 可 |
| JetBrains Mono | SIL OFL 1.1 | 可 | 可 |

**SIL Open Font License 1.1** は、
「フォントファイルそのものを単体で売ることは禁止するが、それ以外はほぼ自由」
という設計のオープンライセンス。ソフトウェアへの同梱配布、改変、商用利用すべて可能。

実務上の制約は2点のみ:

1. **改変時は元の名前を名乗り続けてはいけない**（Reserved Font Name条項）。
   サブセット化のみであれば通常は改変にあたらないと解釈されるが、
   名前を変えておけば確実。
2. **ライセンス文の添付**。`OFL.txt` をフォントと同じ場所に置くか、
   アプリのライセンス表記に含める。

→ facetでは Tauri の `resources` にフォントと `OFL.txt` を並べて配置すれば完了。

なお、デジタル庁デザインシステムも Noto Sans JP / Noto Sans Mono（いずれもOFL）を
採用しており、公的機関での採用実績がある。

### 4.2 避けるべき選択肢

| 選択肢 | 理由 |
|---|---|
| Yu Gothic / Meiryo の同梱 | **再配布不可**。ライセンス違反になる |
| Google Fonts の CDN 読み込み | オフラインで動作しなくなる。デスクトップアプリが起動のたびに外部通信するのは避けるべき |
| 日本語フォントの字数サブセット化 | **禁止**。仕様書ツールである以上、ユーザーがどの漢字を入力するか予測できない。珍しい人名や専門用語が豆腐（□）になる |

### 4.3 ファイルサイズ対策

日本語フォントは収録字数が多く、全ウェイトを入れると数十MB規模になる。

→ **必要なウェイトのみに絞る**（Regular / Medium / SemiBold の3つで足りる）
→ **`unicode-range` でラテンと和文をファイル分割**する。
　 ブラウザが「この文字を描くのにどのファイルが要るか」を判断して
　 必要な分だけ読むため、初期描画が軽くなる。

字数削減ではなくウェイト削減で対処する。

## 5. 個別モジュールの指摘

### 課題ツリー ← rev.3 で追加

**本モジュールは他より明確に進んでおり、U3の参照実装とすべきである。**

#### 到達できている点（規約化の対象）

1. **欠落軸の表現が統一されている。**
   `未決` と `仮説なし` という別種の欠落が、**どちらも赤い破線チップ**で表現されている。
   D1が求めていた状態そのもの。
2. **空欄を放置せず、欠落として「存在させて」いる。**
   用語集の「別名なし」という黒テキストと比べ、思想が正しく実装されている。
3. **全体の未定義量が集計されている。**
   ヘッダーの `⚠ 要対応 4 / 仮説なし 2 / 未決 2` が、ツリー内と同じチップ表現で集計され、
   一目で総量が分かる。**他モジュールにない到達点。**

→ U3は、ゼロから規約を考えるのではなく、**この画面を言語化する**作業とする。

#### 問題点

| 問題 | 対応 |
|---|---|
| 支持／棄却が輝度差ほぼゼロで識別できない | **D15**（最優先） |
| ノード幅可変によりバッジが散り、スキャンできない | **D3**（再定義） |
| グレーアウトと赤警告が同一ノードで矛盾 | **D17** |
| 選択状態の緑が、用語集ヘッダーの装飾緑と衝突 | **D2**。選択は彩度ではなく枠線の太さ／リングで示す |
| `認知されてない` 内のカード内カードが木の文法を破っている | **D3**。ツリー上には `FB 1件` 等の指標のみ置き、実体は別パネルへ |

#### 未確認事項

- **破線エッジの意味が不明。** `需要がない` と `認知されてない` を結ぶ破線が、
  親子エッジと同じ視覚チャネル（線）を使いながら別の関係を表しているなら混同される。
  **D18（見送り配下の導出）は親子関係に依存するため、これを先に確定させる必要がある。**
- ルートの `★` はASCII記号であり、他のどの表現とも系統が違う。
- キーボードヒントが5項目に増え、小さく薄いまま（D11の二重減衰）。

### 用語集

- 別名列: バッジ表示と「別名なし」プレーンテキストが同一列で混在
- 種別セレクトがOSネイティブ（shadcn/ui未適用）
- テーブル外に方眼グリッドが見えており、影も余白ルールもないため「板が浮いている」

### ロジックツリー

- エッジ線とノードのボーダーがほぼ同じ濃度。
  エッジは構造そのものなので、主張させるか、逆にノードのボーダーを消して面だけで表現するか、
  どちらかに振るべき
- ノードの角丸が大きめ（pill寄り）で、テーブルの角丸ゼロと明らかに別デザイン。
  **同一アプリに見えない**
- 右上のキーボードヒントが半透明で、下の方眼が透けている

### エラーカタログ

- 「表示」「絞り込み」ラベルがチップより小さいグレー文字で、ベースラインも揃っていない。
  ツールバーの一行が3種類の高さで構成されている
- テーブルが3行で終わり、下に広大な方眼が残る。
  コンテンツ領域の底が定義されていないため未完成に見える

### シーケンス

- 右パネルの回答欄が画面右端で切れている。未完成に見える最大要因の一つ
- 方眼グリッドのコントラストが高く、コンテンツと競合している
- 入力欄がすべて「枠付きの箱」で描かれており、画面の大半がフォームに見える。
  高密度入力なら、枠を消して罫線とし、ホバー／フォーカス時だけ枠を出す方が
  密度と静けさを両立できる

## 6. 補足: 現行の配色が持つもう一つの問題

現行UIは「クリーム地（#F4F1EA 近辺）＋ 高コントラストの見出し ＋ 温かみのある差し色」
という構成になっている。

この配色は、現在AIが生成するデザインが強く収束している3パターンのうちの1つに一致する。
とくに温かいクレイ／テラコッタ系の差し色（#D97757 近辺）は
Anthropic自身のアクセントカラーであるため、この組み合わせは
**「AIに作らせた画面」の記号として読まれるリスクがある。**

D2（無彩色ベース＋赤のみ）への移行は、この観点からも合理的である。
機能的要請（赤の情報量を回復する）と、識別性の要請が同じ方向を向いている。

## 7. 未決事項

### U1. フォントセットの選定 ← **依然として未決。合意未取得**

| 案 | 構成 | 利点 | 欠点 |
|---|---|---|---|
| A | IBM Plex Sans + Sans JP + Mono | ラテン・和文・等幅が**同一の設計思想**で作られており、混植のズレ（D7）が構造的に起きにくい。ウェイトも揃っている | 字形にやや個性がある |
| B | Noto Sans JP + Noto Sans Mono | デジタル庁デザインシステムと同一構成。公的採用実績あり | ラテン側の選定が別途必要 |
| C | Inter + Noto Sans JP + JetBrains Mono | 字形の癖が少ない | Noto Sans JP は字面が大きく Inter と並べると和文が勝つため、`size-adjust` での補正が必要 |

**推奨: 案A**（D7の解決が構造的に保証され、補正作業が不要なため）

### U2. グレー階調の刻み数と、各色の具体値

D2・D15・D19の実施にあたり必要。未着手。

決めるべきもの:

- グレー階調の刻み数（背景 / ボーダー / テキスト補助 / 棄却 / 見送り で最低5段階が必要）
- 支持の緑の具体値（明度高め・彩度あり。装飾緑との差別化が前提）
- 欠落の赤の具体値と、破線の太さ・破線パターン

### U3. 「未定義」判定の共通規約 ← rev.3 で位置づけ変更

D1実施の前提として、
**「未定義とは何か、どう見せるか」を全モジュール共通の規約として1枚の文書に固定する**
必要がある。D1・D2は設計トークンの書き換えでは済まず、
各モジュールの描画ロジックに手が入るため。

**rev.3 での変更: 課題ツリーを参照実装とする。**

課題ツリーは既に欠落軸を破線チップで統一表現できており（§5参照）、
規約はゼロから設計するのではなく**既存実装の言語化**として作成する。
これにより作業量が大幅に減り、かつ「動いている実装がある」という裏付けが得られる。

規約に含めるべき項目:

- 欠落軸は輪郭（赤の破線枠・塗りなし）で表現する（D14）
- 空セルに文字列を埋めない（D1）
- 欠落は必ずヘッダーで集計する（課題ツリーの実装に倣う）
- 見送り配下の扱い（D17・D18）

### U4. 破線エッジの意味 ← rev.3 で新規追加

課題ツリーの `需要がない` — `認知されてない` 間の破線が、
親子関係なのか別種の参照なのかが不明。

**D18（見送り配下を祖先から導出する）は親子関係の定義に依存するため、
D17・D18の実装前に確定が必要。**

## 8. 実施優先順位

| 順 | 内容 | 対応D | 根拠 |
|---|---|---|---|
| 1 | **支持／棄却の識別性を回復** | D15 | **美観ではなく「ツリーが読めるか」の問題**。判断結果が拾えないなら主要情報が失われている |
| 2 | 数字の等幅化＋数値列の右揃え | D9 | 1行で効く。コスト比最大 |
| 3 | 未定義表現の統一 | D1, D14 | **facetの機能そのものの修復**。見た目改善より価値が高い |
| 4 | 色の役割整理（緑帯廃止・分類の脱色・ボタン脱色） | D2, D16, D19 | 既存トークンの書き換え中心で着手できる |
| 5 | タイポグラフィスケールの適用 | D11, D12, D13 | 基準値16px化・行高の是正。フォント差し替え前でも単独で効果あり |
| 6 | ノード幅・行高の固定＋省略 | D3 | バッジが縦一列に揃い、スキャン可能になる |
| 7 | 見送り配下の集計分離 | D17, D18 | U4（破線の意味）確定後 |
| 8 | フォント差し替え | D6〜D8 | U1確定後。5の完了後、階層表現をウェイトに移譲する |
| 9 | 警告メッセージの改善 | D4, D5 | |
| 10 | ネイティブselect置換・角丸統一 | §1.1 | |

**着手条件:**

| 作業 | 前提 |
|---|---|
| 優先3・4 | **U3**（未定義の共通規約）の確定 |
| 優先1・4 | **U2**（グレー階調と各色の具体値）の確定 |
