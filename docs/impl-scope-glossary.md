## 2. 技術セットアップの前提（**完了済み。やり直さないこと**）

計画フレームワークが想定する出発点（リポジトリが存在し、テストがグリーンで通る状態）は M0 として実施済み。**計画の第1タスクを環境構築にしないこと。** 現状は以下。

- Tauri 2 ＋ Vite ＋ React ＋ TypeScript。`npm run tauri dev` で起動する
- Tailwind CSS ＋ shadcn/ui（Button のみ導入済み）。役割トークンは `src/index.css` に枠だけあり、値は仮置き
- Vitest。`npm test` で空のテストが1本グリーン
- `schemas/glossary.schema.json` → `src/types/glossary.ts` の型生成が `npm run gen:types` で通る
- `.gitattributes` に `*.json text eol=lf`（**必須。** Windows の autocrlf 下では、これが無いと commit 時に CRLF 変換され全行 diff になる。正規形の LF が Git 上で無意味になる）
- Tauri の fs / dialog プラグインを capabilities まで導通済み

計画時に前提を取り違えやすい点:

- **型定義は書かない。** `src/types/glossary.ts` はスキーマからの生成物で、**コミットしていない**（`.gitignore` 済み）。`prepare` / `predev` / `prebuild` / `pretest` で自動再生成されるため、スキーマと型がズレることはない。手書きの型と二重管理しない
- **Tailwind は v4** で、`tailwind.config.js` も `postcss.config.js` も存在しない。トークンは CSS の `@theme inline` で定義する。旧来の JS 設定を前提にした手順は通らない
- **shadcn/ui は Radix ベース（`-b radix`）** で初期化済み。コンポーネント追加は `npx shadcn@latest add <名前>` で、必要になった時点で足す
- `src/components/ui/**` は生成物のため lint 対象外にしてある。手で整形しない

Rust は原則書かない（rev 7章）。ロジックは全て TypeScript 側。Tauri コマンドは1つも定義しておらず、**追加もしない**（ファイルアクセスは fs / dialog プラグインで足りる）。ただし capabilities の scope は現状ダイアログで選んだファイルまでなので、**フォルダ走査（M2 の検証スコープ、M5 の監視）には scope の追加が要る**。

## 3. 正規形（アプリのシリアライザが厳守する値）

Skill 側の `glossary-write.mjs` と**完全一致**させること。1文字でもずれると、Skill が書いたファイルをアプリが開いて保存するたびに全行 diff が出て、「変更履歴を仕様の変更履歴として読める」という目的（rev 5章）が壊れる。

| 項目       | 値                                                       |
| ---------- | -------------------------------------------------------- |
| キー順     | **JSON Schema の properties 記載順から実行時に導出する** |
| インデント | スペース2                                                |
| 改行コード | LF                                                       |
| 末尾改行   | あり                                                     |
| BOM        | なし（読み込み時は除去する）                             |
| 非ASCII    | エスケープしない（日本語をそのまま書く）                 |

**キー順をアプリ側にハードコードしないこと。** Skill 側はスキーマから実行時導出しているため、ハードコードするとスキーマ改訂時に静かにずれる。`$ref` の解決を含む導出ロジックが必要（実装の参考: `glossary-write.mjs` の `reorder` / `deref`）。

**テストで担保する**: Skill が書き出したファイルをアプリが読み→保存して、バイト単位で不変であること。これはこのプロジェクト最大のリスク箇所であり、回帰テストの筆頭。

## 4. 実装順（マイルストーン）

原則は **「歩けるスケルトンを最初に一周させる」**。最もリスクの高い機構（正規化・検証・ファイルI/O）を最初に実証し、その後で独立した層を足す。UIの作り込みを先行させない。

### M1: 歩けるスケルトン（最優先）

フォルダを開く → JSON 読込 → スキーマ検証 → リスト描画 → 編集 → 自動保存（正規形で書き込み）→ **Git diff が編集箇所だけに出る**。

完了条件:

- Skill が生成した用語集ファイルをアプリで開いて1フィールド編集し、`git diff` が該当行だけに出ること（バイト一致テストがグリーン）
- スキーマ検証に落ちるファイルが「開けない」（レベル1拒否）として扱われること

この一周が通れば、プロジェクト固有の技術リスクはほぼ消える。

### M2: 検証レイヤの完成

- **整合性検証（レベル2＝受け入れて赤表示）**: ID重複 / alias重複（用語内・用語間）/ alias と他用語の name 衝突 / **name 同士の重複** / 用語集の単一性違反
  - **name 重複は Skill 側スクリプトにも現状無い検査。今回追加する**（同名2件は「この語を正式名とする」という宣言の矛盾であり、追記のたびに発生確率が上がる。スキーマでは防げない）
- warning 可視化: `kind === "undecided"` は種別セル、`definition === ""` は定義セルに（セル単位）
- 検証スコープはプロジェクト全体。フォルダ内全 JSON を走査し、ファイル一覧に赤バッジ
- 未知 type / 未知 schemaVersion のファイルは「一覧表示のみ・編集不可」（クラッシュしない）

完了条件: 意図的に壊したファイル群（ID重複・name重複・alias衝突・用語集2個・未知type・スキーマ違反）を用意し、それぞれ期待どおりの区分で扱われること。

### M3: エディタの操作性

- キーボード操作を**共通フック/モジュールに一元化**（rev 10章。ツールごとの自前実装は禁止）
- **修飾キーはプラットフォーム抽象を通す**（Windows: Ctrl / Alt、macOS: Cmd / Option）。各コンポーネントが `Ctrl` を直接見ない。Tauri なので macOS で動く可能性は残っており、Ctrl 直書きだと Undo が効かない。M0 時点の動作確認は Windows のみ。以下のキー表記は Windows 側の呼び方
- 階層・リスト系ファミリー標準: Enter＝直後に行追加、空欄 Backspace＝行削除、Alt+↑↓＝並び替え、矢印＝行間移動、**Tab＝セル間移動**（用語集に「子」の意味が無いため）
- **IME 対応**（composition イベント判定。変換確定 Enter の誤爆防止。日本語入力アプリ最大の地雷）
- 境界規則: モーダル表示中・テキスト編集中は操作言語を停止（例外は編集境界キー Enter/Tab/Esc/空欄Backspace のみ）
- 検索（name / aliases / definition 横断）＋種別フィルタ。**導出表示中は Alt+↑↓ を無効化**
- Undo/Redo（Ctrl+Z / Ctrl+Shift+Z、ファイル単位・メモリ内）

### M4: ファイル一覧の額縁とファイル操作

- 新規作成（type選択）/ 削除（OSゴミ箱へ。完全削除しない）/ 赤バッジ表示
- 用語集0個の状態からの自動生成

### M5: 外部変更検知

- **フォルダ単位**で監視（外部リネームも検知するため）
- 自己書き込みの除外（検知ループの構造的排除）
- 未保存編集なし → 再読込＋トースト通知。**Undo履歴は破棄**し、**取り込み前の内容を一時退避してトーストに「取り込み前に戻す」を出す**
- 未保存編集あり → 二択ダイアログ（自分の編集で上書き / 外部変更を取り込む）。マージUIは作らない

### M6: NotePM 向け Markdown 出力

- 種別グルーピングの表形式。`##`＝title、`###`＝種別グループ（h1 は使わない。NotePM 目次は h1〜h3）
- 空の種別は見出しごと省略。グループ順は enum 定義順で固定。グループ内はデータ配列順
- 列: 名称／種別／定義／別名／備考（IDは出さない）
- `definition` 空は `（未定義）`、`undecided` は `### 未分類` として**出力にも明示する**
- クリップボードコピー ＋ .md 書き出しの両方

### M7: デザイントークン整備

- 役割トークン（`ink` / `warning` / `ok` ＋無彩色系）を Tailwind 設定に定義。**色値の直書き禁止**
- ライト/ダークは同じ役割トークンにモード別パレットを割り当て（反転による自動生成はしない）
- 現行3色（#22303C / #C73E3A / #2C7A6E）はライト側の**仮置き**。コード上も仮置きと明示
- 方眼紙背景・フォントもトークン経由
- **フォントは明示的なスタックを書く。** 現在の `--font-sans` は shadcn プリセットが入れた Geist で、**日本語グリフを持たない**（英数字だけ Geist、日本語は OS 既定にフォールバックする混在状態）。フォールバック任せにすると Windows は Yu Gothic UI、macOS は Hiragino Sans となり、**表形式の列幅と行の詰まり方がプラットフォームで変わる**。`system-ui, -apple-system, 'Segoe UI', 'Hiragino Sans', 'Yu Gothic UI', 'Noto Sans JP', sans-serif` のように書けば、フォールバックはグリフ単位に効くので英数字は各OSのUIフォント、日本語は各OSの標準日本語フォントに振り分かる
- **日本語 Web フォントは同梱しない。** Noto Sans JP は丸ごとで数MB、サブセット化すると「どの字を含めるか」の管理が発生する。ユーザーが入力する用語にどの漢字が来るか事前に分からないため、サブセットは破綻する。完全な同一描画は諦め、各OSでネイティブに見えることを取る

M7 は M1〜M3 と並行してよいが、色値の確定はドッグフーディング後（rev 9章）。

## 7. M1 完了に伴う申し送り（2026-08-02 追記）

M1 は実装・レビュー・E2E 完了（PR #2）。完了条件2つ（バイト一致で編集行だけの diff／スキーマ違反のレベル1拒否）は実機確認済み。実装時のレビューで出た残件を後続マイルストーンの計画入力として記録する。

### M2 で扱うもの

- **ウィンドウ close 時の flush**（レビュー指摘・最重要）: 現状、ウィンドウを閉じると React の unmount を経ずに webview が落ちるため、デバウンス窓（500ms）内の最後の編集が保存されない。Tauri の `onCloseRequested` で `flush()` を await してから閉じる配線が必要。あわせて、close/ファイル切替時の flush が**再失敗**した場合に dispose が復元済み pending を破棄する二重失敗エッジも同時に塞ぐ（`src/App.tsx` closeCurrentFile / `src/core/autosave.ts`）
- **自動保存失敗の可視化**: write 失敗は現状 console.error のみ（pending 復元により次の flush/編集で再試行はされる）。M2 の検証エラー表示と同じ枠で UI 通知を設計する
- **listOnly / rejected の理由文言の整備**: `type` が非文字列のとき「type がありません」と表示される・`schemaVersion` 欠落と新版が同文言、など分類は正しいが文言が不正確な箇所がある（`src/core/load.ts`）。M2 の「未知 type / 未知 schemaVersion の一覧表示」本格対応時に直す
- **openFolder の失敗時 UI**: フォルダ読込失敗時に選択状態だけ先にクリアされ、旧フォルダの一覧が残る不整合。openFolder 連打の相互ガードも未実装（selectFile 側のトークンガードは実装済み）
- **レジストリの idPrefixes 自己重複検査**: `['term','term']` のような同一モジュール内重複が検査をすり抜ける（`src/core/registry.ts`）。2本目のモジュールを手書きする時点で実害化するため、モジュール追加前に塞ぐ

### M3 で扱うもの（M1 の暫定仕様の作り直し）

- **別名セル**: 読点・半角カンマ区切りの1入力欄は M1 暫定。全角カンマ・改行貼り付けは分割されない。M3 のキーボード操作設計と一体で作り直す
- **kind セルの表示**: enum 生値（actor 等）をそのまま表示中。日本語ラベルの対応表を UI 層に持たせる（データ・スキーマは英語 enum のまま）
- **非制御入力からの移行**: M1 は IME 対応回避のため defaultValue 方式。M3 の composition 対応時に制御方式を再設計する

### 実装で確定した事項（計画の前提に昇格）

- **自動保存の重複判定は「書き込み実行時点」で行う**: スケジュール時点の比較（M1 計画の原案）は、in-flight write との競合で編集消失を起こすことが実装時に判明した。確定した設計は「update 時の早期 no-op は write が飛んでいない時だけ／chain 実行時に lastSaved（確定したディスク状態）とだけ比較／失敗時は pending に復元して flush で再試行」（`src/core/autosave.ts`）。M5 の外部変更検知（自己書き込み除外）はこの構造を前提に設計すること
- **ファイル選択時は必ずディスクから読み直す**: 走査時キャッシュを編集起点にすると直前の自動保存分を古い内容で上書きする。M5 の監視実装でもこの原則を維持する
- **tsconfig は3分割**（app / test / node）: テストは `node` 型が必要なため app から除外し、`tsconfig.test.json` で型チェックする。以後のテスト追加はこの構成に従う

## 8. M2 完了に伴う申し送り（2026-08-02 追記）

M2 は実装・レビュー完了（PR #3）。整合性検証（レベル2）・warning のセル単位可視化・プロジェクト全体の検証スコープ・M1 申し送りの解消まで入った。手動 E2E で出た指摘（前後空白での重複すり抜け / warning の視認性 / fixture の正規形ずれ）も修正済み。以下は後続マイルストーンの計画入力。

### M3 で扱うもの

7節の M3 項目（別名セル / kind の日本語ラベル / 非制御入力からの移行）は引き続き有効。M2 で新たに積んだものを以下に追加する。

- **別名セルは実使用でも再指摘された**（7節の再掲を兼ねる）: データ自体は `aliases: string[]` の配列なので、直すのは入力 UI だけ。読点・半角カンマ区切りの1入力欄は暫定で、全角カンマ・改行貼り付けは分割されない
- **行キーが配列 index になっている**: ID 重複ファイルを「受け入れて赤表示」する以上 `term.id` はキーに使えない（重複キーで描画が壊れる）。M3 の並び替え（Alt+↑↓）では index キーだと行の同一性が保てないため、この時点で再設計が要る（`src/modules/glossary/GlossaryEditor.tsx`）
- **セル赤表示のキーが entityId のみ**: ID 重複時、同じ ID を持つ全行に同じセルマークが波及する（現状は行全体が赤なので実害は小さい）。上の行キー再設計と併せて直す
- **検索の照合も `normalizeForMatch` を使うこと**: 重複判定と検索で規則を分けない（`src/core/normalize.ts`）

### M4 で扱うもの

- **赤バッジは M2 で実装済み**。4節の M4 に残るのは新規作成（type選択）/ 削除（OSゴミ箱）/ 用語集0個からの自動生成
- **単一性違反の解消手段が無い**: M2 で「検出して赤表示」までは入ったが、アプリ内で直す手段が無い。M4 の削除機能が入って初めて「拒否は修正に外部エディタを強いるので最小限に」の原則（rev 5章）が閉じる

### M5 で扱うもの

- **自己書き込みの除外は autosave の現構造を前提に設計する**: `flush()` は「書き残しの有無」を boolean で返し、ウィンドウ close のゲートに使っている。write 失敗時は pending に復元するが、**復元するのは失敗した内容が直近の要求（`latest`）と一致するときだけ**——後続の write が最新を書き終えた後に古い内容で上書きする巻き戻りを防ぐため（`src/core/autosave.ts`）
- **外部変更の取り込み経路でも `computeIssues` を通す**: 検証は現在「フォルダ走査時」「編集時」の2経路で全ファイル再計算している。外部変更が3本目の経路になる（`src/App.tsx`）
- **`saveError` のクリア条件**: 現状は `onSuccess`（実際に書き込みが起きて成功）でしかクリアされないため、書き込みが起きないままファイルを切り替えると前のファイルのバナーが残りうる。M5 のトースト通知の設計と併せて整理する

### いつでもよいが、忘れると実害化する残件

- **`checkProjectConsistency` の `out.set(f.path, [issue])` が上書き代入**: コア横断ルールが2本目になった瞬間、先のルールの issue を消す。**2本目を足す時点で必ず配列への追記に変える**（`src/core/project-consistency.ts`）
- **unmount 時の effect が `void flush()` の直後に `dispose()` を呼ぶ**: flush 失敗で復元された pending を捨てる経路。実際の close は `interceptClose` 側を通り、そちらは flush 成功時のみ閉じるので現状は実害なし（`src/App.tsx`）
- **保存できないと閉じられない**: flush 失敗時に close をブロックするため、ファイルが恒久的に書けない状態（権限・ロック）だと終了手段が無くなる。「破棄して閉じる」の脱出口が要る
- **編集1打鍵ごとに全ファイルの `checkConsistency` を再実行している**: 数百レコード規模では問題ないが、規模が増えたら選択中ファイルだけの差分計算に変える

### 実装で確定した事項（計画の前提に昇格）

- **モジュール規約の実装スロットが6点中5点埋まった**: `type` / `displayName` / `schema` / `idPrefixes` / `Editor` / `checkConsistency`（規約4）/ `singleton` / `migrate`（規約6・恒等）。残るは出力ロジック（規約5・M6）。**2本目のモジュールはこの形をそのまま実装する**（`src/core/registry.ts`）
- **整合性検証は2層に分かれる**: モジュール内検証＝各モジュールの `checkConsistency`（自ファイルで完結）、コア横断検証＝`src/core/project-consistency.ts`（単一ファイルでは判定できないもの）。参照切れは「参照する側」のモジュールの提供物なので、2本目のツールが来た時点でそちら側に実装する
- **`LoadResult` の3 variant すべてが `type` を持つ**: 単一性は「`type: glossary` のファイルが2つ以上」という物理条件なので、スキーマ違反（rejected）や未知版（listOnly）のファイルも数える必要がある（`src/core/load.ts`）
- **照合の正規化は NFKC ＋ 前後空白の除去 ＋ 英字大文字小文字同一視**: 前後空白の除去は表記ゆれの吸収ではなく入力ノイズの除去（無いと末尾にスペースを足すだけで重複判定をすり抜けられる）。NFKC が全角スペースを半角化した**後**に trim する順序が必要。カナ同一視・送り仮名吸収は引き続きしない
- **エラーと warning の視覚表現は「同系色の面の濃さ」で区別する**: 点線下線は視認性が低く行の罫線と紛れたため廃止した。**波線は表記ゆれの「指摘（suggestion）」用に予約**されているので warning には使わない（session-notes 論点5）。空の定義セルは「未定義」のプレースホルダで明示する（M6 の Markdown 出力の表記と揃えた）。濃さの値は仮置きで、確定は M7
- **capabilities は JS API を追加で使うたびに権限追加が要る**: close 横取りの `destroy()` には `core:window:allow-destroy` が必要だった（無いと ACL 拒否で**ウィンドウが閉じなくなる**）。「Rust を書かない」方針とは別問題なので、新しい Tauri JS API を使うときは `src-tauri/capabilities/default.json` を確認すること。なお2節の「フォルダ走査には scope の追加が要る」は M1 で `recursive: true` により解決済み
