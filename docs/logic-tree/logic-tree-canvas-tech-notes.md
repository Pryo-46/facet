## 論点1: ノード配置方式（確定：自動レイアウト）

**決定**: 座標をデータに持たない。ノードの位置はレイアウト関数がデータから毎回導出する。

**根拠**:

- rev 3章「正となるデータは一つ。図は導出」の直接適用。自由配置は座標という第二の権威をデータに持ち込む
- Git diff のノイズ。文言を1文字直した commit に座標差分が混入するのを避ける

**「マウスで親を掴んで変えたい」との整合**: ドラッグは入力ジェスチャであり、書き換わるのは `parentId` と配列インデックスのみ。**座標の編集ではなく構造の編集**なので自動レイアウトと矛盾しない。エクスプローラのファイル移動と同じ構造。むしろ手で動かした結果が必ず正規レイアウトに吸着するため、ぐちゃぐちゃな配置が保存データに残らない。

**先行事例**: Miro のマインドマップも同じ構造を採る（完全な自由配置は許さず、大きさ・並び替え・親兄弟の付け替え・複製のみ許す）。このうち座標を持つのは「大きさ」だけであり、本ツールはそれも自動算出とする（論点4）。

## 論点2: ライブラリ選定（確定：いずれも不採用）

**決定**: React Flow（@xyflow/react）、tldraw、elkjs、dagre のいずれも採用しない。

### React Flow を採らない理由

MITライセンスで品質も高いが、**設計思想がフローチャート向けに固定されており、facet の要求と構造的にミスマッチ**。

- ノードは `position` を持つ絶対配置DOM。自動レイアウトではその `position` を捨てるため、ライブラリの中心価値が不要になる
- エッジのルーティングが弱い（ノードを避ける直交配線は非搭載。`react-flow-smart-edge` という別パッケージで補う世界）
- レイアウトは非搭載（dagre / elkjs を自分で回す前提）
- Undo/Redo が非搭載（`useUndoable` 等の外部フックで補う）
- **ノード内テキスト編集とキャンバス操作が競合する**。Space がパン、Backspace が削除に食われ、`nodrag` / `nokey` クラスで個別に殺す運用になる。rev 10章「境界規則（テキスト編集中）」と IME 対応を、React Flow のイベント系の上に再構築することになる
- 専用CSSを読み込む前提で、Tailwind / shadcn のトークン体系と二重管理になる

**総括**: facet が必要とするもの（自動レイアウト・Undo・IME・操作言語の一元化）はほぼ全て React Flow の外側にあり、React Flow が提供するもの（座標ドラッグ・ハンドル接続・ベジェエッジ）はほぼ全て facet が使わない。

### tldraw を採らない理由

- 自由描画ホワイトボードであり、facet が必要とするのは「ズーム・パンする面」だけ
- **ライセンスリスク**: 埋め込みアプリでの商用利用は年額 $6,000 の商用ライセンスが必要（100日間トライアルあり、非商用は無料）。社内業務ツールとして配布した時点で該当しうる

### elkjs / dagre を採らない理由

- どちらも任意の有向グラフ向け。ロジックツリーは**単一親の厳密な木**であり、その強みが不要
- elkjs はバンドル1MB超・Web Worker前提の非同期API。会議中に Enter を押すたび非同期レイアウトを待つ構造は避けたい
- ※ 状態遷移図（任意グラフ）の描画では再検討の余地がある。ツリーには過剰、という判断

### Miro / Figma を参考にしない理由

両者は WebGL / WebAssembly ベースの独自描画エンジンで、テキストレイアウト・IME・フォントフォールバック・コピペ・アクセシビリティを全て自前構築している。**ボード全体が1枚の canvas** であり、マインドマップだけライブラリを挿す余地が構造的にない。

facet は「構造が既知のツリー／シーケンス」で、1ファイルは会議単位の小さなJSON（ノード数はせいぜい数百）。この規模で canvas 描画に行くと **IME の自前実装という地獄**が始まるため、越えない。参考にすべきは実装技術ではなく「掴んで動かすが離すと自動レイアウトに吸着する」という**振る舞いの設計**。

## 論点3: 描画構成（当初の想定：DOM＋SVGの2レイヤ）

**決定**: ビューポート層（d3-zoom が算出する `{x, y, k}`）の下に2枚のレイヤを重ね、両方に同一の transform を当てる。

- **下layer: SVG** — エッジ専用。曲線と矢印を描く
- **上layer: 絶対配置DOM** — ノード。通常の `<div>`

座標系が同一なのでズレは原理的に発生しない。ルート `<g>` / コンテナに `translate(x, y) scale(k)` を一発かけるだけ。

**（logic-tree M1 の実装で確定）**: 実装は2レイヤではなく**3レイヤ**になった——背景レイヤ／エッジレイヤ（SVG）／ノードレイヤ（絶対配置DOM）。背景レイヤは M1 では空で、シーケンスの失敗ゾーンのために枠だけ確保している（`data-layer="background"`）。`docs/overview-rev.md` と `docs/logic-tree/logic-tree-m1-scope.md` は当初からこの3レイヤで記述しており、本節の見出しが古いままだった。

**DOM を選ぶ理由**:

1. **IME**（決定打）。SVG内でのテキスト編集は `foreignObject` が必要になるが、Windows のブラウザで変換候補ウィンドウの位置ズレ・フォーカス喪失の報告が絶えない。rev 10章で「日本語入力アプリ最大の地雷」と明記しておきながら、その地雷原の上に実装基盤を置く理由はない。通常のDOMなら `<textarea>` がそのまま使え、composition イベントも素直に取れる
2. **shadcn/ui との互換**。バッジ・チップ・ツールチップがそのまま載る
3. **テキスト折り返しと高さ**。SVG の `<text>` は自動折り返しを持たず、`<tspan>` の y 座標を手計算する必要がある

**d3-zoom を選ぶ理由**: ホイール／ピンチ／ドラッグを正規化して `{x, y, k}` を返すだけの部品であり、React Flow のようにイベント系を乗っ取らない。**操作言語を自前の共通フックに一元化する rev 10章の実装規約と共存できる**。

**注意点**: SVGレイヤは下にあるためDOM側の操作を奪わないが、将来エッジをクリック可能にする場合は SVGレイヤを `pointer-events: none` にしつつパス要素だけ `auto` に戻す。

## 論点4: ノードサイズと測定（確定）

**決定**:

- 幅は文言から自動算出。**最大 320px** で折り返し（日本語で全角22文字前後）。最小幅を設ける
- **等幅フォントは採用しない**。フォントは可読性で選ぶ
- 幅の測定はオフスクリーン `<canvas>` の `measureText` で**同期的**に行う
- 折り返し位置は測定層で確定させ、描画層には**確定済みの行配列**を渡す

**「レンダリング前にサイズが確定していない」問題**: レイアウト計算には各ノードの幅・高さが必要だが、高さは折り返し行数で決まり、行数は幅で決まる。素朴に「描画 → ResizeObserver で実測 → レイアウト → 再描画」の2パスにすると、Enter を押すたびに**一瞬ズレた位置に出てから飛ぶ**ちらつきが発生する。`measureText` はDOMに触れずリフローも起こさないため、「入力 → サイズ計算 → レイアウト → 一度だけ描画」の1パスで完結する。

**等幅を採らない理由**: 「文字数×文字幅で計算できる」という期待が日本語では成立しない。

- Windows の日本語等幅フォントは実質 MSゴシック / BIZ UDゴシックの二択（Consolas 等はCJKグリフを持たずフォールバックで等幅性が崩れる）
- 「全角＝半角の2倍」は完全には成り立たない（半角カナ、絵文字、East Asian Width の Ambiguous 区分、結合文字、サロゲートペア）。正確を期すには EAW テーブルの自前実装が必要になり、`measureText` より厄介なものを、より低い精度で書くことになる

**測定と描画のフォント指定は同一の情報源（rev 9章のフォントトークン）を参照すること**。ズレると全ノードが微妙に窮屈／間延びする。

**やらないこと**: 折り返し後の幅の再縮小（2パスになる。日本語は任意位置で折り返せるためほぼ最大幅に貼りつく）。

**保留**: 最大幅を可変にするスライダーの設置は**見送り**。「決められないからつまみを付ける」は、繰り返すと設定項目が増えてユーザーが仕様でなく見た目をいじる時間が増え、共有時に全員が違う画面を見る。まず 320px 固定で使い、実データで窮屈と分かってから可変化を検討する。可変化する場合の条件は下記（→ 論点8）。

## 論点5: レイアウトアルゴリズムと層構造（確定）

**決定**: Reingold–Tilford 系（可変ノードサイズ対応）を**自前実装**する。

`d3.tree()` の `nodeSize` は全ノード同一サイズ前提であり、文言長で高さが変わる facet では使えない。`d3-flextree` という可変対応の派生もあるが、facet には標準アルゴリズムにない要求（折りたたみ状態、葉数バッジの表示スペース、未定義ノードの強調枠、ドラッグ中のレイアウト固定）が確実に入るため、ライブラリの内部座標系に後から割り込むより最初から自前関数にするほうが安い。輪郭（contour）を持って兄弟部分木を左詰めで寄せる方式で、可変サイズ対応込みでも 200行程度。

### 4層構造

1. **測定層**: `(文字列, フォントトークン) → {幅, 高さ, 行配列}`。canvas measureText と折り返し計算。**DOM非依存**なのでテストが書ける
2. **レイアウト層**: `(ツリーデータ, サイズマップ, 折りたたみ状態) → Map<ノードID, {x, y}>`。**完全な純粋関数**
3. **アニメーション層**: 前回の座標Mapと今回の座標MapをIDで突き合わせ、差分を補間（200〜300ms）
4. **描画層**: 座標Mapを受け取ってDOM / SVGに流す

**レイアウト層の純粋性が最重要**。入力が同じなら出力が同じ、が保たれることで「図は導出」がコードレベルで担保され、スナップショットテストが可能になる。ここに「前回どこにあったか」の状態が混入した瞬間、同じデータから違う図が出るようになり思想が崩れる。

**アニメーションは必須**。自動レイアウトでは親を変えた瞬間に周囲が一斉に再配置されるため、無アニメーションだと画面が瞬間的に別物になり、会議中に全員が現在地を見失う。

## 論点6: マウス操作（確定）

### 6-A: 親付け替えと兄弟並び替え

**決定**: 両者を別機能として実装しない。実体は**「挿入位置 =（親ID, インデックス）の書き換え」という単一の操作**。親が変われば付け替え、親が同じでインデックスだけ変われば並び替え。ドロップ処理は1本で済む。

`children` 配列の順序が兄弟順の正本（rev 5章「配列順が表示順の正」の適用）。移動は splice と挿入のみ。

**ドロップ領域**: ノード矩形を**縦に3分割**する（ノード間の隙間を使う方式は、隙間が数pxしかないと狙えないため避ける）。

- 上端25% → そのノードの**直前**に兄弟として挿入
- 中央50% → そのノードの**子**にする（末尾に追加）
- 下端25% → そのノードの**直後**に兄弟として挿入

**インジケータは意味ごとに見た目を変える**。兄弟挿入＝挿入位置に水平線、子にする＝対象ノードの枠をハイライト。同じ表現だと境界付近でどちらを選んでいるか分からなくなる。

**実装上の落とし穴**:

- **ドラッグ中に自動レイアウトを走らせない**。カーソル移動のたびに再配置すると狙う対象が逃げ続けて操作不能になる。ドラッグ中は元レイアウトを固定し、挿入インジケータだけを動かす。確定した瞬間に一度だけ再レイアウト
- **同一親内移動のインデックスずれ**。「削除 → 挿入」の順だと削除で後続が前にずれ、下方向への移動が1つ手前に着地する。挿入インデックスを先に確定させてから削除位置と比較して補正する
- **循環防止はドラッグ開始時に**。自分自身と全子孫を列挙してドロップ不可表示にする。ドロップ時に弾くのではなく、掴んだ瞬間に「置ける場所」が見えている状態にする
- **折りたたみノードへの子ドロップ**は、末尾に追加した上で自動展開する（追加したのに何も見えない状態を作らない）
- **Undo は1操作1コミット**。内部的に削除＋挿入の2ステップでも履歴には「移動」1件として積む

### 6-B: マウスによるノード追加

**決定**: ホバーで現れる「+」ハンドルを、ノード矩形の**各辺の中央に1つずつ**置く（横向きツリー：親が左、子が右）。

- **右辺の「+」** → 子を追加（末尾）
- **下辺の「+」** → 直後に兄弟を追加
- 上辺（＝直前に兄弟）は初期実装では設けない。稀な要求であり、足してから並び替えれば済む

**鉄則**: 「+」ボタンは Enter / Tab が呼ぶのと**まったく同じコマンド関数**を呼ぶ。追加という意味はキーボード側に既にあり、マウスは二つ目の入口にすぎない。別実装にすると、キーボードで足したノードとマウスで足したノードで挙動が変わる（プロトタイプ4本で観察された問題の再来）。UI層は「どのコマンドを、どの引数で呼ぶか」だけを決め、変更は共通のコマンド層が行う。

**常時表示にしない**。図がボタンだらけになり、仕様書としての可読性が落ちる。

**レイアウトへの非干渉**: ハンドルはノード矩形のサイズに影響してはならない。**測定対象外のオーバーレイ**として矩形の外側に絶対配置する。

**衝突整理**:

| 掴む場所 | 意味 |
| --- | --- |
| ノード本体（ドラッグ） | 移動（親付け替え／並び替え） |
| ノード本体（ダブルクリック） | テキスト編集 |
| 「+」ハンドル（クリックのみ） | 追加 |

- **「+」ハンドルはドラッグを受け付けない**。Miro は「+」からドラッグして位置を決められるが、自動レイアウトでは落とす位置に意味がない
- **ドラッグ中は全ノードのホバーハンドルを抑止する**。移動中にカーソル下のノードに「+」が出ると、ドロップ判定の3分割領域と重なって誤爆する

**追加直後の挙動（最重要）**:

- 追加したノードは**即座にテキスト編集状態に入りフォーカスを持つ**。キーボード側と完全に同じ。「+ をクリック → そのまま打つ」で完結しないと道具としての価値が半減する
- **再レイアウトのアニメーション中でも入力を受け付ける**。フォーカス移動は即座、視覚的な移動だけが補間
- **ビュー追従**: 新ノードが画面外なら追従してパンする。画面内なら動かさない（勝手に視点が動くと画面共有中に混乱する）

**空の状態**: ルートが無いとき、キーボードだけでは最初の1ノードを作れない。空キャンバス中央に「クリックして開始」を出す。**空白クリックでの浮遊ノード追加は行わない**（単一ルートの木であり、親を持たないノードが存在すると整合性検証が破綻する。Miro のマインドマップも同じ理由で許していない）。

### 6-C: 複製（後回し）

**決定**: 初期実装に含めない。

**根拠**: rev の「実際の使用が実際のギャップを明らかにする」の適用。なくても代替経路がある（新規ノードを作って打ち直す）ため、第一関門「会議のスピードに入力が追いつくか」の検証はこれ抜きで成立する。実際に使って「毎回同じ枝を作り直している」と分かってから入れれば、そのときには**どの単位で複製したいのか（葉だけか、サブツリーごとか）も実データで判明している**。

**後追いコストが低い根拠**: 削除と親付け替えを実装した時点でサブツリーの走査は既にある。複製で新規に要るのはID再採番マップだけで、スキーマ変更も伴わない。

**申し送り**: **Ctrl+C / Ctrl+V を他の意味に割り当てないこと**。押しても何も起きない状態にしておけば後から本来の意味で入れられる。別機能を入れると後で剥がす作業が発生する。

**実装時の既知の落とし穴**（着手時に参照）:

- サブツリーを複製する際、**子孫のIDまで新規採番**しないと同一IDが2箇所に存在し整合性検証で死ぬ
- ただし**用語集への参照は再採番してはいけない**。「自ツリー内の内部参照は付け替える／外部マスタへの参照はそのまま残す」の区別が要る。一括で再採番すると用語集参照を壊す
- 着地点は「同じ親の直後の兄弟」（「似た分岐をもう一本作る」が主用途のため）

## 論点7: 明示改行とその出力（確定）

**決定**: ユーザーが入力した改行（`\n`）はデータに永続化する。出力時は **Markdown / Mermaid とも `<br>` に変換**する。

**永続化する根拠**: 「承認 → 却下 → 差し戻し」のような列挙を意図的に3行で見せたい場面は実在し、これは表示指定というより**文言の構造**に近い。座標のような連続値でもないため diff も読める。

**出力時の変換**:

- **Markdown（NotePM）**: 表のセル内では素の改行が使えず、リスト形式でも連結されるため `<br>` が確実。※ rev 8章の既存決定「表のセルは書き手を信用せずエスケープする（`\` → `|` の順、改行は `<br>`）」と整合する
- **Mermaid**: ノードラベル内の改行は `<br>`。素の改行は構文エラー。あわせて `"` `(` `)` `[` `]` `{` `}` 等のエスケープが必要（仕様の文言には括弧が普通に入る）。**ラベル正規化関数を1本用意し、全ツールの Mermaid 出力が必ずそれを通る構造にする**

**重要**: **幅320pxによる自動折り返しは出力に持ち込まない**。あれはアプリ内の表示都合であり出力先の幅とは無関係。出力に含めるのは**ユーザーが明示的に入れた改行だけ**。測定層が計算した折り返しと、データが持つ `\n` を、コード上でも別のものとして扱う。混同すると NotePM 上で意味不明な位置で改行された仕様書が出来上がる。

## 論点8: 保留・申し送り事項

### 最大幅の可変化（保留）

**（logic-tree M1 の実機確認の結果）** M1 の実機確認を一巡した時点で**窮屈だという指摘は出ず、320px 固定を継続する**。ただし記録は「問題なし」の粒度で、**何文字で折り返したかの実測値は取っていない**（[`../history/logic-tree-m1-keyboard-editor.md`](../history/logic-tree-m1-keyboard-editor.md) の「実機確認」参照）。会議1回ぶんを打ち切った体感であり、下の可変化を検討する日が来たらそのときに測り直すこと。

320px で使ってみて窮屈と判明した場合の選択肢。実装コストはほぼゼロ（レイアウト層が純粋関数なので最大幅は引数の一つ）。ただし導入するなら以下3条件を満たすこと。

1. **値をファイル（JSON）に入れない**。仕様の内容ではなく閲覧環境の設定なので、アプリ設定側に持たせる。ここを外すと座標も幅も入れずに守ってきたラインが崩れる
2. **連続値ではなく離散値**（40px刻み、または3〜4段階のプリセット）。連続だと折り返し位置が常時パタパタ変わって図が落ち着かない
3. **恒久機能と決めない**。「結局いつも標準しか使っていない」なら固定して撤去する

**一般化された注意**: 「決められないからつまみを付ける」は繰り返すとツールを壊す。facet の価値は「構造を強制して抜け漏れを見せる」ことであり、設定項目が増えるほどユーザーは仕様でなく見た目をいじる時間が増え、共有時に全員が違う画面を見る。**設計の決定を実行時オプションに変換して先送りしている**という自覚を持つこと。今回は「計器としての一時設置」という目的・データ非混入・撤去可能性が揃えば許容範囲。

### ノード幅の手動調整（不採用、ただし将来の論点として記録）

Miro のマインドマップは幅の手動調整を許すが、これは唯一「表示のデータ」であり永続化が必要になる（座標を持たない方針の部分的な破れ）。導入するなら連続値の `width: 240` ではなく**離散値（`width: "wide"` 等）**にして diff を読める形に保つこと。初期実装では完全自動とし、ドッグフーディング後に判断する。

### その他

- 上辺の「+」（直前に兄弟を追加）の要否
- エッジのクリック可能化（現時点では不要。必要になれば SVGレイヤの `pointer-events` 設定で対応）
- 状態遷移図（任意グラフ）のレイアウト。ツリーとは別問題であり、elkjs の再検討余地がある

## rev 反映候補

- **10章「キャンバス化の決定」**: 「ノード配置を自動レイアウトにするか自由配置にするかはツールごとに要決定」の申し送りについて、**ロジックツリーは自動レイアウトで確定**した旨を追記。あわせて判断の一般則として「**マウスドラッグは座標の編集とは限らない。構造の編集を入力するジェスチャとして使える**」を明記する（自由配置を選ぶ理由として「マウスで動かしたいから」は不十分、という判定基準になる）
- **10章「実装規約」**: キャンバス実装の技術方針を追記。「キャンバスライブラリ（React Flow / tldraw 等）は採用しない。イベント系を乗っ取るライブラリは操作言語の一元化規約と衝突するため」。あわせて「**ノードはDOM、エッジはSVG、ビューポートはd3-zoom**」を全キャンバス系ツール共通の構成として定める（シーケンスエディタも同構成を想定）
- **6章 モジュール規約**: キャンバス系ツールの提供物として「**レイアウト関数（純粋関数。データ＋サイズ → 座標Map）**」を検討。ただしツリーとシーケンスでレイアウトの性質が大きく異なるため、規約化するか各モジュール任せにするかは2つ目の実例（シーケンス）が出てから判断する
- **9章 デザインシステム**: 測定層と描画層が**同一のフォントトークンを参照する**必要がある旨を注記（ズレると全ノードのサイズが狂う）
- **8章 出力**: 「明示改行は `<br>` に変換する。ただし表示上の自動折り返しは出力に持ち込まない」を追記。Mermaid ラベルの正規化関数を共通ユーティリティとして持つ旨も
