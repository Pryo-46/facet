# エラーカタログエディタ 設計セッション 成果物ドキュメント

作成日: 2026-08-05 ／ 前提: overview-rev4.md ／ 状態: **骨格確定。JSON Schema 実体は未作成**

---

## 1. 背景と動機

サポートチームに対して「どんなエラーがあり、ユーザーはどんな対応が必要か」を説明する機会がある。サポートチームはこの情報をもとに**サポートサイトを手書きで作成する**（データのインポート連携はしない）。

この要求は既存4ツールのどれにも収まらない：

- **用語集には入れられない**。`term` は6フィールドのフラット構造で関係を持てず、「エラー ⇄ 発生タイミング ⇄ 対応方法」という複数軸の情報を `notes` に文章で詰めることになる。これは本ツール群が解こうとしている「多次元情報の一次元への直列化」の再生産にあたる。また handoff-04 で「エラー種別は工程ごとに固有だから用語集の対象外」と決定済みであり、その判断とも衝突する。
- **読み手が違う**。既存4ツールは開発者・PdM向けの仕様表現であり、出力先はNotePMの仕様書。エラーカタログの第一の読み手はサポート担当で、出力先は運用ドキュメントの下書き。

よって**5つ目の独立モジュール**とする。

## 2. 決定事項

### 2-1. エンティティとしての位置づけ

- **IDプレフィクス**: `error_`（+ 英数字62文字・10文字。全ツール共通のID規約に従う）
- **プロジェクトにつき1ファイル**（`type: errorCatalog`）。機能ごとの分割はしない
- 他ツールからは `error_` のID参照で結べる構造を持つが、**参照側の実装は当面行わない**（下記スコープ参照）
- 単一ファイルであることの帰結：単一性違反はコア横断検証。これを用語集の特例にせず**モジュール規約の単一性フラグ**として一般化した（overview-rev4 6章）

### 2-2. フィールド構成（1行1エラー）

| フィールド         | 必須          | 意図                                                       |
| ------------------ | ------------- | ---------------------------------------------------------- |
| `id`               | ○             | `error_` + 10文字                                          |
| `title`            | ○             | 引くためのキー。表記ゆれ検知の照合対象                     |
| `occurrence`       | ○（空文字可） | 発生タイミング（当面は手入力。下記「申し送り」参照）       |
| `resolutionLevel`  | ○             | 誰が解決するかの enum（2-3）                               |
| `causeForSupport`  | ○（空文字可） | 業務レベルの原因。サポート向け出力に載る                   |
| `causeForSpec`     | ○（空文字可） | 仕様レベルの原因。開発向け出力のみ                         |
| `userAction`       | ○（空文字可） | ユーザーが取るべき対応                                     |
| `supportAction`    | ○（空文字可） | サポート担当が取るべき対応（確認事項・エスカレーション先） |
| `engineerAction`   | ○（空文字可） | エンジニアの介入内容（データメンテ等）                     |
| `notes`            | ○（空文字可） | 備考。**表記ゆれ検知の対象外**                             |

- **「必須だが空を許す」パターン**は用語集から継承。全キー常在・値で空を表現し、決定的シリアライズと整合させ、warning 判定を単純な値チェックにする
- **同定単位は `title`**。システムとしてエラーコードを持たないプロジェクトがあるため、コード前提にしない
- **表示用のNo（連番）は持たない**。理由は 2-5
- **原因を2フィールドに分けた理由**：サポート向けと開発向けで必要な粒度が違う。業務レベルに寄せると仕様書としての精度が落ち、仕様レベルに寄せるとサポートが使えない。**分けた意味は出力の出し分けで回収する**（2-6）

### 2-3. `resolutionLevel`（enum・5値）

| 値          | 意味                                             |
| ----------- | ------------------------------------------------ |
| `user`      | ユーザー自身で解決できる                         |
| `support`   | サポート対応が必要                               |
| `engineer`  | エンジニアの介入（データメンテ等）が必要         |
| `none`      | 誰にも解決できない（外部サービス障害・仕様上の制約） |
| `undecided` | まだ決めていない（warning）                      |

- **enum として型で持つ理由**：サポート担当が問い合わせを受けて最初に判断するのは「自分で返せるか、エスカレーションか」。対応文から推測させず、それ自体を引ける形にする。用語集の `kind` と同じ位置づけであり、**出力のグルーピング／フィルタ軸そのもの**
- **`none` と `undecided` の区別**：用語集の `other` / `undecided` と同一構造。「検討した上でどれでもない」と「まだ考えていない」を型で分ける。これがないと、対応文の空文字が「未記入」と「そのレベルは関与しない」の両方を意味してしまい、**「未定義」と「決めた上で無効」の型区別**という中核思想が崩れる
- **原因の分類を混ぜない**：「ユーザーがデータを消したことによるエラー」のようなものは**発生原因の分類**であって、誰が対応するかの分類ではない。これは `causeForSupport` に書く。1つのenumに2軸を同居させると分類方針がぶれる（用語集で `tags` を切ったのと同じ理由）
- **「復旧不可」は `none` ではない**：元に戻せないだけで、「作り直してください」「この状態で進めて問題ありません」という案内は存在する。これを `none` にするとサポートサイトで最も需要の高い問い合わせに答えられなくなる

### 2-4. 整合性検証（レベル2・赤表示）

- **ID重複**（共通規定）
- **`resolutionLevel` と対応文の矛盾**：宣言したレベルに対応する Action フィールドが空（例：`user` なのに `userAction` が空）
- **`none` かつ全対応文が空**：warning。解決できなくても案内文は必要
- **`resolutionLevel: undecided`**：warning（用語集の `kind: undecided` と同じ）
- **各対応文・原因の空文字**：warning（用語集の `definition` 空と同じ）
- **`title` の重複**：レベル2。ただし**「name-to-name の重複検出」は用語集側にも欠けているギャップとして特定済み**であり、両方で必要になる。コア側の共通ユーティリティとして実装するのが妥当

### 2-5. 並び順

- **配列順が正**。工程順・時系列に並べたい場合は Alt+↑↓ で手で並べる。これがそのまま正規の並びになる
- **ソート／フィルタは派生ビュー**（`resolutionLevel` 順、`title` 五十音順など）。データは動かさない。**派生表示中はリオーダー操作を無効化**（用語集で確定済みの挙動をそのまま流用）
- **`sortOrder` 等の順序フィールドは持たない**。配列順と併存すると「どちらが正か」が決まらず、挿入のたびに全行を振り直すことになりGit diffが全行変わる
- **表示Noは出力時に配列順から導出**する（Markdown 1列目に 1,2,3…）。永続フィールドにしない
  - **判断の根拠**：サポートサイトはこのデータをインポートせず手書きで作るため、こちらのNoが外部の恒久的な参照キーになる経路がない。恒久性の要求がないなら番号は会議中に口頭で指すための目印にすぎず、導出で足りる。フィールドが1つ減り、リナンバー処理も欠番管理も不要になる
  - **注意**：将来サポートサイトがNoで参照する運用になった場合、この判断は覆る（安定Noを永続フィールドとして持ち、欠番を許す形に変更が必要）

### 2-6. 出力（2プロファイル）

| プロファイル   | 列                                                                     |
| -------------- | ---------------------------------------------------------------------- |
| **サポート向け** | No／エラー名（`title`）／発生タイミング／原因（`causeForSupport`）／ユーザーの対応／サポートの対応／エンジニアの対応 |
| **開発向け**     | 上記＋ `causeForSpec`。全列                                            |

- **`engineerAction` はサポート向けにも含める**。サポートが「エンジニアに何を依頼すべきか」を書けるようにするため
- **グルーピングは `resolutionLevel` 別**（用語集の kind 別グルーピングと同じ）。順は enum 定義順で固定し、空のグループは見出しごと省略、グループ内はデータ配列順
- **見出し階層は用語集と同じ**：h1不使用、エンベロープ `title` を h2、グループを h3（NotePMの目次収載範囲）
- **未定義は出力にも明示**：空フィールドは `（未定義）`、`undecided` は「未分類」グループとして出す。**サポート向け出力でも省略しない**。省略すると「決めていないこと」が消えてしまい、思想に反する
- 形態はクリップボードコピー＋ .md 書き出しの両方（overview 8章）
- Mermaid はなし

### 2-7. 表記ゆれ検知

- エラーカタログが提供するのは**検知対象フィールドパスの宣言のみ**（`title` / `occurrence` / 各 cause / 各 action。`notes` は対象外）
- 検知の実行はコア。用語集の name / aliases を照合データとして使う既存の仕組みがそのまま及ぶ
- これは「用語集から機能を輸入する」話ではなく、**用語集は参照される側、検知の実行主体はコア**という責務整理（overview-rev4 6章に反映）

## 3. 今回スコープに含めなかったこと

- **他ツールからの `error_` 参照**：シーケンス／ロジックツリー／状態遷移がエラーを参照する構造は取れるが、当該3ツールが未設計のため実装しない
- **発生タイミングの導出**：本来は「参照している側から逆引きして導出」するのが正しい（正となるデータは一つ、図は導出）。参照が実装されるまでは `occurrence` に手入力する
  - **申し送り**：参照実装時に「手入力 → 導出」への移行が発生する。schemaVersion 改訂＋マイグレータで対応する想定
  - **失われている価値**：現状のエラーカタログ単体では**網羅性を担保できない**。「表に載っていないエラー」は検出できず、「どこからも参照されていないエラー＝発生経路のない幽霊」も検出できない。網羅性はロジックツリーの葉やシーケンスの失敗ゾーンが持つべきものであり、参照が実装されて初めて回収される
- **機能／領域による分類**：単一ファイルに全機能のエラーが並ぶため、規模が増えると分類軸が必要になる可能性がある。用語集の `term_` 参照にするか自由文字列にするかの判断を含め、実需が出てから決める（`kind` enum に「機能／領域」相当の値がないため、参照にする場合は用語集の schemaVersion 改訂を伴う）
