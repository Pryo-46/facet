# M24 設計スペック: ツリーのノード幅固定（UI ノート D の一部——D3）

> **記録。** 書いた時点の判断をそのまま残す（M21・M23 のスペックと同じ扱い）。実装で確定した差分は申し送り `docs/history/m24-core-node-width-lock.md` と rev 9章に出る。

## 位置づけ

UI ノート（`docs/facet-UI設計ノート.md`）の実施優先順位 §8 の **優先6**（D3）。A（色の規約）は M21・PR #7、C（未定義表現の本体）は M22・PR #8、B（タイポグラフィ）は M23・PR #11 でマージ済み。優先 1〜5・9 は消化済みで、着手条件は無い（U4 は優先7、U1 は優先8 の条件）。

**設計は 2026-08-25 に人間と対話で確定した。** 対話で下された裁定は4つで、いずれも本書の決定の根拠になっている:

1. **テーブルの行高は変えない**（D3 の前半を実施せずに決着させる）
2. ノード幅は**両ツリーとも全ノード一律 320**
3. 高さは**行数上限を設け、溢れはセル内スクロール**
4. 打ち切りの合図は**出さない**（`overflow-hidden` で切るだけ）

### D3 が主張していること

D3「レイアウトが内容に支配される構造をやめる」は2本柱を持つ。

- **テーブルは行高固定＋2行で省略**（用語集の備考列が行高を決めている）
- **ツリーはノード幅固定＋省略記号**、詳細は別パネルで表示

rev.3 の再定義がこのうち後者の優先度を引き上げた——**ノード幅がテキスト量で決まるため右寄せのステータスバッジがバラバラの位置に散り、「どれが未決か」を知るには全ノードを個別に読む必要がある。** 幅を固定すればバッジが縦一列に揃い、列を上から下へなぞるだけでスキャンできる。**これは可読性ではなくスキャン性の問題**であり、会議中に俯瞰するツールとしては後者の方が効く。

M21 でバッジの高さ（`BADGE_BOX_HEIGHT`。M23 で 20）は揃ったが、箱の幅は内容に支配されたままである。

## 決定1: 範囲は課題ツリーとロジックツリーの2本

**テーブル（用語集・エラーカタログ）の行高には触らない。**

D3 の前半は `CellInput` の `MAX_ROWS = 8` に付いた明示的な過去判断——**「行の高さが揃わなくなるが、読めないよりよい」**（M10 決定17。エラーカタログが8列を1440pxの窓に並べると1列170px前後になり、日本語で1行11文字・5行で55文字が上限になるため8行へ上げた）——を反転させることになる。加えて「省略した全文をどこで読むか」の答えを新設する必要がある（テーブルには展開パネルに相当する場所が無い）。

**人間の裁定は「行の高さは変えない」。** これは先送りではなく判断であり、`open-issues.md` にはその判断として記録する（決定7）。

**シーケンスも対象外。** ステップラベルは矢印の上に載る文字で「箱が縦に並んでバッジが散る」構造を持たず、答えセルとガターは既に `ANSWER_WRAP`（`maxWidth === minWidth`）で「ガター幅は導出しない」と決着済み（design-notes 論点7）。`LABEL_MAX_WIDTH`（320）・`ACTOR_MAX_WIDTH`（240）は**上限のまま据え置く**。

**この決定の帰結として、着手前の指示にあった論点が1つ消える。** 「行高固定が `CellInput` の自動 rows 算出（`getComputedStyle` 依存）と衝突しないこと」——ツリーのノードは `autoSize={false}` で測定層が高さを持っており、`measure()` の経路をそもそも通らない。テーブルを触らない以上、衝突する面が存在しない。

## 決定2: 幅は「導出しない」を全箱へ広げる

`measure.ts` の `BOX_WIDTH` の JSDoc は既に D3 と同じ論理を書いている——

> 箱の中には課題の文言と仮説の行という**性質の違う文章が縦に積まれる**ので、一番長い行に幅を合わせると、短い課題と長い課題で箱幅がばらつき、木が階段状に見える。（…）値はロジックツリーのノードと同じ 320

M24 は**この既存判断を例外なく全ノードへ広げる**作業である。新しい原則を持ち込むのではない。

| | 現在 | M24 |
| --- | --- | --- |
| 課題の箱 | 仮説あり／見送り済み＝`BOX_WIDTH` 320 固定、それ以外＝タイトルの自然幅（`ISSUE_TITLE_MIN_WIDTH` + 枠 〜 `ISSUE_MAX_WIDTH`） | **常に `BOX_WIDTH` 320** |
| ロジックのノード | `NODE_MIN_WIDTH` 96 〜 `NODE_MAX_WIDTH` 320 の可変 | **常に 320** |

表現は `wrapWithin` の **`minWidth === maxWidth`**。これは新しい書き方ではなく、シーケンスの答えセル（`ANSWER_WRAP`）が既に使っている同じ手である。

### 消える定数と、消える分岐

- **`ISSUE_TITLE_MIN_WIDTH`（128）** — 「箱の下限ではなく文章の下限」という概念ごと消える
- **`ISSUE_MAX_WIDTH`（320）** — 上限として使う場所が無くなる。課題ツリーの幅は `BOX_WIDTH` 1本になる
- **`NODE_MIN_WIDTH`（96）** — 空のノードが点にならないための下限。固定幅では出番が無い
- **`layout.ts` の if/else 分岐**（`rows.length > 0 || deferred` の有無で幅の決め方を変える箇所）と、その 25 行の JSDoc

**この JSDoc が説明していた実機の欠陥は、構造ごと消える。** 「箱の下限から枠のぶんを引くと、空けた枠が文章を食って入力欄が数 px になり、新しく作った課題に1字も打てない」——固定幅では枠は常に固定幅の中から取られるので、枠が文章を食って下限を割る経路が成立しない。同じ理由で **`wrapWithin` の `minWidth <= maxWidth` 依存**（食い違うと `maxWidth` を採るので、逆転するとタイトルが黙って下限を割る）も課題ツリーからは消える。**`wrap.ts` 側の注意書きは残す**——シーケンスがまだこの依存の上にいる。

### 消しても不変条件は残す

タイトルが十分な幅を保つこと自体はテストとして残す。固定幅のもとでは `titleWidth = BOX_CONTENT_WIDTH − reserve` で、`reserve` は右上に空ける枠（`BADGE_GAP` ＋ 枠幅）である。枠幅は箱の状態で変わる:

| 箱の状態 | 枠に出るもの | 枠幅 | `titleWidth` |
| --- | --- | --- | --- |
| 「仮説なし」が立つ | バッジ（4字） | 70 | **220px（最小）** |
| 見送り済み | 見送りバッジ（3字） | 56 | 234px |
| どちらでもない | 見送りトグル（3字。`badgeW` は 0 だが `DEFER_TRIGGER_LABEL` の幅で下支えされる） | 56 | 234px |

一番広い枠は「仮説なし」バッジ（`text-sm` 14px で4字 ≒ 56 ＋ `BADGE_PADDING_X` 6×2 ＋ `BADGE_BORDER` 1×2 ＝ 70）で、そのとき `titleWidth` は 220px。**`BOX_WIDTH` を縮めるか、バッジの語を伸ばした将来の変更が赤くなる門番**として、`layout.test.ts` にこの下限のアサーションを残す。**枠幅はバッジ文言の実測で決まる**（フォントを変えれば動く）ので、値をリテラルで固定せず不等式で書くこと。

### 改名

**`NODE_MAX_WIDTH` → `NODE_WIDTH`。** 上限ではなく固定値になるので、名前が嘘になる。

**3つの 320（`BOX_WIDTH` / `NODE_WIDTH` / `LABEL_MAX_WIDTH`）を共有定数に束ねることはしない。** M24 の後、2つは固定値・1つは上限であり、**意味の違うものが同じ名前になる方が危険**である。相互参照のコメント（「ロジックツリーのノードと同じ 320」）は、固定値になった事実を含めて書き直す。

## 決定3: 高さは3行で打ち切る

`wrapWithin` に**任意の `maxLines`** を足し、行と高さをそこで止める。**既定は無制限**なので、シーケンスと展開パネルは無変更で通る。

適用先は**閉じた箱に出るもの**だけ:

| 対象 | フォント | 内容幅 | 1行あたり | 上限 |
| --- | --- | --- | --- | --- |
| 課題のタイトル | `text-base leading-normal font-semibold`（16px / 24px） | 220〜234px（枠の幅で変わる。決定2の表） | ≒13.75〜14.6字 | **3行** |
| 見送りの理由 | `text-sm`（14px） | 286px（`BOX_CONTENT_WIDTH` − `ROW_INDENT`） | ≒20.4字 | **3行** |
| ロジックのノード | `text-base leading-normal`（16px / 24px） | 298px | ≒18.6字 | **3行** |

**展開パネルの中（由来・根拠・FB・以前の判断）には上限をかけない**——そこが「詳細を読む場所」そのものであり、D3 の「詳細は別パネルで表示」が指しているのがこの場所である。畳まれた仮説行は既に1行＋`truncate` で確定済み（`layout.ts:226`）。

### 3行の根拠

`sample-project` の実データ:

| | 件数 | 最短 | 中央 | 最長 |
| --- | --- | --- | --- | --- |
| 課題タイトル | 11 | 9字 | 18字 | 22字（`適性検査APIの応答特性が要件を満たすか不明`） |
| ロジックノード | 15 | 0字 | 15字 | 26字（`過去の応募と同一人物と判定し、タレントプールへ回した`） |

**2行だとサンプルの最長がちょうど境界に立つ**（22字 ÷ 13.75 = 1.6行、26字 ÷ 18.6 = 1.4行）ため、少し伸ばしただけで省略が頻発する。3行なら課題タイトル ≦41字・ロジックノード ≦55字まで入り、実運用の余裕がある。**箱の高さの差は最大2行分（48px）に有界化される。**

### 溢れの扱い——`overflow-hidden` のまま、合図は出さない

**`overflow-y: auto` は採らない。** Chromium/Windows の古典的スクロールバーは**レイアウト幅を食う**ため、測定層が前提にしている内容幅（298px）が実効 283px になり、**測定より多く折り返してさらに切れる**。これはこのコードベースが繰り返し警告している形そのものである（`measure.ts` 冒頭「測定が実際より小さいと、ブラウザに与えられる幅が前提より狭くなり、測定より多い行数に折り返して文字が切れる」）。加えてキャンバスのホイールは d3-zoom がパン／ズームに使っているので、**ホイールで読む道は元から無い**。

したがって `IssueBox` / `NodeBox` の `overflow-hidden` は現状のまま。編集中はキャレット移動でブラウザが `textarea` を内部スクロールし、全文に届く。

**`CellInput` の `onBlur` で `scrollTop` を 0 に戻す。** 戻さないと、長文を編集して抜けた箱が途中の行から表示されたまま残る。1箇所で済み、`autoSize` の欄（テーブルのセル）は内容が常に収まるので影響しない。

### 省略記号を出さない理由（技術上の制約）

**`text-overflow: ellipsis` も `-webkit-line-clamp` も `textarea` には効かない**（フォームコントロールであるため）。既存の唯一の省略の先例（`HypothesisRow` の畳まれた行）が「…」を出せているのは、**畳まれている間は `<span>` で描き、展開したときだけ `CellInput` に差し替えている**からである。課題タイトルとロジックノードは常時 `textarea`（フォーカスされている＝編集中、という模型）なので、同じ手を採るには両エディタに「いま編集中か」の状態と `span → textarea` のフォーカス引き継ぎ（キーボード導線・IME）を持ち込むことになる。

**人間の裁定は「合図なし」。** 代償は、閉じた状態で「3行で終わっている」と「先がある」が見分けられないこと。

### 未検証の前提（実機確認で潰す）

**`overflow: hidden` の `textarea` で、キャレット移動時にブラウザが内部スクロールすること。** Chromium の挙動としてはそうだが実測していない。**追従しないなら4行目以降が編集で到達不能になる**ので、実機確認の項目に入れる（決定8）。そのときはフェード案（`mask-image` を `:not(:focus)` に当てる）かスクロール許可へ倒す判断が要る。

## 決定4: 巻き添えになる番人を1つ、作り直す

**`LogicTreeEditor.font.dom.test.tsx` の観測点が死ぬ。**

このテストは「Web フォントの読み込み完了（`document.fonts.ready`）でノードが測り直されるか」を、**ノード矩形の `style.width`（142px → 262px）**で見ている。測定器を「呼ばれるたびに太く測る」偽物に差し替え、幅が動くことで測り直しを証明する形である。**幅が定数 320 になると、測定器を差し替えても幅は動かない。**

テストは赤くなるので見落としはしない。**危ないのは「320 に書き換えて緑にする」直し方**——それは rev 9章の「測定層と描画層が同一のフォントトークンを参照しなければならない」を何も検証しない空のテストになる。M23 決定1（`wrap` 回帰テストの入力長が 16px 化で退化した。「不等式なので自動追従」は隠れリテラルを見落としていた）と同じ罠である。

**観測点を `style.height` へ移す。** 高さは行数を通じてフォントに依存し続けるので、太さが倍になれば折り返しが増えて高さが動く。

**ただし文言長を選び直す必要がある。** 現在の `TEXT` は12文字で、`perChar` が 10 でも 20 でも内容幅 298px に1行で収まる（240 < 298）ため、高さは動かない。**倍化がちょうど行の境界をまたぐ長さ**を選ぶこと——`perChar` 10 で1行、20 で2行になるには文字数 L が `L×10 ≦ 298 < L×20`、すなわち **15 ≦ L ≦ 29**。**選んだ根拠をコメントに書く**（現在の「12文字。幅は 12×10+22=142px → 12×20+22=262px」に相当する導出を、高さの側で書き直す）。

高さの期待値そのもの（`lineHeight` の実測値に依存する）は**着手前スキャンで確定する**（決定6）。

## 決定5: 主張そのものを門番にする

rev.3 の主張「**バッジが縦一列に揃う**」を `layout.test.ts` で直接見る。

- 全ての箱の `rect.width` が `BOX_WIDTH` であること（仮説の有無・見送りの有無によらず）
- 同じ深さに複数の箱があるとき、**見送りバッジの右端が一致すること**（`x + width` ＝ 箱の右端 − `ISSUE_INSET_X`）

**この2本で3種類の枠すべてを覆える。** 右上の枠に出るものは3つ（見送りバッジ・「仮説なし」バッジ・見送りトグル）だが、**レイアウトが矩形を組むのは見送りバッジだけ**で、残る2つは `IssueBox` が CSS の `right: ISSUE_PADDING_X` で右寄せしている。どちらも右端は「箱の右端 − `ISSUE_INSET_X`」に落ちるので、**箱幅が揃っていれば3種類とも同じ x に並ぶ。** 幅の一様性を押さえることが、そのままバッジの縦一列を押さえることになる。

**削除するテスト**: `layout.test.ts` の「仮説を持たない課題の箱はタイトルの自然幅（ロジックツリーと同じ）」——**主張が反転したので消す**。「空のタイトルでもバッジのぶん箱が広がり、入力欄は下限を割らない」も、箱が広がる構造が消えるため書き直す（残すのは「タイトルが下限を割らない」の側だけ）。

`logic-tree/measure.test.ts` の `NODE_MIN_WIDTH` を見る2本（「空文字は1行・最小幅になる」「幅は文言から算出し、最小幅を下回らない」）は、**固定幅の検証に書き換える**。同ファイルの「最大幅を超えたら折り返し、幅は最大で止まる」は `NODE_MAX_WIDTH` の改名に追従させる。

`core/canvas/wrap.test.ts` の既存2群は**そのまま残す**（`minWidth < maxWidth` の一般契約はシーケンスが使い続ける）。**新しく足すのは2群**——`minWidth === maxWidth` のとき幅が常に固定値になること、`maxLines` が行と高さを打ち切ること（明示改行を含む場合も）。

## 検証

実装後、人間が実機（27型 WQHD・ライト・100%）で一巡する。**このマイルストーンは見た目そのものが成果物**なので、チェックリストは `history/m24-core-node-width-lock.md` に空のまま写し、消し込みは `open-issues.md` の「次に手を付ける候補」が管理する。

1. 課題ツリーで、**同じ列の箱のバッジが縦一列に揃っている**（D3 rev.3 の主張そのもの）
2. 短いタイトルの箱と長いタイトルの箱が同じ幅で、木が階段状に見えない
3. 空の課題を新規作成したとき、タイトルの入力欄に十分な幅がある（1字も打てない箱ができていない）
