# 配色差し替え Skill 設計スペック

> **これは設計スペックであり実装計画ではない。** 実装計画は別途 `writing-plans` で起こす。

**Goal:** 外部テーマ（shadcn 系の `theme.css`、Morphos の `theme.json`、色のリスト）を渡すと、`src/styles/palette.css` の11トークン×2モードを埋め、コントラスト要件を満たすまで明度を調整し、`palette.test.ts` が緑になる状態まで持っていく Skill を作る。

**Architecture:** `.claude/skills/palette-retheme/` に自己完結した1ディレクトリとして置く。**3本目の Skill だが、既存2本とは種類が違う**——`glossary-term-register` / `error-catalog-register` は**アプリのユーザーデータ**（プロジェクトフォルダの JSON）を触るが、これは**アプリ自身のソース**（`src/styles/palette.css`）を触る。この違いは SKILL.md の冒頭に書く。

**Tech Stack:** Node.js（ESM）／Markdown（`SKILL.md`）。アプリ側の変更は `src/styles/contrast.ts` への**関数2つの追加のみ**（同ファイルはテスト専用で、アプリからは1箇所も import されていない）。

**設計の出どころ:**

- 手本: `.claude/skills/error-catalog-register/`（自己位置解決の形はこちらが正）

## この Skill が解く問題

配色の差し替えは「`palette.css` の値を書き換えるだけ」に見えて、実際には次の4つが同時に要る。

1. **色形式の正規化** — テーマは hex / hsl / `oklch(92.1% …)` で配られるが、`palette.css` は `oklch(L C H)`（L は 0..1 の小数、アルファ不可）しか受け付けない。`palette.test.ts` が弾く
2. **役割への対応づけ** — 外部テーマの語彙は facet の11役割と1対1ではない。**対応物が存在しない役割が5つある**
3. **明度の調整** — 元の色をそのまま入れるとコントラスト要件を割る。M7 でも Morphos の値を全トークンで持ち上げた
4. **意味論の維持** — `destructive` が赤とは限らず、`ok` を装飾に流用してはならず、`grid` は薄いことに意味がある

このうち 1 と 3 は計算であり、人間にも AI にも暗算できない。2 と 4 は判断であり、機械には決められない。**Skill はこの境界に沿って作る**——計算はスクリプトへ、判断はヒアリングへ。

## 決定A: Skill 名は `palette-retheme`

既存2本は `<対象>-<動作>`（`glossary-term-register` / `error-catalog-register`）。これに倣って `palette-retheme` とし、ディレクトリ名・`SKILL.md` の `name` の2箇所を揃える。

トリガー（`description` に書く）: 「配色を変えて」「テーマを差し替えて」「この theme.css を入れて」「`palette.css` を書き換えて」「もっと暗い配色にして」。**「色」という語だけでは起動させない**——用語集の値やチャートの色の話と混ざる。対象がアプリの外観であることを条件に含める。

## 決定B: 外部テーマから拾うのは6色だけで、残りは明示的に捨てる

**これがこの Skill の設計の中心である。**

`src/index.css` は shadcn の31トークンを**すべて役割トークンから導出**しており、色値を1つも持たない。したがって外部テーマの31変数のうち、facet が使うのは次の6つに対応するものだけである。

| 外部テーマ | facet の役割 | 備考 |
| --- | --- | --- |
| `background` | `canvas` | 地（方眼紙を敷く面） |
| `card` / `popover` | `surface` | 両者が違う値なら `card` を採る |
| `foreground` | `ink` | |
| `muted-foreground` | `ink-muted` | |
| `border` / `input` | `rule` | 両者が違う値なら `border` を採る |
| `destructive` | `warning` | **色相を確認する。決定D参照** |

残る25変数は捨てる。**捨てるのは手抜きではなく設計である**——`--primary: var(--ink)` は「ボタンが緑になると `ok`（確定）と意味が衝突する」から、`--ring: var(--ink)` は「フォーカスと確定は別の意味」だからそう決めた（rev 9章）。テーマの `primary` を持ち込むことは、この決定を壊すことを意味する。

**帰結をユーザーに伝えること。** テーマの印象は多くの場合 `primary` が担っているが、facet ではその色がどこにも出ない。「Amber Minimal を入れても琥珀色は現れない」。これを報告に書かないと、差し替え後に「テーマが反映されていない」という誤診が生まれる。

**この対応表を1対1で信じない。** テーマによっては `card` が `background` と同値だったり、`muted-foreground` が本文と区別できない明度だったりする。値を拾ったら、下の検算で全要件を測る。

## 決定C: 対応物がない5つは候補を出して選ばせる

`ok` / `grid` / `surface-accent` / `warning-fg` / `ok-fg` には、shadcn 系テーマに対応物が無い。**AI が黙って決めない。**

ただし5つを一律に聞くと会議が止まる。**判断の重さで分ける。**

| 役割 | 扱い | 導出の規則（候補の作り方） |
| --- | --- | --- |
| `ok` | **必ず聞く** | 候補を3つ出す: (1) テーマに success / positive 系があればそれ、(2) `chart-*` のうち `warning` と色相が離れているもの、(3) `warning` の補色側から起こした新規色。テーマの `primary` が緑系なら候補に加える |
| `surface-accent` | 候補と既定値を示して1往復で確認 | `ok` の色相から起こした淡い面。`ink` と `ink-muted` の両方が 4.5:1 で載ること |
| `grid` | 既定値を示して確認 | `rule` の色相を保ったまま `canvas` に寄せた薄い線。**ライトは `canvas` 上 1.17:1 を目安にする**（M8 の実機確認で 1.36:1 から薄めた値。会議で投影したときにうるさくない濃さが基準） |
| `warning-fg` / `ok-fg` | 既定値を示して確認 | それぞれの面に 4.5:1 で載る文字。面が明るければ暗い方（`canvas` 相当）、暗ければ明るい方（`surface` 相当）を当てる |

`ok` だけを必ず聞くのは、**これが意味を持つ色だから**である。`ok` は「応答・結果・確定」で、facet の設計思想「未定義と無効の型区別」を運ぶ3系統の1つ（rev 9章）。残り4つは装飾か派生であり、規則から導出できる。

**`ok` を `surface-accent` に流用しない。** 見出しの面は「確定・応答」ではない。M8 で別トークンとして新設した理由がこれで、流用は意味論を壊す。

## 決定D: `destructive` が赤とは限らない

Morphos の配布 `theme.css` は `light.destructive` が Primary（Lichen Green）で上書きされる生成ミスを持っており、そのまま入れると **「削除」が緑になる**。M7 で実際に踏み、`palette.test.ts` が `--destructive: var(--warning)` の紐づきを検査するようになった経緯がある。

だが**その検査はトークンの紐づけを見るだけで、色そのものが赤系かは見ていない**。したがって Skill 側で確認する:

- 拾った `destructive` の色相が `ok` 候補の色相と近い（OKLab の色差が小さい）なら、**テーマの生成ミスを疑ってユーザーに確認する**
- テーマに `destructive` が無い場合も同様に候補を出して聞く

**入力を鵜呑みにしない。** 配布物が壊れていることは実際にある。

## 決定E: 明度だけ動かす。ただし `grid` は例外

要件を割った色は、**色相（H）と彩度（C）を保ったまま明度（L）だけ**動かす。テーマの性格は H と C が持っており、そこを動かすと「そのテーマを入れた」と言えなくなる。M7 も同じ方針で Morphos の値を調整した。

- **閾値ちょうどに置かない。** 要件に対して 3% 以上の余裕を取る（M7 の教訓。丸めの境界に乗った期待値は壊れやすい）
- **`grid` は持ち上げない。** 方眼紙の線は装飾で、`palette.test.ts` の検証対象から意図的に外してある。**薄いことに意味がある**ので、コントラストを上げる方向の「調整」をしてはならない
- 動かした結果を報告する（決定I）

## 決定F: 検算はスクリプト、書き込みは Claude

同梱スクリプトは**測るだけ**にする。`palette.css` を書き出す機能は持たせない。

**理由: `palette.css` はコメントが情報の本体である。** 44行のヘッダ（禁止事項と役割の定義）に加えて、各行が由来を持つ:

```css
--rule: oklch(0.6 0.014 120);           /* Mineral Line の色相から導出 */
--ink: oklch(0.85 0.007 88.6);          /* Ash Surface をそのまま置くと 16.79:1 で眩しい */
```

機械に書かせるとこれが消える。**値だけ差し替えて由来コメントが古いまま残るのは、消えるより悪い**——次に読む人が誤った出所を信じる。だから Claude が `Edit` で値を差し替え、**同じ編集で由来コメントも新しいテーマの語彙に書き直す**。これを SKILL.md に明記する。

ヘッダの「由来は Morphos の morphous-basalt」の段落も、差し替え時に書き換える対象である。

## 決定G: `contrast.ts` に2つ足す。`parseOklch` は緩めない

スクリプトが必要とする計算のうち、既存の `src/styles/contrast.ts` に無いものは2つ。

- `linearToOklch` — 既存の `linearToOklab` の結果に `hypot` / `atan2` を掛けるだけ
- `parseAnyCssColor` — hex（`#rgb` / `#rrggbb`）/ `rgb()` / `hsl()` / `oklch()`（`%` 表記とアルファ付きを含む）を `LinearRgb` にする**緩いパーサ**

**既存の `parseOklch` は絶対に緩めない。** あれは「不透明な `oklch(L C H)`、L は 0..1 の小数」だけを通す門番で、`palette.test.ts` がこれで `%` 表記とアルファを弾いている。入口を広げると門が壊れる。新しいパーサは別名の関数として足し、`palette.test.ts` は今まで通り厳格な方を使う。

`contrast.ts` はアプリから1箇所も import されていない（テスト専用）ので、この追加はアプリの挙動に影響しない。

## 決定H: `contrast.ts` を複製しない

スクリプトは `contrast.ts` を**参照する**。ロジックを `.mjs` にコピーしない。

rev 4章の「スキーマの正は一つ。コピーを同梱しない」と同型の判断である。コントラストの計算式が2箇所にあると、片方だけ直したときに**検算が実装と食い違ったまま緑を返す**——`open-issues.md` に既に載っている「エラー登録 Skill の同梱スクリプトがアプリと複製している」と同じ負債を、避けられるのに作ることになる。

**実行方法は実装時に検証して決める。** 第一候補は Node の型ストリップ（`node --experimental-strip-types`。この環境は v22.20.0）、動かなければ `vitest` 経由に落とす。**どちらでも動かない場合に初めて複製を検討し、そのときは理由を `open-issues.md` に記録する。**

## 決定I: 報告に必ず含める4つ

「テストが緑」だけでは足りない。次を表で見せる。

1. **元テーマの値 → 採用値**、および動かした量（どのトークンの L をいくつからいくつへ、なぜ）
2. **捨てたテーマ色**（`primary` / `accent` / `secondary` / `ring` / `chart-*`）と、その帰結（決定B）
3. **`warning` と `ok` の ΔE**（標準色覚・P型・D型）。`palette.test.ts` が毎回出力する数字をそのまま拾う
4. **候補から選んでもらった5つ**の最終値

3 を必ず出すのは、`open-issues.md` に**「色を差し替えるときに、青緑側へ振る案を再検討すること」という宿題が明示的に開いている**ため。現行配色は P型 0.050 / D型 0.041 で、実用域とされる 0.10 を大きく下回っている。差し替えは**この宿題を片付けられる唯一の機会**なので、Skill が毎回この数字を突きつける形にして、忘れられない構造にする。

**ただし ΔE で失敗させない。** M7 決定4 が「このテストが守るものは無い。見せるだけである」と定めており、閾値を足すのは設計判断の変更にあたる。Skill は数字を報告するだけで、判断はユーザーに委ねる。

## 決定J: 作業前に作業ツリーが綺麗であることを確認する

Skill は `palette.css` を上書きする。**気に入らなかったときに戻せることが、気軽に試せることの前提である。**

手順の最初に `git status --short` を確認し、`palette.css` に未コミットの変更があれば、上書きする前にユーザーへ伝える。**勝手にコミットも stash もしない。**

## スコープ外

- **evals を作らない。** 既存2本は持っているが、この Skill の成果は `palette.test.ts` の緑／赤で既に機械判定できており、採点器をもう一層重ねる価値が薄い。`open-issues.md` の「3本目の Skill を作るときに `grade.mjs` の形を揃える」は**発動しない**ので、その旨を残件側に追記する
- **色見本 HTML の生成・実機確認をしない。** 完了条件はテストが緑になること
- **Web からテーマを取ってこない。** 入力は貼られた CSS / JSON かファイルパスに限る。取得先の知識を Skill に持たせると、サイト側が変わった瞬間に腐る
- **画像から色を拾わない**
- **半径・フォント・余白を差し替えない。** `palette.css` は色値だけを持つ（同ファイルの禁止事項）。テーマの `--radius` を持ち込まない
- **`index.css` の31トークンの紐づけを変えない。** `--primary: var(--ink)` 等は rev 9章の確定事項であり、Skill が触ってよい範囲の外
