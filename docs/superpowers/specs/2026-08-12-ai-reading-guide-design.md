# AI向け読み方ガイドの同梱 — 設計

日付: 2026-08-12
状態: 設計確定（実装計画は未着手）

## 背景と目的

facet の目標状態は「人も AI も、このアプリで作ったデータを見に行けば仕様を把握できる」こと（rev 1章・4章）。読む場面は3つ想定する: 実装の参照資料として読む／仕様の Q&A に根拠として使う／レビュー（網羅漏れの指摘）。読み手の AI が動く場所は2通りある: 仕様プロジェクトのフォルダ内（仕様検討時）と、仕様フォルダが同居する実装リポジトリのルート（実装・調査時）。

スキーマの自己記述性（5章）により JSON の**構造**は Skill なしで読める設計だが、**JSON に書かれていない読み方の規約**が存在する:

- 空欄・`undecided` は「未決」という意思表示であり、欠落ではない（勝手に埋めてはいけない）
- 単一性フラグを持つツール（用語集・エラーカタログ）はプロジェクトに1ファイルずつ
- シーケンスの異常系は矢印ではなく「失敗したら？」の問いスロットで表現される、等のドメイン規約

これらは facet 開発リポジトリの docs にはあるが、ユーザーのプロジェクトフォルダには無い。AI が `undecided` を「自由に決めてよい箇所」と誤読して実装に反映すると、facet の核心価値「決めていないことを消せなくする」が AI 側で静かに壊れる。この読み違いはコードに紛れて発見が遅れるタイプなので、後追い（問題が出てから対処）に向かない。

## 検討した案と選択

| 案 | 内容 | 判断 |
| --- | --- | --- |
| A: 読み方 Skill を作る | 「facet プロジェクトを仕様として読む」基盤 Skill を1本作る | 不採用。実装リポジトリ同居の場合、M11 の同期が置く `.claude/skills/` は仕様フォルダ側に入り、リポジトリ直下で起動した Claude Code から発火しない可能性がある |
| **B: 読み方ガイド .md を同梱**（採用） | アプリが管理する静的 Markdown をプロジェクトフォルダ直下に書き出す | AI がフォルダを読みに行った時点で必ず目に入る。Skill 発火の不確実性がなく、AI 非依存（Claude 以外でも効く）。「接点はファイルのみ」（rev 4章）と整合 |
| C: 今は作らない | 読み違いが出てから作る | 不採用。読み違いに気づける保証がなく、失敗が静かに起きる |

案Aの検証ステップ（素読み比較実験）は案Bに引き継ぐ。

## 設計

### 1. 成果物の形と置き場所

- プロジェクトフォルダ直下に、アプリが管理する読み方ガイドを**1ファイル**置く。ファイル名は `README-for-AI.md` の固定名とする（README 系の名前は人も AI も最初に読む慣習があり、`-for-AI` で対象読者と「仕様本体ではない」ことが自明になる）。AI がフォルダを一覧した瞬間に見つかる位置に置くことが唯一の要件
- **1プロジェクト1ファイル**。ツール別に分けない。中はツール種別ごとのセクションで構成し、そのプロジェクトに存在しないツールのセクションも消さない（後からファイルが増えても書き換え不要にするため）
- **内容は静的**。プロジェクトの中身を反映した動的生成はしない（「用語は現在42件」のような記述は書き換え契機が無限に増える）。書くのは「読み方の規約」だけ

### 2. 誰がいつ書くか（配布と更新）

- ガイドの原本はアプリの resources に同梱する（Skill 群と同じ場所・同じバージョン管理）
- **プロジェクトを開いたときに書き出す**。3分岐: 無ければ作る／内容が原本と一致していれば何もしない（mtime も変えない）／不一致（古い・ユーザーが書き換えた）なら原本で上書きする
- ファイル先頭に「このファイルは facet が自動管理する。手で編集しても次回開いたとき上書きされる」と明記する。プロジェクト固有の注意はユーザー自身の別ファイルに書いてもらう
- アプリはこのファイルを**読まない**。書くだけ。エディタ・検証・描画の対象外
- 書き出し契機を Skill 同期の「端末を開く直前」ではなく「プロジェクトを開いたとき」にする理由: 実装リポジトリ同居のユースケースでは facet の端末を経由せず外部の Claude Code から読まれるため、端末起動を契機にできない

### 3. ガイドの中身（骨子）

書くのは「構造の説明」ではなく **JSON から読み取れないこと**だけ。スキーマで分かることを繰り返さない。

1. **冒頭宣言** — このフォルダは仕様整理ツール facet のプロジェクトであり、ここにある JSON 群が仕様の正である。自動管理の注意書きもここ
2. **ファイルの見つけ方** — ファイル名ではなく中身の `type` で判別する。単一性フラグを持つツール（現在は用語集とエラーカタログ）はプロジェクトに1ファイルずつで、複数見つけたらどちらが正か人間に確認する。シーケンス・ロジックツリーは複数あってよい。用語集は他ツールが ID で参照するハブ
3. **ID の読み方** — `term_XXXXXXXXXX` 形式のプレフィクスが参照先の種類を示す。解決手順（用語集で引く）。存在しない ID を捏造しない
4. **最重要の禁止事項** — 空欄・`undecided` は「未決」という意思表示であり、欠落ではない。要約・実装・回答のとき勝手に埋めたり推測で補ったりせず、「ここは未決」と明示的に扱う
5. **ツール別の読み方** — 各ツール1セクション。JSON を見ただけでは分からないドメイン規約だけ（例: シーケンスの異常系は問いスロット、責任境界は参加者の `domain` から導出）
6. **書きたくなったら** — 編集を頼まれた場合は `.claude/skills/` の登録系 Skill を使う（ID 採番・検証・正規形の経路に乗せる）

### 4. 検証と受け入れ基準

実装のテスト（アプリ側）:

- 書き出しロジックの単体テスト: 3分岐（作る／触らない／上書き）を網羅する
- 判定は「原本とプロジェクト内ファイルのバイト一致」

ガイド本文の受け入れ基準（こちらが本体）:

1. sample-project を使い、**ガイドなしの素の Claude** に「このフォルダの仕様を説明して」「〇〇が失敗したらどうなる？」等を聞き、読み違い・埋め違い（undecided の勝手な補完等）を記録する
2. 同じ質問を**ガイドあり**で行い、記録した読み違いが消えることを確認する
3. 素読みで一度も間違えなかった項目に対応するガイドの記述は削る（想像で書いた規約を残さない）

自動評価（登録系 Skill の evals 相当）は作らない。ガイドは静的文書で変更頻度が低いため、手動の比較記録を残す程度に留める。

## rev への影響

実装完了時、rev 4章に「読み方ガイドの同梱」を AI 活用方針の一部として反映する（Skill 群と並ぶ配布物。アプリは書くだけで読まない、という責務の線も明記）。
