# デシジョンテーブル（設計）

## 背景・目的

条件の組み合わせで結果が決まる仕様を、ロジックツリーは扱いきれない。木は「先に何で分けたか」を構造に固定するので、条件が同時に評価される仕様では同じ判断が枝ごとに散る。

条件の全組み合わせを展開した表を持ち、抜けと「効いていない条件」を機械で見つける。表が効くのは、条件が有限に列挙でき、条件が同時に評価され、結果が離散的な仕様に限る。

## スコープ

- 対象: 6本目のツールモジュール `decisionTable`
- 対象: 表系のキーボードファミリー。rev 10章が「表系（遷移表）は Excel 準拠が優先」と予告している範囲
- 対象: 畳み。結果が同じ行をまとめる導出であり、編集はしない
- 対象外: 状態遷移エディタ。rev 2章の3番は未実装の枠のまま残す
- 対象外: 跨ファイル参照。表記ゆれ検知の対象フィールドを宣言する規約が `ToolModule` に無く、他ツールも持たない
- 対象外: ロジックツリーからの変換。rev 8章「専用のインポート機能は作らない」に従い、変換は AI の仕事とする

## 設計

### 1. データモデル（`schemas/decision-table.schema.json`、新規）

```json
{
  "schemaVersion": 1,
  "type": "decisionTable",
  "title": "送料の決定",

  "conditions": [
    { "id": "cond_AAAAAAAAAA", "name": "会員か",       "values": ["はい", "いいえ"] },
    { "id": "cond_BBBBBBBBBB", "name": "5000円以上か", "values": ["はい", "いいえ"] }
  ],

  "outcomes": [
    { "id": "out_AAAAAAAAAA", "name": "送料",       "choices": ["無料", "500円"] },
    { "id": "out_BBBBBBBBBB", "name": "通知メール", "choices": ["出す", "出さない"] }
  ],

  "rows": [
    { "values": ["はい",   "はい"  ], "impossible": false, "results": ["無料",  "出す"] },
    { "values": ["はい",   "いいえ"], "impossible": false, "results": ["無料",  ""    ] },
    { "values": ["いいえ", "はい"  ], "impossible": false, "results": ["無料",  "出す"] },
    { "values": ["いいえ", "いいえ"], "impossible": false, "results": ["500円", ""    ] }
  ]
}
```

**条件の値と結果の選択肢に ID を振らず、ラベルを行に直接書く。** 行が単体で読め、`conditions` のヘッダを一度読めばあとは CSV と同じ読み方で追える。ID で持つと、行数ぶんの照合を AI に強いる。

ラベルを識別子にできるのは、行が導出物だからである。値のラベルを変えたらアプリが全行を書き直すので、参照切れが起きない。

`conditions` と `outcomes` は ID を持つ。プレフィクスは `cond_` と `out_` で、rev 5章の ID 規約に従う。

`results` は `outcomes` と同じ長さ・同じ順の配列で、`values` は `conditions` に対して同じ関係にある。空文字が未記入で、`read-project` が既に教えている「空文字＝未決」の語彙に乗る。

`impossible` は行単位の真偽値で、現実には起こりえない組み合わせを表す。条件同士が独立でないと直積にそうした行が出るので、永遠に埋まらない黄を残さないために持つ。理由の記述欄は持たない。

### 2. 行の導出と再構築

行の集合は `conditions` の直積であり、人は行を足しも消しもしない。並び順は `conditions` の配列順にネストしたループで、左端の条件が最もゆっくり回る。ロジックツリーが編集のたびに配列を DFS 順へ整えるのと同じ扱いで、アプリが条件の編集のたびに行を直積へ整える。

条件または値を足すと行が増える。既存の結果は複製し、新しい条件は「効いていない」状態から始まる。

条件または値を消すと行が減り、結果が食い違う組が出る。**食い違った結果は空欄に落とし、確認ダイアログを挟む。** 片方を黙って採ると、人が決めていない値が決定済みの顔で残る。

### 3. キーボードファミリー（`src/core/keyboard/keymap.ts`、変更）

`KeyContext` の `hierarchical` と `horizontal` を `family: 'list' | 'tree' | 'horizontal' | 'grid'` に畳む。現在は「同時に `true` にしない」という制約が JSDoc にしか無く、3つ目を足すと8通りのうち4通りだけが有効な状態になる。

`family: 'grid'` の写像は、フラットなリスト（`'list'`）から2点だけ変わる。

| キー | `'list'` | `'grid'` |
| --- | --- | --- |
| `Enter` | `insert-item-after` | `focus-next` |
| `←→` | `null` | `focus-prev-field` / `focus-next-field`（キャレット端で） |

**`Command` の語彙は増やさない。** 行移動を `focus-prev` / `focus-next`、列移動を `focus-*-field` に写せるので、rev 10章の「コマンドの語彙をコアに増やす案は採らない」を守れる。

`Alt+↑↓` は `reorderEnabled: false`、空欄 `Backspace` は `deletableField: false` で止まる。`impossible` の入り切りは主修飾キー＋`Enter`（`toggle-item-state`）に写し、シーケンスの「考慮不要」と同じキーに揃える。

### 4. 画面（`src/modules/decision-table/DecisionTableEditor.tsx`、新規）

画面は定義部と表本体に分かれ、キーボードファミリーが異なる。

- 定義部（`family: 'list'`）: 条件と結果の一覧。名前の編集、値と選択肢の追加・削除、条件と結果の並び替え
- 表本体（`family: 'grid'`）: No 列、条件列、結果列。条件列は導出物なので読み取り専用

条件の値は列見出しに置けない。条件名は見出しだが値の集合は行の中身なので、定義部を別に持つ。

No 列は用語集・エラーカタログと同じ導出列で、`rowRef(index)` が値を作る。

### 5. まとめて入力

表の上に入力バーを置く。条件ごとに値か「どれでも」を選び、適用先を1つ選んで押すと、該当する行が一度に埋まる。

範囲選択にはしない。`Shift+↑↓` で選択を伸ばすコマンドが要り、rev 10章が禁じるコマンド語彙の追加になる。

**この操作の並びは、条件の部分割当でルールを書く形そのものである。** 人は「会員なら無料」と打ち、データは全展開のまま残る。

- 適用先は1回に1つ。結果列のどれか1つか、`impossible` の入り切りを選ぶ。結果の選択肢には「空にする」も並べる
- 上書きは常に行い、確認ダイアログを挟まない。トーストで変更した行数を出し、Undo で1操作として戻せる
- 対象行数をボタンに出し、対象の行を表本体でハイライトする
- `onChange(next, null)` を渡し、構造操作と同じ履歴の粒度にする
- バーは通常のフォームで、`family: 'grid'` を掛けない

### 6. 欠落（`src/modules/decision-table/missing.ts`、新規）

| 欠落（黄） | 欠落ではない |
| --- | --- |
| 結果セルが空。`impossible: false` の行に限る | `impossible: true` の行の結果セル |
| 条件名・値ラベル・結果名・選択肢ラベルが空 | — |

`impossible` はシーケンスの `notApplicable` と同じく「決めた上で該当なし」なので黄にしない。画面と出力のどちらにも `起こりえない` と書き、語の定数を1箇所に置く。

`missing-semantics.md` の規約4に従い、判定関数と集計関数を同じファイルに置き、帯に `MissingTally` を出す。規約6に従い、位置は `#N` で指す。

### 7. 整合性検証（`src/modules/decision-table/consistency.ts`、新規）

| ルール | 内容 |
| --- | --- |
| 値ラベル重複 | 1つの条件の中で同じ値ラベルが2件以上 |
| 選択肢ラベル重複 | 1つの結果の中で同じ選択肢ラベルが2件以上 |
| 名前の重複 | 条件名どうし、結果名どうし。NFKC 正規化と英字の大小同一視で判定する |
| 長さ不一致 | `values` の長さが `conditions` と違う。`results` の長さが `outcomes` と違う |
| 未知の値 | `values[i]` が `conditions[i].values` に無い。`results[j]` が `outcomes[j].choices` に無い。空文字は除く |
| 直積との不一致 | 行の集合が条件の直積と一致しない。欠け・余り・順序違いを含む |

**重複をスキーマの `uniqueItems` で拒否しない。** 打ち終わる前の自動保存がレベル1違反ファイルを作るためで、ロジックツリーが空文字を許している理由と同じである。

### 8. 畳み（`src/modules/decision-table/fold.ts`、新規）

`(conditions, rows, 対象の結果列) => 畳んだ行の配列` の純関数。結果列を1つ選んで畳むので、「送料には『キャンペーン中か』が効いていない」という指摘が列ごとに出る。

- `impossible` の行は「どちらでもよい」として使う。起こりえない組み合わせなので、畳んだ表がその行をどう判定しても実害がない
- 結果が空の行は畳みに参加させず、畳んだ表の下に展開のまま残す。空欄どうしを同じ結果として畳むと抜けが画面から消える
- 畳んだ行のすべてで「どちらでもよい」になっている条件を、その結果列に効いていない条件として名前で挙げる

畳みビューは読み取り専用とする。畳んだ行を直接編集できるようにするかは、実機で一巡してから判断する。

### 9. 出力（`src/modules/decision-table/markdown.ts`、新規）

`outputs` は1本で、`id: 'default'`、`fileSuffix: ''`。rev 6章の「形式ごとにプロファイルを割らない」に従い、判定表と畳んだ表を1つの Markdown に入れる。

```
## <title>
### 条件      | No | 条件 | 値 |
### 結果      | No | 結果 | 選択肢 |
### 判定表    | No | <条件名…> | <結果名…> |
### 畳んだ表  結果列ごとに1つ。効いていない条件を文で添える
```

空欄は `（未定義）`、`impossible` の行の結果列は `起こりえない` と書く。rev 8章の「負債を出力にも残す」に従う。セルのエスケープは `src/core/markdown-table.ts` を使い、書き直さない。

`describeIssueEffect` を持つ。行の集合が直積とずれたまま出力すると、抜けた組み合わせが判定表から静かに消える。

`tableExport` は判定表1本を `variants` に持ち、`options` は `numbering` と `showUndefined` だけを宣言する。`numberStyle` と `repeatParent` は木の都合なので使わない。`variants` は静的な配列なので、結果列ごとの畳みは載せられない。

`clipboardExchanges` は持たない。

### 10. 登録 Skill（`plugins/facet/skills/write-decision-table/`、新規）

会話の内容から `decisionTable` の JSON を作成・追記・更新する。ID の採番、スキーマ検証、正規形での書き出し、行の直積への再構築を同梱スクリプトが行う。

`evals/` を最初から持ち、`package.json` のスクリプトと CI から呼ぶ。

### 11. 文書の更新

- `docs/decision-table/` を1フォルダ切る
- `docs/README.md` の表と rev 2章のツール一覧に行を足す
- `docs/missing-semantics.md` の決定1の表に行を足す
- `plugins/facet/skills/read-project/SKILL.md` に `decisionTable` の節を足す

**`missing-semantics.md` と `read-project/SKILL.md` は同じコミットで直す。** 判定源が一対一である以上、片方だけ進むと画面と AI の読みがずれる。

### 12. テスト

- 正規形のバイト一致。行の並びが直積のネスト順であること
- スキーマ検証の合否。ID の形式、`const` の値、`additionalProperties`
- 整合性検証の各ルール。ルールごとに、赤くなる入力と赤くならない入力の両方を置く
- 行の再構築。条件を足すと結果が複製されること、条件を消して食い違うと空欄に落ちること
- 畳みの不変条件。畳んだ表を全展開に戻したとき、`impossible: false` かつ結果が埋まっている全行で元と同じ値が出ること
- 家族旗の畳み込み。既存5ツールのキー写像が1つも変わらないこと
- 欠落の集計。`tallyLine` の文言が Skill の報告と逐語一致すること

### 分岐

統合ブランチ `decision-table` を `main` から切り、5本のマイルストーンはすべてそこへ PR する。worktree もこのブランチから切る。

**`main` へ入れるのは5本が揃ってからとする。** `'grid'` の家族は消費者が現れるまで使われない値であり、途中の状態を `main` に置くと、次に `main` から切った人が未使用の分岐を読むことになる。

## 採用基準の確認

rev 2章がツールを増やすときに求める3条件に照らす。

| 基準 | 判定 |
| --- | --- |
| 参照グラフに参加する | 条件名・値・結果が用語集の語になり、表記ゆれ検知の対象フィールドを宣言できる |
| 未定義を利用者が自分で解決できる | 空欄の結果セルを埋める。行は導出なので、どこを埋めれば終わるかが数えられる |
| 人と AI の共通言語になる | 行が単体で読め、`#N` で会話の中から指せる |
