# M31 文書の整理——正典を現在形へ戻し、経緯を git に任せる 設計スペック

作成: 2026-09-05

## 1. 目的

docs 配下の文書は Claude Code の情報の地図として作られ、人間は読まない。ところが正典として毎マイルストーン読まれる4本（`CLAUDE.md`・`overview-rev.md`・`open-issues.md`・`lessons-for-planning.md`）の合計が 530KB に達し、実装の精度と速度を落としている。本マイルストーンは、文書を「Claude の行動を変える情報だけ」に絞り、再び太らない規則を置く。

## 2. 現状と原因

| 文書 | 2026-08-08 | 2026-09-05 |
| --- | --- | --- |
| `open-issues.md` | 7.7KB | 204KB（冒頭の「最終更新」段落だけで約100KB） |
| `overview-rev.md` | 46KB | 180KB（マイルストーン番号の言及 173 箇所） |
| `lessons-for-planning.md` | — | 69KB（規則1文にエピソード 600〜1,700 字） |
| `docs/history/` | — | 43本・0.98MB。計画時に直近1〜2本を読む以外の読者がいない |

原因は文書の増減を評価する工程の非対称にある。

- レビューの合格基準が「判断ごとにそれを述べる文が正典にあるか」で、消す・短くするを評価する観点が無い。件名に「レビュー」を含むコミット 62 本のうち 22 本は docs しか触っていない
- Claude が既存文書の癖を規約と読み取り、計画へ転記する。`open-issues.md` の「消した件数・足した件数を検算する規約」は `CLAUDE.md` にも `docs/README.md` にも無く、文書の見た目から逆算されて M30 の計画に「規約」として書かれた
- `CLAUDE.md` の規則が「漏らすな」の一方向で、「何を書かないか」「上限」が無い
- 不変であるべき `history/` の append-only が、可変のはずの `open-issues.md` の冒頭段落や `lessons-for-planning.md` に漏れている

## 3. 方針

1. 経緯（いつ・どのマイルストーンで・なぜ変えたか）は git のコミットと PR に任せ、文書には書かない
2. 正典は現在形で書く。読者は Claude だけなので、「いま従うべきこと」以外を載せない
3. 文書の書き方と上限を `CLAUDE.md` に明文化し、計画とレビューがそれを継承する

## 4. 整理後の構成

| 文書 | 扱い | 目標サイズ |
| --- | --- | --- |
| `CLAUDE.md` | 規則を書き換える（§6） | 8KB 以下 |
| `docs/README.md` | 地図だけにする。マイルストーンの履歴表・進捗の説明を消す | 3KB 以下 |
| `docs/overview-rev.md` | 現在形へ書き直す（§5.1）。**ファイル名と章番号は動かさない**（`rev N章` の参照が 249 箇所ある） | 60KB 以下 |
| `docs/open-issues.md` | 平たい一覧へ書き直す（§5.2） | 20KB 以下 |
| `docs/lessons-for-planning.md` | 規則だけにする（§5.3） | 10KB 以下 |
| `docs/history/`（43本）、`docs/archive/`（2本）、`docs/facet-UI設計ノート.md`、`docs/issue-tree/スキーマv3-引き継ぎ.md` | 削除する | — |
| `docs/project-setup.md`・`docs/release.md`・`docs/missing-semantics.md`・`docs/images/` | そのまま | — |

## 5. 書き直しの規則

### 5.1 `overview-rev.md`

- 章ごとに「いま従う規範」だけを残す。マイルストーン番号・日付・「当初は…だったが改めた」「M30 までは…」の形の経緯を落とす
- 再検討のために残す根拠（「DB を採用しない理由」など、選ばなかった案の理由）は残す
- 9章はデザイン作業の入口として単独で読める形にする。冒頭に UI ノートの診断の原則（差をつける場所と揃える場所・彩度の予算・密度は行高で稼ぐ）を5行程度で置き、**決定は `D1`〜`D20` の番号と名前を見出しに残す**。コードのコメント約25箇所が「UI ノート D19」の形で引いているので、番号が生き続ける必要がある
- 落とし漏れの番人: 旧版から「決定」「確定」「規約」「しない」「禁止」を含む文を機械抽出して一覧を作り、各文について新版に対応する文があるか、または意図して落とした（経緯のみ・実装で消えた）かをレビューで1文ずつ判定する。判定結果の表は PR の本文に貼り、リポジトリには残さない

### 5.2 `open-issues.md`

- 冒頭の「最終更新」段落、増減の検算、`[MN]` の由来タグを捨てる
- 節は「次に手を付ける候補」「テストが無い箇所」「挙動の穴」「性能」「アクセシビリティ」「デザイン」「小さな負債」
- **載せるのは Claude が着手できる項目だけ。** 人間の作業（実機確認・署名鍵・配布・スクリーンショット撮影・仕様の裁定）は載せない。いま載っている人間の項目は書き直し時に落とし、まだ必要なものは本マイルストーンの PR 本文で依頼する
- 1項目は「何が・どこで（パス）・なぜ残っているか」の2文まで。経緯（どのレビューが見つけた、どのマイルストーンで後回しにした）は書かない
- 既存項目のうち、実装が既に解消しているものは書き直し時に落とす。判定は実物のコードで行う（項目の文言を信じない）

### 5.3 `lessons-for-planning.md`

- 各箇条の太字の規則文だけを残し、エピソードを捨てる。1規則1行
- 規則が何を防ぐかが規則文だけで読めない場合に限り、半角括弧で1句だけ補う
- 節構成（大原則・設計判断・デバッグ・テスト・状態と時間・タスク分割・検証手順・文書の更新）は保つ

### 5.4 `docs/README.md`

- 「どれを読むか」の表と「文書の3つの寿命」を残す。寿命は「正（可変・規範）」「現在の状態（可変）」「記録（git）」に改め、`history/` と `lessons-` の append-only の記述を消す
- 各行の説明は1文。進捗（A〜F が実装済み等）を書かない
- マイルストーンの履歴表と採番の説明を消す。採番の規約（`mN` / `<tool>-mN`）は `CLAUDE.md` に1行で移す

### 5.5 削除と参照の掃除

- `docs/history/` を指すコードコメント（`src/core/app-controller.ts`・`src/core/canvas/wrap.ts`・`src/fs/settings-fs.ts`）は、参照先が述べていた根拠を1文でコメントに書き込み、参照を外す
- 「UI ノート DN」の形の参照（`src/` 約25箇所・`.claude/skills/palette-retheme/SKILL.md`・`docs/missing-semantics.md` 等）は「rev 9章 DN」へ置換する
- 残す docs から `history/`・`archive/`・UI ノートへのリンクは、リンク先の内容が rev に移っていれば rev の章へ、経緯のみなら削除する
- `README.md`（リポジトリ直下）の参照も同様に直す

## 6. `CLAUDE.md` の規則

現行の「実装計画は worktree を作ってから書く」「マージ後の後片付け」は残す。「ドキュメント」「マイルストーン完了時に触る3箇所」を次の内容に置き換える。

**文書の書き方**

- 文書は現在形で書く。経緯・マイルストーン番号・日付・「消した／足した」の記録は書かない。経緯は git のコミットと PR にある
- 1項目は2文まで。太字は1段落に1箇所まで。全角括弧の入れ子を作らない
- 既存文書の文体に合わせるのではなく、この規則に合わせる
- 文書の運用に関する規約（何をどこに書くか・件数を数えるか等）は `CLAUDE.md` にあるものだけ。他の文書の書きぶりから運用規約を推定して計画に転記しない

**マイルストーン完了時に触る2箇所**

1. `docs/open-issues.md`: 解消した項目を消し、見つけた項目を足す。上書きであり、変更の記録を残さない
2. `docs/overview-rev.md`: 設計判断が変わったときだけ、該当する章の文を書き換える。追記ではなく置換

`docs/history/` は作らない。申し送りに相当する内容は PR の本文に書く。

**人間への依頼**

- 人間の作業（実機確認・署名鍵・配布・スクリーンショット撮影・仕様の裁定）は文書に書かない。実装完了時の最終メッセージと PR 本文で依頼する。実機確認のチェックリストは PR 本文に置く
- `docs/open-issues.md` に載せるのは Claude が着手できる項目だけ

**計画とレビュー**

- 計画の Global Constraints に「文書の書き方」を継承させる
- レビューは文書の差分に対して「削れる文があるか」「現在形か」を見る。「書いてあるか」だけで合否を決めない
- `docs/lessons-for-planning.md` への追記は規則1行だけ。エピソードは PR の本文に書く

**採番**

- コア・用語集・エラーカタログは `MN`、ロジックツリー・シーケンス・課題ツリーは `<tool>-mN`。ブランチ名と計画ファイル名に使う

## 7. 検証

1. 削除したファイル・ディレクトリへの参照がリポジトリ内に残っていないこと。`grep -rn 'docs/history\|history/m\|facet-UI設計ノート\|UI ノート\|docs/archive\|スキーマv3-引き継ぎ'` を `node_modules`・`src-tauri/target`・`docs/superpowers`・`.git` を除いて回し、無出力であること。`docs/superpowers/` は計画の記録なので参照が残ってよい
2. rev の決定文の突き合わせ表が全行判定済みで、「落とした」の行に理由があること
3. サイズ目標（§4）を `wc -c` で満たしていること
4. `npm test && npx tsc -b && npm run lint` が緑であること。コードコメントしか触らないが、`src/styles/conventions.test.ts` など文書を読むテストが無いことを含めて確かめる
5. `docs/README.md` から辿れるリンクがすべて実在すること

## 8. 実施順

1. `CLAUDE.md` を書き換える（以降の作業がこの規則に従う）
2. `open-issues.md` を書き直す（実物のコードで解消済みを落とす）
3. `lessons-for-planning.md` を書き直す
4. `overview-rev.md` を書き直し、突き合わせレビューを1回入れる
5. 削除と `docs/README.md` の書き直し、参照の掃除
6. 検証（§7）

1本の PR にする。history の削除は git に残るので復元できる。

## 9. 対象外

- `docs/superpowers/` の計画・スペック（4MB）。読まれるのは直近の数本だけで、既定の読書経路に無い
- `docs/issue-tree/仮説検証モジュール-設計ノート.md` と各ツールの設計ノートの圧縮。次の残件にする
- `src/core/reading-guide.md`・`README.md`・`.claude/skills/*/SKILL.md` は配布物で、本マイルストーンの対象ではない（参照の置換だけ行う）

## 10. 効き目の測り方

- 計画時に読む文書の合計（`CLAUDE.md`＋rev＋open-issues＋lessons）が 100KB 以下になること
- 次のマイルストーン以降、docs だけを触るコミットが1マイルストーンあたり数本に収まること（M30 は 22 本中 15 本が docs 変更だった）
