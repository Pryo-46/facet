## 1. 動機となった観察

課題ツリー（issueTree v4）を実PoCで使って出た6件の「できないこと」と、その構造上の正体。

| # | できないこと | 構造上の正体 |
|---|---|---|
| 1 | 課題の背景を残したい | 課題ノードが仮説に比べて痩せている（`text` + `events` のみ） |
| 2 | 課題の温度感を可視化したい | 温度計ではなく「今回やる／本開発へ／未振り分け」の振り分け |
| 3 | この解で他の課題も解決する、と言いたい | 仮説が複数の課題にまたがる。木では表現できない |
| 4 | 課題自体に分かっていないことを残したい | 課題側の `asks`（問いとして立つべき情報） |
| 5 | 課題ノードを出力したい | 設計ノートで観察待ちにしていた項目。まだ弱い |
| 6 | PoCで確認／本開発で調べればOK の目印 | 2と同じ振り分けの裏表。`deferred` + note で表現済みだが俯瞰で見えない |

使い方の前提: 一人利用が中心。Claude が課題を約50個出し、人が絵文字で `text` に印を付けて選別した（印は Claude がファイルから読んで議論に使えた＝ビュー状態ではなくデータ）。

## 2. 構造の結論

### 2.1 仮説は PO とエンジニアの継ぎ目

課題ツリーは「PO が What を考える手助け」であり、仮説を経由して既存の仕様モジュール（How）につながる。

```
課題ツリー ──→ 仮説 ──→ 仕様モジュール群
（What の未知） （橋）  （How の定義）
   PO が主       両者     エンジニアが主
```

仮説は一つのエンティティに両者が書く唯一の場所で、書き手はフィールドで分かれる。

| フィールド | 問い | 主な書き手 |
|---|---|---|
| `title` | 何を作るか | PO |
| `value` | なぜ効くか | PO |
| `detail` | どう作るか | エンジニア（**仮置き**。「あの画面でああして」の粒度） |

**警戒点:** `detail` に How が育つと、PRD を退けた理由（構造の外で自由記述が育つ）が別の顔で戻る。規約: `detail` は着想のスタブ。設計に育ったら仕様モジュールへ移し、仮説 ID を参照する。

### 2.2 発散と収束を分ける

発散と収束では「見えるべき未定義」も、向いている絵も違う。用語集とロジックツリーが ID で参照し合うのと同じ関係。

| | 課題ツリー（発散） | 仮説モジュール（収束） |
|---|---|---|
| 主語 | 課題 | 仮説（ソリューション） |
| 絵 | 木 | 課題 × 仮説の表、または課題を並べた仮説一覧 |
| 見える未定義 | 分かっていないこと（`asks`）、未振り分け | 拾われていない課題（空の行）、判断のない仮説 |
| 主な書き手 | AI が出し、人が振り分ける | 人と AI が置き、人が判断する |
| 参照 | 何も知らない | 課題 ID を一方向に参照 |

### 2.3 エンティティと記録

```
課題ツリー（発散）              仮説モジュール（収束）
──────────────────              ─────────────────────────
課題                            仮説
  属性: text / detail / asks      属性: title / value / detail(仮置き)
  振り分け旗: focused / deferred   asks / feedbacks
    （トグル、0 or 1）              検証結果: 0 or 1（差し替え可）
                                                ↑ 仮説ID
                                 課題への決定（追記）
                                   PoC で試す → 最終的にこれにする
```

記録は4種類。性質が違うので件数の規律も違う。

| 記録 | 付く先 | 性質 | 件数 | 書くモジュール |
|---|---|---|---|---|
| 振り分け | 課題 | 今どこを見ているか | トグル | 発散 |
| 検証結果 | 仮説 | 事実。訂正される | 0 or 1 | 収束 |
| 決定 | 課題（仮説 ID を指す） | 選択。後の決定は前を消さず重なる | 追記 | 収束 |
| FB | 仮説 | 記録。昇格しない（D9） | 追記 | 収束 |

**課題ファイルを書くのは発散側だけ**（1ファイル1書き手）。

`focused` は導出を触らない。「焦点のものだけ問いを立てる」にすると未振り分けの問いが消え、「決めていないことが見える」思想が崩れる。焦点だけ見たいのはビューの絞り込みで担う（データは旗、見せ方はフィルタ）。

### 2.4 「決める」は仮説ではなく課題に付く

「PoC で作る」「最終的にこれにする」は、課題に対して複数の仮説から**ソリューションを一つ選ぶ**行為。「この仮説は正しかったか」（検証結果）は仮説についての事実であり、「この課題にはこの解を使う」は課題についての選択。支持されたが採用しない／棄却されたが採用する、はここで表現できる（D12「支持と解決は別」の延長）。

- **決定は追記、事実は差し替え。** v4 で検証結果を差し替え可に戻したのは「間違いは消したい」から。決定は時点の選択で、「PoC では H1、最終的には H2、理由はこう」が一本で読めることが「後で判断を見返せる」の中身。追記でなければ残らない
- **意思決定ログは別モジュールにしない。** 決定が指すのは課題と仮説だけで、新しいエンティティを持たない。収束モジュールの中の課題側の記録として置く（設計ノート未解決論点3の席がここで決まる）
- **AI の関与:** AI の提案＝関連付け（`issueIds` に足す）だけ。判断（検証結果・決定）は人が押す。D9 と同じ規約に乗る

### 2.5 仮説の課題参照は並列

「この解で A も B も C も行ける」という主張に出自の課題は無い。主従（`issueId` + `relatedIssueIds`）ではなく **`issueIds` の並列**。同じ主張が各課題に対して立つので、各課題の「仮説なし」が消えるのは嘘にならない。

分岐: 「A には効いたが B には効かなかった」が起きたら、判断を組（課題×仮説）に付けるのではなく**仮説を2つに割る**。主張が2つあったということなので、意味に忠実。組単位への移行は、割ってもなお不便だと観察されてから。

## 3. 既存判断への影響

| 判断 | 影響 |
|---|---|
| D1（仮説はどこでも可、問いは葉だけ） | 木と仮説の同居のための妥協だったので、分割で自然に解消 |
| D2（ミュータブル状態を持たない） | `focused` は D12 と同じ「人の表明」として整合。仮説側の `deferred` は決定からの導出に置き換わり、手動イベントが一つ減る |
| D5（見送りの行き先で kind を分けない） | **据え置き**。「本開発へ」は `deferred` + note のまま。「今回やる」を `focused` で持てば D5 を戻す必要が無い |
| D9（FB は昇格しない） | 維持 |
| D12（`resolved` は人の表明） | **決定に吸収**。「解決」は空の旗ではなく仮説 ID 付きの「この解で行く」になる |
| 設計ノート OUT「Markdown出力」 | 観察は来たがまだ弱い。次の観察待ち |
| 設計ノート 未解決論点3（意思決定ログとの分担） | 2.4 で席が決まる |

## 4. 構造でまだ空いている席（今は決めない）

1. **課題側の FB。** 「そもそも課題の立て方が違った」という FB は仮説に付けにくい。課題にも `feedbacks` を持たせて対称にするか、`asks` で受けるか
2. **決定の語彙。** 「PoC で試す」「最終的にこれにする」の2語で足りるか。「PoC でも本開発でも作らない」（課題を閉じる決定）を語彙に持つか、`deferred` の旗で表すか
3. **再発散のループ。** 収束の途中で新しい課題に気づいたとき、課題ファイルを書けるのは発散側だけという規律を守ると、いったん戻る運用になる。一人利用＋AI発散なら Claude 経由で足せるので実害は小さい見込み。観察待ち
4. **`focused` の粒度。** PoC が複数回になったとき「どの PoC で」が要るか。D4「スプリント参照は持たない」との整合（今日の会話には出ていない論点。不要なら削除）

## 5. 分割設計セッションで決めること

- 2ファイル化のスキーマ（issueTree v5 と、収束側の新 type。名前未定）
- v4 ファイルの分割移行（互換変換は用意しない方針との整合）
- 収束モジュールの絵（表か一覧か）と、抑制の導出（見送りの配下は問いが立たない、がファイルをまたぐ）
- 「関連仮説あり」を3段階バリデーションの3段目（弱表示）で出すか
- Skill の分割（`issue-tree-register` を発散／収束で分けるか、フェーズ A/B のまま2ファイルに書くか）
- AI が発散した課題を「未振り分け」として書く規約
- `detail` が仕様に育ったときの移し方（仕様モジュールからの仮説 ID 参照の形）
