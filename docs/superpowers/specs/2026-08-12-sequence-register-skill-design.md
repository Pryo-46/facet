## この Skill の目的

**Claude と仕様を詰める会話の最後に「じゃあこれでシーケンス図作って」と言えば、その会話が `type: "sequence"` の JSON になる。**

既存2本の Skill と材料が違う。用語集は「用語」、エラーカタログは「エラーメッセージ一覧や問い合わせ実績」という**外部の材料**を構造化するが、この Skill の材料は**直前までの会話そのもの**である。会話には既に AI の発言が混ざっているため、「何が人間の決定で何が AI の推測か」の線引きが、既存2本より難しく、かつ重要になる。

**このSkillの価値は「AIが速く書けること」ではなく、会議の速度でユーザーの頭の中を構造化データにすること**にある——既存2本と同じ。

## 2つのフェーズ

| | やること | 起動 |
| --- | --- | --- |
| **フェーズA：図を起こす** | 会話から `actors` + `steps` を組んで書き出す。`failures` は会話で明示的に決まったものだけ転記 | 「作って」で即実行。確認ゲートなし |
| **フェーズB：問いを詰める** | 立っている問いを列挙してまとめて聞き、答えを埋める | 書き出した直後に**1回だけ**提案。断られたら繰り返さない |

### フェーズA に確認ゲートを置かない理由

エラーカタログ Skill は「登録するエラーをユーザーに確定させる」手順を持つ（**入れるのは1往復、消すのは後で何度も**という非対称があるため）。シーケンスにこの非対称は無い。外れならファイル1本を捨てるだけであり、しかも**図にすれば一目で分かる**。テキストで骨格を読み合わせるより、書いてアプリで見るほうが速い。

### フェーズB の提案が催促にならない線引き

エラーカタログ Skill には明文の禁止がある——「`（未定義）` が出力に並ぶのは正常である。『出力が未定義だらけなので埋めましょう』と AI が言わない」。決めていないことを消せなくするのがこのツールの思想であり、`（未定義）` はその思想が働いている証拠だからである。

フェーズB の提案はこれと衝突しかけるが、**別物として整理できる**:

- 禁じられているのは**催促**（ファイルの状態を見て「不完全だから埋めろ」と言うこと）
- フェーズB は**作業の続きの提案**（会話が続いている文脈で、次の作業を1回だけ差し出すこと）

したがって規律は「**書き出した直後に1回だけ提案する。断られたら繰り返さない。既存ファイルを開いて未定義の件数を数えて回らない**」。SKILL.md にこの線引きをそのまま書く。

## ファイルの扱い

**既存2本と構造的に違う点が1つある。** 用語集もエラーカタログも `singleton: true` なので「プロジェクト内の当該 `type` を探して追記」が既定だったが、**シーケンスは `singleton: false`** である。

| 項目 | 決定 |
| --- | --- |
| 既定 | **新規作成**。既存の `type: "sequence"` を探して追記しない |
| 既存への書き足し | ユーザーが**名指ししたとき**だけ（「あの注文確定の図の失敗のところ埋めて」）。名指しがなければ新規 |
| ファイル名 | `title` 由来。既存と衝突したら**報告して確認する**（勝手に上書きしない） |
| 単一性の警告 | **出さない**（シーケンスが複数本あるのは正常） |
| 複数シナリオが混ざっていたら | **主線1本だけ書く**。残りは報告で「取り寄せの流れも出ていたので、必要なら別ファイルで作ります」と伝える |
| 主線の決め方 | **会話で最も長く詰められた流れ**。同程度なら**先に通しで語られたほう**を採る。どちらを採ったかは報告に書く |
| `title` の決め方 | 会話から付けて**報告で伝える**（確認ゲートを置かない方針の帰結。違えばユーザーがアプリで直す）。分岐条件があるなら含める（例:「注文確定（在庫あり）」） |
| 下書きの置き場所 | プロジェクトフォルダの**外**（スクラッチ）。理由は既存2本と違い、中に置くと**アプリのファイル一覧に下書きが本物として並ぶ**ため |
| アプリで開いたまま作業しない | 既存2本と同じ（自動保存との競合で片方の変更が消える） |

`title` はアプリのファイル一覧に出る表示名なので、後から人間が読んで何のシナリオか分かる必要がある（例:「注文確定（在庫あり）」）。

## 同梱スクリプト

### 前提：Skill はユーザーのプロジェクトフォルダへコピーされる

`src/core/skill-sync.ts` の `BUNDLED_SKILLS` に載った Skill は、アプリがプロジェクトフォルダの `.claude/skills/` へ置き直す。**したがってスクリプトは `<プロジェクト>/.claude/skills/sequence-register/` から実行される。そこに `src/modules/sequence/` は存在しない。**

`palette-retheme` が `src/styles/contrast.ts` を直接 import できているのは、あれが facet 自身のソースを触る**非同梱**の Skill だからである。データ作成 Skill は同梱されなければ使えないので、この手は使えない。

`readBundled`（`src/fs/skill-resources.ts`）はディレクトリ配下を再帰的に無条件で集め、`shouldSyncSkillFile` が落とすのは `evals/` と Skill 直下の `package.json` / `.gitignore` だけである。**Skill ディレクトリに置いたファイルは何でも運ばれる。**

### 決定：`questions.ts` のバイト一致コピーを同梱し、一致をテストで強制する

`src/modules/sequence/questions.ts` を `.claude/skills/sequence-register/scripts/questions.ts` として**バイト一致でコピー**し、`sequence-write.mjs` から `import('./questions.ts')` する。

動く根拠（実測済み）:

- `questions.ts` の import は `import type { SequenceStep } from '@/types/sequence'` の1本だけで、型 import は型ストリップで消えるため `@/` エイリアスの解決が要らない。Node v24.12.0 で `import('./src/modules/sequence/questions.ts')` が通ることを確認した
- 相対＋拡張子つきの specifier なので Node ESM が解決できる。リポジトリでもユーザーのプロジェクトでも同じファイルが動く
- 対照的に `consistency.ts` は `from './questions'`（拡張子なし）を持つため Node から直接 import できない。これも実測で確認した

**一致は2つのユニットテストで強制する:**

1. `scripts/questions.ts` と `src/modules/sequence/questions.ts` が**バイト一致**していること
2. `questions.ts` が**型 import しか持たない**こと（値 import が生えるとコピー側で解決できず壊れる。`enum` やコンストラクタのパラメータプロパティなど**消去できない構文**も同様に落ちる）

**これが元案（`src/` を直接 import する）より良い点である。** open-issues #78 はエラーカタログ Skill について「追従漏れがあっても双方は独立に動くため、テストでは検知されない」と記録しているが、シーケンスでは**ズレたらテストが赤くなる**。手で複製するのとは質が違う。

代償は open-issues #80 と同じ「Node のバージョンと構文への見えにくい依存」だが、`questions.ts` は「ユーザー・ツール設定・ステップ側の宣言で変えられるようにしてはならない」とコメントで明記された、意図的に固い関数である。ここに消去不能構文が生える確率は、手複製の追従漏れが起きる確率より小さい。しかも上記テスト2がその生え方を検知する。

**却下した案:** `consistency.ts` 側の import を `./questions.ts` に直して両方 import できるようにする——アプリのソースを Skill の都合で曲げることになるため採らない。

### `scripts/new-id.mjs`

既存2本とほぼ同一（`crypto.randomInt` で英数字62文字・10文字）。既定 prefix を `step` にし、参加者は `--prefix actor` で採る。

```
node scripts/new-id.mjs 12            → step_XXXXXXXXXX を12件
node scripts/new-id.mjs 3 --prefix actor → actor_XXXXXXXXXX を3件
```

prefix の取り違えは書き出し時の `pattern` 検証（`^actor_[A-Za-z0-9]{10}$` 等）が捕まえる。

**既存ステップへの書き足し（フェーズB）では採番しない。** 新しい参加者・ステップを足すときだけ使う。既存の `id` は不変である。

### `scripts/sequence-write.mjs`

```
node scripts/sequence-write.mjs --in <下書き.json> --out <プロジェクト>/<タイトル>.json
node scripts/sequence-write.mjs --check <ファイル>
```

責務は既存2本と同じ3つ:

1. **スキーマ検証**（`schemas/sequence.schema.json` を実行時に探索。コピーは持たない。`--schema` と環境変数 `FACET_SEQUENCE_SCHEMA` で明示指定可）
2. **正規化**（キー順をスキーマの `properties` 記載順から実行時に導出。LF・2スペース・非ASCIIそのまま・末尾改行あり・BOMなし。既存の `reorder` と同じ）
3. **整合性検証**（レベル2相当。警告にとどめ、書き込みは止めない）

整合性検証の内訳:

| 検査 | 出どころ |
| --- | --- |
| 立っていない問いへの答え | `questions.ts` の `unposedAnswers` を **import** |
| 未定義の集計（⚠ 未定義 N ／ ✓ 回答済 N ／ ─ 考慮不要 N） | `poseQuestions` + `presentAnswers` を **import**（アプリのガター集計と同一規則） |
| `from` / `to` の参照切れ | 手で実装（`actors` の ID 集合との照合） |
| ID重複（`actor_` / `step_` 各々） | 手で実装（正規化しない完全一致。IDは機械的識別子） |
| `self` に `to` がある／`call`・`reply` に `to` が無い | 手で実装 |

**単一性の警告は出さない**（`singleton: false`）。

終了コード: 0＝成功（警告はあり得る）／1＝スキーマ検証失敗／2＝使い方の誤り。**0 でも未定義の要約と警告は標準出力に出ている**ので、終了コードだけを見ない。

**警告が出たときの扱いは、出どころで分ける**（SKILL.md に書く）:

| 出どころ | 扱い |
| --- | --- |
| 今回 AI が書いた部分の警告（立っていない問いへの答え、`self` に `to` がある等） | **AI 自身の書き間違い。直して再実行する**（ユーザーに聞かない） |
| 既存ファイルに元からあった警告 | **報告して確認する。勝手に直さない**（`kind` 切替の残骸か意図かはユーザーしか判断できない） |

初回のみ Skill ディレクトリで `npm install`（ajv が必要）。

## SKILL.md の規律

### frontmatter

`name: sequence-register`。`description` は既存2本に倣い、明示的に「シーケンス図」と言われていない場面（仕様の会話の流れで「じゃあこれで図にして」と言われたとき、`type: "sequence"` の JSON があるとき、処理の流れ・登場人物・呼び出し順の整理を頼まれたとき）でも起動するよう書く。

冒頭に既存2本と同じ紐づけを書く: **`type: "sequence"` × `schemaVersion 1`。スキーマが改訂されたらこの Skill も追従させる。**

### フェーズA：`kind` と `awaitsReply` の決め方

**シーケンス固有に最も難しいのがここである。** この2フィールドが問いのセットを決める（design-notes 論点3 の導出テーブル）ため、取り違えると立つ問いが変わる。規律は3つ:

- **`awaitsReply` は「応答を待つか」であって「応答があるか」ではない。** 会話から読めないときは `true`——アプリの既定（`src/modules/sequence/commands.ts`）と同じで、かつ問いを多く立てる安全側に倒れる。ただし**報告で「投げっぱなしかは会話から読めなかったので待つ扱いにした」と明示する**
- **会話で言及されていない `reply` を補わない。** UML の癖で呼出と応答をペアで書きたくなるが、機械的に補うと図が倍の長さになり会議で追えなくなる。「そのあと結果を返す」と会話に出ていれば置く、出ていなければ置かない
- **`domain` は会話で明示されたものだけ。** 「決済会社の」「外部の」と言われていない参加者に推測で入れると、**存在しない責任境界の縦線が描かれる**（`domain` の用途は境界線の描画のみ。design-notes 論点4）

### フェーズA：`failures` の転記

線引きは既存2本と同じ（**転記はする、推測はしない**）。会話が材料である分、3段に分けて明示する:

| 状況 | 扱い |
| --- | --- |
| ユーザーが言った（「与信 NG なら画面にエラー表示で中断」） | 転記する。文言もなるべくそのまま使う |
| AI が提案し、ユーザーが同意した | 転記する |
| AI が提案しただけ／議論に出ていない | **空にする**（キーを置かない） |

**`failures` のキー欠落＝未定義**であり、正規化で欠落キーを補完しない。

**シーケンスには `notes` に相当する欄が無い。** エラーカタログは「なぜ空にしたか」を `notes` に逃がせたが、シーケンスは逃がせない。**空にした理由はファイルに残らないので、報告文に書く**——この事実を SKILL.md に明記する。

### フェーズB：問いの詰め方

1. 立っている問いを **`questions.ts` の `questionLabels` の文言そのままで**列挙する（AI が言い換えない。アプリのガターに出る文言と一致させる）
2. **まとめて聞く。** ステップ順ではなく「同じ答えになりそうなもの」で束ねる（「この3ステップはどれも決済会社への呼出ですが、落ちたときの扱いは同じですか？」）。1問1答で往復すると会議が止まる
3. 答えが出ないものは**空のまま**。3状態（未定義／`handled`／`notApplicable`）の区別を保つ
4. **`notApplicable` はユーザーが「考慮不要」と言ったときだけ。** AI が判断しない——エラーカタログの `resolutionLevel: "none"` と同じ規律で、これは**決定の記録**だからである

既存ファイルを名指しされたときの書き足しも、このフェーズB と同じ手順に合流する。守ること（既存2本と同じ）:

- **`id` を変えない**（不変ID。将来 `errorRefs` / `replyTo` の参照元になる）
- **`actors` / `steps` の配列順を変えない**（配列順＝横の並びと時系列の正本。並べ替えは意味のない diff を生む）
- **`title` を書き換えない**（アプリのファイル一覧に出る表示名）
- **触っていないステップを1バイトも変えない**

### 報告

- 作ったファイルのパスと `title`
- 参加者とステップ数、**主線以外に見えたシナリオ**があればその旨
- **`awaitsReply` を推測で `true` にしたステップ**（あれば）
- ⚠ 未定義 N ／ ✓ 回答済 N ／ ─ 考慮不要 N の集計
- 整合性の警告があれば、何が衝突しているかと判断が要る点
- **フェーズB の提案（1回だけ）**

### やらないこと

- **会話に無い異常系のステップを図に足さない。** 異常系を矢印で描かないのが設計の中核（design-notes 論点1）
- **`reply` に `failures` を書かない／問いの類型を増やさない**（`questions.ts` の導出が正）
- **座標・行番号・幅をデータに入れない**
- **MCP 的な書き込みツールを作らない**（アプリとの接点はファイルだけ。決定済み）
- **既存データの勝手な整形・並べ替え・言い換えをしない**
- **網羅性を主張しない**（「これで全部の失敗が拾えました」と言わない）
- **未定義を催促しない**（フェーズB の提案は書き出し直後に1回だけ）

## テスト

### evals（`evals/evals.json` ＋ `evals/grade.mjs` ＋ `evals/fixtures/`）

既存2本と同じ形。ケース:

| # | 名前 | 見るもの |
| --- | --- | --- |
| 0 | `new-sequence-from-conversation` | 会話から新規作成。主線1本、`failures` は転記分のみ、**言及されていない `reply` を補わない**、ID は `actor_`/`step_` ＋英数字10文字、正規形 |
| 1 | `pick-main-line-from-branching-talk` | 複数シナリオが混ざった会話。主線1本だけ書き、残りを**報告する**（勝手に複数ファイルを作らない） |
| 2 | `fill-in-existing-sequence` | 既存ファイルへの書き足し（フェーズB）。`id`・配列順・触っていないステップが1バイトも変わらない。`notApplicable` を AI が勝手に付けない |
| 3 | `avoid-unposed-answers` | 立たない問いへの答えを書かない（`awaitsReply: false` に `failed`、`reply` に `failures`） |

**open-issues #81 をここで解消する。** 同項目は「2本の Skill の `grade.mjs` で自己位置解決の形が揃っていない。用語集版は主チェックアウトの絶対パス（`C:/Dev/Projects/facet/...`）を持っており worktree では動かない。**3本目の Skill を作るときか、用語集版に触る機会に揃える**」と記録され、「3本目（`palette-retheme`）は evals を持たないため、この揃え直しの機会にはならなかった」と但し書きまで付いている。**evals を持つ3本目が本 Skill なので、用語集版を `import.meta.url` 起点に直し、3本で形を揃える。**

- `src/core/skill-sync.test.ts` が `BUNDLED_SKILLS` の中身を固定しているかを確認し、していれば `sequence-register` を足す

## スコープ外

- **`consistency.ts` をアプリ側で import 可能に直す**（却下済み。アプリのソースを Skill の都合で曲げない）
