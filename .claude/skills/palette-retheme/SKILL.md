# 配色差し替え

外部テーマ（shadcn 系の `theme.css`、色のリスト）を受け取り、`src/styles/palette.css` の20トークン×2モードを埋めて、`npm test` が緑になる状態まで持っていく。

**この Skill が触るのはアプリ自身のソースである。** 同じディレクトリにある `glossary-term-register` / `error-catalog-register` は**ユーザーのデータ**（プロジェクトフォルダの JSON）を作る Skill で、アプリは AI が触ったことを知らない。こちらは**アプリのリポジトリの中身**を書き換える。既存2本の形を期待して読むと、無いものを探すことになる:

- **スキーマは無い。** 検証するのは JSON Schema ではなく `src/styles/palette.test.ts` である
- **正規形で書き出すスクリプトは無い。** 同梱スクリプトは**測るだけ**で、`palette.css` を書くのは Claude の `Edit` である（手順7に理由を書く）
- **やり直しの手段が git である。** だから作業前に作業ツリーが綺麗であることを確かめる（手順1）

**色値を持ってよいのは `src/styles/palette.css` だけである。** `src/index.css` は shadcn の31トークンを**すべて役割トークンから導出**しており、色値を1つも持たない。この二層構造があるから、配色の差し替えは1ファイルの書き換えで済む。**差し替えの作業がこの構造を壊してはならない**——`palette.css` に外部テーマの色を並べたつもりで `index.css` の導出を書き換えると、以後どちらが正か分からなくなる。

## 全体の流れ

**番号は下の手順の節番号と一致させてある。** 「手順N」という言及はすべて節番号を指す。

1. 作業ツリーが綺麗か確認する
2. 渡されたテーマを読む
3. facet の役割へ対応づける（**拾うのは7色だけ**）
4. `destructive` が本当に赤（`invalid`）か疑う
5. 対応物がない13個（`missing` / `pending` / `judge-yes` / `judge-yes-fg` / `judge-no` / `judge-no-fg` / `grid` / `rule-muted` / `ink-faint` / `missing-face` / `invalid-face` / `pending-face` / `judge-yes-face`）をユーザーと決める
6. 下書き JSON を作り、同梱スクリプトで検算する（**終了コード 0 になるまで**）
7. `palette.css` を `Edit` で書き換える（**由来コメントも同じ編集で書き直す**）
8. `npm test` を走らせる
9. 報告する

以下の `node` コマンドは**リポジトリのルート**（`package.json` があるディレクトリ）で実行する。スクリプトは相対パスで `src/styles/` を参照しているので、リポジトリの外へコピーすると動かない。

## 1. 作業前の確認

```
git status --short
```

`src/styles/palette.css` に未コミットの変更があれば、**上書きする前にユーザーへ伝える。**

```
palette.css に未コミットの変更があります。差し替えると上書きされます。
先にコミットしますか、それともこのまま進めますか？
```

**勝手にコミットも stash もしない。** 気に入らなかったときに戻せることが、配色を気軽に試せることの前提である。その前提を Claude の判断で消費しない——コミットするかどうかは、そのユーザーの作業の文脈でしか決められない。

## 2. 入力を読む

入口は2系統ある。どちらから来たかで、対応づけがどれだけ確実かが変わる。

| 入口 | 進め方 |
| --- | --- |
| **shadcn 系の CSS 変数**（`theme.css`、`:root { --background: … }`） | 変数名で機械的に拾える。手順3の表をそのまま当てる |
| **名前付きパレット**（色のリスト、「Lava Paper `#e7e5dc`」のような名前付きの色） | 名前と用途の説明から役割を推測する。**推測になるので、対応づけをユーザーに見せて確認する** |

**色形式を手で直さない。** テーマは hex / `rgb()` / `hsl()` / `oklch(92.1% …)` で配られるが、同梱スクリプトはどれもそのまま読み、`oklch(L C H)` に正規化して出力する。アルファ付きの値も読めて、警告として報告される。手で変換すると、そこが誤差と誤写の入り口になる。

ただし **`palette.css` に書く段階では `oklch(L C H)`（L は 0..1 の小数、アルファ不可）でなければならない**（手順7）。この変換もスクリプトの出力を写すだけで済む。

**ライトとダークの片方しか無いテーマは、反転で自動生成しない。** `palette.css` はライトとダークを独立に置く設計である（rev 9章）。片方が無いなら、もう片方の値から候補を起こしてユーザーに確認する——現行の `.dark` が「ライトの反転ではなく独立に置いた値」であることが、そのまま理由になっている。

**Web からテーマを取りに行かない。** 入力は貼られた内容かファイルパスだけである。

## 3. 役割へ対応づける（拾うのは7色だけ）

**ここがこの Skill の中心である。**

`src/index.css` は shadcn の31トークンをすべて役割トークンから導出しているので、外部テーマの31変数のうち facet が使うのは次の7つに対応するものだけである。

| 外部テーマ | facet の役割 | 備考 |
| --- | --- | --- |
| `background` | `canvas` | 地（方眼紙を敷く面）。**L だけ拾い、C は 0 にする**（下の「地は無彩色」） |
| `card` / `popover` | `surface` | 両者が違う値なら `card` を採る。同じく L だけ |
| `muted` | `surface-muted` | 一段沈んだ面（選択中・種類見出し・見送りの箱）。同じく L だけ |
| `foreground` | `ink` | 同じく L だけ |
| `muted-foreground` | `ink-muted` | 同じく L だけ |
| `border` / `input` | `rule` | 両者が違う値なら `border` を採る。同じく L だけ |
| `destructive` | `invalid` | **色相を確認する。手順4を見る** |

**地は無彩色。** facet は「色を持つのは意味だけ」（rev 9章 規約1・6）で、面・文字・線は
C ≤ 0.01 でなければならない（`palette.test.ts` の `ACHROMATIC` が弾く）。テーマの地が
暖色でも寒色でも、**明度だけを拾って C は 0 に置く**。テーマの「雰囲気」を facet に
持ち込めるのは意味色の4つ（`missing` / `invalid` / `pending` / `judge-yes`）だけである。

### 残る24変数は捨てる

**捨てるのは手抜きではなく設計である。** `index.css` の導出はこう決まっている（rev 9章）:

```css
/* ボタン・選択状態。primary は ink に紐づけるが、facet は塗りボタン
   （default variant）を使わない（M21。conventions.test.ts が弾く）。
   shadcn の他の部品（メニューの選択行等）が accent / muted を参照するので、
   「一段沈んだ面」をそこへ流す */
--primary: var(--ink);

/* フォーカスリング。**judge-yes を当てない**——「いまフォーカスがある」と
   「支持した」は別の意味であり、同じ色にすると型区別が薄まる */
--ring: var(--ink);
```

テーマの `primary` を持ち込むことは、この決定を壊すことを意味する。`accent` / `secondary` / `ring` / `chart-*` も同じ理由で捨てる。

**帰結をユーザーに伝えること。** テーマの印象は多くの場合 `primary` が担っているが、facet ではその色がどこにも現れない。

```
Amber Minimal から拾うのは背景・面・文字・境界・destructive の7色だけです。
このテーマの琥珀色（primary / accent）は facet のどこにも出ません。
ボタンもフォーカスリングも ink（文字色）のままです。
```

これを報告に書かないと、差し替え後に「テーマが反映されていない」という誤診が生まれる。**先に言えば仕様、後で聞かれたら不具合に見える。**

### 対応表を1対1で信じない

テーマによっては `card` が `background` と同値だったり、`muted-foreground` が本文と区別できない明度だったりする。拾った値をそのまま信じず、手順6で全要件を測る。`card` と `background` が同値だった場合は、`canvas` と `surface` が同じ色になる（方眼の有無でしか区別できなくなる）ので、ユーザーに伝えて `surface` をわずかに離すか確認する。

## 4. `destructive` を疑う

**入力を鵜呑みにしない。配布物が壊れていることは実際にある。**

例：過去に使った Morphos の `theme.css` は `destructive` が Primary で上書きされる生成ミスがあった。そのまま入れると**「削除」が緑になる**。

`palette.test.ts` は `--destructive: var(--invalid)` の紐づきを検査するが、**それはトークンの紐づけを見るだけで、色そのものが赤系かは見ていない。** だから Skill 側で確認する。

- 拾った `destructive` の色相が `judge-yes` 候補の色相（緑）に近いなら、**テーマの生成ミスを疑ってユーザーに確認する**
- テーマに `destructive` が無い場合も、候補を出して聞く

判定の道具は手順6の出力にある。トークン一覧の `oklch(L C H)` 列で `invalid` と `judge-yes` の H が近ければ怪しく、末尾の ΔE 行の `normal` が小さければ**両者はほぼ同じ色である**（現行配色でライト `invalid / judge-yes` の `normal=0.535`）。

## 5. 対応物がない13個を決める

| 役割 | 扱い | 導出の規則（候補の作り方） |
| --- | --- | --- |
| `missing` | **必ず聞く** | 黄系（H 70〜95）。白地で 4.5:1 を満たすと黄土色になる——これは仕様（rev 9章 役割トークンの欠落軸）。テーマに warning / caution 系があれば候補に |
| `pending` | **必ず聞く** | 青系（H 230〜260）。テーマに info 系があれば候補に |
| `judge-yes` | **必ず聞く** | 明るい緑の面（L 0.80 以上、C 0.06〜0.10）。テーマに success / positive 系があれば、その色相から起こす。**青緑寄り（H 150〜170）にすると P型・D型で赤・黄土から離れる** |
| `judge-yes-fg` | 既定値を示して確認 | `judge-yes` の面に 4.5:1 で載る暗い無彩色（`ink` 相当） |
| `judge-no` | 既定値を示して確認 | チャコール（L 0.33〜0.38、C 0）。`judge-yes` と 3:1 以上離す（`FACE_PAIRS`） |
| `judge-no-fg` | 既定値を示して確認 | `judge-no` の面に 4.5:1 で載る明るい無彩色（`surface` 相当） |
| `grid` | 既定値を示して確認 | 方眼専任。`canvas` に寄せた薄い無彩色。**ライトは `canvas` 上 1.2:1、ダークは 1.06:1 を目安にする**（M27 の実機） |
| `rule-muted` | 既定値を示して確認 | 表の罫線・弱い境界（M27 で `grid` から分離）。**ライトは `grid` と同値でよい**。ダークは `surface` の上で見える明るさに置く（M27 の実機は `surface` 上 1.8:1）——ダークでは `canvas` と `surface` が線を挟むため、方眼と罫線は1値で両立しない |
| `ink-faint` | 既定値を示して確認 | `ink-muted` からさらに一段動かす——ライトはより明るく、ダークはより暗く。3面（`canvas` / `surface` / `surface-muted`）で 3:1 |
| `missing-face` / `invalid-face` / `pending-face` | 既定値を示して確認 | **同じ軸の線色と同じ色相**で、L 0.93〜0.96（ダーク 0.28〜0.32）、C 0.035〜0.06 の淡い面。`ink` / `ink-muted` / その軸の線色の3つが 4.5:1 で載ること（`FACE_REQUIREMENTS`）。色相を線色から動かさない——面と線が別の色になると「同じ軸の2段」に見えなくなる |
| `judge-yes-face` | 既定値を示して確認 | **`judge-yes` と同じ色相**で、L 0.93〜0.96（**ダーク 0.26〜0.27**）、C 0.04〜0.06 の淡い緑。課題ツリーの「解決した課題の箱」の地（issue-tree-m5）。**上の3面と載る色が違う**——4色が載る: `ink` / `ink-muted`（4.5:1）と、**`rule`**（箱の枠。判断軸には線色のトークンが無い）／**`ink-faint`**（抑制された仮説行の点と文言。**この面だけが「箱の地」で、抑制された内容がその上に乗る**）の2つが 3:1（`FACE_REQUIREMENTS`。どちらも文字ではなく枠・非アクティブなので 3:1）。**ダークの拘束条件は `rule` ではなく `ink-faint` である**——`ink-faint`（L 0.55）は `rule`（L 0.56）よりわずかに暗いので先に割れる。実測: **L 0.28 では `rule` 3.072 で通るが `ink-faint` 2.946 で落ちる**（境目は L 0.275 ＝ 2.996）。**`rule` だけを見て L を選ばないこと**——通ってしまう値でも `ink-faint` を割る |

**黄と赤は D型色覚では色相で分かれない。** `missing` と `invalid` は**明度で**分ける
（`invalid` を一段暗く）。`palette-fit.mjs` の「意味色の識別」が標準・P型・D型の全部で
ΔE ≥ 0.10 を要求する。満たせなければ `palette-requirements.ts` の `DISTINCT_MIN` を
0.08 まで下げてよいが、理由と実測値をその隣に書く。

`missing` / `pending` / `judge-yes` / `judge-yes-fg` / `judge-no` / `judge-no-fg` / `grid` / `rule-muted` / `ink-faint` / `missing-face` / `invalid-face` / `pending-face` / `judge-yes-face` には、shadcn 系テーマに対応物が無い。**AI が黙って決めない。**

ただし13個を一律に聞くと会議が止まる。**判断の重さで分ける。**

**`missing` / `pending` / `judge-yes` を必ず聞くのは、これらが意味を持つ色だからである。** facet は「欠落・無効・着信」の3系統と「支持・棄却」の判断軸で状態を区別する（rev 9章）。`invalid` は手順3で `destructive` から拾える。残る `missing` / `pending` / `judge-yes` には対応物が無く、色を選ぶこと自体が意味の割り当てになるため、AI が黙って決めてはならない。残り10個（`judge-yes-fg` / `judge-no` / `judge-no-fg` / `grid` / `rule-muted` / `ink-faint` / `missing-face` / `invalid-face` / `pending-face` / `judge-yes-face`）は装飾か派生であり、上の規則から導出できる——**淡い面4つは意味色ではなく、聞いて決めた色からの派生である**（同じ色相のまま白／黒へ寄せるだけ。3つは線色から、`judge-yes-face` は `judge-yes` の面から）。

**確認が取れない状況（非対話実行など）では、候補のうち最有力のものを採って進め、報告に「こちらの判断で決めた」トークンとして明示する。** 聞くのをやめてよいという意味ではない。**目的は黙って確定させないことであって、聞くこと自体ではない**——聞けないなら事後に見せて、ユーザーが却下できるようにする。`palette.css` はバージョン管理されたソースなので、気に入らなければ差し戻せる（手順1）。**逆に、ここで止まると差し替え全体が進まない。** この逃げ道が使えるのは報告で名指しした場合だけであり、名指しを落とすと「必ず聞く」を骨抜きにしたことになる（手順9）。

**`missing` / `invalid` / `pending` そのものを面にしない。** 欠落・無効・着信が持つ面は淡い面（`*-face`）だけで、線色そのものは線と文字に使う（rev 9章 規約2）。濃い面を持つのは判断（`judge-yes` / `judge-no`）だけである——淡い面と濃い面が明度で分かれることが、「開いている」と「決着した」の区別になっている。**例外は `judge-yes-face`**（決着したものに付く唯一の淡い面。issue-tree-m5）——濃い面はバッジのような小さな面のためのもので、箱1つの地として敷くと強すぎるため、同じ緑を淡くした面を別に持つ。「決着＝濃い」の読み取りはバッジの側が保つ。

`grid` の 1.2:1 は M8 の実機確認で 1.36:1 から薄めた値である。**会議で投影したときに方眼がうるさくない濃さ**が基準であって、読みやすさの基準ではない。`grid` はコントラストの検査対象には入っていない（無彩色の検査には入る）ので、この目安を自分で守る。

## 6. 検算する

```
node .claude/skills/palette-retheme/scripts/palette-fit.mjs --in <path>
```

| `<path>` | 読み方 |
| --- | --- |
| `.css` | `palette.css` として読む（`:root` と `.dark` の両ブロック） |
| `.json` | 下書きとして読む |

**現行配色を基準に取りたいときは `--in src/styles/palette.css`。** 差し替え前に走らせておくと、「どこがどれだけ余裕を持っていたか」が分かる。1トークンだけ微調整するときも、下書きを起こさずこれで足りる。

下書き JSON の形（**20トークン×2モードすべて**が要る。値は hex / `rgb()` / `hsl()` / `oklch()` のどれでもよい）:

```json
{
  "light": {
    "canvas": "oklch(0.95 0 0)",
    "surface": "oklch(0.985 0 0)",
    "surface-muted": "oklch(0.91 0 0)",
    "ink": "oklch(0.18 0 0)",
    "ink-muted": "oklch(0.42 0 0)",
    "ink-faint": "oklch(0.58 0 0)",
    "rule": "oklch(0.58 0 0)",
    "rule-muted": "oklch(0.89 0 0)",
    "grid": "oklch(0.89 0 0)",
    "missing": "oklch(0.49 0.10 85)",
    "invalid": "oklch(0.38 0.15 30)",
    "pending": "oklch(0.48 0.135 250)",
    "missing-face": "oklch(0.95 0.06 90)",
    "invalid-face": "oklch(0.93 0.035 25)",
    "pending-face": "oklch(0.94 0.03 250)",
    "judge-yes": "oklch(0.87 0.08 165)",
    "judge-yes-fg": "oklch(0.18 0 0)",
    "judge-yes-face": "oklch(0.95 0.045 165)",
    "judge-no": "oklch(0.35 0 0)",
    "judge-no-fg": "oklch(0.985 0 0)"
  },
  "dark": { "...": "同じ20キー" }
}
```

**下書きは一時ファイルに書く。** リポジトリの中に置くと `git status` に混ざり、手順1で見た「綺麗な作業ツリー」が意味を失う。

終了コードは **0＝全要件を満たす／1＝1つでも満たさない／2＝使い方の誤り**（`--in` が無い、拡張子が違う、トークンが足りない、色として読めない）。

**終了コードが 0 なら `npm test` も通る。** スクリプトと `palette.test.ts` は要件テーブル（`src/styles/palette-requirements.ts`）と計算式（`src/styles/contrast.ts`）を共有していて、検算と検証が同じものを見ている。だから**0 になるまでここで回すのが最短**で、テストを走らせながら直すのは遠回りである。

### 出力の読み方

要件を満たさない行は `✗` で、**コントラスト**と**面の文字**の節では直し方が付く（**色域**の節も「C を下げる」とだけ付く）。**面どうし**・**無彩色**・**意味色の識別**の3節には付かない（下で説明する）。

```
  コントラスト
    ✓ ink         / canvas    16.25:1  (>= 4.50)
    ✓ ink-muted   / canvas     7.31:1  (>= 4.50)
    ✗ rule        / canvas     1.24:1  (>= 3.00)  → L を 0.928 から 0.661 へ
    ✗ rule        / surface-muted  1.24:1  (>= 3.00)  → L を 0.928 から 0.661 へ
    ✗ missing     / canvas     3.76:1  (>= 4.50)  → L を 0.637 から 0.586 へ
    ✗ invalid     / canvas     3.74:1  (>= 4.50)  → L を 0.450 から 0.397 へ

  面の文字
    ✗ judge-yes-fg/ judge-yes  3.76:1  (>= 4.50)  → この色相・彩度では満たせない（彩度を下げるか色を変える必要がある）

  面どうし
    ✗ judge-yes   / judge-no   2.10:1  (>= 3.00)

  無彩色（C <= 0.01）
    ✗ ink-faint   C = 0.0230

意味色の識別（ΔE >= 0.1、標準 / P型 / D型）
  ✓ ライト   missing / invalid     normal=0.160  protan=0.173  deutan=0.108
  ✗ ライト   missing / pending     normal=0.240  protan=0.220  deutan=0.062

要件を満たさない項目が 7 件あります。
```

（例。下書き段階の値。実際の数字は差し替えるテーマごとに変わる）

**提案された L はそのまま採用してよい。** 閾値ちょうどではなく 3% の余裕を含んだ値で、`canvas` / `surface` / `surface-muted` の3面の条件を同時に満たすものが選ばれている（1面ずつ直すと、直した先が他の面を割る）。

**面どうしには提案が出ない。これは仕様である。** `judge-yes` と `judge-no` はどちらも意味を持つ面（支持／棄却）なので、**どちらを動かすかは人の判断**だから出さない。

**無彩色にも提案が出ない。** 直し方は常に同じ（C を 0 にする）ので、計算するまでもない。

**色域は「書いた C と、実際に出る C が一致するか」を見る。** `oklch()` は sRGB より広いので、C を上げすぎた値はブラウザが sRGB へクランプする。クランプされてもコントラストも ΔE も通ってしまうため、**「C 0.12 の黄土」と書いたまま 0.102 の色が出ている**状態は、この節でしか見つからない（M21 のライトの `missing` が実際にそうだった）。`✗` が出たら、その行の「→」が示すとおり **C を下げる**——L は動かさない。

**意味色の識別（ΔE）は合否の対象である。** 標準・P型・D型のすべてで `DISTINCT_MIN`（既定 0.1）以上を要求する。満たせない組み合わせがあれば、`missing` / `invalid` / `pending` / `judge-yes` のどれかの色相か明度を動かす。それでも満たせないときの逃げ道は手順9にある。

**「この色相・彩度では満たせない」は、動かせる側が振り切れているという意味である。** 上の例では `judge-yes-fg` がこの色相・彩度の範囲では 4.5:1 に届かない。直すのは面の側（`judge-yes` を暗くする）か、彩度を下げるかである。

**淡い面（`*-face`）の行だけは、提案どおりに直さない。** 「面の文字」の節には `ink / missing-face`・`missing / missing-face` のような行が**13本**出る（3面×3色 ＋ `judge-yes-face` だけ4色）が、そこに出る提案は**文字側の L を動かせ**という内容である。`ink` も `ink-muted` も、面に載る残りの色（3面は線色1つ、`judge-yes-face` は `rule` と `ink-faint` の2つ）も他の面に縛られているので、動かすのは**面（`*-face`）の L の方**——ライトなら明るく、ダークなら暗くする（手順5の範囲: L 0.93〜0.96 / 0.26〜0.32）。

### 直し方の原則

**明度（L）だけ動かす。色相（H）と彩度（C）は保つ。** テーマの性格は H と C が持っており、そこを動かすと「そのテーマを入れた」と言えなくなる。M7 も同じ方針で Morphos の値を調整した。

**`grid` は持ち上げない。** 方眼紙の線は装飾であり、薄いことに意味がある（手順5）。検査対象に無いのは忘れられたからではなく、意図的に外してあるからである。

**1つ直すと別の行が動く。** `missing` や `invalid` を動かせば意味色の識別の ΔE が変わり、`canvas` を動かせば全部が変わる。**終了コードが 0 になるまで繰り返す。**

## 7. `palette.css` を書く

**Claude が `Edit` で値を差し替える。** スクリプトに書かせない——そういう機能を持たせていない。

理由は**このファイルはコメントが情報の本体だから**である。ヘッダー（禁止事項・役割の定義・由来）に加えて、各行が由来を持つ:

```css
--rule: oklch(0.58 0 0);                /* surface-muted 上でも 3:1 */
--ink: oklch(0.85 0.007 88.6);          /* Ash Surface をそのまま置くと 16.79:1 で眩しい */
```

**値だけ差し替えて由来コメントが古いまま残るのは、コメントが消えるより悪い。** 次に読む人が誤った出所を信じる。だから **値の差し替えと由来コメントの書き直しを同じ編集で行う。**

書き直す対象は3種類ある。

| 対象 | 書き直し方 |
| --- | --- |
| 各行の末尾コメント（例: `/* Amber Minimal の border から */`） | 新しいテーマの語彙に置き換える。元の色名が分からないなら書かない（**古い名前を残すより空の方がよい**） |
| 調整の理由（`/* Ember Fault を 4.5:1 超へ */`） | 今回動かした量と理由に書き直す。動かさなかったなら理由の記述ごと消す |
| ヘッダの由来の段落 | 新しいテーマの出所・拾い方・調整方針に書き換える |

書式の制約（`palette.test.ts` が弾く）:

- **`oklch(L C H)` の形。L は 0..1 の小数で、`%` 表記は不可。アルファも不可**（手順6の出力の `oklch(…)` 列がそのまま使える。末尾の 0 は `oklch(0.6 0.014 120)` のように削ってよい）
- `:root`（ライト）と `.dark` の両方を埋める。**トークンを増やさない・減らさない**

**色値以外を書かない。** 半径・余白・フォント・行間は `palette.css` の禁止事項である。テーマの `--radius` を持ち込まない——配色の差し替えがレイアウトや書体の差し替えを巻き込まなくするための境界であり、境界を1回越えると次から誰も守らない。

書き終えたら、**書いた `palette.css` そのものをもう一度検算する。**

```
node .claude/skills/palette-retheme/scripts/palette-fit.mjs --in src/styles/palette.css
```

下書きが 0 でもここが 0 とは限らない——写し間違いは起こる。この1回で、テストが赤になったときに疑う先が「値」ではなく「書式か、触った他のファイル」に絞られる。

## 8. テストを走らせる

```
npm test
```

**対象を絞らない。** `palette.test.ts` だけを走らせると足りない:

- `conventions.test.ts` — 色値の直書きを機械的に弾く。手順7で `palette.css` 以外に色を書いてしまっていないかは、ここでしか分からない
- `contrast.test.ts` — スクリプトが使っている計算式そのもののテスト

赤なら手順6に戻る。**スクリプトが 0 を返しているのにテストが赤なら、原因は色値ではない**（書式か、`palette.css` 以外に触った箇所か）ので、そこを疑う。

仕上げに `npx tsc -b` と `npm run lint` も通す。

## 9. 報告する

「テストが緑」だけでは足りない。次の4つを表で見せる。

1. **元テーマの値 → 採用値**、および動かした量（どのトークンの L をいくつからいくつへ、なぜ）
2. **捨てたテーマ色**（`primary` / `accent` / `secondary` / `ring` / `chart-*`）と、その帰結（手順3。「このテーマの主張色は facet に出ない」）
3. **意味色4色（`missing` / `invalid` / `pending` / `judge-yes`）の ΔE**（標準色覚・P型・D型、ライト／ダーク、6ペアすべて）
4. **候補から選んでもらった13個**の最終値。**ユーザーに確認せずこちらの判断で決めたものがあれば、どれをどの候補から採ったかを名指しする**（特に `missing` / `pending` / `judge-yes`。手順5の非対話の逃げ道は、この名指しとセットでしか成立しない）

**3 を必ず出す。** M21 で ΔE は合否の対象になった（`palette-requirements.ts` の `DISTINCT_MIN`）ので、満たさなければ手順6のスクリプトも `npm test` も赤になり、勝手には先へ進めない。それでも**数字そのものは報告に書く**——全部 0.10 以上で通っていたのか、`DISTINCT_MIN` を下げて通したのかは、次にこの配色を触る人が知るべき情報である。

## 10. 迷ったときの原則

**計算はスクリプトへ、判断はヒアリングへ。** この Skill の手順はこの境界で切ってある。

| 種類 | 中身 | 誰がやるか |
| --- | --- | --- |
| 計算 | 色形式の正規化、コントラストの実測、明度の調整 | スクリプト（人にも AI にも暗算できない） |
| 判断 | 役割への対応づけ、意味論の維持、意味色の選定 | ユーザー（機械には決められない） |

**この境界を跨がない。** AI が色を「見繕う」のは、判断を計算のふりでやることである。

**意味を持つ4系統の意味論は、色値が変わっても維持する。**

| 役割 | 意味（rev 9章） |
| --- | --- |
| `canvas` / `surface` / `surface-muted` | 地／作業する面／一段沈んだ面（無彩色） |
| `ink` / `ink-muted` / `ink-faint` | 文字（無彩色。faint は 3:1、本文に使わない） |
| `rule` / `grid` | 罫線（3:1）／方眼（装飾） |
| `missing` | 欠落（未定義・未決・仮説なし・保留）。黄。線と文字 |
| `invalid` | 無効（重複・参照切れ・整合性違反）。赤。線と文字。削除のホバーにだけ借りる |
| `pending` | 着信（返答していない入力＝未判断）。青。線と文字 |
| `missing-face` / `invalid-face` / `pending-face` | 上の3軸の**淡い面**。同じ色相の、線色と文字が載る明るさの面 |
| `judge-yes` / `judge-yes-fg` | 支持の**濃い**面（緑）とその文字 |
| `judge-no` / `judge-no-fg` | 棄却の**濃い**面（無彩色）とその文字 |

差し替えるのは色であって、割り当てではない。「このテーマでは削除が青系だから `invalid` は青」は、色を変えたのではなく意味を変えている。

**`grid` は装飾なので薄いことに意味がある。** コントラストを上げる方向に「調整」しない。他のトークンと違って基準が「読めること」ではなく「うるさくないこと」なので、良かれと思った調整が要件の改善に見えて劣化になる。

**迷ったら、測ってから聞く。** 数字を添えた選択肢は1往復で決まるが、印象だけの提案は何往復も戻ってくる。

## やらないこと

- **`src/index.css` を触らない。** 31トークンの紐づけ（`--primary: var(--ink)` 等）は rev 9章の確定事項であり、Skill が触ってよい範囲の外である
- **`palette.css` に色値以外を書かない。** 半径・フォント・余白・行間は同ファイルの禁止事項。テーマの `--radius` を持ち込まない
- **淡い面（`*-face`）を濃くしない。** 濃い面は判断軸（`judge-yes` / `judge-no`）に専有させてある（rev 9章 規約2）。「もっと目立たせたい」で L を下げると、開いているものと決着したものが明度で分かれなくなる。目立たせる手は線種と線色の側にある
- **地に彩度を持ち込まない（テーマの地色の C を拾わない）。** `canvas` / `surface` / `surface-muted` / `ink` / `ink-muted` / `ink-faint` / `rule` / `grid` / `judge-no` / `judge-no-fg` は C ≤ 0.01 でなければならない（手順3）
- **スクリプトに `palette.css` を書かせない。** 由来コメントが消える。書き込みは `Edit` で、コメントの書き直しと同時に行う（手順7）
- **Web からテーマを取ってこない。** 入力は貼られた CSS / JSON かファイルパスだけ。取得先の知識を持たせると、サイト側が変わった瞬間に腐る
- **画像から色を拾わない**
- **ΔE の閾値を黙って下げない。** `DISTINCT_MIN` を動かすときは、`palette-requirements.ts` のその定数の隣に理由と実測値を書く（設計スペック 決定5）
- **色見本 HTML を作らない。実機での見た目確認を完了条件にしない。** 完了条件は `npm test` が緑になることである
- **`palette.css` に未コミットの変更があるとき、勝手にコミットや stash をしない**（手順1）
