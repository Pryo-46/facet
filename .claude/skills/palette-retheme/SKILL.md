# 配色差し替え

外部テーマ（shadcn 系の `theme.css`、Morphos の `theme.json`、色のリスト）を受け取り、`src/styles/palette.css` の12トークン×2モードを埋めて、`npm test` が緑になる状態まで持っていく。

**この Skill が触るのはアプリ自身のソースである。** 同じディレクトリにある `glossary-term-register` / `error-catalog-register` は**ユーザーのデータ**（プロジェクトフォルダの JSON）を作る Skill で、アプリは AI が触ったことを知らない。こちらは**アプリのリポジトリの中身**を書き換える。既存2本の形を期待して読むと、無いものを探すことになる:

- **スキーマは無い。** 検証するのは JSON Schema ではなく `src/styles/palette.test.ts` である
- **正規形で書き出すスクリプトは無い。** 同梱スクリプトは**測るだけ**で、`palette.css` を書くのは Claude の `Edit` である（手順7に理由を書く）
- **やり直しの手段が git である。** だから作業前に作業ツリーが綺麗であることを確かめる（手順1）

**色値を持ってよいのは `src/styles/palette.css` だけである。** `src/index.css` は shadcn の31トークンを**すべて役割トークンから導出**しており、色値を1つも持たない。この二層構造があるから、配色の差し替えは1ファイルの書き換えで済む。**差し替えの作業がこの構造を壊してはならない**——`palette.css` に外部テーマの色を並べたつもりで `index.css` の導出を書き換えると、以後どちらが正か分からなくなる。

## 全体の流れ

**番号は下の手順の節番号と一致させてある。** 「手順N」という言及はすべて節番号を指す。

1. 作業ツリーが綺麗か確認する
2. 渡されたテーマを読む
3. facet の役割へ対応づける（**拾うのは6色だけ**）
4. `destructive` が本当に警告色か疑う
5. 対応物がない6つ（`ok` / `surface-accent` / `grid` / `warning-fg` / `ok-fg` / `ink-faint`）をユーザーと決める
6. 下書き JSON を作り、同梱スクリプトで検算する（**終了コード 0 になるまで**）
7. `palette.css` を `Edit` で書き換える（**由来コメントも同じ編集で書き直す**）
8. `npm test` を走らせる
9. 報告する

以下の `node` コマンドは**リポジトリのルート**（`package.json` があるディレクトリ）で実行する。スクリプトは相対パスで `src/styles/` を参照しているので、リポジトリの外へコピーすると動かない。

## 1. 作業前の確認

```
git status --short
```

`src/styles/palette.css` に未コミットの変更があれば、**上書きする前にユーザーへ伝える。**

```
palette.css に未コミットの変更があります。差し替えると上書きされます。
先にコミットしますか、それともこのまま進めますか？
```

**勝手にコミットも stash もしない。** 気に入らなかったときに戻せることが、配色を気軽に試せることの前提である。その前提を Claude の判断で消費しない——コミットするかどうかは、そのユーザーの作業の文脈でしか決められない。

## 2. 入力を読む

入口は2系統ある。どちらから来たかで、対応づけがどれだけ確実かが変わる。

| 入口 | 進め方 |
| --- | --- |
| **shadcn 系の CSS 変数**（`theme.css`、`:root { --background: … }`） | 変数名で機械的に拾える。手順3の表をそのまま当てる |
| **名前付きパレット**（Morphos の `theme.json`、色のリスト、「Lava Paper `#e7e5dc`」） | 名前と用途の説明から役割を推測する。**推測になるので、対応づけをユーザーに見せて確認する** |

**色形式を手で直さない。** テーマは hex / `rgb()` / `hsl()` / `oklch(92.1% …)` で配られるが、同梱スクリプトはどれもそのまま読み、`oklch(L C H)` に正規化して出力する。アルファ付きの値も読めて、警告として報告される。手で変換すると、そこが誤差と誤写の入り口になる。

ただし **`palette.css` に書く段階では `oklch(L C H)`（L は 0..1 の小数、アルファ不可）でなければならない**（手順7）。この変換もスクリプトの出力を写すだけで済む。

**ライトとダークの片方しか無いテーマは、反転で自動生成しない。** `palette.css` はライトとダークを独立に置く設計である（rev 9章）。片方が無いなら、もう片方の値から候補を起こしてユーザーに確認する——現行の `.dark` が「ライトの反転ではなく独立に置いた値」であることが、そのまま理由になっている。

**Web からテーマを取りに行かない。** 入力は貼られた内容かファイルパスだけである。

## 3. 役割へ対応づける（拾うのは6色だけ）

**ここがこの Skill の中心である。**

`src/index.css` は shadcn の31トークンをすべて役割トークンから導出しているので、外部テーマの31変数のうち facet が使うのは次の6つに対応するものだけである。

| 外部テーマ | facet の役割 | 備考 |
| --- | --- | --- |
| `background` | `canvas` | 地（方眼紙を敷く面） |
| `card` / `popover` | `surface` | 両者が違う値なら `card` を採る |
| `foreground` | `ink` | |
| `muted-foreground` | `ink-muted` | |
| `border` / `input` | `rule` | 両者が違う値なら `border` を採る |
| `destructive` | `warning` | **色相を確認する。手順4を見る** |

### 残る25変数は捨てる

**捨てるのは手抜きではなく設計である。** `index.css` の導出はこう決まっている（rev 9章）:

```css
/* ボタンが緑になると ok（確定）と意味が衝突する */
--primary: var(--ink);
/* 「いまフォーカスがある」と「確定した」は別の意味 */
--ring: var(--ink);
```

テーマの `primary` を持ち込むことは、この決定を壊すことを意味する。`accent` / `secondary` / `ring` / `chart-*` も同じ理由で捨てる。

**帰結をユーザーに伝えること。** テーマの印象は多くの場合 `primary` が担っているが、facet ではその色がどこにも現れない。

```
Amber Minimal から拾うのは背景・文字・境界・destructive の6色だけです。
このテーマの琥珀色（primary / accent）は facet のどこにも出ません。
ボタンもフォーカスリングも ink（文字色）のままです。
```

これを報告に書かないと、差し替え後に「テーマが反映されていない」という誤診が生まれる。**先に言えば仕様、後で聞かれたら不具合に見える。**

### 対応表を1対1で信じない

テーマによっては `card` が `background` と同値だったり、`muted-foreground` が本文と区別できない明度だったりする。拾った値をそのまま信じず、手順6で全要件を測る。`card` と `background` が同値だった場合は、`canvas` と `surface` が同じ色になる（方眼の有無でしか区別できなくなる）ので、ユーザーに伝えて `surface` をわずかに離すか確認する。

## 4. `destructive` を疑う

**入力を鵜呑みにしない。配布物が壊れていることは実際にある。**

Morphos が配布する `theme.css` は `light.destructive` が Primary（Lichen Green）で上書きされる生成ミスを持っており、そのまま入れると**「削除」が緑になる**。M7 で実際に踏んだ。

`palette.test.ts` は以後 `--destructive: var(--warning)` の紐づきを検査するようになったが、**それはトークンの紐づけを見るだけで、色そのものが赤系かは見ていない。** だから Skill 側で確認する。

- 拾った `destructive` の色相が `ok` 候補の色相と近いなら、**テーマの生成ミスを疑ってユーザーに確認する**
- テーマに `destructive` が無い場合も、候補を出して聞く

判定の道具は手順6の出力にある。トークン一覧の `oklch(L C H)` 列で `warning` と `ok` の H が近ければ怪しく、末尾の ΔE 行の `normal` が小さければ**両者はほぼ同じ色である**（現行配色でライト `normal=0.151`）。

## 5. 対応物がない6つを決める

`ok` / `surface-accent` / `grid` / `warning-fg` / `ok-fg` / `ink-faint` には、shadcn 系テーマに対応物が無い。**AI が黙って決めない。**

ただし6つを一律に聞くと会議が止まる。**判断の重さで分ける。**

| 役割 | 扱い | 導出の規則（候補の作り方） |
| --- | --- | --- |
| `ok` | **必ず聞く** | 候補を3つ出す: (1) テーマに success / positive 系があればそれ、(2) `chart-*` のうち `warning` と色相が離れているもの、(3) `warning` の補色側から起こした新規色。テーマの `primary` が緑系なら候補に加える |
| `surface-accent` | 候補と既定値を示して1往復で確認 | `ok` の色相から起こした淡い面。`ink` と `ink-muted` の**両方**が 4.5:1 で載ること |
| `grid` | 既定値を示して確認 | `rule` の色相を保ったまま `canvas` に寄せた薄い線。**ライトは `canvas` 上 1.17:1 を目安にする** |
| `warning-fg` / `ok-fg` | 既定値を示して確認 | それぞれの面に 4.5:1 で載る文字。面が明るければ暗い方（`canvas` 相当）、暗ければ明るい方（`surface` 相当）を当てる |
| `ink-faint` | 既定値を示して確認 | **外部テーマが持つ「抑えた前景色」は1段しかない**（facet の `ink-muted` に対応する1色のみで、さらに薄い段は無い）。新しい色相を起こさず、その1色の色相・彩度を保ったまま `ink-muted` からさらに一段動かす——ライトはより明るく、ダークはより暗く（段の向きを反転させない）。両面（`canvas` / `surface`）で 3:1 を満たすまで L を 0.01 刻みで動かす |

**`ok` だけを必ず聞くのは、これが意味を持つ色だからである。** `ok` は「応答・結果・確定」で、facet の設計思想「未定義と無効の型区別」を運ぶ3系統（`ink` / `warning` / `ok`）の1つである（rev 9章）。残り4つは装飾か派生であり、上の規則から導出できる。

**確認が取れない状況（非対話実行など）では、候補(1)——無ければ(3)——を採って進め、報告に「こちらの判断で決めた `ok`」として明示する。** 聞くのをやめてよいという意味ではない。**目的は黙って確定させないことであって、聞くこと自体ではない**——聞けないなら事後に見せて、ユーザーが却下できるようにする。`palette.css` はバージョン管理されたソースなので、気に入らなければ差し戻せる（手順1）。**逆に、ここで止まると差し替え全体が進まない。** この逃げ道が使えるのは `ok` を報告で名指しした場合だけであり、名指しを落とすと「必ず聞く」を骨抜きにしたことになる（手順9）。

**`ok` を `surface-accent` に流用しない。** 見出しの面（テーブルのカラム名）は「確定」でも「応答」でもない。M8 で別トークンとして新設した理由がこれであり、流用すると意味論が壊れる。

`grid` の 1.17:1 は M8 の実機確認で 1.36:1 から薄めた値である。**会議で投影したときに方眼がうるさくない濃さ**が基準であって、読みやすさの基準ではない。`grid` はスクリプトの検査対象にも `palette.test.ts` の検証対象にも入っていない（トークン一覧に値が出るだけ）ので、この目安を自分で守る。

## 6. 検算する

```
node .claude/skills/palette-retheme/scripts/palette-fit.mjs --in <path>
```

| `<path>` | 読み方 |
| --- | --- |
| `.css` | `palette.css` として読む（`:root` と `.dark` の両ブロック） |
| `.json` | 下書きとして読む |

**現行配色を基準に取りたいときは `--in src/styles/palette.css`。** 差し替え前に走らせておくと、「どこがどれだけ余裕を持っていたか」が分かる。1トークンだけ微調整するときも、下書きを起こさずこれで足りる。

下書き JSON の形（**12トークン×2モードすべて**が要る。値は hex / `rgb()` / `hsl()` / `oklch()` のどれでもよい）:

```json
{
  "light": {
    "canvas": "oklch(1 0 0)",
    "surface": "oklch(1 0 0)",
    "ink": "oklch(0.2686 0 0)",
    "ink-muted": "oklch(0.5555 0 0)",
    "ink-faint": "oklch(0.72 0 0)",
    "rule": "oklch(0.9276 0.0058 264.53)",
    "grid": "oklch(0.95 0.005 264.53)",
    "warning": "oklch(0.6368 0.2078 25.33)",
    "ok": "oklch(0.6 0.13 145)",
    "warning-fg": "oklch(1 0 0)",
    "ok-fg": "oklch(1 0 0)",
    "surface-accent": "oklch(0.92 0.04 145)"
  },
  "dark": { "...": "同じ12キー" }
}
```

**下書きは一時ファイルに書く。** リポジトリの中に置くと `git status` に混ざり、手順1で見た「綺麗な作業ツリー」が意味を失う。

終了コードは **0＝全要件を満たす／1＝1つでも満たさない／2＝使い方の誤り**（`--in` が無い、拡張子が違う、トークンが足りない、色として読めない）。

**終了コードが 0 なら `npm test` も通る。** スクリプトと `palette.test.ts` は要件テーブル（`src/styles/palette-requirements.ts`）と計算式（`src/styles/contrast.ts`）を共有していて、検算と検証が同じものを見ている。だから**0 になるまでここで回すのが最短**で、テストを走らせながら直すのは遠回りである。

### 出力の読み方

要件を満たさない行は `✗` で、**コントラスト**と**面の文字**の節では直し方が付く。

```
  コントラスト
    ✓ ink         / canvas    15.13:1  (>= 4.50)
    ✓ ink-muted   / canvas     4.74:1  (>= 4.50)
    ✗ rule        / canvas     1.24:1  (>= 3.00)  → L を 0.928 から 0.661 へ
    ✗ rule        / surface    1.24:1  (>= 3.00)  → L を 0.928 から 0.661 へ
    ✗ warning     / canvas     3.76:1  (>= 4.50)  → L を 0.637 から 0.586 へ
    ✗ ok          / canvas     3.74:1  (>= 4.50)  → L を 0.600 から 0.547 へ

  面の文字
    ✗ warning-fg  / warning    3.76:1  (>= 4.50)  → この色相・彩度では満たせない（彩度を下げるか色を変える必要がある）

  重ね合わせ
    ✗ ink-muted   / bg-warning/20 on canvas  3.64:1  (>= 4.63)

  見出しの面（surface-accent）
    ✗ ink-muted   / surface-accent   3.79:1  (>= 4.50)

warning と ok の色差（ΔE、合否は付けない）
  ライト   normal=0.297  protan=0.100  deutan=0.064

要件を満たさない項目が 16 件あります。
```

**提案された L はそのまま採用してよい。** 閾値ちょうどではなく 3% の余裕を含んだ値で、`canvas` と `surface` の両方の条件を同時に満たすものが選ばれている（片方ずつ直すと、直した先がもう片方を割る）。

**重ね合わせと見出しの面には提案が出ない。これは仕様である。** 重ね合わせの面の色は `warning` から来るので、直すべきは `warning` か `ink-muted` かのどちらかであり、**どちらを動かすかは人の判断**だから出さない。見出しの面も同じで、`ink` / `ink-muted` は他の要件で明度が縛られているため、動かせるのは `surface-accent` の側である。

**「この色相・彩度では満たせない」は、動かせる側が振り切れているという意味である。** 上の例では `warning-fg` が白（L=1）で、これ以上明るくできない。直すのは面の側（`warning` を暗くする）か、彩度を下げるかである。

### 直し方の原則

**明度（L）だけ動かす。色相（H）と彩度（C）は保つ。** テーマの性格は H と C が持っており、そこを動かすと「そのテーマを入れた」と言えなくなる。M7 も同じ方針で Morphos の値を調整した。

**`grid` は持ち上げない。** 方眼紙の線は装飾であり、薄いことに意味がある（手順5）。検査対象に無いのは忘れられたからではなく、意図的に外してあるからである。

**1つ直すと別の行が動く。** `warning` を暗くすれば重ね合わせの比率が変わり、`canvas` を動かせば全部が変わる。**終了コードが 0 になるまで繰り返す。**

## 7. `palette.css` を書く

**Claude が `Edit` で値を差し替える。** スクリプトに書かせない——そういう機能を持たせていない。

理由は**このファイルはコメントが情報の本体だから**である。44行のヘッダ（禁止事項・役割の定義・由来）に加えて、各行が由来を持つ:

```css
--rule: oklch(0.6 0.014 120);           /* Mineral Line の色相から導出 */
--ink: oklch(0.85 0.007 88.6);          /* Ash Surface をそのまま置くと 16.79:1 で眩しい */
```

**値だけ差し替えて由来コメントが古いまま残るのは、コメントが消えるより悪い。** 次に読む人が誤った出所を信じる。だから **値の差し替えと由来コメントの書き直しを同じ編集で行う。**

書き直す対象は3種類ある。

| 対象 | 書き直し方 |
| --- | --- |
| 各行の末尾コメント（`/* Lava Paper */`） | 新しいテーマの語彙に置き換える。元の色名が分からないなら書かない（**古い名前を残すより空の方がよい**） |
| 調整の理由（`/* Ember Fault を 4.5:1 超へ */`） | 今回動かした量と理由に書き直す。動かさなかったなら理由の記述ごと消す |
| ヘッダの「由来は Morphos の morphous-basalt」の段落 | 新しいテーマの出所・拾い方・調整方針に書き換える。Morphos 固有の生成ミスの注記も、そのテーマに該当しないなら消す |

書式の制約（`palette.test.ts` が弾く）:

- **`oklch(L C H)` の形。L は 0..1 の小数で、`%` 表記は不可。アルファも不可**（手順6の出力の `oklch(…)` 列がそのまま使える。末尾の 0 は `oklch(0.6 0.014 120)` のように削ってよい）
- `:root`（ライト）と `.dark` の両方を埋める。**トークンを増やさない・減らさない**

**色値以外を書かない。** 半径・余白・フォント・行間は `palette.css` の禁止事項である。テーマの `--radius` を持ち込まない——配色の差し替えがレイアウトや書体の差し替えを巻き込まなくするための境界であり、境界を1回越えると次から誰も守らない。

書き終えたら、**書いた `palette.css` そのものをもう一度検算する。**

```
node .claude/skills/palette-retheme/scripts/palette-fit.mjs --in src/styles/palette.css
```

下書きが 0 でもここが 0 とは限らない——写し間違いは起こる。この1回で、テストが赤になったときに疑う先が「値」ではなく「書式か、触った他のファイル」に絞られる。

## 8. テストを走らせる

```
npm test
```

**対象を絞らない。** `palette.test.ts` だけを走らせると足りない:

- `conventions.test.ts` — 色値の直書きを機械的に弾く。手順7で `palette.css` 以外に色を書いてしまっていないかは、ここでしか分からない
- `contrast.test.ts` — スクリプトが使っている計算式そのもののテスト

赤なら手順6に戻る。**スクリプトが 0 を返しているのにテストが赤なら、原因は色値ではない**（書式か、`palette.css` 以外に触った箇所か）ので、そこを疑う。

仕上げに `npx tsc -b` と `npm run lint` も通す。

## 9. 報告する

「テストが緑」だけでは足りない。次の4つを表で見せる。

1. **元テーマの値 → 採用値**、および動かした量（どのトークンの L をいくつからいくつへ、なぜ）
2. **捨てたテーマ色**（`primary` / `accent` / `secondary` / `ring` / `chart-*`）と、その帰結（手順3。「このテーマの主張色は facet に出ない」）
3. **`warning` と `ok` の ΔE**（標準色覚・P型・D型、ライト／ダーク）
4. **候補から選んでもらった6つ**の最終値。**ユーザーに確認せずこちらの判断で決めたものがあれば、どれをどの候補から採ったかを名指しする**（特に `ok`。手順5の非対話の逃げ道は、この名指しとセットでしか成立しない）

**3 を必ず出す。** `open-issues.md` に「色を差し替えるときに、青緑側（`oklch(0.470 0.075 168)` 付近）へ振る案を再検討すること」という宿題が明示的に開いている。現行配色は P型 0.050 / D型 0.041 で、実用域とされる 0.10 を大きく下回っており、**差し替えはこの宿題を片付けられる唯一の機会**である。だから毎回この数字を突きつける。

```
warning と ok の色差（ΔE）: ライト normal=0.297 / P型 0.100 / D型 0.064
D型で 0.10 を下回っています（現行の 0.041 よりは改善）。
ok を青緑側へ振ると離れますが、テーマの緑からは外れます。どうしますか？
```

（例。下書き段階の値。実際の数字は差し替えるテーマごとに変わる）

**ただし ΔE を理由に止めない。** M7 決定4 が「このテストが守るものは無い。見せるだけである」と定めており、閾値を足すのは設計判断の変更にあたる。**数字を見せるのが Skill の仕事で、判断はユーザーのものである。** 「このままでいい」と言われたらそのまま進める。

## 10. 迷ったときの原則

**計算はスクリプトへ、判断はヒアリングへ。** この Skill の手順はこの境界で切ってある。

| 種類 | 中身 | 誰がやるか |
| --- | --- | --- |
| 計算 | 色形式の正規化、コントラストの実測、明度の調整 | スクリプト（人にも AI にも暗算できない） |
| 判断 | 役割への対応づけ、意味論の維持、`ok` の色 | ユーザー（機械には決められない） |

**この境界を跨がない。** AI が色を「見繕う」のは、判断を計算のふりでやることである。

**意味を持つ3系統の意味論は、色値が変わっても維持する。**

| 役割 | 意味（rev 9章） |
| --- | --- |
| `ink` | 文字・線・ヘッダ（既定の前景） |
| `warning` | 警告・削除・未定義 |
| `ok` | 応答・結果・確定 |

差し替えるのは色であって、割り当てではない。「このテーマでは削除が青系だから `warning` は青」は、色を変えたのではなく意味を変えている。

**`grid` は装飾なので薄いことに意味がある。** コントラストを上げる方向に「調整」しない。他のトークンと違って基準が「読めること」ではなく「うるさくないこと」なので、良かれと思った調整が要件の改善に見えて劣化になる。

**迷ったら、測ってから聞く。** 数字を添えた選択肢は1往復で決まるが、印象だけの提案は何往復も戻ってくる。

## やらないこと

- **`src/index.css` を触らない。** 31トークンの紐づけ（`--primary: var(--ink)` 等）は rev 9章の確定事項であり、Skill が触ってよい範囲の外である
- **`palette.css` に色値以外を書かない。** 半径・フォント・余白・行間は同ファイルの禁止事項。テーマの `--radius` を持ち込まない
- **スクリプトに `palette.css` を書かせない。** 由来コメントが消える。書き込みは `Edit` で、コメントの書き直しと同時に行う（手順7）
- **Web からテーマを取ってこない。** 入力は貼られた CSS / JSON かファイルパスだけ。取得先の知識を持たせると、サイト側が変わった瞬間に腐る
- **画像から色を拾わない**
- **ΔE を理由に差し替えを止めない。** 数字は見せるだけで、判断はユーザーのものである（M7 決定4）
- **色見本 HTML を作らない。実機での見た目確認を完了条件にしない。** 完了条件は `npm test` が緑になることである
- **`palette.css` に未コミットの変更があるとき、勝手にコミットや stash をしない**（手順1）
