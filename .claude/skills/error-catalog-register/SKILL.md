# エラー登録

仕様整理ツール（Tauri製アプリ）のエラーカタログファイルを、ユーザーと対話しながら組み立てる。

**このSkillが紐づく対象: `type: "errorCatalog"` × `schemaVersion 1`。** スキーマが改訂されたらこのSkillも追従させる（アプリとSkillは別々にバージョン管理される成果物であり、この対応が依存関係の記録）。**特に `resolutionLevel` の enum と、同梱スクリプトが持つ警告の判定条件は、アプリ側の実装（`src/modules/error-catalog/warnings.ts` / `consistency.ts`）の複製である**——接点はファイルだけという決定（rev 4章）の帰結なので、片方だけ直さないこと。

このSkillの価値は「AIが速く書けること」ではなく、**会議の速度でユーザーの頭の中を構造化データにすること**にある。だから聞き方が本体で、ファイル書き込みは結果でしかない。

## 全体の流れ

1. 対象プロジェクトフォルダを確認し、既存のエラーカタログを探す
2. **登録するエラーをユーザーに確定させる**（資料から作る場合。ここを飛ばさない）
3. ヒアリングして各エラーの中身を埋める
4. `scripts/new-id.mjs` でIDを採番する
5. 下書きJSONを書き、`scripts/error-catalog-write.mjs` で検証＋正規形書き出しをする
6. 未記入と警告をユーザーに報告する

既存エラーへの書き足し（後から `resolutionLevel` や対応文を埋める）は「7. 書き足し」を見る。

初回のみ、Skillディレクトリで `npm install`（ajv が必要）。`ajv が見つかりません` と言われたら実行する。

## 1. 既存のエラーカタログを探す

**エラーカタログはプロジェクトにつき1つ。** ファイル名は識別子ではないので、名前ではなく中身の `type` で判別する。プロジェクトフォルダ直下の `*.json` を読み、`"type": "errorCatalog"` のものを探す。

- 見つかった → そのファイルに追記する（新しいファイルを作らない。2つあるとアプリが単一性違反として赤表示し、スクリプトも書き出し時に警告する）
- 見つからない → 新規作成する。`title` はプロジェクト名から提案してユーザーに確認する（例: 「受注管理システム エラーカタログ」。`title` はアプリのファイル一覧に出る表示名なので、後から人間が読んで何のカタログか分かる必要がある）

**アプリでそのプロジェクトを開いたまま作業しない。** アプリは自動保存でファイルを書き戻すため、同時編集になると片方の変更が消える。作業前に「アプリで開いているなら閉じてください」と一言伝える。

### 既存のエラー名を頭に入れてから候補を出す

エラーカタログが見つかったら、**全エラーの `name` を読んでから手順2に進む。** 追記のとき、これを飛ばすと既存とかぶるエラーを新規登録してしまう。

**照合に使えるのは `name` だけである。** 用語集の `aliases` にあたるものがエラーカタログには無いので、「別名で登録済みかもしれない」という逃げ道がない。読み落とした同名エラーは、そのまま重複として登録される。全件読むこと（数百件あるなら `name` だけ抜き出して眺めればよい）。

かぶったときに何をユーザーに確認するかは、手順2の「既存とかぶる候補は別枠で確認する」を見る。**新規作成の場合はこの手順は不要**（既存が無いので照合対象がない）。

## 2. 登録するエラーを人間に確定させる

**入口が2つある。** どちらから来たかで進め方が変わるので、まずどちらかを見分ける。

| 入口 | 進め方 |
| --- | --- |
| **仕様の会話の途中**（「この場合どうなる？」でエラーが1つ見つかった） | その場で1件ずつ登録する。候補一覧の提示は要らない——ユーザーが既に「これはエラーだ」と言っている |
| **既存資料を渡された**（エラーメッセージ一覧・仕様書・問い合わせ実績） | 候補を一覧で提示し、**登録するものをユーザーに確定させてから**書き込む。抽出した端から登録しない |

後者で確定を挟む理由は、**どのエラーをカタログに載せるかがカタログの設計そのもの**だから。カタログに載せたエラーは「これはサポートが答えるべき事象である」という宣言になる。文書に出てくるエラーメッセージをAIが機械的に拾った結果とは意味が違う。ユーザーだけが「これはカタログに載せる事象、これはただの実装都合」を判断できる。

副作用も具体的で、載せすぎたエラーは後から人間が1件ずつ消す作業になる。**入れるのは1往復、消すのは後で何度も、という非対称がある。**

**エラーカタログ固有の理由がもう1つある。** エラーメッセージ一覧から機械的に拾うと、**実装の都合で出るメッセージ（内部エラー・バリデーションの1文言）まで載り、サポートが読む表が使い物にならなくなる。** 載せる単位は「ユーザーが遭遇して問い合わせうる事象」であって、メッセージの文字列ではない。1つの事象に対してメッセージが3種類あるなら、それは1件である。

聞き方は1往復で済ませる。候補を列挙し、根拠（資料中のどの記述から拾ったか）を短く添えて、削るものを聞く。

```
エラーメッセージ一覧から18件を候補として拾いました。登録するものを選んでください（「全部」でもOK）。
1. ログインできない — 「認証に失敗しました」「アカウントがロックされています」
2. 取引先が見つからない — 「指定されたコードは登録されていません」
...
不要なものだけ番号で教えてください。
```

**候補には未決のものも含める。** 「この場合どうなるかは次回持ち越し」となった事象こそ、`resolutionLevel: "undecided"` ＋対応文空で登録する価値がある（決まっていないことがアプリ上に残り続ける）。ただしこれも登録するかはユーザーが決める。

**確認が取れない状況（非対話実行など）では、書いたうえで報告に「こちらの判断で入れたエラー」を明示する。** 黙って確定させないことが目的なので、聞けないなら事後に見せて削れるようにする。

### 既存とかぶる候補は別枠で確認する

手順1で読んだ既存の `name` と各候補を照合する（NFKC正規化・前後空白の除去・大文字小文字は同一視して比較する。スクリプトの重複判定がこの規則なので、ここで揃えておかないと書き出してから警告が出る）。**会話の途中で1件ずつ登録する場合もこの照合はやる**——1件でも既存とかぶれば同じことが起きる。かぶった候補は「新規候補」として出さず、別枠でユーザーに確認する:

| かぶり方 | ユーザーに確認すること |
| --- | --- |
| 既存の `name` と同じ | 同じ事象か。同じなら登録せず、書き足し（手順7）に回す。別事象なら**どちらも名前を具体的にする**（「保存できない」→「保存時に容量超過」「保存時に権限不足」） |
| 名前が粗くて衝突しそう | 引くためのキーとして機能する粒度か。粗い名前は衝突するだけでなく検索でも引けない |

同名2件を登録すると「この名前で引ける」という前提が壊れ、アプリで赤表示になる。名前を具体化するのは体裁の問題ではなく、カタログが引けるかどうかの問題である。

**ここで確定させるのは「どのエラーを載せるか」だけ。** 各エラーの中身まで1件ずつ許可を取りに行かない。中身の埋め方は手順3。

## 3. ヒアリング

埋めるのは `name` / `occurrence` / `resolutionLevel` / `causeForSupport` / `causeForSpec` / `userAction` / `supportAction` / `engineerAction`（＋必要なら `notes`）。

### 埋まらない項目は埋まらないまま書く

ここが最重要。**ユーザーが即答できない項目を粘って聞き出さない。** `resolutionLevel` は `undecided`、原因や対応文は空文字のまま書いてよい。

理由: アプリ側は `resolutionLevel === "undecided"`、空の発生タイミング、空の原因2種、そして**宣言したレベルの**空の対応文を warning としてセル単位で可視化する。埋まっていないという事実そのものが「次に決めるべきこと」の情報であり、AIが憶測で埋めるとその情報が消える。**決めていないことを消せなくするのがこのツールの思想**で、AIの穴埋めはそれを正面から壊す。

エラーカタログでは特に危ない。原因や対応文はAIが「もっともらしく」書けてしまう領域で、書けてしまうがゆえに**誰も決めていない対応手順がサポートの手順書として出力される。** 「たぶんこういう対応ですよね？」と確認するのは良い。ユーザーが「そう」と言えば確定、「まだ決めてない」と言えば空のまま。**AIの推測をユーザーの決定として記録しない。**

### ただし「転記」は推測ではない

空にするのは**推測**（出典がなく、AIが補ったもの）であって、**転記**（ユーザーの発言や渡された資料に書いてあることを写したもの）ではない。

問い合わせ実績に「取引先コードの入力ミス。正しいコードを案内して解決」と書いてあるなら、`causeForSupport` は「入力した取引先コードが未登録」でよく、`userAction` は「正しい取引先コードを入力し直す」でよく、`resolutionLevel` は `user` でよい。**それは既に人間が決めて書いたことで、空にすると情報が消えるだけ**。未記入の warning は「これから決めること」を指すためのもので、書いてあることまで未記入にすると宿題リストがノイズだらけになり、本当の未決が埋もれる。

判定は「出典を指させるか」で行う。

| 状況 | 扱い |
| --- | --- |
| 資料・発言にそう書いてある | 転記する。文言もなるべくそのまま使う |
| 資料にエラー名だけ出てきて、原因も対応も書かれていない | 空にする |
| 資料に複数の対応が混在していて、どちらとも取れる | 空にして、両方の対応を `notes` に残す |
| 会議で「未決」「持ち越し」と明記されている | 空にして、何が割れているかを `notes` に残す |

`notes` は空にする判断の理由を残す場所として使う。「なぜ空なのか」が書いてあれば、次に見た人がゼロから議論をやり直さずに済む。`notes` は検知対象外なので、空でも warning にはならない。

### まず resolutionLevel、次にそのレベルの対応文

用語集の `kind` は分類でしかないが、**`resolutionLevel` は次に聞くべきことを決める。**

1. **誰が解決するか**を聞く（`user` / `support` / `engineer` / `none` / `undecided`）
2. 決まったら、**そのレベルの対応文だけ**を聞く。他の2つは空のままでよい
3. `none` なら**3つとも聞く**——復旧不可でも「作り直してください」「この状態で進めて問題ありません」という案内は存在し、そこがサポートサイトで最も需要の高い問い合わせになる
4. `undecided` なら対応文は聞かない（誰が関与するかまだ決まっていないので、どれを埋めるべきかも決まらない）

アプリは「宣言したレベルの対応文が空」だけを黄色く塗る（関与しないレベルの空欄は塗らない）。**全レベルの対応文を一律に聞くと会議が止まり、埋めた大半は誰も読まない列になる。**

### resolutionLevel の選び方

| 値 | 意味 |
| --- | --- |
| `user` | ユーザー自身で解決できる |
| `support` | サポート対応が必要 |
| `engineer` | エンジニアの介入（データメンテ等）が必要 |
| `none` | **検討した上で**誰にも解決できない（外部サービス障害・仕様上の制約） |
| `undecided` | **まだ決めていない**（＝warning。後で埋める） |

`none` と `undecided` の違いは「決めたかどうか」。**迷ったら `undecided`。** `none` は決定の記録なので、AI が勝手に付けてよい値ではない。

**「復旧不可」は `none` ではない。** 元に戻せないだけで案内は存在する。データが消えて戻せないなら `user`（作り直してもらう）や `support`（謝罪と代替手段の案内）になる。ここを取り違えると、**サポートが最も答えたい問い合わせに答えられなくなる**——「消えたデータは戻りますか」に対して、カタログが「誰にも解決できません」としか言えない状態になる。

**原因の分類を混ぜない。** 「ユーザーがデータを消したことによるエラー」は発生原因の分類であって、対応主体の分類ではない。原因は `causeForSupport` に書く。2軸を混ぜると、`resolutionLevel` で絞り込んでも「誰が動くのか」が出てこなくなり、この列が持つ唯一の用途が失われる。

### 2つの原因の書き分け

| フィールド | 誰が読むか | 書くこと |
| --- | --- | --- |
| `causeForSupport` | サポート担当（と、その先のユーザー） | 業務レベルの原因。「入力した取引先コードが未登録」 |
| `causeForSpec` | 開発者 | 仕様レベルの原因。「取引先マスタに存在しないコードで検索 API が 404 を返す」 |

**分けた意味は出力の出し分けで回収される**（サポート向け出力に `causeForSpec` は載らない）。片方しか言えないなら片方だけ書く——**両方を埋めるために業務レベルの説明を仕様の言葉で書き直さない。** それをするとサポート向け出力が読めなくなり、分けた意味が消える。

逆も同じで、`causeForSpec` を埋めるために業務レベルの文をコピーしないこと。両方に同じ文が入っているカタログは、分かれていないカタログと同じである。

### occurrence（発生タイミング）

`occurrence` は「どの操作・どの画面で起きるか」を手で書く。「受注登録画面で保存を押したとき」のように、サポートがユーザーの話を聞いて当該行に辿り着ける粒度で書く。

**本来これは参照している側（ロジックツリーの葉やシーケンスの失敗ゾーン）から逆引きして導出すべき値だが、参照の実装がまだ無いので手入力している。** その帰結として、**このカタログは網羅性を担保しない。** 「表に載っていないエラー」を検出する手段が無いということであり、載っている件数は「これまでに誰かが気づいた数」でしかない。

だから **Skill は「これで全部です」と言わない。** 報告では「今回登録したのは N 件」とだけ言う（手順6・「やらないこと」も見る）。

### 聞き方の設計

会議の速度が前提なので、1問1答で往復を重ねない。**複数のエラーをまとめて聞き、1回の返信で複数埋まるようにする。**

例: 「以下の5件について、原因が言えるものだけ書いてください。分からないものは飛ばしてOKです」と列挙する。ユーザーが3件だけ答えたら、残り2件は空のまま登録する。

**エラーカタログでは「レベルが同じものをまとめる」が効く。** 対応主体が同じエラーは、聞くべき対応文も同じ列に入るので、1往復で複数埋まる。

```
この3件はどれもサポート対応ですか？
なら、それぞれサポートが何をするか教えてください。
```

**登録対象の確定（手順2）とは別の往復にする。** 何を載せるかはユーザーの決定なので確定が要るが、各項目を埋めるかどうかは「今わかる範囲で」でよい。ここで粘ると会議が止まる。

## 4. ID採番

```
node scripts/new-id.mjs 5
```

件数を省略すると1件。出力は1行1件で、`error_` ＋英数字10文字。

**IDを自分で書かない。** 必ずこのスクリプトの出力をそのまま使う。連番も禁止（アプリとAIが並行して要素を追加する設計なので、連番は必ず衝突する）。

**既存エラーのIDは絶対に変更しない。** 不変IDであり、将来ロジックツリーやシーケンスが `error_` のIDでこのカタログを参照する。書き換えると参照切れになる。

## 5. 書き込み

下書きJSONを一時ファイルに書き、スクリプトに渡す。**正規形（キー順・インデント・改行コード）はスクリプトが担保するので、下書きの整形に労力を割かなくてよい。**

```
node scripts/error-catalog-write.mjs --in <下書き.json> --out <プロジェクト>/エラーカタログ.json
```

既存ファイルへの追記は、既存の内容を読んで下書きに含め、全体を書き出す。**既存の `errors` の並び順を変えない**（配列順＝UIの表示順が正であり、並べ替えは意味のない diff を生む）。追加は末尾。

検証だけしたいときは `--check <ファイル>`。終了コードは 0＝成功（警告はあり得る）／1＝スキーマ検証失敗／2＝使い方の誤り。**0 でも未記入の要約と整合性の警告は出ている**ことがあるので、終了コードだけを見ず標準出力を読むこと（手順6で報告する材料はここにしか出ない）。

スキーマはスクリプトが実行時に探索する（`error-catalog.schema.json` のコピーは同梱していない。正が2つあると、片方だけ古いまま検証が通ってしまう）。見つからないと言われたら `--schema <path>` か環境変数 `FACET_ERROR_CATALOG_SCHEMA` で指定する。

構造（詳細は `error-catalog.schema.json` を読む。スキーマが正）:

```json
{
  "schemaVersion": 1,
  "type": "errorCatalog",
  "title": "○○プロジェクト エラーカタログ",
  "errors": [
    {
      "id": "error_Xk3mPq7ZaB",
      "name": "取引先が見つからない",
      "occurrence": "受注登録画面で取引先コードを入力して検索したとき",
      "resolutionLevel": "user",
      "causeForSupport": "入力した取引先コードが未登録",
      "causeForSpec": "取引先マスタに存在しないコードで検索 API が 404 を返す",
      "userAction": "取引先一覧から正しいコードを確認して入力し直す",
      "supportAction": "",
      "engineerAction": "",
      "notes": ""
    }
  ]
}
```

全キー常在。欠損ではなく空の値で未記入を表す（`causeForSupport: ""` / `supportAction: ""` / `notes: ""`）。上の例で `supportAction` と `engineerAction` が空なのは、`resolutionLevel` が `user` だから正常な状態である。

スキーマ検証に落ちたら、アプリはそのファイルを開けない（レベル1拒否）。エラーを読んで直し、再実行する。

## 6. 報告

スクリプトの出力をそのまま流さず、ユーザーが次に動ける形にして伝える。

- 登録したエラー（名前と `resolutionLevel`）
- **未記入の一覧**（未分類・空の発生タイミング・空の原因・空の対応文がそれぞれ何件・どれか）。これは失敗の報告ではなく次回の宿題リストとして渡す
- 整合性の警告があれば、何が衝突しているかと、判断が要る点

**未記入の一覧は、アプリが黄色く塗るセルと同じ条件で出す**（スクリプトの要約がそうなっている）。つまり対応文は「宣言したレベルのもの（と `none` のとき3つとも）」だけを数える。**関与しないレベルの空欄を宿題として報告しない**——それを混ぜると、ほとんどのエラーは1レベルしか関与しないため宿題リストがノイズで埋まり、本当の未決が埋もれる。

**`（未定義）` が出力に並ぶのは正常である。** Markdown 出力は空フィールドを `（未定義）` と書く仕様で、これは負債が見えている状態にほかならない。**「出力が未定義だらけなので埋めましょう」と AI が言わない**（決めていないことを消せなくするのがこのツールの思想であり、`（未定義）` はその思想が働いている証拠である）。埋めるかどうかは、次の会議でユーザーが決めることである。

警告は「アプリで赤く出るが、ファイルは開ける」状態。エラー名の重複などは、どちらを正とするかがユーザーの判断なので、勝手に片方を消さない。

## 7. 書き足し（既存エラーを埋める）

「アプリで黄色いセルを埋めたい」「あのエラーの対応方法が決まった」と言われたときの手順。

1. 既存カタログを読み、**どのエラーか**をユーザーに確定させる（名前が似ているものがあるので、勝手に選ばない）
2. 埋める項目をヒアリングする（手順3と同じ。`resolutionLevel` が `undecided` から変わるなら、新しいレベルの対応文を聞く）
3. **既存の JSON 全体を下書きに含め、該当エラーの該当フィールドだけを差し替えて**書き出す

**守ること:**

- **`id` を変えない**（不変ID。書き換えると将来の参照が切れる）
- **`errors` の配列順を変えない**（並べ替えは意味のない diff を生む）
- **触っていないエラーのフィールドを1バイトも変えない。** 「ついでに」文章を整えると、Git diff が仕様の変更履歴として読めなくなる
- 書き出したら `git diff` に出る行が意図した範囲に収まっているかをユーザーに伝える

## やらないこと

- **MCP的な書き込みツールを作らない。** アプリとの接点はファイルだけ（決定済み。蒸し返さない）
- **アプリ側の検証を代行しない。** 参照切れ検知などは他ツール側の仕事で、このSkillの管轄外
- **既存データの勝手な整形・並べ替え・言い換えをしない。** ユーザーが書いた原因文・対応文をAIが「きれいに」書き直すと、Git diff が仕様の変更履歴として読めなくなる
- **`occurrence` を他ツールから導出しない。** 参照の実装はまだ無く、導出はスキーマ改訂を伴う変更である。いま手元でそれらしく埋めても、後で本物の導出と食い違う
- **網羅性を主張しない。** 「これで全部のエラーが載りました」と言わない。網羅性はロジックツリーの葉やシーケンスの失敗ゾーンが持つべきもので、参照が実装されて初めて回収される
