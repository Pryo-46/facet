# 用語登録

仕様整理ツール（Tauri製アプリ）の用語集ファイルを、ユーザーと対話しながら組み立てる。

**このSkillが紐づく対象: `type: "glossary"` × `schemaVersion: 1`。** スキーマが改訂されたらこのSkillも追従させる（アプリとSkillは別々にバージョン管理される成果物であり、この対応が依存関係の記録）。

このSkillの価値は「AIが速く書けること」ではなく、**会議の速度でユーザーの頭の中を構造化データにすること**にある。だから聞き方が本体で、ファイル書き込みは結果でしかない。

## 全体の流れ

1. 対象プロジェクトフォルダを確認し、既存の用語集を探す
2. **登録する用語をユーザーに確定させる**（会議メモ等から作る場合。ここを飛ばさない）
3. ヒアリングして各用語の中身を埋める
4. `scripts/new-id.mjs` でIDを採番する
5. 下書きJSONを書き、`scripts/glossary-write.mjs` で検証＋正規形書き出しをする
6. 未記入と警告をユーザーに報告する

初回のみ、Skillディレクトリで `npm install`（ajv が必要）。`ajv が見つかりません` と言われたら実行する。

## 1. 既存の用語集を探す

**用語集はプロジェクトにつき1つ。** ファイル名は識別子ではないので、名前ではなく中身の `type` で判別する。プロジェクトフォルダ直下の `*.json` を読み、`"type": "glossary"` のものを探す。

- 見つかった → そのファイルに追記する（新しいファイルを作らない。2つあると単一性違反でアプリが用語解決を止める）
- 見つからない → 新規作成する。`title` はプロジェクト名から提案してユーザーに確認する

**アプリでそのプロジェクトを開いたまま作業しない。** アプリは自動保存でファイルを書き戻すため、同時編集になると片方の変更が消える。作業前に「アプリで開いているなら閉じてください」と一言伝える。

### 既存の用語を頭に入れてから候補を出す

用語集が見つかったら、**全用語の `name` と `aliases` を読んでから手順2に進む。** 追記のとき、
これを飛ばすと既存とかぶる語を新規登録してしまう。

手順2で候補を出す前に、各候補を既存の name / aliases と照合する（NFKC正規化・大文字小文字は
同一視して比較する）。かぶった候補は「新規候補」として出さず、**別枠でユーザーに確認する**:

| かぶり方                                           | ユーザーに確認すること                                                                                            |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 既存の `name` と同じ                               | 同じ概念か。同じなら登録しない（同名2件は宣言の矛盾で、アプリで赤表示になる）。別概念なら、どう呼び分けるかを聞く |
| 既存の `aliases` に入っている                      | 既に別名として登録済み。正式名に昇格させたいのか、そのままでよいかを聞く                                          |
| 部分的に含む・含まれる（「受注」と「受注データ」） | 別概念か、片方が他方の言い換えか。言い換えなら **既存用語の `aliases` に追加**して新規登録しない                  |

三つ目が最も多く、かつ最も見落としやすい。**新規登録ではなく既存の alias に足すのが正解である
ケースが頻出する** ので、迷ったらユーザーに聞く。alias に足せば表記ゆれ検知の燃料が増え、
新規登録すると重複用語が静かに増える——ここも「入れるのは1往復、消すのは後で何度も」の非対称
が効く。

**新規作成の場合はこの手順は不要**（既存が無いので照合対象がない）。

## 2. 登録する用語を人間に確定させる

会議メモ・議事録・既存の仕様書を渡されて「ここから用語集を作って」と言われたときは、**抽出した候補を一覧で提示し、登録するものをユーザーに確定させてから書き込む。** 抽出した端から登録しない。

理由は、**どの語を用語集に載せるかが用語集の設計そのもの**だから。用語集は他ツールがIDで参照するハブで、載せた語は「この会話ではこの言葉を正式名として扱う」という宣言になる。文書に出てくる名詞をAIが機械的に拾った結果とは意味が違う。ユーザーだけが「これは用語、これはただの言い回し」を判断できる。

副作用も具体的で、載せすぎた用語は後から人間が1件ずつ消す作業になり、消えたIDの参照切れも発生し得る。**入れるのは1往復、消すのは後で何度も、という非対称がある。**

聞き方は1往復で済ませる。候補を列挙し、根拠（文書中のどの記述から拾ったか）を短く添えて、削るものを聞く。

```
メモから12語を候補として拾いました。登録するものを選んでください（「全部」でもOK）。
1. 受注票 — 「営業が受注票を起票する」
2. 引当 — 「受注に対して在庫を確保する作業」
...
不要なものだけ番号で教えてください。
```

**候補には未決の語も含める。** 「仮引当／本引当を分けるかは次回持ち越し」のように議論が割れた語こそ、`undecided` ＋定義空で登録する価値がある（決まっていないことがアプリ上に残り続ける）。ただしこれも登録するかはユーザーが決める。

**確認が取れない状況（非対話実行など）では、書いたうえで報告に「こちらの判断で入れた語」を明示する。** 黙って確定させないことが目的なので、聞けないなら事後に見せて削れるようにする。

**ここで確定させるのは「どの語を載せるか」だけ。** 各用語の中身（種別・定義）まで一語ずつ許可を取りに行かない。中身の埋め方は手順3。

## 3. ヒアリング

埋めるのは `name` / `kind` / `definition` / `aliases`（＋必要なら `notes`）。

### 埋まらない項目は埋まらないまま書く

ここが最重要。**ユーザーが即答できない項目を粘って聞き出さない。** `kind` は `undecided`、`definition` は空文字、`aliases` は空配列のまま書いてよい。

理由: アプリ側は `kind === "undecided"` と `definition === ""` を warning としてセル単位で可視化する。埋まっていないという事実そのものが「次に決めるべきこと」の情報であり、AIが憶測で埋めるとその情報が消える。**決めていないことを消せなくするのがこのツールの思想** で、AIの穴埋めはそれを正面から壊す。

「たぶんこういう意味ですよね？」と確認するのは良い。ユーザーが「そう」と言えば確定、「まだ決めてない」と言えば空のまま。**AIの推測をユーザーの決定として記録しない。**

### ただし「転記」は推測ではない

空にするのは**推測**（出典がなく、AIが補ったもの）であって、**転記**（ユーザーの発言や渡された文書に書いてあることを写したもの）ではない。

メモに「実際にモノが出ると『出荷済』になる」と書いてあるなら、`出荷済` の定義は「実際にモノが出た状態。」でよく、種別も `state` でよい。**それは既に人間が決めて書いたことで、空にすると情報が消えるだけ**。未記入の warning は「これから決めること」を指すためのもので、書いてあることまで未記入にすると宿題リストがノイズだらけになり、本当の未決が埋もれる。

判定は「出典を指させるか」で行う。

| 状況                                               | 扱い                                        |
| -------------------------------------------------- | ------------------------------------------- |
| 文書・発言にそう書いてある                         | 転記する。文言もなるべくそのまま使う        |
| 文書に用語だけ出てきて、何かは書かれていない       | 空にする                                    |
| 文書に複数の読み方が混在していて、どちらとも取れる | 空にして、両方の読み方を `notes` に残す     |
| 会議で「未決」「持ち越し」と明記されている         | 空にして、何が割れているかを `notes` に残す |

`notes` は空にする判断の理由を残す場所として使う。「なぜ空なのか」が書いてあれば、次に見た人がゼロから議論をやり直さずに済む。

### kind の選び方

| 値          | 意味                                                               |
| ----------- | ------------------------------------------------------------------ |
| `actor`     | 人・役割・組織（申請者、承認者）                                   |
| `state`     | 状態（承認待ち、失効）                                             |
| `event`     | 出来事・操作（申請する、差し戻し）                                 |
| `screen`    | 画面・帳票の画面名                                                 |
| `data`      | データ・帳票（受注データ、見積書）                                 |
| `other`     | **検討したうえで**どれでもない（＝これで完成、warning にならない） |
| `undecided` | **まだ決めていない**（＝warning。後で埋める）                      |

`other` と `undecided` の違いは「決めたかどうか」。迷ったら `undecided` を選ぶ。`other` は「考えた結果どれでもなかった」という決定の記録なので、AIが勝手に付けてよい値ではない。

### aliases は表記ゆれ検知の燃料

`aliases` は「この表現を見たら正式名に直すべき」という登録者の明示的な意図で、アプリは他ツールの自由テキストに対してこれを部分一致で照合する。だから**実際に現場で使われている言い方**を聞く価値が高い。

- 良い聞き方: 「この用語、会議で別の言い方をされることはありますか？」「略称や旧称はありますか？」
- 入れないもの: AIが思いついただけの同義語。誤検知になり、指摘の信頼を落とす
- `name` は照合キーにならないので、正式名を alias に重複登録しない

### 聞き方の設計

会議の速度が前提なので、1問1答で往復を重ねない。**複数の用語をまとめて聞き、1回の返信で複数埋まるようにする。**

例: 「以下の5つについて、定義が言えるものだけ書いてください。分からないものは飛ばしてOKです」と列挙する。ユーザーが3つだけ答えたら、残り2つは `undecided` ＋空定義で登録する。

**登録対象の確定（手順2）とは別の往復にする。** 何を載せるかはユーザーの決定なので確定が要るが、各項目を埋めるかどうかは「今わかる範囲で」でよい。ここで粘ると会議が止まる。

## 4. ID採番

```
node scripts/new-id.mjs 5
```

**IDを自分で書かない。** 必ずこのスクリプトの出力をそのまま使う。連番も禁止（アプリとAIが並行して要素を追加する設計なので、連番は必ず衝突する）。既存用語のIDは絶対に変更しない（不変IDであり、他ツールがこのIDで参照している。書き換えると参照切れになる）。

## 5. 書き込み

下書きJSONを一時ファイルに書き、スクリプトに渡す。**正規形（キー順・インデント・改行コード）はスクリプトが担保するので、下書きの整形に労力を割かなくてよい。**

```
node scripts/glossary-write.mjs --in <下書き.json> --out <プロジェクト>/glossary.json
```

既存ファイルへの追記は、既存の内容を読んで下書きに含め、全体を書き出す。**既存の `terms` の並び順を変えない**（配列順＝UIの表示順が正であり、並べ替えは意味のない diff を生む）。追加は末尾。

検証だけしたいときは `--check <ファイル>`。

スキーマはスクリプトが実行時に探索する。**この Skill は `schemas/glossary.schema.json` に自分のコピーを持つ**ので、facet のチェックアウトが無いマシンでも見つかる（コピーは facet の原本とのバイト一致をアプリのテストが強制している。ズレたまま古い版で検証が通ることはない）。それでも見つからないと言われたら `--schema <path>` か環境変数 `FACET_GLOSSARY_SCHEMA` で指定する。

構造（詳細は `schemas/glossary.schema.json` を読む。スキーマが正）:

```json
{
  "schemaVersion": 1,
  "type": "glossary",
  "title": "○○プロジェクト 用語集",
  "terms": [
    {
      "id": "term_Xk3mPq7ZaB",
      "name": "承認待ち",
      "kind": "state",
      "definition": "申請が提出され、承認者の判断を待っている状態。",
      "aliases": ["承認待", "ペンディング"],
      "notes": ""
    }
  ]
}
```

全キー常在。欠損ではなく空の値で未記入を表す（`definition: ""` / `aliases: []` / `notes: ""`）。

スキーマ検証に落ちたら、アプリはそのファイルを開けない（レベル1拒否）。エラーを読んで直し、再実行する。

## 6. 報告

スクリプトの出力をそのまま流さず、ユーザーが次に動ける形にして伝える。

- 登録した用語（名前と種別）
- **未記入の一覧**（未分類・未定義がそれぞれ何件・どれか）。これは失敗の報告ではなく次回の宿題リストとして渡す
- 整合性の警告があれば、何が衝突しているかと、判断が要る点

警告は「アプリで赤く出るが、ファイルは開ける」状態。alias の重複などは、どちらを正とするかがユーザーの判断なので、勝手に片方を消さない。

## やらないこと

- **MCP的な書き込みツールを作らない。** アプリとの接点はファイルだけ（決定済み。蒸し返さない）
- **アプリ側の検証を代行しない。** 参照切れ検知などは他ツール側の仕事で、このSkillの管轄外
- **既存データの勝手な整形・並べ替え・言い換えをしない。** ユーザーが書いた定義文をAIが「きれいに」書き直すと、Git diff が仕様の変更履歴として読めなくなる
