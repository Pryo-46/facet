# 課題ツリー登録

仕様整理ツール（Tauri製アプリ）の課題ツリーファイルを、会話の内容から組み立てる。**PoCで「試さないと分からないこと」を課題として分解し、仮説と検証の履歴を持たせる**のがこのツールの用途である。

**このSkillが紐づく対象: `type: "issueTree"` × `schemaVersion 4`。** スキーマが改訂されたらこのSkillも追従させる（アプリとSkillは別々にバージョン管理される成果物であり、この対応が依存関係の記録）。旧版のファイルは、版番号だけが上がって開かれる——**互換の変換は用意しない。** v4 の形でなければ移行後の検証で弾かれて開けない（読み替えを足すと、もう無いキーがデータの中に別の顔で生き残るため）。**v3 との違いは `events` の件数だけである**——課題の旗も仮説の判断も **0 件か 1 件**（`maxItems: 1`）になった。判断が2件以上ある v3 のファイルは開けない。Skill は 4 で書く。

**問いと抑制の導出（`scripts/generated/derive.mjs`）は生成物である（`npm run gen:skills` が `scripts/generated/` へ作る）。手で編集しない。** 直すときはアプリ側の原本（`src/modules/issue-tree/derive.ts`）を直す（ズレは `scripts/gen-skills.test.mjs` が検知する）。

**このSkillの材料はシーケンスと同じく、直前までの会話そのものである。** 会話には既にAIの発言が混ざっているので、**何が人間の決定で何がAIの推測か**の線引きが最も重要になる。課題ツリーではその線が `feedbacks`（記録）と `events`（判断）の境目に現れる（後述）。

## 全体の流れ

**2つのフェーズがある。**

| | やること |
| --- | --- |
| **フェーズA：木を起こす** | 会話から `issues` + `hypotheses` を組んで書き出す。`events` は会話で人間が下した判断だけ転記 |
| **フェーズB：問いを詰める** | 立っている問い（仮説なし／未決／保留／FB待ち）を列挙してまとめて聞く |

フェーズAは「作って」と言われたら**確認を挟まずに実行する**。フェーズBは書き出した直後に**1回だけ提案する**。

## 1. 対象を決める

**課題ツリーはプロジェクトに何本あってもよい**（`singleton: false`）。1ファイル＝1本の木（単一ルート）で、根はPoCテーマなど「今回の検証の題」に当たるものを置く。

- **既定は新規作成。** プロジェクト内の `type: "issueTree"` を探して追記しない
- **既存への書き足しは、ユーザーが名指ししたときだけ**（「あの決済PoCのツリーに検証結果を入れて」）。名指しがあれば手順8（既存ファイルへの書き足し）へ進む。無ければ新規
- ファイル名は `title` 由来。**既存と衝突したら報告して確認する**（勝手に上書きしない）
- **単一性の警告は出さない。** 課題ツリーが複数本あるのは正常な状態である

**アプリでそのプロジェクトを開いたまま作業しない。** アプリは自動保存でファイルを書き戻すため、同時編集になると片方の変更が消える。作業前に「アプリで開いているなら閉じてください」と一言伝える。

### 木は1本に収める

**単一ルートである。** 会話に別のPoCテーマが混ざっていたら:

- **会話で最も長く詰められたテーマ**を採る。同程度なら**先に通しで語られたほう**
- 残りは**書かない**。報告で「認証まわりの話も出ていたので、必要なら別ファイルで作ります」と伝える
- どちらを根にしたかを報告に書く

**勝手に複数ファイルを作らない。** 外れたテーマを消すのはユーザーの手作業になる。

### `title` を決める

会話から付けて**報告で伝える**（確認は取らない。違えばユーザーがアプリで直せる）。`title` はアプリのファイル一覧に出る表示名なので、後から人間が読んで何のPoCか分かる必要がある。

## 2. 課題（issues）を組む

`{ id, parentId, text, events }` の配列。**全キー常在**（欠損ではなく空の値で「未記入」を表す）。

- `parentId` は親課題の `id`。根だけが `null`
- **配列順が兄弟の表示順の正**。**厳密でなくてよいが、DFS 行きがけ順（親→子の深さ優先。親のすぐ後ろにその子）で書いておくこと。** 書き出しスクリプトは配列順を触らず、アプリも**開くだけでは整えない**（並べ替えが走るのは利用者がアプリで編集して自動保存が走ったとき）。乱れた順のまま置くと、利用者が後で1箇所直した瞬間に配列全体が並び替わり、**大きな無意味 diff** が出る
- `text` は会話の言葉をそのまま使う。明示的な改行（`\n`）は文言の一部として永続化される

### 課題と仮説の書き分け

| | 何か |
| --- | --- |
| **課題** | **観測された事実**、または**望む状態とのギャップ**。「決済のレイテンシが読めない」「オフラインで動くか分からない」 |
| **仮説** | **支持・棄却を判定できる主張**。「既存SDKのままで 200ms を切れる」「ローカルキャッシュだけで運用に足りる」 |

**ただし入力時に厳密な区別を強制しない。** 会話の言葉が課題寄りか仮説寄りかで迷ったら、迷ったまま置いてよい——**検証イベントを付ける段階で「支持・棄却を判定できる文か」が自然に問われる**ので、そこで直せばよい。区別の議論で会議を止めない。

### 課題の `events`（旗）

課題に付けられるイベント（旗）は**見送り（`deferred`）と解決（`resolved`）の2種**である（支持・棄却・保留は仮説にしか付かない）。

| `kind` | 意味 |
| --- | --- |
| `deferred` | 見送り（今回は追わない。次のPoC選定で拾い直すのか、本開発へ送ってPoC中は戻らないのかは `kind` では区別せず、`note` に書く） |
| `resolved` | 解決（出てきたソリューションで解決できる。これ以上の検証は不要）。**ユーザーが解決したと言ったときだけ立てる**——見送りと同じ規律で、AI が判断しない（これは決定の記録である） |

**「本開発送り」という種別は無い。** 本開発へ引き渡すつもりの見送りも `deferred` で、そのことは `note` に書く——見送りの行き先で `kind` を分けても俯瞰の読みは変わらず、選ぶ側が迷うだけだった。

**見送りと解決は意味が逆だが、どちらも配下の問いを抑制する。同時に立ててはならない。** 旗を差し替えるとき（見送り → 解決 など）は前の1件を消してから足す——列に2件並べない。

**旗は、枝の最上位の課題に一度だけ付ける。配下へコピーしない。** 配下の問いが立たなくなる（抑制）のは**祖先を遡る導出**であって、子に持たせる値ではない。コピーすると、旗を外したときに子だけが取り残されて嘘のデータになる。

**課題の `events` は追記専用ではない。** アプリでは旗は**入り切りのトグル**で、戻すと**その1件が消える**（解除を表す種別は無い）。「一度立てて戻した」という履歴も、そのとき書いた理由も残らない。**この列は 0 件か 1 件である**——v4 でスキーマが `maxItems: 1` を課したので、2件以上あるファイルは検証で落ちて**開けない**（v3 までは読めてしまい、2件目以降は画面に出ないデータとして残っていた）。**仮説の `events` も v4 から同じ規律である。**

**イベントも全キー常在である。** 1件は `{ kind, note, date }` の3キーちょうどで、**`note` と `date` はスキーマ上 required**——「理由が無いからキーごと省く」はできない（`kind` だけのイベントはスキーマ検証で落ちる）。`note`（理由）は**空文字を許す**ので、会話に理由が無ければ `"note": ""` と書く。**`date`（`YYYY-MM-DD`）は空文字を許さない。手で打たせない**——会話の日付が分かればそれ、分からなければ今日を入れる。

## 3. 仮説（hypotheses）を組む

`{ id, issueId, title, detail, value, asks, feedbacks, events }` の配列。**全キー常在。**

- `issueId` はぶら下がり先の課題。**中間の課題にも付けてよい**（当たりをつける段階の入力を潰さないため）。ただし「仮説なし」の問いが立つのは**子を持たない課題**だけ
- **`title`＝ソリューション仮説（何を作るか）／`value`＝価値仮説（なぜ効くか）は別の主張である。** 会話に片方しか無ければもう片方は空のままにする。**埋めるために推測しない**
- **`detail`** は作り方の詳細。空でよい（空でも warning にならない）
- `title` / `detail` / `value` は会話の言葉をそのまま使う

### `asks`（聞きたいこと）と `feedbacks`（FB）

**`asks`** は「レビューで何を聞けば支持・棄却が判定できるか」の配列（`{ id, text }`）。**会話に問いが出ていれば書き、出ていなければ空配列。** `id` は `node scripts/new-id.mjs 2 --prefix ask` で採番する。

**`feedbacks`** は `{ askId, text, by, sentiment, date }` の配列。

- `by`（誰の発言か）は**会話から取る。分からなければ空文字。推測しない**
- `sentiment` は `like`（賛成）／`concern`（懸念）／`question`（質問）／`note`（ただのメモ・分類しない）の4語。**迷ったら `note`**——嘘の分類を残さない
- `askId` は**用意した問いに答えているときだけ**その `id` を入れる。それ以外は `null`（用意した問いの外から来る指摘こそ重いので、紐づけを強制しない）
- `date`（`YYYY-MM-DD`）は**必ず入れる**。会話の日付が分かればそれ、分からなければ今日

**文言のある問い（`asks`）に FB が1件も無ければ「FB待ち」が立つ**（`derive.ts` の導出。文言が空の問いは数えない）。

### `events`（判断）は 0 件か 1 件

**0件＝未決。判断は高々1件で、差し替えでき、取り消して未決へ戻せる。**

**v3 まではここが追記専用だった。** 覆った判断の履歴が残ることが利点だったが、実機で一巡した結果**間違えて付けた判断を消せない**ことのほうが高くつくと分かり、v4 で反転した——課題の旗と同じ規律に揃えた形である。**差し替えは前の1件を消してから足す。列に2件並べない**（並べると「いまどちらが有効か」が列の中身に依存し始める）。

| `kind` | 意味 |
| --- | --- |
| `supported` | 支持（この仮説は成り立つ） |
| `rejected` | 棄却（成り立たない） |
| `onHold` | 保留（見たが判断できなかった。**理由を `note` に必ず書く**。空の保留は次のレビューに何も渡さない） |
| `deferred` | 見送り（今回は追わない） |

**判断の語彙はこの4つで尽きる。** 画面に出る5語目の「未決」は `events` が0件であることから導出される値で、`kind` としては存在しない。**「検証したのか、実験なしで決めたのか」を `kind` で書き分けない**——どちらも `supported` / `rejected` で、経緯は `note` に書く。

**ステータスのフィールドを作らない。** 現在ステータスは `events` の最新要素から導出される。`kind` の隣に `status` を書き足そうとしても `additionalProperties: false` で弾かれる。見送り回数のような集計もこの列から導出できるので、別フィールドを持たない。

**イベントも全キー常在である**（課題側と同じ）。1件は `{ kind, note, date }` の3キーちょうどで、**`note` と `date` はスキーマ上 required**。根拠が無くても `note` は**空文字で置く**（`"note": ""`）——キーごと省くとスキーマ検証で落ちる。**`date`（`YYYY-MM-DD`）は空文字を許さない。** 会話の日付が分かればそれ、分からなければ今日。

**「今回も見送り・理由も同じ」なら何も触らない**（いまの1件が引き続き有効）。

**覆った経緯は残らない。** 差し替えると前の判断とそのとき書いた理由は消える——受け入れた上での選択で、経緯を残したいなら `feedbacks` か `note` に書く（`feedbacks` は何件でも並ぶ）。

### `feedbacks` は判断待ちの下書きではない。記録である

`feedbacks` は**移動も昇格もしない。記録としてその場に残る。**

**判断の理由（`events[].note`）は人が自分の言葉で書く。** AIが FB の文言をそのまま `note` へ写さない——判断の根拠を機械的に移す経路は持たない。

**AIがこれを勝手に判断イベントへ昇格させない。** 会話に出たSHの発言は `feedbacks` へ入れ、`events` へ入れるのは**人間が下した判断だけ**である。

| 状況 | 扱い |
| --- | --- |
| ユーザーが判断を言った（「これは支持でいい」） | `events` を**その1件にする**（既にあれば差し替え） |
| AIが提案し、**ユーザーが同意した** | `events` を**その1件にする**（同上） |
| レビューで出た指摘・感想（「表示が遅い気がする」） | **`feedbacks` に入れる** |
| AIが提案しただけ／議論に出ていない | **どちらにも入れない** |

## 4. ID採番

```
node scripts/new-id.mjs 12                    → issue_XXXXXXXXXX を12件
node scripts/new-id.mjs 3 --prefix hypothesis → hypothesis_XXXXXXXXXX を3件
node scripts/new-id.mjs 2 --prefix ask        → ask_XXXXXXXXXX を2件
```

**IDを自分で書かない。** 必ずこのスクリプトの出力をそのまま使う。連番も禁止（アプリとAIが並行して要素を追加する設計なので、連番は必ず衝突する）。

**既存の `id` は絶対に変更しない。** 不変IDであり、`parentId` と `issueId` がこれを参照する。

## 5. 書き込み

下書きJSONを一時ファイルに書き、スクリプトに渡す。**正規形（キー順・インデント・改行コード）はスクリプトが担保するので、下書きの整形に労力を割かなくてよい。**

**下書きは対象プロジェクトフォルダの外に置く。** 中に置くと、アプリのファイル一覧に下書きが本物として並ぶ。

```
node scripts/issue-tree-write.mjs --in <下書き.json> --out <プロジェクト>/<タイトル>.json
```

検証だけしたいときは `--check <ファイル>`。終了コードは 0＝成功（警告はあり得る）／1＝スキーマ検証失敗／2＝使い方の誤り。**0 でも要対応の集計と整合性の警告は出ている**ので、終了コードだけを見ず標準出力を読むこと。

**このスクリプトは配列順を並べ替えない。** 兄弟順・仮説の表示順は配列順が正だが、DFS 行きがけ順への整えは**アプリの編集コマンドが行う**——つまり利用者がアプリで**編集して自動保存が走ったとき**であり、**開くだけでは整わない**。

だから**下書きの時点で DFS 行きがけ順（親→子の深さ優先）に並べ、仮説はぶら下がり先の課題の順に並べておくこと。** 並びが乱れていても意味は変わらないし壊れもしないが、そのままディスクに残るので、**利用者が後で1箇所直した瞬間に配列全体が並び替わって大きな無意味 diff が出る**。Git diff を仕様の変更履歴として読めなくするのがこのプロジェクトで最も避けたい形である。

スキーマ検証は同梱の生成物（`scripts/generated/validate.mjs`）が行う。**スキーマの差し替えはできない**——検証は生成時に焼き付いており、アプリが開けるかどうかの基準は同梱スキーマそのものだからである。`schemas/issue-tree.schema.json` は正規形のキー順を決めるために読まれ、facet の原本とのバイト一致はアプリのテストが強制している。

構造（詳細は `schemas/issue-tree.schema.json` を読む。スキーマが正）:

**下のブロックは `sample-project/課題ツリー.json`（お手本）から逐語で抜いた実例。**

```json
{
  "schemaVersion": 4,
  "type": "issueTree",
  "title": "適性検査サービス連携PoC",
  "issues": [
    { "id": "issue_uFL1ENjyRj", "parentId": null, "text": "適性検査サービス連携（PoCテーマ）", "events": [] },
    { "id": "issue_O2uN5LnCT8", "parentId": "issue_uFL1ENjyRj", "text": "受検案内の再送導線", "events": [] }
  ],
  "hypotheses": [
    {
      "id": "hypothesis_m9ZvA5LtyQ",
      "issueId": "issue_O2uN5LnCT8",
      "title": "再送は応募者から再送依頼が来る前提でよい",
      "detail": "",
      "value": "現行の紙の案内でも、再送は問い合わせ起点で回っている",
      "asks": [],
      "feedbacks": [
        { "askId": null, "text": "案内メールが迷惑メールに入る例が月に数件ある。依頼を待つ運用で辞退につながらないか", "by": "採用担当", "sentiment": "concern", "date": "2026-08-24" }
      ],
      "events": [
        { "kind": "onHold", "note": "応募者からの再送依頼の頻度が分からず、PoC では判断を持ち越す", "date": "2026-08-25" }
      ]
    }
  ]
}
```

### 警告が出たときの扱いは、出どころで分ける

| 出どころ | 扱い |
| --- | --- |
| **今回このSkillが書いた部分**の警告（ID重複、`parentId` の参照切れ、ルートが複数、仮説のぶら下がり先が無い等） | **自分の書き間違い。直して再実行する**（ユーザーに聞かない） |
| **既存ファイルに元からあった**警告 | **報告して確認する。勝手に直さない**（削除の残骸か作業途中かはユーザーしか判断できない） |

## 6. 報告

スクリプトの出力をそのまま流さず、ユーザーが次に動ける形にして伝える。

- 作ったファイルのパスと `title`
- 課題と仮説の件数。**根に採らなかったテーマ**があればその旨
- **`feedbacks` に入れたフィードバック（判断へは昇格させていないこと）**
- **`value` / `detail` を空にしたもの（会話に無かったこと）**
- `⚠ 要対応 N（仮説なし N ／ 未決 N ／ 保留 N ／ FB待ち N）`（0 の内訳は出ない）
- 旗を掲げた課題があるときだけ `見送り N（見送り配下の問いは要対応に数えません）` と `解決 N（解決配下の問いは要対応に数えません）` の行が続く（0件では出ない。字面の正は `scripts/derive.ts` の `issueEventLine` / `ISSUE_EVENT_NOTES`）
- 整合性の警告があれば、何が衝突しているかと判断が要る点
- **フェーズBの提案（1回だけ）**

**`⚠ 要対応` が並ぶのは正常である。** 決めていないことを消せなくするのがこのツールの思想であり、要対応はその思想が働いている証拠にほかならない。

## 7. フェーズB（問いを詰める）

書き出した直後に**1回だけ**提案する。

> 「要対応が6件あります。続けて『未決』も詰めますか？」

**断られたら繰り返さない。既存ファイルを開いて要対応の件数を数えて回らない。** 禁じられているのは催促であって、作業の続きの提案ではない——この線を越えないこと。

進め方:

1. **立っている問いを、アプリの画面と同じ文言で列挙する。** 言い換えない

   | 対象 | 立つ問い | 立つ条件 |
   | --- | --- | --- |
   | 課題 | 仮説なし | 子を持たない課題に仮説が1件も無い |
   | 仮説 | 未決 | `events` が0件 |
   | 仮説 | 保留 | 最新が `onHold` |
   | 仮説 | FB待ち | 文言のある問い（`asks`）に FB が1件も無い |

   **祖先の課題に旗（見送り／解決）が立っている配下には、問いが立たない**（抑制は導出）。旗が立った枝を掘り返して聞かないこと。

2. **まとめて聞く。** 木の並び順ではなく「同じ答えになりそうなもの」で束ねる

   ```
   この3件はどれも決済SDK まわりの仮説です。今回のPoCでは全部見送りますか？
   違うものだけ教えてください。
   ```

   1問1答で往復すると会議が止まる。

3. **答えが出ないものには判断を書かない。** `events` が空のまま＝「まだ検証していない」であり、これは情報である

4. **旗（`deferred`＝見送り／`resolved`＝解決）は、ユーザーが見送る・解決したと言ったときだけ。** AIが判断しない——これは**決定の記録**だからである。迷ったら書かない

## 8. 既存ファイルへの書き足し

「あのツリーに検証結果を入れて」と言われたときの手順。

1. 既存ファイルを読み、**どのツリーか**をユーザーに確定させる（名前が似ているものがあるので勝手に選ばない）
2. 手順7と同じ要領で聞く
3. **既存の JSON 全体を下書きに含め、追記する要素だけを足して**書き出す（既存要素の `id` は採番し直さない）

**守ること:**

- **`id` を変えない**（不変ID。`parentId` / `issueId` が参照している）
- **`events` は課題も仮説も 0 件か 1 件。** 判断や旗を差し替えるときは前の1件を消してから足す——列に2件並べると検証で落ちて開けなくなる。**ユーザーが言っていない判断を消さない**（取り消しは決定の記録であり、AI が勝手に外さない）
- **`issues` / `hypotheses` の配列順を変えない**（兄弟順・表示順の正本。並べ替えは意味のない diff を生む）
- **`title` を書き換えない**（アプリのファイル一覧に出る表示名。「ついでに」整えると表示名が黙って変わる）
- **触っていない要素を1バイトも変えない**（「ついでに」文章を整えると、Git diff が仕様の変更履歴として読めなくなる）
- 書き出したら `git diff` に出る行が意図した範囲に収まっているかをユーザーに伝える

## やらないこと

- **AIの推測を判断イベントにしない。** `events` に載るのは人間が下した判断だけ。迷いは `feedbacks` へ
- **ユーザーが言っていない判断を勝手に消さない・差し替えない。** 取り消しも差し替えも決定の記録である（立てるときと同じ規律）
- **`feedbacks` を勝手に消さない。** FBが残っていること自体が「レビューを締めていない」の表現である
- **ステータスのフィールドを足さない。** 現在ステータスは `events` の最新から導出する（手動ステータスは更新忘れで嘘をつく）
- **旗を配下へコピーしない。** 抑制は祖先を遡る導出である
- **問いの類型を増やさない。** 4つ（仮説なし／未決／保留／FB待ち）はスキーマ固定で、どれが立つかは木の形と件数から導出される。ユーザーやAIが増やせるようにした瞬間、「問いのセットが完成しているか」をツールが判定できなくなり、網羅の担保が消える
- **`value` / `detail` / `asks` を埋めるために推測しない。** 空は warning にならない
- **解決の旗はユーザーが解決したと言ったときだけ立てる。** 見送りと同じ規律——AIが判断しない。これは決定の記録である
- **FB の文言を判断の根拠へ写さない。** 判断の理由（`events[].note`）は人が自分の言葉で書く
- **1ファイルに複数の木を入れない**（単一ルート）
- **座標・行番号・幅をデータに入れない**
- **MCP的な書き込みツールを作らない。** アプリとの接点はファイルだけ（決定済み。蒸し返さない）
- **既存データの勝手な整形・並べ替え・言い換えをしない**
- **網羅性を主張しない。** 「これでPoCの論点は全部出ました」と言わない
- **要対応を催促しない。** フェーズBの提案は書き出し直後に1回だけ
