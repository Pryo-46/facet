# デシジョンテーブル登録

**このフォルダのデータの読み方は `facet:read-project` が持つ。** 既存のファイルを読んでから書くときは先にそちらを見ること。

仕様整理ツール（Tauri製アプリ）のデシジョンテーブルファイルを、会話の内容から組み立てる。

**このSkillが紐づく対象: `type: "decisionTable"` × `schemaVersion 1`。** スキーマが改訂されたらこのSkillも追従させる。

**行の整列と組み直し（`scripts/generated/rows.mjs`）と欠落の集計（`scripts/generated/missing.mjs`・`missing-tally.mjs`）は生成物である。手で編集しない。** 直すときはアプリ側の原本（`src/modules/decision-table/rows.ts` ほか）を直す。

## 全体の流れ

| フェーズ | やること |
| --- | --- |
| **フェーズA：表を起こす** | 会話から条件と結果を組み、決まった組み合わせの結果だけを書いて書き出す |
| **フェーズB：空欄を詰める** | 未記入の結果を列挙してまとめて聞き、答えを埋める |

フェーズAは「作って」と言われたら**確認を挟まずに実行する**。フェーズBは書き出した直後に**1回だけ提案する**。

## 1. 対象を決める

**デシジョンテーブルはプロジェクトに何本あってもよい。**

- **既定は新規作成。** プロジェクト内の `type: "decisionTable"` を探して追記しない
- **既存への書き足しは、ユーザーが名指ししたときだけ**。名指しがあれば手順8へ進む
- ファイル名は `title` 由来。**既存と衝突したら報告して確認する**（勝手に上書きしない）

**アプリでそのプロジェクトを開いたまま作業しない。** アプリは自動保存でファイルを書き戻すため、同時編集になると片方の変更が消える。作業前に「アプリで開いているなら閉じてください」と一言伝える。

`title` は会話から付けて**報告で伝える**（確認は取らない）。

### 表が向く仕様か

表が効くのは、**条件が有限に列挙でき、条件が同時に評価され、結果が離散的な**仕様だけである。

| 仕様の形 | 振る舞い |
| --- | --- |
| 条件がどれも数個の値に分かれ、全部を見てから結果が決まる | **このSkillで表にする** |
| 「まず A で分け、A のときだけ B を見る」のように順に分ける | 表にもできるが、報告で**ロジックツリーの方が読みやすい**と一言添える |
| 金額・日時などの連続値そのものが結果を決める | 閾値で値に区切れるか聞く。区切れなければ表にしない |
| 原因の洗い出し・場合分けの網羅 | **表にしない。** `write-logic-tree` を使う |

## 2. 条件と結果を組む

```json
{
  "conditions": [
    { "id": "cond_Xp2mQ9rT4k", "name": "会員か",       "values": ["はい", "いいえ"] },
    { "id": "cond_Kd4hR6yU1c", "name": "5000円以上か", "values": ["はい", "いいえ"] }
  ],
  "outcomes": [
    { "id": "out_Ab3xK9mP2q", "name": "送料", "choices": ["無料", "500円"] }
  ]
}
```

- **条件は同時に評価される軸だけにする。** 「会員か」と「会員ランク」のように片方が片方に含まれる軸を並べると、起こりえない行が大量に出る
- **値は条件ごとに漏れなく、重ならずに並べる。** 行は値の直積なので、値を足すたびに行が値の本数の比で増える（上限は1024行）
- **結果の選択肢は、会話に出た値だけを置く。** 決まっていない選択肢を「網羅のため」に足さない
- **`conditions` の配列順が行の並びを決める。** 左端の条件が最もゆっくり回る。会話で主軸になっている条件を左に置く
- **名前やラベルの空文字は「未記入」であって欠陥ではない。** 埋まらないものを推測で埋めない

## 3. 行を書く

**行は条件の値の直積であり、人が足したり消したりするものではない。** 行の数と並びはスクリプトが決める。

```json
{ "values": ["はい", "はい"], "impossible": false, "results": ["無料"] }
```

- **決まった組み合わせの行だけを書けばよい。** 書かなかった組み合わせは、結果が空の行としてスクリプトが補う
- `values` は `conditions` と同じ本数・同じ順で、各要素は `conditions[i].values` のラベルをそのまま書く
- `results` は `outcomes` と同じ本数・同じ順で、各要素は選択肢のラベルか空文字
- **結果の空文字は「未記入」（未決）である。** 会話で決まっていない結果を推測で埋めない
- **`impossible: true` はユーザーが「その組み合わせは起こりえない」と言ったときだけ立てる。** 起こりえないと決めるのは人であり、AIが条件の意味から推し量らない。迷ったら `false` のまま空欄にする
- 同じ組み合わせの行を2つ書かない

## 4. ID採番

```
node scripts/new-id.mjs 3 --prefix cond   → cond_XXXXXXXXXX を3件
node scripts/new-id.mjs 1 --prefix out    → out_XXXXXXXXXX を1件
```

**IDを自分で書かない。** 必ずこのスクリプトの出力をそのまま使う。連番も禁止。

**既存の `id` は絶対に変更しない**（不変ID）。行は ID を持たないので採番しない。

## 5. 書き込み

**下書きは対象プロジェクトフォルダの外に置く。** 中に置くと、アプリのファイル一覧に下書きが本物として並ぶ。

書き出しは目的で2つに分ける。**1回の書き出しで両方をしない。**

| 目的 | コマンド |
| --- | --- |
| 新しく作る・結果を書く・`impossible` を入り切りする | `node scripts/decision-table-write.mjs --in <下書き.json> --out <プロジェクト>/<タイトル>.json` |
| 条件・値・結果・選択肢を足す・消す・改名する | `node scripts/decision-table-write.mjs --in <下書き.json> --base <既存ファイル> --out <既存ファイル>` |

検証だけしたいときは `--check <ファイル>`。

終了コードは 0＝成功（警告はあり得る）／1＝スキーマ検証失敗・JSON 破損・書き出せない下書き／2＝使い方の誤り。**0 でも未記入の集計と整合性の警告は出ている**ので、終了コードだけを見ず標準出力を読むこと。

**exit 1 で書き出しを止める下書きは次の4つ。** どれも止めなければ、人が決めた結果が黙って消えるか、アプリが扱えない表になる。

| 標準エラーの見出し | 直し方 |
| --- | --- |
| `直積に当てはまらない行があります` | 値のラベルを `conditions` のものに揃え、`values` と `results` の本数を合わせる |
| `同じ組み合わせの行が食い違っています` | 1行にまとめる。どちらが正しいか分からなければユーザーに聞く |
| `記入済みの結果がN件失われます` | 件数と、どの定義の変更で失われるかをユーザーに伝える。了承を得たときだけ `--allow-loss` を付けて再実行する |
| `直積が行数の上限（1024行）を超えます` | 条件か値を減らす。表に向かない仕様かをユーザーと確かめる |

### `--base`（定義を変える）の決まり

- 下書きは既存ファイルの JSON 全体を写し、**`rows` には手を入れない**（違うと exit 2）
- 条件と結果は `id` で対応づく。**`id` を変えると別の条件として扱われ、結果が引き継がれない**
- 値と選択肢は、本数を変えなければ位置で対応づく（改名になる）。本数を変えるとラベルで対応づく
- **改名と追加・削除を1回に混ぜない。** 混ぜると改名した側がラベルで引けず、結果を失う。改名の書き出しと、増減の書き出しを分ける
- 条件を足すと、既存の結果が新しい値ぶん複製される。条件や値を消して結果が食い違う行は、空欄に落ちる
- 選択肢を改名すると、それを選んでいた結果セルも書き換わる

スキーマ検証は同梱の生成物（`scripts/generated/validate.mjs`）が行う。**スキーマの差し替えはできない。** `schemas/decision-table.schema.json` は正規形のキー順を決めるために読まれる。

**全キー常在である**（条件は `id` / `name` / `values`、結果は `id` / `name` / `choices`、行は `values` / `impossible` / `results` を必ず置く）。

### 警告が出たときの扱いは、出どころで分ける

| 出どころ | 扱い |
| --- | --- |
| **今回このSkillが書いた部分**の警告 | **自分の書き間違い。直して再実行する**（ユーザーに聞かない） |
| **既存ファイルに元からあった**警告 | **報告して確認する。勝手に直さない** |

## 6. 報告

スクリプトの出力をそのまま流さず、ユーザーが次に動ける形にして伝える。

- 作ったファイルのパスと `title`
- 条件・結果の本数と行数（`起こりえない` の行数を含む）
- **AI が起こした条件・値・選択肢**（会話に無かったもの）
- `⚠ 要対応 N（未記入 N ／ 名前なし N）`（アプリの帯と同じ文言。言い換えない。欠落が無ければ `要対応 0`）
- `--base` を使ったときは、組み直しで失われた結果の件数
- 整合性の警告があれば、何が衝突しているか
- **フェーズBの提案（1回だけ）**

**`⚠ 要対応` が並ぶのは正常である。** 決めていない組み合わせが空欄として残り、埋めるまで消えないのがこのツールの見方である。

## 7. フェーズB（空欄を詰める）

書き出した直後に**1回だけ**提案する。

> 「結果が未記入の組み合わせが5件あります。続けて埋めますか？」

**断られたら繰り返さない。既存ファイルを開いて未記入を数えて回らない。**

進め方:

1. **未記入の組み合わせを、行番号と条件の値で列挙する。** スクリプトの `未記入の結果:` が行番号を出す
2. **まとめて聞く。** 行番号順ではなく、「同じ答えになりそうな行」で束ねる

   ```
   #5〜#8 はどれも「会員でない」行です。送料はすべて500円でよいですか？
   違う組み合わせだけ教えてください。
   ```

3. **答えが出ないものは空のまま。**
4. **ユーザーが「その組み合わせは起こりえない」と言った行は、結果を空のまま `impossible: true` にする**
5. 既存の JSON 全体を下書きに含め、該当する行の `results` と `impossible` だけを変えて `--in/--out` で書き出す

## 8. 既存ファイルへの書き足し

1. 既存ファイルを読み、**どの表か**をユーザーに確定させる（名前が似ているものがあるので勝手に選ばない）
2. **既存の JSON 全体を下書きに含め**、変える部分だけを変える。定義を変えるなら手順5の `--base`、結果を変えるなら `--in/--out`
3. 守ること: **`id` を変えない** ／ **`title` を書き換えない** ／ **触っていない行の結果を1バイトも変えない**
4. 書き出したら `git diff` に出る行が意図した範囲に収まっているかをユーザーに伝える

## やらないこと

- **行を足す・消す提案をしない。** 行は導出物であり、増減は条件か値で表す
- **網羅性を主張しない。** 「これで全部の組み合わせが決まりました」と言わない。直積が網羅するのは組み合わせであって、条件の選び方ではない
- **未記入を催促しない。** フェーズBの提案は書き出し直後に1回だけ
- **`impossible` を推測で立てない**
- **効いていない条件を手で挙げて表を畳まない。** 畳みはアプリの導出で行う
- **座標・列幅・絞り込みの状態をデータに入れない**
- **MCP的な書き込みツールを作らない。** アプリとの接点はファイルだけ（決定済み。蒸し返さない）
- **既存データの勝手な整形・並べ替え・言い換えをしない**
